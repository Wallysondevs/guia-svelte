SvelteKit · Adaptadores

A Ana aprendeu a assar o pão e agora quer vender em três lugares: na porta da padaria, numa feira e pela internet. O pão é o mesmo; o que muda é a tomada de cada lugar. Com o site dela acontece igual: o código é um só, mas o Netlify, o Vercel e um servidor alugado esperam formatos diferentes de arquivo. Quem faz essa tradução é o adaptador — e é ele que decide se o seu projeto vira um site de arquivos parados ou um programa de verdade rodando num servidor.

Você vai aprender
  • O que é um adaptador e qual é o trabalho dele no build.
  • Onde o adaptador é configurado no SvelteKit 3 e por que não é mais no svelte.config.js.
  • O que o adapter-auto faz e qual aviso ele imprime quando não reconhece o lugar.
  • Como trocar para o adapter-node e como ler a saída do build.
  • O que existe dentro da pasta build/ gerada.
  • Quando o adapter-static serve e por que ele recusa rotas dinâmicas.
  • O que significa uma rota “prerenderizável” na hora de escolher o adaptador.
  • Os três avisos e erros reais desta configuração, com a mensagem copiada.
  • O custo de cada adaptador em manutenção e em dinheiro.

1. A ideia: o pão e a tomada

Um adaptador de tomada não muda a eletricidade: ele muda o encaixe. Você leva o mesmo aparelho para a Europa e ele funciona, desde que o encaixe seja o certo. No SvelteKit, o adaptador não muda o seu código: ele pega o resultado do build — HTML, JavaScript, CSS e as funções de servidor — e escreve esse resultado no formato que a plataforma de destino entende.

O motivo de existir é simples. Um site pode rodar de duas maneiras muito diferentes. Na primeira, alguém gera arquivos e os coloca num servidor que só entrega arquivos: nada é calculado na hora do pedido, o banco é consultado durante o build. Na segunda, existe um programa sempre ligado que recebe cada pedido, consulta o banco e monta a resposta na hora. Cada plataforma oferece uma dessas formas — às vezes as duas — e cada uma espera um formato próprio de entrada.

Sem adaptador, você escreveria esse formato à mão, e cada troca de plataforma seria um projeto novo. Com adaptador, a troca é uma linha. O preço é que essa linha muda o que o seu site consegue fazer: escolher errado faz o build falhar, ou pior, faz uma página que precisava de servidor virar arquivo parado.

2. O que é um adaptador, em uma frase

Adaptador é um pacote que roda no fim do build e responde a uma pergunta: como o meu site é servido neste lugar? A resposta vira uma pasta de saída. No adapter-node é a pasta build/, com um servidor Node pronto. No adapter-static é a pasta build/ com arquivos .html e nada mais. No adapter-netlify são funções no formato do Netlify; no adapter-vercel, no formato do Vercel.

Repare que o nome do pacote sempre começa com @sveltejs/adapter-. Isso não é decoração: é a convenção que o instalador usa para saber o que procurar. Os adaptadores oficiais cobrem os destinos mais comuns; para um destino esquisito existe a API de adaptadores, que é assunto de quem escreve pacote, não de quem publica padaria.

AdaptadorServe paraPrecisa de servidor?
adapter-autodescobrir a plataforma sozinhodepende do destino
adapter-nodeVPS, Docker, máquina própriasim
adapter-staticsite de arquivos paradosnão

3. Onde o adaptador é configurado

Esta é a mudança que mais confunde quem vem de tutorial antigo. No SvelteKit 2 o adaptador ficava no svelte.config.js. No SvelteKit 3 esse arquivo não é mais lido, e a configuração passou para o plugin dentro do vite.config.js:

import adapter from '@sveltejs/adapter-node';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [
		sveltekit({
			adapter: adapter()
		})
	]
});
import adapter
o pacote do adaptador escolhido. Trocar de destino começa aqui: outro pacote, outro nome.
sveltekit({ … })
o plugin que liga o SvelteKit ao Vite. É dentro dele que a configuração do Kit mora agora.
adapter: adapter()
a chamada que cria o adaptador. Os parênteses existem porque alguns adaptadores recebem opções: adapter({ out: 'dist' }).
plugins: [ … ]
a lista de plugins do Vite. O SvelteKit precisa ser um deles, e o adaptador vai junto com ele.
defineConfig
a função que só existe para o editor ajudar com os nomes das opções. Não muda o comportamento.

O projeto criado pelo sv create já vem com o adapter-auto configurado e com as dependências no package.json. O trecho abaixo é o do projeto da Ana, copiado do arquivo:

	"devDependencies": {
		"@sveltejs/adapter-auto": "^8.0.1",
		"@sveltejs/adapter-node": "^6.0.6",
		"@sveltejs/adapter-static": "^4.0.1",
		"@sveltejs/kit": "^3.2.0",
		"@sveltejs/vite-plugin-svelte": "^7.3.1",
		"svelte": "^5.57.3",

Três adaptadores instalados ao mesmo tempo não é problema: só o que está importado no vite.config.js é usado. Os outros ficam parados, ocupando alguns quilobytes no disco de desenvolvimento — nada vão para o site publicado.

4. O adaptador padrão e o aviso real

O adapter-auto é o detetive. Durante o build ele olha as variáveis de ambiente que as plataformas costumam deixar — NETLIFY, VERCEL, CF_PAGES e outras — e, se reconhecer uma, usa o adaptador certo para ela. Se não reconhecer nenhuma, ele não inventa: avisa e termina. Este é o fim da sessão de build na máquina da Ana, sem nenhuma dessas variáveis:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

Leia as duas últimas linhas com atenção. “Could not detect a supported production environment” quer dizer “não reconheci o lugar onde você vai publicar”. O build termina com sucesso — o ✔ done está lá — mas o resultado não serve para publicar em lugar nenhum. É um build de desenvolvimento sofisticado: bom para conferir, inútil para entregar.

Há também uma lição escondida no meio da sessão. As linhas GET /seo → 200 e GET / → 204 são o SvelteKit rodando o seu app para gerar as páginas que têm prerender = true. Os 204 aparecem nas rotas que foram apenas visitadas pelo rastreador de links e não geraram arquivo. O adaptador só entra depois disso: primeiro o app roda, depois o formato é escolhido.

5. Caixa 1: qual adaptador para cada destino

A escolha do adaptador é uma tabela mental simples, e vale treinar antes de mexer no arquivo. A caixa abaixo responde sempre adapter-auto, mesmo quando o destino é conhecido. A missão é usar o mapa que já está no código.

Missão: digite netlify no campo e o texto deve virar netlify → adapter-netlify. Use o objeto mapa que está no componente; destino desconhecido continua caindo em adapter-auto.

<script>
	const mapa = {
		netlify: 'adapter-netlify',
		vercel: 'adapter-vercel',
		node: 'adapter-node',
		estatico: 'adapter-static'
	};

	let destino = $state('');
</script>

<input oninput={(e) => (destino = e.currentTarget.value)} placeholder="destino" />
<p>{destino} → adapter-auto</p>
<script>
	const mapa = {
		netlify: 'adapter-netlify',
		vercel: 'adapter-vercel',
		node: 'adapter-node',
		estatico: 'adapter-static'
	};

	let destino = $state('');
</script>

<input oninput={(e) => (destino = e.currentTarget.value)} placeholder="destino" />
<p>{destino} → {mapa[destino] ?? 'adapter-auto'}</p>

O operador ?? é o “se não houver nada”. Ele devolve o valor da esquerda quando ela existe e o da direita quando ela é undefined. Diferente de ||, que também troca por zero e por texto vazio; para escolher padrão de configuração, ?? é o operador certo.

6. Trocando para o adapter-node

O destino da Ana é uma VPS: uma máquina Linux comum, com Node instalado, sem plataforma mágica em volta. Para esse caso o adaptador é o @sveltejs/adapter-node. A instalação é um comando, e ele registra o pacote no package.json:

ana@notebook:~/loja$ npm i -D @sveltejs/adapter-node

added 4 packages, removed 1 package, and audited 53 packages in 7s

11 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

O -D instala como dependência de desenvolvimento. Faz sentido: o adaptador trabalha no build, não em tempo de execução. O programa final que ele gera é Node puro, sem depender do pacote do adaptador.

Depois vem a troca no vite.config.js, que é a única mudança no código do site: uma linha de import e uma de uso. O build seguinte já mostra outro final:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

✓ built in 376ms

GET /seo → 200 (12 ms)
GET /sobre → 200 (2 ms)

GET /produtos → 204 (0 ms)

Comparado com o build anterior, o aviso sumiu e três linhas novas apareceram. “Using @sveltejs/adapter-node” é o adaptador se apresentando. “Copying assets” é a cópia dos arquivos que já existiam prontos — as imagens, o robots.txt, tudo o que veio da pasta static. “Compressing and hashing assets” é a geração das versões .gz e .br e do hash no nome de cada arquivo, do mesmo jeito que o Vite faz no projeto sem Kit.

7. O que sai na pasta build/

O adaptador-node escreve uma pasta que é um programa completo. Listar o conteúdo é a forma mais rápida de entender o que ele fez:

ana@notebook:~/loja$ ls build
adapter-node.js
client
handler.js
index.js
prerendered
server
Dentro de build/O que é
index.jso ponto de entrada: é ele que o node build executa
handler.jso pedaço que recebe as requisições e chama o app
client/o JavaScript e o CSS que vão para o navegador
server/o código do servidor: suas rotas, seus load
prerendered/as páginas que viraram HTML no build
adapter-node.jsa cola entre o adaptador e o servidor gerado

Essa pasta é o que você copia para a VPS. Ela não precisa do seu código-fonte, nem da pasta node_modules de desenvolvimento, nem do Vite. Precisa de Node instalado e das dependências de produção — no caso da Ana, nenhuma além do próprio Node. Menos coisa para dar errado na máquina de produção.

E a pasta prerendered/ merece uma olhada antes de publicar, porque o que está lá não muda mais. No projeto da Ana ela trouxe seo.html, sobre.html e também um conta.html que ninguém pediu: o rastreador seguiu o link do menu e congelou uma página que dependia de login. O arquivo é um redirecionamento de 112 bytes, mas o susto é real. Cache e pré-render têm aula própria; aqui o que importa é saber que a pasta existe e que você deve abri-la.

8. Caixa 2: o que precisa de servidor

Escolher adaptador é escolher o que o site consegue fazer. Uma página que só mostra texto igual para todo mundo pode virar arquivo. Uma página com formulário que grava pedido precisa de alguém rodando para receber o POST. Numa lista de rotas, esse teste vira um componente pequeno:

<script>
	let { nome = 'entrar', actions = true } = $props();
</script>

<p>{nome}: {actions ? 'precisa de servidor' : 'pode ser estática'}</p>
<p>entrar: precisa de servidor</p>

Com os valores padrão do exemplo, o componente já responde sozinho. A caixa abaixo usa a mesma ideia numa lista de duas páginas, mas diz “estática” para as duas.

Missão: a página entrar tem actions, então depende de servidor. Faça a lista mostrar precisa de servidor quando p.actions for verdadeiro e pode ser estática quando for falso.

<script>
	const paginas = [
		{ nome: 'sobre', actions: false },
		{ nome: 'entrar', actions: true }
	];
</script>

<ul>
	{#each paginas as p}
		<li>{p.nome}: estática</li>
	{/each}
</ul>
<script>
	const paginas = [
		{ nome: 'sobre', actions: false },
		{ nome: 'entrar', actions: true }
	];
</script>

<ul>
	{#each paginas as p}
		<li>{p.nome}: {p.actions ? 'precisa de servidor' : 'pode ser estática'}</li>
	{/each}
</ul>

Esse teste é o mesmo que o adapter-static faz no build, só que em escala: ele percorre todas as rotas e verifica se alguma depende de servidor. Se a resposta for sim, o build para. Não é teimosia do pacote: um site estático não tem onde rodar um load que lê cookie.

9. adapter-static: quando serve

Um site de arquivos parados tem vantagens concretas: pode ser servido de graça, responde rápido, não tem servidor para cair. É a escolha certa para a página de divulgação da padaria, o cardápio do dia e o blog de receitas. Para o painel de pedidos, que muda a cada pedido, não serve.

O adaptador aceita três saídas possíveis quando alguma rota é dinâmica. A primeira é congelar tudo: export const prerender = true no +layout.js raiz, o que tenta pré-renderizar todas as páginas. A segunda é apontar um fallback, um arquivo que o servidor estático devolve quando não acha a rota, transformando o site numa SPA. A terceira é strict: false, que manda o adaptador ignorar as rotas dinâmicas — útil só quando você tem certeza de que elas não são necessárias no pacote final.

SituaçãoAdaptador indicadoPor quê
cardápio que muda uma vez por diaadapter-staticnada é calculado no pedido
painel de pedidos com loginadapter-nodeprecisa ler cookie e gravar no banco
publicar no Netlifyadapter-netlifyo formato das funções é do Netlify
não sei ainda onde publicaradapter-autoele tenta descobrir no build

10. Caixa 3: contando o que o build gerou

Ler a pasta de saída é uma habilidade, e contar arquivos é o primeiro passo. A caixa abaixo lista cinco itens da pasta build/ e escreve “6” no texto. A missão é deixar a conta com o próprio código.

Missão: o número está escrito à mão e está errado. Use o tamanho da lista para mostrar Arquivos no build: 5.

<script>
	const arquivos = ['client', 'server', 'prerendered', 'index.js', 'handler.js'];
</script>

<p>Arquivos no build: 6</p>
<script>
	const arquivos = ['client', 'server', 'prerendered', 'index.js', 'handler.js'];
</script>

<p>Arquivos no build: {arquivos.length}</p>

arquivos.length é a propriedade de lista que devolve a quantidade de itens. Contar com o código em vez de digitar o número é o que impede o texto de mentir quando alguém acrescenta um arquivo à lista. A mesma ideia vale para o total de produtos da padaria, de itens no carrinho e de pedidos do dia.

11. Quando dá errado

As três mensagens abaixo são do build de verdade, com SvelteKit 3.4.1. A primeira é a mais comum em quem vem de tutorial antigo.

Erro 1 — configuração no arquivo que não é mais lido

Você cria um svelte.config.js com kit.adapter, como fazia no SvelteKit 2. O build nem começa: ele para na leitura da configuração.

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

error during build:
SvelteKit error: config_file_unsupported
`svelte.config.js` is no longer used. Please pass configuration via the `sveltekit(...)` plugin in your Vite config.
https://svelte.dev/e/kit/config_file_unsupported
  plugin: 'vite-plugin-sveltekit-resolve-root',
  hook: 'config'
}

A mensagem diz o que fazer e onde: dentro do sveltekit(…), no vite.config.js. O erro é bom porque aparece antes de qualquer trabalho: apagar o arquivo e mover a opção resolve.

Erro 2 — rotas dinâmicas num site estático

Você troca para o adapter-static e o build termina, mas o adaptador recusa o pacote. Ele lista cada rota que não conseguiu congelar e mostra as saídas possíveis.

> Using @sveltejs/adapter-static

@sveltejs/adapter-static: all routes must be fully prerenderable, but found the following routes that are dynamic:
  - src/routes/
  - src/routes/api/produtos
  - src/routes/cache
  - src/routes/conta
  - src/routes/entrar
  - src/routes/env
  - src/routes/erro
  - src/routes/produtos
  - src/routes/static

You have the following options:
  - set the `fallback` option — see https://svelte.dev/docs/kit/single-page-apps#usage for more info.
  - add `export const prerender = true` to your root `+layout.js/.ts` or `+layout.server.js/.ts` file. This will try to prerender all pages.
  - add `export const prerender = true` to any `+server.js/ts` files that are not fetched by page `load` functions.
  - pass `strict: false` to `adapter-static` to ignore this error. Only do this if you are sure you don't need the routes in question in your final app, as they will be unavailable. See https://github.com/sveltejs/kit/tree/main/packages/adapter-static#strict for more info.

If this doesn't help, you may need to use a different adapter. @sveltejs/adapter-static can only be used for sites that don't need a server for dynamic rendering, and can run on just a static file server.

See https://svelte.dev/docs/kit/page-options#prerender for more details

error during build:
[Error: Encountered dynamic routes] {
  plugin: 'vite-plugin-sveltekit-adapter',
  hook: 'buildApp'
}

O erro final é curto — Encountered dynamic routes — e a explicação está em cima. A leitura útil é a lista: cada linha é uma pasta de src/routes/ que não pôde virar arquivo. Se a lista tem só páginas que você não precisa, strict: false resolve. Se tem a página de login, o adaptador certo é outro.

Aviso 3 — o adaptador não reconheceu a plataforma

Este não é um erro: o build termina com ✔ done. Mas o pacote gerado não serve para publicar. O texto é o mesmo do adapter-auto, e vale reconhecer de longe.

> Using @sveltejs/adapter-auto
Could not detect a supported production environment. See https://svelte.dev/docs/kit/adapters to learn how to configure your app to run on the platform of your choosing
✔ done

A leitura é direta: “não reconheci o ambiente de produção”. A correção é trocar por um adaptador explícito — node, static, netlify — em vez de esperar que o detetive adivinhe. Em plataformas conhecidas o aviso some sozinho, porque a variável de ambiente que o adaptador procura existe.

Exercícios

1. Onde o adaptador é configurado no SvelteKit 3?

2. O build terminou com Could not detect a supported production environment. O que aconteceu?

3. Por que o adapter-static recusa uma rota com form actions?

Complete o código

// vite.config.js
import adapter from '';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [sveltekit({ adapter: adapter() })]
});

// o destino é uma VPS comum, com Node instalado

Resumo

  • Adaptador é o pacote que traduz o resultado do build para o formato da plataforma de destino.
  • No SvelteKit 3 ele é configurado dentro de sveltekit({ adapter }), no vite.config.js; o svelte.config.js não é mais lido.
  • adapter-auto tenta descobrir a plataforma; sem reconhecer, avisa e gera um pacote que não serve para publicar.
  • adapter-node gera a pasta build/ com index.js, handler.js, client/, server/ e prerendered/.
  • adapter-static só aceita rotas que possam virar arquivo; rotas com load que lê cookie ou com actions são recusadas.
  • As saídas para uma rota dinâmica são prerender = true, fallback ou strict: false.
  • O build primeiro roda o app e pré-renderiza; só depois o adaptador escreve o pacote.
  • Três adaptadores instalados não atrapalham: só o importado no vite.config.js vale.
  • Antes de publicar, abra a pasta prerendered/: o rastreador congela até páginas que você não pediu.
  • Erro 1 desta aula: config_file_unsupported. Erro 2: Encountered dynamic routes. Aviso 3: plataforma não reconhecida.
