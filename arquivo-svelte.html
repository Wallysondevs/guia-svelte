Svelte · O Arquivo .svelte

A Ana guarda as receitas em fichas de um tamanho só, sempre com o mesmo cabeçalho: nome, rendimento, tempo de forno. O formato é dela, não é página de livro nem receita de revista — e é justamente por ter formato próprio que ela acha qualquer coisa em segundos. O arquivo .svelte é a ficha do guia: um formato próprio, que nenhum navegador conhece e que o compilador transforma em JavaScript. Nesta aula você abre essa ficha, vê o que o compilador faz com ela e descobre por que o nome do arquivo aparece no CSS.

Você vai aprender
  • O que existe dentro de um arquivo .svelte: texto, e nada além de texto.
  • Por que o navegador não abre o arquivo direto e o que o compilador faz no lugar.
  • Como o nome do arquivo entra no hash do CSS e por que isso importa.
  • Que o componente compilado vira uma função JavaScript.
  • De onde vem o export default — e por que você não deve escrevê-lo.
  • Como ler o JavaScript gerado para entender o que o Svelte otimizou.
  • O que um arquivo vazio faz e quando isso é útil.
  • As variações do bloco de script: lang e module.
  • Os erros reais: return no topo, variável repetida e palavra reservada.

1. A ideia: a ficha com formato próprio

Uma ficha de receita não é um livro nem um cartaz: é um formato inventado para um uso. Tem campos fixos, na ordem que interessa a quem cozinha. Quem não conhece o formato estranha; quem conhece acha tudo rápido. O arquivo .svelte segue a mesma lógica: um formato inventado para descrever um pedaço de tela.

Esse formato tem três partes possíveis — o script, o HTML e o estilo — e uma regra de leitura: o compilador entra no arquivo, separa as partes, executa o que dá para executar naquele momento e gera JavaScript. O navegador nunca vê a ficha; vê o resultado dela.

Por isso a extensão é diferente de .html. Se fosse HTML, o navegador tentaria abrir e mostraria as chaves {nome} como texto literal, ou reclamaria de tags desconhecidas. A extensão própria é um aviso: "este arquivo precisa de um compilador antes de virar página".

2. O que existe dentro do arquivo

Um arquivo .svelte é texto puro, salvo em UTF-8 — o mesmo padrão que guarda acentos e cedilha. O sistema operacional vê um arquivo comum, com algumas linhas:

ana@notebook:~/loja$ file src/App.svelte
src/App.svelte: HTML document, Unicode text, UTF-8 text
ana@notebook:~/loja$ wc -l src/App.svelte
5 src/App.svelte
ana@notebook:~/loja$ wc -c src/App.svelte
70 src/App.svelte

Cinco linhas, setenta bytes. O file chuta "HTML document" porque o arquivo começa com uma tag, mas o palpite está errado: o navegador não sabe o que fazer com um .svelte. Se você abrir o arquivo no navegador, verá o texto cru ou um download — nunca o componente funcionando.

O UTF-8 é o detalhe que estraga o dia de quem salva no formato antigo do Windows. Um arquivo em Latin-1 com "Pão" aparece como "PÃ£o" na página, porque os bytes foram lidos com outra tabela. Se um acento sair errado, a primeira suspeita é a codificação do arquivo, não o Svelte.

Outra consequência de ser texto: você pode versionar no git, comparar diferenças, revisar em qualquer editor. Não existe parte binária, não existe projeto proprietário. Um arquivo .svelte é tão legível quanto uma receita escrita à mão — e é por isso que o guia insiste em mostrar o arquivo inteiro, e não pedaços soltos.

3. O nome do arquivo entra no resultado

Aqui está uma coisa que quase ninguém espera: o nome do arquivo faz parte do componente. O compilador usa o caminho para calcular o selo do CSS. O mesmo conteúdo, em dois arquivos diferentes, gera dois selos diferentes:

<h1>Pão francês</h1>
<p>R$ 0.90</p>

<style>
  h1 { color: #2e7d32; }
</style>
<h1 class="svelte-1n46o8q">Pão francês</h1> <p>R$ 0.90</p>

O CSS correspondente:

h1.svelte-1n46o8q { color: #2e7d32; }

Agora o mesmo conteúdo, salvo como src/Cartao.svelte:

<h1>Pão francês</h1>
<p>R$ 0.90</p>

<style>
  h1 { color: #2e7d32; }
</style>
<h1 class="svelte-11u2pyd">Pão francês</h1> <p>R$ 0.90</p>

Outro selo: svelte-11u2pyd em vez de svelte-1n46o8q. É a prova de que o selo não vem do conteúdo do CSS: vem da identidade do arquivo. Duas consequências práticas: renomear um componente muda o CSS gerado (e o hash do build), e dois arquivos com o mesmo conteúdo nunca colidem entre si.

O nome também aparece nas mensagens de erro, na posição do arquivo. Se você renomear App.svelte para app.svelte, o import ./App.svelte deixa de achar o arquivo — e o erro vai falar de módulo não encontrado, não de componente. Nomes em maiúscula existem por convenção e por causa da diferença entre maiúsculas e minúsculas nos sistemas de arquivos.

4. O arquivo vira uma função

Para entender o que o compilador faz, vale ver o resultado. O comando abaixo compila o componente e imprime todo o JavaScript gerado para o navegador:

ana@notebook:~/loja$ node -e "const {compile}=require('svelte/compiler');console.log(compile(require('fs').readFileSync('src/App.svelte','utf8'),{generate:'client',filename:'src/App.svelte'}).js.code)"
import 'svelte/internal/init-operations';
import 'svelte/internal/disclose-version';
import * as $ from 'svelte/internal/client';

var root = $.from_html(`
`);

export default function App($$anchor) {
	let nome = 'Ana';
	var h1 = root();

	h1.textContent = 'Olá, Ana';
	$.append($$anchor, h1);
}

Treze linhas. O componente virou uma função chamada App, que recebe um lugar onde se encaixar ($$anchor), cria o elemento a partir de um molde e escreve o texto. O HTML do molde é <h1></h1>, vazio: o conteúdo entra depois, por textContent.

Repare em h1.textContent = 'Olá, Ana'. O compilador já sabia o valor — ninguém muda nome neste componente — e escreveu o texto direto, sem consultar variável nenhuma na hora de rodar. Isso é otimização de compilador: o que dá para decidir antes, ele decide antes. Em um componente com botão, o código gerado seria diferente, com funções de atualização.

import … de 'svelte/internal/client'
o motor do Svelte, que sabe criar elementos, atualizar texto e reagir a mudanças. É uma dependência pequena comparada a um framework inteiro.
var root = $.from_html(`<h1></h1>`)
o molde do componente: um pedaço de HTML criado uma vez e clonado a cada uso. Repare que a marcação foi reduzida ao esqueleto.
export default function App
a função que representa o componente. É por isso que o arquivo não tem export default escrito por você: ele já existe, gerado.
$$anchor
o lugar onde o componente será encaixado na página, passado pelo componente pai ou pelo mount().
$.append($$anchor, h1)
a montagem final: o elemento criado é colocado dentro do lugar recebido.

Há mais duas coisas para notar no JavaScript gerado. A primeira é que as tabulações do código são do compilador, não suas: ele formata a saída do jeito dele, e isso não afeta o resultado. A segunda é que a variável nome continua ali, dentro da função, mesmo que nesse caso não seja usada para nada reativo — o compilador manteve a declaração porque o valor poderia ser lido por uma função que você escrevesse.

Não é preciso entender cada linha agora. O que importa é a ideia: componente é função, marcação é molde, valor é dado. Todo o resto do guia é consequência disso.

5. Por que o componente não tem export default

Na aula de estrutura, o erro era escrever export default {} dentro do componente. Agora dá para ver o motivo: o compilador já gera um export default function App. Se você escrevesse outro, o arquivo teria dois exports padrão — e o JavaScript não permite.

Quem precisa do export é o main.js, que importa o componente e o monta. O export default que aparece lá é do arquivo JavaScript, não do componente. São arquivos diferentes, com papéis diferentes: o componente descreve um pedaço de tela; o main.js decide onde ele começa.

Isso também explica o erro "A component cannot have a default export": não é uma regra arbitrária do Svelte, é uma consequência do código que ele gera. Entender o porquê economiza decoreba — quando a mensagem parecer sem sentido, vale perguntar que código o compilador precisa produzir.

6. Um arquivo vazio é um componente válido

Pode parecer piada, mas é verdade: um arquivo .svelte sem nenhuma linha compila e produz um componente que não desenha nada. Sem erro, sem aviso. O compilador gera uma função vazia e segue a vida.

Isso é útil quando você está começando um componente novo: cria o arquivo, importa no lugar certo, confirma que a página não quebrou e só então escreve o conteúdo. Se algo der errado depois, você sabe que o problema está no que acabou de escrever, não na ligação entre os arquivos.

Um arquivo com apenas um comentário tem o mesmo efeito: o comentário é descartado e o componente não mostra nada. É o estado inicial da caixa abaixo.

Missão: o arquivo só tem um comentário, então a tela fica vazia. Escreva o componente: um <script> com nome valendo 'Ana' e um <h1> com "Padaria da {nome}".

<!-- o arquivo ainda está vazio -->
<script>
  let nome = $state('Ana');
</script>

<h1>Padaria da {nome}</h1>

A caixa mostra o componente rodando de verdade: o arquivo que você edita é compilado e montado no navegador, do mesmo jeito que o Vite faz no projeto. A diferença é que aqui não existe main.js nem index.html — a caixa monta o componente direto.

7. Variações do bloco de script

O bloco <script> aceita dois atributos que mudam o comportamento. O primeiro é lang="ts", que avisa: "o conteúdo aqui é TypeScript, com tipos". O compilador então usa o pré-processador para remover os tipos antes de compilar.

<script lang="ts">
  let nome: string = 'Ana';
</script>

<p>{nome}</p>
<p>Ana</p>

O segundo é module, que cria um bloco que roda uma vez para todos os usos do componente, em vez de uma vez por componente. Serve para estado compartilhado e constantes:

<script module>
  export const versao = '1.0';
</script>

<p>versão {versao}</p>
<p>versão 1.0</p>

Os dois atributos têm aula própria mais adiante. Por enquanto, saiba que existem e que não são necessários para começar: um <script> simples resolve a maioria dos casos. Usar TypeScript sem necessidade acrescenta uma camada de configuração que você vai ter de manter.

8. O que fica fora do arquivo

Nem tudo pertence ao componente. O título da aba, a fonte do site, o favicon e a cor de fundo da página inteira ficam no index.html ou em um CSS global. O componente cuida do pedaço de tela que ele representa; a página cuida do envelope.

Quando você precisa de algo global dentro do componente, existem duas portas. Uma é :global() no bloco de estilo. A outra é a tag especial <svelte:head>, que escreve no head da página — útil para o título de uma rota, por exemplo. As duas são exceções; o padrão é o componente não saber que existe uma página em volta.

Existe ainda a questão do tamanho do arquivo. Um componente de trezentas linhas é difícil de ler, e a solução não é comprimir o código: é dividir em componentes menores, cada um com a sua responsabilidade. O arquivo .svelte não tem limite técnico de tamanho, mas tem limite humano. Quando você precisa rolar a tela para achar o fim do bloco de estilo, é sinal de que já passou do ponto.

Já as imagens e fontes entram por importação, dentro do script. O arquivo .svelte não tem uma pasta secreta de recursos: ele usa o mesmo sistema de importação do JavaScript, e o Vite resolve o caminho no build. Se a imagem não aparece, o problema costuma estar no caminho, não no componente.

9. O editor ajuda, mas não compila

Um arquivo .svelte aberto em um editor comum é só texto com cores diferentes. Com a extensão oficial do Svelte para o VS Code, você ganha destaque de sintaxe nas três partes, sugestões e verificação de erros enquanto digita. O editor não compila nada: ele chama o mesmo compilador para conferir.

Isso significa que um erro marcado no editor é o mesmo erro que apareceria no terminal. Se o editor está silencioso e o terminal reclama, desconfie da versão da extensão ou de um arquivo salvo em outro lugar. E se o editor marca erro em algo que funciona, o problema pode ser configuração de tipos, não o Svelte.

Para quem está começando, a configuração mínima basta: a extensão oficial, o arquivo salvo na pasta certa e o terminal rodando o servidor. Não invente uma configuração de pré-processador antes de precisar dela — cada linha de configuração é uma coisa a mais para dar errado.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão. Todas são erros de JavaScript dentro do arquivo, não de Svelte: o bloco de script é JavaScript de verdade, com as regras da linguagem.

Erro 1 — return no topo do script

O conteúdo do script vira o corpo de uma função, mas você não pode escrever return solto: ele só vale dentro de uma função que você mesmo declarou.

<script>
  return 1;
</script>

<p>oi</p>
Erro de compilação (linha 2, coluna 2): 'return' outside of function

A mensagem é do JavaScript: "return fora de função". Se você quer que algo aconteça ao montar, o caminho é $effect ou a função onMount, que têm aulas próprias no Nível 2.

Erro 2 — a mesma variável declarada duas vezes

Duas declarações com o mesmo nome no mesmo bloco. O JavaScript não sabe qual valor vale e recusa o arquivo.

<script>
  let nome = 'Ana';
  let nome = 'Bia';
</script>

<p>Olá, {nome}</p>
Erro de compilação (linha 3, coluna 6): Identifier 'nome' has already been declared

"Já foi declarado" quer dizer que o nome está ocupado. Apague uma das linhas ou renomeie a segunda — nomePreferido, por exemplo. A posição aponta a segunda declaração, não a primeira.

Missão: o componente declara nome duas vezes e não compila. Deixe uma declaração só, com o valor 'Ana'.

<script>
  let nome = 'Ana';
  let nome = 'Bia';
</script>

<p>Olá, {nome}</p>
<script>
  let nome = 'Ana';
</script>

<p>Olá, {nome}</p>

O erro de declaração repetida é mais traiçoeiro do que parece: ele não aparece quando você copia uma linha, mas quando cola um bloco inteiro por cima do que já existia. Depois de colar, vale olhar o script de cima a baixo e procurar nomes que se repetem — o compilador aponta a segunda ocorrência, e é para lá que você deve ir.

Erro 3 — palavra reservada como nome de variável

class é uma palavra da linguagem usada para criar classes. Não pode virar nome de variável, por mais que faça sentido em português.

<script>
  let class = 'Ana';
</script>

<p>{class}</p>
Erro de compilação (linha 2, coluna 6): Unexpected keyword 'class'

Renomeie para turma, classe ou grupo. A lista de palavras reservadas inclui class, function, return, new e outras. O editor costuma colorir essas palavras de forma diferente — bom sinal de alerta.

Missão: a variável se chama class, que é palavra reservada, e o arquivo não compila. Renomeie para turma nos dois lugares.

<script>
  let class = 3;
</script>

<p>Turma: {class}</p>
<script>
  let turma = 3;
</script>

<p>Turma: {turma}</p>

Note que a meta confere o texto que aparece na tela, e não o nome da variável. O Svelte não liga para o nome que você escolhe; quem liga é o JavaScript, que tem uma lista de palavras que não podem ser usadas como identificador.

Resumo

  • Um arquivo .svelte é texto UTF-8 com até três blocos.
  • O navegador não abre o arquivo direto: ele precisa ser compilado.
  • O nome e o caminho do arquivo entram no hash do CSS e nas mensagens de erro.
  • O componente compila para uma função com export default gerado.
  • Valores que não mudam são escritos direto no código gerado.
  • Um arquivo vazio é um componente válido que não desenha nada.
  • lang="ts" liga o TypeScript; module cria um bloco compartilhado.
  • Página, fonte e favicon ficam no index.html; o componente cuida do pedaço dele.
  • Os erros desta aula: return no topo, variável repetida e palavra reservada.
