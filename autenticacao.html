SvelteKit · Autenticação

A Ana tem quatro funcionários e uma porta de serviço. Cada um recebe um crachá com nome e função; sem crachá, ninguém entra na cozinha. No site acontece igual: o cliente digita a senha uma vez, o servidor entrega um crachá chamado cookie de sessão e, a cada pedido novo, confere o crachá antes de mostrar a conta. Esta aula monta esse caminho inteiro — formulário, ação, cookie, hook e página protegida — e mostra o que o servidor responde em cada passo.

Você vai aprender
  • Por que autenticação precisa de servidor, e não só de estado no componente.
  • Como é um formulário de login ligado a um form action.
  • Como conferir a senha, devolver erro com fail e redirecionar com redirect.
  • Como gravar o cookie de sessão com cookies.set e as bandeiras certas.
  • Como o hook barra a área logada antes de a página carregar.
  • Como locals leva o usuário do hook até o load e até a tela.
  • Como fazer logout apagando o cookie.
  • Por que senha nunca é guardada como texto e o que é hash.
  • Os três tropeços reais: dado nulo na tela, CSRF e página protegida que virou arquivo.

1. A ideia: o crachá da equipe

O crachá da padaria tem três propriedades que interessam. Ele é emitido pelo dono, não pelo funcionário — ninguém fabrica o próprio crachá. Ele é conferido na porta, não dentro da cozinha. E ele pode ser cancelado: quando alguém sai da equipe, o crachá para de funcionar.

No site, o crachá é um cookie: um pedacinho de texto que o servidor manda e o navegador devolve em cada pedido seguinte. Esse texto não é a senha. É um identificador que só o servidor sabe interpretar. A senha foi conferida uma vez, no login; depois disso, o que viaja é a marca de que aquela sessão já foi autenticada.

Quem emite o cookie é o servidor, numa ação de formulário. Quem confere é um hook, antes de a página ser renderizada. E quem mostra a conta é a página, lendo o usuário que o hook colocou em locals. Três peças, cada uma no seu lugar — e o valor de entender as três é saber onde procurar quando o login “não funciona”.

2. Sessão em três peças

Antes do código, o mapa. Uma sessão de login atravessa três arquivos e cada um tem uma responsabilidade que não se mistura com as outras:

PeçaArquivoResponsabilidade
Formulário+page.sveltemostrar os campos e a mensagem de erro
Ação+page.server.jsconferir a senha, criar ou apagar o cookie
Porteirohooks.server.jsler o cookie e barrar quem não tem crachá
Página protegida+page.server.js da rotaler locals e devolver os dados

A confusão mais comum é tentar autenticar no componente. Guardar a senha numa variável $state e comparar com a senha certa dentro do .svelte parece funcionar no teste e não funciona na prática: o código do componente vai para o navegador, e a senha certa vai junto. Autenticação mora no servidor, sempre.

3. O formulário de entrada

A página de login é um formulário comum, com um detalhe: o action aponta para uma ação nomeada do servidor, e o SvelteKit entrega o resultado da ação numa propriedade chamada form.

<script>
	let { form } = $props();
</script>

<h1>Entrar</h1>

{#if form?.erro}
	<p class="erro">{form.erro}</p>
{/if}

<form method="POST" action="?/entrar">
	<label>Senha <input type="password" name="senha" /></label>
	<button>Entrar</button>
</form>
<h1>Entrar</h1>  <form method="POST" action="?/entrar"><label>Senha <input type="password" name="senha"/></label> <button>Entrar</button></form>
let { form }
os dados que a ação devolveu. Começa undefined na primeira visita e chega preenchido quando o POST falha.
form?.erro
o encadeamento opcional evita quebrar quando não há erro. Se form for undefined, a condição é falsa.
method="POST"
envia os campos no corpo do pedido. Sem método, o navegador manda GET e a senha aparece na URL.
action="?/entrar"
o nome da ação, com interrogação na frente. É o que liga o formulário à função entrar do servidor.
name="senha"
o nome do campo. Sem ele, o valor não chega no formData do servidor.
type="password"
esconde os caracteres na tela. Esconde na tela, não no pedido: quem protege o pedido é o HTTPS.

Repare no HTML que o compilador gerou: o parágrafo de erro não aparece, porque form está vazio. É o mesmo componente em dois estados — sem erro e com erro — e a diferença vem do servidor, não de uma variável do navegador.

4. A ação que confere a senha

A ação é uma função exportada com nome, dentro do +page.server.js da rota. Ela recebe o pedido, lê os campos, decide e responde:

import { fail, redirect } from '@sveltejs/kit';

export const actions = {
	entrar: async ({ request, cookies }) => {
		const dados = await request.formData();
		const senha = dados.get('senha');

		if (senha !== 'pao123') {
			return fail(400, { erro: 'Senha incorreta, tente de novo.', senha });
		}

		cookies.set('sessao', 'ana-123', {
			path: '/',
			httpOnly: true,
			sameSite: 'lax',
			maxAge: 60 * 60 * 24
		});

		throw redirect(303, '/conta');
	}
};

Quatro decisões moram nesse bloco. A primeira: a comparação acontece no servidor, com a senha que só ele conhece. A segunda: senha errada devolve fail(400, …), que é um erro “esperado” — o formulário recebe os dados e mostra a mensagem sem derrubar a página. A terceira: o cookie nasce com httpOnly, então o JavaScript da página não consegue lê-lo. A quarta: quem deu certo não fica vendo a tela de login; recebe um redirecionamento 303 para a conta.

Sobre o throw redirect: no SvelteKit 3 a função redirect() já lança o redirecionamento por dentro. Escrever throw na frente funciona igual e deixa a intenção explícita para quem lê o código — é a forma que o guia usa.

5. O que o servidor responde

Os três pedidos abaixo foram feitos ao servidor de desenvolvimento desta máquina e estão copiados como chegaram. O primeiro pede a conta sem crachá:

ana@notebook:~/loja$ curl -s -i http://localhost:5173/conta | head -5
HTTP/1.1 303 See Other
Vary: Origin
location: /entrar?de=/conta
Date: Thu, 26 Nov 2026 17:41:59 GMT
Connection: keep-alive

O 303 manda o navegador para /entrar?de=/conta. O pedaço de=/conta é uma convenção útil: depois de entrar, a página de login pode devolver o cliente para onde ele queria ir. Sem isso, ele cai sempre na página inicial e perde o caminho.

O segundo pedido é o formulário com a senha errada. Note o status e o corpo:

ana@notebook:~/loja$ curl -s -i -X POST -d 'senha=errada' 'http://localhost:5173/entrar?/entrar' | head -14
HTTP/1.1 400 Bad Request
Vary: Origin
content-type: application/json
x-sveltekit-version: 1795714916883
content-length: 135
Date: Thu, 26 Nov 2026 17:41:59 GMT
Connection: keep-alive
Keep-Alive: timeout=5

{"type":"failure","status":400,"location":"/entrar","data":"[{\"erro\":1,\"senha\":2},\"Senha incorreta, tente de novo.\",\"errada\"]"}

O curl não pediu HTML, então o SvelteKit respondeu no formato de dados: tipo failure, status 400 e um pacote com a mensagem e o valor digitado. Num navegador, a mesma resposta vira a página com o parágrafo de erro — o componente que você viu na seção 3.

O terceiro pedido é o login que dá certo:

ana@notebook:~/loja$ curl -s -i -X POST -d 'senha=pao123' 'http://localhost:5173/entrar?/entrar' | head -6
HTTP/1.1 200 OK
Vary: Origin
content-type: application/json
set-cookie: sessao=ana-123; Max-Age=86400; Path=/; HttpOnly; SameSite=Lax
content-length: 52

{"type":"redirect","status":303,"location":"/conta"}

O status 200 aqui não significa “ficou na página”: significa que a ação respondeu com um redirecionamento dentro do envelope. O cabeçalho set-cookie é o crachá sendo entregue, com as bandeiras: Max-Age=86400 (um dia), Path=/ (vale no site inteiro), HttpOnly (script não lê) e SameSite=Lax (não viaja em POST de outro site).

6. Caixa 1: a mensagem de erro no formulário

A caixa abaixo confere a senha e não mostra nada quando erra. A missão é exibir a mensagem que já está calculada.

Missão: digite errada no campo, clique no botão e mostre a mensagem Senha incorreta na tela. A variável erro já tem o texto certo.

<script>
	let senha = $state('');
	let erro = $state('');

	function entrar() {
		erro = senha === 'pao123' ? '' : 'Senha incorreta';
	}
</script>

<input oninput={(e) => (senha = e.currentTarget.value)} />
<button onclick={entrar}>Entrar</button>
<script>
	let senha = $state('');
	let erro = $state('');

	function entrar() {
		erro = senha === 'pao123' ? '' : 'Senha incorreta';
	}
</script>

<input oninput={(e) => (senha = e.currentTarget.value)} />
<button onclick={entrar}>Entrar</button>
{#if erro}
	<p>{erro}</p>
{/if}

O bloco {#if} com {/if} mostra o parágrafo só quando a condição é verdadeira. Como erro começa vazio, texto vazio é falso, e o parágrafo não aparece na primeira visita. É a mesma estrutura do form?.erro do componente real, com a diferença de que lá o valor vem do servidor.

7. O hook que barra a área logada

Conferir o crachá em cada página protegida seria repetitivo e fácil de esquecer. O lugar certo é o hooks.server.js, que roda em todo pedido, antes da rota:

import { sequence } from '@sveltejs/kit/hooks';
import { redirect } from '@sveltejs/kit';

const sessao = async ({ event, resolve }) => {
	const sid = event.cookies.get('sessao');
	event.locals.usuario = sid === 'ana-123' ? { nome: 'Ana', papel: 'dona' } : null;

	if (event.url.pathname.startsWith('/conta') && !event.locals.usuario) {
		throw redirect(303, `/entrar?de=${event.url.pathname}`);
	}
	return resolve(event);
};

export const handle = sequence(sessao);

Três linhas fazem o trabalho. cookies.get('sessao') lê o crachá. locals.usuario recebe o funcionário ou null. E o if decide: caminho dentro de /conta sem usuário vira redirecionamento 303. Repare que a condição usa startsWith e não igualdade, para cobrir também /conta/pedidos e /conta/endereco.

O !event.locals.usuario funciona porque null é falso em JavaScript. É uma economia de código que cobra o preço da clareza: quem lê precisa saber que locals.usuario é null, e não undefined, em caso de visita anônima. Numa equipe, vale comentar.

8. Caixa 2: a decisão do porteiro

O hook é uma decisão binária: entra ou é barrado. A caixa abaixo recebe o conteúdo do cookie e sempre mostra a conta.

Missão: o cookie está vazio, então a visita é anônima. Mostre redireciona para /entrar quando não houver crachá, e mostra a conta quando houver.

<script>
	const cookie = '';
</script>

<p>mostra a conta</p>
<script>
	const cookie = '';
	const logado = $derived(cookie.startsWith('sessao='));
</script>

<p>{logado ? 'mostra a conta' : 'redireciona para /entrar'}</p>

Se você trocar const cookie = '' por 'sessao=ana-123', o texto vira “mostra a conta” — e é isso que o servidor faz quando o crachá é válido. A decisão é sempre do servidor: a página nunca recebe os dados antes de o hook liberar.

9. A página protegida

A rota /conta tem dois arquivos. O +page.server.js devolve o usuário; o +page.svelte mostra:

export function load({ locals }) {
	return { usuario: locals.usuario };
}
<script>
	let { data } = $props();
</script>

<h1>Minha conta</h1>
<p>Bem-vinda, {data.usuario.nome} ({data.usuario.papel}).</p>

Com o crachá certo, o pedido devolve a página montada. Este é o terminal, com o cookie enviado à mão:

ana@notebook:~/loja$ curl -s -H 'cookie: sessao=ana-123' http://localhost:5173/conta | grep -o '<p>Bem-vinda[^<]*</p>'
<p>Bem-vinda, Ana (dona).</p>

Uma nota sobre o menu: o projeto da Ana tem um +layout.server.js que devolve locals.usuario para todas as páginas. É por isso que o cabeçalho consegue mostrar “Minha conta” ou “Entrar” sem repetir a leitura do cookie em cada load. O layout serve de ponte entre o hook e qualquer página.

Duas observações que evitam erro futuro. O data.usuario.nome só funciona porque o hook garante que existe usuário quando a página é renderizada. E o +layout.server.js do projeto também devolve locals.usuario, o que deixa qualquer página do site saber quem está logado — útil para o menu mostrar “Minha conta” ou “Entrar”.

10. Caixa 3: sair da conta

Logout é apagar o crachá. No componente, isso aparece como limpar o estado e voltar para o texto de visitante:

Missão: faça o botão Sair limpar a sessão. Depois do clique, o texto na tela precisa conter sessão encerrada.

<script>
	let sessao = $state('ana-123');
</script>

<button onclick={() => (sessao = sessao)}>Sair</button>
<p>sessão ativa: {sessao}</p>
<script>
	let sessao = $state('ana-123');
</script>

<button onclick={() => (sessao = '')}>Sair</button>
<p>{sessao ? `sessão ativa: ${sessao}` : 'sessão encerrada'}</p>

No servidor, a mesma ideia precisa de uma ação e de uma linha de cookies.delete('sessao', { path: '/' }). O path importa: apagar sem caminho não remove o cookie gravado em /, e o crachá continua valendo. Depois da exclusão, um redirecionamento 303 para a página inicial fecha o ciclo.

11. Senha: hash, nunca texto

O exemplo desta aula compara a senha com 'pao123' escrita no código. Isso serve para aprender o caminho e não serve para a vida real. Numa padaria de verdade, as senhas ficam num banco, guardadas como hash: o resultado de uma função que transforma o texto num código do qual não se volta.

GuardarSe o banco vazarServe?
senha em textotodas as senhas legíveisnunca
MD5 ou SHA-1quebráveis com tabela prontanunca
hash com salt e custo altoinviável em massasim
senha dentro do componenteestá no navegador de todosnunca

Na prática, você não escreve a função de hash: usa uma biblioteca feita para isso, como argon2 ou bcrypt. O fluxo é sempre o mesmo — no cadastro, gerar o hash e guardar; no login, gerar o hash da senha digitada e comparar com o guardado. A senha original nunca é armazenada, e nem o dono do site consegue lê-la.

Duas práticas completam o quadro. A primeira: nunca dizer se o erro foi “usuário não existe” ou “senha errada”. A mensagem única “usuário ou senha incorretos” impede alguém de descobrir quais e-mails têm conta. A segunda: limitar tentativas. O fail(400) registrado no log, repetido cem vezes em um minuto, é o sinal de ataque de força bruta.

12. Quando dá errado

As três respostas abaixo são reais. A primeira é uma tela que quebrou; a segunda é o servidor recusando um pedido de outro site; a terceira é um arquivo que ninguém queria gerar.

Erro 1 — a página protegida sem crachá

Quando o hook não existe ou não cobre a rota, o load devolve usuario: null e o componente tenta ler .nome. O servidor responde 500 e registra a pilha.

TypeError: Cannot read properties of null (reading 'nome')
    at eval (src/routes/quebra-locals/+page.svelte:5:29)
    at eval (node_modules/svelte/src/internal/server/renderer.js:416:11)
    at Renderer.child (node_modules/svelte/src/internal/server/renderer.js:305:18)

Há duas correções possíveis, e elas não são equivalentes. A primeira é data.usuario?.nome ?? 'visitante', que esconde o problema e mostra a página para quem não deveria vê-la. A segunda é garantir o redirecionamento no hook, para que a página só seja renderizada com usuário. Em área logada, a segunda é a certa.

Erro 2 — o POST de outro site

Um formulário enviado de outra origem é recusado em produção. A defesa é automática e o corpo da resposta é uma frase curta.

HTTP/1.1 403 Forbidden
content-length: 46
Date: Thu, 26 Nov 2026 17:10:32 GMT
Connection: keep-alive
Keep-Alive: timeout=5

Cross-site POST form submissions are forbidden

Se esse 403 aparecer num teste com curl, o motivo costuma ser a falta do cabeçalho de origem: sem origin, o pedido é tratado como suspeito. Mandar -H 'origin: http://localhost:3000' resolve o teste. Em navegador, o cabeçalho vai sozinho.

Aviso 3 — a página de conta que virou arquivo

O rastreador de links do build encontrou /conta pelo menu, recebeu o redirecionamento do hook e congelou o resultado. Em produção, o pedido devolve 200 sem passar pelo hook.

ana@notebook:~/loja$ wc -c build/prerendered/conta.html
112 build/prerendered/conta.html
ana@notebook:~/loja$ grep -o 'url=[^"]*' build/prerendered/conta.html
url=/entrar?de=/conta
ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/conta | head -2
HTTP/1.1 200 OK
etag: "7-DYfYF_Azx3mHEh08LY_w65McduCKKcStU7BxjvvLY"

Nenhum dado pessoal vazou — o arquivo é só o redirecionamento. Mas a área logada não deve ser pré-renderizável: export const prerender = false no layout de /conta impede o arquivo de nascer, e a revisão da pasta antes de publicar pega o caso.

Resumo

  • Autenticação mora no servidor: senha comparada no +page.server.js, nunca no componente.
  • O formulário usa method="POST" e action="?/nome-da-acao".
  • fail(400, dados) devolve erro esperado e entrega os dados ao form da página.
  • cookies.set emite o crachá com httpOnly, sameSite e maxAge.
  • Login bem-sucedido termina com redirect(303, '/conta').
  • O hook handle lê o cookie, preenche locals.usuario e barra quem não tem crachá.
  • locals leva o usuário do hook até o load e até a tela.
  • Logout é cookies.delete com o mesmo path usado na criação.
  • Senha vai para o banco como hash com salt, nunca como texto.
  • Erros desta aula: leitura de null, 403 de CSRF e conta.html pré-renderizada.
