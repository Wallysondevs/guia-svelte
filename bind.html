Svelte · bind:

A Ana anota os pedidos num caderno com duas folhas carbonadas: o que ela escreve na primeira aparece na segunda sem ninguém copiar nada. Se ela corrige um preço na segunda folha, a correção também vale para a primeira. É uma rua de mão dupla, e é exatamente isso que o bind: faz entre um campo da tela e uma variável do componente. Nesta aula você vai ver a rua funcionando, o que existe embaixo dela e o preço que se paga por usá-la sem pensar.

1. A ideia: as duas folhas carbonadas

Papel carbonado funciona assim: você escreve na folha de cima e a pressão do lápis copia o texto para a folha de baixo. Não existe mágica, existe contato. Na programação de tela, o campo e a variável são as duas folhas, e o bind é o carbono entre elas. Digitar no campo escreve na variável; mudar a variável pela lógica do programa reescreve o campo.

Sem essa ligação, você tem duas direções separadas. A ida, da variável para a tela, já existe em qualquer atributo: value={nome} mostra o valor. A volta, da tela para a variável, precisa de um evento: oninput lê o campo e grava na variável. O bind junta as duas pontas em uma palavra e assume o trabalho de manter as duas folhas iguais.

Vale entender o nome. A palavra vem do inglês bind, "amarrar". O que está amarrado é o valor da variável e o valor do elemento. Quando um dos dois muda, a corda puxa o outro. Nada é copiado por magia: o compilador gera o código que lê o campo no evento certo e escreve no estado; a diferença é que você não precisa escrever esse código.

Repare na última linha: é perfeitamente possível ter o valor na tela e nunca receber o que a pessoa digita. O campo mostra o texto inicial e ignora o resto. Muita gente passa por isso achando que o problema é o navegador, quando o que falta é a segunda direção.

3. O primeiro bind:value

<script>
  let nome = $state('Ana');
</script>

<input bind:value={nome}>
<p>Olá, {nome}</p>

Duas coisas acontecem ao mesmo tempo. O campo começa com o texto Ana, porque a variável começa assim. E cada tecla digitada atualiza a variável, porque o bind escuta o evento de entrada do campo. O parágrafo, que lê a mesma variável, acompanha cada letra.

<input value="Ana"/> <p>Olá, Ana</p>

Esse HTML tem uma diferença em relação aos exemplos da aula de eventos: o atributo value aparece com o valor inicial. Faz sentido — o servidor precisa mandar o campo já preenchido para a pessoa ver o texto antes de qualquer JavaScript rodar. O que não aparece é o evento: o bind também vira código de navegador, não marcação.

A anatomia do binding

bind:
o prefixo que diz "ligue este elemento a uma variável". Depois dos dois-pontos vem o nome do binding, que depende do tipo de elemento: value, checked, group, this.
value
o binding do conteúdo de campos de texto, números, áreas de texto e listas de opção. É o mais usado de todos.
{nome}
a variável do estado. Precisa ter sido criada com $state (ou vir de $props); uma variável comum não avisa a tela.
<input …>
o elemento amarrado. O binding não é universal: cada nome só vale em certos elementos, e o compilador reclama quando você erra o par.
oninput embutido
o que o compilador gera por baixo. Você economiza o evento e o código que lê o campo.

4. A saída real: o servidor manda o valor

Vale olhar só o texto da tela para confirmar que o valor inicial chega ao navegador. Nada de JavaScript foi executado ainda: isto é o que o servidor entrega.

Olá, Ana

Quando a página chega no navegador, o Svelte assume e liga o campo à variável. A partir daí, cada tecla muda o estado e o parágrafo. O texto que você vê na tela depois de digitar não é o mesmo que o servidor mandou — e é por isso que testar só o HTML do servidor não conta a história toda.

5. O que o bind faz por baixo

Para entender o atalho, escreva o caminho longo. O campo recebe o valor atual e escuta cada alteração; quando a alteração chega, o texto do campo é copiado para o estado.

<script>
  let nome = $state('Ana');

  function guardar(evento) {
    nome = evento.target.value;
  }
</script>

<input value={nome} oninput={guardar}>
<p>Olá, {nome}</p>
<input value="Ana"/> <p>Olá, Ana</p>

O HTML é idêntico ao do bind. Isso não é coincidência: o compilador gera exatamente esse tipo de código, só que sem você escrever. A diferença está no arquivo, não na tela. O caminho longo tem quatro linhas a mais e um nome de função a manter; o atalho tem uma palavra.

Você escreveO compilador entendeLinhas no arquivo
bind:value={nome}lê o campo no evento e escreve no estado1
value={nome} oninput={guardar}o mesmo, com função sua5
value={nome}só escreve na tela; nunca lê1
oninput={guardar}só lê o campo; a tela não acompanha o estado5

A terceira linha é a mais traiçoeira. O campo mostra o valor, a pessoa digita, e nada acontece no estado. O sintoma é "o campo não está ligado", mas o código parece certo. Se você quer as duas direções, use bind ou escreva as duas pontas.

Missão: o contador de letras está travado em zero. Faça ele mostrar o tamanho do texto que está no campo: digitando leite, deve aparecer 5 letras.

<script>
  let texto = $state('');
</script>

<p>0 letras</p>
<input bind:value={texto}>
<script>
  let texto = $state('');
</script>

<p>{texto.length} letras</p>
<input bind:value={texto}>

O binding já estava certo nos dois casos; o que faltava era o parágrafo ler o estado. Isso ilustra uma divisão que vale para o guia inteiro: o bind cuida de manter o valor atualizado, e a expressão dentro das chaves cuida de mostrar o valor do jeito que você quer. São duas responsabilidades, e misturar as duas é a origem de metade dos bugs de formulário.

6. Duas caixas, um estado

Como o bind é uma ligação e não uma cópia, dois campos podem apontar para a mesma variável. Digitar em um reescreve o outro, porque não existem dois valores: existe um valor com dois lugares mostrando.

<script>
  let nome = $state('Ana');
</script>

<input bind:value={nome}>
<input bind:value={nome}>
<p>Olá, {nome}</p>
<input value="Ana"/> <input value="Ana"/> <p>Olá, Ana</p>

O perigo mora aqui. Com dois campos ligados ao mesmo estado, não existe "o valor do primeiro" e "o valor do segundo": existe um valor só, e os dois campos são janelas para ele. Se a regra de negócio precisa de dois valores independentes, você precisa de duas variáveis. Se precisa de um valor com dois lugares de edição, um bind em cada campo resolve.

Missão: o campo mostra o nome, mas digitar não muda o parágrafo. Faça o parágrafo acompanhar o que a pessoa escreve, de modo que digitar Ana mostre Olá, Ana.

<script>
  let nome = $state('');
</script>

<input value={nome}>
<p>Olá, {nome}</p>
<script>
  let nome = $state('');
</script>

<input bind:value={nome}>
<p>Olá, {nome}</p>

Se você tentar resolver com oninput em vez de bind, também funciona: são duas formas de dizer a mesma coisa. O guia usa bind quando a ligação é direta, sem regra no meio, e usa o evento quando precisa decidir algo antes de gravar. A aula de Quando Não Usar bind é toda sobre essa escolha.

7. A forma curta e os bindings que existem

Quando a variável tem o mesmo nome do binding, o Svelte aceita a forma curta. Em vez de bind:value={value}, você escreve só bind:value. O detalhe é que a variável precisa se chamar value — um nome genérico que costuma atrapalhar a leitura do código.

<script>
  let value = $state('Ana');
</script>

<input bind:value>
<p>Olá, {value}</p>
<input value="Ana"/> <p>Olá, Ana</p>

O HTML é o mesmo de sempre. A forma curta economiza onze caracteres e custa clareza: quem lê bind:value não sabe de qual variável se trata sem procurar no script. Em código de verdade, a forma longa com um nome descritivo (nome, quantidade, email) é a escolha padrão. A curta aparece em exemplos pequenos e em nomes que já são óbvios.

Cada tipo de elemento tem o seu binding. A tabela abaixo é o mapa; os próximos três capítulos abrem cada linha com calma.

Missão: as duas caixas guardam valores diferentes. Faça as duas mostrarem o mesmo nome: digitando ana na primeira, o parágrafo deve dizer Segundo: ana.

<script>
  let primeiro = $state('');
  let segundo = $state('');
</script>

<p>Segundo: {segundo}</p>
<input id="primeiro" bind:value={primeiro}>
<input id="segundo" bind:value={segundo}>
<script>
  let primeiro = $state('');
</script>

<p>Segundo: {primeiro}</p>
<input id="primeiro" bind:value={primeiro}>
<input id="segundo" bind:value={primeiro}>

A solução apaga a segunda variável. Duas variáveis ligadas a dois campos não se conversam sozinhas; o que faz as duas caixas andarem juntas é apontarem para o mesmo lugar. Se você quisesse valores independentes e sincronizados, precisaria de uma função que copiasse de um para o outro — e aí já não é bind, é regra de negócio.

8. O preço do bind

O bind é conforto, e conforto tem custo. O primeiro custo é de leitura: o HTML mostra bind:value={nome} e não mostra o que acontece a cada tecla. Quem lê o arquivo precisa saber o que o binding faz por baixo. Em um formulário de dez campos, isso significa dez lugares onde a tela escreve no estado sem que o código diga isso em palavras.

O segundo custo é de controle. Quando o valor precisa ser validado, formatado ou convertido antes de entrar no estado, o bind puro não serve: ele grava o que a pessoa digitou, sem passar por nenhuma decisão sua. Nessas horas, o caminho longo (value mais oninput) permite decidir antes de gravar, e o bind volta a ser útil depois que a decisão está tomada.

O terceiro custo é de dependência. Um bind cria uma ligação que só existe enquanto os dois lados estão vivos. Se o elemento sai da tela, a variável continua com o último valor; se a variável muda para um valor que o campo não aceita, o campo mostra o que der. Nada disso é erro, mas é comportamento que você precisa conhecer para não se surpreender.

Regra prática

Use bind:value quando a ligação é direta e o valor pode ser gravado como veio. Use value mais oninput quando existe uma regra entre a digitação e o estado — converter para número, cortar caracteres, recusar letras. O critério é simples: se você precisa decidir, não use o atalho.

9. Quando dá errado

Erro 1 — binding em elemento que não aceita

Cada nome de binding vale em certos elementos. bind:value é de campo, não de caixa de texto genérica.

<script>
  let texto = $state('');
</script>

<div bind:value={texto}>oi</div>
Erro de compilação (linha 5, coluna 5): `bind:value` can only be used with `<input>`, `<textarea>`, `<select>`

A mensagem lista os três elementos que aceitam esse binding. Um <div> não tem valor editável; para mostrar texto, use {texto} dentro dele. Quando o erro aparece, a pergunta útil é: "este elemento tem um valor que muda por dentro?".

Erro 2 — ligar a uma conta em vez de a uma variável

O lado direito do bind precisa ser um lugar onde se pode gravar: uma variável ou uma propriedade de objeto.

<script>
  let a = $state(1);
  let b = $state(2);
</script>

<input bind:value={a + b}>
Erro de compilação (linha 6, coluna 7): Can only bind to an Identifier or MemberExpression or a `{get, set}` pair

"Identifier" é um nome de variável; "MemberExpression" é um caminho como obj.campo. a + b é uma conta, um valor sem endereço — não há onde gravar o que a pessoa digitar. Crie uma variável para receber o texto e calcule a partir dela.

Erro 3 — binding em constante

O bind escreve na variável. Se ela é constante, não há o que escrever.

<script>
  const nome = 'Ana';
</script>

<input bind:value={nome}>
Erro de compilação (linha 5, coluna 7): Cannot bind to constant

A troca de const por let resolve. E lembre que o estado precisa da runa: let nome = $state('Ana'). Sem $state, o binding compila mas a tela não acompanha — o compilador chega a avisar com non_reactive_update quando percebe a variável sendo atualizada sem ser reativa.
