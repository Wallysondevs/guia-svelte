Svelte · svelte:boundary

A padaria da Ana tem um forno elétrico novo, e o eletricista instalou um disjuntor: quando algo dá curto, o disjuntor desliga a linha antes de o prédio pegar fogo. A tela de um componente precisa do mesmo aparelho. Um cálculo com dado errado, um gráfico que não carrega, uma lista com um item corrompido — qualquer um desses derruba a página inteira e deixa a pessoa olhando para o vazio. O svelte:boundary é o disjuntor: isola o estrago, mostra uma mensagem no lugar do conteúdo e oferece um botão para religar.

Você vai aprender
  • O que é um boundary e por que ele existe.
  • Como envolver uma parte da tela com <svelte:boundary>.
  • Como escrever o snippet failed com erro e reset.
  • Como usar onerror para registrar a falha em algum lugar.
  • Por que o botão de tentar de novo também precisa arrumar a causa.
  • O que o boundary não pega: erro de clique, erro no servidor, código fora da área.
  • Como usar dois boundaries para isolar dois widgets.
  • Onde vale a pena proteger e onde é exagero.
  • Os três erros reais desta aula, com a mensagem do compilador.

1. A ideia: o disjuntor da tela

Um disjuntor não conserta o curto. Ele faz duas coisas: impede que o curto derrube a casa inteira e dá um jeito de religar depois de o problema ser resolvido. Um boundary de tela é igual: ele não conserta o erro do seu código, ele impede que o erro apague a página toda e oferece um caminho de volta.

Sem boundary, o comportamento é drástico: um erro durante o desenho do componente interrompe o desenho, e o que a pessoa vê é a página pela metade ou completamente vazia. Pior: a pessoa não tem o que fazer, porque não há botão nenhum. Com boundary, a parte quebrada vira uma mensagem — e o resto da tela continua funcionando.

O caso clássico é o widget de fora: um gráfico, um mapa, um editor que você não escreveu. Você não controla o código dele, então não pode prometer que ele nunca vai falhar. Pode prometer que, se falhar, o cabeçalho e o carrinho vão continuar na tela.

O vocabulário: boundary é a área protegida; snippet é o pedaço de marcação com nome, que você já viu em {#snippet}; failed é o snippet que o Svelte desenha no lugar do conteúdo quando algo quebra; e reset é a função que reabre o disjuntor.

2. A área protegida

A tag é uma das tags especiais do Svelte, com o prefixo svelte:. Tudo o que está dentro dela fica protegido; tudo o que está fora continua sendo problema de quem escreveu.

<script>
  let quebrado = $state(false);
  let falhas = $state(0);

  function temperatura() {
    if (quebrado) throw new Error('o forno não acendeu');
    return '180 °C';
  }
</script>

<svelte:boundary>
  <p>Temperatura: {temperatura()}</p>
  <button onclick={() => (quebrado = true)}>ligar o forno</button>

  {#snippet failed(erro, reset)}
    <p>Deu erro: {erro.message}</p>
    <button onclick={() => { quebrado = false; falhas += 1; reset(); }}>
      tentar de novo
    </button>
  {/snippet}
</svelte:boundary>

<p>tentativas: {falhas}</p>

Na primeira renderização, nada quebrou: o compilador do servidor devolve o conteúdo normal e a contagem de tentativas em zero.

<p>Temperatura: 180 °C</p> <button>ligar o forno</button> <p>tentativas: 0</p>

No navegador, o botão "ligar o forno" muda o estado, a função temperatura() lança o erro e o boundary entra em ação. Este é o texto que aparece nesse momento, colhido no mesmo avaliador das caixas:

Deu erro: o forno não acendeu tentar de novo tentativas: 0
<svelte:boundary>
a área protegida. Se o desenho de qualquer coisa aqui dentro lançar erro, o conteúdo é substituído pelo snippet failed.
temperatura()
a função que lança o erro. O throw interrompe o desenho naquele ponto; o boundary captura e segue.
{#snippet failed(erro, reset)}
o plano B. Recebe o erro capturado e a função que reabre a área. Só existe dentro do boundary.
erro.message
o texto do erro, o mesmo que você escreveu no new Error(...). É o que a pessoa pode ler sem susto.
falhas += 1
a contagem de tentativas. Fica fora do boundary para continuar visível mesmo quando o conteúdo cai.

Repare que a contagem de tentativas não é restaurada pelo reset: ela mora no estado do componente que envolve o boundary, e o boundary só substitui o conteúdo interno. Essa separação é útil — o histórico de falhas sobrevive ao religamento.

3. O snippet failed: o que mostrar no lugar

O snippet recebe dois parâmetros, e os dois são opcionais na declaração mas úteis na prática. O primeiro é o erro, com mensagem e pilha. O segundo é o reset, uma função que manda o Svelte tentar desenhar o conteúdo de novo.

Uma mensagem boa tem três partes: o que a pessoa perdeu, o que ela pode fazer e um identificador para quem dá suporte. "Deu erro: Cannot read properties of undefined" cumpre a primeira e falha nas outras duas. "Os preços não carregaram. Tente de novo em instantes." cumpre as duas primeiras. O identificador pode ser um código curto que você registra junto com o erro completo.

O texto técnico tem seu lugar: no onerror, para o registro, e não na cara de quem está comprando pão. Se você precisa mostrar o detalhe para a equipe, use um endereço de desenvolvimento — nunca a mensagem crua em produção.

Não esconda o erro para sempre

Um boundary que engole tudo e nunca registra nada transforma um problema visível em problema invisível. O onerror existe para isso: mesmo que a tela mostre uma mensagem gentil, alguém precisa saber que a falha aconteceu, com a mensagem original e a hora.

4. onerror: o caderno do zelador

O atributo onerror recebe uma função chamada quando o boundary captura um erro. Ela recebe o erro e o reset, na mesma ordem do snippet. É o lugar de registrar: guardar a mensagem num estado para mostrar na tela, mandar para um serviço de monitoramento, incrementar um contador.

<script>
  let ultimoErro = $state('nenhum');

  function explodir() {
    throw new Error('o forno não acendeu');
  }

  function registrar(erro) {
    ultimoErro = erro.message;
  }
</script>

<svelte:boundary onerror={registrar}>
  <p>Conteúdo da vitrine</p>
  {#snippet failed(erro)}
    <p>A vitrine falhou: {erro.message}</p>
  {/snippet}
</svelte:boundary>

<p>último erro registrado: {ultimoErro}</p>

Fora do boundary, o registro do último erro aparece normalmente na primeira renderização:

<p>Conteúdo da vitrine</p> <p>último erro registrado: nenhum</p>

O onerror é chamado quando o erro é capturado, e o valor que ele grava fica disponível para a tela — inclusive para o parágrafo que está fora do boundary. Se você quiser mostrar o horário da falha, é ali que ele precisa ser capturado.

Missão: o boundary mostra a mensagem, mas o registro fora dele fica vazio. Faça o onerror guardar a mensagem do erro e a tela terminar com registrado: "o forno não acendeu".

<script>
  let ultimoErro = $state('');

  function explodir() {
    throw new Error('o forno não acendeu');
  }

  function registrar(erro) {
    ultimoErro = '';
  }
</script>

<svelte:boundary onerror={registrar}>
  <p>{explodir()}</p>
  {#snippet failed(erro)}
    <p>Deu erro: {erro.message}</p>
  {/snippet}
</svelte:boundary>

<p>registrado: "{ultimoErro}"</p>

5. reset: tentar de novo

O botão de religar é a parte que todo mundo esquece de testar. O reset manda o Svelte tentar desenhar o conteúdo outra vez — mas, se a causa do erro continua lá, o conteúdo quebra de novo, o boundary captura de novo e a pessoa vê a mesma mensagem. Um botão que não muda nada é pior que nenhum botão.

Por isso o handler do reset costuma fazer duas coisas: arrumar o estado que causou o erro e só então chamar reset(). No componente da seção 2, o handler faz quebrado = false antes. A ordem entre as duas linhas não muda o resultado aqui, porque o Svelte aplica as mudanças juntas no fim do evento; o que não pode é esquecer a primeira.

Missão: o botão "tentar de novo" chama reset, mas a tela volta para a mesma mensagem. Faça o segundo clique devolver tudo certo e o botão "ligar".

<script>
  let quebrado = $state(false);
</script>

<svelte:boundary>
  {#if quebrado}
    <p>{[].primeiro.nome}</p>
  {:else}
    <p>tudo certo</p>
  {/if}

  {#snippet failed(erro, reset)}
    <p>Deu erro: {erro.message}</p>
    <button class="reset" onclick={reset}>tentar de novo</button>
  {/snippet}
</svelte:boundary>

<button class="liga" onclick={() => (quebrado = true)}>ligar</button>
<script>

</script>

<svelte:boundary>

A mensagem que aparece no caso quebrado é a do erro de verdade: Cannot read properties of undefined (reading 'nome'). Ela é feia, e é exatamente por isso que o snippet failed deve traduzir: "Não foi possível carregar os preços" é o que a pessoa precisa ler; a mensagem crua vai para o registro.

6. O que o boundary não pega

O disjuntor protege a fiação daquele trecho, não a casa toda. Existem três buracos que confundem quem está começando, e os três aparecem na prática.

O primeiro: erro dentro de um event handler. O clique roda depois do desenho, fora do ciclo que o boundary observa. Se o handler lança, o erro vai para o console do navegador e a tela não muda. Para esse caso, use try/catch dentro do handler e guarde o erro num estado.

O segundo: erro durante a renderização no servidor. O boundary é uma peça de tempo de execução no navegador; no servidor, o desenho acontece de uma vez e o erro sobe. Quem protege a requisição no servidor é outra camada — o tratamento de erro do framework. O sintoma é claro: a página inteira falha, mesmo com o boundary no lugar.

O terceiro: conteúdo fora da área. Um boundary em volta da lista não protege o cabeçalho. Se o erro acontece antes da tag de abertura, ele não é capturado por nada.

7. Dois boundaries, dois estragos

Um boundary por widget é a regra de ouro quando a tela tem partes independentes. Se o gráfico de vendas quebra, a tabela de preços não tem por que sumir junto. Cada área protegida tem o próprio snippet, com uma mensagem específica — "o gráfico não carregou" diz mais do que "algo deu errado".

<script>
  function explodir() {
    throw new Error('o gráfico não carregou');
  }
</script>

<svelte:boundary>
  <p>preços de hoje</p>
  {#snippet failed(erro)}
    <p>Os preços não carregaram</p>
  {/snippet}
</svelte:boundary>

<svelte:boundary>
  <p>gráfico de vendas</p>
  {#snippet failed(erro)}
    <p>O gráfico não carregou</p>
  {/snippet}
</svelte:boundary>
<p>preços de hoje</p> <p>gráfico de vendas</p>

O custo de exagerar é o contrário: um boundary por botão transforma cada falha num retalho de mensagens diferentes, e a pessoa não entende que o problema é um só. O bom senso é agrupar por assunto: os preços juntos, o gráfico sozinho, a lista de pedidos em outro lugar.

8. Onde vale a pena proteger

Boundary não é enfeite para toda tela. Ele custa um pedaço a mais de marcação e um caminho a mais para testar. Vale a pena quando a falha de uma parte não deveria derrubar as outras e quando você tem uma mensagem útil para mostrar.

SituaçãoBoundary?Por quê
widget de terceiro (gráfico, mapa, editor)simvocê não controla o código dele
dados que vêm de fora e podem vir tortossima falha é esperada, não excepcional
formulário simples do próprio appraramenteerro aqui é bug seu; corrija o bug
componente que já valida os dadosnãoo erro não deveria existir
área com várias partes independentesum por parteisolar o estrago

Existe ainda o irmão do failed, o snippet pending, que mostra algo enquanto o conteúdo assíncrono ainda está a caminho. Ele faz sentido quando o conteúdo protegido espera dados; a aula sobre componentes assíncronos mostra esse caso com calma.

9. Quando dá errado

As três mensagens abaixo saíram do compilador e do renderizador desta versão, copiadas como estão.

Erro 1 — nome da tag escrito errado

As tags svelte: são poucas e fixas. Um e no lugar do a faz o compilador listar todas as que existem.

<p>fora</p>

<svelte:boundry>
  <p>dentro</p>
</svelte:boundry>
Erro de compilação (linha 3, coluna 1): Valid `<svelte:...>` tag names are svelte:head, svelte:options, svelte:window, svelte:document, svelte:body, svelte:element, svelte:component, svelte:self, svelte:fragment or svelte:boundary

A mensagem é comprida porque serve de lembrete: svelte:head, svelte:window, svelte:element, svelte:boundary e mais algumas. Para esta aula, o nome certo é svelte:boundary, com "a" depois do "d".

Erro 2 — o boundary não protege o servidor

O mesmo componente que funciona no navegador derruba a renderização do servidor. O erro sobe em vez de virar mensagem.

<script>
  function explodir() {
    throw new Error('o forno não acendeu');
  }
</script>

<svelte:boundary>
  <p>{explodir()}</p>
  {#snippet failed(erro, reset)}
    <p>Deu erro: {erro.message}</p>
  {/snippet}
</svelte:boundary>
Erro ao renderizar: o forno não acendeu

A tradução: durante o desenho do servidor, o erro foi lançado e ninguém o capturou. Para o servidor, use o tratamento de erro do framework; para o navegador, o boundary continua valendo.

Erro 3 — erro usado fora do snippet

O objeto do erro só existe dentro do snippet failed. Escrever {erro.message} no conteúdo normal faz o desenho procurar um nome que não foi declarado.

<svelte:boundary>
  <p>Deu erro: {erro.message}</p>
  {#snippet failed(erro, reset)}
    <p>falhou</p>
  {/snippet}
</svelte:boundary>
Erro ao renderizar: erro is not defined

"erro is not defined" quer dizer que o nome não existe naquele escopo. Para mostrar a mensagem, ela precisa estar dentro de {#snippet failed(erro)} ou guardada num estado pelo onerror.

10. O boundary não substitui o conserto

É tentador envolver tudo num boundary e considerar o assunto resolvido. O problema é que a tela passa a funcionar pela metade com mais frequência, e ninguém percebe: a mensagem é gentil, o layout não quebra, e o erro se acumula no registro sem que ninguém olhe.

O uso saudável é o inverso: boundary é rede de segurança, não plano principal. Se a mesma mensagem aparece toda semana no mesmo lugar, o boundary está fazendo o trabalho de um bug tracker — e o conserto é arrumar a causa, não melhorar o texto do snippet.

Vale também cuidar do estado depois da falha. Um carrinho que quebrou no meio pode ter ficado pela metade; o botão de tentar de novo deve recomeçar de um estado conhecido, não continuar de onde parou. No exemplo da seção 2, é por isso que o handler zera quebrado antes de chamar reset(): religar sem arrumar a causa é pedir para quebrar de novo.

Exercícios

1. O que o boundary faz quando o conteúdo lança um erro?

2. Qual erro o boundary não captura?

3. Por que o botão de reset costuma arrumar o estado antes de chamar reset()?

Complete o código

<svelte:boundary onerror={(erro) => registrar(erro)}>
  <Grafico />
  {#snippet (erro, reset)}
    <p>O gráfico não carregou</p>
  {/snippet}
</svelte:boundary>

Resumo

  • svelte:boundary isola o erro de uma parte da tela: o resto continua funcionando.
  • O snippet failed(erro, reset) substitui o conteúdo quebrado.
  • onerror registra a falha antes de a mensagem aparecer.
  • reset() reabre a área; sem arrumar a causa, o erro volta.
  • O boundary não pega erro de clique, erro no servidor nem conteúdo fora da tag.
  • Um boundary por widget independente; um por botão é exagero.
  • Mensagem boa diz o que se perdeu e o que fazer; o texto técnico vai para o registro.
  • Boundary é rede de segurança, não substituto do conserto.
  • O gêmeo pending cobre o tempo de espera do conteúdo assíncrono.
