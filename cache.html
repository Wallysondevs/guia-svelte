SvelteKit · Cache e Pré-render

A Ana descobriu que pão congelado, bem embalado, sai do forno tão bom quanto o do dia — desde que ela saiba o que congelar. O pão de queijo sim; a coxinha frita, não. Com página de site é igual: a página “sobre” pode ser preparada uma vez e servida igual para todo mundo; a página da conta de cada cliente, nunca. Esta aula mostra como o SvelteKit pré-renderiza, como os cabeçalhos de cache mudam o comportamento do navegador e o que acontece quando você congela a coisa errada.

Você vai aprender
  • O que é pré-renderizar: gerar o HTML no build em vez de no pedido.
  • Como ligar e desligar o pré-render com export const prerender.
  • O que sai na pasta build/prerendered e por que há arquivos .gz e .br.
  • Como o rastreador de links decide o que congelar.
  • Como definir cache-control com setHeaders.
  • Por que um cabeçalho definido numa página pré-renderizada não chega ao cliente.
  • Quais rotas não podem ser congeladas e o erro que o build dá.
  • O que acontece quando uma página de login vira arquivo estático.
  • Os três tropeços reais: ações num site estático, rota dinâmica sem entradas e cache que serve dado velho.

1. A ideia: o que dá para congelar

Congelar é trocar trabalho por espaço. A Ana congela pão de queijo porque ele é igual todos os dias, sai do forno em minutos e não depende de quem pediu. Ela não congela o pão recheado que o cliente monta na hora, com o recheio que ele escolheu.

No SvelteKit, pré-renderizar é exatamente isso: rodar a página durante o build, gerar o HTML final e guardar em arquivo. Quando alguém pedir aquela página, o servidor entrega o arquivo — não roda load, não consulta banco, não monta componente. É o pedido mais barato que existe, e é por isso que ele é a primeira otimização de qualquer site.

O custo aparece no dia em que o dado muda. Página congelada mostra o dado do dia do build até alguém compilar de novo. Se o preço do pão está no HTML congelado, mudar o preço no banco não muda a página. A pergunta que decide tudo é uma só: este conteúdo muda com que frequência, e quanto tempo de atraso o cliente aceita?

Na cozinha da AnaNo SvelteKit

2. As três camadas de cache

“Cache” não é uma coisa só. No caminho entre o banco e o olho do cliente existem três lugares onde a resposta pode ser guardada, e cada um tem o seu controle:

CamadaQuem guardaComo se controla
Builda pasta build/prerenderedexport const prerender
Servidoro processo Node e o proxysetHeaders, CDN, proxy
Navegadoro computador do clientecache-control, etag

A ordem importa: o build decide o que pode virar arquivo; o servidor decide por quanto tempo pode guardar a resposta; o navegador decide se pede de novo. Errar a camada do meio é comum — a página não é pré-renderizada, mas o cabeçalho diz “guarde por um dia”, e o cliente passa um dia vendo o preço antigo mesmo com o banco atualizado.

Existe ainda uma quarta camada que não é sua: o cache da plataforma. Netlify, Vercel e Cloudflare guardam respostas na borda, perto do cliente. As regras deles são configuradas no painel ou em arquivo próprio, e obedecem ao mesmo cache-control que você manda.

3. Pré-render: congelar no build

Ligar o pré-render é uma linha num arquivo +page.js. O arquivo não tem função nenhuma, só uma configuração:

export const prerender = true;

A escolha vale para a rota inteira. Também pode ser feita no +layout.js, e aí vale para todas as páginas abaixo dele — é assim que se congela o site inteiro de uma vez. No nível da página, ela vence a do layout, então dá para congelar tudo e abrir exceção para a área logada.

export const
uma constante exportada. O SvelteKit lê esse valor antes de renderizar, por isso ele não pode ser uma função nem depender de dado.
prerender
o nome exato que o framework procura. Outro nome é ignorado em silêncio.
= true
congela no build. Com false, a página é sempre renderizada no pedido.
+page.js
o arquivo de opções da página. Pode ser +page.server.js também; a diferença é que o segundo roda só no servidor.

Com o pré-render ligado, o build passa a rodar o app e registra cada página gerada:

Prerendering
GET /seo → 200 (34 ms)
GET /sobre → 200 (11 ms)
GET / → 204 (1 ms)
GET /produtos → 204 (2 ms)
GET /entrar → 204 (0 ms)

As duas primeiras linhas são páginas que viraram arquivo. As três com 204 foram visitadas pelo rastreador de links e não geraram arquivo — 204 é “sem conteúdo” e aqui significa “não foi prerenderizada”. Repare que os tempos são pequenos: isso é a página sendo montada uma vez, no seu computador, não a resposta para um cliente.

4. O que sai na pasta prerendered

Depois do build, os arquivos estão no disco. Listar a pasta é a forma mais direta de ver o que foi congelado:

ana@notebook:~/loja$ ls build/prerendered
conta.html
conta.html.br
conta.html.gz
seo
seo.html
seo.html.br
seo.html.gz
sobre
sobre.html
sobre.html.br
sobre.html.gz

Cada página aparece três vezes, em formatos diferentes. O .html é o texto original; o .gz é o mesmo texto comprimido com gzip; o .br é comprimido com Brotli, que costuma ser menor. O servidor escolhe pelo cabeçalho Accept-Encoding que o navegador manda — é por isso que os três existem. A pasta sem extensão (por exemplo seo) guarda o conteúdo auxiliar da rota, como o arquivo de dados que o cliente busca na navegação.

E tem um intruso na lista: conta.html. Ninguém escreveu prerender = true nessa página. O rastreador de links saiu da página inicial, seguiu o link do menu para /conta, recebeu o redirecionamento do hook e congelou o resultado. O conteúdo do arquivo mostra exatamente isso:

ana@notebook:~/loja$ wc -c build/prerendered/conta.html
112 build/prerendered/conta.html
ana@notebook:~/loja$ grep -o 'url=[^"]*' build/prerendered/conta.html
url=/entrar?de=/conta
ana@notebook:~/loja$ grep -c 'location.href' build/prerendered/conta.html
1

O arquivo tem 112 bytes e é um redirecionamento em duas técnicas: JavaScript e meta refresh. Nenhum dado vazou — a página de conta nunca foi renderizada com o usuário dentro. Mas o arquivo existe, é servido com status 200 e confunde qualquer conferência de segurança. A lição é revisar a pasta antes de publicar.

5. Caixa 1: o que pode ser congelado

A decisão de congelar é uma pergunta por rota. A caixa abaixo diz “congela” para as duas, inclusive para a página de conta, que depende de quem está logado.

Missão: mostre congela quando muda for falso e servidor quando for verdadeiro. O texto precisa conter /conta: servidor.

<script>
	const rotas = [
		{ caminho: '/sobre', muda: false },
		{ caminho: '/conta', muda: true }
	];
</script>

<ul>
	{#each rotas as r}
		<li>{r.caminho}: congela</li>
	{/each}
</ul>
<script>
	const rotas = [
		{ caminho: '/sobre', muda: false },
		{ caminho: '/conta', muda: true }
	];
</script>

<ul>
	{#each rotas as r}
		<li>{r.caminho}: {r.muda ? 'servidor' : 'congela'}</li>
	{/each}
</ul>

A regra por trás da caixa: se a página depende de cookie, de sessão ou de um dado que muda a cada pedido, ela é do servidor. Se a página é igual para todo mundo durante semanas, congele. Na dúvida, deixe no servidor — uma página no servidor funciona sempre; uma página congelada errada serve dado errado sem avisar ninguém.

6. Cabeçalhos: setHeaders e cache-control

A segunda camada é a do servidor. Dentro de um load, o objeto de contexto traz setHeaders, e o cabeçalho mais comum é o cache-control:

export function load({ setHeaders }) {
	setHeaders({ 'cache-control': 'max-age=60' });
	return { geradoEm: new Date().toISOString() };
}

A página calcula um valor novo a cada pedido e avisa que ele pode ser guardado por 60 segundos. Rodando o build e subindo o servidor, o cabeçalho aparece na resposta:

ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/cache | grep -i 'cache-control\|etag'
cache-control: max-age=60
etag: "ik6uzg"

max-age=60 quer dizer “pode guardar por sessenta segundos”. O etag é a impressão digital do conteúdo: o navegador manda o que tem, o servidor responde 304 Not Modified se for igual, e o corpo não viaja de novo. São mecanismos diferentes que se completam.

A política também pode ser representada na tela, numa página de diagnóstico que mostra as regras do site:

<script>
	let { segundos = 60 } = $props();
</script>

<p>cache-control: max-age={segundos}</p>
<p>cache-control: max-age=60</p>

Outros valores aparecem na prática. no-store diz “não guarde nada”, e é o certo para página de conta e de pagamento. s-maxage vale só para o cache compartilhado do proxy e da CDN. stale-while-revalidate permite entregar a versão velha enquanto a nova é buscada em segundo plano. Todos são texto no mesmo cabeçalho, e a escolha é sempre uma negociação entre frescor e velocidade.

Existe uma armadilha aqui. Se essa página fosse pré-renderizada, o cabeçalho não chegaria ao cliente: o arquivo estático não carrega a decisão do load, porque o load não roda no pedido. A comparação abaixo é de execuções reais no servidor de produção:

ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/congela-header | head -3
HTTP/1.1 200 OK
etag: "f-mdoX6ApbHtBcebMPcvwN47rXqoTj-vzRVIYf1qk3s"
vary: Accept-Encoding
ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/cache | head -3
HTTP/1.1 200 OK
cache-control: max-age=60

A página congelada devolve etag e vary, mas nenhum cache-control definido por você. Para controlar cache de página congelada, o lugar é a configuração do servidor ou da plataforma — não o load.

7. Caixa 2: um número, uma política

Cabeçalho de cache é decisão de produto escrita em número. Sessenta segundos é diferente de uma hora, e o texto precisa refletir a constante. A caixa abaixo tem a constante certa e o número errado no texto.

Missão: monte o texto usando a constante segundos, para sair cache-control: max-age=60.

<script>
	const segundos = 60;
</script>

<p>cache-control: max-age=3600</p>
<script>
	const segundos = 60;
</script>

<p>cache-control: max-age={segundos}</p>

Escrever o número duas vezes — na constante e no texto — é como a página passa a mentir depois de uma mudança. Com o buraco {segundos}, existe um só lugar para mudar. O mesmo raciocínio vale para o tempo de expiração do cookie, a taxa de entrega e o limite de itens do carrinho.

8. O que não pode ser congelado

Algumas construções do SvelteKit simplesmente não cabem num arquivo. A mais comum é a ação de formulário: uma página com actions recebe POST, e POST precisa de servidor. Quando você marca essa página como pré-renderizável, o build avisa:

SvelteKit error: prerender_actions
Cannot prerender pages with actions
https://svelte.dev/e/kit/prerender_actions
    at sessao (src/hooks.server.js:19:9)

A mensagem é curta e direta. O detalhe interessante é a linha de baixo: o erro aconteceu dentro do hook sessao, no arquivo src/hooks.server.js, linha 19 — porque foi o hook que tentou resolver a rota durante o build. Uma mensagem de pré-render pode apontar para um arquivo que você nem estava editando.

A lista do que não combina com pré-render inclui ações de formulário, páginas que dependem de cookie de sessão e rotas com parâmetro que não têm lista de entradas. Para estes casos existem duas saídas: deixar a página no servidor, ou usar fallback no adaptador estático, que entrega um HTML mínimo e deixa o JavaScript montar a página no navegador — a chamada SPA.

9. Caixa 3: a ordem das camadas

Saber a ordem ajuda a escolher onde mexer quando o cliente vê dado velho. A caixa abaixo lista as camadas fora de ordem.

Missão: ordene as camadas como o pedido caminha: primeiro o que foi congelado no build, depois o servidor, por último o navegador.

<script>
	const camadas = ['build', 'navegador', 'servidor'];
</script>

<p>Ordem: {camadas.join(' → ')}</p>
<script>
	const camadas = ['build', 'servidor', 'navegador'];
</script>

<p>Ordem: {camadas.join(' → ')}</p>

Com a ordem na cabeça, o diagnóstico fica rápido. Página pré-renderizada com dado velho: mexa no build, ou tire o pré-render. Página dinâmica com dado velho: confira o cache-control e o cache da plataforma. Página certa no servidor e errada no navegador: o problema está no cache do próprio cliente, e um recarregamento forçado resolve na hora de testar.

Repare que “talvez” aparece duas vezes. Não existe resposta única: depende de quanto tempo a Ana aceita mostrar o preço anterior. O que existe é a obrigação de decidir, porque o padrão — sem pré-render e sem cabeçalho — é sempre servir o dado fresco, ao custo de consultar o banco em cada pedido.

11. Quando dá errado

As três mensagens abaixo saíram de builds reais deste projeto. A primeira e a segunda são erros que interrompem o build; a terceira é um comportamento que não gera erro nenhum e por isso engana mais.

Erro 1 — página com ações marcada como estática

Basta uma página com actions receber prerender = true, ou herdar isso de um layout, para o build parar. O SvelteKit não consegue gerar um arquivo que receba POST.

SvelteKit error: prerender_actions
Cannot prerender pages with actions
https://svelte.dev/e/kit/prerender_actions
    at sessao (src/hooks.server.js:19:9)
GET /quebra-prerender → 500 (24 ms)
500 GET /quebra-prerender

Em desenvolvimento o sintoma é uma página 500; no build, o processo para. A correção é remover o prerender dessa rota ou tirar as ações dela, movendo o formulário para outra página. As duas coisas não convivem.

Erro 2 — rota dinâmica sem lista de entradas

Uma rota como /congela-id/[id] marcada como pré-renderizável precisa que alguém diga quais valores de id existem. Sem essa lista, o rastreador não encontra nenhum, e o build reclama.

prerender_unseen_routes
The following routes were marked as prerenderable, but were not prerendered because they were not found while crawling your app:
  - /congela-id/[id]
https://svelte.dev/e/kit/prerender_unseen_routes

To suppress or handle this error, implement `handleUnseenRoutes` in https://svelte.dev/docs/kit/@sveltejs-kit-vite#prerender

error during build:
[Error: Prerendering failed] {
  plugin: 'vite-plugin-sveltekit-compile',
  hook: 'buildApp'
}

O nome do erro diz o que aconteceu: rotas marcadas, não vistas. A saída é gerar a lista com a opção entries do pré-render — entries: ['1', '2', '3'] — ou deixar a rota no servidor. Para um catálogo que cresce todo dia, a lista costuma vir do banco durante o build.

Aviso 3 — a página de login que virou arquivo

Nenhum erro aparece, e é justamente o problema. O rastreador seguiu o link do menu, recebeu o redirecionamento do hook e congelou o resultado em conta.html. Em produção, o pedido a /conta devolve 200, sem passar pelo hook.

ana@notebook:~/loja$ wc -c build/prerendered/conta.html
112 build/prerendered/conta.html
ana@notebook:~/loja$ grep -o 'url=[^"]*' build/prerendered/conta.html
url=/entrar?de=/conta
ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/conta | head -3
HTTP/1.1 200 OK
etag: "7-DYfYF_Azx3mHEh08LY_w65McduCKKcStU7BxjvvLY"
vary: Accept-Encoding

O status 200 para uma página protegida assusta, mesmo quando o corpo é só um redirecionamento. A correção é excluir a área logada do pré-render — export const prerender = false no layout da área — e revisar a pasta depois de cada build.

Exercícios

2. Por que uma página de conta não deve ser pré-renderizada?

// src/routes/sobre/+page.js
export const = true;

Resumo

  • Pré-renderizar é gerar o HTML no build e servir arquivo pronto, sem rodar load.
  • export const prerender = true vale para a rota; no layout, vale para tudo abaixo.
  • O build mostra Prerendering e o status de cada página; 204 é “visitada e não gerada”.
  • A pasta build/prerendered guarda .html, .gz e .br de cada página.
  • O rastreador de links congela páginas alcançáveis — inclusive um redirecionamento de login.
  • setHeaders({ 'cache-control': 'max-age=60' }) controla o cache do servidor nas páginas dinâmicas.
  • Página pré-renderizada não leva o cache-control do load: não há load no pedido.
  • prerender_actions avisa que página com ações não pode ser congelada.
  • prerender_unseen_routes avisa que rota dinâmica precisa de lista de entradas.
  • Cache tem três camadas — build, servidor e navegador — e cada uma tem seu controle.
