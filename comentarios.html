Svelte · Comentários

A Ana anota nas margens do caderno de receitas: "o forno aqui é mais forte", "usar menos açúcar em julho". São recados para ela mesma, não para o cliente. Ninguém compra um pão com a anotação escrita na casca. Comentário em código é isso: uma anotação para quem lê o arquivo, que o programa ignora — e que o navegador não deve receber. Nesta aula você aprende as três sintaxes, onde cada uma vale e por que escrever bem um comentário é tão importante quanto não escrever nenhum.

Você vai aprender
  • As três sintaxes de comentário: //, /* */ e <!-- -->.
  • Em qual bloco cada sintaxe funciona e em qual quebra o arquivo.
  • Por que os comentários desaparecem do HTML gerado.
  • Como usar comentário para desligar um pedaço de marcação.
  • O que acontece quando você escreve // no meio do HTML.
  • Para que serve o comentário especial svelte-ignore.
  • Por que comentário não é lugar de senha nem de dado pessoal.
  • O que o build faz com os comentários do CSS.
  • Os erros reais: comentário de HTML dentro do script, comentário de JS solto no HTML e comentário sem fechar.

1. A ideia: a anotação na margem

Existe uma diferença entre o que o cliente lê e o que a Ana precisa lembrar. O cliente lê "PÃO FRANCÊS — R$ 0,90". A Ana precisa lembrar "o preço sobe em janeiro" e "o fornecedor novo entrega mais tarde". Se ela escrevesse tudo na placa, o cliente veria informação interna. Por isso a placa tem só o preço, e o caderno tem as anotações.

Comentário em código é a anotação do caderno. Ele fica no arquivo, ao lado do código, mas não vira programa: o compilador o descarta. Você pode escrever o motivo de uma decisão, um aviso para o próximo a mexer no arquivo, uma explicação de uma conta complicada. O navegador nunca vê esse texto — e isso é uma vantagem de segurança, como veremos.

Existe também o comentário que desliga código. Em vez de apagar três linhas que talvez você use amanhã, você as comenta: elas continuam no arquivo, mas deixam de valer. É o equivalente a cobrir uma placa com um pano em vez de arrancar a placa da parede. Útil durante testes, perigoso quando vira hábito — código comentado acumula poeira e ninguém sabe se ainda serve.

2. Comentário de JavaScript: // e /* */

Dentro do bloco <script> roda JavaScript, então valem as duas formas de comentário da linguagem. A primeira é de uma linha só, começando com duas barras:

<script>
  // o preço do pão passou a valer em novembro
  let preco = $state(0.9);

  /* a conta abaixo aplica o desconto de 10%
     para pagamento no dinheiro */
  let desconto = $state(preco * 0.1);
</script>

<p>R$ {preco.toFixed(2)}</p>
<p>Desconto: R$ {desconto.toFixed(2)}</p>
<p>R$ 0.90</p> <p>Desconto: R$ 0.09</p>

Repare no que a saída não tem: nenhuma das duas anotações. O compilador leu o script, executou as contas e escreveu os valores no HTML. O texto dos comentários não chegou nem perto da página.

//
comentário de uma linha. Vale do // até o fim daquela linha; o que vier depois é ignorado pelo motor.
/*
abre o comentário de bloco. Pode atravessar várias linhas e é o formato para explicações mais longas.
*/
fecha o bloco. Se faltar, o compilador lê o resto do arquivo como comentário e reclama no fim.
o texto
o que você escreve aqui não é executado nem mostrado: é margem do caderno, para quem lê o arquivo.

O comentário de bloco, entre /* e */, pode ocupar várias linhas e é o mais indicado para explicar uma decisão com contexto. O de linha, //, serve para uma observação curta. Os dois são ignorados igualmente pelo motor JavaScript — a diferença é de leitura, não de comportamento.

Repare que o comentário de bloco é o único que aceita várias linhas. Em troca, ele tem uma regra chata: não aninha. Um /* dentro de outro comentário não abre nada — o primeiro */ que aparecer fecha tudo, e o que sobra vira código inválido.

Uma armadilha do comentário de bloco: ele não aninha. Se você escrever /* começo /* meio */ fim */, o comentário termina no primeiro */ e o resto vira código inválido. Em código de verdade, isso aparece quando alguém comenta um trecho que já tinha comentário — vale conferir antes de salvar.

Missão: a Ana usou um comentário de HTML dentro do <script> e o compilador recusa. Troque pela sintaxe de comentário de JavaScript, mantendo o preço em 0.90.

<script>
  <!-- lembrar: o preço antigo era 0.75 -->
  let preco = $state(0.9);
</script>

<p>R$ {preco.toFixed(2)}</p>
<script>
  // lembrar: o preço antigo era 0.75
  let preco = $state(0.9);
</script>

<p>R$ {preco.toFixed(2)}</p>

A mensagem que aparece na caixa é Unexpected token — "token inesperado". O compilador não traduz o motivo em português claro porque, para ele, aquilo é apenas um caractere que não podia estar ali. A pista é a posição: a linha 2, dentro do script, onde só deveria haver JavaScript.

3. Comentário de HTML: <!-- -->

No bloco de marcação, o comentário é o do HTML: começa com <!-- e termina com -->. Ele pode ocupar várias linhas e serve para anotar o que é aquela seção, ou para esconder um pedaço de marcação.

<script>
  let preco = $state(0.9);
</script>

<!-- cabeçalho da vitrine -->
<h1>Pão francês</h1>

<!-- o parágrafo abaixo está fora do ar até a nova tabela chegar
<p>Tabela de preços em breve</p>
-->

<p>R$ {preco.toFixed(2)}</p>
<h1>Pão francês</h1> <p>R$ 0.90</p>

Os dois comentários desapareceram, e o parágrafo que estava dentro do segundo também. Esse é o truque para desligar marcação sem apagar: coloque <!-- antes e --> depois. Enquanto estiver ali, o navegador nem sabe que existe.

Repare que o comentário de várias linhas tem um detalhe: o fechamento --> pode ficar em uma linha só dele, como no exemplo. Não importa a formatação, só o par de abertura e fechamento. O que está no meio é ignorado.

Missão: a placa mostra "Padaria" e "Pão" juntos. Use um comentário de HTML para esconder o parágrafo do pão, deixando só o título na tela.

<h1>Padaria</h1>
<p>Pão</p>
<h1>Padaria</h1>
<!-- <p>Pão</p> -->

A meta desta caixa confere o texto inteiro da tela: só "Padaria", sem o "Pão". É a forma mais direta de ver que o comentário realmente tirou o parágrafo de circulação, em vez de só escondê-lo com CSS.

4. Comentário de CSS: /* */ dentro do estilo

No bloco <style>, o comentário é o do CSS: /* até */. Ele aparece na saída do compilador, porque faz parte do CSS gerado:

<h1>Pão francês</h1>

<style>
  /* a cor vem da identidade da padaria */
  h1 { color: #2e7d32; }
</style>
/* a cor vem da identidade da padaria */
  h1.svelte-1n46o8q { color: #2e7d32; }

Duas coisas para notar. A primeira: o comentário sobreviveu à compilação, ao contrário do que acontece no script e no HTML. A segunda: o seletor ganhou o selo svelte-1n46o8q, o mesmo das aulas anteriores.

No build de produção, porém, o comentário do CSS é removido pelo minificador. O que sobra é só a regra, comprimida. Guarde essa diferença: durante o desenvolvimento você vê o comentário; no arquivo publicado, não. Se a intenção era documentar, o lugar definitivo é o código-fonte, não o arquivo gerado.

Um comentário de CSS não pode ficar aberto. Se faltar o */, o compilador continua lendo tudo como comentário até o fim do arquivo e reclama com Expected token */. É o equivalente ao comentário de HTML sem fechar, que veremos adiante.

5. O que o compilador faz com cada um

A tabela abaixo resume o destino de cada sintaxe. Ela vale como consulta rápida quando você não lembra onde pode escrever o quê.

SintaxeOnde valeAparece na saída?
// …dentro do <script>não
/* … */dentro do <script> ou do <style>no CSS sim; no build, não
<!-- … -->na marcação, entre tagsnão
<!-- svelte-ignore … -->na marcação, antes do elementonão (e muda um aviso)

O caso que mais confunde é o do meio: /* */ vale nos dois blocos de código (script e estilo), mas com destinos diferentes. No script, o comentário é descartado antes de qualquer coisa. No estilo, ele faz parte do CSS e só some na minificação.

Já o comentário de HTML vale apenas na marcação. Colocá-lo dentro do script é erro de sintaxe, porque o JavaScript não conhece essa sintaxe. É o primeiro cenário desta aula, com a mensagem real.

6. // no HTML não é comentário

Quem vem de JavaScript escreve // por reflexo, em qualquer lugar. No meio da marcação, essas duas barras não comentam nada: elas são texto, e texto aparece na tela.

<script>
  let nome = $state('Ana');
</script>

<p>Olá, {nome}</p>
// anotação do dia
<p>Olá, Ana</p> // anotação do dia

O compilador não tem como adivinhar que aquilo era uma anotação. Para ele, é uma sequência de caracteres no meio do HTML, e o HTML aceita texto solto. O resultado é a frase aparecendo na página, muitas vezes no rodapé, sem que você entenda de onde veio.

A correção tem duas formas: mover a anotação para dentro do <script>, onde // funciona, ou trocar por um comentário de HTML. Mover para o script costuma ser melhor quando a anotação é sobre o código; usar <!-- --> faz sentido quando é sobre a estrutura da página.

Missão: a anotação com // ficou fora do script e aparece na tela. Leve a anotação para dentro do <script>, para que a página mostre só "Olá, Ana".

<script>
  let nome = $state('Ana');
</script>

<p>Olá, {nome}</p>
// anotação do dia
<script>
  let nome = $state('Ana');
  // anotação do dia
</script>

<p>Olá, {nome}</p>

A meta confere o texto inteiro: "Olá, Ana", sem sobra. Esse tipo de conferência é útil porque o erro não quebra nada — só suja a tela, e às vezes passa despercebido em uma revisão rápida.

7. svelte-ignore: o comentário que fala com o compilador

Existe um comentário especial que não é para humanos: o svelte-ignore. Ele fica na marcação, antes de um elemento, e diz ao compilador para não emitir um aviso específico naquele elemento. É a forma de assumir uma escolha de propósito, em vez de deixar o aviso aparecer para sempre.

<script>
  let itens = ['pão'];
</script>

<!-- svelte-ignore a11y_click_events_have_key_events -->
<div onclick={() => itens.push('bolo')}>comprar</div>

O aviso silenciado é de acessibilidade: um elemento que responde a clique mas não pode ser alcançado pelo teclado. Silenciar não corrige o problema — só esconde o alerta. A atitude honesta é corrigir; o svelte-ignore fica reservado para casos em que você sabe o que está fazendo e tem um motivo.

Se o código do aviso estiver errado, o svelte-ignore não faz nada e o aviso continua aparecendo. Os códigos são os que o próprio compilador imprime (na saída do guia, aparecem como css_unused_selector, a11y_no_static_element_interactions e outros). Copie da mensagem, não invente.

Existe também o svelte-ignore para erros de acessibilidade em elementos específicos, e a versão de arquivo inteiro, com a diretiva no começo do arquivo. Antes de usar qualquer uma, pergunte: o aviso está apontando um problema real? Se sim, o comentário é uma venda, não um remédio.

8. Comentário não é lugar de segredo

Como o comentário do script e do HTML é descartado na compilação, ele não chega ao navegador do cliente. Isso dá uma falsa sensação de segurança: "posso deixar a senha aqui, ninguém vê". Não pode. O comentário continua no repositório, no histórico do git e nas cópias que outras pessoas baixam. Apagar depois não apaga o passado.

A regra prática: nada de senha, chave de API, dado pessoal de cliente ou endereço interno em comentário, nem em código. Se precisa registrar uma informação sensível, ela vai para um arquivo de configuração que não é versionado, como um .env. O comentário é público para quem tem o código, e o código costuma ser mais compartilhado do que parece.

Existe um efeito colateral curioso de o comentário não chegar ao navegador: quem inspeciona a página não encontra pistas do seu trabalho. Em projetos antigos, era comum ver no código-fonte do site recados como "versão 2.1, revisar o carrinho". Hoje, com compilador e minificador, essas notas somem. Quem precisa delas é o time, e o lugar do time é o repositório — não o arquivo publicado.

O inverso também vale: comentário bom não repete o código. // soma 1 ao contador em cima de contador++ não ajuda ninguém. O que ajuda é o porquê: "o contador começa em 1 porque o primeiro pão já está na sacola". Uma frase dessas economiza meia hora de quem chegar depois — inclusive você, em três meses.

9. O que o build faz com os comentários

Para fechar a ideia, o teste do mundo real: gerar o build e procurar o texto dos comentários nos arquivos finais. O componente abaixo tem um comentário de JavaScript, um de HTML e um de CSS:

<script>
  // o preço antigo era 0.75
  let preco = $state(0.9);
</script>

<!-- este comentário é de HTML -->
<h1>Pão francês</h1>
<p>R$ {preco.toFixed(2)}</p>

<style>
  /* a cor vem da identidade da padaria */
  h1 { color: #2e7d32; }
</style>
<h1 class="svelte-1n46o8q">Pão francês</h1> <p>R$ 0.90</p>

No build, o CSS e o JavaScript saem em arquivos separados, cada um com hash no nome:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v7.3.8 building client environment for production...
transforming...
✓ 112 modules transformed.
rendering chunks...
computing gzip size...
dist/index.html                  0.32 kB │ gzip:  0.23 kB
dist/assets/index-BPubFjsH.css   0.03 kB │ gzip:  0.05 kB
dist/assets/index-Q4u7RwmO.js   35.98 kB │ gzip: 13.90 kB
✓ built in 2.24s

Agora a busca pelo texto dos comentários dentro do arquivo JavaScript gerado. O grep -c conta quantas linhas casam com o padrão:

ana@notebook:~/loja$ grep -c "Pão francês" dist/assets/index-Q4u7RwmO.js
1
ana@notebook:~/loja$ grep -c "preço antigo" dist/assets/index-Q4u7RwmO.js
0
ana@notebook:~/loja$ grep -c "comentário" dist/assets/index-Q4u7RwmO.js
0

O texto que aparece na tela está lá (1). Os dois comentários, não (0 e 0). O compilador e o minificador cumpriram o papel: o arquivo publicado tem só o necessário. É por isso que comentar não deixa o site mais pesado — e é por isso que um comentário nunca deve ser usado como documentação para o usuário final, porque ele não chega até ele.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Todas são comentário no lugar errado ou sem fechamento.

Erro 1 — comentário de JS solto no HTML

A forma {/* … */} só vale dentro de uma expressão. Solta entre duas tags, ela não é comentário: o compilador tenta ler como código e para.

<p>Pão</p>
{/* comentário de JavaScript no HTML */}
<p>Bolo</p>
Erro de compilação (linha 2, coluna 39): Unexpected token

Para comentar marcação, use <!-- … -->. A forma com chaves é útil dentro de uma expressão, como {nome /* o nome do cadastro */}, e só ali.

Erro 2 — comentário de CSS sem fechar

Faltou o */. O compilador lê o resto do estilo como comentário e avisa no fim do arquivo.

<p>Pão</p>

<style>
  /* comentário sem fim
  p { color: green; }
</style>
Erro de compilação (linha 6, coluna 8): Expected token */

"Expected token */" quer dizer "esperava o fechamento do comentário". Comente sempre em pares: abriu com /*, feche com */ na mesma hora, e escreva o texto no meio depois.

Erro 3 — comentário de HTML sem fechar

O --> ficou faltando. O compilador continua procurando o fim do comentário até o arquivo acabar.

<p>Olá</p>
<!-- sem fim
<p>Ana</p>
Erro de compilação (linha 3, coluna 10): Expected token -->

A posição aponta para o fim do arquivo, onde o compilador desistiu — não para a linha do comentário. Quando a mensagem falar de "token" no fim do arquivo, desconfie de um comentário aberto antes.

Resumo

  • // e /* */ valem dentro do <script>.
  • <!-- … --> vale na marcação e é a forma de esconder um trecho de HTML.
  • /* */ também vale no <style>, mas o build remove esses comentários.
  • Comentários do script e do HTML não chegam ao navegador.
  • // no meio do HTML não comenta nada: aparece como texto na tela.
  • svelte-ignore silencia um aviso específico e não corrige o problema.
  • Nunca escreva senha, chave ou dado pessoal em comentário.
  • Comentário bom explica o porquê; repetir o código não ajuda ninguém.
  • Os erros desta aula: sintaxe de outro bloco, comentário de CSS sem fechar e comentário de HTML sem fechar.
