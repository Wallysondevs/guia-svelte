Svelte · Componentes Pequenos

O App.svelte da Ana chegou a duzentas linhas. Dentro dele tem a vitrine, o carrinho, o cálculo do frete e o rodapé com o endereço da padaria. Quando o frete mudou, ela passou meia hora procurando a linha certa. Nesta aula ela aprende a quebrar o arquivo em peças de um trabalho só — e a decidir quando quebrar vale a pena e quando só espalha o problema.

Você vai aprender
  • O que faz um componente ser “grande” de verdade, além do número de linhas.
  • Como dividir um componente em peças com um trabalho cada.
  • Como uma peça recebe dados de fora com $props().
  • Por que valor padrão evita peça quebrada em demonstração.
  • Como a lista monta vários pedaços iguais com {#each}.
  • Quando mover a conta do HTML para uma função com nome.
  • O sinal de que dividir cedo demais também custa caro.
  • Como medir o tamanho real dos arquivos com wc -l.
  • Os três erros de $props() desta aula, com a mensagem do compilador.

1. A ideia: uma peça, um trabalho

Na cozinha da padaria, ninguém usa uma ferramenta só para tudo. A colher de pau mexe, a forma assa, a faca corta. Uma ferramenta que fizesse as três coisas seria péssima nas três — e ninguém saberia onde guardá-la.

Componente é ferramenta. Um componente que faz a vitrine, o carrinho e o rodapé ao mesmo tempo é o mesmo problema: não dá para reaproveitar a vitrine em outra página sem levar o carrinho junto, não dá para testar o rodapé sozinho, e a menor mudança exige entender o arquivo inteiro.

Um componente pequeno tem um trabalho, que cabe numa frase: “mostra um cartão de produto”, “formata um preço”, “mostra a lista de produtos”. Se você precisa de “e” para descrever o que ele faz, provavelmente são dois componentes dentro de um.

2. Como saber que o componente está grande

Contar linhas ajuda pouco: um arquivo de oitenta linhas com quatro responsabilidades é pior que um de duzentas com uma tabela de configuração. O que denuncia o exagero são outros sinais:

SinalO que costuma significar
Você precisa do “e” para descrever o componenteDuas ou mais responsabilidades juntas
Um bloco de HTML se repete quase igualFalta uma peça que receba o que muda
A conta aparece no meio do HTMLFalta uma função com nome
Você rola a tela para achar a parte que quer mudarO arquivo já não cabe na cabeça
Mudar o rodapé quebrou a vitrineAs partes compartilham estado sem precisar

Repare que nenhum sinal fala de número. O critério é de leitura: se para mexer numa parte você precisa entender três, o arquivo está grande. E o contrário também vale — se para entender uma linha você precisa abrir quatro arquivos, a divisão passou do ponto. Voltamos a isso na seção 9.

3. O componente que faz tudo

Esta é a vitrine da Ana antes da divisão. Ela mostra os produtos, formata os preços e calcula o total — tudo no mesmo lugar:

<script>
  let produtos = $state([
    { nome: 'Pão francês', preco: 0.9 },
    { nome: 'Sonho', preco: 2.5 }
  ]);
  let total = $derived(produtos.reduce((soma, p) => soma + p.preco, 0));
</script>

<h1>Vitrine</h1>

{#each produtos as produto}
  <article>
    <h2>{produto.nome}</h2>
    <p>R$ {produto.preco.toFixed(2)}</p>
  </article>
{/each}

<p>Total: R$ {total.toFixed(2)}</p>
<h1>Vitrine</h1> <article><h2>Pão francês</h2> <p>R$ 0.90</p></article><article><h2>Sonho</h2> <p>R$ 2.50</p></article> <p>Total: R$ 3.40</p>

Vinte linhas, tudo funcionando. O problema não é o tamanho de hoje: é o crescimento. Amanhã entram a foto do produto, o botão de adicionar ao carrinho e o selo de promoção. Cada um desses entra no mesmo {#each}, e a vitrine vira o arquivo que ninguém quer abrir.

O detalhe mais importante está na linha do <article>: ela desenha um produto. O {#each} repete essa linha para cada item da lista. Ou seja, o arquivo já sabe qual é a peça — ele só não deu nome a ela.

<script>
guarda duas coisas de naturezas diferentes: os dados (produtos) e o total derivado. Já são duas responsabilidades no mesmo bloco.
<h1>Vitrine</h1>
o título da página. Isso não é papel de um cartão de produto; é papel de quem monta a página.
{#each produtos as produto}
o laço que monta a lista. O nome produto é o item da vez, e é ele que a peça precisa receber.
<article> … </article>
o desenho de um produto: título e preço. Esse bloco é o candidato natural a virar componente.
R$ {produto.preco.toFixed(2)}
formatação do dinheiro no meio do HTML. Repete em qualquer outro lugar que mostre preço.

Missão: o componente desenha só o primeiro produto, porque a lista está escrita à mão. Transforme o bloco em um {#each} que repete o <article> para cada produto — assim a peça passa a valer para a lista inteira.

<script>
  let produtos = $state([
    { nome: 'Pão francês', preco: 0.9 },
    { nome: 'Sonho', preco: 2.5 }
  ]);
</script>

<article>
  <h2>{produtos[0].nome}</h2>
  <p>R$ {produtos[0].preco.toFixed(2)}</p>
</article>
<script>
  let produtos = $state([
    { nome: 'Pão francês', preco: 0.9 },
    { nome: 'Sonho', preco: 2.5 }
  ]);
</script>

{#each produtos as produto}
  <article>
    <h2>{produto.nome}</h2>
    <p>R$ {produto.preco.toFixed(2)}</p>
  </article>
{/each}

Repare no que mudou: nenhuma informação nova apareceu. A lista já tinha dois produtos; o que faltava era o mecanismo que percorre. O {#each} é a ponte entre “uma peça” e “a lista de peças”, e é isso que permite dividir o componente sem repetir HTML.

4. A primeira divisão: nasce o cartão

Agora o bloco que desenha um produto ganha arquivo próprio. Ele recebe o título e o preço de fora, e não sabe de onde vieram:

<script>
  let { titulo = 'Pão francês', preco = 0.9 } = $props();
</script>

<article>
  <h2>{titulo}</h2>
  <p>R$ {preco.toFixed(2)}</p>
</article>
<article><h2>Pão francês</h2> <p>R$ 0.90</p></article>

O componente ficou com oito linhas e uma frase de descrição: “mostra um cartão de produto”. Nada de lista, nada de total, nada de título de página. Quem chama decide quais dados passar:

<script>
  import Cartao from './lib/Cartao.svelte';

  let produtos = $state([
    { nome: 'Pão francês', preco: 0.9 },
    { nome: 'Sonho', preco: 2.5 }
  ]);
</script>

<h1>Vitrine</h1>

{#each produtos as produto}
  <Cartao titulo={produto.nome} preco={produto.preco} />
{/each}

Sobrou para o App o trabalho de montar a página: título, lista e ordem. Sobrou para o Cartao o trabalho de desenhar. Cada um pode mudar sem arrastar o outro — desde que o contrato de dados continue o mesmo.

let { titulo = 'Pão francês', preco = 0.9 } = $props()
declara que o componente recebe duas propriedades. O que vem antes do = é o nome que chega; depois do = é o valor padrão, usado quando ninguém passa nada.
{titulo}
usa o valor recebido dentro do HTML. O componente trata titulo como um dado local — ele não sabe nem se importa de onde veio.
<Cartao titulo={produto.nome} preco={produto.preco} />
do lado de quem chama, o nome na esquerda é a propriedade; o valor entre chaves é a expressão que produz o dado.

Existe um custo nessa divisão, e ele é real: agora são dois arquivos para ler quando algo não aparece na tela. Se o cartão mostra o preço errado, você não sabe de longe se o problema é a conta no App ou a formatação no Cartao. O ganho vem quando a peça é usada em vários lugares — aí o custo é pago uma vez só.

5. A segunda divisão: a linha de preço

A formatação de dinheiro aparece em mais de um lugar. Em vez de repetir toFixed(2) em cada um, a Ana criou uma peça mínima:

<script>
  let { valor = 0 } = $props();
</script>

<span>R$ {valor.toFixed(2)}</span>
<span>R$ 0.00</span>

Cinco linhas. Um trabalho: mostrar um valor em reais. O valor padrão 0 garante que a peça nunca quebre sozinha — sem ele, valor seria undefined e undefined.toFixed(2) derrubaria o componente. Isso não é detalhe de estilo: é a diferença entre uma peça que aguenta ser usada e uma que exige que todo mundo passe tudo.

Com as duas peças prontas, o App fica assim:

<script>
  import Cartao from './lib/Cartao.svelte';
  import PrecoLinha from './lib/PrecoLinha.svelte';

  let produtos = $state([
    { nome: 'Pão francês', preco: 0.9 },
    { nome: 'Sonho', preco: 2.5 }
  ]);
</script>

<h1>Vitrine</h1>

{#each produtos as produto}
  <Cartao titulo={produto.nome} preco={produto.preco} />
{/each}

<p>Menor preço: <PrecoLinha valor={0.9} /></p>

O arquivo principal continua montando; as peças continuam desenhando. É a mesma divisão de trabalho de uma cozinha: quem monta o prato é o cozinheiro, quem faz o molho é a panela. Se o molho mudar de receita, o prato continua igual.

Missão: o cartão recebe a propriedade nome, mas o HTML usa titulo, que não existe — e a tela quebra. Faça o HTML usar o nome que o componente realmente recebe, com o valor padrão 'Pão francês'.

<script>
  let { nome } = $props();
</script>

<h2>{titulo}</h2>
<script>
  let { nome = 'Pão francês' } = $props();
</script>

<h2>{nome}</h2>

A caixa mostra a mensagem titulo is not defined ao rodar o código inicial. É sempre a mesma história: propriedade é nome combinado entre duas partes. Se a peça declara nome, quem chama tem de passar nome — e o HTML de dentro tem de usar nome também.

6. A conta sai do HTML e ganha nome

Conta no meio do HTML funciona, mas não tem nome e por isso não pode ser reaproveitada nem conferida sozinha. Veja o caso do total:

<script>
  let preco = $state(0.9);
  let quantidade = $state(3);
</script>

<p>Total: R$ {preco * quantidade}</p>
<p>Total: R$ 2.7</p>

A conta está certa e a tela mostra 2.7. Para uma padaria, o preço é 2.70 — e a diferença não é de matemática, é de apresentação. Arrumar isso com a conta solta no HTML significa mexer na expressão toda; arrumar com uma função significa dar um nome ao cálculo:

<script>
  let preco = $state(0.9);
  let quantidade = $state(3);

  function calcularTotal() {
    return preco * quantidade;
  }
</script>

<p>Total: R$ {calcularTotal().toFixed(2)}</p>
<p>Total: R$ 2.70</p>

Agora existem dois assuntos separados: quanto é (a função) e como mostrar (o toFixed na tela). Se amanhã o total ganhar desconto, você muda a função e a tela não precisa saber. Se amanhã o preço tiver três casas, você muda a tela e a conta continua igual.

Missão: o total aparece como R$ 2.7, sem a segunda casa. Tire a conta do HTML: crie a função calcularTotal() que multiplica os dois valores e formate o resultado com duas casas.

<script>
  let preco = $state(0.9);
  let quantidade = $state(3);
</script>

<p>Total: R$ {preco * quantidade}</p>
<script>
  let preco = $state(0.9);
  let quantidade = $state(3);

  function calcularTotal() {
    return preco * quantidade;
  }
</script>

<p>Total: R$ {calcularTotal().toFixed(2)}</p>

A função enxerga preco e quantidade porque está no mesmo arquivo, e elas são variáveis de estado. Se uma delas mudar, o Svelte chama a função de novo e a tela se atualiza — sem $derived, sem nada extra. A conta virou parte do desenho.

7. O contrato entre as peças

Dividir componente é criar contratos. O Cartao promete desenhar um produto se receber titulo e preco; o App promete passar os dois. Se um dos lados muda o nome, o contrato quebra — e quebra de um jeito silencioso, porque o Svelte não reclama de propriedade que ninguém passou.

No componente que recebeNo componente que usa
let { titulo } = $props();<Cartao titulo="Pão" />
let { preco = 0 } = $props();<Cartao preco={0.9} /> ou sem passar nada
let { item } = $props(); (objeto)<Cartao item={produto} />

Repare na segunda linha: quem declara preco = 0 aceita ser chamado sem preco. Quem declara só preco não aceita — vai receber undefined e quebrar na primeira conta. Valor padrão é a rede de proteção do contrato.

Existe uma decisão a tomar em cada divisão: passar campos soltos (titulo, preco) ou o objeto inteiro (item)? Campos soltos deixam claro o que a peça usa; o objeto é mais curto e cresce sem mudar a chamada. Para peça pequena, prefira campos soltos: se o cartão só precisa do nome e do preço, ele não deveria poder mexer no resto do produto.

8. Medindo: quantas linhas cada um ficou

O terminal tem uma ferramenta simples para isso. wc -l conta as linhas de cada arquivo que você passar:

ana@notebook:~/loja$ wc -l src/App.svelte src/lib/*.svelte
 17 src/App.svelte
  8 src/lib/Cartao.svelte
  5 src/lib/PrecoLinha.svelte
 30 total

Trinta linhas no total contra as vinte de antes. A divisão aumentou o código: cada arquivo novo custa uma linha de <script> de abertura e uma de fechamento, mais a importação. Isso não é defeito — é o preço da separação, e ele aparece em qualquer linguagem.

O que melhorou foi a distribuição. O App tem 17 linhas e monta a página; o Cartao tem 8 e desenha um produto; o PrecoLinha tem 5 e formata dinheiro. Nenhum arquivo precisa ser lido inteiro para mexer numa parte. Se amanhã o cartão ganhar foto, ele vai para 12 linhas e ninguém mais é afetado.

9. Quando não dividir

Dividir cedo demais tem custo, e ele aparece rápido: um componente usado uma vez só, com propriedades que só ele entende, é uma indireção — você abre dois arquivos para ler uma coisa. O guia sugere três critérios antes de criar um arquivo novo:

PerguntaSe a resposta for não
Isso vai aparecer em mais de um lugar?Deixe dentro do arquivo por enquanto
Isso tem nome próprio e um trabalho só?Ainda não é peça; é trecho
Dá para descrever sem citar o resto da página?A peça depende demais do contexto

Se as três respostas forem “não”, o trecho fica onde está. Um componente de quarenta linhas com uma responsabilidade clara é melhor que quatro arquivos de dez linhas amarrados por propriedades. O número que importa não é o de arquivos: é o de coisas que você precisa ter na cabeça ao mesmo tempo.

Não divida no meio de uma tarefa

Reorganizar código enquanto conserta um bug é receita de confusão: você não sabe se quebrou por causa do conserto ou da mudança de lugar. Conserte primeiro, confirme na tela, e só então mova. A aula de refatoração volta a esse ponto.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Todas são erros de $props() — a linha onde o componente declara o que recebe.

Erro 1 — chamar $props() duas vezes

Cada componente tem um único ponto de entrada de dados. Duas chamadas não somam propriedades: a segunda é recusada.

<script>
  let { a } = $props();
  let { b } = $props();
</script>

<p>{a} {b}</p>
Erro de compilação (linha 3, coluna 14): Cannot use `$props()` more than once

“Não é possível usar $props() mais de uma vez”. A correção é juntar tudo numa chamada só: let { a, b } = $props(). Repare que a linha apontada é a segunda chamada, e a coluna 14 é onde o $props começa.

Erro 2 — $props() dentro de uma função

Propriedade é declarada no topo do componente, não no meio de uma função. O compilador precisa ver a declaração para montar o contrato.

<script>
  function pegar() {
    return $props();
  }
</script>

<p>oi</p>
Erro de compilação (linha 3, coluna 11): `$props()` can only be used at the top level of components as a variable declaration initializer

A mensagem explica o lugar permitido: “só pode ser usado no nível de cima do componente, como inicializador de declaração de variável”. Em português direto: let { x } = $props(), no começo do <script>.

Erro 3 — propriedade que não chega e é usada como número

Sem valor padrão, uma propriedade não passada vale undefined. O componente compila e quebra só na hora de desenhar.

<script>
  let { preco } = $props();
</script>

<p>R$ {preco.toFixed(2)}</p>
Cannot read properties of undefined (reading 'toFixed')

“Não consigo ler propriedades de undefined (lendo ‘toFixed’)”. Traduzindo: preco não tem valor, então não há toFixed para chamar. A correção pode ser valor padrão (preco = 0) ou garantir que quem chama sempre passe o preço — as duas funcionam, a primeira protege mais.

Resumo

  • Componente pequeno tem um trabalho, descrito numa frase sem “e”.
  • O sinal de exagero é a leitura difícil, não o número de linhas.
  • O bloco que desenha um item é o candidato natural a virar peça.
  • let { titulo, preco } = $props() declara o que a peça recebe de fora.
  • Valor padrão (preco = 0) protege a peça de chamada incompleta.
  • {#each} repete a peça para cada item da lista, sem copiar HTML.
  • Conta dentro do HTML não tem nome; mova para uma função como calcularTotal().
  • Dividir aumenta o total de linhas e a quantidade de arquivos: o ganho é de leitura.
  • Usado uma vez só, com propriedades próprias, o trecho pode ficar onde está.
  • $props() aparece uma vez, no topo do script; sem valor padrão, propriedade ausente vale undefined.
