Svelte · setContext e getContext

A Ana pendurou um quadro no corredor da padaria com um recado só: "a cor das placas deste mês é verde". Não é um envelope entregue na mão de cada funcionário — é um aviso na parede, que qualquer um que passe por ali lê. No Svelte, esse quadro se chama contexto: o componente de cima escreve com setContext, e qualquer componente abaixo dele lê com getContext, sem precisar de prop em cada andar. Esta aula é sobre quando o recado resolve o problema — e quando ele só cria confusão.

Você vai aprender
  • O que é contexto e por que ele existe quando há muitos andares de componentes.
  • Escrever com setContext(chave, valor) e ler com getContext(chave).
  • Por que a chave é um contrato entre quem escreve e quem lê.
  • Descobrir se o recado existe com hasContext antes de ler.
  • Como o contexto desce sozinho, sem prop em cada componente do caminho.
  • Contexto com objeto: o que é reativo e o que não é.
  • Contexto × props × store: o custo e o uso de cada um.
  • Boas chaves: texto, símbolo e o risco de duas chaves iguais.
  • Os três erros reais desta aula, com a mensagem que aparece.
  • Como o terminal mostra quem escreve e quem lê o contexto no projeto.

1. A ideia: o recado no quadro do corredor

A padaria da Ana tem três níveis de gente: ela, o caixa e os atendentes do balcão. Quando ela decide que as placas do mês são verdes, ela não sai entregando um papel para cada pessoa — ela escreve no quadro do corredor e quem precisa lê. Quem está no corredor lê; quem está no depósito, fechado, não lê nada.

É exatamente assim que o contexto do Svelte funciona. Um componente escreve um valor com uma chave; qualquer componente abaixo dele na árvore consegue ler aquele valor pela mesma chave. Os componentes que não estão abaixo — irmãos, primos, gente de outro galho — não veem nada. O recado desce pela árvore, nunca sobe e nunca atravessa para o lado.

A vantagem aparece quando a distância é grande. Imagine que o painel do caixa mostre uma etiqueta lá no fundo, cinco componentes abaixo. Passar a cor por prop exigiria que cada um dos quatro componentes do caminho recebesse a prop e a repassasse — quatro assinaturas mudadas para um valor que nenhum deles usa. Com contexto, o painel escreve uma vez e a etiqueta lê direto. Os quatro do caminho não sabem que o recado existe.

O preço é que o contexto é invisível. Uma prop aparece na assinatura do componente; um contexto não aparece em lugar nenhum. Quem lê um componente isolado não tem como adivinhar que ele depende de um recado escrito três andares acima. É por isso que o guia trata contexto como ferramenta para problemas específicos — tema, sessão, carrinho — e não como substituto de prop.

A última linha merece atenção porque é a confusão mais comum. Contexto e store guardam valores compartilhados, mas o alcance é diferente: o store vale para o projeto inteiro, o contexto vale só para a subárvore de quem escreveu. Se dois painéis independentes precisam de cores diferentes, contexto resolve; se todos precisam do mesmo carrinho, store.

3. setContext e getContext: a mesma chave nos dois lados

As duas funções vêm de svelte — não de svelte/store. Quem escreve chama setContext no corpo do componente, durante a inicialização; quem lê chama getContext com a mesma chave.

<script>
  import { setContext, getContext } from 'svelte';

  setContext('cor', 'verde');
  const cor = getContext('cor');
</script>

<p>Cor: {cor}</p>
<p>Cor: verde</p>
setContext('cor', 'verde')
escreve no quadro: a chave 'cor' passa a valer 'verde' para todo mundo que estiver abaixo deste componente.
getContext('cor')
lê o recado. Se ninguém escreveu essa chave em nenhum ancestral, o resultado é undefined — sem erro, sem aviso.
'cor'
a chave. Ela é a única ligação entre quem escreve e quem lê: nomes diferentes, recados diferentes.
+ svelte
as duas funções vêm do pacote svelte. Elas não são runas: precisam de import.

Neste exemplo os dois lados estão no mesmo arquivo, e a leitura devolve o que acabou de ser escrito. Isso ajuda a entender o mecanismo, mas o ganho real aparece quando o leitor está em outro componente, mais abaixo — é o que a seção 5 mostra.

Quando chamar setContext

No corpo do <script>, no nível de cima, junto com as declarações. O Svelte só aceita escrever no contexto durante a inicialização do componente; tentar escrever depois, dentro de um $effect ou de um clique, produz o erro que aparece na seção 10.

4. hasContext: quando o recado pode não existir

getContext sempre devolve alguma coisa: o valor, se a chave existir, ou undefined, se não existir. Como undefined é um valor legítimo, o componente não tem como saber se o recado não foi escrito ou se foi escrito como "nada". Para isso existe hasContext, que responde sim ou não sem ler:

<script>
  import { setContext, hasContext, getContext } from 'svelte';

  setContext('cor', 'verde');
  const tem = hasContext('cor');
  const temTamanho = hasContext('tamanho');
  const tamanho = getContext('tamanho') ?? 'padrão';
</script>

<p>cor? {tem} · tamanho? {temTamanho} · tamanho: {tamanho}</p>
<p>cor? true · tamanho? false · tamanho: padrão</p>

O padrão que escala é este: o componente que lê decide o que fazer quando não há recado. Um valor padrão com ?? resolve a maioria dos casos; hasContext serve quando a ausência muda o comportamento — por exemplo, um componente de cartão que, sem contexto de tema, desenha o estilo antigo.

Missão: o quadro diz 'cor' e o leitor procura 'color'. Faça a leitura achar o recado e a tela mostrar cor: verde.

<script>
  import { setContext, getContext, hasContext } from 'svelte';

  setContext('cor', 'verde');
  const cor = getContext('color');

</script>

<p>cor: {cor ?? 'sem cor'}</p>
<script>
  import { setContext, getContext, hasContext } from 'svelte';

  setContext('cor', 'verde');
  const cor = getContext('cor');

</script>

<p>cor: {cor ?? 'sem cor'}</p>

A missão parece boba e é a que mais acontece na vida real: o erro não é de sintaxe, é de combinado. Uma chave escrita à mão de um lado e digitada de outro jeito do outro lado não dá erro nenhum — dá undefined e uma tela vazia. A defesa é ter a chave num lugar só, e o próximo bloco mostra como.

Missão: ninguém escreveu a chave 'borda' e a tela mostra borda: vazio. Use hasContext para escrever sem borda quando o recado não existir.

<script>
  import { setContext, getContext, hasContext } from 'svelte';

  setContext('cor', 'verde');
  const borda = getContext('borda');

</script>

<p>borda: {borda}</p>
<script>
  import { setContext, getContext, hasContext } from 'svelte';

  setContext('cor', 'verde');
  const borda = hasContext('borda') ? getContext('borda') : 'sem borda';

</script>

<p>borda: {borda}</p>

Repare que a solução não usa ??: ela pergunta antes. As duas formas funcionam quando o valor ausente é undefined; a diferença aparece quando o recado existe e vale null de propósito — aí ?? trocaria por 'sem borda' e hasContext respeitaria o null.

5. O contexto desce sozinho, sem props

Agora o caso real da Ana. O painel define a cor e monta um cartão; o cartão lê a cor. São dois arquivos, e o segundo não recebe prop nenhuma:

<script>
  import { setContext } from 'svelte';
  import Cartao from './Cartao.svelte';

  setContext('cor', 'verde');
</script>

<section>
  <Cartao />
</section>
<script>
  import { getContext } from 'svelte';

  const cor = getContext('cor');
</script>

<p>Cor: {cor}</p>
<script>
  import Painel from './Painel.svelte';
</script>

<Painel />

Some da assinatura do Cartao qualquer menção à cor. Ele não recebe prop, não recebe argumento, não sabe quem escreveu — só sabe que existe um recado com a chave 'cor'. O App também não sabe: ele só monta o painel. Se um dia o painel mudar a cor para azul, o cartão acompanha sem uma linha alterada.

Para caber num arquivo só, dá para escrever e ler no mesmo componente. O resultado é idêntico ao da composição dos três arquivos:

<script>
  import { setContext, getContext } from 'svelte';

  setContext('cor', 'verde');
  const cor = getContext('cor');
</script>

<section>
  <p>Cor: {cor}</p>
</section>
<section><p>Cor: verde</p></section>

O <section> na saída não é enfeite: é a prova de que houve dois componentes no caminho. No projeto da Ana, quem desenha a section é o Painel e quem desenha o p é o Cartao. A tag externa vem de fora, o texto vem de dentro, e o valor atravessou a fronteira pelo contexto.

Contexto não é "variável global"

Cada instância de Painel tem o seu contexto. Se a tela mostrar dois painéis, um com verde e outro com azul, cada Cartao lê o recado do seu painel — porque a leitura sobe pela árvore, e cada galho tem o seu quadro. Um store não faria isso: seria um valor só para todos.

6. Contexto com objeto e reatividade

Contexto carrega qualquer valor: texto, número, função, objeto. Quando o valor precisa mudar com o tempo, a pergunta é outra: esse objeto é reativo? Um objeto comum guardado no contexto não avisa ninguém quando muda; um objeto com $state avisa.

<script>
  import { setContext, getContext } from 'svelte';

  const carrinho = $state({ itens: [], total: 0 });
  setContext('carrinho', carrinho);

  const mesmo = getContext('carrinho');
</script>

<p>{mesmo.itens.length} itens · R$ {mesmo.total.toFixed(2)}</p>
<button onclick={() => mesmo.itens.push('pão')}>adicionar pão</button>
<p>0 itens · R$ 0.00</p> <button>adicionar pão</button>

Aqui o contexto carrega a referência de um objeto com estado. Quem lê recebe a mesma referência, não uma cópia: quando o cartão empurra um pão na lista, o objeto é o mesmo que o painel conhece, e todos os componentes que mostram itens.length se redesenham. Se o objeto fosse comum (const carrinho = { itens: [] }), o push mudaria a lista e ninguém seria avisado — mesma armadilha da aula de stores.

Missão: o clique empurra um pão, mas a tela continua em Itens: 0. Faça o objeto do carrinho ser reativo para o clique mostrar Itens: 1.

<script>
  import { setContext, getContext, hasContext } from 'svelte';

  const carrinho = { itens: [] };
  setContext('carrinho', carrinho);

  const lido = getContext('carrinho');

</script>

<p>Itens: {lido.itens.length}</p>
<button onclick={() => lido.itens.push('pão')}>adicionar</button>
<script>
  import { setContext, getContext, hasContext } from 'svelte';

  const carrinho = $state({ itens: [] });
  setContext('carrinho', carrinho);

  const lido = getContext('carrinho');

</script>

<p>Itens: {lido.itens.length}</p>
<button onclick={() => lido.itens.push('pão')}>adicionar</button>

A mudança é de três caracteres — $state( em volta do objeto — e o comportamento é outro. Não é mágica do contexto: é o $state fazendo o trabalho de sempre, agora num objeto que vários componentes compartilham. O contexto só foi o veículo.

7. Contexto × props × store: quando usar cada um

As três formas levam dados de um lugar para outro, e escolher errado custa caro em manutenção. O critério é sempre o mesmo: quem precisa do valor e quem pode mudá-lo.

FormaAlcanceQuando é a certa
propum filho diretovalor que o pai escolhe por filho e que muda de instância para instância
contextoa subárvore inteiravalor que todos os filhos daquele galho compartilham: tema, formulário, sessão, carrinho
storeo projeto inteirovalor que atravessa galhos diferentes ou vive fora da árvore

O sinal de que você devia usar contexto é o "repasse de prop": um componente que recebe cor e não usa cor para nada, só para entregar ao filho. Quando o mesmo repasse aparece em dois ou três andares, o contexto paga o custo de ser invisível.

O sinal contrário, de que contexto é exagero: um componente que tem um filho direto e um valor só dele. Aí a prop é mais clara, porque o valor aparece na assinatura e quem lê o arquivo sabe de onde ele vem. Contexto esconde a dependência de propósito — e esconder tem preço.

8. Chaves: um nome combinado, não um apelido

A chave é o que liga os dois lados, então ela merece cuidado. Três regras práticas:

Um arquivo com a chave, importado pelos dois lados. Em vez de digitar 'cor' em dois lugares, exporte a chave de um módulo e importe:

export const COR = Symbol('cor');
export const CARRINHO = Symbol('carrinho');

Um Symbol é um valor único e impronunciável, perfeito para não colidir com a chave de outra pessoa. Com texto, duas bibliotecas diferentes podem usar 'theme' e uma sobrescrever a outra; com símbolo, isso não acontece. O custo é que a chave deixa de ser legível no DevTools — você vê o nome do símbolo, não o valor.

Texto quando é simples. Para um projeto pequeno, 'cor' é mais legível e não dá problema. A regra é: se duas partes do projeto escrevem contexto, prefira símbolos.

A última escrita vence. Se o mesmo componente chamar setContext('cor', 'verde') e depois setContext('cor', 'azul'), quem ler recebe 'azul'. Não há aviso, não há erro — é sobrescrita. Isso é útil quando um componente quer trocar o recado do pai para os seus próprios filhos, e perigoso quando é engano.

E há o caso que mais confunde: o componente que escreve contexto e também lê a mesma chave recebe o que ele mesmo escreveu. O contexto que ele lê é o da subárvore dele, não o do pai. Se você quiser ler o recado do pai e passar um novo para os filhos, leia antes de escrever:

<script>
  import { setContext, getContext } from 'svelte';

  setContext('cor', 'verde');
  const corDoPai = getContext('cor');
  setContext('cor', 'azul');
</script>

<p>pai: {corDoPai}</p>
<p>pai: verde</p>

A saída mostra verde, e não azul. A leitura aconteceu antes da segunda escrita, então pegou o valor daquele instante; um filho que lesse depois veria azul. Contexto não tem "antes" e "depois" guardados: tem o valor que está no quadro na hora em que cada um olha. E o componente que escreve também lê o próprio quadro — por isso o getContext devolveu verde, o que ele mesmo tinha acabado de escrever, e não um valor de um pai distante.

9. O recado vive enquanto o pai vive

O contexto não é guardado num lugar central: ele pertence à instância do componente que escreveu. Quando o painel sai da tela, o recado vai com ele. Se o painel voltar, o recado é escrito de novo, do zero, com o valor daquele momento.

Isso tem duas consequências práticas. A primeira: não tente guardar dados que precisam durar mais que a tela no contexto — para isso existe o store, que vive no módulo e não morre com o componente. A segunda: o valor escrito no contexto é o valor da inicialização. Se você escrever setContext('cor', cor) onde cor é uma variável comum, o recado fica com o valor de quando o componente nasceu; mudanças depois não chegam aos filhos.

Para o recado acompanhar mudanças, o valor precisa ser reativo por dentro: um objeto com $state (como o carrinho da seção 6), um store, ou uma função que os filhos chamam para obter o valor atual. O contexto em si é só o fio: ele não observa nada.

O que você guardaOs filhos acompanham mudanças?
texto ou número ('verde', 3)não: é uma cópia do valor daquele instante
objeto comumnão: mudar uma propriedade não avisa ninguém
objeto com $statesim: as propriedades são reativas
store (writable)sim: o filho usa $store normalmente
funçãosim, se a função ler algo reativo ao ser chamada

10. Quando dá errado

As três mensagens abaixo são reais, copiadas da execução. As duas primeiras vêm do renderizador e a terceira também — nenhuma delas é erro de sintaxe, e é isso que as torna traiçoeiras.

Erro 1 — contexto dentro de <script module>

O bloco de módulo roda uma vez, fora de qualquer componente, e não tem quadro onde pendurar recado:

<script module>
  import { setContext } from 'svelte';
  setContext('cor', 'verde');
</script>

<p>ok</p>
Erro ao renderizar: https://svelte.dev/e/lifecycle_outside_component

O Svelte 5 identifica os erros de ciclo de vida por um endereço de documentação: lifecycle_outside_component quer dizer "esta função só pode ser chamada dentro da inicialização de um componente". A correção é mover a chamada para o <script> normal — o contexto é por instância, e o módulo não tem instância.

Erro 2 — importar de svelte/store

setContext não é uma função de store. Trocar o módulo no import produz um erro de exportação:

<script>
  import { setContext } from 'svelte/store';

  setContext('cor', 'verde');
</script>

<p>ok</p>
Erro ao renderizar: The requested module 'svelte/store' does not provide an export named 'setContext'

"O módulo svelte/store não fornece uma exportação chamada setContext." Guarde o mapa: setContext, getContext, hasContext, onMount e tick vêm de svelte; writable, readable, derived e get vêm de svelte/store.

Erro 3 — o recado que não chegou

Este é o clássico. Ninguém escreveu a chave 'carrinho' acima deste componente, então getContext devolveu undefined e o primeiro acesso a uma propriedade quebrou:

<script>
  import { getContext } from 'svelte';

  const carrinho = getContext('carrinho');
</script>

<p>{carrinho.itens.length} itens</p>
Erro ao renderizar: Cannot read properties of undefined (reading 'itens')

"Não é possível ler propriedades de undefined (lendo 'itens')." Três causas possíveis, em ordem de frequência: a chave digitada diferente nos dois lados; o componente que lê não está abaixo de quem escreve; e o setContext foi chamado dentro de uma função que ainda não rodou. Comece conferindo a chave, letra por letra.

Um contexto, um módulo

Se mais de um componente escreve ou lê a mesma chave, coloque a chave num arquivo só (src/lib/contexto.js) e importe nos dois lados. Além de evitar erro de digitação, o arquivo vira a documentação do recado: qualquer pessoa que procure a chave encontra a explicação no mesmo lugar.

Exercícios

1. Quem consegue ler um contexto escrito por um componente?

2. O que getContext('cor') devolve quando ninguém escreveu essa chave?

3. Um objeto comum guardado no contexto faz os filhos se redesenhandem quando uma propriedade muda?

Complete o código

import { setContext, getContext } from 'svelte';

// quem escreve, no componente de cima
('cor', 'verde');

// quem lê, num componente abaixo
const cor = ('cor');

Resumo

  • Contexto é um valor que um componente deixa disponível para toda a sua subárvore, sem passar props.
  • setContext(chave, valor) escreve; getContext(chave) lê; hasContext(chave) responde se existe.
  • As três vêm de svelte — não de svelte/store.
  • A chave é o contrato: nomes diferentes nos dois lados devolvem undefined sem aviso.
  • O contexto desce pela árvore e não sobe nem atravessa para os lados.
  • Cada instância tem o seu contexto: dois painéis podem ter cores diferentes.
  • O recado guarda o valor da inicialização; para acompanhar mudanças, guarde um objeto com $state ou um store.
  • setContext só pode ser chamado durante a inicialização; em <script module> dá lifecycle_outside_component.
  • Use contexto para tema, sessão, formulário e carrinho; use prop para o filho direto; use store para o projeto inteiro.
  • Com duas ou mais partes usando a mesma chave, prefira um Symbol exportado de um módulo.
