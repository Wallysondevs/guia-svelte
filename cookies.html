SvelteKit · Cookies e Sessão

A Ana conhece os clientes pelo nome, mas não pode decorar a lista. Ela dá um crachá: o cliente leva, e na volta ela lê o crachá em vez de perguntar tudo de novo. Na web, o crachá se chama cookie: um pedacinho de texto que o servidor manda e o navegador devolve em cada visita. Esta aula é sobre entregar, ler e apagar esse crachá no SvelteKit — e sobre o cuidado que faz a diferença entre um crachá e um vazamento.

Você vai aprender
  • O que é um cookie e por que a web precisa dele.
  • Como gravar com cookies.set e ler com cookies.get.
  • O que significam path, httpOnly, sameSite, maxAge e secure.
  • Como ler o cabeçalho set-cookie real com curl -i.
  • Como apagar um cookie e por que Max-Age=0 aparece.
  • Por que httpOnly impede o JavaScript de ler o crachá.
  • A diferença entre guardar o nome e guardar um id de sessão.
  • Como o hooks.server.js transforma cookie em locals.
  • Três erros reais de cookie, com a mensagem do servidor.
  • O que nunca deve entrar num cookie.

1. A ideia: o crachá que volta na próxima visita

HTTP não tem memória. Cada requisição chega como se fosse a primeira: o servidor não sabe que você esteve ali dez segundos atrás. Sem algo a mais, o site pediria sua senha em cada clique. O cookie resolve isso do jeito mais simples possível: o servidor manda um texto na resposta, o navegador guarda, e devolve o mesmo texto em toda requisição seguinte para aquele endereço.

É um crachá, com as mesmas vantagens e os mesmos riscos. Vantagem: você não precisa se identificar de novo a cada porta. Risco: quem pegar o crachá na sua mão pode se passar por você. Por isso o crachá de sessão de verdade não tem o seu nome — tem um número aleatório difícil de adivinhar, e o servidor é quem sabe a qual pessoa aquele número pertence.

Outro detalhe importante: o cookie pertence a um domínio. O que o site da padaria guarda não é enviado para o site do banco. E existe um limite de tamanho — cerca de 4 KB por cookie — porque ele viaja em toda requisição, e crachá gigante atrasa a fila inteira.

2. Gravar e ler com cookies

No SvelteKit, cookies chega no evento do +page.server.js (e do +server.js, e do hooks.server.js). Gravar só faz sentido onde há resposta para anexar o cabeçalho: numa action ou num endpoint. Ler pode ser no load.

import { redirect } from '@sveltejs/kit';

export function load({ cookies }) {
	const nome = cookies.get('cliente');
	return { nome: nome ?? null };
}

export const actions = {
	entrar: async ({ request, cookies }) => {
		const dados = await request.formData();
		const nome = dados.get('nome')?.trim();

		cookies.set('cliente', nome ?? 'visitante', {
			path: '/',
			httpOnly: true,
			sameSite: 'lax',
			maxAge: 60 * 60 * 24
		});

		redirect(303, '/entrar');
	},

	sair: async ({ cookies }) => {
		cookies.delete('cliente', { path: '/' });
		redirect(303, '/entrar');
	}
};
cookies.get('cliente')
devolve o valor ou undefined. Nunca lança erro por cookie ausente — quem decide o que fazer é você.
cookies.set(nome, valor, opções)
grava. O valor tem de ser texto; número e objeto precisam de conversão.
path: '/'
em quais endereços o cookie vale. '/' é o site inteiro. O padrão já é esse.
httpOnly: true
o JavaScript do navegador não consegue ler. É o padrão do SvelteKit e você quase nunca deve mudar.
sameSite: 'lax'
o cookie só acompanha requisições do próprio site. Protege contra envio a partir de outro domínio.
maxAge: 86400
quantos segundos o navegador guarda. 60 * 60 * 24 é um dia. Sem isso, o cookie morre ao fechar o navegador.
cookies.delete('cliente', { path: '/' })
apaga. O path precisa ser o mesmo da gravação, senão o navegador não encontra o crachá.
<script>
	let { data, form } = $props();
</script>

<h1>Área da Ana</h1>

{#if data.nome}

	<form method="POST" action="?/entrar">
		<input name="nome" placeholder="seu nome" />

Repare que o componente não sabe que existe cookie: ele recebe data.nome, que pode ser null. Essa é a divisão de trabalho que vale a pena manter. O cookie é detalhe de transporte; o componente trabalha com dado limpo.

3. A saída real: o cabeçalho set-cookie

Cookie não aparece no corpo da resposta. Ele vai num cabeçalho, e o curl -i mostra os dois. Primeiro, sem crachá:

ana@notebook:~/loja$ curl -s localhost:5173/entrar | grep -o '<p>[^<]*</p>'
<p>Você ainda não entrou.</p>

Agora o envio do formulário, com o cabeçalho de resposta filtrado:

ana@notebook:~/loja$ curl -s -i -X POST -H 'accept: text/html' -d 'nome=Ana' 'localhost:5173/entrar?/entrar' | grep -i '^HTTP/\|^location\|^set-cookie'
HTTP/1.1 303 See Other
location: /entrar
set-cookie: cliente=Ana; Max-Age=86400; Path=/; HttpOnly; SameSite=Lax

Três linhas que contam tudo. O 303 é o redirecionamento da action. O set-cookie é o crachá sendo entregue, com as opções que você escreveu: Max-Age=86400 veio de maxAge: 60 * 60 * 24; Path=/ de path; HttpOnly e SameSite=Lax das suas opções. O SvelteKit não inventa nada: ele escreve o cabeçalho padrão do HTTP.

Com o crachá, a página já sabe quem é. O -b do curl manda cookies, como o navegador faria:

ana@notebook:~/loja$ curl -s -b 'cliente=Ana' localhost:5173/entrar | grep -o '<p>[^<]*</p>'
<p>Bem-vinda de volta, Ana.</p>

E o "sair" apaga. Note o valor vazio e o Max-Age=0: é assim que se apaga um cookie — o servidor manda o mesmo nome, com prazo no passado, e o navegador joga fora.

ana@notebook:~/loja$ curl -s -i -X POST -H 'accept: text/html' -d '' 'localhost:5173/entrar?/sair' | grep -i '^set-cookie'
set-cookie: cliente=; Max-Age=0; Path=/; HttpOnly; SameSite=Lax

O componente que desenha a saudação não precisa saber de onde veio o nome. Isolado, com o valor fixo no script, ele compila para um único parágrafo — e é essa a saída que o navegador recebe quando o cookie existe:

<script>
	const nome = 'Ana';
</script>

<p>Bem-vinda de volta, {nome}.</p>
<p>Bem-vinda de volta, Ana.</p>

Missão: este é o cabeçalho de cookies que chegou na requisição. O crachá se chama cliente. Faça a saudação mostrar Olá, Ana.

<script>
	const cabecalho = 'tema=escuro; cliente=Ana';

	function ler(nome) {
		const par = cabecalho.split('; ').find((p) => p.startsWith(nome + '='));
		return par ? par.split('=')[1] : null;
	}

	let cliente = ler('client');
</script>

<p>Olá, {cliente ?? 'visitante'}</p>

<p>Olá, {cliente ?? 'visitante'}</p>

O ?? é o operador de coalescência nula: usa o valor da direita quando o da esquerda é null ou undefined. Ele é o par natural de cookies.get(), que devolve undefined quando o crachá não veio. Nome de cookie é sensível a maiúscula e a espaço: cliente e Client são crachás diferentes.

4. httpOnly: o crachá que o JavaScript não vê

Aquela palavra no cabeçalho tem um efeito concreto: com HttpOnly, o cookie não aparece em document.cookie. O JavaScript do navegador simplesmente não o enxerga. Ele continua sendo enviado ao servidor em cada requisição, mas não pode ser lido nem copiado por um script.

Por que isso importa? Porque um script malicioso injetado na sua página — o famoso XSS — roda com os poderes da sua página. Se ele pudesse ler o crachá de sessão, mandaria o crachá para o atacante, que passaria a agir como o visitante. Com HttpOnly, o script não tem o que roubar.

O SvelteKit já liga httpOnly por padrão. Você só precisa desligar quando o JavaScript do navegador realmente tem de ler aquele cookie — um tema claro/escuro, por exemplo. E, nesse caso, guarde ali só o que não é segredo.

OpçãoPadrão do SvelteKitQuando mudar
httpOnlytruesó para preferência de tela que o JS precisa ler
securetrue fora do devnunca, em produção com HTTPS
sameSite'lax''strict' para crachá de sessão; 'none' exige secure

O SvelteKit desliga secure no desenvolvimento porque a sua máquina fala http://localhost, e o navegador recusaria um cookie Secure em HTTP. Em produção, com HTTPS, ele liga sozinho. Se você vir um cookie sem Secure no site publicado, alguma configuração está errada — e o crachá está viajando em texto claro.

5. Sessão de verdade: um número, não o nome

Guardar cliente=Ana funciona para uma demonstração e é uma péssima ideia em produção. O valor do cookie é texto que o visitante pode editar à vontade — basta abrir as ferramentas do navegador. Se o site acredita no que está escrito ali, qualquer pessoa vira qualquer pessoa escrevendo cliente=Admin.

A solução é não guardar o dado, e sim uma chave. O servidor cria um número aleatório, guarda num mapa (ou no banco) a ligação entre esse número e a pessoa, e manda só o número. Na volta, ele procura o número no mapa. Se não achar, é visitante; se achar, é a Ana. O crachá deixa de ser a identidade e passa a ser o número do armário.

import { randomUUID } from 'node:crypto';

const sessoes = new Map();

export function abrir(nome) {
	const id = randomUUID();
	sessoes.set(id, { nome, desde: Date.now() });
	return id;
}

export function buscar(id) {
	return sessoes.get(id) ?? null;
}

export function fechar(id) {
	sessoes.delete(id);
}

Com esse módulo, a action grava o id e o load busca a pessoa:

import { abrir, buscar } from '#lib/sessoes.js';

export function load({ cookies }) {
	const id = cookies.get('sessao');
	const pessoa = id ? buscar(id) : null;
	return { nome: pessoa?.nome ?? null };
}

export const actions = {
	entrar: async ({ request, cookies }) => {
		const dados = await request.formData();
		const id = abrir(dados.get('nome')?.trim() ?? 'visitante');

		cookies.set('sessao', id, {
			path: '/',
			httpOnly: true,
			sameSite: 'strict',
			maxAge: 60 * 60 * 24
		});

		redirect(303, '/entrar');
	}
};

O valor que aparece no cabeçalho agora é um UUID, algo como d9f0c2a4-…. Copiar esse número não ajuda o visitante a virar outra pessoa: ele só serve para aquela sessão que o servidor abriu, e você pode fechá-la a qualquer momento apagando a entrada do mapa.

Missão: este cookie tem maxAge: 0, que significa "apague agora". Faça a página dizer sessão expirada.

<script>
	let cookies = $state([{ nome: 'cliente', valor: 'Ana', maxAge: 0 }]);
	let ativo = $derived(cookies.find((c) => c.maxAge >= 0));
</script>

<p>{ativo ? 'sessão ativa: ' + ativo.valor : 'sessão expirada'}</p>
<script>
	let cookies = $state([{ nome: 'cliente', valor: 'Ana', maxAge: 0 }]);
	let ativo = $derived(cookies.find((c) => c.maxAge > 0));
</script>

<p>{ativo ? 'sessão ativa: ' + ativo.valor : 'sessão expirada'}</p>

A comparação com > 0 e não >= 0 é o detalhe: maxAge: 0 é justamente o valor que manda apagar. Quem testa "maior ou igual a zero" trata o crachá cancelado como válido — e a sessão que deveria ter acabado continua de pé.

6. Do cookie ao locals, no hooks.server.js

Ler o cookie em cada load funciona e repete código. O lugar certo para essa leitura é o hooks.server.js, que roda antes de qualquer rota e pode preencher locals uma vez para toda a requisição:

import { buscar } from '#lib/sessoes.js';

export async function handle({ event, resolve }) {
	const id = event.cookies.get('sessao');
	event.locals.pessoa = id ? buscar(id) : null;

	return resolve(event);
}

A partir daí, qualquer load ou action lê locals.pessoa sem tocar em cookie. O hook é também o lugar de redirecionar quem não está logado, de registrar a requisição no log e de responder antes mesmo de chegar à rota.

export function load({ locals }) {
	const pedidos = listar();

	return {
		pessoa: locals.pessoa?.nome ?? 'visitante',
		pedidos,
		prontos: pedidos.filter((p) => p.pronto).length
	};
}

Cuidado com uma armadilha de iniciante: locals é do servidor e não vai para o navegador. Se a página precisa do nome, ele tem de sair no return do load, como acima. Colocar o objeto inteiro da pessoa em locals é seguro; colocar a senha em data não é.

7. Quando dá errado

Erro 1 — nome de cookie inválido

O nome do cookie só aceita letras, números, hífen e sublinhado. Espaço não entra, e o erro é direto:

entrar: async ({ cookies }) => {
	cookies.set('nome do meio', 'Ana');
	redirect(303, '/entrar');
}
TypeError: cookie name is invalid: nome do meio
500 POST /entrar?/entrar

Trocar por nome_do_meio resolve. A mensagem mostra o nome recusado, o que economiza tempo quando há vários cookies no projeto.

Erro 2 — cookie grande demais

O limite é de cerca de 4 KB. Um valor maior que isso é recusado pelo próprio servidor, antes de o navegador descartá-lo:

entrar: async ({ cookies }) => {
	cookies.set('grande', 'a'.repeat(5000));
	redirect(303, '/entrar');
}
SvelteKit error: cookie_too_large
Cookie `grande` is too large, and will be discarded by the browser
https://svelte.dev/e/kit/cookie_too_large
    at entrar (src/routes/entrar/+page.server.js:5:11)
500 POST /entrar?/entrar

A tradução: "o cookie é grande demais e o navegador vai descartá-lo". Se o dado é grande — uma lista, um carrinho cheio — ele não pertence ao crachá. Guarde um id pequeno e mantenha o conteúdo no servidor.

Erro 3 — valor inválido em sameSite

As opções também são validadas. 'nenhum' não existe; os valores são 'lax', 'strict' e 'none' — este último exigindo secure:

entrar: async ({ cookies }) => {
	cookies.set('cliente', 'Ana', { sameSite: 'nenhum' });
	redirect(303, '/entrar');
}
TypeError: cookie sameSite is invalid: nenhum
500 POST /entrar?/entrar

O SvelteKit recusa a requisição inteira em vez de mandar um cabeçalho malformado. É melhor assim: falha no servidor, onde você pode ler a mensagem, do que no navegador, onde o cookie simplesmente não funciona e ninguém sabe por quê.

8. Crachá de sessão e crachá de preferência

Nem todo cookie é igual, e misturar os dois tipos é fonte de bug e de susto. O crachá de sessão identifica a pessoa: ele é secreto, curto, httpOnly, e vale por horas. O crachá de preferência guarda uma escolha: tema escuro, idioma, tamanho da fonte. Ele não identifica ninguém, o JavaScript pode ler, e vale por meses.

A regra prática sai daí: se o cookie responde "quem é você", trate como segredo; se responde "como você gosta", trate como configuração. O primeiro nunca aparece em document.cookie; o segundo pode, e deve, porque a página precisa aplicá-lo antes de desenhar — é o que o guia faz com o tema no topo de cada página.

No projeto, "sair" faz duas coisas de uma vez: apaga o cookie com cookies.delete e fecha a sessão no mapa do servidor. Só a primeira deixaria o id válido para quem tivesse uma cópia; só a segunda deixaria o navegador mandando um crachá que não corresponde a ninguém.

9. O que nunca entra num cookie

O crachá viaja em toda requisição para aquele domínio, fica guardado no disco do visitante e é legível por quem tem acesso à máquina. Trate o conteúdo dele como público. Senha, chave de API, dado de cartão, CPF inteiro, histórico de compras: nada disso entra.

Também não entra informação que você não quer expor no tráfego. Mesmo com HTTPS, o cookie aparece nas ferramentas de desenvolvedor do visitante. Se a informação é sensível, ela fica no servidor e o cookie carrega apenas a chave de acesso — o mesmo princípio do id de sessão.

Sempre apague no logout

Apagar o cookie é o passo que fecha a porta. No servidor, apague também a sessão do mapa, senão o id continua válido para quem tiver uma cópia. Fazer os dois é o mínimo: cookies.delete('sessao', { path: '/' }) e fechar(id). Só o primeiro deixa o crachá cancelado mas a fechadura aberta.

Exercícios

1. Onde é possível gravar um cookie no SvelteKit?

2. O que httpOnly faz?

3. Por que o cookie de sessão guarda um id e não o nome?

Complete o código

export const actions = {
  entrar: async ({ cookies }) => {
    cookies.('sessao', id, {
      path: '/',
      : true,
      maxAge: 60 * 60 * 24
    });
    redirect(303, '/entrar');
  }
};

Resumo

  • Cookie é um texto que o servidor manda e o navegador devolve em cada requisição ao mesmo domínio.
  • cookies.get lê; cookies.set grava; cookies.delete apaga com Max-Age=0.
  • Gravar só funciona onde há resposta: action, endpoint ou hooks.server.js.
  • O cabeçalho real é set-cookie: cliente=Ana; Max-Age=86400; Path=/; HttpOnly; SameSite=Lax.
  • httpOnly é o padrão e esconde o cookie do JavaScript: é a defesa contra roubo por script.
  • secure só é desligado no desenvolvimento, porque lá o endereço é http://localhost.
  • O valor do cookie pode ser editado pelo visitante: nunca confie nele para decidir quem é quem.
  • Sessão de verdade guarda um id aleatório e mantém os dados no servidor.
  • hooks.server.js lê o cookie uma vez e preenche locals para todas as rotas.
  • Os erros desta aula: nome inválido, valor grande demais e sameSite inexistente.
