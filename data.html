SvelteKit · Lendo o data

O load fez o trabalho dele e devolveu o pacote. Agora a Ana precisa abrir esse pacote no balcão. No SvelteKit o pacote chega com um nome fixo — data — e o componente o recebe como propriedade, do mesmo jeito que recebe qualquer valor vindo de fora. Esta aula é sobre abrir o pacote sem quebrar o embrulho: declarar o prop, dar um valor padrão, calcular em cima dele e não confundir o dado que chega com o dado que você inventa.

Você vai aprender
  • Como o +page.svelte declara o prop data com $props().
  • Por que sem essa linha a página quebra com data is not defined.
  • Como dar um valor padrão para o componente não quebrar quando o dado falta.
  • Como calcular em cima do data com $derived sem alterar o original.
  • O que é o form, o outro prop que toda página de rota recebe.
  • Como o data do layout se junta ao da página.
  • Como ler o data de dentro de um componente fundo, sem passar prop em prop.
  • O aviso real do Svelte sobre <tr> fora de <tbody>.
  • Três erros reais, com a linha apontada pelo compilador.
  • Como conferir o texto final com curl e grep.

1. A ideia: o pacote que chega com nome escrito

Quando o mensageiro da padaria volta da cozinha, ele não joga a bandeja na mesa: entrega na mão de quem pediu, com um bilhete dizendo o que é. No SvelteKit o bilhete está sempre escrito data. Você não escolhe esse nome, não importa esse valor e não chama função nenhuma para recebê-lo. Ele simplesmente está disponível no componente — desde que você o declare.

Essa declaração é a linha mais importante da aula: let { data } = $props(). Do lado direito, $props() devolve todos os valores que vieram de fora. Do lado esquerdo, as chaves desmontam esse objeto e pegam só o campo data. Se você não escrever essa linha, a variável data não existe dentro do componente, e o primeiro data.qualquerCoisa estoura.

Existe uma sutileza que vale desde já: data é uma propriedade, não uma variável de estado. Você pode ler à vontade, mas não deve escrever nela. Quando a página precisa de um valor derivado — uma contagem, um total, um rótulo — esse valor nasce com $derived, e o data fica intocado.

2. A declaração do prop, linha por linha

A rota /painel da Ana mostra a fila da cozinha. O +page.server.js devolve dois campos: a lista de pedidos e quantos já estão prontos.

import { listar } from '#lib/pedidos.js';

export function load() {
	const pedidos = listar();

	return {
		pedidos,
		prontos: pedidos.filter((p) => p.pronto).length
	};
}

O componente recebe esse pacote e declara o prop. Uma linha, e a partir dela todos os campos ficam disponíveis com data. na frente:

<script>
	let { data } = $props();

	let faltam = $derived(data.pedidos.length - data.prontos);
</script>

<h1>Painel da cozinha</h1>
<p>{data.prontos} pronto(s), {faltam} na fila</p>

<ul>
	{#each data.pedidos as pedido (pedido.id)}
		<li>{pedido.cliente}: {pedido.sabor} {pedido.pronto ? '✓' : '…'}</li>
	{/each}
</ul>
let { data }
declara uma variável chamada data. As chaves são desestruturação: pegam o campo data do objeto que vem depois do sinal de igual.
= $props()
a runa que entrega tudo o que o componente recebeu de fora. Sem ela, não há props — e sem props, não há data.
data.pedidos.length
quantos pedidos chegaram. É leitura pura: nada é alterado.
$derived(…)
uma variável que se recalcula sozinha quando data muda. O valor não é recalculado por você em lugar nenhum.
(pedido.id)
a chave do {#each}. Diz ao Svelte qual item é qual, para reaproveitar o HTML em vez de refazer tudo.

Repare que o componente não sabe que existe um arquivo .json, um readFile ou um banco atrás desse dado. Ele recebe um objeto e desenha. Essa ignorância é a força do desenho: no dia em que a Ana trocar a memória por um banco de verdade, o componente continua igual.

3. A saída real do painel

Com o servidor no ar, o curl mostra o que o visitante recebe. Os três pedaços que interessam são o título, a contagem e a lista:

ana@notebook:~/loja$ curl -s localhost:5173/painel | grep -o '<h1>[^<]*</h1>'
<h1>Painel da cozinha</h1>
ana@notebook:~/loja$ curl -s localhost:5173/painel | grep -o '<p>[^<]*</p>'
<p>1 pronto(s), 1 na fila</p>
ana@notebook:~/loja$ curl -s localhost:5173/painel | grep -o '<li>[^<]*</li>'
<li>Ana: frango ✓</li>
<li>Bia: queijo …</li>

O 1 pronto(s), 1 na fila não veio escrito de lugar nenhum: data.prontos valia 1, a lista tinha 2 itens, então faltam calculou 1. O $derived rodou no servidor antes de o HTML sair; no navegador, ele rodará de novo quando o data mudar.

O {pedido.pronto ? '✓' : '…'} é uma expressão condicional dentro das chaves: se pronto for verdadeiro, escreve o sinal de visto; se não, as reticências. Não é um bloco, é uma expressão — cabe numa linha e devolve um valor. Expressões assim são o jeito mais curto de escolher entre dois textos.

Missão: este componente é montado sem nenhum prop, e por isso quebra ao ler data.pedidos. Dê um valor padrão ao data para a página mostrar 0 pedido(s) em vez de estourar.

<script>
	let { data } = $props();
</script>

<p>{data.pedidos.length} pedido(s)</p>
<script>
	let { data = { pedidos: [] } } = $props();
</script>

<p>{data.pedidos.length} pedido(s)</p>

O valor padrão aparece depois do sinal de igual, dentro da desestruturação: let { data = { pedidos: [] } } = $props(). Ele só é usado quando o prop não vem. Em uma página de rota o SvelteKit sempre manda data, então o padrão parece inútil — até o dia em que você renderiza aquele componente em outro lugar, num teste ou numa caixa como esta.

4. Calcular a partir do data, sem estragar o data

Quase toda página faz uma conta com o que recebeu. A tentação é guardar o resultado numa variável comum e atualizá-la à mão em cada lugar que mexe no dado. Isso funciona até a primeira distração. O $derived elimina a distração: a conta é declarada uma vez e o Svelte sabe quando refazer.

<script>
	const data = {
		pedidos: [
			{ cliente: 'Ana', sabor: 'frango' },
			{ cliente: 'Bia', sabor: 'queijo' }
		],
		prontos: 1
	};

	let faltam = $derived(data.pedidos.length - data.prontos);
</script>

<p>{data.prontos} pronto(s), {faltam} na fila</p>
<ul>
	{#each data.pedidos as p}
		<li>{p.cliente}: {p.sabor}</li>
	{/each}
</ul>
<p>1 pronto(s), 1 na fila</p> <ul><li>Ana: frango</li><li>Bia: queijo</li></ul>

O componente acima tem o data escrito à mão, só para você ver a conta isolada do SvelteKit. A saída é a do compilador: a conta virou 1, e a lista virou dois <li>. Note que o $derived aparece antes de qualquer uso — ele precisa ser declarado no script, não no meio do HTML.

Se a conta for mais do que uma expressão, existe $derived.by: você passa uma função e escreve quantas linhas quiser dentro dela. O resultado é o mesmo; muda só o conforto de quem escreve. O guia volta a esse ponto na aula de $derived.by.

Missão: quando falta pedido na fila, o painel precisa avisar. Faça aparecer Atenção: 1 na fila com os dados atuais.

<script>
	const data = { pedidos: ['frango', 'queijo'], prontos: 1 };
	let faltam = $derived(data.pedidos.length - data.prontos);
</script>

{#if faltam < 0}
	<p>Atenção: {faltam} na fila</p>
{:else}
	<p>Tudo pronto</p>
{/if}
<script>
	const data = { pedidos: ['frango', 'queijo'], prontos: 1 };
	let faltam = $derived(data.pedidos.length - data.prontos);
</script>

{#if faltam > 0}
	<p>Atenção: {faltam} na fila</p>
{:else}
	<p>Tudo pronto</p>
{/if}

A comparação trocada é o erro de lógica mais comum que existe. O código compila, a página aparece e o texto está errado — nenhum aviso, nenhum sublinhado vermelho. Por isso a conferência de saída importa tanto: curl e grep mostram o texto final, sem opinião.

5. O outro prop: form

Além de data, toda página de rota recebe form. Ele é o resultado de um envio de formulário — quando não houve envio, vale null. Você vai usar muito daqui a poucas aulas; por ora basta saber que ele existe e que se declara junto:

<script>
	let { data, form } = $props();
</script>

{#if form?.ok}
	<p class="ok">Anotado para {form.cliente}.</p>
{:else if form?.falta}
	<p class="erro">{form.falta}</p>
{/if}

O ponto de interrogação em form?.ok é o encadeamento opcional: se form for null, a expressão inteira vira undefined em vez de estourar. Sem ele, a primeira renderização de qualquer página com esse código quebraria, porque null.ok não existe. Uma tecla que evita a maior parte dos erros de "cannot read properties of null".

Repare também que o mesmo componente usa data e form lado a lado. Eles não se misturam: data é o que o load devolveu agora; form é a resposta do último envio. Cada um tem seu papel, e a página lê os dois com o mesmo $props().

6. O data que vem do layout

Algumas informações valem para o site inteiro: o nome da padaria, o carrinho, o usuário logado. Elas não pertencem a uma rota só. O lugar delas é o +layout.server.js, cujo load roda para todas as páginas abaixo dele.

export function load() {
	return {
		loja: 'Padaria da Ana',
		aberta: new Date().getHours() >= 6 && new Date().getHours() < 19
	};
}

O data que chega a uma página é a junção do que o layout devolveu com o que a página devolveu. Se os dois têm um campo com o mesmo nome, o da página vence. Se a página precisa do valor do layout para calcular o seu, ela chama parent():

export async function load({ parent }) {
	const { aberta } = await parent();
	const pedidos = listar();

	return {
		aberta,
		pedidos,
		prontos: pedidos.filter((p) => p.pronto).length
	};
}

A ordem importa: chame parent() só quando precisar do valor dele, e de preferência depois de já ter buscado o que é seu. Assim as duas buscas acontecem em paralelo em vez de uma esperar a outra. O SvelteKit não faz mágica de ordenação; ele respeita a ordem em que você escreve.

Ler o data num componente fundo

Passar data por cinco componentes até chegar no rodapé é cansativo. Dentro de qualquer componente que esteja na árvore da página, import { page } from '$app/state' dá acesso a page.data, que é reativo. Use com parcimônia: componente que lê o mundo inteiro fica difícil de reaproveitar e de testar.

7. Quando o data vira estado

Ler o data resolve a maior parte das páginas. Mas existe um caso em que a tela precisa mudar depois de carregada, sem ir ao servidor de novo: o funcionário marca um pedido como pronto e quer ver o número mudar na hora. Aí o dado recebido deixa de ser só leitura e passa a ser uma cópia editável na memória do navegador.

A receita tem três passos e nenhum deles altera o data original. Primeiro, copie o valor para uma variável de estado: let pedidos = $state(data.pedidos). Segundo, calcule o que depende dele com $derived. Terceiro, escreva funções que troquem a lista por outra lista, em vez de mexer no item.

<script>
	let { data } = $props();

	let pedidos = $state(data.pedidos);
	let prontos = $derived(pedidos.filter((p) => p.pronto).length);

	function marcar(id) {
		pedidos = pedidos.map((p) => (p.id === id ? { ...p, pronto: true } : p));
	}
</script>

<button onclick={() => marcar(1)}>marcar o primeiro</button>
<p>{prontos} pronto(s)</p>

Missão: o botão devia marcar o pedido de id 1 como pronto, e não marca nada. Depois do clique, mostre 1 pronto(s).

<script>
	const data = {
		pedidos: [
			{ id: 1, cliente: 'Ana', pronto: false },
			{ id: 2, cliente: 'Bia', pronto: false }
		]
	};

	let pedidos = $state(data.pedidos);
	let prontos = $derived(pedidos.filter((p) => p.pronto).length);

	function marcar(id) {
		pedidos = pedidos.map((p) => (p.cliente === id ? { ...p, pronto: true } : p));
	}
</script>

<button onclick={() => marcar(1)}>marcar o primeiro</button>
<p>{prontos} pronto(s)</p>
<script>
	const data = {
		pedidos: [
			{ id: 1, cliente: 'Ana', pronto: false },
			{ id: 2, cliente: 'Bia', pronto: false }
		]
	};

<p>{prontos} pronto(s)</p>

O map devolve uma lista nova: para o item marcado, um objeto novo com pronto: true; para os outros, o mesmo objeto. Trocar a lista inteira é o que avisa a tela; mexer em p.pronto direto no item funcionaria em alguns casos e falharia em outros, e essa imprevisibilidade custa caro para quem está começando.

Note que a cópia é rasa: $state(data.pedidos) guarda a mesma lista de objetos. Isso basta aqui porque nunca alteramos um objeto no lugar. Se a página precisasse mexer dentro de um item, o caminho seria copiar também o item, como o { ...p } faz.

8. Quando dá errado

Três erros de quem está começando com o data. Os três aconteceram no projeto da Ana, e as mensagens estão copiadas do terminal.

Erro 1 — o jeito antigo de declarar prop

Quem já viu Svelte 4 escreve export let data. Em modo runas isso não existe mais, e o compilador diz exatamente qual é o substituto.

<script>
	export let data;
</script>

<h1>{data.pedidos.length}</h1>
Internal server error: src/routes/painel/+page.svelte:2:1 Cannot use `export let` in runes mode — use `$props()` instead
https://svelte.dev/e/legacy_export_invalid
  Plugin: vite-plugin-svelte:compile
  File: src/routes/painel/+page.svelte:2:1
   1 |  <script>
   2 |    export let data;
                          ^
   3 |  </script>

A setinha aponta a coluna exata do problema. A troca é mecânica: export let data vira let { data } = $props(). As outras props seguem a mesma regra, dentro das mesmas chaves.

Erro 2 — esquecer o $props()

Sem a declaração, o nome data simplesmente não existe no componente. O compilador não reclama, porque poderia ser uma variável global; o erro só aparece na hora de desenhar.

<script>
	let pedidos = [];
</script>

<h1>{data.pedidos.length}</h1>
ReferenceError: data is not defined
    at eval (src/routes/painel/+page.svelte:5:6)
    at eval (node_modules/svelte/src/internal/server/renderer.js:416:11)
500 GET /painel

is not defined é o recado de "esse nome não existe aqui". A linha 5 é a do {data.pedidos.length}. Conserto: declarar o prop na linha 1, ou usar a variável que você realmente declarou.

Erro 3 — o campo que o load não devolveu

O load devolveu pedidos; o HTML pediu data.lista. O resultado é undefined, e o primeiro .length estoura.

<script>
	let { data } = $props();
</script>

<h1>{data.lista.length}</h1>
TypeError: Cannot read properties of undefined (reading 'length')
    at eval (src/routes/painel/+page.svelte:5:17)
500 GET /painel

O compilador não tem como saber o formato do seu objeto; para ele, data é um valor qualquer. A conferência é sua: abra o +page.server.js e o +page.svelte lado a lado e compare os nomes dos campos letra por letra.

Um aviso que não é erro, mas suja a página

Este apareceu no projeto sem quebrar nada: uma tabela com <tr> solto, sem <tbody> em volta. O navegador reorganiza o HTML por conta própria e o Svelte avisa que a hidratação pode desencontrar.

5:25:01 PM [vite-plugin-svelte] src/routes/encomendas/+page.svelte:11:2 `<tr>` cannot be a child of `<table>`. `<table>` only allows these children: `<caption>`, `<colgroup>`, `<tbody>`, `<thead>`, `<tfoot>`, `<style>`, `<script>`, `<template>`. When rendering this component on the server, the resulting HTML will be modified by the browser (by moving, removing, or inserting elements), likely resulting in a `hydration_mismatch` warning
https://svelte.dev/e/node_invalid_placement_ssr

A correção é envolver as linhas em <tbody>. Vale tratar aviso assim como erro: ele quase sempre aponta um HTML que o navegador vai "consertar" sozinho, e o conserto dele nem sempre é o que você queria.

9. Conferindo o que a página escreveu

Conferir texto é mais fácil do que parece. Escolha um pedaço do texto que só existe se o dado chegou — um número, um nome — e peça ao grep para encontrá-lo:

ana@notebook:~/loja$ curl -s localhost:5173/painel | grep -o 'na fila'
na fila
ana@notebook:~/loja$ curl -s localhost:5173/painel | grep -o '1 pronto(s), 1 na fila'
1 pronto(s), 1 na fila

Se a segunda linha sair, a página está certa. Se a primeira sair e a segunda não, o texto mudou — talvez o $derived esteja com a conta errada. Esse tipo de conferência entra em qualquer rotina de teste depois, e é a mesma ideia que uma ferramenta de teste automatizado faz: procurar no HTML final o texto que deveria estar ali.

Uma armadilha conhecida: o navegador pode mostrar um valor e o curl outro se você estiver vendo uma versão em cache. Antes de acusar o código, recarregue com Ctrl+Shift+R e rode o curl de novo. Quando os dois discordam, quase sempre é cache de um dos lados.

Resumo

  • O data chega ao +page.svelte como prop e se declara com let { data } = $props().
  • Sem essa linha, o nome data não existe: ReferenceError: data is not defined.
  • Valor padrão na desestruturação evita quebra quando o prop não vem: let { data = { pedidos: [] } } = $props().
  • data é para ler. Para calcular, use $derived; para mudar, copie para uma variável de estado.
  • form é o outro prop da rota: a resposta do último envio, ou null.
  • form?.ok é encadeamento opcional e evita o erro de ler propriedade de null.
  • O data da página é a junção do data do layout com o do load da página; parent() acessa o do layout.
  • Nome de campo errado não gera erro de compilação: gera Cannot read properties of undefined na hora de desenhar.
  • Aviso também é recado: node_invalid_placement_ssr aponta HTML que o navegador vai reorganizar.
  • curl mais grep conferem o texto final sem depender do navegador.
