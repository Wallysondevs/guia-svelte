Svelte · Debounce e Busca

Toda vez que a Ana digita uma letra no campo de busca da padaria, o sistema corre até a prateleira, procura o produto e volta. Na primeira letra ele ainda está voltando quando a segunda chega; na terceira, há três corridas acontecendo e a resposta que aparece pode ser a da primeira. O nome desse problema é excesso de trabalho por tecla, e a cura tem um nome esquisito: debounce. A ideia é simples como a vida no balcão: espere a pessoa terminar de falar antes de sair correndo.

Você vai aprender
  • Por que responder a cada letra digitada é caro e às vezes errado.
  • O que é debounce e o que ele não é.
  • Como usar setTimeout e clearTimeout para esperar.
  • Como fazer o mesmo com $effect e a função de limpeza.
  • Por que a resposta antiga pode chegar depois da nova e como evitar.
  • Debounce contra throttle: duas ideias parecidas com usos diferentes.
  • Que atraso escolher e como o número muda a sensação de velocidade.
  • Cuidados com o campo: foco, cursor e leitores de tela.
  • Os três erros reais desta aula, com a mensagem do compilador.

1. A ideia: esperar a pessoa terminar a palavra

Quando alguém pede "pão de queijo" no balcão, a Ana não corre para a cozinha a cada sílaba. Ela espera a frase terminar, confere se é isso mesmo e só então vai. Se ela corresse a cada som, faria quatro viagens para atender um pedido — e voltaria com a coisa errada nas três primeiras.

Um campo de busca sem cuidado faz exatamente isso. Cada tecla dispara uma busca: "p", "pã", "pão". As duas primeiras são inúteis, e a terceira é a única que interessa. Pior: se a busca vai pela rede, as três respostas podem voltar fora de ordem, e a tela termina mostrando o resultado de "p" — o nome bonito disso é condição de corrida.

Debounce é a regra de esperar um tempinho antes de agir. Cada tecla reinicia a contagem: se a pessoa digitar de novo antes do tempo acabar, a busca anterior é cancelada e a contagem começa do zero. Quando ela para de digitar por tempo suficiente, aí sim a busca acontece — uma só, com a palavra inteira.

No balcãoNo componente
Ouvir a sílaba e já sair correndooninput chamando a busca direto
Esperar a frase terminaresperar alguns milissegundos sem nova tecla
A frase mudou no meio: recomeçar a esperaclearTimeout e um setTimeout novo
Ninguém falou mais nada: iro temporizador termina e a busca roda
Um pedido, uma viagemuma busca por palavra digitada

O vocabulário: temporizador é o relógio que conta até um horário e chama uma função; atraso ou espera é quanto tempo ele conta; limpar é cancelar um temporizador antes de ele disparar; e debounce é o padrão inteiro — cancelar e reagendar a cada tecla. Quatro palavras, um conceito só.

2. A busca que responde a cada letra

Comece pelo jeito direto. O termo é estado, os produtos são uma constante, e um $derived recalcula a lista de achados a cada mudança no termo. Enquanto a busca é local, feita na memória, isso é rápido e honesto: não há rede, não há espera, e mostrar o resultado a cada letra dá até prazer.

<script>
  const produtos = ['Pão francês', 'Pão de queijo', 'Bolo de fubá'];
  let termo = $state('pão');
  let achados = $derived(
    produtos.filter((p) => p.toLowerCase().includes(termo.toLowerCase()))
  );
</script>

<input bind:value={termo} placeholder="buscar" />
<p>{achados.length} achado(s) para "{termo}"</p>

Com o termo começando em "pão", o HTML já sai com a resposta pronta:

<input value="pão" placeholder="buscar"/> <p>2 achado(s) para "pão"</p>
let termo = $state('pão')
o texto digitado é estado: muda a cada tecla e a tela acompanha.
bind:value={termo}
liga o campo ao estado nos dois sentidos. O valor inicial aparece no campo, e o que a pessoa digita entra no estado.
$derived(…)
a lista de achados é calculada. Cada mudança no termo refaz o filtro; a tela nunca fica com a lista velha.
includes(termo.toLowerCase())
a condição da busca, com minúsculas dos dois lados para "Pão" e "pão" darem no mesmo lugar.
{achados.length}
mostrar a contagem ajuda a pessoa a saber se a busca encontrou algo, antes mesmo de ler a lista.

O bind:value é a única peça que muda de comportamento quando a busca deixa de ser local. Com a lista na memória, cada letra é uma conta de microssegundos. Com a lista no servidor, cada letra é uma viagem de rede — e aí o problema desta aula aparece de verdade.

3. Esperar a poeira baixar

A receita do debounce cabe em três linhas. Primeiro, guarde o identificador do temporizador numa variável. Segundo, antes de criar um novo, cancele o anterior com clearTimeout. Terceiro, crie o novo com setTimeout, com o atraso escolhido.

<script>
  let termo = $state('');
  let buscado = $state('');
  let buscas = $state(0);
  let relogio;

  function aoDigitar(evento) {
    termo = evento.target.value;
    clearTimeout(relogio);
    relogio = setTimeout(() => {
      buscado = termo;
      buscas += 1;
    }, 300);
  }
</script>

<input value={termo} oninput={aoDigitar} placeholder="buscar" />
<p>buscas: {buscas} · termo buscado: "{buscado}"</p>

A saída do servidor mostra o estado inicial, sem busca nenhuma — ninguém digitou ainda:

<input value="" placeholder="buscar"/> <p>buscas: 0 · termo buscado: ""</p>
let relogio
o identificador do temporizador pendente. Não é estado: ele não aparece na tela, então não precisa avisar ninguém quando muda.
clearTimeout(relogio)
cancela o temporizador anterior, se existir. Cancelar um número que não existe não dá erro: a função não faz nada.
setTimeout(f, 300)
marca f para rodar daqui a 300 ms e devolve um número que identifica esse agendamento.
() => { buscado = termo; }
o trabalho que só roda depois da espera. Aqui ele lê o termo do momento em que a função roda, não do momento em que foi agendada.
evento.target.value
o texto atual do campo. É o valor de agora, mesmo que o estado demore um instante para acompanhar.

Missão: o contador sobe a cada tecla: digitar "p", "pã" e "pão" dá 3 buscas. Faça a busca esperar 300 ms sem nova tecla e o mesmo teste terminar em buscas: 1.

<script>
  let buscas = $state(0);
</script>

<input oninput={() => (buscas += 1)} placeholder="buscar" />
<p>buscas: {buscas}</p>
<script>
  let buscas = $state(0);
  let relogio;

  function aoDigitar() {
    clearTimeout(relogio);
    relogio = setTimeout(() => (buscas += 1), 300);
  }
</script>

<input oninput={aoDigitar} placeholder="buscar" />
<p>buscas: {buscas}</p>

Repare que o campo ficou sem bind:value na solução: quem lê o texto é evento.target.value. As duas formas funcionam, e a diferença aparece na seção 7 — usar bind junto com o temporizador cria um estado a mais para sincronizar, e estado a mais é oportunidade de erro.

4. O mesmo com $effect e a função de limpeza

Existe um jeito mais declarativo de fazer a mesma coisa: em vez de reagir ao evento, reagir à mudança do estado. O $effect roda quando o termo muda, agenda a busca, e devolve uma função de limpeza que o Svelte chama antes da próxima execução e quando o componente sai da tela.

<script>
  let termo = $state('');
  let buscado = $state('');
  let buscas = $state(0);

  $effect(() => {
    const atual = termo;
    const relogio = setTimeout(() => {
      buscado = atual;
      buscas += 1;
    }, 300);
    return () => clearTimeout(relogio);
  });
</script>

<input bind:value={termo} placeholder="buscar" />
<p>buscas: {buscas} · termo buscado: "{buscado}"</p>
<input value="" placeholder="buscar"/> <p>buscas: 0 · termo buscado: ""</p>

A função de limpeza é a peça que faz o debounce funcionar: cada execução do efeito cancela o temporizador da execução anterior. Sem ela, cada tecla deixa um temporizador vivo, e todos disparam — o mesmo problema do começo, só que agora escondido dentro de um efeito.

O efeito precisa ler o que ele observa

O $effect só reage ao que ele lê durante a execução. A linha const atual = termo existe para isso: ela lê o estado e registra a dependência. Se você tirar essa linha e usar apenas o valor dentro do setTimeout, a leitura acontece fora do rastreamento e o efeito roda uma vez só, na montagem.

Missão: o efeito agenda um temporizador por tecla e o contador chega a 4 buscas (uma da montagem e três das letras). Devolva a função de limpeza certa e faça o teste terminar em buscas: 1.

<script>
  let termo = $state('');
  let buscas = $state(0);

  $effect(() => {
    const atual = termo;
    setTimeout(() => (buscas += 1), 300);
  });
</script>

<input bind:value={termo} placeholder="buscar" />
<p>buscas: {buscas}</p>
<script>
  let termo = $state('');
  let buscas = $state(0);

  $effect(() => {
    const atual = termo;
    const relogio = setTimeout(() => (buscas += 1), 300);
    return () => clearTimeout(relogio);
  });
</script>

<input bind:value={termo} placeholder="buscar" />
<p>buscas: {buscas}</p>

Qual das duas formas usar? A do evento é mais fácil de explicar e de testar: o temporizador nasce e morre dentro de uma função. A do efeito acompanha qualquer mudança no estado, inclusive as que não vieram do teclado — um botão "limpar", um link que preenche a busca, um valor restaurado da memória. Se a busca pode mudar por vários caminhos, o efeito é o lugar certo.

5. A resposta antiga que chega depois

Existe um caso em que atrasar não é economia, é correção. Imagine que a busca de "p" seja lenta (o índice é grande) e a de "pão" seja rápida. Sem cancelamento, a resposta de "pão" chega primeiro e a de "p" chega depois e sobrescreve a tela com o resultado errado. A pessoa vê resultado de uma busca que ela já abandonou.

O clearTimeout resolve o caso quando o atraso é seu. Quando a busca já saiu para a rede e não dá mais para cancelar o temporizador, a ferramenta é o AbortController: cada busca leva um controlador, e a nova busca chama abort() na anterior. O fetch abortado rejeita com um erro que você ignora de propósito, porque ele não é falha — é cancelamento.

Missão: a busca curta demora 400 ms e a longa 100 ms, e a antiga sobrescreve a nova. Faça a última digitada vencer: o teste termina com resultado: "pão".

<script>
  let resultado = $state('');

  function aoDigitar(evento) {
    const valor = evento.target.value;
    const atraso = valor.length <= 1 ? 400 : 100;
    setTimeout(() => (resultado = valor), atraso);
  }
</script>

<input oninput={aoDigitar} placeholder="buscar" />
<p>resultado: "{resultado}"</p>
<script>
  let resultado = $state('');
  let relogio;

  function aoDigitar(evento) {
    const valor = evento.target.value;
    const atraso = valor.length <= 1 ? 400 : 100;
    clearTimeout(relogio);
    relogio = setTimeout(() => (resultado = valor), atraso);
  }
</script>

<input oninput={aoDigitar} placeholder="buscar" />
<p>resultado: "{resultado}"</p>

O mesmo problema, com rede, se chama last write wins — a última escrita vence. A solução é a mesma em espírito: dar identidade a cada pedido e ignorar a resposta que não corresponde ao pedido mais recente.

6. Debounce, throttle e nenhum dos dois

Debounce espera o silêncio. Throttle (acelerador) faz o contrário: garante que a função rode no máximo uma vez a cada intervalo, mesmo que os eventos continuem chegando. Os dois economizam trabalho, com efeitos diferentes na tela.

PadrãoQuando rodaBom para
Sem nadaa cada eventobusca local, filtro na memória
Debouncedepois de um silêncio de N msbusca com rede, validação de formulário
Throttleno máximo uma vez a cada N msrolagem, movimento do mouse, redimensionar
Leading debouncena primeira tecla, e ignora o resto por N msbotão que não pode repetir o clique

O erro comum é usar debounce onde precisava de throttle. Numa rolagem, debounce só dispara quando a pessoa para de rolar — e uma barra de progresso que só atualiza no fim é quase inútil. Numa busca, throttle dispara no meio da palavra — o problema que você queria evitar. A pergunta que decide: você quer o valor final ou quer uma amostra regular durante o movimento?

7. Que atraso escolher

Não existe número certo, existe número justificável. Abaixo de 100 ms, o debounce quase não economiza nada: a pessoa não consegue digitar duas letras nesse intervalo. Acima de 500 ms, a pausa é sentida como lentidão. A faixa útil fica entre 200 e 400 ms, e 300 ms é o meio da faixa.

O número depende do custo da busca. Uma consulta local de 2 ms não precisa de debounce nenhum; uma chamada de rede de 200 ms precisa, e o atraso pode ser maior porque a viagem já demora. O que não muda é a regra de ouro: o atraso é uma promessa. Se você escolhe 300 ms, a busca não pode demorar 800 — o debounce esconde a espera que você controla, não a que você não controla.

Uma forma honesta de escolher é medir. Coloque um contador de buscas na tela, digite uma palavra de dez letras e veja quantas buscas aconteceram com e sem o debounce. Sem ele, dez; com ele, uma. A diferença é o trabalho que a sua máquina e a rede deixaram de fazer.

8. Cuidados com o campo

Debounce mexe com o tempo, e o tempo mexe com a sensação de quem digita. Três cuidados evitam a maioria das reclamações. O primeiro: não recrie o campo. Se o elemento do input for recriado a cada mudança, o cursor volta para o começo e o foco se perde. Isso acontece quando o campo está dentro de um bloco condicional que muda de posição.

O segundo: cuide do texto que a pessoa já digitou. Debounce atrasa a busca, nunca o valor do campo. O campo precisa mostrar cada letra na hora; o que espera é a consulta. Na solução da seção 3, isso está garantido porque o campo é o dono do próprio texto e o estado só recebe o resultado depois.

O terceiro: acessibilidade. Quem usa leitor de tela precisa saber que a lista mudou. Uma região com aria-live="polite" anuncia o resultado novo; sem ela, a pessoa ouve o mesmo silêncio de antes. E o contador de resultados — "2 achados" — é a informação mais útil que a tela pode dar nesse momento.

9. Quando dá errado

As três mensagens abaixo saíram do compilador e do renderizador desta versão, copiadas como estão.

Erro 1 — ligar o campo a uma constante

O campo precisa escrever no estado, e uma constante não aceita escrita. O compilador percebe e recusa antes de qualquer execução.

<script>
  const termo = '';
</script>

<input bind:value={termo} />
<p>{termo}</p>
Erro de compilação (linha 5, coluna 7): Cannot bind to constant

"Cannot bind to constant" quer dizer "não posso ligar a uma constante". Troque const por let e acrescente $state, e o campo volta a funcionar: let termo = $state('').

Erro 2 — nome da função com minúscula errada

O JavaScript diferencia maiúsculas de minúsculas. setTimeout tem um "T" grande no meio, e escrever tudo minúsculo cria uma função que não existe.

<script>
  let buscas = $state(0);
</script>

<p>{settimeout(() => buscas++, 300)}</p>
Erro ao renderizar: settimeout is not defined

"is not defined" é o recado de que o nome não existe naquele lugar. Aqui o erro aparece na renderização porque a chamada está dentro do HTML; no <script>, apareceria na hora do clique.

Erro 3 — window no servidor

setTimeout é global: existe no navegador e no Node. window é só do navegador, e usá-lo no corpo do script quebra a renderização do servidor.

<script>
  let buscas = $state(0);
  let relogio = window.setTimeout(() => (buscas += 1), 300);
</script>

<p>buscas: {buscas}</p>
Erro ao renderizar: window is not defined

"window is not defined" é a mensagem que mais aparece para quem esquece que o componente roda nos dois lugares. Para temporizadores, use setTimeout sem o prefixo; para o resto, mova a chamada para um $effect.

10. O debounce que não cancela nada

Existe uma armadilha silenciosa: criar o temporizador dentro de uma função que é chamada de novo, mas guardar o identificador numa variável local. A cada chamada nasce uma variável nova, o clearTimeout sempre recebe undefined e nenhum temporizador é cancelado. O código parece certo e não faz nada.

A correção é declarar o identificador fora da função, no corpo do <script>, para todas as chamadas enxergarem o mesmo. No exemplo da seção 3, let relogio; está lá em cima, e é por isso que funciona. Esse é o tipo de erro que o compilador não vê: ele não sabe que a sua intenção era compartilhar a variável.

Outra armadilha é limpar o temporizador no lugar errado. Limpar na montagem do componente não cancela a busca da última tecla; limpar no evento, antes de criar o novo, cancela. A ordem — clearTimeout primeiro, setTimeout depois — não é estilo: é a diferença entre cancelar o anterior e cancelar o novo.

Resumo

  • Sem debounce, cada tecla dispara uma busca — e a resposta antiga pode chegar por último.
  • Debounce espera um silêncio de N milissegundos antes de agir.
  • A receita: clearTimeout(relogio) e depois relogio = setTimeout(…).
  • O identificador do temporizador fica fora da função, para todas as chamadas verem o mesmo.
  • Com $effect, a função de limpeza faz o papel do clearTimeout.
  • O efeito precisa ler o estado durante a execução para registrar a dependência.
  • Throttle é para amostras regulares; debounce é para o valor final.
  • Atrasos entre 200 e 400 ms; 300 ms é um meio de faixa defensável.
  • Debounce atrasa a busca, nunca o texto do campo.
  • AbortController cancela a busca que já saiu para a rede.
