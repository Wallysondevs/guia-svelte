SvelteKit · Build e Deploy

Até agora o site da Ana só existe no notebook dela, num endereço que começa com localhost e que ninguém mais no mundo consegue abrir. Chegou a hora de levar a padaria para a internet. A viagem tem quatro etapas: gerar o pacote, conferir o pacote, ligar o servidor e apontar o endereço. Cada etapa tem um comando e cada comando tem uma saída — e é isso que esta aula mostra, com o terminal copiado de uma execução real.

Você vai aprender
  • O que muda entre o servidor de desenvolvimento e o pacote de produção.
  • Como ler a saída de npm run build sem se perder nas linhas.
  • Como subir o pacote gerado com node build.
  • Quais variáveis de ambiente precisam existir na máquina de produção.
  • O que fazer quando a porta já está ocupada.
  • Por que o servidor precisa continuar rodando depois que você fecha o terminal.
  • O que é o SIGTERM e por que o adaptador-node trata esse sinal.
  • Como conferir com npm run preview antes de anunciar o endereço.
  • Os três tropeços reais: variável faltando, porta ocupada e servidor fora do ar.

1. A ideia: a mudança do pão para a loja nova

Enquanto a Ana vende na porta de casa, ela usa a cozinha inteira: a bancada, a farinha espalhada, o forno ligado o dia todo. É prático porque ela está ali mesmo. No dia em que abre a loja na rua, ela não leva a cozinha suja: leva o pão pronto, numa caixa, e a loja tem a sua própria estrutura — balcão, vitrine, caixa registradora.

Publicar um site é essa mudança. O servidor de desenvolvimento é a cozinha: recompila a cada arquivo salvo, mostra mensagem detalhada, recarrega a página sozinho. Nada disso serve no ar. O pacote de produção é a caixa de pão: só o que o cliente precisa, sem farinha espalhada, sem ferramenta de cozinha.

O adaptador (assunto da aula anterior) decide o formato da caixa. Nesta aula a caixa é a do adapter-node, que produz uma pasta build/ com um servidor Node completo. As etapas seguintes são iguais para qualquer adaptador: gerar, conferir, ligar, apontar.

2. O que o build de produção faz

O comando é o mesmo de sempre — npm run build —, mas o que ele produz é outra coisa. Os três primeiros segundos da sessão mostram o Vite compilando o lado do servidor:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v8.4.0 building ssr environment for production...
transforming...
✓ 161 modules transformed.
rendering chunks...
computing gzip size...

“building ssr environment for production” é a frase que separa desenvolvimento de produção: SSR quer dizer renderização no servidor, o modo em que o HTML sai pronto do servidor antes de chegar ao navegador. “161 modules transformed” é a conta dos seus arquivos e das dependências que o SvelteKit juntou.

Depois do build do servidor vem o build do cliente, e então a parte que só existe no SvelteKit:

✓ built in 404ms
Prerendering
GET /seo → 200 (12 ms)
GET /sobre → 200 (2 ms)
GET / → 204 (0 ms)
GET /produtos → 204 (0 ms)
GET /entrar → 204 (0 ms)

Run npm run preview to preview your production build locally.

> Using @sveltejs/adapter-node
Copying assets
Compressing and hashing assets
✔ done

A seção Prerendering é o app rodando de verdade durante o build, para gerar as páginas que têm prerender = true. É por isso que o console.log do seu hooks.server.js aparece ali: o servidor está no ar, só que por alguns milissegundos e sem ninguém visitando. Se um load consulta o banco nessa hora, o banco precisa estar acessível durante o build também.

“✔ done” é o adaptador terminando. A partir daí existe uma pasta build/ que é o site inteiro. O próximo passo é colocar essa pasta para rodar.

3. Subindo o pacote: node build

O comando é curto porque o adaptador-node escreveu um ponto de entrada. Rodando na máquina da Ana, com a variável do banco no ambiente:

ana@notebook:~/loja$ DATABASE_URL='postgres://ana:segredo@localhost:5432/padaria' node build
Listening on http://0.0.0.0:3000
DATABASE_URL='…'
a variável de ambiente passada só para este comando. Ela vale para o processo que está nascendo, não para o resto do terminal.
node
o programa que executa JavaScript fora do navegador. É o mesmo node de todos os outros comandos do projeto.
build
o nome da pasta gerada pelo adaptador. O Node procura um index.js dentro dela; é esse arquivo que liga o servidor.
Listening on http://0.0.0.0:3000
a confirmação: o servidor está escutando em todas as interfaces, na porta 3000.
%{http_code}
nos comandos de conferência, o espaço onde o curl escreve o status da resposta.

Uma linha e o servidor está no ar. 0.0.0.0 é “todas as interfaces de rede”: significa que o servidor aceita pedido vindo de fora da máquina, não só do próprio computador. É diferente de 127.0.0.1, que aceitaria apenas pedidos locais. O 3000 é a porta padrão do adaptador-node.

Com o servidor no ar, um pedido de fora funciona igual ao de desenvolvimento — e agora sem localhost na frente:

ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3000/
200
ana@notebook:~/loja$ curl -s http://localhost:3000/seo | grep -o '<title>[^<]*</title>'
<title>Pão francês quentinho toda manhã | Padaria da Ana</title>
ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/cache | grep -i 'cache-control\|etag'
cache-control: max-age=60
etag: "1yfxlpq"

Repare que a página /seo já vem com o título certo no HTML, sem JavaScript nenhum rodando: ela foi pré-renderizada no build. E o cache-control definido no load com setHeaders chegou ao cliente, junto com um etag que o adaptador calculou.

4. As variáveis que a máquina de produção precisa ter

Aqui mora o tropeço mais comum da primeira publicação. O arquivo .env é do desenvolvimento: ele fica na máquina da Ana e não vai para o Git. Na máquina de produção o .env não existe, então as variáveis precisam ser passadas de outro jeito — na linha de comando, como no exemplo acima, ou no painel da plataforma de deploy.

Quais variáveis, exatamente? O adaptador-node tem as dele, para configurar o próprio servidor. O arquivo gerado no build lista todas, e vale conhecer as principais:

5. Caixa 1: o roteiro de publicação

Publicar é seguir um roteiro. A caixa abaixo tem três passos e diz “ok” para os três, mesmo quando um deles não foi feito. A missão é mostrar falta onde o passo está pendente.

Missão: cada passo tem feito: true ou feito: false. Mostre ok quando estiver feito e falta quando não estiver; o texto precisa conter passar DATABASE_URL: falta.

<script>
	const passos = [
		{ nome: 'rodar o build', feito: true },
		{ nome: 'passar DATABASE_URL', feito: false },
		{ nome: 'subir o servidor', feito: false }
	];
</script>

<ul>
	{#each passos as p}
		<li>{p.nome}: ok</li>
	{/each}
</ul>
<script>
	const passos = [
		{ nome: 'rodar o build', feito: true },
		{ nome: 'passar DATABASE_URL', feito: false },
		{ nome: 'subir o servidor', feito: false }
	];
</script>

<ul>
	{#each passos as p}
		<li>{p.nome}: {p.feito ? 'ok' : 'falta'}</li>
	{/each}
</ul>

Esse tipo de lista de verificação vale mais do que parece. Numa publicação real, “passar a variável” é o passo que ninguém lembra, e o sintoma é o servidor subindo e caindo em seguida com env_invalid — você vai ver essa mensagem na seção de erros.

6. O servidor precisa continuar rodando

Enquanto o terminal estiver aberto, node build fica no ar. Feche o terminal e o servidor morre junto: o processo é filho do shell. Numa máquina de verdade isso não resolve — ninguém vai deixar uma janela aberta a vida toda.

A solução é um gerenciador de processos, um programa cujo trabalho é manter outro programa vivo. No Linux, o mais comum é o systemd; no mundo Node, o pm2 é popular. Os dois fazem a mesma coisa: iniciam o processo no boot, reiniciam se ele cair e guardam a saída num arquivo de log.

O adaptador-node ajuda nesse trabalho porque trata sinais do sistema. Quando o systemd ou o Docker pede para parar, ele manda o sinal SIGTERM; o servidor gerado espera os pedidos em andamento terminarem, dentro do SHUTDOWN_TIMEOUT, e só então encerra. A prova está no terminal: ao receber o sinal, nada de erro e nada de pilha.

ana@notebook:~/loja$ node build > loja.log 2>&1 &
ana@notebook:~/loja$ sleep 2; curl -s -o /dev/null -w 'GET / -> %{http_code}\n' http://localhost:3000/
GET / -> 200
ana@notebook:~/loja$ kill -TERM $!; wait $!; echo "codigo de saida: $?"
codigo de saida: 0
ana@notebook:~/loja$ cat loja.log
Listening on http://0.0.0.0:3000
GET / → 200 (40 ms)

O código de saída é zero, e zero em Unix quer dizer “terminei bem”. O servidor recebeu o pedido de encerramento, esperou os pedidos em andamento terminarem e saiu sem erro. Esse cuidado é o que evita cliente vendo “erro de conexão” no meio de um pagamento quando a máquina é reiniciada.

Um processo, uma porta

Cada processo escuta uma porta. Se você subir node build duas vezes sem mudar a porta, o segundo não consegue escutar — e é isso que a seção de erros mostra com EADDRINUSE. Em produção, a plataforma cuida disso; na VPS, você decide a porta no comando.

7. Caixa 2: quais variáveis precisam existir no servidor

Nem toda variável declarada em src/env.js precisa aparecer na máquina de produção. As estáticas já foram congeladas no build. As outras precisam ser encontradas quando o servidor sobe. A caixa abaixo conta todas.

Missão: conte só as variáveis com estatica: false, que são as que o servidor precisa encontrar na hora de subir. O texto deve virar Precisam existir no servidor: 1.

<script>
	const vars = [
		{ nome: 'DATABASE_URL', publica: false, estatica: false },
		{ nome: 'PUBLIC_LOJA_NOME', publica: true, estatica: true }
	];
</script>

<p>Precisam existir no servidor: 2</p>
<script>
	const vars = [
		{ nome: 'DATABASE_URL', publica: false, estatica: false },
		{ nome: 'PUBLIC_LOJA_NOME', publica: true, estatica: true }
	];

	const noServidor = $derived(vars.filter((v) => !v.estatica));
</script>

<p>Precisam existir no servidor: {noServidor.length}</p>

filter devolve uma lista nova só com os itens aprovados pela função. O ! antes de v.estatica inverte o valor: aprovado quando for falso. Depois, length conta. A mesma estrutura serve para “quantos pedidos estão pendentes” ou “quantos produtos estão sem estoque”.

8. Conferindo antes de anunciar

Antes de apontar o domínio, uma passada de olho no pacote evita vexame. O comando npm run preview serve o build pelo Vite, sem o adaptador, e é útil para conferir página por página:

ana@notebook:~/loja$ npm run preview -- --port 4173

> loja@0.0.1 preview
> vite preview --port 4173

  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose

Note que o preview não imprime a versão do Vite nem a linha de “ready”: ele é mais silencioso que o dev. O comportamento das páginas, porém, é o do pacote final — inclusive o das variáveis congeladas no build.

O que conferirComo conferir
O título e a descrição aparecem no HTMLver o código-fonte da página, não o inspetor
O formulário de login funcionaenviar senha errada e senha certa
As páginas com prerender estão na pastals build/prerendered
Imagem e PDF abremclicar em cada link da pasta static
Nenhuma página protegida virou arquivoprocurar conta.html na pasta prerendered

Numa página de diagnóstico, o status vira componente com uma linha de lógica:

<script>
	let { status = 200 } = $props();
</script>

<p>Resposta: {status} {status === 200 ? 'ok' : 'verificar'}</p>
<p>Resposta: 200 ok</p>

Com o valor padrão, o componente já responde ok quando ninguém passa nada. Quem passa 404 recebe verificar — a mesma ideia dos passos da caixa 1, agora com o status que o curl mostrou.

A última linha da tabela é uma armadilha real. No projeto da Ana, o rastreador de links do build chegou na página /conta pelo menu, recebeu o redirecionamento do hook e congelou o resultado num arquivo conta.html de 112 bytes. Não vazou dado nenhum, mas a página passou a existir como arquivo estático. Quem depende de login para tudo precisa revisar a pasta antes de publicar.

9. Caixa 3: a ordem dos passos

Ordem errada em publicação custa tempo e susto. A caixa abaixo tem os três passos fora de ordem e mostra na sequência em que estão. A missão é colocar rodar o build primeiro.

Missão: reordene a lista para que o primeiro parágrafo na tela seja rodar o build, depois conferir com preview e por último subir o servidor.

<script>
	const passos = ['subir o servidor', 'rodar o build', 'conferir com preview'];
</script>

{#each passos as p}
	<p>{p}</p>
{/each}
<script>
	const passos = ['rodar o build', 'conferir com preview', 'subir o servidor'];
</script>

{#each passos as p}
	<p>{p}</p>
{/each}

A ordem não é capricho: sem build não existe o que conferir, e sem conferir você sobe um pacote que talvez não funcione. Quem publica com pressa pula o meio e descobre o problema com o cliente olhando — que é exatamente o custo que o preview existe para evitar.

10. O endereço e o proxy

Falta o último pedaço: fazer o domínio apontar para a máquina. Num servidor alugado, o caminho comum é um proxy reverso — Nginx ou Caddy — recebendo o pedido na porta 80 e 443 e repassando para o node build na porta 3000. O proxy cuida do certificado HTTPS; o SvelteKit cuida da página.

Nesse arranjo existem duas armadilhas. A primeira: o servidor Node passa a ver todos os pedidos vindo do proxy, então o IP do cliente precisa ser lido de um cabeçalho — é para isso que serve ADDRESS_HEADER e XFF_DEPTH. A segunda: URLs absolutas, como as de um sitemap, precisam saber o endereço público; é para isso que serve ORIGIN.

Também vale saber que o endereço público não muda o código: o SvelteKit monta links relativos por padrão, e a página funciona em qualquer domínio. Configuração de proxy é infraestrutura, não programação de componente — e as duas coisas vivem em arquivos diferentes.

11. Quando dá errado

As três mensagens abaixo saíram da máquina da Ana. Duas são do próprio servidor Node; a terceira vem do curl tentando falar com um servidor que não está no ar.

Erro 1 — a variável não chegou na produção

O .env ficou na máquina de desenvolvimento e ninguém passou DATABASE_URL para o processo. O servidor sobe, valida o ambiente e cai antes de aceitar o primeiro pedido.

ana@notebook:~/loja$ node build
node:internal/modules/run_main:123
    triggerUncaughtException(
    ^

[SvelteKit error: env_invalid
Invalid environment variables:

DATABASE_URL
  - Value is missing. If it is optional, add a validator declaring it as such.

https://svelte.dev/e/kit/env_invalid]

Node.js v22.23.5

A correção é passar a variável na hora de subir — DATABASE_URL='…' node build — ou configurá-la no painel da plataforma. Um detalhe que confunde: no npm run dev isso não acontece, porque o Vite lê o .env sozinho. A diferença entre dev e produção é justamente essa.

Erro 2 — a porta já está ocupada

Você subiu o servidor uma vez e esqueceu. Ao subir de novo, o segundo processo não consegue escutar na mesma porta.

ana@notebook:~/loja$ node build
node:events:497
      throw er; // Unhandled 'error' event
      ^

Error: listen EADDRINUSE: address already in use 0.0.0.0:3000
    at Server.setupListenHandle [as _listen2] (node:net:1941:16)
    at listenInCluster (node:net:1998:12)
    at node:net:2207:7
    at process.processTicksAndRejections (node:internal/process/task_queues:89:21)
Emitted 'error' event on Server instance at:
    at emitErrorNT (node:net:1977:8)

EADDRINUSE é “endereço em uso”. A leitura é literal: já existe alguém escutando na porta 3000. As saídas são parar o processo antigo ou escolher outra porta — PORT=3001 node build — lembrando de ajustar o proxy para a porta nova.

Erro 3 — ninguém do outro lado

Este é o erro que o cliente vê quando o servidor não está no ar, ou quando a porta está errada. O curl é o mensageiro: ele avisa que a conexão não foi aceita.

ana@notebook:~/loja$ curl -sS http://localhost:3000/
curl: (7) Failed to connect to localhost port 3000 after 0 ms: Couldn't connect to server

O código 7 do curl é “não consegui conectar”, e não “a página não existe”. Isso ajuda a separar os dois problemas: 404 é páginas, 7 é servidor. Se o processo estiver rodando, confira a porta no comando e no proxy antes de suspeitar do código.

Resumo

  • npm run dev é a cozinha; npm run build é a caixa de pão pronta para a loja.
  • O build roda o app para pré-renderizar páginas — por isso o banco precisa estar acessível durante o build.
  • node build sobe o pacote do adapter-node e imprime Listening on http://0.0.0.0:3000.
  • O .env é do desenvolvimento; em produção a variável vem do ambiente ou do painel da plataforma.
  • O adaptador-node lê PORT, HOST, ORIGIN, BODY_SIZE_LIMIT e outros para se configurar.
  • Um gerenciador de processos (systemd ou pm2) mantém o servidor vivo e o reinicia.
  • SIGTERM pede encerramento educado: o adaptador espera os pedidos em andamento.
  • npm run preview confere o build antes de anunciar o endereço.
  • Erros desta aula: env_invalid, EADDRINUSE e curl: (7).
