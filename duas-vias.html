Svelte · Quando Não Usar bind

A Ana tem uma porta de duas folhas no balcão: entra e sai gente o tempo todo, e isso é bom. Mas na porta do estoque ela instalou uma porta de uma folha só, que abre para dentro e tem trava. O bind é a porta de duas folhas: cômodo, rápido, e perigoso quando você precisa controlar quem passa. Esta aula é sobre escolher a porta certa — quando o atalho ajuda e quando ele esconde a regra que você precisa escrever.

Você vai aprender
  • O que o bind faz que você não vê no código.
  • Como escrever a ligação de duas vias à mão, com value e oninput.
  • Como formatar o valor antes de guardar, recusando o que não serve.
  • Como validar sem deixar o estado receber lixo.
  • Por que valor calculado não deve ser digitado.
  • O que é $bindable e quando ele aparece em componentes.
  • Os três erros reais desta aula, com a mensagem do compilador.
  • Uma tabela de decisão para escolher entre atalho e caminho longo.

1. A ideia: a porta de duas folhas

Uma porta de duas folhas é prática: qualquer pessoa entra e sai sem pensar. O problema aparece quando você precisa saber quem passou, em que ordem, com o que nas mãos. A porta não registra nada: ela só abre. Para controlar, você troca por uma porta com trava, câmera e catraca — mais trabalho, mais controle.

O bind:value é a porta de duas folhas. Ele deixa o campo escrever no estado sem passar por nenhuma decisão sua. Isso é exatamente o que você quer quando o valor pode ser guardado como veio: um nome, uma observação, uma quantidade simples. E é exatamente o que você não quer quando o valor precisa de formato, de validação ou de conversão antes de entrar.

A alternativa não é abolir o binding; é usá-lo com critério. O caminho longo — value={x} mais oninput={guardar} — coloca a decisão no meio do caminho. O campo mostra o estado, o handler decide o que fazer com o texto digitado e só depois o estado muda. O custo é mais código; o ganho é controle.

Repare na quinta linha: para valor calculado, nem atalho nem caminho longo. O total não é digitado; ele vem de uma conta. O erro comum é criar um estado para o total e esquecer de atualizá-lo quando o preço muda. A solução é $derived, que recalcula sozinho.

3. O caminho de ida e volta, escrito à mão

Para comparar, comece com o equivalente exato do bind:value sem o atalho. O campo recebe o estado e escuta a digitação; o handler lê o campo e grava.

<script>
  let nome = $state('Ana');

  function guardar(evento) {
    nome = evento.target.value.trim();
  }
</script>

<input value={nome} oninput={guardar}>
<p>Olá, {nome}</p>
<input value="Ana"/> <p>Olá, Ana</p>
value={nome}
a ida: o estado escreve no campo. Sem isso, o campo não acompanha mudanças feitas por código.
oninput={guardar}
a volta: cada tecla chama o handler. O nome do evento é o mesmo que você viu na aula de eventos.
evento.target.value
o texto cru do campo, do jeito que a pessoa digitou, com espaços e tudo.
.trim()
a decisão que o bind não toma: cortar os espaços das pontas antes de guardar.

Esse exemplo já mostra a diferença. O bind:value guardaria " Ana " com os espaços; o caminho longo guarda "Ana". Se a Ana digitar o nome com espaço no fim e o programa comparar com o cadastro, a comparação falha por causa de um caractere invisível. Você não vê o problema na tela — o espaço não aparece —, mas o banco de dados vê.

Existe um detalhe de comportamento que muita gente esquece: quando o handler grava um valor diferente do que está no campo, o campo é reescrito. Se você digitar ana e o handler guardar Ana, o cursor pode pular para o fim do texto. Em campos de formatação avançada, isso incomoda; para cortar espaços nas pontas, quase nunca. Guarde a informação para o dia em que o cursor começar a pular.

4. Quando o valor precisa de formato

Telefone, CPF, código de barras: campos que aceitam apenas dígitos. O bind:value puro aceita letras, símbolos e o que a pessoa quiser. O handler resolve em uma linha.

<script>
  let telefone = $state('');

  function guardar(evento) {
    telefone = evento.target.value.replace(/\D/g, '');
  }
</script>

<input value={telefone} oninput={guardar}>
<p>Telefone: {telefone}</p>
<input value=""/> <p>Telefone: </p>

O replace(/\D/g, '') troca tudo o que não é dígito por nada. A barra invertida maiúscula \D significa "não é dígito"; o g significa "todas as ocorrências", não só a primeira. O resultado é uma string só com números. No terminal, a mesma conta aparece sem Svelte nenhum:

ana@notebook:~/loja$ node -e "console.log('abc123'.replace(/\D/g, ''))"
123

Com o handler no lugar, digitar abc123 guarda "123" e o campo mostra 123 na hora. A pessoa vê o filtro funcionando e entende o formato esperado sem precisar de mensagem de erro. É uma validação silenciosa, e das mais eficazes.

O build do projeto com esse handler fica assim. O número de módulos não muda; o tamanho cresce um pouco por causa da função e da expressão regular:

Vale comparar com a aula de bind:value: o componente de lá tinha um binding puro e pesava quarenta kilobytes; este tem uma regra e pesa trinta e sete, porque tem menos campos. O tamanho não mede a qualidade da decisão. O que mede é o comportamento quando alguém digita algo inesperado.

Uma observação sobre expressões regulares, que assustam no começo: /\D/g é curto, mas tem duas partes. O D maiúsculo é o complemento de d, que significa dígito; o g manda trocar todas as ocorrências. Existem dezenas de letras com significados parecidos, e você não precisa decorar todas hoje. Precisa saber que dá para filtrar texto e onde procurar quando precisar.

Missão: o campo guarda tudo o que a pessoa digita. Faça o handler descartar o que não for dígito, para que digitar abc123 mostre Só números: 123.

<script>
  let telefone = $state('');
</script>

<p>Só números: {telefone}</p>
<input bind:value={telefone}>
<script>
  let telefone = $state('');

  function guardar(evento) {
    telefone = evento.target.value.replace(/\D/g, '');
  }
</script>

<p>Só números: {telefone}</p>
<input value={telefone} oninput={guardar}>

A solução troca bind:value por value mais oninput. Não é mais difícil; é mais explícito. Quem lê o arquivo vê que existe uma decisão entre a tecla e o estado. Essa visibilidade é o argumento principal a favor do caminho longo quando há regra.

5. Quando o valor precisa de validação

Validar não é só recusar no fim: é impedir que o estado receba um valor que não serve. O componente abaixo guarda um nome e só aceita o envio se houver algo de verdade no campo.

<script>
  let nome = $state('');
  let mensagem = $state('');

  function salvar() {
    if (nome.trim() === '') {
      mensagem = 'Não salvo: campo vazio';
      return;
    }
    mensagem = 'Salvo: ' + nome;
  }
</script>

<p>{mensagem}</p>
<input bind:value={nome}>
<button type="button" onclick={salvar}>salvar</button>
<p></p> <input value=""/> <button type="button">salvar</button>

Aqui o bind continua, porque o valor pode ser guardado como veio. A validação acontece na hora de salvar, não na digitação. Essa combinação é a mais comum em formulários: binding para os campos, validação na ação. O que muda em relação ao uso ingênuo é que a função decide antes de aceitar.

Quando a validação precisa acontecer a cada tecla — senha com regra de tamanho, por exemplo —, o caminho longo volta a ser melhor. Você lê o campo, compara, e grava um estado de erro junto com o texto. O campo passa a mostrar uma mensagem embaixo enquanto a pessoa digita. O custo é mais código e mais estado; o ganho é feedback imediato.

Missão: o botão salva um nome vazio. Faça a função recusar o envio quando não houver nome e mostrar Não salvo: campo vazio.

<script>
  let nome = $state('');
  let mensagem = $state('');

  function salvar() {
    mensagem = 'Salvo: ' + nome;
  }
</script>

<p>{mensagem}</p>
<input bind:value={nome}>
<button type="button" onclick={salvar}>salvar</button>
<script>
  let nome = $state('');
  let mensagem = $state('');

  function salvar() {
    if (nome.trim() === '') {
      mensagem = 'Não salvo: campo vazio';
      return;
    }
    mensagem = 'Salvo: ' + nome;
  }
</script>

<p>{mensagem}</p>
<input bind:value={nome}>
<button type="button" onclick={salvar}>salvar</button>

O ponto pedagógico aqui é que bind e validação não são inimigos. O problema não é o binding em si; é usar o binding quando existe uma regra que precisa ser aplicada antes de guardar. Se a regra é aplicada depois, no envio, o binding continua sendo a ferramenta certa.

6. Valores calculados não se digitam

O total da compra é o exemplo perfeito de valor que não deve ter bind. Ele não é digitado: é a quantidade multiplicada pelo preço. Se você criar um estado para o total, precisa lembrar de atualizá-lo em todo lugar que muda a quantidade ou o preço. Um dia você esquece.

<script>
  let quantidade = $state(2);
  let preco = $state(9.5);
  let total = $derived(quantidade * preco);
</script>

<p>Total: R$ {total.toFixed(2)}</p>
<input type="number" bind:value={quantidade}>
<input type="number" bind:value={preco}>
<p>Total: R$ 19.00</p> <input type="number" value="2"/> <input type="number" value="9.5"/>

O $derived calcula a partir de quantidade e preco e se atualiza sozinho quando qualquer um dos dois muda. Não existe estado separado para o total, e por isso não existe a chance de ele ficar desatualizado. O valor sai do HTML com duas casas porque o toFixed(2) formata na hora de mostrar.

O contraste é instrutivo: usar bind:value no total permitiria que a pessoa digitasse um valor que não corresponde à conta. Mesmo que o binding funcionasse, o estado passaria a ter duas verdades — o preço digitado e o preço calculado — e uma delas estaria errada. Valores calculados não se digitam; eles se derivam.

Missão: o total é um estado separado que ninguém atualiza. Faça ele acompanhar o preço, de modo que digitar 5 no campo mostre Total: 10 (o dobro do preço).

<script>
  let preco = $state(0);
  let total = $state(0);
</script>

<p>Total: {total}</p>
<input id="preco" type="number" bind:value={preco}>
<script>
  let preco = $state(0);
  let total = $derived(preco * 2);
</script>

<p>Total: {total}</p>
<input id="preco" type="number" bind:value={preco}>

Note que a solução mantém o binding no preço: o preço é digitado, o total é calculado. Cada valor tem o seu papel. O erro não era o binding; era tratar como digitável um valor que só podia ser calculado.

7. bind em componente: $bindable

Quando o campo está dentro de outro componente, o binding atravessa a fronteira. Para isso, o componente filho precisa declarar que aquela propriedade aceita receber valor de volta. A marca é a runa $bindable.

<script>
  let { valor = $bindable(0) } = $props();
</script>

<input type="number" bind:value={valor}>
<input type="number" value="0"/>

Do lado de quem usa, a chamada é <Campo bind:valor={quantidade} />. O valor digitado dentro do filho volta para a variável do pai. Sem $bindable, a ligação não funciona: o filho recebe uma cópia do valor e o que ele escrever não volta para o pai. É a mesma ideia do bind:value, agora entre dois arquivos.

O custo é de acoplamento: o filho passa a poder escrever no estado do pai. Em componentes pequenos de formulário, isso é conveniente. Em componentes grandes, é melhor o filho receber o valor e avisar por callback, deixando o pai decidir se aceita. A escolha é a mesma da seção 1: atalho ou controle.

8. O custo escondido do bind

O bind esconde…Consequência
o momento em que o estado mudadepurar exige saber que o campo escreveu
a regra de formataçãoo estado guarda o texto cru
a validaçãovalor inválido entra no estado e precisa ser tratado depois
a conversão de tiponúmero vira string sem aviso em campo de texto
o acoplamento entre componenteso filho escreve no pai sem pedir licença

Nada disso é defeito; é o preço do atalho. O programador experiente não evita o bind: ele sabe quando o preço vale a pena. O iniciante tende a usar sempre o atalho e depois passa horas procurando por que o estado tem um valor que ninguém digitou. Saber que o campo escreve sozinho encurta a busca.

Existe também o custo de teste. Um componente com bind precisa de um navegador para exercitar a digitação; um componente que recebe o valor e chama uma função pode ser testado chamando a função. Quanto mais regra no handler, mais fácil testar sem interface. A aula de testes do Nível 2 volta a esse ponto.

Para fechar a decisão, três perguntas rápidas antes de escrever bind:value. O valor pode ser guardado exatamente como a pessoa digitou? Nenhuma regra precisa rodar antes? Ninguém mais precisa saber que ele mudou? Se as três respostas forem sim, o atalho é a escolha certa. Se qualquer uma for não, escreva o caminho longo e deixe a decisão visível.

9. Quando dá errado

Erro 1 — $bindable fora de $props

A runa só existe dentro da desestruturação das propriedades. Solta no script, não tem a que se referir.

<script>
  let valor = $bindable(0);
</script>

<p>{valor}</p>
Erro de compilação (linha 2, coluna 14): `$bindable()` can only be used inside a `$props()` declaration

A mensagem diz "só pode ser usada dentro de uma declaração $props()". A forma certa é let { valor = $bindable(0) } = $props(). O valor padrão entre parênteses é opcional; sem ele, a propriedade começa indefinida.

Erro 2 — runa sem parênteses

Toda runa é uma chamada. Escrever o nome sem os parênteses faz o compilador achar que você quis dizer outra coisa.

<script>
  let { nome = $bindable } = $props();
</script>

<p>{nome}</p>
Erro de compilação (linha 2, coluna 15): Cannot use rune without parentheses

"Não posso usar a runa sem parênteses". A correção é $bindable() ou $bindable(valorPadrao). O mesmo vale para $state, $derived, $effect e $props.

Erro 3 — bind numa expressão

O lado direito do binding precisa ser um lugar onde se grava. Uma transformação como nome.trim() produz um valor novo, sem endereço.

<script>
  let nome = $state(' Ana ');
</script>

<input bind:value={nome.trim()}>
Erro de compilação (linha 5, coluna 7): Can only bind to an Identifier or MemberExpression or a `{get, set}` pair

É o caso em que a pessoa quer formatar e tenta fazer isso no binding. Formatar é trabalho de handler: use value={nome} com oninput, como na seção 4. O compilador está dizendo que não existe endereço para gravar o texto que a pessoa digitar.

Resumo
