SvelteKit · +server.js

A Ana tem um balcão para clientes e uma janela para entregadores. O entregador não quer ver o cardápio na parede: ele quer uma lista com número de pedido e endereço, entregue na mão, em formato combinado. No SvelteKit essa janela é o arquivo +server.js: um endereço que responde dados, não uma página. É o mesmo servidor, outra porta de entrada — e o formato combinado se chama JSON.

Você vai aprender
  • O que é um endpoint e por que ele não tem HTML.
  • Como criar um endereço com +server.js e uma função GET.
  • Como responder JSON com json() e escolher o status.
  • Como ler o corpo de um POST com request.json().
  • Como recusar um pedido inválido com error(400, …).
  • O que é o 405 e o cabeçalho allow que o SvelteKit escreve sozinho.
  • Quem chama um endpoint: o load, um formulário e outro programa.
  • Como ler as respostas com curl -i e conferir status e cabeçalhos.
  • Três erros reais de endpoint, copiados do terminal.
  • Quando usar json(), text() ou um Response na mão.

1. A ideia: uma janela que entrega lista, não vitrine

Página é vitrine: tem título, cor, imagem e é feita para olho humano. Endpoint é janela de serviço: entrega dado cru para quem sabe o que fazer com ele. O mesmo pedido de "lista de pedidos" pode sair como página colorida em /painel e como lista em JSON em /api/pedidos. São duas portas do mesmo prédio.

Quem usa a janela? Outro programa. Pode ser o seu próprio load buscando dados, pode ser o JavaScript do navegador atualizando uma lista sem recarregar, pode ser o aplicativo do entregador no celular. Nenhum deles quer o seu HTML; todos querem os dados. Por isso o endpoint responde com um tipo de conteúdo declarado: application/json.

JSON é só texto com regras: chaves entre aspas, valores que podem ser texto, número, verdadeiro/falso, nulo, lista ou outro objeto. Ele é a língua franca porque qualquer linguagem lê e escreve. Quando o seu load faz await resposta.json(), está transformando esse texto de volta em objeto JavaScript.

2. O primeiro endpoint: a lista de pedidos

O arquivo se chama +server.js e mora numa pasta de rota, igual ao +page.svelte. A diferença é que ele exporta funções com nome de método HTTP: GET para buscar, POST para criar, e assim por diante.

import { json, error } from '@sveltejs/kit';
import { listar, criar } from '#lib/pedidos.js';

export function GET({ url }) {
	const sabor = url.searchParams.get('sabor');
	const lista = sabor ? listar().filter((p) => p.sabor === sabor) : listar();
	return json(lista);
}

export async function POST({ request }) {
	const corpo = await request.json();

	if (!corpo.cliente) {
		error(400, 'todo pedido precisa de um cliente');
	}

	const pedido = criar(corpo.cliente, corpo.sabor ?? 'queijo');
	return json(pedido, { status: 201 });
}
export function GET
o método. O nome é maiúsculo e reservado: GET, POST, PUT, PATCH, DELETE. Um get minúsculo é só uma função que ninguém chama.
({ url })
o evento, igual ao do load: traz url, params, request, cookies e locals.
return json(lista)
monta a resposta com o cabeçalho content-type: application/json e status 200. Sem o json(), o SvelteKit recusa a resposta.
await request.json()
lê o corpo da requisição e transforma o texto em objeto. Só faz sentido em POST, PUT e PATCH.
error(400, '…')
interrompe e responde com status 400 e a mensagem. O texto vai no corpo, no formato de erro do SvelteKit.
{ status: 201 }
o segundo argumento do json(): cabeçalhos e status. 201 é "criei algo".

Repare no que não existe: nenhum HTML, nenhum componente, nenhum export let. Um endpoint é uma função que recebe requisição e devolve resposta. Se você precisar de página, o arquivo é outro; e os dois no mesmo endereço não convivem.

3. A saída real: status, cabeçalho e corpo

O curl com -i mostra os cabeçalhos junto com o corpo. É a forma mais direta de ver o que o endpoint respondeu sem depender de navegador:

ana@notebook:~/loja$ curl -s -i localhost:5173/api/pedidos | head -4
HTTP/1.1 200 OK
Vary: Origin
content-length: 114
content-type: application/json

Quatro linhas, três informações. 200 OK é o status de sucesso. content-type: application/json avisa o cliente como interpretar o corpo. content-length: 114 é o tamanho em bytes — se o seu número for diferente, o conteúdo é diferente, e isso já é uma pista de conferência.

ana@notebook:~/loja$ curl -s localhost:5173/api/pedidos
[{"id":1,"cliente":"Ana","sabor":"frango","pronto":true},{"id":2,"cliente":"Bia","sabor":"queijo","pronto":false}]

O corpo é uma lista de objetos. Quem consome decide o que fazer: o aplicativo do entregador desenha cartões, o seu load passa a lista para o componente, um script de relatório soma totais. O endpoint não tem opinião sobre a aparência.

Missão: a resposta do servidor tem o status dentro do campo status. Mostre 201 Criado — o código e a palavra.

<script>
	// no projeto, este objeto vem da resposta do endpoint
	const resposta = { status: 201, corpo: { id: 3, cliente: 'Dora' } };
</script>

<p>{resposta.codigo} Criado</p>
<script>
	// no projeto, este objeto vem da resposta do endpoint
	const resposta = { status: 201, corpo: { id: 3, cliente: 'Dora' } };
</script>

<p>{resposta.status} Criado</p>

Status é número, mas quem lê prefere palavra. A lista curta que vale decorar: 200 deu certo, 201 criei algo, 400 o pedido está malformado, 401 falta identificação, 404 não existe, 405 esse método não é aceito aqui, 500 o servidor quebrou. O número vai no cabeçalho; a explicação vai no corpo.

4. Criar com POST e recusar com error()

Buscar é fácil porque não muda nada. Criar exige ler o que chegou, conferir e responder com o resultado. O POST abaixo lê o corpo, testa o campo obrigatório e devolve o pedido criado com status 201:

ana@notebook:~/loja$ curl -s -X POST -H 'content-type: application/json' -d '{"cliente":"Dora","sabor":"queijo"}' localhost:5173/api/pedidos -w '\n%{http_code}\n'
{"id":3,"cliente":"Dora","sabor":"queijo","pronto":false}
201

O -X POST escolhe o método, o -H 'content-type: application/json' avisa o formato do corpo e o -d manda o corpo. Sem o cabeçalho, o servidor não tem como saber que aquele texto é JSON; com ele, o request.json() funciona. O -w '\n%{http_code}\n' imprime o status no fim, que é o que o corpo não mostra.

Agora o mesmo endereço com um corpo vazio. A validação entra em ação e o error() responde 400 com a mensagem:

ana@notebook:~/loja$ curl -s -X POST -H 'content-type: application/json' -d '{}' localhost:5173/api/pedidos -w '\n%{http_code}\n'
{"status":400,"message":"todo pedido precisa de um cliente"}
400

Aquele {"status":400,"message":"…"} é o formato de erro do SvelteKit: o número que você passou e o texto que você escreveu. Não é o formato que você escolheu — é o que o error() monta. Se você quiser um formato próprio, monte a resposta com json(..., { status: 400 }) em vez de error().

Mensagem de erro também é interface

Quem lê o corpo de um 400 pode ser uma pessoa ou outro programa. Escreva a mensagem pensando nos dois: "todo pedido precisa de um cliente" diz o que fazer; "erro de validação" não diz nada. Não coloque caminho de arquivo, consulta SQL nem nome de tabela — isso é presente para quem procura falhas.

5. Os métodos que você não escreveu

Se o endpoint só tem GET e POST, o que acontece quando alguém manda PUT? O SvelteKit responde sozinho, com 405 e a lista do que é aceito. Você não escreve esse código; ele existe porque você não escreveu a função.

ana@notebook:~/loja$ curl -s -X PUT localhost:5173/api/pedidos
PUT method not allowed
ana@notebook:~/loja$ curl -s -X DELETE -i localhost:5173/api/pedidos | head -4
HTTP/1.1 405 Method Not Allowed
Vary: Origin
allow: GET, POST, HEAD
content-length: 25

A linha allow: GET, POST, HEAD é o recado completo: "aqui aceito estes". O HEAD aparece porque é o GET sem corpo — o SvelteKit responde de graça. Um cliente bem feito lê esse cabeçalho e sabe o que pode tentar antes de tentar.

Missão: o servidor só aceita GET e POST. Faça o botão PUT mostrar 405 PUT method not allowed.

<script>
	let resposta = $state('');

	function pedir(metodo) {
		resposta = metodo === 'put' ? '405 PUT method not allowed' : '200 OK';
	}
</script>

<button id="put" onclick={() => pedir('PUT')}>PUT</button>
<p>{resposta}</p>

A comparação com 'put' minúsculo passa despercebida porque não gera erro: ela simplesmente nunca é verdadeira. É o mesmo padrão do campo com nome trocado — JavaScript não sabe qual era a sua intenção. Métodos HTTP são maiúsculos por convenção forte; trate o texto como chave exata.

6. Quem chama o endpoint

O endpoint que você acabou de escrever tem três clientes possíveis, e cada um precisa de uma coisa diferente do cabeçalho. Vale conhecer os três porque o mesmo erro aparece nos três: esquecer o content-type no POST.

O primeiro é o load, que você já conhece. Ele usa o fetch do evento e precisa esperar a resposta, senão recebe uma promessa:

export async function load({ fetch }) {
	const resposta = await fetch('/api/pedidos');
	const pedidos = await resposta.json();

	return { pedidos };
}

O segundo é o JavaScript do navegador, num onclick. É o mesmo fetch, mas global, e o cabeçalho precisa ser escrito à mão:

<script>
	let cliente = $state('');
	let aviso = $state('');

	async function enviar() {
		const resposta = await fetch('/api/pedidos', {
			method: 'POST',
			headers: { 'content-type': 'application/json' },
			body: JSON.stringify({ cliente, sabor: 'queijo' })
		});

		const corpo = await resposta.json();
		aviso = resposta.ok ? 'pedido ' + corpo.id + ' criado' : corpo.message;
	}
</script>

<input bind:value={cliente} placeholder="quem pediu" />
<button onclick={enviar}>enviar</button>
<p>{aviso}</p>

O terceiro cliente é qualquer programa de fora: o aplicativo do entregador, um script de planilha, o curl do seu terminal. Para esse, não existe SvelteKit nem fetch especial: existe HTTP puro, com método, cabeçalho e corpo. É por isso que o endpoint é a porta mais universal do projeto.

Missão: o campo preenche a variável cliente, mas o aviso mostra outra coisa. Digite Dora e faça aparecer recebido: Dora.

<script>
	let cliente = $state('Dora');
	let corpo = { nome: 'Bia' };
</script>

<input placeholder="quem pediu" bind:value={cliente} />
<p>recebido: {corpo.nome}</p>
<script>
	let cliente = $state('');
</script>

<input placeholder="quem pediu" bind:value={cliente} />
<p>recebido: {cliente}</p>

Aqui o defeito é de origem: o componente mostra o objeto fixo em vez da variável que o campo atualiza. Em endpoint de verdade, o equivalente é montar o body com um valor que não veio do formulário. A tela parece funcionar — até alguém digitar algo diferente do que estava escrito no código.

7. json(), text() ou Response

O SvelteKit dá três caminhos para responder. O mais usado é json(), que serializa o objeto e ajusta o cabeçalho. Para texto puro — um arquivo .txt, um CSV, um XML — existe text(). E para tudo o que os dois não cobrem, existe o Response padrão da plataforma, com o corpo e os cabeçalhos que você quiser.

import { json, text } from '@sveltejs/kit';

export function GET({ url }) {
	if (url.searchParams.get('formato') === 'texto') {
		return text('versão 3.4.1');
	}

	return json({ versao: '3.4.1' }, { headers: { 'cache-control': 'max-age=60' } });
}

O cache-control é um exemplo do que só se faz com cabeçalho: dizer ao cliente por quanto tempo ele pode guardar a resposta. Dado que muda a cada segundo não deve ter cache; dado que muda uma vez por dia economiza muito com max-age.

Não devolva objeto puro

É tentador escrever return { ola: 'Ana' } e esperar que o SvelteKit "entenda". Ele não entende: a função precisa devolver um Response, e é isso que json() e text() fazem por você. O erro aparece no terminal como endpoint_invalid_response — um dos cenários abaixo.

8. Quando dá errado

Erro 1 — devolver um objeto em vez de uma resposta

A função devolveu dado solto. O SvelteKit espera um Response e recusa, dizendo qual rota e o que faltou.

export function GET() {
	return { ola: 'Ana' };
}
SvelteKit error: endpoint_invalid_response
Invalid response from route `/api/pedidos`: handler should return a `Response` object
https://svelte.dev/e/kit/endpoint_invalid_response
500 GET /api/pedidos

A tradução é direta: "o manipulador deve devolver um Response". Trocar por return json({ ola: 'Ana' }) resolve. O endereço na mensagem mostra exatamente qual rota falhou — útil quando há dez endpoints no projeto.

Erro 2 — corpo que não é JSON

O cliente mandou dados de formulário, e o servidor tentou ler como JSON. O request.json() estoura com o texto recebido.

import { json } from '@sveltejs/kit';

export async function POST({ request }) {
	const corpo = await request.json();
	return json(corpo);
}
ana@notebook:~/loja$ curl -s -X POST -H 'content-type: application/x-www-form-urlencoded' -d 'cliente=Dora' localhost:5173/api/pedidos
{"status":500,"message":"Internal Error"}

No terminal do servidor, a linha que explica:

SyntaxError: Unexpected token 'c', "cliente=Dora" is not valid JSON
    at async POST (src/routes/api/pedidos/+server.js:4:16)
500 POST /api/pedidos

O 'c' inesperado é a primeira letra de cliente. Duas correções possíveis: exigir JSON do cliente (content-type: application/json) ou ler com request.formData() quando o corpo é de formulário. Escolher errado aqui é a causa mais comum de "funciona no meu teste, quebra no site".

Erro 3 — método que não existe na rota

Não é falha de código: é o SvelteKit protegendo o endereço. Quem chamou com PUT recebe 405 e a lista do que pode.

export function GET({ url }) {
	const sabor = url.searchParams.get('sabor');
	const lista = sabor ? listar().filter((p) => p.sabor === sabor) : listar();
	return json(lista);
}

export async function POST({ request }) {
	const corpo = await request.json();
	if (!corpo.cliente) {
		error(400, 'todo pedido precisa de um cliente');
	}
	return json(criar(corpo.cliente, corpo.sabor ?? 'queijo'), { status: 201 });
}
ana@notebook:~/loja$ curl -s -X PUT localhost:5173/api/pedidos
PUT method not allowed
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X PUT localhost:5173/api/pedidos
405

O corpo muda conforme o cliente: com accept: text/html vem uma página de erro; sem ele, vem o texto curto. O status é sempre 405. Se você queria aceitar PUT, falta escrever a função export function PUT.

9. Conferindo um endpoint sem navegador

Endpoint é a parte do projeto mais fácil de conferir, porque ele não depende de tela. Um roteiro de quatro comandos cobre quase tudo: buscar, criar, criar inválido e método errado. Se os quatro status estiverem certos, o caminho está certo.

ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' localhost:5173/api/pedidos
200
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'content-type: application/json' -d '{"cliente":"Dora"}' localhost:5173/api/pedidos
201
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'content-type: application/json' -d '{}' localhost:5173/api/pedidos
400
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X PUT localhost:5173/api/pedidos
405

O -o /dev/null joga o corpo fora e deixa só o status. É o que você quer quando a pergunta é "o código está certo?" e não "a mensagem está boa?". Quando a pergunta for a mensagem, tire o -o /dev/null e leia o corpo.

<script>
	const pedidos = [
		{ id: 1, cliente: 'Ana', pronto: true },
		{ id: 2, cliente: 'Bia', pronto: false }
	];
</script>

<p>{pedidos.length} pedido(s)</p>
<ul>
	{#each pedidos as p}
		<li>{p.cliente}: {p.pronto ? 'pronto' : 'na fila'}</li>
	{/each}
</ul>
<p>2 pedido(s)</p> <ul><li>Ana: pronto</li><li>Bia: na fila</li></ul>

O componente acima é o outro lado do endpoint: recebe a lista e desenha. A saída é a do compilador, com os dados fixos no script. No projeto, a lista chega do fetch — o desenho é o mesmo.

Resumo

  • +server.js cria um endereço que responde dados, não uma página.
  • As funções exportadas têm nome de método HTTP, em maiúsculas: GET, POST, PUT, PATCH, DELETE.
  • A resposta tem de ser um Response: use json() ou text(), ou monte o Response à mão.
  • json(dado, { status }) define o corpo e o código; o cabeçalho content-type vem junto.
  • request.json() lê corpo JSON; request.formData() lê corpo de formulário.
  • error(400, '…') responde no formato {"status":400,"message":"…"}.
  • Método sem função correspondente vira 405 com allow: GET, POST, HEAD — de graça.
  • O mesmo endereço serve ao load, ao fetch do navegador e a qualquer programa de fora.
  • curl -i mostra status e cabeçalhos; -o /dev/null -w '%{http_code}' mostra só o status.
  • Mensagem de erro de endpoint é interface: diga o que fazer, sem vazar caminho, SQL ou nome de tabela.
