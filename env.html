SvelteKit · $env

A Ana agora tem um banco de dados na padaria: é lá que ficam os pedidos, os preços e o nome dos clientes. O programa precisa de duas informações que não moram no código — o endereço do banco (com usuário e senha) e o nome que aparece na vitrine. Uma dessas informações é um segredo: se ela chegar ao navegador de qualquer visitante, qualquer pessoa lê a senha. A outra é o contrário: precisa ir para a tela de todo mundo. Esta aula mostra como o SvelteKit separa essas duas caixas, e o que o compilador faz quando você troca uma pela outra.

Você vai aprender
  • Por que senha e nome da loja não podem morar no mesmo lugar.
  • O que é variável de ambiente e por que ela fica fora do código.
  • Como declarar variáveis no arquivo src/env.js do SvelteKit 3.
  • A diferença entre $app/env/private e $app/env/public.
  • O que static: true faz com o valor na hora do build.
  • Como validar uma variável com schema e o que acontece quando falta.
  • O papel do arquivo .env e por que ele fica no .gitignore.
  • Os erros reais: variável sem declaração, valor faltando e importação no lugar errado.
  • O nome antigo $env/static/private e o aviso de que ele está obsoleto.

1. A ideia: a chave da despensa e o cartaz da porta

Na padaria da Ana existem duas informações que parecem do mesmo tipo, mas não são. A primeira é a chave da despensa: só a Ana e o gerente têm. A segunda é o nome da loja na fachada: todo mundo que passa na rua lê. Se a Ana colar a chave na porta, o estoque inteiro fica exposto. Se ela esconder o nome da loja, ninguém entra.

Um programa que conversa com banco de dados tem exatamente essas duas categorias. O endereço do banco, com usuário e senha, é a chave: o servidor usa, o navegador não pode nem saber que existe. O nome da padaria, o telefone, o horário de funcionamento são o cartaz: precisam chegar ao navegador para aparecer na tela.

A analogia vale para o vocabulário. Variável de ambiente é um valor que mora fora do código, no ambiente onde o programa roda — a gaveta da Ana, não o caderno de receitas. O mesmo código roda na máquina dela e no servidor de produção, cada um com a sua gaveta. Por isso o valor não pode estar escrito no arquivo: se estivesse, você precisaria de dois códigos diferentes.

Na padariaNo SvelteKit
A chave da despensa, só com a equipevariável privada, lida só no servidor
O nome pintado na fachadavariável pública, pode ir ao navegador
A gaveta onde a chave fica guardadao arquivo .env, fora do Git
A lista do que existe na despensao arquivo src/env.js
Conferir se a chave abre a porta antes de sairo schema que valida o valor

Repare que a lista e a gaveta são coisas diferentes. O src/env.js diz quais variáveis existem e qual é o papel de cada uma; o .env guarda os valores daquela máquina. Confundir os dois é o erro número um de quem começa, e é a origem de quase todos os cenários desta aula.

2. Duas caixas: $app/env/private e $app/env/public

No SvelteKit atual existem dois módulos para ler variáveis de ambiente, e o nome de cada um já diz quem pode importar:

  • $app/env/private — só o código que roda no servidor. Um +page.server.js, um +server.js, o hooks.server.js.
  • $app/env/public — o servidor e também o navegador. É daqui que sai o que aparece na tela.

A regra é aplicada pelo próprio build, não pela sua disciplina. Se um componente .svelte — que roda nos dois lados — importar do módulo privado, o build para com uma mensagem. Você vai ver essa mensagem na seção de erros, e ela é bem direta: o SvelteKit não deixa o segredo sair do servidor.

Existe ainda um terceiro módulo, $app/env, sem sufixo, que responde a perguntas sobre o ambiente: browser (estou no navegador?), dev (é o servidor de desenvolvimento?), building (estou sendo compilado?) e version (a versão publicada). Ele não traz valores seus; serve para o código saber onde está rodando.

O nome antigo ainda funciona, com aviso

Quem aprendeu SvelteKit 2 conhece $env/static/private e $env/dynamic/private. No SvelteKit 3 eles continuam existindo como atalhos para os módulos novos, mas o servidor de desenvolvimento imprime um aviso de obsolescência. Nesta aula você usa os nomes atuais; o antigo aparece só para você reconhecer quando encontrar em tutorial velho.

3. src/env.js: onde as variáveis são declaradas

No SvelteKit 3 as variáveis não aparecem por mágica: você declara cada uma num arquivo chamado src/env.js, ao lado da pasta routes. É uma lista de intenções. Para cada nome, você diz se ele pode ir ao navegador, se o valor é fixado no build e como ele deve ser validado.

import { defineEnvVars } from '@sveltejs/kit/env';

export const variables = defineEnvVars({
	DATABASE_URL: {
		description: 'Endereço do banco da padaria'
	},
	PUBLIC_LOJA_NOME: {
		public: true,
		static: true,
		description: 'Nome que aparece no rodapé'
	}
});
import { defineEnvVars }
a função que dá tipo e validação à lista. Ela vem do pacote @sveltejs/kit/env, que já está instalado no projeto.
export const variables
o nome é obrigatório: o SvelteKit procura exatamente este export no arquivo. Sem ele, o build reclama que as variáveis não existem.
DATABASE_URL: { }
uma variável privada, porque public não foi escrito. O padrão é fechado — quem esquece a opção fica no lado seguro.
public: true
libera a variável para o navegador. Só coloque isso em valor que você mostraria num cartaz na rua.
static: true
congela o valor no momento do build. O valor entra no arquivo final como texto; trocar a variável depois exige compilar de novo.
description
um lembrete para quem lê o código depois. Não aparece na tela; serve de documentação.

O arquivo tem uma consequência prática que agrada: se você digitar o nome de uma variável que não está nessa lista, o build falha com uma mensagem clara. O compilador conhece a lista inteira, então o erro aparece antes de a página abrir — não depois, em produção, com o cliente reclamando.

4. O arquivo .env e o que não vai para o Git

A lista diz que DATABASE_URL existe. O valor dela mora no arquivo .env, na raiz do projeto:

DATABASE_URL="postgres://ana:segredo@localhost:5432/padaria"
PUBLIC_LOJA_NOME="Padaria da Ana"

Cada linha é NOME=valor. As aspas não fazem parte do valor: servem para o arquivo aceitar espaços e caracteres especiais, como os dois pontos e a barra do endereço do banco.

O projeto criado pelo comando sv create já vem com o .env dentro do .gitignore. Isso é intencional: o Git guarda histórico para sempre, e uma senha que entra num commit nunca sai de verdade — mesmo que você apague o arquivo no commit seguinte. O que se versiona é um exemplo, o .env.example, com nomes e valores falsos, para a próxima pessoa saber o que precisa preencher.

Um .env por máquina

A máquina da Ana usa o banco local; o servidor de produção usa outro endereço. Se os dois usassem o mesmo arquivo, um sobrescreveria o outro. O .env é do ambiente, não do projeto — é por isso que ele fica fora do repositório.

5. Lendo no servidor

Com a variável declarada e o valor no .env, a leitura é uma importação comum. O arquivo abaixo roda só no servidor, então pode importar do módulo privado:

import { DATABASE_URL } from '$app/env/private';
import { PUBLIC_LOJA_NOME } from '$app/env/public';

export function load() {
	return {
		nome: PUBLIC_LOJA_NOME,
		banco: DATABASE_URL.replace(/:\/\/.*@/, '://***@')
	};
}

O replace com a expressão regular troca tudo o que está entre :// e @ por três asteriscos. É uma decisão de segurança dentro do código: mesmo que alguém imprima o resultado na tela, a senha não aparece. Guardar o valor completo e mascarar na hora de mostrar é diferente de mandar o valor completo para o navegador e esconder com CSS — a segunda opção deixa a senha no HTML.

A página que recebe esses dados é um componente normal:

<script>
	let { data } = $props();
</script>

<h1>{data.nome}</h1>
<p>Banco: {data.banco}</p>

Com o servidor de desenvolvimento ligado, um pedido de fora mostra o resultado. Este é o terminal da máquina da Ana, copiado de uma execução de verdade:

ana@notebook:~/loja$ curl -s http://localhost:5173/env | grep -o '<h1>[^<]*</h1>\|<p>Banco[^<]*</p>'
<h1>Padaria da Ana</h1>
<p>Banco: postgres://***@localhost:5432/padaria</p>

Duas coisas ficaram de fora do HTML: a senha e o usuário. O que o navegador recebeu foi a versão mascarada, que é o que a tela precisa. O valor verdadeiro existiu só dentro do processo do servidor, durante o load.

6. Caixa 1: só o público vai para o navegador

Antes de voltar ao código do servidor, vale treinar a decisão. A caixa abaixo tem um objeto de configuração completo — nome e endereço do banco — e o manda inteiro para o navegador. A missão é deixar passar só o que é cartaz.

Missão: o objeto paraOCliente está levando o banco junto. Monte esse objeto com apenas o nome da padaria, para o texto virar No navegador: {"nome":"Padaria da Ana"}.

<script>
	const config = {
		nome: 'Padaria da Ana',
		banco: 'postgres://ana:segredo@localhost:5432/padaria'
	};

	let paraOCliente = $state(config);
</script>

<p>No navegador: {JSON.stringify(paraOCliente)}</p>
<script>
	const config = {
		nome: 'Padaria da Ana',
		banco: 'postgres://ana:segredo@localhost:5432/padaria'
	};

	let paraOCliente = $state({ nome: config.nome });
</script>

<p>No navegador: {JSON.stringify(paraOCliente)}</p>

O JSON.stringify transforma o objeto em texto, e é só para você ver o que passou. Numa aplicação de verdade o mesmo cuidado aparece como uma pergunta: este dado precisa existir no navegador? Se a resposta for não, ele nem sai do servidor. Cada campo a mais no navegador é uma informação que qualquer pessoa lê abrindo o inspetor do próprio browser.

7. static: true e o que vai para o navegador

Quando você roda o build, o SvelteKit gera os módulos de ambiente. Vale abrir um deles e ler: é código curto e mostra exatamente o que acontece com cada variável.

ana@notebook:~/loja$ cat .svelte-kit/generated/build/env/config.js
import { variables } from "../../../../src/env.js";
import { validate, handle_issues } from '@sveltejs/kit/internal/env';

const issues = {};

export { variables }

export const dynamic_private_env = {};

export const explicit_public_env = {};

export const rendered_env = {};

explicit_public_env.PUBLIC_LOJA_NOME = "Padaria da Ana";

handle_issues(issues);

export function set_env(env) {
	const issues = {};
	const DATABASE_URL = validate(variables, env.DATABASE_URL, "DATABASE_URL", issues);
	dynamic_private_env.DATABASE_URL = DATABASE_URL;
	handle_issues(issues);
}

Leia com calma: PUBLIC_LOJA_NOME é atribuído ali, com o valor entre aspas, no arquivo gerado. Já DATABASE_URL não tem valor nenhum no arquivo — ele é preenchido pela função set_env, que recebe o ambiente quando o servidor sobe. É a diferença entre o que é congelado e o que é lido na hora.

O módulo público do cliente, por sua vez, é literalmente uma constante:

ana@notebook:~/loja$ cat .svelte-kit/generated/build/env/public/client.js
import { payload } from "../../../../../node_modules/@sveltejs/kit/src/runtime/client/payload.js";
const env = payload.env;

export const PUBLIC_LOJA_NOME = "Padaria da Ana";

Esse arquivo vai para o navegador. O nome da padaria está lá como texto, e isso é o esperado: qualquer visitante pode ler o HTML e achar o nome da loja. A pergunta que você faz antes de marcar public: true é sempre a mesma: eu mostraria este valor para qualquer pessoa na rua?

O módulo privado tem outra forma, e o comentário fica claro quando você vê os dois lado a lado:

ana@notebook:~/loja$ cat .svelte-kit/generated/build/env/private/server.js
import { dynamic_private_env as env } from '../config.js';

export const DATABASE_URL = env.DATABASE_URL;

Ele lê de dynamic_private_env, que só existe no processo do servidor. Nenhum arquivo enviado ao navegador importa esse caminho. A garantia não é uma promessa da documentação: é o grafo de importações do bundle, e o vite-plugin-sveltekit-guard cuida para que ninguém quebre a regra por acidente.

8. Caixa 2: o prefixo que libera

Em projetos SvelteKit 2 a convenção era o prefixo PUBLIC_ no nome da variável. No SvelteKit 3 quem decide é a opção public: true, mas o prefixo continua sendo uma boa convenção: quem lê o nome sabe na hora o que ele é. A caixa abaixo treina a regra com um campo de texto.

Missão: a linha diz que toda variável vai para o navegador. Faça o texto depender do nome: começando com PUBLIC_ mostra pode ir para o navegador; qualquer outro nome mostra fica no servidor. Digite PUBLIC_LOJA_NOME e depois DATABASE_URL.

<script>
	let nome = $state('');
</script>

<input oninput={(e) => (nome = e.currentTarget.value)} placeholder="nome da variável" />
<p>{nome}: vai para o navegador</p>
<script>
	let nome = $state('');
	let podeIr = $derived(nome.startsWith('PUBLIC_'));
</script>

<input oninput={(e) => (nome = e.currentTarget.value)} placeholder="nome da variável" />
<p>{nome}: {podeIr ? 'pode ir para o navegador' : 'fica no servidor'}</p>

$derived calcula um valor a partir de outro: quando nome muda, podeIr é recalculado antes de a tela ser desenhada. startsWith é uma função de texto que devolve true ou false. O resto é o mesmo condicional de sempre.

9. Validação: o schema que segura o build

Declarar a variável resolve o "existe ou não existe". Falta o "está no formato certo". Para isso o defineEnvVars aceita um schema: uma função que recebe o texto cru e devolve o valor pronto, ou lança um erro explicando o problema.

import { defineEnvVars } from '@sveltejs/kit/env';

export const variables = defineEnvVars({
	DATABASE_URL: {
		schema: (valor) => {
			if (!valor?.startsWith('postgres://')) {
				throw new Error('DATABASE_URL precisa começar com postgres://');
			}
			return valor;
		}
	},
	TAXA_ENTREGA: {
		schema: (valor) => {
			if (valor === undefined) return 5;
			const numero = Number(valor);
			if (Number.isNaN(numero)) throw new Error('TAXA_ENTREGA precisa ser número');
			return numero;
		}
	}
});

Note a diferença entre as duas funções. A primeira exige o valor: se ele falta, o ?.startsWith devolve undefined e o erro é lançado. A segunda aceita a falta e devolve um padrão — cinco reais de taxa. Esse é o jeito de declarar uma variável opcional: não é deixando o campo vazio, é escrevendo a função que aceita vazio.

O valor de retorno não precisa ser texto. TAXA_ENTREGA devolve número, então o resto do código soma em vez de concatenar. Quem lê a variável nunca vê texto cru: vê o resultado da validação. Isso concentra a conversão num lugar só, em vez de espalhar Number() por dez arquivos.

10. Caixa 3: a senha na tela

Mesmo com todo o cuidado do lado do servidor, alguém pode imprimir o endereço completo do banco numa página de diagnóstico. Um jeito de impedir isso é receber a configuração por propriedade e mascarar dentro do componente:

<script>
	let {
		nome = 'Padaria da Ana',
		banco = 'postgres://ana:segredo@localhost:5432/padaria'
	} = $props();

	const visivel = $derived(banco.replace(/:\/\/.*@/, '://***@'));
</script>

<p>{nome} · {visivel}</p>
<p>Padaria da Ana · postgres://***@localhost:5432/padaria</p>

Aquele $derived importa: sem ele, o valor seria calculado uma vez só, com o primeiro banco recebido, e o compilador avisaria que a referência captura só o valor inicial. Com a runa, o texto acompanha qualquer troca de propriedade. A senha sai mascarada mesmo que o componente receba o endereço completo.

A caixa abaixo faz o caminho oposto de propósito: imprime o endereço cru. A missão é mascarar antes de mostrar.

Missão: a tela mostra o endereço do banco com usuário e senha. Troque a senha (e o usuário) por três asteriscos, mantendo o resto igual: Banco: postgres://***@localhost:5432/padaria.

<script>
	const banco = 'postgres://ana:segredo@localhost:5432/padaria';
	let tela = $state(banco);
</script>

<p>Banco: {tela}</p>
<script>
	const banco = 'postgres://ana:segredo@localhost:5432/padaria';
	let tela = $state(banco.replace(/:\/\/.*@/, '://***@'));
</script>

<p>Banco: {tela}</p>

A expressão regular /:\/\/.*@/ procura dois pontos, duas barras, qualquer quantidade de caracteres e um arroba. O .* é guloso: pega até o último arroba da linha, o que funciona porque o endereço tem um só. Trocar o valor guardado seria errado — o programa precisa do endereço real para conectar. Mascarar é uma decisão sobre o que aparece, não sobre o que existe.

11. Quando dá errado

As três mensagens abaixo saíram do terminal desta máquina, com o SvelteKit 3.4.1 e o Vite 8.4.0. Elas estão copiadas como o build as imprime.

Erro 1 — a variável não foi declarada

Você importa de $env/static/private ou de $app/env/private um nome que não está no src/env.js. O build acusa exportação faltando e mostra o caminho do módulo gerado.

vite v8.4.0 building ssr environment for production...
transforming...
✓ 162 modules transformed.
rendering chunks...
✗ Build failed in 353ms
error during build:
Build failed with 2 errors:

[MISSING_EXPORT] "DATABASE_URL" is not exported by "node_modules/@sveltejs/kit/src/runtime/env/static/private.js".
   ╭─[ src/routes/env/+page.server.js:1:10 ]
   │
 1 │ import { DATABASE_URL } from '$env/static/private';
   │          ──────┬─────  
   │                ╰─────── Missing export
───╯

O trecho Missing export quer dizer "esse nome não existe no módulo". A correção é declarar a variável em src/env.js. Repare que o erro aponta a linha e a coluna exatas, então você vai direto ao ponto.

Erro 2 — a variável está declarada, o valor não existe

Aqui a declaração está certa e o .env está sem a linha. O build termina a maior parte do trabalho e só então valida as variáveis, porque precisa rodar o app para gerar as páginas estáticas.

✓ built in 1.42s
Analysing routes
error during build:
[SvelteKit error: env_invalid
Invalid environment variables:

DATABASE_URL
  - Value is missing. If it is optional, add a validator declaring it as such.

https://svelte.dev/e/kit/env_invalid] {
  plugin: 'vite-plugin-sveltekit-compile',
  hook: 'buildApp'
}

A dica está na própria mensagem: se o valor pode faltar, escreva um schema que aceite a falta e devolva um padrão. "Value is missing" é o aviso de que a variável é obrigatória do jeito que está declarada.

Erro 3 — o segredo importado no lugar errado

Um componente .svelte roda no servidor e no navegador. Quando ele importa do módulo privado, o build para antes de gerar o pacote do cliente.

Building app
vite v8.4.0 building client environment for production...
transforming...
✓ 196 modules transformed.
✗ Build failed in 281ms
error during build:
Build failed with 1 error:

[plugin vite-plugin-sveltekit-guard]
SvelteKit error: server_only_import
Cannot import `$app/env/private` into code that runs in the browser, as this could leak sensitive information.

 src/routes/quebra/+page.svelte imports
  $app/env/private

If you're only using the import as a type, change it to `import type`.
https://svelte.dev/e/kit/server_only_import

O nome do erro é server_only_import: módulo só de servidor, importado em código de navegador. A saída é mover a leitura para um +page.server.js e devolver só o que a tela precisa — ou usar o módulo público, se o valor realmente pode ser público. Quem decide é você, e a decisão tem consequência: o que for público aparece no HTML de qualquer visitante.

Exercícios

1. A senha do banco precisa ser lida por um +page.server.js. De qual módulo ela vem?

2. O que static: true faz com uma variável pública?

3. O build parou com Cannot import `$app/env/private` into code that runs in the browser. O que aconteceu?

Complete o código

// src/env.js

    schema: (valor) => {
      if (valor === undefined) return ;

Resumo

  • Variável de ambiente é um valor que mora fora do código, no ambiente onde o programa roda.
  • src/env.js declara quais variáveis existem e qual é o papel de cada uma, usando defineEnvVars.
  • O .env guarda os valores daquela máquina e fica no .gitignore: senha em commit não sai do histórico.
  • $app/env/private só pode ser importado por código de servidor; $app/env/public vai também ao navegador.
  • Sem public: true a variável é privada — o padrão é o lado seguro.
  • static: true congela o valor no build; o arquivo gerado mostra o texto entre aspas.
  • schema valida e transforma: é onde uma variável opcional ganha valor padrão.
  • O build falha com MISSING_EXPORT quando o nome não está declarado e com env_invalid quando o valor falta.
  • server_only_import é o erro de quem importa segredo num componente que roda no navegador.
  • $env/static/private e $env/dynamic/private são os nomes antigos, ainda aceitos com aviso de obsolescência.
  • Mascarar na tela é decisão de exibição; o valor completo continua existindo só no servidor.
