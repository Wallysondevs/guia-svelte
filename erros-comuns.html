Svelte · Erros Comuns

A Ana anotou num caderno os erros que a fizeram perder tempo no primeiro mês. Eram sempre os mesmos cinco: o número que virou texto, o estado que ninguém avisa, o bloco que abre e não fecha, a propriedade que não chega e o bind no lugar errado. Nesta aula, cada um aparece com a mensagem de verdade que o compilador escreve — e com o conserto.

1. A ideia: os erros se repetem

Quem começa a programar imagina que vai encontrar milhares de erros diferentes. Na prática, encontra os mesmos cinco, várias vezes, com roupa diferente. Saber reconhecer o padrão economiza mais tempo do que decorar sintaxe.

Isso acontece porque erro de programação quase nunca é aleatório. Ele nasce de uma suposição errada sobre o que a linguagem faz: que texto soma como número, que qualquer variável atualiza a tela, que o bloco fecha sozinho no fim do arquivo. Cada suposição dessas tem uma mensagem própria — e a mensagem diz exatamente qual foi a suposição.

O caminho é sempre o mesmo: ler a mensagem inteira, achar a linha, olhar o trecho, testar uma hipótese de cada vez. O resto desta aula é esse caminho aplicado aos cinco casos mais comuns no projeto da Ana.

Antes de procurar o que está errado, descubra quem está reclamando. Existem três lugares, e cada um vê uma parte diferente do problema.

3. A anatomia de uma mensagem

Toda mensagem de compilação do Svelte tem a mesma forma. Aprender a ler cada pedaço vale para os cinco erros desta aula e para os próximos.

Erro de compilação (linha 5, coluna 0): Block was left open
Erro de compilação
quem reclamou. Aqui é o compilador do Svelte, antes de qualquer coisa rodar no navegador.
(linha 5, coluna 0)
onde. A linha é contada a partir do topo do arquivo .svelte; a coluna começa em zero, contando caracteres da esquerda.
:
o fim do endereço e o começo da explicação. Tudo o que vem depois é a mensagem em inglês — curta, técnica e específica.
Block was left open
“o bloco ficou aberto”. Um {#if} começou e o compilador nunca encontrou o {/if} correspondente.

A coluna zero é uma pista forte. Ela quase sempre aponta para o começo de uma linha, e no Svelte as linhas que começam com {#, {: ou {/ são justamente as que abrem e fecham blocos. Quando a coluna é 0, olhe primeiro para essas chaves.

Leia a mensagem em voz alta em inglês técnico

“Block was left open” não quer dizer “bloco deixado aberto” no sentido de arquivo aberto no editor. Quer dizer “sobrou um bloco sem fechamento”. As mensagens do Svelte são curtas porque descrevem o estado do compilador, não o seu problema de negócio.

4. Erro clássico 1: o número que virou texto

Este é o campeão. A Ana recebeu o valor pago como texto, porque veio de um campo de formulário, e tentou somar:

<script>
  let pago = '0.90';
</script>

<p>{pago + 0.1}</p>
<p>0.900.1</p>

Não é bug do Svelte: é como o JavaScript funciona. O sinal de mais tem dois empregos — somar números e juntar textos. Quando um dos lados é texto, o outro é convertido em texto e os dois são colados. '0.90' é texto com aspas; 0.1 é número; o resultado é a colagem 0.900.1.

A consequência mais confusa vem depois: a variável continua sendo texto, e texto não tem toFixed. O componente então quebra na hora de desenhar:

<script>
  let preco = $state('0.90');
</script>

<p>R$ {preco.toFixed(2)}</p>
preco.toFixed is not a function

“preco.toFixed não é uma função”: o valor não tem esse método porque é texto. A correção é converter na entrada, com Number(valor), e guardar número. Calcule com número; formate só na hora de mostrar.

Missão: o preço foi guardado entre aspas, virou texto e o toFixed não existe nele. Guarde o número de verdade e a placa mostra R$ 0.90.

<script>
  let preco = $state('0.90');
</script>

<p>R$ {preco.toFixed(2)}</p>
<script>
  let preco = $state(0.9);
</script>

<p>R$ {preco.toFixed(2)}</p>

Repare que a diferença entre o código que quebra e o que funciona é só um par de aspas. Por isso este erro é tão comum: o arquivo fica quase igual, e a mensagem fala de uma função que existe na linguagem — mas não naquele valor.

5. Erro clássico 2: o estado que ninguém avisa

Aqui existe uma sutileza do Svelte 5 que confunde muita gente. Um componente sem nenhuma runa é compilado no modo antigo, e nele uma variável comum ainda atualiza a tela. A partir da primeira runa — $state, $derived, $props — o arquivo inteiro passa para o modo runas, e aí a variável comum para de avisar a tela.

A versão abaixo tem uma runa ($state no nome) e um contador declarado sem runa:

<script>
  let nome = $state('Ana');
  let cliques = 0;
</script>

<p>{nome}</p>
<button onclick={() => cliques++}>Cliques: {cliques}</button>
<p>Ana</p> <button>Cliques: 0</button>

A saída parece normal — e é, no primeiro desenho. O problema aparece no clique: cliques muda de valor, mas ninguém avisa o botão. O compilador sabe que isso vai acontecer e deixa um aviso na compilação:

non_reactive_update (linha 3): `cliques` is updated, but is not declared with `$state(...)`. Changing its value will not correctly trigger updates

“cliques é atualizado, mas não foi declarado com $state(...). Mudar o valor não vai disparar as atualizações corretamente.” A linha 3 é a declaração, e a mensagem já diz o conserto. Esse aviso não impede o build: o componente compila, a tela desenha, e só o clique fica sem efeito.

Missão: o botão conta no valor, mas o número na tela não muda, porque cliques não é estado reativo. Faça o clique aparecer na tela.

<script>
  let nome = $state('Ana');
  let cliques = 0;
</script>

<p>{nome}</p>
<button onclick={() => cliques++}>Cliques: {cliques}</button>
<script>
  let nome = $state('Ana');
  let cliques = $state(0);
</script>

<p>{nome}</p>
<button onclick={() => cliques++}>Cliques: {cliques}</button>

Uma dica prática que evita o problema: se o valor aparece na tela e muda durante o uso, ele é $state. Se ele nunca muda, pode ser const. Entre os dois não existe meio-termo útil — e é aí que nasce este erro.

6. Erro clássico 3: o bloco que abre e não fecha

Cada {#if} pede um {/if}, cada {#each} pede um {/each}, cada {#snippet} pede um {/snippet}. Quando falta o fechamento, o compilador reclama do bloco que ficou aberto:

<script>
  let aberto = $state(false);
</script>

{#if aberto}
  <p>Aberto</p>
Erro de compilação (linha 5, coluna 0): Block was left open

A linha apontada é a do {#if}, não a do fim do arquivo. Isso ajuda: o problema é o bloco que começou ali e não terminou. Em arquivos grandes, a dica é contar os pares — quantos {#if}, quantos {/if}. Se os números não batem, o erro está no que sobra.

Existe um segundo motivo, mais sutil, para o mesmo erro: o fechamento existe, mas está no lugar errado, dentro de outra tag. O compilador não consegue casar os pares e reclama do bloco aberto.

Missão: a tela fica vazia quando não há nada aberto, porque o {#if} não tem caminho alternativo. Acrescente o {:else} com a mensagem Fechado.

<script>
  let aberto = $state(false);
</script>

{#if aberto}
  <p>Aberto</p>
{/if}
<script>
  let aberto = $state(false);
</script>

{#if aberto}
  <p>Aberto</p>
{:else}
  <p>Fechado</p>
{/if}

O {:else} não é enfeite: é o caminho que garante que sempre existe algo na tela. Um {#if} sem {:else} é uma tela vazia esperando para acontecer — e a tela vazia nunca dá erro, o que a torna mais difícil de achar.

7. Erro clássico 4: a propriedade que não chega

Quando um componente recebe propriedades sem valor padrão e ninguém as passa, elas valem undefined. O componente compila e quebra no desenho, com uma mensagem que fala de “propriedades de undefined”:

<script>
  let { preco } = $props();
</script>

<p>R$ {preco.toFixed(2)}</p>
Cannot read properties of undefined (reading 'toFixed')

“Não consigo ler propriedades de undefined (lendo ‘toFixed’)”. O valor não existe, então não há de onde tirar o método. Duas correções possíveis: dar valor padrão (let { preco = 0 } = $props()) ou garantir que quem usa o componente sempre passe o preço. A primeira protege mais, porque vale mesmo quando o esquecimento é de outra pessoa.

8. O hábito: um erro por vez, o primeiro primeiro

Quando aparecem três erros juntos, comece pelo primeiro. Cada erro de compilação pode esconder os seguintes: com um bloco aberto, o compilador não sabe onde o resto começa, e as mensagens de baixo viram consequência.

OrdemO que conferir
1O primeiro erro do terminal, de cima para baixo
2A linha que ele aponta, com o arquivo aberto nela
3Se há um par de chaves faltando por perto
4Se o valor é do tipo que a operação espera (número, texto, lista)
5Salvar, olhar de novo, e só então o próximo erro

Vale anotar o que cada mensagem não diz. Ela não diz o que você queria fazer, não diz qual é o conserto e não sabe do seu negócio. Ela descreve o estado do arquivo no ponto em que o compilador desistiu: “sobrou um bloco”, “esse nome não existe”, “esse valor não tem esse método”. Quem traduz isso para a intenção original é você, e é por isso que ler o código em volta ainda é necessário.

Existe um teste que resolve a maioria dos casos em segundos: reduza o problema. Comente metade do HTML e veja se o erro continua; se continuar, ele está na metade que sobrou. Faça isso duas ou três vezes e o problema fica do tamanho de uma linha — e uma linha se lê inteira.

Não conserte no escuro

Trocar uma linha de lugar e salvar para “ver se resolve” transforma um problema em dois. Mude uma coisa, olhe o resultado, anote o que viu. Se piorar, desfaça — e o editor tem o atalho de desfazer exatamente para isso.

9. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Vale notar que todas as três apontam linha e coluna — e nenhuma delas fala do que você queria fazer, só do que o compilador encontrou.

Erro 1 — atribuir a uma constante

const promete que o valor não muda. Atribuir de novo é recusado na compilação.

<script>
  const preco = 0.9;
  preco = 1.2;
</script>

<p>R$ {preco.toFixed(2)}</p>
Erro de compilação (linha 3, coluna 2): Cannot assign to constant

“Não é possível atribuir a uma constante”. A coluna 2 é o começo do nome preco na segunda linha. Se o valor precisa mudar, use let com $state; se não precisa, apague a atribuição.

Erro 2 — bloco aberto sem fechamento

O mesmo erro da seção 6, agora visto com o arquivo completo: o {#if} abre na linha 5 e o arquivo termina sem o {/if}.

<script>
  let aberto = $state(false);
</script>

{#if aberto}
  <p>Aberto</p>
Erro de compilação (linha 5, coluna 0): Block was left open

A coluna 0 é o indício de que o problema é uma chave de bloco no começo da linha. Fechar o {#if} faz o erro desaparecer — mesmo que o resultado na tela ainda precise de ajuste.

Erro 3 — bind em tag que não guarda valor

bind:value liga um campo de formulário a uma variável, nas duas direções. Um parágrafo não tem valor para ligar.

<script>
  let nome = $state('Ana');
</script>

<p bind:value={nome}>{nome}</p>
Erro de compilação (linha 5, coluna 3): `bind:value` can only be used with `<input>`, `<textarea>`, `<select>`

“bind:value só pode ser usado com <input>, <textarea> e <select>”. A mensagem lista os três elementos válidos: são os únicos que guardam um valor digitado. Para mostrar texto, use {nome} sem bind.

10. Depois do conserto, o build passa

Consertar erro de compilação tem uma prova objetiva: o comando de produção termina com o sinal de certo. A Ana fechou o bloco, trocou a constante por $state e rodou de novo:

ana@notebook:~/loja$ npm run build

Repare nas duas linhas que importam quando algo dá errado: ✓ 111 modules transformed e ✓ built in 1.59s. O sinal de certo no começo da linha é o “terminei”; a ausência dele, junto com ✗ Build failed, é o “parei”. Lendo só essas duas linhas você já sabe se o problema é de compilação ou de outra coisa.

O nome do arquivo gerado (index-D0rj40xc.js) muda a cada build em que o conteúdo muda. É de propósito: o navegador guarda em cache pelo nome, então conteúdo novo significa nome novo. Se o nome não mudou, o conteúdo também não — e às vezes isso é a pista de que você salvou o arquivo errado.

Resumo

  • Erro tem endereço: linha e coluna, contando a coluna do zero.
  • Três lugares reclamam: compilação, build e console do navegador — cada um vê uma parte.
  • Texto com número soma por colagem: '0.90' + 0.1 vira 0.900.1.
