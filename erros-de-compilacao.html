Svelte · Quando Não Compila

A Ana tem uma tia que revisa receitas. Ela lê a ficha antes de ir para a cozinha e anota na margem: "aqui falta a quantidade de açúcar", "esta linha não faz sentido". Nada é assado até a ficha passar pela revisão — e é melhor assim, porque errar na ficha custa uma canetada, errar no forno custa a tarde. O compilador do Svelte é essa tia: ele lê o arquivo antes de qualquer coisa e devolve uma mensagem quando algo não fecha. Nesta aula você aprende a ler essas mensagens sem pânico.

  • Onde a mensagem aparece: terminal, navegador, editor e as caixas do guia.
  • Por que às vezes a mensagem parece falar de outro assunto.
  • O que é um aviso e por que ele não impede o build.

  • Os hábitos que evitam a maior parte dos erros de sintaxe.
  • Uma tabela das mensagens mais comuns e o que cada uma quer dizer.
  • Três erros reais, com a mensagem do compilador desta versão.

1. A ideia: o revisor antes do forno

Existem dois momentos em que uma receita pode dar errado. No primeiro, a ficha está ilegível ou incompleta: falta a quantidade, a palavra está cortada, a linha não termina. Quem revisa percebe antes de acender o forno. No segundo, a ficha está perfeita, mas o forno está frio ou a farinha venceu — o problema aparece durante o preparo.

Programação tem os mesmos dois momentos, e eles têm nomes. O erro de compilação acontece antes de a página rodar: o compilador lê o arquivo e não consegue transformá-lo em JavaScript. O erro de execução acontece depois, quando o componente já está na tela e alguma conta dá errado. As mensagens são diferentes, e o caminho para corrigir também.

A vantagem do primeiro tipo é que ele é barato: nada foi publicado, ninguém viu a página quebrada. O compilador aponta o lugar e você conserta. A desvantagem é que a mensagem nem sempre é clara — ela fala a língua de quem escreveu o compilador, não a de quem está começando. Traduzir essa língua é o assunto desta aula.

2. Erro de compilação × erro de execução

Vale fixar a diferença com um exemplo de cada. No erro de compilação, o arquivo nem chega a virar componente: uma chave aberta sem fechar, uma tag esquecida, uma runa no lugar errado. O compilador para e devolve a mensagem. No erro de execução, o componente compila, é montado, e quebra ao tentar usar um valor que não existe.

PerguntaErro de compilaçãoErro de execução
Quando acontece?antes de a página abrircom a página já rodando
Quem avisa?o compiladoro navegador (ou o renderizador)
Como começa a mensagem?"Erro de compilação (linha x, coluna y)""Erro ao renderizar" ou o nome do erro
O que corrigir?a sintaxe do arquivoo valor ou a lógica

Na prática, os dois pedem abordagens diferentes. Compilação é caça ao caractere: quase sempre é uma chave, uma aspa, uma tag. Execução é caça ao valor: uma variável vazia, um tipo trocado, uma conta que devia ser feita antes. Misturar os dois na cabeça faz você procurar chave onde o problema é dado — e vice-versa.

3. A anatomia de uma mensagem

Toda mensagem de compilação deste guia tem a mesma forma. Aprender a lê-la é metade do trabalho:

Erro de compilação (linha 5, coluna 15): Unterminated regular expression
Erro de compilação
o tipo. Se dissesse "Erro ao renderizar", o problema seria de execução, e a estratégia mudaria.
linha 5
onde o compilador parou. Nem sempre é onde o erro começou: um bloco aberto na linha 5 só é notado no fim do arquivo.
coluna 15
o caractere dentro da linha, contando do começo. Serve para achar o ponto exato em linhas compridas.
a mensagem
o texto em inglês, curto, escrito por quem fez o compilador. É diagnóstico, não instrução.
o código
em algumas saídas aparece também um endereço como svelte.dev/e/js_parse_error. É o código do erro, útil para procurar a explicação.

O detalhe mais importante é o primeiro: linha e coluna apontam onde o compilador desistiu, não necessariamente onde o erro está. Um {#if} sem fechamento é detectado no fim do arquivo. Uma aspa que abre e não fecha é detectada até o fim da linha. Ler "linha 40" em um arquivo de 40 linhas costuma significar "o problema começou bem antes".

4. Onde a mensagem aparece

O mesmo erro pode aparecer em quatro lugares, com roupas diferentes. O primeiro é o terminal, quando o servidor de desenvolvimento tenta compilar o arquivo. O segundo é o navegador, em uma sobreposição que cobre a página e mostra o texto do erro. O terceiro é o editor, com um sublinhado vermelho. O quarto são as caixas deste guia, que compilam o seu código de verdade.

Antes de investigar qualquer erro, vale conferir a versão do compilador. Um erro que não existe na documentação pode ser de outra versão:

ana@notebook:~/loja$ node -e "console.log(require('svelte/compiler').VERSION)"
5.59.2

E aqui está o compilador falando sozinho, sem o embrulho do guia. O comando tenta compilar o arquivo e imprime a mensagem crua quando falha:

ana@notebook:~/loja$ node -e "try { require('svelte/compiler').compile(require('fs').readFileSync('src/App.svelte','utf8'),{filename:'src/App.svelte'}) } catch (e) { console.log(e.message) }"
Unterminated regular expression
https://svelte.dev/e/js_parse_error

A mensagem crua é só a frase, sem linha nem coluna. O endereço no fim é o código do erro: js_parse_error quer dizer "o JavaScript dentro do arquivo não pôde ser lido". O guia acrescenta a posição porque ela é a informação mais útil — e é por isso que as caixas mostram o formato completo.

5. Erro × aviso

Nem tudo o que o compilador fala é erro. Existe uma categoria intermediária: o aviso. Ele não impede o build, não quebra a página e não aparece para o usuário. Aponta algo suspeito, que funciona mas provavelmente não é o que você queria. Este componente compila e roda:

<script>
  let nome = $state('Ana');
</script>

<div />
<p>{nome}</p>
<div></div> <p>Ana</p>

E, junto com a saída, vem um aviso no terminal:

aviso: element_invalid_self_closing_tag (linha 5): Self-closing HTML tags for non-void elements are ambiguous — use `<div ...></div>` rather than `<div ... />`
https://svelte.dev/e/element_invalid_self_closing_tag

A tradução: "tags HTML que não são vazias não devem se fechar sozinhas". O <div /> funcionou porque o compilador foi generoso, mas a forma correta é <div></div>. Em HTML, só alguns elementos podem se fechar sozinhos — img, input, br, hr — porque não têm conteúdo dentro.

A regra prática: erro impede, aviso aconselha. Um aviso ignorado hoje vira um problema na semana que vem, quando alguém menos experiente mexer no arquivo. Se o aviso aponta algo que você não entende, vale investigar antes de seguir; se aponta algo que você decidiu de propósito, o svelte-ignore documenta a decisão.

Missão: falta fechar a chave da expressão e o compilador reclama de "expressão regular sem fim". Feche a chave no lugar certo.

<script>
  let preco = $state(0.9);
</script>

<p>R$ {preco.toFixed(2)</p>
<script>
  let preco = $state(0.9);
</script>

<p>R$ {preco.toFixed(2)}</p>

Repare na mensagem que a caixa mostra: Unterminated regular expression. Ela fala de "expressão regular", que é um recurso de JavaScript para buscar padrões em texto — nada a ver com o seu preço. O compilador tentou interpretar o que veio depois da chave como código JavaScript e, não achando fechamento, chutou o que estava mais próximo na gramática dele.

6. Por que a mensagem parece falar de outra coisa

O compilador não lê o seu arquivo como um humano lê. Ele segue uma gramática: cada caractere pode iniciar certas construções e não outras. Quando encontra algo que não esperava, precisa escolher a interpretação mais próxima — e às vezes escolhe uma que não tem nada a ver com a sua intenção.

É o caso do "Unterminated regular expression". Em JavaScript, a barra / pode abrir uma expressão regular; o compilador viu uma expressão aberta e procurou o fechamento. A sua intenção era só fechar uma chave. O resultado é uma mensagem tecnicamente correta e praticamente inútil — e é por isso que a posição vale mais do que a frase.

A lição geral: quando a mensagem não fizer sentido, vá pela posição. Olhe a linha apontada e as três ou quatro linhas acima. Procure caracteres de abertura sem par: chave, parêntese, colchete, aspa, tag. Na maioria dos casos, o erro está nessa janela, e não no fim do arquivo.

7. O roteiro de cinco passos

Com o tempo você cria intuição, mas um roteiro ajuda nos primeiros meses. Cinco passos, na ordem:

Primeiro: leia o tipo. "Erro de compilação" ou "Erro ao renderizar"? Isso decide se você vai caçar sintaxe ou valor. Se for compilação, siga os passos abaixo; se for execução, pule para o valor.

Segundo: vá à posição. Abra o arquivo na linha indicada. Se a linha apontada for o fim do arquivo, olhe o arquivo inteiro procurando um par aberto: {#if} sem {/if}, <script> sem </script>, <!-- sem -->.

Terceiro: reduza. Se não achar, comente metade do arquivo. Compilou? O erro está na metade comentada. Não compilou? Está na outra. Repita até sobrar uma linha. Esse método de dividir ao meio acha qualquer erro em poucos minutos, mesmo em arquivos grandes.

Quarto: compare com o que funciona. Pegue um componente que compila e vá mudando uma coisa de cada vez até ele se parecer com o quebrado. A diferença que fizer parar de compilar é o erro. É mais rápido do que reler o arquivo quebrado dez vezes.

Quinto: escreva de novo, não conserte. Quando o trecho estiver muito embaralhado, apague e digite de novo, devagar. Digitar força você a passar por cada caractere — e é aí que a aspa que faltava aparece.

Missão: o {@html} está sem valor e o compilador reclama de espaço. Passe a variável texto para dentro da expressão.

<script>
  let texto = '<b>pão</b>';
</script>

<p>{@html}</p>
<script>
  let texto = '<b>pão</b>';
</script>

<p>{@html texto}</p>

A mensagem aqui é Expected whitespace — "esperava um espaço". O compilador leu {@html e esperava, depois do nome, um espaço e uma expressão. Como encontrou a chave de fechamento, reclamou do espaço que falta. Outra mensagem que só faz sentido quando você sabe o que ele esperava encontrar.

8. Prevenindo: hábitos que evitam a maior parte dos erros

Quase todo erro de compilação vem de um punhado de causas. Fechar as tags na hora em que abre é o primeiro hábito: escrever <h1></h1> e depois preencher o meio evita o "was left open". O mesmo vale para chaves de bloco e para aspas.

O segundo hábito é salvar antes de rodar. Parece bobo, mas metade dos "não funciona" em aula ao vivo é arquivo não salvo. O servidor de desenvolvimento recompila quando o arquivo muda no disco; se o editor está com a alteração só na tela, o Vite não vê nada.

O terceiro é não copiar blocos grandes de lugares diferentes. Cada exemplo da internet foi escrito para um contexto: uma versão do Svelte, um tipo de arquivo, uma configuração. Colar dois exemplos no mesmo componente cria o erro de "dois scripts" ou de runa misturada com sintaxe antiga, que já apareceram em aulas anteriores.

O quarto hábito é ler a mensagem em voz alta. Sério: dizer "expected token, expected whitespace, unexpected token" em voz alta obriga o cérebro a processar a frase, em vez de pular direto para o pânico. Depois de três ou quatro leituras, você começa a reconhecer os padrões.

Existe um quinto hábito que parece detalhe e não é: mantenha o terminal visível. O servidor de desenvolvimento imprime o erro no instante em que você salva, com a posição. Se o terminal está escondido atrás do navegador, você vê a página quebrada sem saber por quê e começa a procurar no lugar errado. Duas janelas lado a lado — editor e terminal — economizam mais tempo do que qualquer atalho de teclado.

Por último: deixe o arquivo em um estado que compila antes de parar. Se você precisa sair no meio de uma alteração, comente o trecho em construção ou desfaça. Voltar a um projeto que não compila, sem lembrar onde parou, é o pior jeito de começar o dia.

10. Quando dá errado

Os três casos abaixo saíram do compilador desta versão, copiados como estão. São os erros mais comuns de quem está começando com Svelte.

Erro 1 — chave sem fechar

Faltou o } da expressão. O compilador tentou ler o resto como código e desistiu.

<script>
  let nome = $state('Ana');
</script>

<p>Olá, {nome</p>
Erro de compilação (linha 5, coluna 15): Unterminated regular expression

Conte os pares: cada { precisa de um }. A posição aponta o fim da linha, onde ele parou de entender. A correção é escrever {nome} antes do </p>.

Erro 2 — atributo repetido

A mesma tag com dois atributos de mesmo nome. O compilador não sabe qual vale e recusa.

<script>
  let preco = $state(0.9);
</script>

<p class="preco" class="destaque">R$ {preco.toFixed(2)}</p>
Erro de compilação (linha 5, coluna 17): Attributes need to be unique

Junte os dois valores em um atributo só: class="preco destaque". A coluna 17 é o começo do segundo class, que é o que sobra.

Erro 3 — evento escrito como texto

onclick espera uma função, não uma string. Escrever o código dentro de aspas não faz o navegador executá-lo.

<button onclick="alert('oi')">comprar</button>
Erro de compilação (linha 1, coluna 8): Event attribute must be a JavaScript expression, not a string

Use chaves e uma função: onclick={() => alert('oi')}. A mensagem é literal: "atributo de evento tem de ser uma expressão JavaScript, não uma string".

Missão: sobrou um </p> no fim do arquivo e o compilador reclama. Apague a tag que não tem abertura.

<p>Preço: <strong>R$ 2</strong></p>
</p>
<p>Preço: <strong>R$ 2</strong></p>

Esse erro aparece quando você apaga um parágrafo e esquece o fechamento, ou copia um trecho pela metade. A mensagem attempted to close an element that was not open é generosa: ela diz que a tag tentou fechar algo que não estava aberto. É só apagar a sobra.

Resumo

  • Erro de compilação acontece antes de a página abrir; erro de execução, durante.
  • A mensagem tem tipo, linha, coluna e texto — e às vezes um código de documentação.
  • A posição aponta onde o compilador parou, não necessariamente onde o erro começou.
  • "Expected" costuma indicar falta; "Unexpected", sobra ou lugar errado.
  • Aviso não impede o build; erro impede.
  • Quando a mensagem não fizer sentido, vá pela posição e procure pares abertos.
  • Comentar metade do arquivo é o método mais rápido para achar o erro.
  • Os casos desta aula: chave sem fechar, atributo repetido e evento escrito como texto.
  • Salvar o arquivo antes de testar evita uma boa parte dos falsos alarmes.
