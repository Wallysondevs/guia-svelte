SvelteKit · error() e redirect()

A Ana pendurou dois avisos na padaria. O primeiro diz “esgotado” e fica no lugar do produto: o cliente entende na hora que não tem, sem precisar perguntar. O segundo é uma seta apontando para o caixa do outro lado, quando o pedido precisa ser pago antes de ser retirado. No SvelteKit essas duas placas se chamam error() e redirect(): as duas interrompem o que estava acontecendo, e a diferença é o que acontece depois. Esta aula mostra quando usar cada uma e o que o servidor responde de verdade.

Você vai aprender
  • O que significa interromper uma requisição no meio do load.
  • Como lançar um erro esperado com error(status, mensagem).
  • Como o +error.svelte mostra o status e a mensagem com $app/state.
  • Por que redirect() nunca devolve nada: ele lança por dentro.
  • Quando usar 303, 307 e 308.
  • Como redirecionar para fora do site com { external: true }.
  • A diferença entre erro esperado (4xx) e inesperado (500).
  • Como o handleError decide a mensagem que o cliente lê.
  • Os três tropeços reais: status fora da faixa, redirecionamento externo e corpo de erro obsoleto.

1. A ideia: a placa de esgotado e a seta

As duas placas da Ana resolvem problemas diferentes. A de “esgotado” informa um fim: aquele produto acabou, e o cliente não vai levar. A seta informa um caminho: o pedido existe, mas o próximo passo é em outro lugar. Nenhuma das duas é grosseria — as duas evitam que o cliente fique esperando por algo que não vai acontecer.

No código, a mesma divisão. error(404, 'Pão não encontrado') diz “esta página não existe” e mostra uma página de erro com status 404. redirect(303, '/entrar') diz “o conteúdo está em outro endereço, vá para lá” e manda o navegador buscar o novo endereço. Nos dois casos a função interrompe o load na hora: nada depois dela é executado.

Interromper é o ponto central. Quem começa tenta “avisar e continuar” — retorna um objeto com erro: true e deixa a página decidir. Funciona, e é mais trabalho: a página precisa checar, o status HTTP continua 200, o buscador indexa uma página que não existe. Lançar o erro deixa o framework cuidar do status, da página e do log.

2. Dois jeitos de interromper

As duas funções vêm do pacote @sveltejs/kit e são usadas dentro de load, de ações de formulário, de endpoints e de hooks. A tabela abaixo é o resumo que vale decorar:

error()redirect()
Primeiro argumentostatus de 400 a 599status de 300 a 308
Segundo argumentomensagem para o clienteendereço de destino
O que o navegador fazmostra a página de erropede o novo endereço
O que a URL mostraa mesma URL, com status de erroa URL nova
Uso típicoproduto inexistente, acesso negadologin feito, URL antiga, saída

Repare que as faixas não se cruzam: 4xx e 5xx para erro, 3xx para redirecionamento. Essa separação não é capricho do SvelteKit — é o protocolo HTTP. Um erro com status 200 engana o buscador e o monitoramento; um redirecionamento com status 200 é uma página em branco.

3. error(): a página que diz o que aconteceu

O uso mais comum é num load do servidor: procurar um produto pelo identificador e, se não existir, interromper com 404.

import { error } from '@sveltejs/kit';

export function load() {
	throw error(404, 'Pão não encontrado na prateleira');
}
throw
a palavra que interrompe. error() devolve um objeto especial; lançar é o que faz o SvelteKit parar o load e montar a resposta de erro.
404
o status HTTP. Diz “não encontrado”; o navegador, o buscador e o monitoramento entendem o número sem ler a mensagem.
'Pão não encontrado…'
a mensagem para quem está lendo. Curta, sem detalhe técnico, sem nome de tabela do banco.
load
o lugar onde isso costuma acontecer: é o código que busca o dado e descobre que ele não existe.

No SvelteKit 3 essa função já lança por dentro. Isso surpreende quem vem de versão anterior, em que o padrão era throw error(...) e o retorno era inútil. Hoje os dois jeitos funcionam, porque o lançamento acontece dentro da própria função — e é por isso que o guia mantém o throw: ele deixa claro, para quem lê, que a linha abaixo não será executada.

As mensagens de status inválido confirmam a faixa aceita. Com um erro de status 200, o terminal do servidor mostra:

SvelteKit error: invalid_error_status
HTTP error status codes must be between 400 and 599 — 200 is invalid
https://svelte.dev/e/kit/invalid_error_status
    at load (src/routes/quebra-error-status/+page.server.js:4:8)

A leitura é direta: “status de erro HTTP precisa estar entre 400 e 599”. O 200 é sucesso, e sucesso não é erro. A linha de baixo mostra o arquivo e a posição da chamada.

4. A página de erro do projeto

Sem nenhum arquivo especial, o SvelteKit já mostra uma página de erro. Para personalizar, você cria um +error.svelte na raiz de src/routes (ou numa pasta, para valer só ali). No SvelteKit 3, os dados da página vêm do módulo $app/state:

<script>
	import { page } from '$app/state';
</script>

<h1>{page.status}</h1>
<p>{page.error.message}</p>
<p><small>{page.error.codigo}</small></p>
<a href="/">voltar para a padaria</a>

Com esse arquivo no lugar, um pedido a /erro devolve 404 e o corpo com os dados que o handleError decidiu. O terminal mostra o resultado:

ana@notebook:~/loja$ curl -s http://localhost:5173/erro | grep -o '<h1>[^<]*</h1>\|<p>[^<]*</p>'
<h1>404</h1>
<p>A padaria teve um problema. Tente de novo em instantes.</p>

Note que a mensagem não é a do error() — é a que o handleError devolveu. O hook de erro tem a palavra final sobre o que o cliente lê, e isso é intencional: o mesmo handleError atende todos os erros do site, então a mensagem fica consistente. Se você quiser a mensagem específica na tela, é o handleError que precisa repassá-la.

Antes de seguir, uma distinção que evita muita confusão. error() troca a página inteira pela página de erro. Já fail(), usado em ações de formulário, mantém a página no lugar e devolve os dados para o componente — é o que a aula de autenticação usa para mostrar “senha incorreta” sem sair da tela de login. A regra é: erro que impede a página de existir usa error(); erro de preenchimento usa fail().

E existe um componente que resume a página de erro em duas linhas, útil para testar o visual:

<script>
	let { status = 404, mensagem = 'Pão não encontrado na prateleira' } = $props();
</script>

<h1>{status}</h1>
<p>{mensagem}</p>
<h1>404</h1> <p>Pão não encontrado na prateleira</p>

5. Caixa 1: o status vira mensagem

Uma página de erro precisa traduzir número em frase. A caixa abaixo mostra “ok” para qualquer status, inclusive 404.

Missão: clique no botão e faça o texto virar 404: Pão não encontrado. Para qualquer outro status, mantenha ok.

<script>
	let status = $state(200);
</script>

<button onclick={() => (status = 404)}>buscar pão</button>
<p>{status}: ok</p>
<script>
	let status = $state(200);
	const mensagem = $derived(status === 404 ? 'Pão não encontrado' : 'ok');
</script>

<button onclick={() => (status = 404)}>buscar pão</button>
<p>{status}: {mensagem}</p>

O $derived recalcula a frase quando o status muda, e o botão muda o status. Numa página de erro de verdade, esse par vem do servidor: o status chega no page.status e a mensagem em page.error.message.

6. redirect(): por que ele nunca volta

Aqui está a diferença que confunde. redirect() não devolve um valor para você usar depois: ele lança um objeto especial. É o que o código do próprio SvelteKit mostra:

ana@notebook:~/loja$ sed -n 129,137p node_modules/@sveltejs/kit/src/exports/index.js
export function redirect(status, location, options) {
	if ((!BROWSER || DEV) && (isNaN(status) || status < 300 || status > 308)) {
		e.invalid_redirect_status({ status: String(status) });
	}

	const href = location.toString();
	validate_redirect_location(href, options);

	throw new Redirect(

Duas coisas nesse trecho explicam o comportamento. A primeira: a validação do status acontece antes de qualquer coisa, com a faixa de 300 a 308. A segunda: a última linha é um throw. Como a função lança por dentro, escrever return redirect(…) ou throw redirect(…) dá no mesmo — nos dois casos a linha seguinte não executa.

O resultado prático, no servidor:

ana@notebook:~/loja$ curl -s -i http://localhost:5173/conta | head -3
HTTP/1.1 303 See Other
Vary: Origin
location: /entrar?de=/conta

O status 303 e o cabeçalho location são a seta da padaria. O navegador lê e faz um pedido novo, com GET, ao endereço indicado. Se você estiver no cliente e quiser navegar sem recarregar a página inteira, a ferramenta é outra: a função goto, do módulo $app/navigation.

7. Caixa 2: 303 para POST, 307 para GET

O status do redirecionamento não é detalhe: ele diz ao navegador qual método usar no pedido seguinte. A caixa abaixo tem os dois casos e nenhum número.

Missão: use 303 para o POST (o navegador busca com GET) e 307 para o GET (o método continua o mesmo). O texto precisa conter POST → 303.

<script>
	const pedidos = [
		{ metodo: 'POST', status: '—' },
		{ metodo: 'GET', status: '—' }
	];
</script>

{#each pedidos as p}
	<p>{p.metodo} → {p.status}</p>
{/each}
<script>
	const pedidos = [
		{ metodo: 'POST', status: 303 },
		{ metodo: 'GET', status: 307 }
	];
</script>

{#each pedidos as p}
	<p>{p.metodo} → {p.status}</p>
{/each}

Depois de um POST de formulário, o 303 é quase sempre a escolha certa: o navegador deixa de reenviar o formulário e faz um GET limpo. Não à toa o SvelteKit devolve 303 no login bem-sucedido e na saída de conta.

8. 303, 307 e 308

StatusMétodo no destinoQuando usar
303sempre GETdepois de POST de formulário
307o mesmo métodoredirecionamento temporário que preserva o pedido
308o mesmo métodomudança permanente de endereço
302historicamente GETcompatibilidade com sistema antigo

A diferença entre temporário e permanente tem consequência de SEO. Um 308 diz ao buscador “este endereço mudou para sempre, atualize o índice”; um 307 diz “hoje é aqui, amanhã pode ser outro lugar”. Usar 308 numa mudança que você pretende desfazer transfere autoridade de busca para um endereço que talvez não exista no mês seguinte.

Também existe o redirecionamento para fora do site, e ele precisa de permissão explícita. Sem o terceiro argumento, o SvelteKit recusa:

SvelteKit error: redirect_external_not_allowed
Cannot redirect to external URL `"https://evil.example/pagina"`. To redirect to an external URL, pass `{ external: true }` or an allowlist of permitted origins as the third argument to `redirect`
https://svelte.dev/e/kit/redirect_external_not_allowed

A proteção existe porque redirecionamento aberto é ferramenta de golpe: um link do seu site levando para uma página falsa. Com redirect(303, url, { external: true }) você assume a responsabilidade; com { external: ['https://parceiro.com'] }, limita o destino a uma lista.

9. Caixa 3: o erro que vira mensagem

Dentro de um componente, um erro comum não é tratado pelo SvelteKit — ele quebra a função que o lançou. A caixa abaixo chama uma função que lança e deixa o erro subir.

Missão: clique em buscar e mostre a mensagem do erro na tela. Capture com try/catch e use e.message.

<script>
	let msg = $state('');
	function buscar() {
		throw new Error('Pão não encontrado');
	}
	function tentar() {
		buscar();
	}
</script>

<button onclick={tentar}>buscar</button>
<p>{msg || 'nada'}</p>
<script>
	let msg = $state('');
	function buscar() {
		throw new Error('Pão não encontrado');
	}
	function tentar() {
		try {
			buscar();
		} catch (e) {
			msg = e.message;
		}
	}
</script>

<button onclick={tentar}>buscar</button>
<p>{msg || 'nada'}</p>

try marca o trecho que pode falhar; catch (e) recebe o erro; e.message é o texto que a função passou para Error. Sem o catch, o erro sobe até o topo e o navegador registra no console — a página continua na tela, mas nada acontece para o usuário. Numa página de verdade, o mesmo caso é resolvido por um load que lança error(404, …).

10. Erro esperado e erro inesperado

Nem todo erro é uma placa. Existem os que você previu — produto inexistente, acesso negado, campo inválido — e os que você não previu: banco fora do ar, variável nula, função que não existe. O SvelteKit trata os dois de forma diferente, e o hook handleError recebe os dois.

Um erro previsto tem status escolhido por você e mensagem escrita por você. Um erro não previsto é qualquer exceção solta: o status vira 500 e a mensagem padrão é “Internal Error”. O terminal registra a pilha — os milissegundos mudam a cada execução, o status não:

TypeError: Cannot read properties of null (reading 'nome')
    at eval (src/routes/quebra-locals/+page.svelte:5:29)
    at eval (node_modules/svelte/src/internal/server/renderer.js:416:11)
GET /quebra-locals → 500 (35 ms)
500 GET /quebra-locals

No cliente, a página é a do +error.svelte, com o status 500. O handleError do projeto recebeu esse erro e registrou com console.error, como a aula de logs mostrou. O que o cliente lê é a mensagem amigável; o que a equipe lê é a pilha.

Não esconda o 500

Transformar todo erro em 404 é tentador e atrapalha. O 404 diz “isso não existe” e o buscador remove a página do índice; o 500 diz “o servidor falhou” e o monitoramento acende o alarme. Trocar um pelo outro faz você perder as duas informações.

11. Quando dá errado

As três mensagens abaixo saíram do servidor de desenvolvimento desta máquina. As duas primeiras são erros reais de uso; a terceira é um aviso de código obsoleto.

Erro 1 — status de redirecionamento fora da faixa

Você escreveu redirect(200, '/conta'), misturando sucesso com redirecionamento. O servidor responde 500 e explica no terminal.

SvelteKit error: invalid_redirect_status
Redirect status codes must be between 300 and 308 — 200 is invalid
https://svelte.dev/e/kit/invalid_redirect_status
    at load (src/routes/quebra-status/+page.server.js:4:8)
GET /quebra-status → 500 (252 ms)

Esquecer o status produz uma mensagem curiosa, com o endereço no lugar do número: Redirect status codes must be between 300 and 308 — /conta is invalid. Ela vem do mesmo erro e o motivo é o mesmo: o primeiro argumento precisa ser um número na faixa 300–308.

Erro 2 — redirecionamento para fora sem permissão

Um destino externo precisa ser declarado. Sem isso, o erro aparece no terminal e o cliente recebe 500.

SvelteKit error: redirect_external_not_allowed
Cannot redirect to external URL `"https://evil.example/pagina"`. To redirect to an external URL, pass `{ external: true }` or an allowlist of permitted origins as the third argument to `redirect`
https://svelte.dev/e/kit/redirect_external_not_allowed
GET /quebra-externo → 500 (11 ms)
500 GET /quebra-externo

A correção é o terceiro argumento: redirect(303, url, { external: true }) para liberar qualquer destino, ou { external: ['https://parceiro.com'] } para limitar a uma lista. A segunda opção é a que resiste a erro de digitação.

Aviso 3 — corpo de erro no formato antigo

Passar um objeto como segundo argumento de error() ainda funciona, mas o SvelteKit 3 avisa que o formato mudou: mensagem no segundo argumento, propriedades extras no terceiro.

[sveltekit] error_body_deprecated
Passing an `App.Error` body as the second argument is deprecated — pass the `message` as the second argument, and any additional properties as the third
https://svelte.dev/e/kit/error_body_deprecated

O formato novo é error(404, 'Pão não encontrado', { codigo: 'PAO-404' }). O objeto App.Error declara os campos extras, e eles chegam no page.error do +error.svelte.

Resumo

  • error() e redirect() interrompem o load: nada depois delas executa.
  • No SvelteKit 3 as duas lançam por dentro; throw na frente deixa a intenção explícita.
  • error() aceita status de 400 a 599; redirect(), de 300 a 308.
  • O +error.svelte personaliza a página e lê page.status e page.error de $app/state.
  • O handleError decide a mensagem que o cliente lê em qualquer erro do site.
  • 303 manda buscar com GET; 307 e 308 preservam o método.
  • Destino externo exige { external: true } ou uma lista de origens.
  • Erro esperado vira 4xx com mensagem sua; inesperado vira 500 com pilha no terminal.
  • Erros desta aula: invalid_redirect_status, redirect_external_not_allowed e error_body_deprecated.
  • fail() é para formulário: mantém a página e devolve os dados; error() troca a página inteira.
  • O erro procura o +error.svelte mais próximo subindo pelas pastas; sem nenhum, o Kit usa a página padrão dele.
  • O que aparece para o visitante é sempre a mensagem que o handleError devolveu — nunca a pilha do servidor, que fica registrada apenas no terminal de quem programou.
