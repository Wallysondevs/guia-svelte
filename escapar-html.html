Svelte · Escapando HTML

A Ana colou na vitrine um cartaz que um cliente trouxe: o papel dizia "PÃO & BOLO" e, embaixo, um desenho. Ela não leu o desenho como instrução — colou o papel inteiro. Mas se alguém entregasse um papel escrito "arranque a vitrine", ela não faria isso: papel é papel, instrução é instrução. O navegador tem o mesmo dilema com texto que vem de uma variável: é conteúdo para mostrar ou marcação para obedecer? O Svelte escolhe mostrar. Nesta aula você vê como isso funciona, como o `{@html}` muda a regra e por que essa mudança é perigosa.

Você vai aprender

  • Como o Svelte escapa o valor de {texto} automaticamente.

  • Como funciona o escape dentro de um atributo.
  • O que {@html texto} faz e o que o compilador gera em cada caso.
  • Quando o atalho é legítimo e quando é falha de segurança.
  • Por que javascript: em um href é uma armadilha.
  • Por que não se escreve </script> dentro de uma string do script.
  • Os erros reais desta aula, com a mensagem do compilador.

1. A ideia: a etiqueta e o vidro

Toda padaria tem dois tipos de papel: o que o cliente lê e o que a máquina lê. A etiqueta da balança, com código de barras, é lida pela máquina. O cartaz da parede é lido pelo cliente. Se você colar um cartaz dentro da balança, a balança não vai entender; se colar um código de barras na parede, o cliente não vai entender. O mesmo texto pode ser conteúdo ou instrução, dependendo de quem lê.

No navegador, "etiqueta" é HTML: a marcação que o navegador interpreta para construir elementos. "Cartaz" é texto: aquilo que aparece na tela, sem interpretação. Quando você escreve <b>pão</b> no arquivo, o navegador cria um elemento em negrito. Quando a mesma sequência vem de uma variável e vai para a tela como texto, o navegador mostra os próprios sinais: <b>pão</b>.

Quem decide qual dos dois acontece é o lugar de onde o valor veio. No Svelte, o padrão é "cartaz": valor de variável é sempre texto. Para tratar como HTML, é preciso pedir — e pedir tem consequências, porque um HTML vindo de fora pode conter mais do que negrito.

2. {texto} já escapa

O componente abaixo tem uma variável cujo valor contém tags. Veja as duas saídas: a primeira com chaves simples, a segunda com o atalho {@html}.

<script>
  let texto = '<b>pão</b> quentinho & fresco';
</script>

<p>{texto}</p>
<p>{@html texto}</p>
<p>&lt;b>pão&lt;/b> quentinho &amp; fresco</p> <p><b>pão</b> quentinho & fresco</p>

Dois parágrafos com resultados diferentes para o mesmo valor. No primeiro, &lt; e &amp; são entidades: formas de escrever < e & sem que o navegador os interprete como marcação. O navegador lê a entidade, mostra o sinal e não constrói elemento nenhum. No segundo, o HTML foi entregue cru e o navegador criou o negrito de verdade.

Repare que o texto da tela do segundo parágrafo é "pão quentinho & fresco", sem os sinais. Isso porque as tags viraram elementos. Já o primeiro mostra os sinais e as palavras: para quem lê a página, tudo é texto.

3. O que exatamente é escapado

O Svelte escapa os caracteres que poderiam abrir marcação ou confundir o parser: < vira &lt; e & vira &amp;. O > costuma ficar como está, porque sozinho não abre nada. Veja:

<script>
  let texto = '5 < 6 e 7 > 6';
</script>

<p>{texto}</p>
<p>5 &lt; 6 e 7 > 6</p>

Na tela, o cliente lê "5 < 6 e 7 > 6" corretamente. No HTML, o sinal de menor virou entidade e o de maior não. Não é inconsistência: é o mínimo necessário para o parser não se enganar.

Dentro de um atributo, o escape inclui as aspas. Se o valor tem aspas duplas e o atributo é delimitado por elas, sem escape o atributo terminaria no meio:

<script>
  let texto = 'A & B "citação" <tag>';
</script>

<p title={texto}>passe o mouse</p>
<p title="A &amp; B &quot;citação&quot; &lt;tag>">passe o mouse</p>
&lt;
entidade do sinal de menor (less than). É o escape mais importante, porque é ele que abre tag.
&amp;
entidade do e comercial. Sem escape, o navegador tentaria ler o que vem depois como começo de outra entidade.
&quot;
entidade da aspa dupla. Aparece no escape de atributos, onde a aspa fecharia o valor antes da hora.
&gt;
entidade do sinal de maior. O Svelte quase nunca precisa dela no texto, mas ela existe e você vai encontrá-la em HTML de terceiros.

Três entidades no mesmo atributo: &amp;, &quot; e &lt;. Tudo isso é trabalho do compilador. Você escreve title={texto} e ele resolve o resto — inclusive o caso de o valor vir de um formulário.

Missão: o parágrafo mostra as tags como texto. Use o atalho {@html} para que o navegador interprete o negrito, e a tela mostre só "pão quentinho".

<script>
  let texto = '<b>pão</b> quentinho';
</script>

<p>{texto}</p>
<script>
  let texto = '<b>pão</b> quentinho';
</script>

<p>{@html texto}</p>

A meta confere o texto inteiro da tela: "pão quentinho", sem os sinais de menor e maior. Só o {@html} produz isso, porque no outro caso os sinais fazem parte do texto visível.

4. {@html}: o atalho e o preço

O atalho se chama {@html} e faz uma coisa só: em vez de inserir o valor como texto, insere como marcação. O compilador gera instruções diferentes para cada caso, e vale ver a diferença. Este é o JavaScript gerado para {texto}:

ana@notebook:~/loja$ node -e "const {compile}=require('svelte/compiler');console.log(compile(require('fs').readFileSync('src/App.svelte','utf8'),{generate:'client',filename:'src/App.svelte'}).js.code)"
import 'svelte/internal/init-operations';
import 'svelte/internal/disclose-version';
import * as $ from 'svelte/internal/client';

var root = $.from_html(`
`);

export default function App($$anchor) {
	let texto = 'pão';
	var p = root();

	p.textContent = 'pão';
	$.append($$anchor, p);
}

O que importa é a linha p.textContent = …. A propriedade textContent do DOM existe exatamente para isso: recebe texto e não interpreta nada. O navegador cria um nó de texto com os sinais e mostra o que está escrito.

Agora o mesmo componente com {@html texto}:

ana@notebook:~/loja$ node -e "const {compile}=require('svelte/compiler');console.log(compile(require('fs').readFileSync('src/App.svelte','utf8'),{generate:'client',filename:'src/App.svelte'}).js.code)"
import 'svelte/internal/init-operations';
import 'svelte/internal/disclose-version';
import * as $ from 'svelte/internal/client';

var root = $.from_html(`
`);

export default function App($$anchor) {
	let texto = 'pão';
	var p = root();

	$.html(p, () => texto, true);
	$.reset(p);
	$.append($$anchor, p);
}

Duas linhas novas, e nenhuma delas é textContent. $.html(p, () => texto, true) manda o motor colocar o valor como HTML dentro do parágrafo. $.reset(p) ajusta as referências internas depois que o conteúdo muda. É uma operação mais cara e mais poderosa.

O preço não é de desempenho: é de confiança. Quando você usa {@html}, assume que o valor é seguro. Se esse valor vier de um formulário, de um comentário de cliente, de um arquivo enviado ou de uma API de terceiros, você acabou de entregar ao visitante o controle sobre a marcação da sua página.

5. Quando o atalho é legítimo

Existe um caso em que {@html} é a ferramenta certa: quando o HTML foi produzido por você ou por uma biblioteca confiável, a partir de uma fonte controlada. O exemplo clássico é converter Markdown em HTML. O texto do arquivo é seu, o conversor é seu, e o resultado é marcação que você quer mostrar.

Outro caso legítimo: conteúdo de um editor que você mesmo administra, com revisão. A Ana escreve a descrição do pão no painel da padaria, com negrito e listas. Aquele HTML é dela, revisado por ela. Mostrar como marcação faz sentido.

O caso ilegítimo é qualquer coisa que o visitante digitou. Comentário, nome no cadastro, mensagem de contato, avaliação de produto: nada disso deve passar por {@html}. Se você quer permitir negrito em um comentário, o caminho é converter um subconjunto seguro — nunca entregar o texto cru.

Vale um exemplo concreto de quanto custa errar. Um site de receitas mostra comentários de leitores com {@html}. Um leitor mal-intencionado escreve um comentário com uma imagem que tem um endereço falso e um manipulador de erro; quando outro leitor abre a página, o código roda no navegador dele, no domínio do site. O estrago pode ir de um alerta chato até o roubo de uma sessão. O conserto não é "escapar melhor": é parar de interpretar o que o visitante escreveu.

Existe também o custo de manutenção: HTML solto dentro de uma string não é verificado pelo compilador. Uma tag sem fechar dentro de {@html} não gera erro de compilação; gera um DOM estranho na hora de rodar. Quanto menos HTML em string, melhor.

Missão: monte o preço em negrito usando {@html} com uma string concatenada: "R$ " mais <b> com o preço formatado em duas casas, mais </b>.

<script>
  let preco = $state(0.9);
</script>

<p>R$ {preco}</p>
<script>
  let preco = $state(0.9);
</script>

<p>{@html 'R$ <b>' + preco.toFixed(2) + '</b>'}</p>

Note que a solução usa toFixed(2) para chegar em 0.90: a meta confere o texto "R$ 0.90". Sem a formatação, sairia "R$ 0.9" e a conferência falharia. Duas ideias de aulas diferentes trabalhando juntas.

6. O caso do </script> na string

Um detalhe que pega todo mundo: dentro do bloco <script>, a sequência </script> encerra o bloco, mesmo que esteja dentro de uma string. O compilador não está sendo burro: o HTML é lido assim desde sempre, e o Svelte segue a mesma regra.

Se você precisa escrever essa sequência em uma string, escape a barra: <\/script>. Para o JavaScript, a barra invertida antes de uma barra não muda nada — o valor continua igual. Para o parser do HTML, a sequência deixou de existir.

O mesmo vale para comentários e para qualquer texto dentro do script. É uma daquelas regras que você aprende uma vez e reconhece pelo sintoma: a mensagem fala de "string sem fim", e o fim está lá, na sua frente.

7. O href que executa código

Existe uma marcação que parece inofensiva e é uma armadilha: o endereço que começa com javascript:. O navegador executa o que vem depois. O Svelte não bloqueia isso automaticamente:

<script>
  let link = 'javascript:alert(1)';
</script>

<a href={link}>cardápio</a>
<a href="javascript:alert(1)">cardápio</a>

Se esse link vier de um campo que o visitante controla, ele pode colocar javascript: no lugar de https: e executar código quando alguém clicar. A defesa é validar o endereço antes de usar: aceitar só o que começa com https:// ou com uma barra, e recusar o resto.

Existe uma variante ainda mais discreta: o endereço que começa com data: e carrega um documento inteiro. Ele não executa script na maioria dos navegadores modernos, mas pode ser usado para exibir conteúdo enganoso em um iframe ou em uma nova aba. Na dúvida, trate qualquer esquema que não seja http, https, mailto ou tel como suspeito e recuse.

A regra geral vale para todo atributo que aponta para um recurso: href, src, action. O escape de texto protege contra a interpretação de marcação; não protege contra um esquema de URL perigoso. São duas camadas diferentes, e as duas precisam de atenção.

8. Quando o texto tem sinal de menor

No HTML do componente, um < fora de tag é tratado como começo de tag. Se você escrever o sinal direto no texto, o compilador tenta interpretar o que vem depois como nome de elemento e reclama. É o primeiro cenário abaixo.

A solução é escrever a entidade: &lt; no lugar de <. Parece redundante, mas é a regra do HTML desde a invenção: alguns caracteres são reservados. O mesmo vale para &amp; quando você quer mostrar um & literal.

Uma confusão frequente é escrever &lt; dentro de uma variável. Não faça isso: o escape automático transformaria o & em &amp;, e o visitante leria a entidade escrita, letra por letra. Entidade é coisa do HTML, não do valor. Dentro da variável, o sinal entra cru.

Quando o sinal vem de uma variável, o problema não existe: o escape é automático, como vimos no começo da aula. É mais uma razão para preferir valores a texto fixo — a regra é aplicada pelo compilador, não pela sua memória.

9. Um caminho seguro para texto de fora

Chame de "texto de fora" qualquer coisa que você não escreveu: comentário, nome, mensagem, descrição de produto vinda de um painel, resposta de API. Para esse tipo de texto, o caminho seguro tem três passos.

O primeiro é mostrar com chaves simples. {comentario} escapa e pronto. Você não precisa limpar nada, não precisa converter nada: o compilador faz o trabalho. É a opção mais segura e a que dá menos manutenção.

O segundo passo, quando o layout exige formatação, é converter de um formato seguro para HTML no seu código. Um exemplo comum: guardar o comentário em Markdown, converter com uma biblioteca e exibir o resultado com {@html}. O texto do visitante nunca é interpretado como HTML; o que ele escreveu é transformado por uma biblioteca que você escolheu, com regras que você conhece.

O terceiro passo é validar o que não é texto: endereços e identificadores. Um link vindo de fora precisa ser checado antes de virar href. Uma imagem vinda de fora precisa vir de um domínio permitido. O escape não resolve isso, porque o problema não é marcação: é destino.

E existe o passo zero, que é uma decisão de projeto: não aceitar HTML de visitante. Muitos sistemas famosos permitem negrito e itálico em comentários e bloqueiam todo o resto. É menos flexível e muito mais seguro. Quando alguém pedir "quero poder colocar imagem no comentário", a resposta saudável é "queremos, mas com um botão que insere a imagem por nós", não "pode colar HTML".

9. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão. Todas são armadilhas de marcação que o iniciante encontra na primeira semana.

Erro 1 — sinal de menor no texto

O < solto no parágrafo fez o compilador procurar uma tag. Ele chegou ao número e desistiu.

<p>5 < 6</p>
Erro de compilação (linha 1, coluna 6): Expected a valid element or component name. Components must have a valid variable name or dot notation expression

A tradução é "esperava um nome de elemento válido". Use 5 &lt; 6 para mostrar o sinal, ou coloque o texto em uma variável: {'5 < 6'} também funciona, porque dentro de aspas o sinal é texto.

Erro 2 — </script> dentro de uma string

O parser do HTML fechou o bloco no meio da string. O compilador ficou com uma aspa aberta e um monte de código solto.

<script>
  let codigo = '<script>alert(1)</script>';
</script>

<p>Exemplo: {codigo}</p>
Erro de compilação (linha 2, coluna 15): Unterminated string constant

"String sem fim" — e o fim estava ali. Escape a barra: '<script>alert(1)<\/script>'. O valor continua igual e o parser não fecha mais o bloco antes da hora.

Erro 3 — aspas dentro de aspas no atributo

O atributo abre com aspas duplas e o texto também tem aspas duplas. A segunda fecha o atributo, e o resto sobra.

<p title="A "citação"">passe o mouse</p>
Erro de compilação (linha 1, coluna 20): Expected token =

Use aspas simples no atributo: title='A "citação"'. Ou coloque o texto em uma variável e passe com chaves — nesse caso o compilador escapa as aspas sozinho, como vimos na seção 3.

Missão: a string contém </script> e quebra o arquivo. Escape a barra com \ para o valor continuar igual sem fechar o bloco.

<script>
  let codigo = '<script>alert(1)</script>';
</script>

<p>Exemplo: {codigo}</p>
<script>
  let codigo = '<script>alert(1)<\/script>';
</script>

<p>Exemplo: {codigo}</p>

O texto que aparece na tela é a sequência inteira, porque o valor é usado com chaves simples: o escape de texto entra em ação de novo e o visitante vê os sinais, não um alerta.

Resumo

  • Valor de variável entra na tela como texto, não como marcação.
  • {texto} escapa < e &, gerando textContent no código compilado.
  • Em atributos, o escape inclui as aspas.
