Svelte · Estilos Escopados

A Ana quer o título da padaria em dourado, mas só na placa da entrada — não no site inteiro, onde outros títulos também são <h1>. Em CSS tradicional, "todo h1 dourado" é uma regra que vaza e obriga a inventar nomes de classe. No Svelte, o estilo escrito dentro do componente vale só ali, e quem garante isso é o compilador, com um selo que ele mesmo inventa.

Você vai aprender
  • O que é escopo e por que ele evita nomes de classe inventados.
  • Como o compilador renomeia os seletores do componente.
  • Que o mesmo selo aparece nas tags do HTML gerado.
  • Por que o selo muda quando o nome do arquivo muda.
  • Como abrir uma exceção com :global(…).
  • O que é um seletor que não casa e o aviso css_unused_selector.
  • O :where(…) que aparece nos seletores descendentes.
  • Como o CSS do componente sai no build, num arquivo só.
  • Os três erros reais desta aula, com a mensagem do compilador.
  • Como conferir o CSS gerado com npm run build.

1. A ideia: o estilo da placa não vaza

Na padaria, a placa da entrada tem letra dourada. O cartaz do café, ao lado, tem letra preta. Se a regra fosse "toda letra grande é dourada", o cartaz do café ficaria dourado por acidente. Em CSS tradicional, é exatamente isso que acontece: um seletor h1 { color: gold } numa folha de estilo atinge todos os h1 da página, de todos os componentes.

A solução clássica é inventar nomes de classe únicos — .titulo-padaria-dourado — e torcer para ninguém repetir. Funciona, mas custa disciplina: cada regra precisa de um nome inventado, e o HTML fica cheio de apelidos que não dizem nada sobre o conteúdo.

No Svelte, o problema simplesmente não existe. O CSS escrito dentro do componente é compilado com um selo: o compilador acrescenta ao seletor uma classe que só aquele componente tem, e coloca a mesma classe nas tags do HTML. A regra continua sendo "todo h1", mas passa a significar "todo h1 deste arquivo".

Vale entender o tamanho da economia. Num site com trinta componentes, o CSS tradicional precisa de trinta nomes de classe únicos e de uma convenção que todos sigam. Quando alguém esquece a convenção, o estilo de um componente pinta o de outro, e o problema aparece longe de onde foi criado. Com escopo automático, o nome do arquivo já é o nome do escopo — e ninguém precisa combinar nada.

Na padariaNo componente
A placa da entrada, com o seu douradoO bloco <style> de App.svelte
O número da placa que a identificaO selo svelte-1n46o8q na classe
Pintar só a placa, não a loja todaO escopo do componente

2. O primeiro estilo escopado

Um componente com estilo é um arquivo com o HTML em cima e um bloco <style> embaixo:

<h1>Padaria da Ana</h1>
<p>Pão francês: R$ 0,90</p>

<style>
  h1 {
    color: #b8860b;
    font-family: system-ui, sans-serif;
  }
  p {
    margin: 0;
  }
</style>

Peça o CSS ao compilador e ele devolve os seletores com o selo, não como você escreveu:

h1.svelte-1n46o8q {
    color: #b8860b;
    font-family: system-ui, sans-serif;
  }
  p.svelte-1n46o8q {
    margin: 0;
  }

svelte-1n46o8q é o selo deste arquivo. Ele não foi escolhido por você, não aparece no seu código e não precisa ser lembrado. O compilador o gera a partir do nome do arquivo, e usa o mesmo valor em todos os seletores daquele componente.

Quando o projeto roda em modo de desenvolvimento, o selo aparece com outro formato (algo como s-XsEmFtvddWTw) porque o Vite injeta o CSS de um jeito diferente, pensado para trocar o estilo sem recarregar a página. No build, vale o formato svelte-… que você vê acima. Os dois funcionam igual: o que muda é o nome do selo, não a ideia.

A anatomia do seletor escopado

h1
o seletor que você escreveu. Continua sendo uma tag, uma classe ou um atributo — o que você quiser.
.svelte-1n46o8q
o selo acrescentado pelo compilador. Ele restringe a regra aos elementos deste componente.
{ … }
o bloco de declarações: cada linha é uma propriedade e um valor, terminada em ponto e vírgula.
#b8860b
um valor. Cores podem ser nome (goldenrod), hexadecimal (#b8860b) ou rgb(…).
<style>
o bloco do componente. Fica no fim do arquivo, depois do HTML.

O selo tem outra metade, que aparece no HTML. O compilador coloca a mesma classe nas tags que casam com alguma regra do componente:

O h1 sai como <h1 class="svelte-1n46o8q"> e o p sai como <p class="svelte-1n46o8q">. É esse par — seletor com selo no CSS, classe com selo no HTML — que faz o estilo valer só ali.

O selo depende do nome do arquivo

O mesmo CSS em App.svelte e em Cartao.svelte gera selos diferentes. Por isso as aulas deste guia dizem com qual nome de arquivo cada saída foi colhida: o valor do selo muda junto. Se o seu resultado tiver outro código depois de svelte-, não é erro — é outro nome de arquivo.

3. O selo só vai para quem casa

Uma consequência que surpreende: o Svelte não coloca a classe em todos os elementos do componente, só nos que alguma regra pode atingir. Se a sua única regra é sobre h1, o p fica sem classe nenhuma.

Isso importa quando você olha o HTML gerado e não encontra o selo: ele não é um enfeite global, é parte do seletor. Sem regra que case, sem classe.

Missão: o componente não tem estilo nenhum. Adicione um <style> que pinte só o h1 — o HTML gerado tem de sair com o selo no título e sem selo no parágrafo.

<h1>Padaria</h1>
<p>Pão</p>
<h1>Padaria</h1>
<p>Pão</p>

<style>
  h1 { color: #b8860b; }
</style>

A caixa mostra o HTML gerado embaixo do componente. Antes da correção ele é <h1>Padaria</h1> <p>Pão</p>; depois, o h1 ganha class="svelte-n50uah". O valor do selo muda porque a caixa compila com o nome App.svelte — o mesmo nome de arquivo deste guia, mas sem a pasta src/.

4. :global(…): a porta de saída

De vez em quando você quer atingir algo fora do componente: o body, uma classe aplicada por uma biblioteca, o html inteiro. Para isso existe :global(…), que desliga o escopo naquele seletor:

<h1>Padaria da Ana</h1>

<style>
  :global(body) {
    margin: 0;
    background: #fffdf5;
  }
  h1 {
    color: #b8860b;
  }
</style>
body {
    margin: 0;
    background: #fffdf5;
  }
  h1.svelte-1n46o8q {
    color: #b8860b;
  }

Repare na diferença: o body saiu sem selo, porque a regra é global de propósito; o h1 continua escopado. As duas regras convivem no mesmo bloco de estilo, cada uma com o seu alcance.

O custo do :global é o mesmo de qualquer porta aberta: a regra pode atingir qualquer elemento da página, inclusive de componentes que você nem conhece. Use para o que é realmente global — body, html, variáveis CSS na raiz — e não como atalho para "resolver" um seletor que não estava casando.

Um uso legítimo e comum é declarar as cores da padaria uma vez só, no componente que embrulha a aplicação: :global(:root) { --dourado: #b8860b; }. A partir daí, qualquer componente usa color: var(--dourado) sem precisar de :global — a variável viaja pela herança do CSS, que é global por natureza. Assim você abre uma porta em vez de deixar todas abertas.

Missão: a regra do parágrafo está escopada e o Svelte marca o p com o selo. Torne a regra global, para o HTML sair sem selo em nenhum elemento.

<h1>Padaria</h1>
<p>Pão</p>

<style>
  p { color: #b8860b; }
</style>
<h1>Padaria</h1>
<p>Pão</p>

<style>
  :global(p) { color: #b8860b; }
</style>

Sem o selo, a regra vale para todo parágrafo da página — inclusive os de fora do componente. É exatamente o que o :global promete, e é por isso que ele pede cuidado.

5. O seletor que não casa

Um erro silencioso: escrever uma regra para uma classe que não existe no HTML. O CSS compila, a classe fica sem efeito e a página não muda. O compilador avisa com o código css_unused_selector — a mensagem, na linha da regra, é "Unused CSS selector '.preco'" (a documentação fica em https://svelte.dev/e/css_unused_selector).

O CSS gerado mostra o que aconteceu: a regra não é aplicada, fica como comentário.

<p class="valor">R$ 0,90</p>

<style>
  .preco {
    color: #2e7d32;
  }
</style>
/* (unused) .preco {
    color: #2e7d32;
  }*/

(unused) quer dizer "não usada". Repare também que o HTML não ganhou selo: <p class="valor">R$ 0,90</p> sai igual ao que foi escrito, porque nenhuma regra casou. Um seletor que não casa não deixa o código mais lento — deixa a intenção perdida.

Missão: a regra fala de .preco, e o parágrafo tem class="valor". Faça o estilo valer para o preço — o HTML tem de sair com o selo junto da classe.

<p class="valor">R$ 0,90</p>

<style>
  .preco { color: green; }
</style>
<p class="valor">R$ 0,90</p>

<style>
  p { color: green; }
</style>

A solução troca a classe por um seletor de tag. Outra saída seria mudar o HTML para class="valor preco" — aí a regra casaria e o selo apareceria junto. As duas funcionam; escolha a que diz melhor o que você quer.

6. Descendentes e o :where(…)

Quando o seletor tem mais de um pedaço — "o parágrafo dentro do cartão" — o compilador precisa ser cuidadoso. Ele marca o ancestral e envolve o descendente num :where(…), que é uma forma de aplicar o selo sem aumentar a especificidade da regra:

<div class="cartao">
  <p>Pão francês</p>
</div>

<style>
  .cartao {
    padding: 8px;
  }
  .cartao p {
    margin: 0;
  }
</style>
.cartao.svelte-1n46o8q {
    padding: 8px;
  }
  .cartao.svelte-1n46o8q p:where(.svelte-1n46o8q) {
    margin: 0;
  }

O HTML correspondente sai com selo nos dois elementos: <div class="cartao svelte-1n46o8q"> e <p class="svelte-1n46o8q">. O :where() tem peso zero na conta de especificidade do CSS — ele marca sem brigar com as suas regras. É um detalhe que você não precisa escrever, mas que explica por que o CSS gerado parece diferente do seu.

Você escreveO compilador gera
h1h1.svelte-xxxx
.cartao.cartao.svelte-xxxx
.cartao p.cartao.svelte-xxxx p:where(.svelte-xxxx)
:global(body)body
.preco sem uso/* (unused) .preco { … }*/

7. Especificidade: quem ganha a briga

Quando duas regras pintam o mesmo elemento, o CSS decide pela especificidade: conta quantos seletores de tag, classe e id cada regra tem. O selo acrescentado pelo Svelte entra nessa conta como uma classe a mais, e é aí que mora uma surpresa: uma regra do componente fica mais "forte" do que uma regra global equivalente.

Isso é bom na maioria dos casos — o estilo do componente vence o estilo geral do site, que é o que você espera. Mas pode atrapalhar quando a intenção é justamente o contrário, e a solução é a de sempre em CSS: aumentar a especificidade da regra que deve vencer, não brigar com !important.

SituaçãoQuem vencePor quê
h1 global × h1 do componenteo do componenteo selo conta como classe
.cartao p × p.cartao po :where() não soma, mas a classe do cartão soma
:global(p) × p escopadoo escopadoo escopado tem o selo; o global não
estilo inline style="…"o inlineestilo no atributo vence seletor

O conselho prático: mantenha os seletores curtos. Se você precisar de três níveis para explicar o que quer pintar, provavelmente o componente está grande demais — dividir em dois componentes resolve a pintura e a leitura.

E evite !important. Ele resolve a briga de hoje e cria a de amanhã, porque só perde para outro !important. Quando o estilo não aplica, quase sempre a causa é uma classe escrita errada, um seletor que não casa ou uma regra global mais específica — três coisas que você consegue ver lendo o CSS gerado.

8. Rodando no computador da Ana

No servidor de desenvolvimento, o CSS do componente é injetado na página e o selo é outro formato (o Vite usa um nome diferente do build). Na hora de salvar o arquivo, o terminal mostra a atualização:

ana@notebook:~/loja$ npm run dev -- --port 5193

> loja@0.0.1 dev
> vite --port 5193

  VITE v7.3.8  ready in 510 ms

  ➜  Local:   http://localhost:5193/
  ➜  Network: use --host to expose
5:49:13 PM [vite] (client) hmr update /src/App.svelte?svelte&type=style&lang.css

A linha hmr update é o Vite avisando que trocou o CSS do componente sem recarregar a página. O número da porta aparece porque a 5173 estava ocupada nesta gravação: o endereço vem do terminal, nunca do código.

No build, o CSS de todos os componentes vai para um arquivo separado:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v7.3.8 building client environment for production...
transforming...
✓ 112 modules transformed.
rendering chunks...

dist/index.html                  0.32 kB │ gzip:  0.23 kB

dist/assets/index-uhv52wBK.js   36.00 kB │ gzip: 13.91 kB

O arquivo .css tem 0,03 kB porque o componente da Ana tem poucas regras. Num projeto grande, ele cresce — e como o nome tem hash, o navegador pode guardar em cache para sempre: se o CSS mudar, o nome muda junto.

Repare que o CSS saiu do JavaScript: o navegador baixa um arquivo de estilo e um de script. Isso é melhor do que injetar estilo por código, porque o navegador consegue aplicar o CSS antes de desenhar a página e evitar o piscar de conteúdo sem estilo. O selo viaja junto: as classes do HTML continuam batendo com os seletores do arquivo.

9. Quando dá errado

Três erros de compilação, todos de CSS malformado. Nenhum deles é sobre escopo: o compilador só consegue aplicar o selo se o CSS estiver válido.

Isso tem uma consequência prática: um erro de CSS derruba o componente inteiro, não só o estilo. O HTML deixa de ser gerado e a página fica em branco até você corrigir. Por isso vale escrever o bloco de estilo devagar, fechando cada regra antes de passar para a próxima — e desconfiar do editor quando ele "ajuda" demais com autocompletar.

1. Declaração sem valor. Faltou o valor depois dos dois-pontos:

<h1>Padaria</h1>

<style>
  h1 { color: ; }
</style>
Erro de compilação (linha 4, coluna 7): Declaration cannot be empty

"Declaração não pode ficar vazia". Toda propriedade precisa de um valor: color: #b8860b;, margin: 0;.

2. Chave sem fechar. O bloco de regra foi aberto e o arquivo terminou antes do fechamento:

<h1>Padaria</h1>

<style>
  h1 { color: red;
</style>
Erro de compilação (linha 5, coluna 8): Unexpected end of input

"Fim de entrada inesperado" quer dizer que algo ficou aberto. Conte as chaves: cada { precisa de um }.

3. Seletor com dois pontos. Um erro de digitação no seletor de classe:

<h1>Padaria</h1>

<style>
  h1..x { color: red; }
</style>
Erro de compilação (linha 4, coluna 5): Expected a valid CSS identifier

"Esperava um identificador CSS válido". Depois do ponto vem o nome da classe, sem outro ponto: .x. O compilador para na primeira coisa que não consegue interpretar.

A ideia final: o escopo é do arquivo, não do seletor. Você escreve CSS como escreveria numa folha de estilo, e o compilador cuida de não vazar. O único momento em que você precisa pensar nisso é quando quer vazar — e aí existe o :global, com o custo de abrir a porta.

Resumo

  • Escopo é o alcance de uma regra; no Svelte, o CSS do componente vale só para ele.
  • O compilador acrescenta um selo aos seletores (h1.svelte-xxxx) e às tags do HTML.
  • O selo vem do nome do arquivo: o mesmo CSS em outro arquivo gera outro código.
  • Só recebem a classe os elementos que alguma regra pode atingir.
  • :global(…) desliga o escopo naquele seletor e atinge a página inteira.
  • Seletor que não casa gera o aviso css_unused_selector e aparece como /* (unused) … */ no CSS.
  • Seletores descendentes viram .cartao.svelte-xxxx p:where(.svelte-xxxx).
  • O selo conta como classe na especificidade, então o estilo do componente vence o global equivalente.
  • No build, o CSS de todos os componentes vira um arquivo com hash no nome.
  • Erros desta aula: declaração vazia, chave sem fechar e seletor inválido.
