Svelte · A Estrutura do Projeto

A Ana organiza a cozinha por estações: a bancada de farinha, a geladeira, o forno, a louça. Se o açúcar ficar no armário da louça, ela perde tempo toda vez que faz um bolo. Um projeto Svelte funciona igual: cada arquivo tem um lugar, e quem sabe o lugar não fica caçando nada. Nesta aula você abre a pasta da Ana, vê o que existe dentro, entende por que cada coisa está ali e aprende o que acontece quando um arquivo vai para o lugar errado.

Você vai aprender
  • As pastas de um projeto Svelte e o papel de cada uma.
  • O que é escrito por você e o que é gerado pelo npm e pelo Vite.
  • Por que o componente não é uma página HTML completa.
  • O caminho que vai de index.html até o componente raiz.
  • Como importar um componente e por que o caminho começa com ./.
  • Onde colocar imagens e por que existem duas respostas possíveis.
  • O que o build cria em dist/ e por que o nome do arquivo tem hash.
  • Por que node_modules/ nunca vai para o repositório.
  • Os erros reais de estrutura: dois scripts, dois estilos e um bloco sem fechar.

1. A ideia: cada coisa na sua estação

Na cozinha da Ana existe uma regra simples: o que é usado junto fica junto. A farinha perto da balança, a forma perto do forno, o caderno de pedidos perto do telefone. Ninguém precisa decorar onde está o quê: o lugar conta a história do uso. Um projeto de software tem a mesma lógica, com uma diferença: os lugares têm nomes fixos, combinados entre todas as ferramentas.

Esses nomes fixos existem porque três programas diferentes precisam concordar sobre onde estão as coisas. O npm espera o package.json na raiz. O Vite espera o index.html na raiz e procura o código em src/. O compilador do Svelte compila os arquivos .svelte que o Vite encontrar. Se você renomear a pasta src para codigo, nada funciona até você avisar cada ferramenta — e avisar cada uma é trabalho que não vale a pena.

Por isso a estrutura é conservadora. Você não desenha a sua: usa a que o ecossistema já conhece e reserva a criatividade para dentro dela — novos componentes, novas pastas dentro de src/. É como a cozinha: a posição do forno é do apartamento, mas a Ana decide onde ficam as forminhas.

2. A árvore do projeto

A pasta do projeto tem sete entradas na raiz. O comando abaixo mostra o que existe dentro de src, que é a parte escrita por você:

ana@notebook:~/loja$ find src
src
src/App.svelte
src/main.js

Duas coisas: um componente e um arquivo JavaScript. O resto do projeto é configuração e material gerado. A tabela abaixo é o mapa completo, com a origem de cada peça.

CaminhoO que éQuem cria
src/o seu código: componentes e o ponto de entradavocê
index.htmla página que o navegador carrega primeirovocê
package.jsonpacotes e atalhos de comandovocê
vite.config.jsliga o plugin do Svelte no Vitevocê
svelte.config.jsopções do compiladorvocê
node_modules/os pacotes baixadoso npm
dist/o site pronto, depois do buildo Vite

Existe uma razão prática para os arquivos de configuração ficarem na raiz e não dentro de src: as ferramentas os procuram pelo nome, a partir da pasta onde você rodou o comando. O Vite lê vite.config.js antes de qualquer outra coisa; o npm lê package.json antes de instalar. Se você mover um deles para dentro de src, o comando continua rodando — só que ignorando a sua configuração, o que é pior do que dar erro, porque o sintoma aparece longe da causa.

Guarde a coluna da direita: ela decide o que você pode apagar. node_modules e dist são resultado de comando; se sumirem, um comando os recria. Já src é o contrário: se sumir, o trabalho foi embora. Quem entende essa diferença nunca tem medo de apagar a pasta errada — e nunca perde código por acidente.

3. src/: onde mora o seu código

Dentro de src ficam os componentes. Um componente é um arquivo .svelte com nome em maiúscula. Este é o cartão de preço da padaria, um segundo componente que a Ana criou para não repetir HTML:

<script>
  let titulo = 'Pão francês';
  let preco = $state(0.9);
</script>

<article>
  <h2>{titulo}</h2>
  <p>R$ {preco.toFixed(2)}</p>
</article>
<article><h2>Pão francês</h2> <p>R$ 0.90</p></article>

Repare no article em volta de tudo. Componentes podem ter mais de um elemento no nível de cima, mas agrupar em uma tag só costuma ser melhor: o componente vira uma caixa previsível, que o CSS pode posicionar sem surpresa. O article foi escolhido porque o conteúdo faz sentido sozinho, como uma ficha de produto.

Quando o projeto cresce, src ganha subpastas. Duas convenções resolvem quase todos os casos: src/lib/ para componentes reaproveitáveis e src/routes/ só quando você usar SvelteKit, no Nível 3. Antes disso, uma pasta src/lib com os componentes que não são a tela principal já deixa o projeto arrumado.

4. O componente não é uma página

Este é o mal-entendido mais comum de quem vem do HTML. Um arquivo .svelte não é uma página completa: não tem <html>, não tem <head>, não tem <!doctype>. Ele é um pedaço de tela que será montado dentro de uma página. Se você colar um documento inteiro num componente, o compilador não reclama — e o resultado é estranho:

<!doctype html>
<html lang="pt-BR">
<body>
  <h1>Padaria da Ana</h1>
</body>
</html>
<!doctype html=""/> <html lang="pt-BR"><body><h1>Padaria da Ana</h1></body></html>

O <!doctype> virou um elemento com um atributo vazio, e o <html> foi colocado dentro do corpo da página que já existia — um HTML dentro do outro. Nada disso é o que você queria. A página de verdade é o index.html, na raiz; o componente é só o miolo.

Essa separação tem um custo e um ganho. O custo é que você precisa de dois arquivos para ver a primeira tela. O ganho é que o mesmo componente pode ser usado em páginas diferentes — ou várias vezes na mesma página — sem repetir head, fonte e título. A Ana escreve o cartão de preço uma vez e o usa em três lugares.

Missão: o componente tem dois blocos <style> e o compilador recusa. Junte as regras num bloco só, mantendo o título "Bem-vinda, Ana" e o parágrafo "pão quentinho".

<script>
  let nome = $state('Ana');
</script>

<h1>Bem-vinda, {nome}</h1>

<style>
  h1 { color: #2e7d32; }
</style>

<style>
  p { padding: 4px; }
</style>

<p>pão quentinho</p>
<script>
  let nome = $state('Ana');
</script>

<h1>Bem-vinda, {nome}</h1>
<p>pão quentinho</p>

<style>
  h1 { color: #2e7d32; }
  p { padding: 4px; }
</style>

A regra é a mesma para os três blocos: no máximo um <script>, no máximo um <style>, e todo o HTML que você quiser. O compilador precisa de uma ordem única para executar; dois blocos do mesmo tipo deixariam essa ordem ambígua.

5. O caminho do index.html até o componente

Quando o navegador abre http://localhost:5173/, ele recebe o index.html. Esse arquivo tem uma div vazia com identificador app e uma tag script que carrega /src/main.js. O main.js é o ponto de entrada: ele importa o componente raiz e manda montá-lo dentro daquela div.

import { mount } from 'svelte';
import App from './App.svelte';

const app = mount(App, { target: document.getElementById('app') });

export default app;
import { mount } from 'svelte'
traz a função mount, que cria o componente dentro de um elemento da página. É o único lugar do projeto em que o Svelte é chamado diretamente.
import App from './App.svelte'
importa o componente raiz. O ./ significa "na mesma pasta deste arquivo"; sem ele, o Node procuraria um pacote instalado.
document.getElementById('app')
acha a div do index.html. Se o identificador não bater, a montagem falha e a página fica vazia.
export default app
exporta o resultado da montagem. O Vite usa isso para recarregar o componente durante o desenvolvimento.

Esse arquivo é o único que "conversa" com o HTML. Todo o resto do projeto são componentes que se importam entre si. Se um dia a página abrir em branco, a investigação começa aqui: o index.html tem a div#app? O main.js está sendo carregado? O caminho do import do App está certo?

6. Importar um componente de outro arquivo

Para usar o cartão dentro do componente principal, você importa o arquivo e escreve a tag com o mesmo nome, em maiúscula:

<script>
  import Cartao from './Cartao.svelte';

  let nome = $state('Ana');
</script>

<h1>Padaria da {nome}</h1>
<Cartao />

Três detalhes que quebram o iniciante. Primeiro: o caminho ./Cartao.svelte tem a extensão e começa com ./ — sem isso, o Vite procura um pacote chamado Cartao.svelte no node_modules e não acha. Segundo: o nome do import (Cartao) é o nome que você usa na tag; manter igual ao arquivo é convenção, não obrigação. Terceiro: a tag é maiúscula. <cartao /> seria uma tag desconhecida e apareceria literalmente na tela.

O App.svelte acima não pode ser compilado sozinho: ele depende de outro arquivo. É por isso que os exemplos de duas peças neste guia aparecem em caixas separadas ou em arquivos completos. A caixa "Experimente" compila um componente por vez — bom lembrete de que importar é uma ligação entre arquivos, não um recurso de texto.

Missão: o bloco <script> foi escrito dentro da div e a caixa mostra um erro. Mova o script para o topo do arquivo, que é o lugar dele.

<div>
  <script>
    let nome = 'Ana';
  </script>
  <h1>Pão fresquinho, {nome}</h1>
</div>
<script>
  let nome = 'Ana';
</script>

<div>
  <h1>Pão fresquinho, {nome}</h1>
</div>

O compilador só reconhece o <script> de nível superior — aquele que fica solto no arquivo. Dentro de uma div, ele é apenas uma tag de HTML que o navegador ignora, e a variável nunca é declarada.

7. Imagens e arquivos estáticos

O projeto da Ana ainda não tem imagem nenhuma. Quando tiver, há dois lugares possíveis, e a escolha muda o resultado. O primeiro é public/, na raiz: tudo o que está ali é copiado para o build sem passar pelo compilador e fica acessível pelo caminho absoluto, como /favicon.svg. Bom para favicon, ícone de aplicativo e arquivos que precisam de nome fixo.

O segundo é src/assets/: arquivos importados dentro do código, como import foto from './assets/pao.png'. O Vite processa esses arquivos, otimiza quando pode e, no build, troca o nome por um com hash. Você ganha cache longo e não precisa se preocupar com colisão de nome; perde o endereço fixo.

Sobre os nomes dos arquivos de imagem, duas convenções evitam dor de cabeça: tudo em minúsculas, sem acento e sem espaço. pao-frances.png funciona em qualquer servidor; Pão Francês (1).png precisa de conversão para texto na URL e quebra em alguns sistemas. O mesmo vale para componentes: CartaoDePreco.svelte é melhor que cartão de preço.svelte, que o import não consegue escrever sem escapar.

A regra prática: imagem usada dentro de um componente e que pode mudar de nome, src/assets; arquivo que precisa ser buscado por um caminho conhecido (favicon, robots.txt, imagem de compartilhamento), public. Se você não tem certeza, comece por src/assets — é o caminho que o build resolve sozinho.

8. dist/: o resultado do build

Depois de npm run build, aparece a pasta dist. Ela é o site inteiro, pronto para subir em qualquer servidor de arquivos. O conteúdo, de verdade:

ana@notebook:~/loja$ ls dist
assets
index.html
ana@notebook:~/loja$ ls dist/assets
index-D4Bgwu4I.js
ana@notebook:~/loja$ du -sh dist
48K	dist

Dois arquivos e 48 kB. O index.html é a página; o arquivo com hash é o JavaScript com todos os componentes compilados dentro. Se você tivesse uma imagem, ela estaria em assets também, com o nome trocado por um hash.

Aquele D4Bgwu4I não é enfeite: é a impressão digital do conteúdo. Mude uma letra no componente e o nome do arquivo muda. É o que permite dizer ao navegador "guarde este arquivo para sempre" sem o risco de ele mostrar uma versão velha depois de uma atualização. O custo é que o nome é feio e não dá para adivinhar — por isso ninguém digita esse caminho à mão.

A pasta dist é descartável: rodar o build de novo apaga e recria. Nunca edite um arquivo dentro dela; a próxima compilação sobrescreve. O mesmo vale para node_modules, que veremos a seguir.

9. node_modules/: a despensa

A pasta node_modules guarda todos os pacotes baixados, inclusive os que os pacotes usam. Por isso ela é grande:

ana@notebook:~/loja$ du -sh node_modules
31M	node_modules

Trinta e um megabytes para um projeto de dois arquivos. É normal. Cada pacote tem as suas dependências, e elas têm as suas; o npm achata tudo isso numa pasta só. Você nunca abre essa pasta para editar nada — a não ser para investigar um bug muito estranho, e mesmo assim com cuidado: a próxima instalação desfaz qualquer mudança.

O package-lock.json merece uma linha, porque ele é o que garante que a máquina do sobrinho instale exatamente o que a máquina da Ana instalou. Sem ele, o npm install olharia só as faixas do package.json e poderia trazer uma versão mais nova de uma dependência indireta — aquele pacote que ninguém declarou, mas que o Vite usa por baixo. Com ele, o npm segue o recibo. Versione os dois arquivos juntos e o projeto fica reproduzível.

Como ela é caríssima de versionar e totalmente reproduzível a partir da lista, ela fica fora do git. O arquivo que ensina o git a ignorá-la chama-se .gitignore e fica na raiz:

node_modules
dist

Duas linhas. A primeira impede que a despensa vá para o repositório; a segunda faz o mesmo com o resultado do build, que também é gerado. Quem clonar o projeto roda npm install e npm run build e chega no mesmo lugar. Essa é a beleza da separação entre fonte (o que você escreve) e artefato (o que as ferramentas geram).

10. Quando dá errado

Os três erros abaixo são de estrutura, não de lógica: o arquivo está com dois blocos do mesmo tipo ou com um bloco aberto. As mensagens saíram do compilador desta versão, copiadas como estão.

Erro 1 — dois blocos <script>

Acontece quando você cola um exemplo embaixo do outro. Um componente tem um script comum e, se precisar, um <script module>.

<script>
  let nome = 'Ana';
</script>

<script>
  let idade = 30;
</script>

<p>{nome} {idade}</p>
Erro de compilação (linha 5, coluna 0): A component can have a single top-level `<script>` element and/or a single top-level `<script module>` element

Junte as declarações no primeiro bloco e apague o segundo. A linha apontada é o começo do segundo script: o compilador aceita o primeiro e reclama do seguinte.

Erro 2 — bloco {#each} sem fechamento

O fechamento {/each} sumiu, e o compilador encontrou o </ul> enquanto ainda esperava o fim do bloco.

<script>
  let itens = ['pão', 'bolo'];
</script>

<ul>
  {#each itens as item}
    <li>{item}</li>
</ul>
Erro de compilação (linha 8, coluna 0): `</ul>` attempted to close an element that was not open

A mensagem fala do </ul>, mas o problema está uma linha antes: falta {/each}. Blocos que abrem com {# fecham com {/. Confira os pares antes de procurar em outro lugar.

Erro 3 — tag aberta e não fechada

Um <h1> sem </h1> deixa o compilador esperando o resto do arquivo.

<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}
Erro de compilação (linha 5, coluna 0): `<h1>` was left open

"Left open" quer dizer "ficou aberta". Note que a linha apontada é o fim do arquivo, não a linha da tag: o compilador só percebe que faltou fechar quando o arquivo acaba. A dica é fechar a tag na mesma hora em que você abre.

Missão: o componente tem um export default copiado do main.js, e o compilador recusa. Remova essa linha: quem exporta o componente é o próprio Svelte.

<script>
  export default {};
  let nome = $state('Ana');
</script>

<p>Pão quentinho, {nome}</p>
<script>
  let nome = $state('Ana');
</script>

<p>Pão quentinho, {nome}</p>

export default é coisa do main.js, que precisa entregar o resultado da montagem para o Vite. O componente não: o compilador gera o export sozinho, e um segundo export seria conflito.

Exercícios

1. Qual pasta contém o código que você escreve?

2. Por que node_modules não vai para o git?

3. O que o src/main.js faz?

Complete o código

import { } from 'svelte';
import App from './App.svelte';

const app = mount(App, { target: document.getElementById('app') });

// a função que coloca o componente dentro da página

Resumo

  • A estrutura é padrão: src/ tem o seu código, a raiz tem os arquivos de configuração.
  • src/main.js importa o componente raiz e chama mount() dentro da div#app do index.html.
  • Componente não é página: <!doctype> e <html> ficam no index.html.
  • Ao importar, use ./, a extensão .svelte e um nome em maiúscula na tag.
  • Imagens: src/assets quando o código importa, public quando o caminho precisa ser fixo.
  • dist/ é o site pronto, com nomes que carregam hash do conteúdo.
  • node_modules/ e dist/ são gerados: podem ser apagados e recriados por comando.
  • O .gitignore mantém fora do repositório o que é gerado.
  • Um componente tem no máximo um <script> e um <style>, e não tem export default.
