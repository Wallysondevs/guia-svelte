Svelte · createEventDispatcher

A padaria da Ana ganhou um interfone. Quando o pão sai do forno, a cozinha aperta o botão e o balcão ouve o recado — sem que ninguém precise atravessar a loja. No Svelte, esse interfone tem nome: createEventDispatcher. É a API clássica de eventos de componente, ainda funcionando no Svelte 5, e é o que você vai encontrar em todo projeto escrito antes das runas. Esta aula mostra como ela funciona, o que ela carrega e por que o caminho novo passa por funções.

Você vai aprender

  • Como o pai escuta com on:pedir.
  • O que é evento.detail e o que ele carrega.
  • Por que o dispatcher precisa ser criado na inicialização do componente.
  • A diferença entre evento de componente e evento do DOM.
  • Por que o Svelte 5 recomenda propriedades de função no lugar do dispatcher.
  • Como migrar um componente antigo sem quebrar nada.
  • Os três erros reais desta aula, com a mensagem copiada do compilador.

1. A ideia: o interfone da cozinha

O interfone tem três peças. O aparelho do lado de dentro, que a cozinha instala uma vez. O botão, que dispara um recado com um nome — "saiu pão". E o aparelho do balcão, que escuta aquele nome. Se o balcão não tiver aparelho, o recado sai e ninguém ouve; nada quebra, nada acontece.

O dispatcher é o aparelho de dentro. Ele é criado com createEventDispatcher() e devolve uma função, que costuma se chamar dispatch. Você chama essa função com o nome do evento e, opcionalmente, um dado para levar. O pai escuta pelo nome do evento e recebe um objeto comum do navegador — um CustomEvent — com o dado dentro da propriedade detail.

Há uma diferença importante entre evento de componente e evento do DOM, e ela confunde no começo. O evento do DOM já existe: o navegador dispara click quando alguém clica, e o componente só escuta. O evento de componente é inventado por você: o navegador não sabe o que é "pedir", e ninguém dispara nada se o seu código não chamar dispatch. Por isso o dispatcher precisa ser criado e usado de propósito, enquanto o onclick funciona sozinho.

Repare que o nome do evento é texto. Isso significa que ele não é verificado pelo compilador: se o filho dispara 'pedir' e o pai escuta 'pedido', o recado sai e ninguém ouve, sem uma única mensagem. É a fragilidade central dessa API, e uma das razões pelas quais o Svelte 5 prefere funções, que pelo menos erram na hora.

2. O filho que dispara

O componente abaixo é o filho da padaria, agora com dispatcher. Ele cria o aparelho no topo do script e dispara no clique.

<script>
  import { createEventDispatcher } from 'svelte';

  const dispatch = createEventDispatcher();
  let sabor = $state('pão');

  function pedir() {
    dispatch('pedir', sabor);
  }
</script>

<button onclick={pedir}>pedir {sabor}</button>
<button>pedir pão</button>

O HTML não tem vestígio de evento: o dispatcher não escreve nada na marcação. Ele só cria um canal em memória que o pai, se estiver montado em volta, pode ligar. Quem olha o HTML vê apenas um botão.

A anatomia do dispatcher

import { createEventDispatcher } from 'svelte'
vem da biblioteca. No Svelte 5 é uma API mantida por compatibilidade, e continua no módulo principal.
const dispatch = createEventDispatcher()
cria a função de disparo. Precisa acontecer durante a inicialização do componente: chamar depois, dentro de um clique, é erro.
dispatch('pedir', sabor)
o primeiro argumento é o nome do evento; o segundo é o dado, que chega ao pai em evento.detail. O terceiro, opcional, aceita { cancelable: true }.
return true
o retorno de dispatch é false se algum ouvinte chamou preventDefault. Serve para o filho saber que o pedido foi recusado.

O segundo argumento é uma escolha de projeto, e não um detalhe. Disparar dispatch('pedir', sabor) manda uma string; disparar dispatch('pedir', { sabor, quantidade }) manda um pacote. O pai lê evento.detail.sabor. Como no caso das funções, o pacote envelhece melhor: acrescentar um campo não obriga a mudar quem escuta.

3. O pai que escuta

Do lado de fora, a escuta usa a sintaxe antiga com dois-pontos, que o Svelte 5 ainda aceita para componentes:

<script>
  import Filho from './Filho.svelte';

  let pedidos = $state([]);
</script>

<Filho on:pedir={(evento) => (pedidos = [...pedidos, evento.detail])} />

{#each pedidos as p}
  <p>{p}</p>
{:else}
  <p>nenhum pedido</p>
{/each}

O handler recebe um CustomEvent, e o dado está em evento.detail. A lista começa vazia e cresce a cada clique no botão do filho — o filho não sabe que existe lista, e o pai não sabe que existe botão.

Uma descoberta real, que surpreende quem espera uma mensagem de aviso: neste compilador, on:pedir num componente não gera aviso nenhum. O arquivo compila em silêncio e funciona. Já on:click num elemento do DOM emite o aviso event_directive_deprecated, recomendando o atributo onclick. Ou seja: a API antiga de componente não avisa que está antiga — mais um motivo para conhecer as duas e escolher com consciência.

O Svelte 5 tem duas formas de o filho avisar o pai. As duas funcionam; uma é a recomendada hoje.

Outro ponto que só aparece em projeto grande: o dispatcher não deixa rastro de quem escuta. Ao ler o filho, você não tem como saber se algum pai usa aquele evento, nem com que dado. Com propriedades de função, o contrato está escrito na desestruturação do $props(), e uma busca pelo nome acha todos os usos. Manutenção é, na maior parte, leitura de código alheio.

A vantagem decisiva da função é o erro na hora certa. Com dispatcher, um nome trocado produz silêncio; com propriedade, o componente que chama uma função inexistente quebra imediatamente e mostra a linha. Erro cedo custa menos que erro silencioso.

Há um caso em que o dispatcher ainda ganha: quando o componente é usado por código que não é Svelte, ou quando o projeto inteiro usa a API antiga e a consistência vale mais que a novidade. Num projeto novo, escrito com runas, o guia recomenda funções.

5. Experimente: o dispatcher que não existe

A caixa mostra o clique chamando dispatch sem que ninguém o tenha criado. O componente quebra e a lista não registra nada.

Missão: crie o dispatcher no topo do script com createEventDispatcher() para o clique conseguir disparar e registrar o pedido.

<script>
  let registro = $state([]);
  let sabor = $state('pão');

  function pedir() {
    dispatch('pedir', sabor);
    registro = [...registro, sabor];
  }
</script>

<button onclick={pedir}>pedir</button>

Se você quiser ver o recado sendo ouvido de verdade, o caminho tem dois arquivos: um filho com o dispatcher e um pai com on:pedir. Este guia não coloca esse par numa caixa porque a caixa compila um arquivo por vez. No projeto real, os dois convivem na mesma pasta e o build junta tudo, como o terminal da seção 10 mostra.

A caixa roda um arquivo só, então não há pai escutando: o recado sai e ninguém ouve. O que você vê é o registro interno, que prova que a função existia e foi chamada sem erro. É o suficiente para aprender a peça que costuma faltar.

6. O que chega ao pai: detail

O handler do pai sempre recebe um objeto de evento, mesmo quando o filho não manda dado nenhum. Confundir o evento com o dado é o tropeço mais frequente — e o sintoma é uma lista cheia de [object CustomEvent].

Missão: o handler guarda o evento inteiro. Faça ele guardar o dado que o filho mandou, em evento.detail.

<script>
  let ultimo = $state('—');

  function aoPedir(evento) {
    ultimo = String(evento);
  }
</script>

<button onclick={() => aoPedir(new CustomEvent('pedir', { detail: 'pão' }))}>simular</button>
<p>último: {ultimo}</p>
<script>
  let ultimo = $state('—');

  function aoPedir(evento) {
    ultimo = evento.detail;
  }
</script>

<button onclick={() => aoPedir(new CustomEvent('pedir', { detail: 'pão' }))}>simular</button>
<p>último: {ultimo}</p>

O botão cria um CustomEvent à mão, com detail: 'pão' — exatamente o que o dispatcher faria. Assim você testa o handler sem precisar de um componente pai. É um bom hábito: handlers que recebem evento podem ser exercitados com eventos fabricados.

7. O dispatcher nasce na inicialização

O createEventDispatcher depende do contexto do componente, que só existe enquanto ele está sendo criado. Chamar dentro de um clique é chamar depois que esse contexto se foi.

Missão: o dispatcher está sendo criado dentro do clique e estoura. Crie-o no topo do script, uma vez, e use a mesma função no clique.

<script>
  import { createEventDispatcher } from 'svelte';
  let registro = $state([]);

  function pedir() {
    const dispatch = createEventDispatcher();
    dispatch('pedir', 'pão');
    registro = [...registro, 'pão'];
  }
</script>

<button onclick={pedir}>pedir</button>
<p>registro: {registro.join(', ') || 'vazio'}</p>

Existe uma terceira armadilha, mais sutil: disparar dentro de um $effect que reage ao próprio estado. O efeito roda, dispara, o pai muda uma propriedade, o filho reage e dispara de novo — e o ciclo só termina quando alguém para. Se o disparo depender de uma mudança de estado, proteja com uma comparação do valor anterior ou mova o disparo para o evento que causou a mudança.

Vale entender o porquê, e não só a regra. O dispatcher guarda uma referência ao componente que o criou, porque precisa saber quais ouvintes procurar. Durante um clique, o componente já está montado e a criação terminou — não há a quem associar o aparelho. Criar uma vez, no topo, é a única forma que faz sentido.

8. Migrando sem quebrar

Se o projeto da Ana já usa dispatcher e você quer adotar funções, o caminho seguro é aceitar as duas formas por um tempo: o filho declara a propriedade de função e, se ela não vier, dispara o evento antigo.

<script>
  import { createEventDispatcher } from 'svelte';

  const dispatch = createEventDispatcher();
  let { aoPedir } = $props();
  let sabor = $state('pão');

  function pedir() {
    if (aoPedir) {
      aoPedir(sabor);
    } else {
      dispatch('pedir', sabor);
    }
  }
</script>

<button onclick={pedir}>pedir {sabor}</button>
<button>pedir pão</button>

O pai novo passa aoPedir; o pai antigo continua com on:pedir. Quando todos os pais migrarem, você apaga o dispatcher e a importação. Essa transição em duas etapas é mais segura que trocar tudo de uma vez num projeto com muitas telas.

9. Escolhendo o que sobe

Nem toda mudança interna merece virar aviso. O filho que muda o próprio texto de um campo não precisa contar ao pai a cada letra digitada; o pai só quer saber quando o formulário foi enviado. A regra é a do interfone: só se aperta o botão quando o recado interessa a alguém do outro lado.

Na prática, isso significa escolher poucos eventos e com nomes de fato — pedir, cancelar, finalizar. Nomes vagos como mudou ou atualizou obrigam o pai a inspecionar detail para descobrir o que aconteceu, e voltam a acoplar os dois componentes.

Quando o aviso carrega vários campos, o pacote de detail deve ser pequeno e previsível: identificadores e valores simples, sem objetos do DOM. Um CustomEvent que carrega o elemento clicado é difícil de testar e mantém referências vivas na memória. Mande o que o pai precisa para decidir, e nada mais.

Uma nota sobre o tempo de vida do aparelho: o dispatcher criado no topo do script pertence àquela instância do componente. Dois filhos montados na mesma tela têm dois aparelhos independentes, e o pai pode escutar o mesmo nome nos dois, recebendo recados separados. Não existe um canal global — o que existe é um aparelho por instância, ligado na hora da montagem e desligado quando o componente sai.

O build não distingue dispatcher de função: os dois viram JavaScript comum. O tamanho muda pouco, mas o caminho de eventos do runtime continua no pacote enquanto houver um componente usando dispatcher.

11. Quando dá errado

As três mensagens abaixo saíram da execução real dos componentes quebrados.

Erro 1 — $on, a API que saiu do Svelte

Quem lê código antigo encontra $on para escutar eventos. No Svelte 5, o cifrão seguido de on é tratado como runa, e o compilador recusa.

<script>
  import { createEventDispatcher } from 'svelte';
  const dispatch = createEventDispatcher();
  const parar = $on('pedir', () => {});
</script>

<p>oi</p>
Erro de compilação (linha 4, coluna 16): `$on` is an illegal variable name. To reference a global variable called `$on`, use `globalThis.$on`

A mensagem é técnica, mas o diagnóstico é simples: não existe $on no Svelte 5. Escutar evento de componente é trabalho do pai, com on:pedir ou com uma propriedade de função.

Erro 2 — createEventDispatcher sem import

A função não é global: precisa vir de 'svelte'. Sem a linha de importação, o componente compila e falha ao executar.

<script>
  const dispatch = createEventDispatcher();
  let sabor = $state('pão');
</script>

<button onclick={() => dispatch('pedir', sabor)}>pedir</button>
Erro ao renderizar: createEventDispatcher is not defined

Como sempre, o nome citado na mensagem é a pista: falta import { createEventDispatcher } from 'svelte'.

Erro 3 — disparar sem criar o dispatcher

Aqui o nome dispatch aparece solto no código. Compila, porque o JavaScript aceita um nome livre no script, e quebra na hora de renderizar.

<script>
  let sabor = $state('pão');

  dispatch('pedir', sabor);
</script>

<p>pedido: {sabor}</p>
Erro ao renderizar: dispatch is not defined

A correção é criar a função antes de usá-la: const dispatch = createEventDispatcher(). E, se o disparo estiver no corpo do script, mover para um evento — disparar durante o desenho não é aviso, é parte da renderização.

Exercícios

1. Onde o dispatcher deve ser criado?

2. Onde o pai encontra o dado enviado por dispatch('pedir', sabor)?

3. Por que o Svelte 5 recomenda propriedades de função em vez de dispatcher?

Complete o código

import { createEventDispatcher } from 'svelte';
 

function pedir() {
  dispatch('pedir', 'pão');
}

Resumo

  • createEventDispatcher() cria a função de disparo e deve rodar na inicialização.
  • dispatch('nome', dado) envia o dado em evento.detail.
  • O pai escuta com on:pedir={fn}, a sintaxe antiga ainda aceita.
  • Sem ouvinte, o disparo não faz nada e não gera erro.
  • O nome do evento é texto: trocar uma letra quebra em silêncio.
  • on:pedir em componente não emite aviso de depreciação; on:click em elemento emite.
  • A forma recomendada no Svelte 5 é passar uma função como propriedade.
  • A migração segura aceita as duas formas por um tempo.
  • Os erros desta aula: $on inexistente, import ausente e dispatch não criado.
