SvelteKit · Form Actions

A Ana anota encomenda em papel porque o papel nunca cai. O formulário da web tem o mesmo valor: funciona antes de qualquer JavaScript carregar. No SvelteKit, quem recebe o formulário é uma action — uma função no +page.server.js que lê os campos, confere, grava e responde. O navegador envia, o servidor decide, a página volta com a resposta na mão. Sem mágica, sem biblioteca, sem depender do navegador moderno.

Você vai aprender
  • O que é uma form action e onde ela mora.
  • Como o <form method="POST"> aponta para a action.
  • Como ler os campos com request.formData().
  • Como recusar um envio com fail(400, { … }) e mostrar a mensagem.
  • Como redirecionar depois de gravar, com redirect(303, …).
  • O que é o prop form e quando ele vale null.
  • Actions nomeadas com ?/limpar e a regra do default.
  • O que o servidor responde em cada caso: 200, 400, 303, 404 e 415.
  • Três erros reais, com o status que cada um devolve.
  • Como testar um formulário inteiro com curl, sem clicar.

1. A ideia: papel que nunca cai

Formulário é a parte do site em que a pessoa fala com o servidor. Ela escreve o nome, escolhe o sabor, clica em "anotar". Para isso funcionar, alguém precisa receber esses campos e decidir o que fazer. Numa página Svelte comum, esse alguém é o seu JavaScript, no onclick. No SvelteKit existe uma opção melhor: o servidor recebe.

Receber no servidor tem três vantagens que aparecem no primeiro dia de uso. Primeira: funciona sem JavaScript, então funciona em navegador antigo, em rede ruim e quando o script falha. Segunda: a validação fica onde ninguém pode burlar — no servidor. Terceira: a gravação acontece perto do banco, sem ida e volta extra.

Chama-se form action porque o alvo do formulário é uma ação nomeada. O HTML envia um POST para a própria página, com um sufixo dizendo qual ação executar: ?/anotar. O SvelteKit olha o nome, chama a função correspondente e monta a resposta.

2. A action no +page.server.js

A rota /encomenda tem dois trabalhos: mostrar a fila e receber um pedido novo. O primeiro é load; o segundo é actions. Os dois convivem no mesmo arquivo, em exports diferentes:

import { fail, redirect } from '@sveltejs/kit';
import { listar, criar } from '#lib/pedidos.js';

export function load() {
	return { pedidos: listar() };
}

export const actions = {
	anotar: async ({ request }) => {
		const dados = await request.formData();
		const cliente = dados.get('cliente')?.trim();
		const sabor = dados.get('sabor');

		if (!cliente) {
			return fail(400, { cliente, falta: 'escreva o nome de quem pediu' });
		}

		criar(cliente, sabor);
		return { ok: true, cliente };
	},

	limpar: async () => {
		redirect(303, '/encomenda?limpo=1');
	}
};
export const actions
um objeto em que cada chave é o nome de uma ação. Os nomes viram o sufixo do formulário: ?/anotar, ?/limpar.
async ({ request })
o evento, como no load. Aqui o que importa é request, com o corpo do formulário.
await request.formData()
lê os campos e devolve algo parecido com um objeto de formulário. dados.get('cliente') pega o valor do campo com name="cliente".
?.trim()
encadeamento opcional mais trim: se o campo não vier, não estoura; se vier, tira os espaços das pontas. Campo com só espaços deve contar como vazio.
return fail(400, { … })
recusa o envio com status 400 e um objeto que a página recebe. O return é obrigatório: sem ele, o SvelteKit não sabe que houve falha.
return { ok: true }
sucesso. O status padrão é 200 e a página redesenha com esse objeto no prop form.
redirect(303, '/…')
interrompe a action e manda o navegador para outro endereço. O 303 é o código certo depois de um POST.

O evento.preventDefault() impede o envio de verdade e deixa o JavaScript cuidar de tudo. É o jeito antigo, e ele tem um custo que o SvelteKit resolve: sem JavaScript, esse formulário não faz nada. Na action de verdade, o preventDefault não existe — quem decide é o servidor.

3. A saída real de um envio

Testar formulário com curl é mais simples do que parece: o navegador manda um POST com os campos separados por &, no formato de formulário. O -d faz esse papel.

ana@notebook:~/loja$ curl -s -X POST -H 'accept: text/html' -d 'cliente=Caio&sabor=frango' 'localhost:5173/encomenda?/anotar' | grep -o '<p class="ok">[^<]*</p>'
<p class="ok">Anotado para Caio.</p>

O -H 'accept: text/html' é o detalhe que engana. Sem ele, o curl recebe JSON — o mesmo JSON que o use:enhance usa no navegador. Com ele, o SvelteKit entende que o cliente quer uma página e devolve HTML completo, com a mensagem dentro. O status é 200, porque o envio deu certo.

Quando a validação recusa, o status muda para 400 e a mensagem vem no lugar da confirmação:

ana@notebook:~/loja$ curl -s -X POST -H 'accept: text/html' -d 'cliente=' 'localhost:5173/encomenda?/anotar' | grep -o '<p class="erro">[^<]*</p>'
<p class="erro">escreva o nome de quem pediu</p>
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'accept: text/html' -d 'cliente=' 'localhost:5173/encomenda?/anotar'
400

O 400 é parte da resposta, não um acidente: a action chamou fail(400, …) e o SvelteKit repassou o status. Um formulário que devolve 500 quando falta um campo está dizendo a coisa errada — o servidor não quebrou, o pedido é que veio incompleto.

<script>
	const form = { falta: 'escreva o nome de quem pediu' };
</script>

{#if form?.falta}
	<p class="erro">{form.falta}</p>
{:else}
	<p>tudo certo</p>
{/if}
<p class="erro">escreva o nome de quem pediu</p>

O componente acima isola a decisão do que mostrar. O compilador gerou exatamente um parágrafo, com a classe de erro e o texto do fail. No projeto, o mesmo trecho roda dentro da página e o form vem do servidor em vez de estar escrito no script.

Missão: com o campo vazio, o envio deve mostrar o recado de validação. Faça aparecer escreva o nome de quem pediu.

		evento.preventDefault();
		aviso = cliente ? 'anotado' : 'anotado';
	}
</script>

	<button>anotar</button>
</form>
<p>{aviso}</p>

Aqui a validação está no navegador, que é onde ela não basta: qualquer pessoa pode desligar o JavaScript e enviar o formulário mesmo assim. No projeto, a mesma conferência existe duas vezes — no campo, para avisar rápido, e na action, para valer de verdade. Regra sem exceção: validação que protege dado mora no servidor.

4. Action nomeada e o 303

O segundo formulário da página aponta para ?/limpar. Aquela action não devolve dado: ela chama redirect(303, '/encomenda?limpo=1') e o navegador vai para o endereço novo. O 303 é o código certo aqui — diz "terminei o POST, agora pegue o resultado com um GET".

ana@notebook:~/loja$ curl -s -i -X POST -H 'accept: text/html' -d '' 'localhost:5173/encomenda?/limpar' | grep -i '^HTTP/\|^location'
HTTP/1.1 303 See Other
location: /encomenda?limpo=1

O -d '' não é enfeite: sem corpo e sem content-type, o SvelteKit recusa o POST com 415. Um navegador sempre manda o cabeçalho; o curl, não. Se você esquecer, o erro não é do seu código.

Se você devolvesse 200 depois de gravar, o botão "atualizar" do navegador reenviaria o formulário e gravaria duas vezes. O 303 resolve isso: depois dele, a página atual é um GET, e atualizar só busca de novo. É por isso que todo formulário que grava termina em redirecionamento.

redirect(303, '/x')303nada: o navegador vai para /x

O {:else} não é obrigatório, mas evita a página muda. Sem ele, uma renderização sem envio não mostra nada — o que é correto e, ao mesmo tempo, deixa o leitor sem saber se o formulário existe. Uma mensagem neutra resolve.

5. fail() ou error()?

As duas funções recusam. A diferença está no que acontece com a página. fail() volta para o formulário, com os dados que você mandou, e mantém a pessoa no lugar onde ela estava. error() troca a página pela tela de erro e perde o formulário.

Use fail() quando o problema é do preenchimento: campo vazio, e-mail sem arroba, quantidade negativa. É conserto rápido, e a pessoa deve poder corrigir ali mesmo. Use error() quando o problema é de permissão ou de recurso: não existe o pedido, você não é o dono, o servidor está fora. Aí não adianta mostrar o formulário de novo.

limpar: async ({ locals }) => {
	if (!locals.dono) {
		error(403, 'só a Ana pode limpar a fila');
	}

	redirect(303, '/encomenda?limpo=1');
}

Repare que o error() é chamado sem return. Ele interrompe a execução lançando um erro especial, então a linha seguinte nunca roda — exatamente como o redirect no primeiro exemplo. Se você escrever return error(...), funciona também, mas o hábito é chamar direto e deixar o SvelteKit cuidar do resto.

6. Quando dá errado

Erro 1 — default e action nomeada no mesmo arquivo

A regra parece estranha até você ver a mensagem: se existe action com nome, não pode existir default. Um formulário sem sufixo não tem como escolher entre duas.

export const actions = {
	default: async ({ request }) => {
		const dados = await request.formData();
		criar(dados.get('cliente'), dados.get('sabor'));
		return { ok: true };
	},
	limpar: async () => {
		return { ok: true };
	}
};
SvelteKit error: action_default_with_named
When using named actions, the default action cannot be used. See the docs for more info: https://svelte.dev/docs/kit/form-actions#Named-actions
https://svelte.dev/e/kit/action_default_with_named
500 POST /encomenda?/anotar

A correção é escolher: ou só default (e os formulários sem sufixo), ou só actions nomeadas (e todo formulário com ?/nome). O guia usa a segunda forma porque ela permite dois botões na mesma página.

Erro 2 — POST sem content-type

O navegador sempre manda esse cabeçalho; ferramentas de linha de comando, não. O resultado é 415, "tipo de mídia não suportado", em JSON:

ana@notebook:~/loja$ curl -s -X POST 'localhost:5173/encomenda?/anotar' -w '\n%{http_code}\n'
{"type":"error","location":"/encomenda","error":{"status":415,"message":"Unsupported Media Type"}}
415

Conserto: mandar o corpo com -d 'cliente=Ana', que já inclui o cabeçalho, ou declarar -H 'content-type: application/x-www-form-urlencoded'. Sem corpo nenhum, use -d '' — o cabeçalho vem junto e o 415 desaparece.

Erro 3 — apontar para uma action que não existe

O formulário diz ?/apagar e não há apagar em actions. O SvelteKit responde 404, e não uma mensagem de campo:

ana@notebook:~/loja$ curl -s -i -X POST -d 'cliente=Ana' 'localhost:5173/encomenda?/apagar' | head -1
HTTP/1.1 404 Not Found
ana@notebook:~/loja$ curl -s -X POST -H 'accept: text/html' -d 'cliente=Ana' 'localhost:5173/encomenda?/apagar' | head -c 60
<!doctype html>
<html lang="pt-BR">
	<head>
		<meta charset=

Sem accept: text/html a resposta vem em JSON; com o cabeçalho, vem a página de erro. Nos dois casos o status é 404 — o endereço existe, a ação não. Confira o nome no action="?/…" contra as chaves do objeto actions.

7. O formulário que melhora quando o JavaScript chega

O mesmo <form method="POST"> serve a dois mundos. Sem JavaScript, o navegador faz o envio clássico: recarrega a página, o servidor responde HTML, a mensagem aparece. Com JavaScript, o SvelteKit pode interceptar o envio, mandar os campos em segundo plano e trocar só o pedaço que mudou — mais rápido, mesma action, mesmas regras.

É por isso que a escolha de fazer o formulário no servidor não é nostalgia. Você escreve uma vez e ganha os dois comportamentos. O que muda é só uma diretiva no componente, o use:enhance, que é assunto da próxima aula. A action não muda nada: continua lendo request.formData() e devolvendo fail ou dados.

Vale entender o que o navegador faz sozinho nesse caminho, porque é o que explica os códigos que você viu. O envio de formulário é um POST de verdade; a página que volta é uma resposta HTTP; o redirecionamento é um 303 que o navegador segue sozinho. Nada disso depende de Svelte. O SvelteKit só organiza o arquivo e entrega o formulário pronto.

8. Onde a action guarda o dado

No projeto da Ana, a action chama criar() de um módulo que guarda a lista numa variável. Isso funciona para estudar e tem uma consequência que você precisa conhecer: a lista vive na memória do servidor. Reiniciou o processo, a lista volta ao que estava escrito no código.

let pedidos = [
	{ id: 1, cliente: 'Ana', sabor: 'frango', pronto: true },
	{ id: 2, cliente: 'Bia', sabor: 'queijo', pronto: false }
];

export function criar(cliente, sabor) {
	const pedido = { id: pedidos.length + 1, cliente, sabor, pronto: false };
	pedidos = [...pedidos, pedido];
	return pedido;
}

Outro detalhe do mesmo módulo: a lista é do processo, não do visitante. Duas pessoas que abrirem a página veem a mesma fila, e o pedido de uma aparece para a outra. Em produção, isso é o comportamento esperado de um painel de cozinha compartilhado — e um desastre se o dado fosse carrinho de compras. Guarde a pergunta: este dado é de quem?

Trocar a memória por banco de dados não muda a action: ela continua lendo o formulário, validando e chamando uma função. O que muda é o conteúdo de criar(). Essa é a vantagem de separar o módulo: o dia da troca fica num arquivo só, e o formulário nem percebe.

9. Testando o formulário inteiro com curl

Formulário é chato de testar clicando: você precisa digitar, apagar, corrigir, recarregar. Com curl, cada caso é uma linha e o resultado é comparável. Um roteiro de quatro casos cobre o essencial.

ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'accept: text/html' -d 'cliente=Caio&sabor=frango' 'localhost:5173/encomenda?/anotar'
200
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'accept: text/html' -d 'cliente=' 'localhost:5173/encomenda?/anotar'
400
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -H 'accept: text/html' -d '' 'localhost:5173/encomenda?/limpar'
303
ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' -X POST -d 'cliente=Ana' 'localhost:5173/encomenda?/apagar'
404

Quatro números, quatro significados: criou, recusou por validação, redirecionou, não achou a ação. Se um deles vier diferente do esperado, você sabe qual caso quebrou sem abrir navegador. Depois, quando a página for automatizada com uma ferramenta de teste, esses mesmos casos viram testes.

Não confie no required do HTML

O atributo required no campo é conveniência para quem usa o formulário, não proteção. Ele é do navegador: qualquer requisição feita fora dele passa direto, como o curl acabou de mostrar. Toda regra que protege dado precisa existir na action também.

Resumo

  • Form action é uma função no +page.server.js, dentro de export const actions.
  • O formulário aponta para ela com method="POST" e action="?/nome".
  • Os campos chegam por await request.formData(); cada name é uma chave.
  • return fail(400, { … }) recusa e devolve dados para o prop form.
  • redirect(303, '/x') termina o POST e evita reenvio ao atualizar a página.
  • Com action nomeada não pode existir default: escolha um dos dois estilos.
  • A resposta muda com o cabeçalho accept: HTML para navegador, JSON para o enhance.
  • POST sem content-type recebe 415; ação inexistente recebe 404.
  • Validação no navegador é conveniência; a que protege dado mora na action.
  • Quatro curl com -w '%{http_code}' testam o formulário inteiro sem clicar.
