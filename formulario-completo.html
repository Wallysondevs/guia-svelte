Svelte · Formulário Completo

A Ana recebia pedidos por mensagem: nome, quantidade, forma de pagamento, tudo no meio de uma conversa. Metade chegava sem o nome, e um pedido de trinta sonhos chegou como “três” porque ninguém sabia o que era o campo. Nesta aula ela monta um formulário de verdade, com rótulo em cada campo, validação antes de enviar e mensagens de erro no lugar certo.

Você vai aprender
  • As peças de um formulário e o trabalho de cada uma.
  • Como ligar o rótulo ao campo, para leitor de tela e para o clique.
  • Como bind:value faz o valor caminhar nos dois sentidos.
  • Como usar bind:group em rádio e bind:checked em caixa de seleção.
  • Por que campo numérico devolve número, e campo de texto devolve texto.
  • Como validar antes de enviar, devolvendo uma lista de erros.
  • Como mostrar a lista de erros na tela.
  • Por que onsubmit precisa de preventDefault().
  • Os três erros desta aula, com a mensagem real de cada um.

1. A ideia: formulário é uma conversa com regras

Um formulário é a Ana perguntando e o cliente respondendo. O que muda em relação à conversa é que aqui as regras estão escritas: o nome é obrigatório, a quantidade mínima é um, os termos precisam ser aceitos. Regra escrita no código vale sempre; regra combinada na conversa vale enquanto alguém lembra.

Formulário bom tem três qualidades. Cada campo tem rótulo, para se saber o que perguntar. Cada campo tem um tipo certo, para o teclado do celular abrir no modo adequado. E o envio é conferido antes, com a mensagem de erro ao lado do campo que falhou.

O resto é consequência: rotular bem evita dúvida, tipar bem evita digitação errada, validar bem evita pedido incompleto. Nenhuma das três é difícil separada; o problema é lembrar das três ao mesmo tempo — e é isso que esta aula organiza.

2. As peças de um formulário

Cada tipo de pergunta tem uma peça própria. Escolher a peça certa economiza validação e melhora o uso no celular:

PeçaPara quêComo ligar ao estado
<input type="text">texto livre: nome, telefone, endereçobind:value={nome}
<input type="number">quantidade, medidabind:value={quantidade} (devolve número)
<input type="radio">uma escolha entre poucasbind:group={pagamento}
<input type="checkbox">sim ou não: aceito os termosbind:checked={aceitou}
<select>uma escolha entre muitasbind:value={sabor}
<textarea>texto longo: observação do pedidobind:value={observacao}

Escolher type="text" para tudo funciona, e é o caminho que a Ana tinha no começo. O custo aparece no celular: sem type="number", o teclado numérico não abre para a quantidade; sem type="tel", o telefone vem com letras. E aparece também na validação: cada campo de texto exige Number() antes de qualquer conta.

Repare que quatro das seis usam bind:value. A diferença aparece nas outras duas: rádio e caixa de seleção não guardam “um valor digitado”, guardam “estou marcado” ou “pertenço a este grupo”. Por isso têm diretivas próprias.

3. O formulário completo da Ana

Juntando as peças, este é o formulário de pedido. Ele tem nome, quantidade, forma de pagamento, aceite dos termos e a lista de erros embaixo:

<script>
  let nome = $state('');
  let quantidade = $state(1);
  let pagamento = $state('pix');
  let aceitou = $state(false);
  let erros = $state([]);

  function validar() {
    erros = [];
    if (nome.trim() === '') erros = [...erros, 'Informe o nome'];
    if (quantidade < 1) erros = [...erros, 'A quantidade mínima é 1'];
    if (!aceitou) erros = [...erros, 'Aceite os termos'];
    return erros.length === 0;
  }

  function enviar(evento) {
    evento.preventDefault();
    if (validar()) {
      erros = ['Pedido enviado para a Ana'];
    }
  }
</script>

<form onsubmit={enviar}>
  <label for="nome">Nome</label>
  <input id="nome" bind:value={nome} />

  <label for="quantidade">Quantidade</label>
  <input id="quantidade" type="number" bind:value={quantidade} />

  <fieldset>
    <legend>Pagamento</legend>
    <label><input type="radio" value="pix" bind:group={pagamento} /> Pix</label>
    <label><input type="radio" value="cartao" bind:group={pagamento} /> Cartão</label>
  </fieldset>

  <label><input type="checkbox" bind:checked={aceitou} /> Aceito os termos</label>

  <button>Enviar pedido</button>
</form>

{#if erros.length > 0}
  <ul class="erros">
    {#each erros as erro}
      <li>{erro}</li>
    {/each}
  </ul>
{/if}

No primeiro desenho — nenhum campo preenchido e nada aceito —, o HTML gerado é este:

<form><label for="nome">Nome</label> <input id="nome" value=""/> <label for="quantidade">Quantidade</label> <input id="quantidade" type="number" value="1"/> <fieldset><legend>Pagamento</legend> <label><input type="radio" value="pix" checked=""/> Pix</label> <label><input type="radio" value="cartao"/> Cartão</label></fieldset> <label><input type="checkbox"/> Aceito os termos</label> <button>Enviar pedido</button></form>

Três detalhes para ler nessa saída. O rádio do Pix já vem marcado (checked=""), porque pagamento começa com 'pix'. O campo de quantidade já vem com 1. E a lista de erros não aparece — erros começa vazio, e o {#if} não desenha nada.

4. A anatomia de um campo com rótulo

Um campo sozinho não diz nada. O rótulo é a pergunta; o campo é a linha em branco. Eles precisam estar ligados por um id:

<label for="nome">Nome</label>
<input id="nome" placeholder="Como devemos chamar você?" />
<label for="nome">Nome</label> <input id="nome" placeholder="Como devemos chamar você?"/>
<label for="nome">
o rótulo. O for carrega o mesmo texto do id do campo: é essa combinação que os liga.
Nome
o texto visível. Curto e no singular: “Nome”, não “Informe o nome completo do cliente”.
<input id="nome">
o campo. O id é único na página — dois campos com id="nome" deixam o rótulo apontando para o primeiro.
placeholder
a dica cinza dentro do campo. Ela não substitui o rótulo: em telas pequenas, o texto cinza desaparece quando a pessoa começa a digitar.

A ligação for + id faz duas coisas que não se veem. Primeiro, clicar no rótulo foca o campo — útil em tela pequena, onde acertar o campo é difícil. Segundo, o leitor de tela anuncia “Nome” antes de cada campo, e quem não vê a tela sabe o que está digitando. O compilador avisa quando essa ligação falta.

5. bind:value: o valor nos dois sentidos

Sem bind, o valor caminha de um lado só: do estado para a tela. Com bind, ele caminha nos dois sentidos — o que a pessoa digita volta para o estado, e o estado continua podendo mudar a tela.

Missão: o campo recebe o valor do estado, mas digitar não atualiza o parágrafo: só falta a via de volta. Faça o campo escrever no estado enquanto a pessoa digita.

<script>
  let nome = $state('');
</script>

<input aria-label="Nome" value={nome} />
<p>Olá, {nome}</p>
<script>
  let nome = $state('');
</script>

<input aria-label="Nome" bind:value={nome} />
<p>Olá, {nome}</p>

O código inicial mostra “Olá, ” e não muda ao digitar. A solução troca value={nome} por bind:value={nome}: a diferença de uma palavra, e o parágrafo passa a acompanhar cada tecla.

No campo numérico, bind:value faz uma coisa a mais: converte o texto digitado em número. O componente abaixo mostra o tipo do valor guardado:

<script>
  let quantidade = $state(1);
</script>

<input type="number" bind:value={quantidade} />
<p>{typeof quantidade}</p>
<input type="number" value="1"/> <p>number</p>

Isso importa para a validação: se a quantidade fosse texto, quantidade < 1 compararia texto com número. Com type="number" e bind:value, ela é número de verdade, e a comparação funciona como se espera.

Também vale saber o que o bind não faz: ele não converte texto em número em campo de texto, não valida, não impede envio. Ele só mantém as duas pontas iguais. Todo o resto continua sendo trabalho do código — e é o assunto das próximas seções.

6. Validação: a lista de erros

Validar é conferir todas as regras e juntar o que falhou, em vez de parar no primeiro problema. A função da Ana zera a lista, testa uma regra por linha e devolve se está tudo certo:

<script>
  let nome = $state('');
  let aceitou = $state(false);
  let erros = $state(['Informe o nome', 'Aceite os termos']);

  function validar() {
    erros = [];
    if (nome.trim() === '') erros = [...erros, 'Informe o nome'];
    if (!aceitou) erros = [...erros, 'Aceite os termos'];
    return erros.length === 0;
  }
</script>

<input aria-label="Nome" bind:value={nome} />

{#if erros.length > 0}
  <ul class="erros">
    {#each erros as erro}
      <li>{erro}</li>
    {/each}
  </ul>
{/if}
<input aria-label="Nome" value=""/> <ul class="erros"><li>Informe o nome</li><li>Aceite os termos</li></ul>

Esse é o HTML com duas regras quebradas. A lista aparece embaixo do formulário, uma linha por regra — e o cliente vê tudo o que falta de uma vez, não um erro por tentativa.

Repare no nome.trim(): ele tira os espaços das pontas antes de comparar. Sem isso, digitar três espaços passaria na validação e o pedido chegaria sem nome. É uma linha pequena que evita um problema real.

Missão: a mensagem de erro está guardada num valor fixo e nunca muda. Faça ela ser calculada a partir do nome: “Informe o nome” enquanto estiver vazio, “Tudo certo” quando houver texto.

<script>
  let nome = $state('');
  let erro = $state('Informe o nome');
</script>

<input aria-label="Nome" bind:value={nome} />
<p>{erro}</p>
<script>
  let nome = $state('');
  let erro = $derived(nome.trim() === '' ? 'Informe o nome' : 'Tudo certo');
</script>

<input aria-label="Nome" bind:value={nome} />
<p>{erro}</p>

O $derived é a peça certa aqui: a mensagem não é um dado novo, é uma conclusão sobre o nome. Guardar essa conclusão num segundo $state exigiria lembrar de atualizá-la em cada mudança — e é assim que as mensagens de erro ficam desatualizadas na tela.

7. onsubmit e o preventDefault()

O envio de um formulário tem um comportamento antigo do navegador: recarregar a página mandando os dados para o endereço atual. Num componente Svelte, recarregar apaga todo o estado — e o pedido some. Para evitar isso, o primeiro comando do handler cancela o comportamento padrão:

<script>
  let nome = $state('');

  function enviar(evento) {
    evento.preventDefault();
    console.log('pedido de', nome);
  }
</script>

<form onsubmit={enviar}>
  <input bind:value={nome} />
  <button>Enviar</button>
</form>

O evento chega como argumento da função, e preventDefault() diz ao navegador: “não faça o que você faria sozinho”. A partir daí, quem decide o que acontece é o seu código. Note também que o <button> não tem onclick: dentro de um formulário, o botão dispara o onsubmit sozinho — é o caminho esperado, que também funciona quando a pessoa aperta Enter no campo.

Uma armadilha comum é escrever onsubmit={enviar()}, com parênteses. Os parênteses chamam a função na hora do desenho, e o que fica no lugar do handler é o resultado da chamada — não a função. O <form> continua na tela, e o envio passa a não fazer nada. A forma correta é onsubmit={enviar}, sem parênteses: você entrega a função para ser chamada depois.

O preventDefault vem primeiro

Se você validar antes e a validação falhar, o navegador recarrega a página do mesmo jeito e a lista de erros nunca aparece. Cancele o comportamento padrão na primeira linha do handler, sempre.

8. O botão que só envia quando pode

Desabilitar o botão é uma decisão de produto, e tem custo: quem não entende por que o botão está apagado desiste. A alternativa é deixar o clique acontecer e explicar o que falta — que é o que o formulário da Ana faz.

Missão: o botão envia mesmo sem o aceite dos termos. Faça o envio depender da caixa marcada: primeiro clique não envia, depois de marcar o segundo clique envia.

<script>
  let aceitou = $state(false);
  let enviado = $state(false);
</script>

<label><input type="checkbox" bind:checked={aceitou} /> Aceito os termos</label>
<button onclick={() => (enviado = true)}>Enviar</button>
<p>{enviado ? 'Pedido enviado' : 'Aguardando'}</p>
<script>
  let aceitou = $state(false);
  let enviado = $state(false);

  function enviar() {
    if (!aceitou) return;
    enviado = true;
  }
</script>

<label><input type="checkbox" bind:checked={aceitou} /> Aceito os termos</label>
<button onclick={enviar}>Enviar</button>
<p>{enviado ? 'Pedido enviado' : 'Aguardando'}</p>

Uma terceira opção, que a Ana adotou no fim, é desabilitar o botão e mostrar o motivo em texto. O botão apagado impede o clique; o texto ao lado explica o que falta. As duas informações juntas resolvem o problema do usuário — só uma delas, não.

No projeto da Ana, essa decisão mudou com o público. No balcão, o botão apagado bastava, porque o cliente perguntava. Na página, ninguém pergunta: quem vê um botão apagado fecha a aba. Por isso a versão final mostra sempre o motivo em texto, mesmo com o botão liberado.

O return sozinho dentro do if encerra a função sem fazer nada — é a forma mais curta de dizer “para aqui se não pode”. A caixa marcada é lida por aceitou, que o bind:checked mantém sincronizado com o que a pessoa marcou.

9. Quando dá errado

As três saídas abaixo vieram do compilador e do renderizador desta versão. As duas primeiras param o projeto; a terceira quebra na hora de desenhar.

Erro 1 — um formulário dentro de outro

O HTML não permite formulário aninhado: o navegador “conserta” a estrutura ao carregar, e o Svelte perde a referência de qual elemento é qual. Por isso o compilador recusa antes.

<form>
  <form>
    <input />
  </form>
</form>
Erro de compilação (linha 2, coluna 2): `<form>` cannot be a child of `<form>`. The browser will 'repair' the HTML (by moving, removing, or inserting elements) which breaks Svelte's assumptions about the structure of your components.

A mensagem explica o motivo: o navegador vai mover, remover ou inserir elementos para “consertar” o HTML, e isso quebra as suposições do Svelte sobre a estrutura. Um formulário por componente; para dividir, use um componente separado com os campos, sem outro <form> dentro.

Erro 2 — rótulo sem campo

Um <label> que não aponta para campo nenhum e não envolve um. O compilador avisa; a tela continua funcionando, e o leitor de tela não.

<label>Nome</label>
<input id="nome" />
aviso na compilação:

a11y_label_has_associated_control (linha 1): A form label must be associated with a control

“Um rótulo de formulário precisa estar associado a um controle.” A correção é <label for="nome"> com o mesmo id do campo, ou envolver o campo com o <label>. O aviso não impede o build: por isso ele passa fácil.

Erro 3 — validar um campo que ainda não tem valor

Uma variável de estado criada sem valor inicial vale undefined. Chamar trim() nela quebra o componente antes de qualquer digitação.

<script>
  let nome = $state();

  function validar() {
    return nome.trim() !== '';
  }

  let valido = validar();
</script>

<p>{valido ? 'ok' : 'vazio'}</p>
Cannot read properties of undefined (reading 'trim')

“Não consigo ler propriedades de undefined (lendo ‘trim’)”. Campo de texto começa como texto vazio, não como undefined: let nome = $state(''). Parece detalhe, e é o tipo de detalhe que só aparece quando alguém abre a página pela primeira vez.

Quarenta e seis quilobytes de JavaScript, 17,68 kB comprimidos — um pouco mais que a vitrine sem formulário, e o suficiente para uma página de pedido. Nenhum aviso de acessibilidade desta vez, o que confirma que os rótulos estão ligados aos campos.

O build não testa o formulário: ele não preenche campo, não clica em enviar, não vê a lista de erros. Ele só garante que o código compila. A conferência de comportamento é a que a Ana faz clicando — ou a que um teste faz por ela.
