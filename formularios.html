Svelte · Formulários e Validação

A Ana recebe encomendas por telefone e anota numa ficha: nome, telefone, o que quer, para quando. Quando a ficha chega incompleta, ela liga de volta — e perde tempo. Um formulário na tela tem o mesmo problema: se o programa aceita qualquer coisa, a Ana descobre o erro tarde demais. Esta aula monta a ficha inteira no Svelte, liga cada campo ao estado, mostra como impedir o recarregamento da página e como recusar o que não serve antes de gravar.

Você vai aprender
  • Como ligar cada campo da ficha ao seu pedaço de estado.
  • Por que o formulário recarrega a página e como impedir isso.
  • O que evento.preventDefault() faz na prática.
  • Como validar no handler e mostrar uma mensagem de erro.
  • Como usar required, pattern e maxlength.
  • Por que {3} dentro de um atributo vira conta, e como escapar.
  • Como separar os erros por campo em vez de uma mensagem só.
  • Como limpar o formulário depois de enviar.
  • Os três erros reais desta aula, com a mensagem do compilador.

1. A ideia: a ficha de encomenda

Uma ficha de padaria tem campos com finalidades diferentes. O nome é texto livre e obrigatório. O telefone tem formato conhecido. A data de entrega é uma data. O tipo de pão é uma escolha entre poucos. A observação é texto longo e opcional. Se o programa trata todos como "um texto qualquer", a Ana recebe "asdf" no telefone e "ontem" na data.

Um formulário é a soma de três coisas: os campos, o estado que guarda o que foi digitado e a regra que decide se aquilo serve. No Svelte, os dois primeiros já estão resolvidos pelos bindings das aulas anteriores. O terceiro é o assunto desta aula: validação é o nome dado à conferência feita antes de aceitar.

Existem dois momentos para validar. O primeiro é durante a digitação: avisar que o telefone está incompleto enquanto a pessoa escreve. O segundo é no envio: recusar a ficha inteira se algo essencial falta. Os dois são úteis, e os dois usam as mesmas ferramentas: uma função que olha o estado e decide, e uma parte da tela que mostra o resultado da decisão.

Validar não é desconfiar de quem preenche; é poupar a segunda conversa. A ficha que chega completa na primeira vez resolve o pedido na hora, e a Ana volta para o balcão em vez de voltar para o telefone.

Repare que a validação não é um recurso novo do Svelte: é uma função comum com um if. O que o Svelte faz é ligar o resultado à tela. Se a função muda a mensagem, a tela mostra a mensagem nova. Toda a inteligência fica no seu código, e é por isso que vale aprender a escrever condições claras.

3. O formulário com bind em cada campo

<script>
  let nome = $state('');
  let email = $state('');
</script>

<form>
  <input bind:value={nome}>
  <input type="email" bind:value={email}>
</form>
<p>{nome} · {email}</p>

Dois campos, dois pedaços de estado, um binding em cada. O HTML gerado não mostra nada de especial: os campos vão vazios e o parágrafo mostra o separador entre dois valores vazios.

<form><input value=""/> <input type="email" value=""/></form> <p> · </p>
<form>
o agrupador. Ele existe para o envio e para a validação nativa do navegador; o binding dos campos funciona com ou sem ele.
bind:value={nome}
liga o campo ao estado. Cada campo precisa do seu binding e da sua variável.
type="email"
muda o teclado no celular e liga a validação de formato do navegador. Não muda o tipo do valor: continua string.
{nome} · {email}
mostra os dois valores. Útil para conferir, e um bom teste de que os bindings estão ligados.

Uma decisão de projeto: a ficha pode ter um único objeto de estado (let ficha = $state({ nome: '', email: '' })) ou uma variável por campo. As duas funcionam. Uma variável por campo é mais fácil de ler no começo; um objeto agrupa os dados e facilita enviar tudo junto para o servidor. O guia usa variáveis separadas nesta aula e mostra o objeto na aula de projeto.

4. onsubmit e o recarregamento

O comportamento padrão do formulário no navegador é enviar os dados para o endereço do action e recarregar a página. Quando o envio é feito por JavaScript, recarregar é exatamente o que você não quer: o estado é perdido e a mensagem de sucesso some. A solução é cancelar o comportamento padrão dentro do handler.

<script>
  let nome = $state('');
  let enviado = $state('');

  function enviar(evento) {
    evento.preventDefault();
    enviado = nome;
  }
</script>

<form onsubmit={enviar}>
  <input bind:value={nome}>
  <button>enviar</button>
</form>
<p>Enviado: {enviado}</p>
<form><input value=""/> <button>enviar</button></form> <p>Enviado: </p>

O botão dentro do formulário, sem atributo type, é um botão de envio: clicar nele dispara o evento submit do formulário. Se você quer um botão que não envie — para limpar os campos, por exemplo —, escreva type="button". Essa distinção é a causa de muitos "meu formulário recarrega sozinho".

Por que as caixas desta aula usam onclick

As caixas interativas do guia rodam dentro de um quadro isolado que bloqueia o envio de formulário de propósito: sem essa proteção, um clique poderia navegar para fora da aula. Por isso os exemplos práticos usam um botão type="button" com onclick, que exercita a mesma função de validação. No projeto da Ana, o caminho é o da seção acima: <form onsubmit={enviar}> com evento.preventDefault().

O terminal não tem formulário, mas tem a função que você vai usar para conferir texto vazio. O trim() remove os espaços das pontas, o que evita aceitar um nome feito só de espaços:

ana@notebook:~/loja$ node -e "console.log('  ana  '.trim(), '  ana  '.trim().length)"
ana 3

Sem trim(), a string " ana " teria sete caracteres e passaria em qualquer teste de "não está vazia". Com trim(), o teste vê três e o nome fica limpo. Use trim() sempre que a regra for "precisa ter algo".

Trinta e sete kilobytes e oitenta e nove centésimos para uma ficha com dois campos e validação. O tamanho não cresce na proporção do número de campos, e sim do código que decide o que fazer com eles. Se você adicionar dez campos com o mesmo binding, o peso quase não muda; se adicionar dez regras diferentes, muda.

Uma consequência prática: a validação no cliente deixa a página maior e mais lenta de baixar, mas economiza uma ida ao servidor para cada erro óbvio. Num formulário curto, o ganho é grande. Num formulário com regras que só o servidor conhece, o melhor é validar o básico no cliente e deixar o resto para a resposta do servidor.

5. Validação antes de enviar

A validação mais simples é a de campo obrigatório. Se o nome está vazio, o handler grava uma mensagem e para; se não está, segue com o envio.

Missão: o botão salva mesmo com o campo vazio. Faça o handler recusar o envio e mostrar Erro: informe o nome quando não houver nome.

<script>
  let nome = $state('');
  let mensagem = $state('');

  function salvar() {
    mensagem = 'Salvo: ' + nome;
  }
</script>

<p>{mensagem}</p>
<input bind:value={nome}>
<button type="button" onclick={salvar}>salvar</button>
<script>
  let nome = $state('');
  let mensagem = $state('');

  function salvar() {
    if (nome.trim() === '') {
      mensagem = 'Erro: informe o nome';
      return;
    }
    mensagem = 'Salvo: ' + nome;
  }
</script>

<p>{mensagem}</p>
<input bind:value={nome}>
<button type="button" onclick={salvar}>salvar</button>

O return dentro do if é o que faz a função parar ali. Sem ele, a mensagem de erro seria escrita e logo substituída pela de sucesso. É um erro comum: a condição funciona, mas a função continua executando. A regra é simples: quando a validação falha, a função termina naquele ponto.

Repare também que a mensagem é uma variável de estado, não um alert. Mostrar o erro na página é melhor do que interromper a pessoa com uma caixa de diálogo: o texto fica visível enquanto ela corrige o campo, e o leitor de tela anuncia a mudança. Guarde o alert para experimentos rápidos.

6. required, pattern e o problema das chaves

O navegador tem validação própria, ligada por atributos do HTML. Ela não substitui a do handler, mas evita ida e volta para os casos óbvios.

<script>
  let codigo = $state('');
</script>

<form>
  <input required pattern={"[0-9]{3}"} maxlength="3" bind:value={codigo}>
  <button>enviar</button>
</form>
<p>Código: {codigo}</p>
<form><input required="" pattern="[0-9]{3}" maxlength="3" value=""/> <button>enviar</button></form> <p>Código: </p>
AtributoO que exigeO que o navegador faz
requiredcampo preenchidoavisa que o campo é obrigatório
minlength="3"pelo menos 3 caracteresavisa o mínimo de caracteres
maxlength="10"no máximo 10 caracteresimpede digitar além do limite
pattern="[0-9]{3}"o texto casa com a expressãoavisa que o formato não confere
type="email"formato de e-mailavisa que falta o @
min="0" / max="10"faixa de númeroavisa que o valor está fora da faixa

Aqui aparece uma armadilha do Svelte que vale o preço da aula. As chaves dentro de um atributo são interpretadas como expressão. Escrever pattern="[0-9]{3}" faz o compilador tratar o {3} como um valor e o atributo sai como pattern="[0-9]3", que não valida três dígitos. As duas saídas corretas são pattern={"[0-9]{3}"} (expressão com string) e pattern="[0-9]{3}" (entidades no lugar das chaves).

Missão: o botão aceita qualquer e-mail. Faça o handler recusar texto sem @ e mostrar E-mail inválido quando a pessoa digitar ana.

<script>
  let email = $state('');
  let mensagem = $state('');

  function salvar() {
    mensagem = 'Salvo: ' + email;
  }
</script>

<p>{mensagem}</p>
<input id="email" type="email" bind:value={email}>
<button type="button" onclick={salvar}>salvar</button>
<script>
  let email = $state('');
  let mensagem = $state('');

  function salvar() {
    if (!email.includes('@')) {
      mensagem = 'E-mail inválido';
      return;
    }
    mensagem = 'Salvo: ' + email;
  }
</script>

<p>{mensagem}</p>
<input id="email" type="email" bind:value={email}>
<button type="button" onclick={salvar}>salvar</button>

O includes('@') é uma conferência grosseira, e é honesto dizer isso: validação de e-mail de verdade é assunto de servidor, porque qualquer regra no navegador pode ser burlada. A regra do cliente serve para avisar cedo, não para garantir. O servidor confere de novo, sempre — mesmo que o cliente já tenha conferido.

7. Uma mensagem por campo

Uma mensagem só para a ficha inteira obriga a pessoa a descobrir qual campo está errado. Uma mensagem por campo resolve o problema, e o custo é pequeno: um pedaço de estado para cada erro.

<script>
  let nome = $state('');
  let telefone = $state('');
  let erroNome = $state('');
  let erroTelefone = $state('');

  function validar() {
    erroNome = nome.trim() === '' ? 'Informe o nome' : '';
    erroTelefone = telefone.trim().length < 8 ? 'Telefone curto' : '';
    return !erroNome && !erroTelefone;
  }
</script>

<p>{erroNome} {erroTelefone}</p>
<input bind:value={nome}>
<input bind:value={telefone}>
<p>  </p> <input value=""/> <input value=""/>

A função devolve true quando tudo passou e false quando algum campo falhou. Quem chama decide o que fazer com esse resultado: parar o envio, destacar o campo, mostrar um resumo. A validação fica em um lugar só, e o handler de envio fica curto.

O && na última linha é o "e" lógico: a expressão é verdadeira apenas se as duas negações forem verdadeiras, isto é, se não houver erro em nenhum dos dois campos. Esse tipo de expressão é o motivo de a validação ser uma função separada: dá para testá-la sem clicar em nada, e dá para reaproveitá-la em dois botões diferentes.

Uma escolha de interface: mostrar o erro embaixo do campo correspondente, e não num bloco distante. Quem preenche olha para o campo e para a mensagem no mesmo lugar. Se a mensagem fica no topo, a pessoa precisa procurar o que corrigir, e em formulário longo isso cansa. O texto do erro também deve dizer o que fazer, não apenas que algo está errado: "Informe o nome" ajuda; "Campo inválido" não.

8. Limpar depois de enviar

Depois de aceitar a ficha, o formulário deve voltar ao estado inicial. Com bind, isso é uma atribuição: o campo acompanha o estado.

<script>
  let nome = $state('');
  let enviado = $state('');

  function enviar() {
    enviado = nome;
    nome = '';
  }
</script>

<p>Enviado: {enviado} · Campo: {nome}</p>
<input bind:value={nome}>
<button type="button" onclick={enviar}>enviar</button>
<p>Enviado:  · Campo: </p> <input value=""/> <button type="button">enviar</button>

A ordem importa: primeiro copie o valor para onde ele deve ficar, depois limpe o campo. Se você limpar antes, o que foi enviado vira vazio. Esse é o tipo de bug que não aparece no primeiro teste, porque o formulário estava vazio; aparece depois de digitar algo e clicar rápido.

Missão: depois de enviar, o nome continua no campo. Faça o handler guardar o valor enviado e limpar o campo, para que a tela mostre Enviado: ana · Campo: e o botão.

<script>
  let nome = $state('');
  let enviado = $state('');

  function enviar() {
    enviado = nome;
  }
</script>

<p>Enviado: {enviado} · Campo: {nome}</p>
<input id="nome" bind:value={nome}>
<button type="button" onclick={enviar}>enviar</button>
<script>
  let nome = $state('');
  let enviado = $state('');

  function enviar() {
    enviado = nome;
    nome = '';
  }
</script>

<p>Enviado: {enviado} · Campo: {nome}</p>
<input id="nome" bind:value={nome}>
<button type="button" onclick={enviar}>enviar</button>

Em formulário de verdade, limpar tudo de uma vez também pode ser feito com form.reset(), mas aí o estado do Svelte e o DOM podem sair de sincronia: o campo esvazia e a variável continua com o valor antigo. Com binding, limpar as variáveis é o caminho previsível, porque o estado é a fonte da verdade.

9. Quando dá errado

Erro 1 — bind:value no formulário

O formulário agrupa campos, mas não tem valor próprio. Quem tem valor são os campos.

<script>
  let email = $state('');
</script>

<form bind:value={email}>
  <input bind:value={email}>
</form>
Erro de compilação (linha 5, coluna 6): `bind:value` can only be used with `<input>`, `<textarea>`, `<select>`

A mensagem lista os três elementos que aceitam valor. Tire o binding do <form> e deixe no campo. Se a intenção era reagir ao envio, o atributo é onsubmit, não bind:value.

Erro 2 — handler de envio como texto

Evento precisa de expressão. Aspas transformam o handler em string e o compilador recusa.

<script>
  let email = $state('');

  function enviar() {
    alert(email);
  }
</script>

<form onsubmit="enviar">
  <input bind:value={email}>
  <button>enviar</button>
</form>
Erro de compilação (linha 9, coluna 6): Event attribute must be a JavaScript expression, not a string

A linha 9 é a do <form>. A correção é onsubmit={enviar}, sem aspas. O mesmo vale para onclick, oninput e qualquer atributo que comece com on.

Erro 3 — parêntese aberto no handler

Dentro de uma seta, o parêntese que abre precisa fechar. O compilador aponta a coluna onde a expressão deixou de fazer sentido.

<script>
  let nome = $state('');
</script>

<form onsubmit={() => enviar(}>
  <input bind:value={nome}>
</form>
Erro de compilação (linha 5, coluna 29): Unexpected token

"Unexpected token" quer dizer que o compilador encontrou um pedaço de código fora de lugar. Aqui, o fecha-chaves apareceu antes do fecha-parênteses. A dica é fechar o par antes de escrever o conteúdo: () => enviar().

Exercícios

1. O que evento.preventDefault() faz no envio do formulário?

2. Por que pattern="[0-9]{3}" não funciona como esperado?

3. Onde deve ficar a validação de um formulário?

Complete o código

function enviar(evento) {

Resumo

  • Formulário é campos + estado + regra de validação; o binding cuida dos dois primeiros.
  • <form onsubmit={enviar}> reage ao envio; preventDefault() impede o recarregamento.
  • Um <button> dentro do formulário envia por padrão; type="button" não envia.
  • Valide no handler com if e return: quando falha, a função para.
  • Mostre o erro numa variável de estado, não em alert.
  • required, pattern e maxlength dão validação nativa de graça.
  • Chaves dentro de atributo são expressão: pattern="[0-9]{3}" vira [0-9]3.
  • Uma mensagem por campo ajuda mais do que um aviso único no topo.
  • Limpe o estado depois de enviar, guardando antes o valor que precisa sobreviver.
  • Validação de cliente avisa; validação de servidor garante.
