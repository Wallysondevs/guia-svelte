SvelteKit · hooks.server.js

A padaria da Ana tem um porteiro. Ele não assa o pão nem atende no caixa, mas nenhuma pessoa entra sem passar por ele: anota quem chegou, confere se pode entrar na área dos fundos e avisa a equipe quando alguém cai na escada. No SvelteKit esse porteiro é um arquivo chamado src/hooks.server.js. Ele roda em toda requisição que chega ao servidor — antes da página, antes do load, antes de qualquer componente. Esta aula mostra o que ele pode fazer, o que ele não vê e como as mensagens aparecem no terminal.

Você vai aprender
  • O que é um hook de servidor e por que ele roda antes da página.
  • Como é a assinatura de um handle: event e resolve.
  • Como registrar cada requisição com método, caminho, status e tempo.
  • Como usar sequence para encadear vários hooks e por que a ordem importa.
  • Como guardar dados da requisição em event.locals para o load usar.
  • Como barrar uma área com redirect antes da página carregar.
  • O que o hook não vê: arquivo estático e página pré-renderizada.
  • Como o handleError transforma um erro em mensagem amigável.
  • Os três tropeços reais: hook sem retorno, redirecionamento em loop e o aviso do status.

1. A ideia: o porteiro na porta

Imagine a padaria cheia, num sábado. O porteiro fica na porta e faz três coisas em ordem: olha quem está chegando, decide se deixa passar e, se a pessoa for para a área dos fundos sem crachá, encaminha para a entrada de novo. Só depois disso o atendente do balcão vê o cliente.

O hooks.server.js é esse porteiro, e a ordem importa do mesmo jeito. Cada requisição que chega ao servidor — um pedido de página, uma imagem, um envio de formulário — passa por ele. Se o hook devolver uma resposta, a requisição termina ali, sem chegar à rota. Se ele chamar resolve(event), a requisição segue o caminho normal e o hook recebe a resposta de volta, podendo mexer nela.

O detalhe que faz diferença: um arquivo só, para o site inteiro. Você não escreve hook por página; escreve um src/hooks.server.js ao lado da pasta routes, e ele vale para tudo. É onde ficam as coisas que precisam acontecer em todas as requisições — sessão, cabeçalhos, registro de log, medição de tempo.

2. O arquivo que roda antes de tudo

O arquivo tem 30 linhas e faz três trabalhos diferentes. Vale ler inteiro, porque cada parte é reaproveitada na vida real:

import { sequence } from '@sveltejs/kit/hooks';
import { redirect } from '@sveltejs/kit';

const registrar = async ({ event, resolve }) => {
	const inicio = performance.now();
	const resposta = await resolve(event);
	const ms = Math.round(performance.now() - inicio);
	console.log(`${event.request.method} ${event.url.pathname} → ${resposta.status} (${ms} ms)`);
	return resposta;
};

const sessao = async ({ event, resolve }) => {
	const sid = event.cookies.get('sessao');
	event.locals.usuario = sid === 'ana-123' ? { nome: 'Ana', papel: 'dona' } : null;

	if (event.url.pathname.startsWith('/conta') && !event.locals.usuario) {
		throw redirect(303, `/entrar?de=${event.url.pathname}`);
	}
	return resolve(event);
};

export const handle = sequence(registrar, sessao);

export function handleError({ error, event, status }) {
	console.error(`[erro ${status}] ${event.request.method} ${event.url.pathname}: ${error.message}`);
	return {
		message: 'A padaria teve um problema. Tente de novo em instantes.',
		codigo: status
	};
}
export const handle
o nome obrigatório do hook principal. O SvelteKit procura exatamente este export; com outro nome, o arquivo é ignorado em silêncio.
{ event, resolve }
o que o hook recebe. event descreve a requisição; resolve é a função que entrega a requisição para o resto do app.
await resolve(event)
a chamada que “deixa passar”. Ela devolve a Response pronta — status, cabeçalhos e corpo.
event.locals
uma caixa vazia para o hook guardar o que quiser, disponível depois em todo load daquela requisição.
event.cookies.get
lê o cookie que veio do navegador. É assim que o porteiro reconhece o crachá.
sequence(registrar, sessao)
junta dois hooks num só, na ordem em que estão escritos. O primeiro da lista é o primeiro a rodar.
handleError
o hook de erro. Recebe o erro, o evento e o status, e devolve os dados que a página de erro mostra.

Repare que registrar chama resolve e depois mexe na resposta; sessao chama resolve no fim, como última linha. Essa diferença não é estilo: o que vem antes do resolve acontece na ida, o que vem depois acontece na volta. Medir tempo só faz sentido com a resposta na mão.

3. event e resolve, peça por peça

Quase todo hook é a mesma pergunta: o que eu preciso saber da requisição e o que eu faço com a resposta? O objeto event responde a primeira parte:

Em eventO que éExemplo
event.requesto pedido cru: método, cabeçalhos, corpoevent.request.method
event.urlo endereço pedido, já como objeto URLevent.url.pathname
event.cookiesleitor e gravador de cookiesevent.cookies.get('sessao')
event.localsa caixa que o hook entrega ao loadevent.locals.usuario
event.paramsos pedaços variáveis da rotaevent.params.id
event.setHeadersdefine cabeçalho da respostaevent.setHeaders({ 'x-loja': 'ana' })

resolve(event) entrega tudo isso ao restante do app e devolve uma Response. Com a resposta na mão, o hook pode ler resposta.status, acrescentar um cabeçalho — resposta.headers.set('x-tempo', ms + 'ms') — ou simplesmente devolver como veio. O que ele não pode é esquecer de devolver: o contrato diz que todo handle termina com uma Response, e o primeiro cenário de erro desta aula mostra o que acontece quando ele termina com nada.

5. Caixa 1: quem entra e quem é barrado

O trabalho mais comum de um hook é decidir. A caixa abaixo tem dois pedidos e diz que os dois entram, mesmo quando um deles não tem crachá.

Missão: mostre entra para quem tem temCookie: true e barrado para quem não tem. O texto precisa conter /painel: barrado.

<script>
	const pedidos = [
		{ caminho: '/conta', temCookie: true },
		{ caminho: '/painel', temCookie: false }
	];
</script>

<ul>
	{#each pedidos as p}
		<li>{p.caminho}: entra</li>
	{/each}
</ul>
<script>
	const pedidos = [
		{ caminho: '/conta', temCookie: true },
		{ caminho: '/painel', temCookie: false }
	];
</script>

<ul>
	{#each pedidos as p}
		<li>{p.caminho}: {p.temCookie ? 'entra' : 'barrado'}</li>
	{/each}
</ul>

No hook de verdade essa decisão não vira texto: vira throw redirect(303, '/entrar') ou return resolve(event). O 303 é o status “veja outro endereço”, e ele é o certo depois de um POST, porque manda o navegador buscar a página com GET. Usar 302 também funciona, mas o 303 deixa a intenção explícita.

6. sequence: dois hooks, uma fila

Quando um arquivo tem dois hooks, alguém precisa dizer em que ordem eles rodam. Isso é o sequence: ele recebe os hooks e devolve um só, encadeado. O primeiro da lista é o mais externo — ele começa antes e termina depois.

import { sequence } from '@sveltejs/kit/hooks';

const registrar = async ({ event, resolve }) => {
	const inicio = performance.now();
	const resposta = await resolve(event);
	console.log(`${event.request.method} ${event.url.pathname} → ${resposta.status}`);
	return resposta;
};

const sessao = async ({ event, resolve }) => {
	event.locals.usuario = event.cookies.get('sessao') === 'ana-123' ? { nome: 'Ana' } : null;
	return resolve(event);
};

export const handle = sequence(registrar, sessao);

Com essa ordem, o fluxo é: registrar anota a hora, chama resolve, que chama sessao, que define locals e chama o app. Na volta, registrar recebe a resposta e imprime o status. Se a ordem fosse sequence(sessao, registrar), o cálculo de tempo ficaria dentro da sessão e o porteiro mais externo passaria a ser o de sessão — o que muda o que acontece quando sessao lança um redirecionamento.

E é exatamente isso que explica uma ausência no log. Quando a Ana pediu /conta sem cookie, o Vite registrou 303 GET /conta, mas o hook registrar não imprimiu nada. O motivo: sessao lançou o redirecionamento antes de a resposta existir, e o await resolve(event) de registrar nunca devolveu. Sem resposta, não há status para imprimir.

7. O que o hook não vê

Duas categorias de pedido passam longe do seu hook, e as duas surpreendem. A primeira é o arquivo estático: imagem, PDF, robots.txt. Eles são entregues antes de o app ser chamado. A segunda é a página pré-renderizada: o HTML já existe no disco, e o pedido é atendido sem rodar o servidor.

GET / → 200 (92 ms)
200 GET /
[erro 404] GET /naoexiste.svg: Not Found
GET /naoexiste.svg → 404 (20 ms)
404 GET /naoexiste.svg

Nessa sessão três pedidos foram feitos: a página inicial, o /logo.svg e um arquivo inventado. Só dois aparecem no registro. O logotipo foi entregue direto do disco, sem app, sem hook. O arquivo inventado não existia, caiu no roteador e passou pelo hook — por isso virou página de erro com registro.

A consequência prática é dupla. Contagem de acesso por hook é uma contagem de páginas, não de pedidos; se a Ana quiser medir tráfego de imagem, precisa de outra ferramenta. E proteção por hook não alcança arquivo estático: um PDF confidencial em static está público mesmo com a sessão sendo verificada no handle.

8. Caixa 2: a ordem da fila

A ordem em que os hooks rodam muda o resultado, então vale treinar. A caixa abaixo empilha dois nomes numa trilha, na ordem errada. A missão é fazer a trilha começar por registrar.

Missão: troque a ordem das chamadas para a trilha ficar registrar → sessao, que é a ordem de um sequence(registrar, sessao).

<script>
	const trilha = [];
	function registrar(nome) {
		trilha.push(nome);
	}

	registrar('sessao');
	registrar('registrar');
</script>

<p>Ordem: {trilha.join(' → ')}</p>
<script>
	const trilha = [];
	function registrar(nome) {
		trilha.push(nome);
	}

	registrar('registrar');
	registrar('sessao');
</script>

<p>Ordem: {trilha.join(' → ')}</p>

push acrescenta no fim da lista e join transforma a lista em texto, com o separador que você escolher. É a forma mais direta de ver a ordem de execução sem abrir o depurador — e o mesmo truque serve para entender qualquer sequência de funções, dentro ou fora do Svelte.

9. locals, handleError e o que fica registrado

event.locals é a ponte entre o hook e o load. O hook escreve; a página lê. No projeto da Ana, sessao grava { nome: 'Ana', papel: 'dona' } quando o cookie é o esperado, e null quando não é. O +layout.server.js devolve esse valor, e qualquer página acessa data.usuario.

Dois outros exports completam o arquivo, e vale saber que existem mesmo que você não precise deles hoje. O init roda uma vez só, quando o servidor sobe — é o lugar de abrir conexão com o banco, ler um arquivo de configuração ou preparar um cache em memória. Já o handleFetch roda quando o código do servidor faz um fetch para uma API; ele serve para repassar o cookie da requisição original para essa API, coisa que o fetch do Node não faz sozinho. Nenhum dos dois aparece em toda requisição: o primeiro é da vida do processo, o segundo é das chamadas internas.

O handleError é o outro lado do porteiro: ele cuida de quem tropeça. Roda quando um erro escapa de um load ou de uma ação, e o que ele devolve vira o que a página de erro mostra. No terminal, cada erro passa por ele e sai registrado:

[sveltekit] handle_error_status_deprecated
The `status` property of `handleError` is deprecated. Use `error.status` for expected and framework errors, or `500` for unexpected errors.
https://svelte.dev/e/kit/handle_error_status_deprecated
[erro 404] GET /erro: Pão não encontrado na prateleira
GET /erro → 404 (16 ms)
404 GET /erro

O aviso de obsolescência é do SvelteKit 3: o segundo parâmetro do handleError não deve mais trazer status como propriedade separada. O valor continua funcionando por enquanto, mas o caminho novo é ler error.status — o status viaja dentro do próprio erro. A linha [erro 404] é do console.error do projeto, e mostra o mesmo pedido que o Vite registra logo abaixo.

10. Caixa 3: a caixa que o hook entrega

Quando ninguém está logado, event.locals.usuario é null — e acessar .nome de null quebra a página, como o primeiro cenário de erro vai mostrar. A caixa abaixo escreve o nome fixo “Ana”, mesmo com o usuário nulo.

Missão: use locals.usuario?.nome e o operador ?? para mostrar visitante quando não houver usuário. O texto deve virar Bem-vinda, visitante.

<script>
	const locals = { usuario: null };
</script>

<p>Bem-vinda, Ana</p>
<script>
	const locals = { usuario: null };
	const nome = $derived(locals.usuario?.nome ?? 'visitante');
</script>

<p>Bem-vinda, {nome}</p>

O ?. é o encadeamento opcional: se a parte da esquerda for null ou undefined, a expressão inteira vira undefined em vez de quebrar. O ?? então troca esse undefined pelo texto padrão. Juntos, eles resolvem o caso “usuário pode não existir” sem if e sem risco de derrubar a página.

11. Quando dá errado

As três mensagens abaixo saíram do servidor de desenvolvimento desta máquina. A primeira derruba a página; a segunda gira para sempre; a terceira é um aviso que aparece toda vez que o erro passa pelo hook.

Erro 1 — o hook não devolve resposta

Um handle que não chama resolve e não devolve Response deixa o SvelteKit sem resposta. O servidor tenta ler o status de undefined e o pedido termina em 500.

export const handle = async ({ event }) => {
	return undefined;
};
TypeError: Cannot read properties of undefined (reading 'status')
500 GET /
TypeError: Cannot read properties of undefined (reading 'status')
500 GET /produtos

A leitura é literal: alguém tentou ler .status de undefined. A correção é terminar o hook com return resolve(event) ou com uma Response montada à mão. Todo caminho do hook precisa terminar devolvendo alguma coisa.

Erro 2 — o redirecionamento em loop

Um hook que manda todo mundo para /entrar cria um ciclo: o pedido de /entrar também é redirecionado para /entrar. O navegador desiste depois de algumas voltas, e o curl avisa com o código 47.

ana@notebook:~/loja$ curl -sS -L -o /dev/null http://localhost:5173/
curl: (47) Maximum (50) redirects followed

No terminal do servidor, o mesmo pedido aparece repetido até o limite: 303 GET /entrar várias vezes seguidas. A correção é excluir a própria rota de destino da regra — no projeto da Ana, event.url.pathname.startsWith('/conta') faz exatamente isso, porque /entrar não começa com /conta.

Aviso 3 — status no handleError

Não derruba nada, mas aparece no terminal a cada erro. É o SvelteKit 3 avisando que a propriedade mudou de lugar.

[sveltekit] handle_error_status_deprecated
The `status` property of `handleError` is deprecated. Use `error.status` for expected and framework errors, or `500` for unexpected errors.
https://svelte.dev/e/kit/handle_error_status_deprecated

A mensagem diz o que fazer: usar error.status em vez do status separado. Enquanto você não trocar, o aviso volta a cada erro — e um terminal cheio de aviso esconde o erro de verdade.

Complete o código

// src/hooks.server.js
export const handle = async ({ event, resolve }) => {
  if (event.url.pathname.startsWith('/conta') && !event.locals.usuario) {
    throw ;
  }
  return resolve(event);
};

Resumo

  • src/hooks.server.js é o porteiro: roda em toda requisição ao servidor, antes da rota.
  • O handle recebe { event, resolve } e precisa terminar devolvendo uma Response.
  • event traz request, url, cookies, params e a caixa locals.
  • await resolve(event) deixa a requisição seguir e devolve a resposta para o hook mexer.
  • sequence(a, b) encadeia hooks na ordem escrita; o primeiro é o mais externo.
  • Quem redireciona antes do resolve não gera linha de status para o hook que mede tempo.
  • Arquivo estático não passa pelo hook; página pré-renderizada também não.
  • locals é a ponte entre hook e load; use ?. e ?? para lidar com a ausência de usuário.
  • handleError decide a mensagem da página de erro e registra o problema.
  • Erros desta aula: hook sem retorno, redirecionamento em loop e handle_error_status_deprecated.
