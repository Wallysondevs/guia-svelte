Svelte · Instalando

A Ana quer fazer o site da padaria no notebook que ela comprou na promoção. O sobrinho disse "é só instalar o Svelte" e sumiu. Ela abriu o terminal, aquela janela preta, e ficou olhando o cursor piscando. Esta aula é o que ela precisava: o que instalar, em que ordem, o que cada comando faz e o que aparece na tela quando dá certo — e quando não dá. Nada de mágica: são quatro programas e uma pasta.

  • Como conferir as versões que já estão na máquina.
  • O que é o package.json e por que ele é a lista de compras do projeto.
  • Como rodar npm install e ler a saída sem susto.
  • Para que servem os três pacotes instalados: svelte, vite e o plugin.
  • Por que o guia prende as versões e o que muda se você não prender.

  • Como conferir a instalação com dois comandos.
  • Os erros reais desta etapa: TypeScript sem aviso, aspas inteligentes e $props() repetido.

1. A ideia: a bancada antes do primeiro pão

Antes de assar o primeiro pão, a Ana não liga o forno. Ela limpa a bancada, separa a balança, confere se a tomada funciona. Instalar o Svelte é isso: preparar a bancada. O componente que ela vai escrever daqui a pouco é o pão; o que faremos agora é colocar na bancada as ferramentas que transformam farinha em pão.

Essas ferramentas são programas que ficam no computador dela, não na internet. O primeiro é o Node, que executa JavaScript fora do navegador — é nele que o compilador do Svelte roda. O segundo é o npm, que vem junto com o Node e serve para baixar pacotes e rodar comandos. O terceiro é o Vite, que junta os arquivos e serve a página durante o desenvolvimento. O quarto é o próprio Svelte.

Repare no que não está nessa lista: editor de texto não entra na conta, porque qualquer um serve; navegador você já tem. A instalação é pequena. O que assusta é o vocabulário — e o vocabulário se resolve lendo a saída de cada comando com calma, que é o que faremos aqui.

2. O que precisa estar na máquina

Abra o terminal. No Linux e no macOS ele se chama Terminal; no Windows, use o WSL, que é um Linux dentro do Windows — os comandos deste guia são de Linux. O prompt parece com isto: ana@notebook:~/loja$. Ele diz três coisas: quem você é (ana), em que máquina (notebook) e em que pasta (~/loja). O ~ é atalho para a sua pasta pessoal.

O primeiro comando confere se o Node está instalado e em que versão:

ana@notebook:~/loja$ node -v
v22.23.5
ana@notebook:~/loja$ npm -v
10.9.9

Se a resposta for um número parecido com esses, está tudo certo. Se aparecer "command not found", o Node não está instalado: baixe a versão LTS no site oficial e instale como qualquer programa. A versão 22 é a que este guia usa; versões 20.19 ou mais novas também funcionam. Versões muito antigas fazem o Vite reclamar — e você vai ver a mensagem exata mais adiante.

Um detalhe que economiza meia hora de sofrimento: depois de instalar o Node, feche e abra o terminal de novo. O terminal guarda uma lista de onde os programas ficam, e essa lista só é lida quando ele abre. Instalar sem reabrir dá a impressão de que nada funcionou.

3. Node e npm: o motor e a lista de compras

O Node é um motor: ele pega um arquivo JavaScript e executa. O npm é o balcão de encomendas que vem acoplado ao motor: com ele você baixa pacotes prontos, escolhe versões e roda atalhos definidos no projeto. Os dois vivem juntos, mas fazem coisas diferentes — e é comum confundir.

Quando você digita npm install, o npm lê um arquivo chamado package.json, vê quais pacotes estão listados ali e baixa cada um para uma pasta chamada node_modules. Quando você digita npm run dev, o npm lê o mesmo arquivo, procura um atalho chamado dev e executa o comando que estiver escrito nele. Nada de mágica: é leitura de arquivo e execução.

Por isso o package.json é a peça central. Ele não guarda o código do Svelte, nem o Vite: guarda nomes e versões, do mesmo jeito que a lista de compras da Ana não guarda a farinha, só o que comprar. Quem tem a farinha é a despensa — no nosso caso, a pasta node_modules, que pode ser apagada e refeita a qualquer momento a partir da lista.

4. O package.json: a lista de compras escrita

Crie a pasta do projeto e entre nela. No exemplo, a pasta é loja, dentro da pasta pessoal da Ana. Depois crie o arquivo package.json com exatamente este conteúdo:

{
  "name": "loja",
  "private": true,
  "version": "0.0.1",
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  },
  "devDependencies": {
    "@sveltejs/vite-plugin-svelte": "^6.2.1",
    "svelte": "^5.59.2",
    "vite": "^7.1.3"
  }
}

Parece complicado, mas são cinco informações. A anatomia:

"name" e "version"
o nome do projeto e a versão dele. Aparecem no terminal quando um comando roda: é a linha > loja@0.0.1 dev.
"private": true
impede que alguém publique este projeto no npm por acidente. Para o site da padaria, é o que queremos.
"type": "module"
diz ao Node que os arquivos .js usam import e export, o formato moderno de módulos.
"scripts"
os atalhos. "dev": "vite" quer dizer: quando eu digitar npm run dev, execute o programa vite.
"devDependencies"
os pacotes necessários para desenvolver, não para o site funcionar no ar. Aqui ficam o Svelte, o Vite e o plugin que liga um no outro.

Os três acentos circunflexos (^) merecem uma frase. Eles dizem "aceito esta versão ou uma mais nova que não mude o número do meio". É uma margem de segurança pequena e é ela que permite o projeto receber correções sem você mexer em nada. Mais adiante nesta aula veremos por que o guia escolheu justamente estes números.

5. npm install: comprando a lista

Com a lista escrita, o comando é um só. Ele lê o package.json, baixa o que falta e cria a pasta node_modules:

ana@notebook:~/loja$ npm install

added 36 packages, and audited 37 packages in 8s

6 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

Quatro blocos de informação. added 36 packages é o número de pacotes baixados — não três, porque cada pacote depende de outros. audited 37 packages é a verificação de segurança que o npm faz sozinho. 6 packages are looking for funding é um pedido de doação de quem mantém as bibliotecas: você pode ignorar. found 0 vulnerabilities é o resultado da auditoria — nenhum problema conhecido nas versões baixadas.

Se aparecer um número diferente de pacotes, não é erro: depende da versão exata que o npm resolveu. O que importa é a última linha, sem "vulnerabilities" em vermelho, e a pasta node_modules criada. Essa pasta pode ter milhares de arquivos — é normal. Ela não vai para o repositório nem para o servidor: é refeita a partir da lista com um npm install.

Junto com ela nasce um arquivo chamado package-lock.json. Ele registra a versão exata de cada pacote baixado, inclusive as dependências indiretas. O package.json diz "svelte 5.59.2 ou mais novo dentro do 5"; o package-lock.json diz "foi este aqui, exatamente este". Guarde os dois no projeto: é assim que a máquina da Ana e a máquina do sobrinho instalam a mesma coisa.

6. As três dependências e o preço de prender as versões

Três pacotes foram declarados. Cada um tem um papel distinto, e nenhum é opcional neste arranjo.

PacoteVersão no projetoPara que serve
svelte^5.59.2o compilador e o motor que fazem o componente funcionar; é a versão que este guia usa
vite^7.1.3o servidor de desenvolvimento e o empacotador: junta os arquivos e serve a página
@sveltejs/vite-plugin-svelte^6.2.1a ponte entre os dois: ensina o Vite a compilar arquivos .svelte

Por que não instalar sempre a versão mais nova de tudo? Porque a saída muda. Um guia que mostra VITE v7.3.8 ready in 830 ms precisa que o seu Vite seja o 7.3.8; um guia que mostra uma mensagem de erro na linha 2 precisa do compilador que gera aquela mensagem. Fixar as versões é o que faz a aula ser reproduzível — e é o que permite comparar o seu resultado com o do guia sem adivinhar.

O custo é real: você fica alguns meses atrás do lançamento mais recente e precisa atualizar de propósito, lendo o que mudou. Para quem está aprendendo, esse é um preço barato. Para um projeto em produção, a equipe costuma atualizar em lotes, com testes. O importante é saber que a escolha existe e que foi feita de propósito, não por descuido.

7. Os arquivos que completam o projeto

O node_modules sozinho não faz nada. Faltam cinco arquivos pequenos que dizem ao Vite onde começar, o que compilar e qual página abrir. O primeiro é a configuração do Vite:

import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';

export default defineConfig({
  plugins: [svelte()]
});

Três linhas fazem o serviço: importam o Vite, importam o plugin do Svelte e ligam o plugin na lista de plugins. Sem o svelte() ali, o Vite trataria o .svelte como texto e a página abriria em branco.

O segundo arquivo é a configuração do próprio Svelte. Ele começa quase vazio, mas já tem uma função importante:

import { vitePreprocess } from '@sveltejs/vite-plugin-svelte';

export default {
  preprocess: vitePreprocess()
};

preprocess é o que roda antes da compilação. É graças a ele que o Svelte entende TypeScript dentro de um componente marcado com lang="ts". Sem essa linha, um componente com tipos não compila — e a mensagem que aparece é justamente a do primeiro cenário abaixo.

O terceiro arquivo é a página que o navegador carrega. Ela é HTML comum, com uma div vazia e um script que puxa o ponto de entrada:

<!doctype html>
<html lang="pt-BR">
  <head>
    <meta charset="utf-8" />
    <title>Loja da Ana</title>
  </head>
  <body>
    <div id="app"></div>
    <script type="module" src="/src/main.js"></script>
  </body>
</html>

O quarto arquivo é o ponto de entrada, em src/main.js. Ele importa o componente principal e manda montá-lo dentro da div com identificador app:

import { mount } from 'svelte';
import App from './App.svelte';

const app = mount(App, { target: document.getElementById('app') });

export default app;

O quinto é o componente em si. Este é o primeiro da Ana no projeto novo, e ele já usa estado:

<script>
  let aberta = $state(true);
</script>

<h1>Padaria da Ana</h1>
<p>{aberta ? 'Aberta agora' : 'Fechada'}</p>
<h1>Padaria da Ana</h1> <p>Aberta agora</p>

Se a placa está aberta, aparece "Aberta agora"; se aberta virar false, aparece "Fechada" — sem ninguém tocar no HTML. O ? e o : formam a expressão condicional, que tem aula própria mais adiante. Por enquanto, leia como "se isto, então aquilo; senão, aquilo outro".

Missão: o componente usa {nome} mas ninguém declarou nome, e a caixa mostra um erro. Declare a variável no bloco <script> com o valor 'Ana', do jeito que os arquivos acima fazem.

<h1>Olá, {nome}</h1>
<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}</h1>

Esse erro — usar um nome que não foi declarado — é o mais comum de quem copiou um pedaço de exemplo pela metade. O compilador não tem como saber se você esqueceu a declaração ou se o nome está escrito diferente; ele só sabe que aquele nome não existe ali.

8. Conferindo com dois comandos

Instalação boa é instalação conferida. O primeiro comando mostra o que o package.json declara, em formato de dado:

ana@notebook:~/loja$ npm pkg get devDependencies
{
  "@sveltejs/vite-plugin-svelte": "^6.2.1",
  "svelte": "^5.59.2",
  "vite": "^7.1.3"
}

O segundo mostra a versão que foi de fato instalada, perguntando ao pacote dentro de node_modules:

ana@notebook:~/loja$ node -e "console.log(require('svelte/package.json').version)"
5.59.2

Repare na diferença entre os dois: o primeiro lê a intenção (o que está escrito), o segundo lê a realidade (o que está na pasta). Quando os dois discordam, quase sempre é porque falta rodar npm install depois de editar o package.json.

Se o número que aparecer for 5.59.2, você está exatamente na versão deste guia. Se for 6.x ou outro, alguma coisa instalou mais novo do que a lista pedia — confira o arquivo e rode a instalação de novo.

Missão: a Ana escreveu o cumprimento dentro do console.log e a tela mostra só "Bem-vinda!". Faça o texto completo aparecer na página, com o nome vindo da variável.

<script>
  let nome = $state('Ana');
  console.log('Bem-vinda, ' + nome);
</script>

<h1>Bem-vinda!</h1>
<script>
  let nome = $state('Ana');
</script>

<h1>Bem-vinda, {nome}</h1>

console.log escreve no console do navegador, não na tela. É uma ferramenta de diagnóstico, não de interface. Quem começa confunde os dois e passa meia hora procurando um texto que está lá, no painel de desenvolvedor, enquanto a página mostra outra coisa.

9. O que apareceu na pasta

Depois da instalação, a pasta do projeto tem sete entradas. Este é o resultado real de ls:

ana@notebook:~/loja$ ls
index.html
node_modules
package-lock.json
package.json
src
svelte.config.js
vite.config.js

Traduzindo: index.html é a página que o navegador carrega; src é onde o seu código mora (o App.svelte e o main.js); package.json e package-lock.json são a lista de compras e o recibo; svelte.config.js e vite.config.js são as configurações; node_modules é a despensa. Só os dois primeiros e a pasta src são escritos por você.

ana@notebook:~/loja$ du -sh node_modules
31M	node_modules

Trinta e um megabytes para um projeto que ainda mostra um título e um parágrafo. É o preço de ter as ferramentas de desenvolvimento na máquina. No site publicado, esse peso não existe: o build gera dois arquivos pequenos, e é isso que o navegador do cliente baixa.

O teste final da instalação é o build. Quando ele termina com ✓ built in e cria a pasta dist, o compilador leu todos os seus componentes e gerou o site. Se algo estiver faltando — plugin, configuração, dependência —, é aqui que aparece. A aula O Servidor de Desenvolvimento mostra o build e o servidor em detalhe.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Duas delas acontecem na primeira hora de qualquer pessoa; não são sinal de que você fez algo muito errado.

Erro 1 — TypeScript sem avisar o compilador

O arquivo tem tipos, mas o <script> não está marcado com lang="ts". O compilador tenta ler como JavaScript e para no dois-pontos.

<script>
  let nome: string = 'Ana';
</script>

<h1>Olá, {nome}</h1>
Erro de compilação (linha 2, coluna 10): Unexpected token (did you forget to add `lang="ts"`?)

A mensagem já entrega a solução entre parênteses: escreva <script lang="ts">. Aí o vitePreprocess entra em ação e os tipos são removidos antes da compilação. Se você não quer TypeScript, basta não escrever tipos.

Erro 2 — aspas inteligentes coladas de outro lugar

O editor trocou as aspas retas por aspas curvas, do tipo que aparece em textos formatados. Para o JavaScript, isso não é aspa: é um caractere desconhecido.

<script>
  let nome = ‘Ana’;
</script>

<h1>Olá, {nome}</h1>
Erro de compilação (linha 2, coluna 13): Unexpected character '‘'

Olhe a posição: coluna 13 é exatamente a aspa de abertura. A solução é apagar e digitar de novo, no teclado, sem copiar de página de blog. Vale para aspas, travessões e qualquer caractere "bonito" que o editor invente.

Erro 3 — $props() duas vezes

Cada componente declara as propriedades que recebe uma vez só. Copiar dois exemplos para o mesmo arquivo cria duas declarações e o compilador recusa.

<script>
  let { titulo } = $props();
  let { preco } = $props();
</script>

<h2>{titulo}</h2>
<p>{preco}</p>
Erro de compilação (linha 3, coluna 18): Cannot use `$props()` more than once

Junte tudo numa declaração só: let { titulo, preco } = $props(). O assunto tem aula própria no nível de componentes; por ora, guarde a regra: uma chamada por arquivo.

Missão: a Ana inventou uma runa que não existe e a caixa mostra um erro de compilação. Troque $contador pela runa certa, que guarda um valor que pode mudar.

<script>
  let total = $contador(0);
</script>

<p>Total: {total}</p>
<script>
  let total = $state(0);
</script>

<p>Total: {total}</p>

Resumo

  • O Svelte roda em cima do Node, que executa JavaScript fora do navegador.
  • O npm baixa pacotes e roda os atalhos escritos no package.json.
  • package.json é a lista de compras; node_modules é a despensa; package-lock.json é o recibo com as versões exatas.
  • Três pacotes bastam: svelte, vite e @sveltejs/vite-plugin-svelte.
  • As versões estão presas de propósito, para a saída das aulas bater com a sua.
  • npm install termina com found 0 vulnerabilities quando dá tudo certo.
  • vite.config.js liga o plugin; svelte.config.js liga o pré-processador.
  • index.html tem a div#app; src/main.js chama mount() dentro dela.
  • TypeScript exige lang="ts"; aspas curvas quebram o arquivo; $props() é uma vez por componente.
  • console.log não é tela: o que aparece na página vem do HTML com chaves.
