SvelteKit · O que é SvelteKit

A Ana passou as últimas semanas aprendendo Svelte e montou um componente de lista de pães que funciona lindamente. Aí a cliente perguntou o endereço do site. A Ana abriu a boca e não tinha resposta: o componente dela não tem endereço, não abre sozinho, não aparece no Google. É a diferença entre um forno e uma padaria. O forno faz o pão; a padaria tem porta, endereço, vitrine e horário. O SvelteKit é a padaria em volta do forno — e nesta aula você vai ver o que ele põe a mais, com o HTML que o servidor manda de verdade.

Você vai aprender
  • A diferença entre Svelte (o compilador de componentes) e SvelteKit (a aplicação inteira).
  • Quais problemas o Kit resolve de uma vez: rotas, servidor, dados, formulários, publicação.
  • Por que o HTML chega pronto do servidor e o que isso muda para quem visita.
  • O que é hidratação e por que o mesmo componente roda duas vezes.
  • O papel de src/app.html e dos marcadores %sveltekit.head% e %sveltekit.body%.
  • Como o data do load chega ao componente.
  • Que page.url só pode ser lido no servidor durante o desenho.
  • O que o SvelteKit não é, para não esperar dele o que ele não faz.
  • Os três avisos e erros reais desta aula, com a saída do terminal.

1. A ideia: o forno e a padaria

Um componente Svelte é um forno excelente. Ele recebe dados, assa (desenha) e devolve HTML. Mas um forno na garagem não vende pão: falta a porta na rua, o endereço que o cliente digita, a vitrine que mostra o que tem hoje, o caixa e a entrega. Nada disso é responsabilidade do forno — e é exatamente isso que o SvelteKit faz.

Na prática, o Kit é um conjunto de decisões já tomadas em cima do Svelte: as páginas moram em src/routes e a pasta vira endereço; existe um servidor que desenha a página antes de mandar; existe um jeito padrão de buscar dados antes do desenho; e existe uma saída de build que você publica numa plataforma. Você não precisa inventar nada disso, e pode trocar cada peça se quiser.

Svelte sozinho é uma biblioteca: você escreve um componente, monta num ponto do HTML e pronto. Quem decide qual componente aparece em qual endereço é você, com código. O Kit assume essa decisão por você, do jeito que a maioria dos sites precisa — e é por isso que a documentação oficial recomenda o Kit como ponto de partida, não o Svelte puro.

No dia a dia × no SvelteKit

Na padariaNo SvelteKit
O forno que assa o pãoO componente .svelte e o compilador
O endereço na fachadaA rota: src/routes/paes/+page.svelte
A vitrine montada antes de abrirO HTML que o servidor manda pronto
O atendente que continua o serviçoO JavaScript que assume a página no navegador
O caderno de encomendas da cozinhaO load, que busca dados antes do desenho
O caminhão de entregaO adaptador, que embala o build para a plataforma

Repare que a tabela não tem uma linha "o Kit substitui o Svelte". Ele não substitui: ele usa. Todo componente que você aprendeu no Nível 1 continua igual dentro do Kit — $state, $props, {#if}, {#each}, onclick, <style> escopado. O que muda é o que está em volta.

2. Svelte × SvelteKit

A confusão entre os dois nomes é a primeira coisa a resolver, porque ela faz a pessoa procurar respostas no lugar errado. A tabela separa as responsabilidades:

PerguntaSvelteSvelteKit
Quem compila .svelte em JavaScript?o compilador do Svelteusa o compilador do Svelte
Quem decide qual página responde em /paes?ninguém: você monta à mãoo roteador do Kit, pela pasta
Quem gera o HTML no servidor?não faz parteo servidor do Kit
Quem busca dados antes do desenho?você, com fetch e $effectload, com +page.js
Quem prepara o build para publicar?o Vite empacotao adaptador escolhido

Uma forma de guardar: Svelte é a linguagem; SvelteKit é a aplicação. Quando você lê "Svelte 5", o assunto é a linguagem, as runas, os componentes. Quando lê "SvelteKit", o assunto é rotas, servidor, dados, publicação. Os dois evoluem juntos, mas são coisas diferentes — e a maior parte dos erros de iniciante vem de procurar uma resposta de um no lugar do outro.

3. O que o Kit resolve de uma vez

Cinco problemas aparecem em qualquer site que cresce, e o Kit já tem resposta para os cinco. A tabela é o mapa; as próximas aulas abrem cada linha.

ProblemaResposta do KitAula
Qual arquivo responde em qual endereço?pastas em src/routesRotas por Arquivo
Como não repetir o menu em todas as páginas?+layout.svelte+layout.svelte
Como buscar dados antes de desenhar?load em +page.jsParâmetros de Rota
Como tratar endereço inexistente e falha?+error.svelte e error(…) +error.svelte
Como trocar de página sem recarregar?links + gotoNavegando com goto

Existe ainda uma sexta linha, invisível e importante: o Kit decide onde cada pedaço roda. O componente da página roda nos dois lados; o +page.server.js roda só no servidor; o onclick roda só no navegador. Essa separação é o que permite falar com banco de dados sem vazar segredo para o navegador — e é a origem do erro mais confuso desta aula, na seção 8.

4. O HTML já vem pronto: a prova

A promessa do Kit mais fácil de provar é esta: quando alguém pede uma página, o servidor já manda o HTML montado. Não é uma tela em branco que o navegador preenche depois. Veja o que o servidor da Ana respondeu para /paes:

ana@notebook:~/loja/kit$ curl -s -i localhost:4173/paes | head -4
HTTP/1.1 200 OK
content-type: text/html
x-sveltekit-page: true

ana@notebook:~/loja/kit$ curl -s localhost:4173/paes | sed -e 's/<!--[^>]*-->//g' | grep -o '<main.*</main>'
<main><h1>Pães</h1> <ul><li><a href="/paes/frances">Pão francês</a></li> <li><a href="/paes/forma">Pão de forma</a></li> <li><a href="/paes/queijo">Pão de queijo</a></li></ul></main>

O <h1>Pães</h1> e a lista inteira vieram dentro da resposta, escritos pelo servidor. O curl não executa JavaScript: o que ele recebeu é o que o navegador recebe no primeiro pedido. Isso é renderização no servidor (SSR).

Três consequências práticas. A primeira: a página aparece com conteúdo antes de qualquer script carregar, então não existe aquele piscar branco. A segunda: robôs de busca que não executam JavaScript leem o conteúdo inteiro — o que muda o posicionamento no Google. A terceira: quem está num celular ruim e numa rede lenta vê o texto antes de o JavaScript chegar.

5. As duas execuções do mesmo componente

Se o servidor já mandou o HTML, por que o navegador baixa JavaScript? Porque HTML pronto é foto, não aplicação: sem JavaScript, um clique não muda nada. O Kit faz as duas coisas — manda o HTML e depois hidrata a página, que é o nome do processo de ligar o JavaScript ao HTML que já está na tela.

Na hidratação, o componente roda de novo no navegador, encontra o HTML que o servidor deixou e assume o controle. A partir daí, $state funciona, onclick responde, e a navegação entre páginas passa a ser do jeito rápido, sem recarregar. O usuário vê uma página que já estava lá e que, um instante depois, ganha vida.

SSR
"server-side rendering": o HTML é montado no servidor, a cada pedido.
hidratação
o JavaScript do navegador assume o HTML existente, sem redesenhar do zero.
duas execuções
o mesmo arquivo .svelte roda no servidor (para gerar HTML) e no navegador (para reagir).
código de servidor
o que só pode rodar no servidor: +page.server.js, +server.js, hooks.server.js.
código de navegador
o que só pode rodar no navegador: onclick, goto, localStorage, window.

Essa dupla execução explica quase todos os erros de "funciona no meu computador, quebra no servidor": você usou algo de navegador na parte que roda no servidor. A regra é simples de enunciar e chata de seguir: se a função só existe no navegador, ela precisa estar dentro de um evento ou de um $effect.

6. src/app.html: o molde de todas as páginas

Falta uma peça para entender o caminho do HTML. O componente da página não tem <html> nem <head> — ele é só o miolo. Quem monta o documento completo é o Kit, usando um molde chamado src/app.html. Este é o do projeto da Ana:

<!doctype html>
<html lang="en">
	<head>
		<meta charset="utf-8" />
		<meta name="viewport" content="width=device-width, initial-scale=1" />
		<meta name="text-scale" content="scale" />
		%sveltekit.head%
	</head>
	<body data-sveltekit-preload-data="hover">
		<div style="display: contents">%sveltekit.body%</div>
	</body>
</html>

Os dois marcadores são substituídos na hora de responder. %sveltekit.head% vira as tags que o layout ou a página injetaram com <svelte:head> — título, favicon, meta de descrição. %sveltekit.body% vira o HTML do layout com a página dentro. Repare também no data-sveltekit-preload-data="hover" no <body>: é ele que faz o Kit buscar a próxima página quando o mouse passa por cima de um link.

Um detalhe para quem fala português: o molde nasce com lang="en". Para um site em português, essa linha precisa virar lang="pt-BR" — é ela que diz ao leitor de tela e ao navegador em que idioma a página está, e afeta até a tradução automática. É uma edição de um caractere que quase todo mundo esquece.

7. Experimente: a página recebe dados de fora

O load busca os dados e o Kit entrega ao componente como uma prop chamada data. A página não sabe de onde o dado veio — se de um arquivo, de um banco ou de uma API. Ela só sabe que recebeu. A caixa abaixo mostra esse contrato, com o dado chegando pela prop em vez do servidor.

Missão: o load falhou e o componente recebeu data nulo. Faça a página mostrar Padaria da Ana quando não houver dado nenhum.

<script>
  // no SvelteKit este objeto chega pronto do load: let { data } = $props();
  let { data = null } = $props();
</script>

<h1>{data.titulo}</h1>
<script>
  // no SvelteKit este objeto chega pronto do load: let { data } = $props();
  let { data = null } = $props();
</script>

{#if data}
  <h1>{data.titulo}</h1>
{:else}
  <h1>Padaria da Ana</h1>
{/if}

Sem a proteção, o componente estoura ao ler data.titulo — e você já viu no guia como isso aparece: um 500 e a página de erro. Com {#if}, a página tem um caminho para quando o dado existe e outro para quando não existe. Esse segundo caminho é o que separa um site que aguenta uma falha de um site que fica em branco.

8. Cuidado com o lado: page.url no lugar errado

Agora a armadilha que só existe porque o Kit roda código nos dois lados. O objeto page, de $app/state, descreve a página atual — mas "atual" significa coisas diferentes conforme o lado. No navegador, é a página que a pessoa está vendo. No servidor, é a requisição que está sendo atendida naquele instante, e o servidor atende várias pessoas ao mesmo tempo.

A Ana tentou ler page.url.pathname dentro de um +page.server.js, para saber em que endereço estava. O servidor recusou, e com uma explicação que vale a pena ler inteira:

SvelteKit error: state_read_outside_render
Can only read `page.url` on the server during rendering (not in e.g. `load` functions), as it is bound to the current request via component context. This prevents state from leaking between users.
https://svelte.dev/e/kit/state_read_outside_render
    at load (src/routes/sobre/+page.server.js:4:25)
500 GET /sobre

A frase "prevents state from leaking between users" é o motivo: se o page pudesse ser lido livremente no servidor, um pedido poderia enxergar o endereço de outro. Em vez de correr esse risco, o Kit proíbe e mostra o caminho certo. E o caminho certo depende do que você precisa: dentro de um load, o endereço chega no argumento (load({ url })); dentro do componente, page.url funciona; dentro de um +page.server.js, o endereço também chega em load({ url }) — sem precisar importar page.

9. O que o SvelteKit não é

Meia hora de expectativa errada economizada. O Kit não é banco de dados, não é CSS, não é hospedagem, não é sistema de login pronto. Ele é a estrutura da aplicação; o resto você escolhe e liga.

Você pode achar que…Na verdade…
o Kit guarda os dadosele lê e escreve onde você mandar: arquivo, banco, API
o Kit tem login prontoele tem o lugar do login: hooks.server.js, cookies, +layout.server.js
o Kit é o servidor webem produção ele roda dentro do Node, do Deno ou da plataforma, conforme o adaptador
o Kit estiliza a páginao CSS é seu; o Kit só garante o escopo do <style>
o Kit substitui o Svelteele usa o Svelte por dentro: mesmo componente, mesma sintaxe

Isso ajuda a decidir onde procurar quando algo não funciona. Se o erro é de sintaxe no componente, o assunto é Svelte. Se o erro é de endereço, dados ou publicação, o assunto é Kit. Se o erro é de rede, porta ou DNS, não é nenhum dos dois — é infraestrutura.

Missão: o servidor mandou três pães em data.paes, mas o contador está fixo em 0. Faça o número vir do tamanho da lista usando $derived.

<script>
  let { data = { paes: ['francês', 'forma', 'queijo'] } } = $props();
  let total = 0;
</script>

<h1>Pães</h1>
<p>{total} na prateleira</p>
<script>
  let { data = { paes: ['francês', 'forma', 'queijo'] } } = $props();
  let total = $derived(data.paes.length);
</script>

<h1>Pães</h1>
<p>{total} na prateleira</p>

$derived diz "este valor é calculado a partir de outro". Quando data.paes muda — porque o load rodou de novo —, total se recalcula sem que ninguém escreva total = …. A diferença para let total = data.paes.length é justamente essa: sem $derived, o valor é calculado uma vez e congela.

10. Experimente: o trecho que precisa ser desenhado

O último conceito que separa "Svelte" de "SvelteKit" na cabeça de quem começa: um trecho de marcação pode ser guardado numa função e desenhado depois, em outro lugar. É assim que o Kit encaixa a página dentro do layout e o layout dentro do molde. Em Svelte 5 isso se chama snippet, e a instrução para desenhar é {@render}.

Missão: o trecho cartao foi declarado mas nunca desenhado, e a lista saiu vazia. Desenhe-o com {@render cartao(p)} dentro do {#each}.

<script>
  let paes = ['francês', 'forma', 'queijo'];
</script>

{#snippet cartao(nome)}
  <li>{nome.toUpperCase()}</li>
{/snippet}

<ul>
  {#each paes as p}
    {cartao(p)}
  {/each}
</ul>
<script>
  let paes = ['francês', 'forma', 'queijo'];
</script>

{#snippet cartao(nome)}
  <li>{nome.toUpperCase()}</li>
{/snippet}

<ul>
  {#each paes as p}
    {@render cartao(p)}
  {/each}
</ul>

{cartao(p)} sem o @render não é um erro de sintaxe: o Svelte tenta transformar o resultado da função em texto e não consegue desenhar o trecho. O {@render} é a ordem explícita de desenhar ali. É a mesma peça que aparece no {@render children()} do +layout.svelte — e é por isso que as duas aulas se parecem tanto.

11. Quando dá errado

Os três casos abaixo são do projeto da Ana. Os dois primeiros são erros do SvelteKit; o terceiro é um aviso do compilador que aparece no projeto criado por esta versão, porque o Kit força o modo moderno.

Erro 1 — o molde perdeu o marcador do corpo

Ao editar o src/app.html para trocar o idioma, a Ana apagou sem querer a linha do %sveltekit.body%. Sem ela não há onde encaixar a página, e o build para:

ana@notebook:~/loja/kit$ npm run build

> kit@0.0.1 build
> vite build

error during build:
SvelteKit error: app_template_tag_missing
src/app.html is missing `%sveltekit.body%`
https://svelte.dev/e/kit/app_template_tag_missing

O nome do erro é literal: falta uma tag no molde do app. Os dois marcadores obrigatórios são %sveltekit.head% e %sveltekit.body%; se um deles desaparecer, o Kit não tenta adivinhar onde colocar o conteúdo — ele avisa e para.

Erro 2 — ler page.url fora do desenho

Este é o erro da seção 8, na versão que aparece no terminal do servidor de desenvolvimento. O componente compila, o build passa e a página responde 500 na hora do pedido:

SvelteKit error: state_read_outside_render
Can only read `page.url` on the server during rendering (not in e.g. `load` functions), as it is bound to the current request via component context. This prevents state from leaking between users.
https://svelte.dev/e/kit/state_read_outside_render
    at load (src/routes/sobre/+page.server.js:4:25)
500 GET /sobre

A mensagem já entrega o conselho: use o argumento do load. Em vez de importar page, escreva load({ url }) e leia url.pathname. O valor é o mesmo, mas chega amarrado àquela requisição — sem risco de um usuário ver o endereço do outro.

Aviso 3 — sintaxe antiga de eventos

Como o projeto força o modo moderno, o hábito antigo de escrever on:click gera aviso a cada build. Não impede nada, mas polui a saída e some daqui a algumas versões:

ana@notebook:~/loja/kit$ npm run build
vite v8.4.0 building ssr environment for production...
transforming...
5:02:13 PM [vite-plugin-svelte] src/routes/sobre/+page.svelte:5:8 Using `on:click` to listen to the click event is deprecated. Use the event attribute `onclick` instead
https://svelte.dev/e/event_directive_deprecated
3: </script>
4:

"deprecated" quer dizer "desaconselhado, vai sair". A troca é de duas letras: on:click vira onclick. O guia usa a forma nova em todas as aulas, e o aviso é o compilador confirmando que você está no caminho certo.

Um resumo em três frases, para levar: o Svelte compila componentes; o SvelteKit transforma componentes em site, decidindo endereço, dados e lado de execução; o HTML sai pronto do servidor e o navegador assume em seguida. Se você entender essas três, o resto das aulas de Kit é detalhe de cada arquivo.

13. O caminho até aqui

A Ana agora sabe responder a pergunta da cliente: o endereço existe porque a pasta existe, o site abre rápido porque o HTML vem pronto e continua vivo porque o navegador hidrata. Sabe também onde cada coisa pode rodar — e por isso não vai mais tentar ler page.url na cozinha.

O próximo passo natural é criar o projeto de verdade, com o comando que monta a estrutura: Criando o Projeto. Se você quer primeiro ver a pasta virando endereço, Rotas por Arquivo. E se a dúvida é o que já existe pronto no Svelte sem Kit, o Nível 1 começa em Seu Primeiro Componente.

Resumo

  • Svelte é a linguagem dos componentes; SvelteKit é a aplicação em volta deles.
  • O Kit resolve rotas, layout, dados, erros e publicação com convenções de arquivo.
  • O HTML sai montado do servidor: a página aparece antes do JavaScript carregar.
  • Depois o navegador hidrata: o mesmo componente roda de novo e assume a interação.
  • src/app.html é o molde, com %sveltekit.head% e %sveltekit.body%.
  • O load busca dados e entrega ao componente como prop data.
  • $derived recalcula quando o dado de fora muda; let x = … congela.
  • page.url no servidor só durante o desenho; em load, use o argumento url.
  • O Kit não é banco de dados, CSS, login pronto nem hospedagem: ele é a estrutura.
  • {@render} desenha snippets — a mesma peça que encaixa a página no layout.
