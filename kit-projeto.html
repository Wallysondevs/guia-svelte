SvelteKit · Criando o Projeto

A Ana decidiu abrir a filial: uma loja online da padaria, com endereços de verdade, formulário de encomenda e uma área restrita. Ela não vai montar a loja tijolo por tijolo — vai usar uma planta pronta. O comando npx sv create entrega a loja vazia, com as prateleiras no lugar, a fiação passada e um cartaz de boas-vindas na vitrine. Nesta aula você vê o comando rodando de verdade, o que ele deixa no disco, o servidor que ele liga e as três coisas que costumam dar errado no primeiro dia.

Você vai aprender
  • O que o comando npx sv create faz e quais opções ele aceita.
  • O que aparece no terminal quando o projeto nasce, linha por linha.
  • O que cada arquivo criado faz: app.html, +layout.svelte, vite.config.js.
  • Por que nesta versão não existe svelte.config.js.
  • Como ler os scripts do package.json.
  • O que npm run dev mostra e por que a porta pode mudar.
  • A diferença entre desenvolvimento (dev), produção (build) e conferência (preview).
  • Para que serve a pasta .svelte-kit e por que ela não vai para o Git.
  • O aviso do adapter-auto e o que ele quer dizer.
  • Os três erros reais do primeiro dia: bloco aberto, porta ocupada e pasta não vazia.

1. A ideia: a loja vazia com as prateleiras montadas

Quando a Ana abriu a padaria de verdade, ela não começou pelo tijolo. Alugou um ponto que já tinha parede, piso, tomada e porta. Depois comprou as prateleiras, o balcão e o forno. O que ela trouxe foi o conteúdo; a estrutura veio antes. Criar um projeto SvelteKit é o mesmo movimento: você recebe a estrutura pronta e gasta o seu tempo no que só você sabe fazer — a padaria.

A estrutura que vem no pacote não é enfeite. Ela inclui o compilador do Svelte ligado, o servidor de desenvolvimento com recarga automática, a pasta de rotas, o molde do HTML, as configurações de JavaScript e um README dizendo o que rodar. Se você montasse tudo na mão, levaria uma tarde e esqueceria alguma coisa — provavelmente a parte que faz o servidor recompilar ao salvar.

O comando se chama sv, é o CLI oficial do Svelte e vive no npm. Você não precisa instalá-lo: o npx baixa na hora e executa. É por isso que o comando começa com npx e não com npm install. O npx é o "executador de pacotes" que vem junto com o npm.

Duas dessas linhas merecem atenção desde já, porque voltam em todo projeto: node_modules é o depósito de tudo o que foi baixado do npm, e .svelte-kit é a pasta que o SvelteKit gera sozinho com o mapa de rotas e os tipos. As três linhas que importam no meio são "Project created" (a estrutura nasceu), "Installing dependencies with npm" (o depósito foi abastecido) e "Successfully installed" (deu certo).

npx sv create
executa o CLI do Svelte sem instalar globalmente. O npx procura, baixa e roda.
kit
o nome da pasta que vai nascer (e o nome do pacote no package.json).
--template minimal
o modelo mais enxuto: uma página de boas-vindas e um layout, sem exemplo de contador.
--types jsdoc
liga a checagem de tipos usando comentários JSDoc em vez de arquivos .ts. Menos barulho para quem começa.
--no-add-ons
não instala complementos (Prettier, ESLint, Tailwind, Vitest). Dá para acrescentar depois.
--install npm
roda o npm install no fim, sem perguntar.

O sv ainda avisa o comando completo com a versão fixa (npx sv@1.7.1 create …). Fixar a versão é boa prática em projeto de equipe: todo mundo cria a mesma estrutura, mesmo que uma versão nova saia no meio do caminho.

Quatro arquivos merecem explicação antes de qualquer código seu. O src/app.html é o molde do documento: é nele que ficam o <html>, o <head> e os dois marcadores que o SvelteKit preenche (%sveltekit.head% e %sveltekit.body%). O src/routes/+layout.svelte é a moldura de todas as páginas. O src/routes/+page.svelte é a página inicial. E o static/ guarda arquivo público servido na raiz — como o robots.txt, que diz aos robôs de busca o que eles podem visitar.

O src/lib é a pasta de código reaproveitável: componentes, funções, imagens importadas. O sv já liga um apelido esperto para ela no package.json:

ana@notebook:~/loja/kit$ head -14 package.json
{
	"name": "kit",
	"version": "0.0.1",
	"private": true,
	"type": "module",
	"imports": {
		"#lib": "./src/lib/index.js",
		"#lib/*": "./src/lib/*"

O bloco imports define o apelido #lib. Em vez de escrever import x from '../../../lib/x.js', você escreve import x from '#lib/x.js' e o Node resolve. É o mesmo apelido que aparece no layout criado pelo sv: import favicon from '#lib/assets/favicon.svg'.

5. Onde mora a configuração: vite.config.js

Aqui vai uma observação que economiza meia hora de procura: nesta versão do SvelteKit não existe svelte.config.js. A configuração do Kit mora dentro do vite.config.js, na chamada sveltekit({ … }). Este é o arquivo real do projeto:

import adapter from '@sveltejs/adapter-auto';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
	plugins: [
		sveltekit({
			compilerOptions: {
				// Force runes mode for the project, except for libraries. Can be removed in svelte 6.
				runes: ({ filename }) =>
					filename.split(/[/\\]/).includes('node_modules') ? undefined : true
			},

			// adapter-auto only supports some environments, see https://svelte.dev/docs/kit/adapter-auto for a list.
			// If your environment is not supported, or you settled on a specific environment, switch out the adapter.
			// See https://svelte.dev/docs/kit/adapters for more information about adapters.
			adapter: adapter()
		})
	]
});

Duas linhas explicam o resto. runes: … true força o modo moderno do Svelte em todo arquivo do projeto — é por isso que export let e <slot /> reclamam nas aulas anteriores, e por isso o guia ensina $props() desde o começo. E adapter: adapter() escolhe o adaptador, que é a peça que traduz o build para a plataforma onde o site vai rodar.

Se você procurar por svelte.config.js em tutoriais de 2024, vai encontrar — versões anteriores do Kit usavam um arquivo separado para isso. Nada quebra se você criar um: o Kit ainda lê. Mas o projeto novo não traz, e misturar os dois é a receita para configurar no lugar errado e não entender por que nada muda.

6. npm run dev: o servidor que recompila

Com o projeto criado, o primeiro comando é o servidor de desenvolvimento. Ele compila, serve e observa os arquivos: cada Ctrl+S aparece no navegador em menos de um segundo.

ana@notebook:~/loja/kit$ npm run dev

> kit@0.0.1 dev
> vite dev

4:59:28 PM [vite] (ssr) connected.
Port 5173 is in use, trying another one...

  VITE v8.4.0  ready in 1139 ms

  ➜  Local:   http://localhost:5174/
  ➜  Network: use --host to expose
  ➜  press h + enter to show help

Três informações na tela. O Local é o endereço para abrir no navegador da própria máquina. O Network só aparece quando você quer acessar de outro aparelho — e, por padrão, o servidor não se expõe na rede; o Vite lembra que existe a opção --host para isso. E a linha "Port 5173 is in use, trying another one" apareceu porque a máquina da Ana já tinha outro projeto rodando na porta padrão: o Vite pulou para a 5174 sem reclamar.

Esse detalhe da porta confunde muita gente no começo. A porta é o número que o servidor usa para atender; a 5173 é só a preferida. Se ela estiver ocupada, o Vite procura a próxima livre e escreve o endereço certo na tela. Leia sempre a linha "Local" em vez de decorar o número.

7. Os scripts do package.json

Todo comando que você roda com npm run está listado ali. A tabela traduz cada um:

ScriptComando realPara que serve
npm run devvite devservidor de desenvolvimento, com recarga automática
npm run buildvite buildgera a versão de produção em .svelte-kit/output
npm run previewvite previewserve o build por HTTP, para conferir
npm run checksvelte-kit sync && svelte-check …confere tipos e avisos do projeto inteiro
npm run preparesvelte-kit sync || echo ''gera os tipos das rotas; roda sozinho no npm install

O prepare merece uma nota porque assusta: ele começa com svelte-kit sync, que lê a pasta src/routes e escreve os arquivos de tipo em .svelte-kit. O || echo '' no fim faz o script não falhar quando a pasta de rotas ainda não existe (caso de uma instalação limpa em CI). É um detalhe de robustez, não um erro.

Missão: a lista de scripts aparece como dev,vite dev, tudo grudado. Corrija o {#each} para desestruturar cada par e mostrar dev: vite dev na primeira linha.

<script>
  let scripts = {
    dev: 'vite dev',
    build: 'vite build',
    preview: 'vite preview'
  };
  let lista = Object.entries(scripts);
</script>

{#each lista as item}
  <p>{item}</p>
{/each}
<script>
  let scripts = {
    dev: 'vite dev',
    build: 'vite build',
    preview: 'vite preview'
  };
  let lista = Object.entries(scripts);
</script>

{#each lista as [nome, comando]}
  <p>{nome}: {comando}</p>
{/each}

Object.entries transforma o objeto numa lista de pares: [['dev', 'vite dev'], …]. Sem a desestruturação, o {item} mostra o par inteiro convertido em texto, com vírgula no meio. Com as [nome, comando], cada metade ganha um nome — e a saída fica legível. Esse padrão volta toda vez que você quiser listar as chaves de um objeto.

8. build e preview: a versão de produção

O servidor de desenvolvimento é confortável e pesado: ele traz ferramentas de depuração e recompila tudo na hora. O site publicado não precisa disso. O npm run build gera a versão final, e o fim da saída é o mais informativo:

ana@notebook:~/loja/kit$ npm run build
vite v8.4.0 building ssr environment for production...
transforming...
✓ 144 modules transformed.
...
✓ built in 282ms
Analysing routes
Building app
vite v8.4.0 building client environment for production...
transforming...
✓ 189 modules transformed.
...
✓ built in 466ms

Run npm run preview to preview your production build locally.

> Using @sveltejs/adapter-auto
Could not detect a supported production environment. See https://svelte.dev/docs/kit/adapters to learn how to configure your app to run on the platform of your choosing
✔ done

(No meio da saída há uma linha de tamanho por arquivo gerado; cortei para caber.) Dois builds acontecem: o ssr, que gera o código que roda no servidor, e o client, que gera o que vai para o navegador. O SvelteKit faz os dois porque as páginas são desenhadas no servidor e continuam no navegador — é o que faz o primeiro carregamento ser rápido.

O aviso do adapter-auto não é erro: ele diz que não reconheceu a plataforma de publicação. Localmente, tudo funciona — o adaptador só escolhe o formato de saída quando você publica numa Netlify, Vercel, Cloudflare ou num servidor Node. Quando chegar a hora de publicar, você troca o adaptador; o assunto está na aula Adaptadores.

Para conferir o build sem publicar, o npm run preview serve a saída por HTTP:

ana@notebook:~/loja/kit$ npm run preview

> kit@0.0.1 preview
> vite preview

  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose

A porta padrão do preview é a 4173. É este servidor que o guia usa para os curl das aulas: ele responde igual ao site publicado, com o HTML já montado no servidor, sem as ferramentas de desenvolvimento no meio.

9. A pasta .svelte-kit

Uma pasta gerada que aparece na listagem e assusta: .svelte-kit. Ela não é código seu e não se edita. O SvelteKit escreve ali o mapa de rotas que descobriu em src/routes, os tipos para o editor e a saída do build.

ana@notebook:~/loja/kit$ ls .svelte-kit
generated
output
types

generated tem os módulos internos que ligam as rotas; types tem os arquivos que dão autocompletar no editor; output só existe depois do build, com as versões server e client. Se algo parecer estranho — uma rota que existe no disco e não aparece no site —, apagar .svelte-kit e reiniciar o servidor costuma resolver: ele é reconstruído do zero a cada npm run dev.

Missão: o contador soma tudo o que está em src/routes, inclusive o layout, e mostra 4 arquivos. Conte só as páginas (+page.svelte) e mostre 3 páginas.

<script>
  let arquivos = [
    '+layout.svelte',
    '+page.svelte',
    'paes/+page.svelte',
    'sobre/+page.svelte'
  ];
  let rotas = $derived(arquivos.length);
</script>

<p>{rotas} arquivos</p>
<script>
  let arquivos = [
    '+layout.svelte',
    '+page.svelte',
    'paes/+page.svelte',
    'sobre/+page.svelte'
  ];
  let rotas = $derived(arquivos.filter((a) => a.endsWith('+page.svelte')).length);
</script>

<p>{rotas} páginas</p>

filter devolve uma lista nova só com os itens aprovados no teste; endsWith confere o fim do texto. Como rotas é $derived, se a lista de arquivos mudar, a contagem se atualiza sozinha. É o mesmo raciocínio que o SvelteKit usa para montar o mapa de rotas: ele lê nomes de arquivo, filtra os que importam e conta.

10. A página inicial que veio no pacote

O --template minimal entrega uma página de boas-vindas. Ela é o seu primeiro alvo: apagar e substituir pela página da padaria. O conteúdo original é este:

<h1>Welcome to SvelteKit</h1>
<p>Visit <a href="https://svelte.dev/docs/kit">svelte.dev/docs/kit</a> to read the documentation</p>

Não há nada de mágico nesse arquivo: é um componente Svelte, com HTML e um link. Trocar o conteúdo é a primeira edição de verdade do projeto, e é o que confirma que o servidor de desenvolvimento está observando os arquivos — salve e veja a página mudar sem recarregar.

Missão: a página de boas-vindas ainda é a do pacote. Troque o título por Padaria da Ana e o parágrafo por Pão francês saindo do forno às 6h.

<h1>Welcome to SvelteKit</h1>
<p>Visit <a href="https://svelte.dev/docs/kit">svelte.dev/docs/kit</a> to read the documentation</p>
<h1>Padaria da Ana</h1>
<p>Pão francês saindo do forno às 6h.</p>

O +page.svelte que veio no pacote tem um link externo com https://. O SvelteKit não intercepta links externos: eles recarregam a página, como em qualquer site. Só os endereços do próprio projeto ganham a navegação rápida — o que faz sentido, porque o servidor não tem como montar a outra ponta.

11. Quando dá errado

Os três casos abaixo são do primeiro dia do projeto da Ana. O primeiro é do build, o segundo do servidor de desenvolvimento e o terceiro do próprio comando de criação.

Erro 1 — bloco aberto no arquivo da página

Ela começou um {#if} e salvou antes de fechar. O build mostra o trecho do arquivo, com o circunflexo no ponto exato:

ana@notebook:~/loja/kit$ npm run build
vite v8.4.0 building ssr environment for production...
transforming...
✓ 143 modules transformed.
✗ Build failed in 166ms
error during build:
Build failed with 1 error:

RolldownError: src/routes/sobre/+page.svelte:5:0 Block was left open
https://svelte.dev/e/block_unclosed
 3 |  </script>
 4 |
 5 |  {#if temPao}
       ^
 6 |    <p>Tem pão na prateleira.</p>
 7 |

"Block was left open" é o compilador do Svelte dizendo que o bloco ficou sem fechamento. A posição 5:0 é a linha do {#if}. Enquanto isso, no servidor de desenvolvimento, a página quebra na hora de abrir e o erro aparece no terminal a cada recarregamento.

Erro 2 — a porta escolhida está ocupada

Ao fixar a porta com --strictPort, o Vite não pula para outra livre: ele para. A mensagem é curta e direta, e a pilha de chamadas abaixo dela é ruído para quem está começando.

ana@notebook:~/loja/kit$ npm run dev -- --port 5173 --strictPort

> kit@0.0.1 dev
> vite dev --port 5173 --strictPort

error when starting dev server:
Error: Port 5173 is already in use

Sem --strictPort, o mesmo comando teria subido na 5174 e avisado "trying another one". A opção existe para quando você precisa daquele número (um link fixo, um proxy, um teste automatizado). Para o dia a dia, deixe o Vite escolher e leia a linha "Local".

Erro 3 — criar em cima de uma pasta que já tem coisa

A Ana rodou o comando duas vezes na mesma pasta. O sv não sobrescreve nada em silêncio: pergunta. Como a resposta padrão é "No", ele sai sem tocar nos arquivos.

ana@notebook:~/loja$ npx sv create kit
◆  Directory not empty:
│  Continue?
│  ○ Yes  ● No
└  Exiting.

(A pergunta mostra também o caminho completo da pasta; cortei aqui.) A saída é segura por desenho: o padrão é não mexer. Se você quer mesmo usar a pasta existente, responda "Yes" ou acrescente --no-dir-check; se foi engano, apague a pasta e rode de novo com outro nome.

13. O caminho até aqui

Em quinze minutos a Ana saiu de uma pasta vazia para um site respondendo em localhost, com página inicial, layout, favicon e robôs de busca configurados. Ela não escreveu nenhuma configuração: o sv escreveu, e o papel dela foi escolher as opções e trocar o conteúdo da vitrine.

O que ficou de fora é o que faz esse site virar o site da padaria: as rotas. Isso é Rotas por Arquivo, a próxima aula. Se você quer entender primeiro a ideia geral do Kit, O que é SvelteKit vem antes. E quando aparecer a dúvida "onde coloco esse arquivo?", a resposta está na Estrutura do Projeto do Nível 1.

Complete o código

Crie o projeto e entre na pasta:

Resumo

  • npx sv create kit cria a estrutura; o npx executa o CLI sem instalar globalmente.
  • As opções --template, --types, --no-add-ons e --install respondem ao assistente de uma vez.
  • O projeto nasce com src/routes, src/lib, static, app.html, layout e página inicial.
  • Nesta versão não existe svelte.config.js: a configuração mora no vite.config.js.
  • runes: true força o modo moderno do Svelte no projeto inteiro.
  • npm run dev liga o servidor; se a porta 5173 estiver ocupada, ele usa a próxima e avisa.
  • npm run build gera duas saídas: ssr e client.
  • npm run preview serve o build na porta 4173, para conferir antes de publicar.
  • .svelte-kit e node_modules são geradas: não se editam e não vão para o Git.
  • O aviso do adapter-auto só importa na hora de publicar.
