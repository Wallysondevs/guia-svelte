SvelteKit · +layout.svelte

A Ana mandou fazer um quadro de avisos novo para a padaria: uma moldura de madeira, o vidro e a fechadura. O vidraceiro entregou a moldura e disse uma frase que ela não esqueceu: "aqui dentro vai o que você quiser mostrar, e eu não preciso saber o que é". O +layout.svelte do SvelteKit é essa moldura. Ele aparece no topo de todas as páginas e tem um buraco no meio; cada página entra nesse buraco sem que a moldura saiba qual página é. Nesta aula você vai ver o buraco, o que acontece quando ele falta e como fazer uma moldura só para uma parte do site.

Você vai aprender
  • O que é um layout e por que ele existe.
  • Como o sv create já entrega um layout pronto e o que tem dentro dele.
  • De onde vem children e o que $props() faz com ele.
  • Por que {@render children()} é obrigatório e o que acontece sem ele.
  • Como montar o menu e o rodapé num lugar só e servir todas as páginas.
  • Que a página entra dentro do <main> do layout, não no lugar dele.
  • Como criar um layout que vale só para uma pasta e suas subpastas.
  • Como o layout descobre em qual página a pessoa está.
  • Os três avisos reais do compilador desta aula: sem buraco, com <slot /> e com export let.
  • A diferença entre +layout.svelte e +layout.js.

1. A ideia: a moldura e o que entra nela

Toda padaria tem coisas que se repetem em qualquer canto do balcão: o preço do pão na parede, a placa de "aceitamos cartão", o cartaz do fiado. Se você pendurasse esses avisos separadamente em cada parede, uma mudança de preço viraria uma peregrinação. O que a Ana fez foi criar uma moldura com os avisos fixos e trocar só o papel de dentro conforme o dia. A moldura não sabe o que está no papel; o papel não sabe onde está a moldura.

Um layout no SvelteKit funciona exatamente assim. Ele é um componente como outro, com uma diferença: o SvelteKit chama o layout por fora e a página por dentro. O layout recebe a página pronta num pedaço chamado children e decide onde colocá-la. Se o layout põe children dentro de um <main>, todas as páginas do site aparecem dentro desse <main>. Se o layout põe um menu em cima, o menu aparece em todas.

O ganho é de manutenção. O menu do site da Ana tem quatro links; se ele estivesse copiado em cada +page.svelte, acrescentar o link "Contato" seria quatro edições e a certeza de esquecer uma. Com o layout, é uma edição. O custo é uma camada a mais para entender: quando você abre um +page.svelte, o que está nele não é a página inteira — é só o miolo. A página inteira é a moldura mais o miolo.

Uma diferença importante em relação à parede: no SvelteKit, o layout não escolhe se vai aparecer. Se existe um +layout.svelte numa pasta, tudo o que está naquela pasta e abaixo dela passa por ele. Não há como uma página "escapar" do layout do pai — e é isso que garante que o menu nunca suma numa página nova.

3. O layout que já vem no projeto

Quando o projeto da Ana nasceu, ele já tinha um layout. Todo projeto SvelteKit precisa de pelo menos um, na raiz de src/routes, porque é nele que o SvelteKit encaixa o HTML de qualquer página. Este é o arquivo entregue pelo sv create, copiado do projeto dela:

<script>
	import favicon from '#lib/assets/favicon.svg';

	/** @type {{children: import('svelte').Snippet}} */
	let { children } = $props();
</script>

<svelte:head>
	<link rel="icon" href={favicon} />
</svelte:head>

{@render children()}

Três coisas acontecem nesse arquivo pequeno. O import traz o ícone da aba do navegador da pasta src/lib, usando o apelido #lib que o projeto define no package.json. O <svelte:head> injeta a tag <link> dentro do <head> do documento — repare que o layout não tem <html> nem <body>. E a última linha, sozinha, é o buraco: é ali que a página entra.

let { children } = $props()
o layout recebe a página como propriedade. $props() é a runa que lê o que vem de fora; { children } é a desestruturação que pega só o pedaço chamado children.
children
um snippet (trecho de marcação guardado numa função), não texto. Por isso não se usa {children}: o Svelte mostraria o código da função em vez do conteúdo.
{@render children()}
manda desenhar o snippet naquele ponto. Os parênteses são obrigatórios: children é uma função, e {@render} chama a função.
<svelte:head>
uma tag especial do Svelte: o que está dentro dela vai para o <head> do HTML final, não para o corpo.
/** @type … */
um comentário de tipo do JSDoc, porque o projeto foi criado com --types jsdoc. Ele não roda; só avisa ao editor o que é children.

4. O buraco da moldura: $props e {@render}

Vale desmontar a ideia de children com calma, porque é ela que confunde. No Svelte 5, um componente recebe o que vem de fora através de $props(). Uma página de pão, por exemplo, recebe data com os dados que o load buscou. Um layout recebe duas coisas do SvelteKit: os dados (data, quando existem) e a página (children).

A diferença é o tipo do que chega. data é um objeto comum: você lê data.titulo e pronto. children é um trecho de marcação embrulhado numa função — por isso o {@render children()} e não {children}. O {@render} é a instrução "execute este trecho aqui, neste ponto do HTML". Só isso.

Uma consequência que assusta no começo: se o layout não chamar {@render children()} em nenhum lugar, a página não aparece. O SvelteKit avisa, mas não impede o build. É como entregar a moldura sem o vidro: a moldura está lá, bonita, e o papel do dia não tem onde entrar. Você vai ver o aviso exato na seção de erros.

5. A moldura da Ana: menu, conteúdo e rodapé

Com a ideia entendida, o layout da padaria ficou assim. O menu vive em cima, o rodapé embaixo, e o conteúdo de cada página entra no meio, dentro de um <main>:

<script>
	import favicon from '#lib/assets/favicon.svg';
	/** @type {{children: import('svelte').Snippet}} */
	let { children } = $props();
</script>

<svelte:head>
	<link rel="icon" href={favicon} />
</svelte:head>

<nav>
	<a href="/">Início</a>
	<a href="/paes">Pães</a>
	<a href="/sobre">Sobre</a>
	<a href="/contato">Contato</a>
</nav>

<main>
	{@render children()}
</main>

<footer>Padaria da Ana</footer>

<style>
	nav { display: flex; gap: 12px; padding: 8px 0; }
	nav a { color: #2e7d32; }
	footer { margin-top: 24px; color: #666; font-size: 14px; }
</style>

Note onde o {@render children()} está: dentro do <main>. Isso é uma decisão de projeto, não uma obrigação do SvelteKit. A Ana poderia ter posto o conteúdo antes do menu, ou envolto em dois <div>, ou dentro de um <article>. O layout decide a estrutura; a página só preenche o espaço.

Note também que o <style> está no layout. Ele vale para os elementos do layout — o nav, os links, o footer — e não vaza para as páginas, porque o Svelte põe um selo no seletor (aquele svelte-12qhfyh da aula Seu Primeiro Componente). O main não recebeu o selo porque nenhum seletor o menciona.

6. O que o servidor manda: a página dentro da moldura

A prova de que a moldura é única e as páginas entram nela está no HTML que o servidor envia. A Ana pediu a página /sobre e recortou do HTML a parte que interessa, tirando os comentários internos do Svelte com um sed para a leitura ficar limpa:

ana@notebook:~/loja/kit$ curl -s localhost:4173/sobre | sed -e 's/<!--[^>]*-->//g' | grep -o '<nav.*</footer>'
<nav class="svelte-12qhfyh"><a href="/" class="svelte-12qhfyh">Início</a> <a href="/paes" class="svelte-12qhfyh">Pães</a> <a href="/sobre" class="svelte-12qhfyh">Sobre</a> <a href="/contato" class="svelte-12qhfyh">Contato</a></nav> <main><h1>Sobre</h1> <p>A padaria abriu em 1998, na esquina da rua das Flores.</p></main> <footer class="svelte-12qhfyh">Padaria da Ana</footer>

Leia a linha inteira como uma fita: abre o nav, fecha o nav, abre o main, e dentro do main estão o <h1>Sobre</h1> e o parágrafo do arquivo sobre/+page.svelte. Depois fecha o main e vem o footer. O HTML do layout vem antes e depois do HTML da página — a intercalação é feita pelo SvelteKit, não por você.

O mesmo comando em / e em /paes mostra o mesmo nav e o mesmo footer, com miolos diferentes:

ana@notebook:~/loja/kit$ curl -s localhost:4173/ | sed -e 's/<!--[^>]*-->//g' | grep -o '<main.*</main>'
<main><h1>Padaria da Ana</h1> <p>Pão francês saindo do forno às 6h.</p> <a href="/paes">ver os pães</a></main>
ana@notebook:~/loja/kit$ curl -s localhost:4173/paes | sed -e 's/<!--[^>]*-->//g' | grep -o '<main.*</main>'
<main><h1>Pães</h1> <ul><li><a href="/paes/frances">Pão francês</a></li> <li><a href="/paes/forma">Pão de forma</a></li> <li><a href="/paes/queijo">Pão de queijo</a></li></ul></main>

Duas páginas, um layout, zero repetição. E repare que o <a href="/paes"> da página inicial continua sendo um link comum no HTML — é no navegador que o SvelteKit intercepta o clique para trocar de página sem recarregar.

Missão: a moldura está montada e o papel do dia ficou de fora: o <main> está vazio. Ponha o conteúdo dentro do <main> com {@render conteudo()}. No SvelteKit esse trecho vem de children; aqui ele foi declarado no próprio arquivo para você ver o buraco funcionando.

<script>
  let paginas = { '/': 'Padaria da Ana', '/paes': 'Pães' };
  let caminho = $state('/paes');
</script>

{#snippet conteudo()}
  <h1>{paginas[caminho]}</h1>
{/snippet}

<nav>Início · Pães · Sobre</nav>
<main></main>
<footer>Padaria da Ana</footer>
<script>
  let paginas = { '/': 'Padaria da Ana', '/paes': 'Pães' };
  let caminho = $state('/paes');
</script>

{#snippet conteudo()}
  <h1>{paginas[caminho]}</h1>
{/snippet}

<nav>Início · Pães · Sobre</nav>
<main>{@render conteudo()}</main>
<footer>Padaria da Ana</footer>

Uma coisa que a caixa mostra e o SvelteKit esconde: o snippet conteudo é declarado antes de ser usado, mas aparece na tela depois do nav, porque o {@render} está no meio do HTML. A posição do {@render} é a posição do conteúdo — nada mais.

7. Um layout só para uma pasta

A padaria tem uma parte pública e uma parte restrita, onde só a Ana entra para ver as encomendas. Um aviso "Área restrita" no topo do site inteiro seria feio; repetir o aviso em cada página restrita seria pior. A solução é um layout dentro da pasta: ele vale para a pasta e para tudo o que estiver abaixo dela.

<script>
	/** @type {{children: import('svelte').Snippet}} */
	let { children } = $props();
</script>

<aside>Área restrita</aside>
{@render children()}

O resultado é um layout dentro do outro. O layout raiz desenha o nav, o main e o footer; dentro do main entra o layout da pasta, que desenha o aside; e dentro do aside entra a página. O HTML confirma a ordem:

ana@notebook:~/loja/kit$ curl -s localhost:4173/admin | sed -e 's/<!--[^>]*-->//g' | grep -o '<main.*</main>'
<main><aside>Área restrita</aside> <h1>Painel</h1> <p>Só a Ana entra aqui.</p></main>

O aside está dentro do main porque foi ali que o layout raiz pôs o buraco dele. Se o layout raiz tivesse posto o buraco fora do main, o mesmo aside apareceria fora. Essa é a regra: cada layout decide onde fica o próprio buraco, e o layout de dentro sempre entra no buraco do de fora.

8. O layout sabe onde a pessoa está

O layout não recebe a página como texto, mas recebe o endereço. É o suficiente para o menu marcar o item atual: basta comparar o caminho de cada link com page.url.pathname, de $app/state. A versão da Ana usa uma variável no lugar do módulo, para você ver a lógica sem o servidor:

Missão: o menu mostra os três links, mas nada indica onde a pessoa está. Quando o link for o caminho atual, acrescente um • depois do texto. O caminho é /paes.

<script>
  let caminho = $state('/paes');
  let itens = ['/', '/paes', '/sobre'];
</script>

<nav>
  {#each itens as item}
    <a href={item}>{item}</a>
  {/each}
</nav>
<script>
  let caminho = $state('/paes');
  let itens = ['/', '/paes', '/sobre'];
</script>

<nav>
  {#each itens as item}
    <a href={item}>{item}{#if item === caminho} •{/if}</a>
  {/each}
</nav>

No projeto de verdade, a linha do caminho desaparece e entra o import: import { page } from '$app/state', e a comparação vira item === page.url.pathname. Como page é reativo, ao navegar o menu se atualiza sozinho — sem ninguém avisar.

9. Layout que decide o que mostrar

Como o layout recebe data, ele também pode decidir o que aparece. Imagine que a Ana queira mostrar o painel só para quem entrou. O layout do grupo verifica o dado e escolhe entre o conteúdo e um convite para entrar. É a mesma ideia de {#if} da aula {#if}, só que aplicada à moldura em vez da página.

Missão: a pessoa não está logada (entrou é false) e a área restrita sumiu sem explicação. Faça o layout mostrar entre para ver quando ninguém tiver entrado.

<script>
  let entrou = $state(false);
</script>

{#snippet pagina()}
  <h1>Painel</h1>
{/snippet}

<nav>Início · Pães</nav>
{#if entrou}
  <aside>Área restrita</aside>
  <main>{@render pagina()}</main>
{/if}
<script>
  let entrou = $state(false);
</script>

{#snippet pagina()}
  <h1>Painel</h1>
{/snippet}

<nav>Início · Pães</nav>
{#if entrou}
  <aside>Área restrita</aside>
  <main>{@render pagina()}</main>
{:else}
  <p>entre para ver</p>
{/if}

O {:else} é o par do {#if}: o que fazer quando a condição é falsa. Sem ele, o layout simplesmente não desenha nada e a tela fica com um vazio sem explicação — o pior tipo de erro de interface, porque não há mensagem para procurar.

10. +layout.js não é +layout.svelte

Os dois moram na mesma pasta e têm nomes parecidos, mas fazem coisas opostas. O .svelte desenha; o .js busca dados para o layout e para as páginas abaixo dele. A tabela resume; a aula Parâmetros de Rota já mostra o load em ação.

ArquivoO que fazRoda onde
+layout.sveltedesenha a moldura e o buraco childrenservidor e navegador
+layout.jsload que devolve dados para o layout e as páginas filhasservidor e navegador
+layout.server.jso mesmo, mas só no servidor (segredos, banco)só servidor
+page.svelteo miolo que entra no buracoservidor e navegador

O data que chega ao layout é a soma do que os +layout.js acima devolveram com o que o próprio layout devolveu. Um layout pode passar dado para baixo; uma página não passa dado para o layout. Isso parece uma limitação e é, na verdade, a garantia de que a moldura funciona mesmo quando a página não existe — no 404, por exemplo, o layout continua lá.

11. Quando dá errado

Os dois primeiros avisos abaixo saíram do npm run build do projeto da Ana e não impedem o build: o site sobe, mas o conteúdo não aparece. O terceiro é erro e para tudo. Onde a saída original traz o caminho completo, o recorte ficou com o nome do arquivo.

Aviso 1 — falta o buraco da moldura

A Ana reescreveu o layout para experimentar um menu novo e esqueceu de recolocar o {@render children()}. O build terminou, o site respondeu 200, e todas as páginas ficaram sem conteúdo.

ana@notebook:~/loja/kit$ npm run build
vite v8.4.0 building ssr environment for production...
transforming...
layout_children_missing
`src/routes/+layout.svelte`: `<slot />` or `{@render ...}` tag missing — inner content will not be rendered
https://svelte.dev/e/kit/layout_children_missing
✓ 143 modules transformed.

A frase "inner content will not be rendered" é literal: o conteúdo de dentro não será desenhado. O aviso vem antes do ✓ e o build continua — por isso é fácil passar batido. Se uma página aparecer em branco, procure o {@render children()} antes de qualquer outra coisa.

Aviso 2 — <slot /> é do Svelte antigo

Quem aprendeu Svelte antes da versão 5 escrevia <slot /> no lugar do buraco. Ainda funciona em componentes no modo antigo, mas o projeto da Ana força as runas, e o compilador avisa:

ana@notebook:~/loja/kit$ npm run build
vite v8.4.0 building ssr environment for production...
transforming...
5:01:15 PM [vite-plugin-svelte] src/routes/+layout.svelte:2:0 Using `<slot>` to render parent content is deprecated. Use `{@render ...}` tags instead
https://svelte.dev/e/slot_element_deprecated
1: <nav><a href="/">Início</a></nav>
2: <slot />
           ^
3:

O circunflexo aponta para o fechamento da tag. A troca é direta: no lugar de <slot />, use {@render children()}, e não esqueça de pedir children com let { children } = $props(). As duas peças andam juntas: uma recebe, a outra desenha.

Erro 3 — export let no modo moderno

Outro hábito do Svelte antigo: declarar a propriedade com export let children. No modo das runas, isso é recusado antes de qualquer coisa rodar:

ana@notebook:~/loja/kit$ npm run build
vite v8.4.0 building ssr environment for production...
transforming...
✓ 141 modules transformed.
✗ Build failed in 356ms
error during build:
Build failed with 1 error:

RolldownError: src/routes/+layout.svelte:2:1 Cannot use `export let` in runes mode — use `$props()` instead
https://svelte.dev/e/legacy_export_invalid

A mensagem diz o remédio: use $props(). A posição 2:1 é a linha do export let. "runes mode" é o modo moderno, em que as runas ($state, $props, $derived) são a forma de declarar as coisas; o projeto da Ana foi criado já nesse modo.

13. O caminho até aqui

O site da Ana agora tem uma moldura só, um menu só e um rodapé só, servindo todas as páginas — inclusive a de erro, o que dá um ar de site cuidado quando alguém digita um endereço errado. A parte restrita ganhou uma moldura menor, dentro da maior, sem tocar no menu público.

A pergunta que sobra é o que colocar nesse buraco quando o caminho não corresponde a nenhuma página, ou quando o load chama error(404, …). É o assunto de +error.svelte. E se você quiser agrupar rotas sem que a pasta apareça na URL — como o (painel) desta aula —, o caminho é Grupos de Rotas.

Resumo

  • +layout.svelte é a moldura: envolve as páginas da pasta e das subpastas.
  • O layout recebe a página em children e a desenha com {@render children()}.
  • children é snippet, não texto: use {@render}, nunca {children}.
  • Sem o {@render children()}, o build passa com o aviso layout_children_missing e as páginas ficam em branco.
  • <slot /> é do Svelte antigo; no modo das runas, o aviso é slot_element_deprecated.
  • export let children é recusado no modo das runas: use $props().
  • O layout raiz envolve tudo, inclusive a página de erro; layouts em pastas envolvem só aquela parte.
  • O conteúdo da página entra dentro do HTML do layout, no ponto do {@render}.
  • page.url.pathname diz ao layout (ou ao menu) em que página a pessoa está.
  • +layout.js busca dados; +layout.svelte desenha. Dado desce, nunca sobe.
