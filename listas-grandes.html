Svelte · Listas Grandes

O mural de avisos da padaria virou o mural da rua inteira: cinco mil papéis, um por cliente. A Ana quer mostrar todos na tela, e o navegador dela começa a engasgar — a página demora a aparecer, o dedo rola e nada se move, o botão de fechar não responde. O problema não é ter cinco mil avisos guardados; é tentar desenhar os cinco mil de uma vez. Esta aula ensina a desenhar por partes, a esperar o desenho terminar e a deixar o navegador pular o que ninguém está olhando.

Você vai aprender
  • Por que uma lista grande trava a tela mesmo com o computador sobrando.
  • A diferença entre guardar cinco mil itens e desenhar cinco mil elementos.
  • Como desenhar por lotes com slice e um botão.
  • Como usar requestAnimationFrame para espalhar o trabalho em quadros.
  • Por que efeito não roda no servidor e o que isso muda na saída.
  • Como esperar o Svelte terminar de desenhar com tick().
  • Por que a chave do {#each} importa quando a lista muda.
  • Como pedir ao navegador que pule o que está fora da tela com content-visibility.
  • Quando paginar, quando carregar aos poucos e quando só ignorar o problema.
  • Os três erros reais desta aula, com a mensagem do compilador.

1. A ideia: o mural e o pincel

Imagine que a Ana precise pintar cinco mil plaquinhas de aviso. Ela tem tinta e tem tempo; o que ela não tem é cinco mil mãos ao mesmo tempo. Se ela pintar uma por uma, sem parar, o trabalho termina — mas ninguém consegue falar com ela enquanto isso, porque ela está ocupada. É exatamente o que acontece quando o navegador recebe a ordem de desenhar cinco mil elementos: ele desenha um atrás do outro e fica surdo para o resto, inclusive para o clique no botão de fechar.

Guardar cinco mil avisos numa lista é barato: são cinco mil pedaços de texto na memória, e o computador nem sente. O caro é transformar cada um num elemento da página, com estilo, posição e evento. Cada elemento é uma caixinha que o navegador precisa calcular e pintar. Multiplique por cinco mil e o trabalho de um quadro de tela passa a levar mais de um segundo — e a pessoa vê a página travada.

A solução tem três nomes, e todos querem dizer "faça menos trabalho de uma vez": desenhar por lotes (cem agora, cem no próximo quadro), deixar o navegador pular o que está fora da tela, e medir antes de otimizar, porque às vezes a lista nem é grande o bastante para o esforço.

No muralNo componente
Os cinco mil papéis guardados na gavetaa lista avisos na memória
Os papéis pregados na paredeos elementos que o {#each} cria no DOM
Pintar tudo de uma vez e sumir do balcãodesenhar cinco mil de uma vez e travar a página
Pintar cem, atender o cliente, pintar mais cemlotes com requestAnimationFrame
Deixar o papel de lado até alguém olharcontent-visibility: auto

O vocabulário: DOM é a árvore de elementos que o navegador desenha; quadro é uma passada de desenho, umas sessenta por segundo num monitor comum; lote é um pedaço do trabalho; e tick é o aviso de que o Svelte terminou de aplicar as mudanças. Quatro palavras que separam "funciona" de "funciona sem travar".

2. O problema: cinco mil de uma vez

Comece com a lista inteira, do jeito mais direto. O componente abaixo cria cinco mil avisos com Array.from e desenha todos com um {#each}. Na tela não parece muito; no DOM, é uma parede de cinco mil elementos.

<script>
  const avisos = Array.from({ length: 5000 }, (_, i) => `Aviso ${i + 1}`);
</script>

<p>O mural tem {avisos.length} avisos.</p>

<ul>
  {#each avisos.slice(0, 3) as aviso}
    <li>{aviso}</li>
  {/each}
</ul>

Para não publicar cinco mil linhas de saída, este primeiro exemplo mostra só os três primeiros. O número no começo é o que importa:

<p>O mural tem 5000 avisos.</p> <ul><li>Aviso 1</li><li>Aviso 2</li><li>Aviso 3</li></ul>
Array.from({ length: 5000 })
cria uma lista de cinco mil posições. O segundo argumento, (_, i) => …, preenche cada posição; o _ é o valor que não usamos e o i é o índice.
{avisos.length}
quantos itens existem. O número sai na tela e é a prova de que a lista está completa, mesmo quando o desenho é só de um pedaço.
avisos.slice(0, 3)
a fatia dos três primeiros. Fatiar aqui é uma escolha de quem escreve o exemplo: sem ela, o {#each} desenharia os cinco mil.
{#each avisos.slice(0, 3) as aviso}
um bloco repetido por item da fatia. Cada volta cria um <li> de verdade no DOM.
{aviso}
o texto do item atual. Um item de lista grande quase sempre é um objeto; aqui é texto para o exemplo caber na cabeça.

O custo aparece quando o {#each} recebe a lista inteira. Cada item vira um elemento, e cada elemento precisa ser criado, medido e pintado. O navegador faz isso num único quadro; enquanto ele está ocupado, o clique na tela espera na fila. Não é a memória que acaba — é o tempo do quadro que estoura.

Cinco mil não é o número mágico

A conta muda com o tamanho de cada item e com a máquina da pessoa. Um celular simples começa a engasgar com algumas centenas de cartões com imagem; um notebook novo desenha alguns milhares sem reclamar. O número que importa é o que a sua tela mostra sem travar, e ele se descobre medindo, não adivinhando.

3. Desenhar por lotes

A primeira defesa é simples: desenhe um lote e deixe o resto para depois. O estado guarda quantos itens já estão na tela, e o {#each} recebe uma fatia desse tamanho. O botão "mais 500" aumenta o número, e mais quinhentos elementos aparecem.

<script>
  const avisos = Array.from({ length: 5000 }, (_, i) => `Aviso ${i + 1}`);
  const LOTE = 500;

  let quantos = $state(LOTE);
  let visiveis = $derived(avisos.slice(0, quantos));
</script>

<p>Desenhando {visiveis.length} de {avisos.length}</p>
<p>Último: {visiveis.at(-1)}</p>

<button onclick={() => (quantos += LOTE)}>mais {LOTE}</button>

O HTML sai com o primeiro lote já desenhado, e o botão mostra o tamanho do próximo:

<p>Desenhando 500 de 5000</p> <p>Último: Aviso 500</p> <button>mais 500</button>

Repare no visiveis.at(-1): ele devolve o último item da fatia, e é uma forma barata de mostrar na tela que o lote chegou até o fim. O at(-1) conta de trás para a frente — -1 é o último, -2 o penúltimo — e evita a conta visiveis[visiveis.length - 1], que é a mesma coisa escrita com mais caracteres.

Missão: o botão diz "mais 100" e soma 1. Faça ele somar um lote de 100 e chegar a 150 de 300 depois de um clique.

<script>
  const avisos = Array.from({ length: 300 }, (_, i) => `Aviso ${i + 1}`);
  const LOTE = 100;
  let quantos = $state(50);
</script>

<p>{quantos} de 300</p>
<button onclick={() => (quantos += 1)}>mais 100</button>
<script>
  const avisos = Array.from({ length: 300 }, (_, i) => `Aviso ${i + 1}`);
  const LOTE = 100;
  let quantos = $state(50);
</script>

<p>{quantos} de 300</p>
<button onclick={() => (quantos += LOTE)}>mais 100</button>

Essa solução resolve o travamento, mas tem um custo de paciência: para chegar ao fim de cinco mil itens, a pessoa precisa clicar dez vezes. É o mesmo trade-off da paginação, com uma diferença: ali a tela mostrava uma página por vez e o número era explícito; aqui a lista cresce e a rolagem continua de onde estava.

4. Espalhar o trabalho em quadros

Em vez de esperar o clique, o componente pode desenhar sozinho, um lote por quadro. Quem marca o próximo quadro é requestAnimationFrame: você entrega uma função e o navegador a chama antes de pintar o próximo quadro. Entre um quadro e outro, ele atende o clique, a rolagem e o que mais estiver esperando.

<script>
  const avisos = Array.from({ length: 5000 }, (_, i) => `Aviso ${i + 1}`);
  const LOTE = 500;

  let quantos = $state(0);

  $effect(() => {
    function passo() {
      quantos = Math.min(quantos + LOTE, avisos.length);
      if (quantos < avisos.length) requestAnimationFrame(passo);
    }
    requestAnimationFrame(passo);
  });
</script>

<p>{quantos} de {avisos.length} avisos desenhados</p>

<ol>
  {#each avisos.slice(0, quantos) as aviso}
    <li>{aviso}</li>
  {/each}
</ol>

Aqui a saída do compilador mostra zero, e isso não é defeito:

<p>0 de 5000 avisos desenhados</p> <ol></ol>

O {#each} recebeu uma fatia de zero itens porque o estado começa em zero e quem o aumenta é um $effect. Efeito é código que só existe no navegador: no servidor não há tela para atualizar, e o Svelte não executa efeitos durante a renderização do servidor. Por isso o HTML devolvido mostra o estado inicial e a lista vazia. No navegador, o primeiro quadro desenha 500, o segundo 1000, e assim por diante.

Um cuidado que vale a pena registrar: um $effect que muda o estado que ele mesmo lê entra em laço, e o navegador interrompe com https://svelte.dev/e/effect_update_depth_exceeded. No exemplo acima o efeito escreve em quantos e não lê quantos fora da função passo, que roda por quadro — por isso ele para no fim da lista.

Esse detalhe muda como você escreve componentes que vão rodar nos dois lugares. Se a lista precisa aparecer completa já no primeiro HTML — por causa de busca ou de leitor de tela —, o lote inicial não pode ser zero. Uma saída comum é começar com um lote pequeno, tipo 50, e deixar o efeito cuidar do resto.

5. Esperar o desenho terminar: tick()

Quando você muda um estado, o Svelte não redesenha na mesma linha: ele anota a mudança e desenha no fim do trabalho atual. Isso é ótimo para desempenho, porque dez mudanças seguidas viram um desenho só. E é uma armadilha quando você precisa ler o DOM logo depois de mudar o estado, porque o DOM ainda está velho.

A função tick() devolve uma promessa que resolve quando as mudanças pendentes forem aplicadas. Ela vem do pacote svelte e é importada como qualquer outra função. Quem espera com await recebe o controle depois do desenho, com o DOM atualizado.

<script>
  import { tick } from 'svelte';

  const avisos = Array.from({ length: 500 }, (_, i) => `Aviso ${i + 1}`);
  let quantos = $state(0);
  let noDom = $state(0);

  async function desenhar() {
    quantos = avisos.length;
    await tick();
    noDom = document.querySelectorAll('li').length;
  }
</script>

<p>{noDom} itens no DOM</p>
<button onclick={desenhar}>desenhar</button>

<ul>
  {#each avisos.slice(0, quantos) as aviso}
    <li>{aviso}</li>
  {/each}
</ul>
<p>0 itens no DOM</p> <button>desenhar</button> <ul></ul>

Sem o await tick(), a conta sairia com o número antigo: a função mudou quantos para 500, mas o DOM ainda tinha zero elementos quando a medição rodou. Esse "zero" é o tipo de número que faz alguém desconfiar do Svelte quando o problema está na ordem em que o código roda.

Missão: o botão mede antes de o Svelte desenhar e mostra 0 itens no DOM. Faça a medição acontecer depois do desenho e mostrar 300 itens no DOM.

Medir o DOM com document.querySelectorAll funciona dentro do componente, mas não é o jeito mais Svelte de fazer as coisas: o estado já sabe quantos itens existem. Use tick() quando precisar falar com uma biblioteca de fora — um gráfico, um mapa, um editor — que só aceita medidas do DOM pronto.

6. A chave de cada item

Quando a lista muda — um item entra, outro sai, a ordem troca —, o Svelte precisa saber qual elemento corresponde a qual item. A chave, aquele parêntese depois do as, responde isso. Sem chave, ele usa a posição; com chave, ele usa a identidade que você escolher.

<script>
  let avisos = $state([
    { id: 7, texto: 'Pão saindo do forno' },
    { id: 8, texto: 'Bolo de fubá na promoção' }
  ]);
</script>

<ul>
  {#each avisos as aviso (aviso.id)}
    <li>{aviso.texto}</li>
  {/each}
</ul>

<button onclick={() => avisos.unshift({ id: 6, texto: 'Forno ligado' })}>
  chegar aviso novo
</button>
<ul><li>Pão saindo do forno</li><li>Bolo de fubá na promoção</li></ul> <button>chegar aviso novo</button>

O botão coloca um aviso novo no começo da lista com unshift. Com a chave (aviso.id), o Svelte reconhece os dois avisos antigos e move os elementos em vez de recriá-los; no navegador, o resultado é o mesmo, mas o custo é menor e o foco do teclado não se perde. Sem chave, ele recria os três, e qualquer coisa que estivesse dentro do elemento — um campo digitado, uma imagem carregada — se perde.

A chave precisa ser única na lista e estável entre uma renderização e outra. O índice da posição é a pior chave possível: quando um item entra no começo, todos os índices mudam e o Svelte conclui que todos os itens são novos. Use o id que veio do banco ou um identificador criado na hora em que o item nasceu. Se duas linhas receberem a mesma chave, o navegador interrompe a montagem com https://svelte.dev/e/each_key_duplicate — o endereço é a própria mensagem, em produção.

7. Deixar o navegador pular o que não aparece

Existe uma ajuda que não muda nada no JavaScript: uma propriedade de CSS chamada content-visibility. Com o valor auto, o navegador pula o desenho dos elementos que estão fora da área visível e calcula só quando eles se aproximam da tela. Os cinco mil elementos continuam no DOM; o que muda é quanto trabalho de pintura eles custam.

<script>
  const avisos = Array.from({ length: 5000 }, (_, i) => `Aviso ${i + 1}`);
</script>

<ul>
  {#each avisos as aviso}
    <li class="cartao">{aviso}</li>
  {/each}
</ul>

<style>
  .cartao {
    content-visibility: auto;
    contain-intrinsic-size: auto 40px;
    padding: 4px 0;
    border-bottom: 1px solid #ddd;
  }
</style>

O CSS que o compilador gerou leva o selo do componente em cada seletor:

.cartao.svelte-1n46o8q {
    content-visibility: auto;
    contain-intrinsic-size: auto 40px;
    padding: 4px 0;
    border-bottom: 1px solid #ddd;
  }

O contain-intrinsic-size é o par obrigatório dessa técnica: sem ele, o navegador não sabe a altura de um elemento que ainda não desenhou, e a barra de rolagem fica pulando. Declarar uma altura estimada — auto 40px quer dizer "quarenta pixels, ou a altura real se ela já for conhecida" — mantém a rolagem estável.

O custo é que a técnica não ajuda a criar os elementos, só a pintá-los. Criar cinco mil nós ainda leva tempo; o ganho vem na rolagem e na memória de pintura. Para listas realmente grandes, o caminho é combinar: fatiar para criar menos e content-visibility para pintar menos.

8. Três jeitos de domar uma lista grande

Não existe uma resposta única. Cada técnica resolve um problema diferente, e a escolha depende do que a pessoa precisa fazer com a lista.

TécnicaO que resolveCusto
Paginarpoucos elementos no DOM e um número de página explícitoa pessoa não vê o todo; precisa clicar
Lotes com botãoa lista cresce sem perder a posição da rolagemdez cliques para chegar ao fim
Lotes automáticosa tela responde enquanto o resto chegamais código e um estado a mais para cuidar
content-visibilitypintura e rolagem de listas já criadasnão reduz a criação dos elementos
Busca e filtromostrar menos itens porque a pessoa pediu menosdepende de a pessoa saber o que procura

A ordem em que eu tentaria: primeiro filtrar (a lista de cinco mil raramente precisa aparecer inteira), depois paginar ou lotear, e só então mexer em CSS. O ganho maior quase sempre vem de mostrar menos itens, não de desenhar os mesmos itens mais rápido.

9. Medir antes de otimizar

Otimizar sem medir é chutar. A pergunta "está lento?" tem uma resposta numérica: quantos elementos existem no DOM e quanto tempo o navegador leva para desenhar. As ferramentas do navegador mostram isso no painel de desempenho, e um contador na própria tela já resolve a dúvida do dia a dia. Para o exemplo caber nesta página, ele mostra só os números; o {#each} que desenha os itens é o mesmo da seção 3.

<script>
  const avisos = Array.from({ length: 5000 }, (_, i) => `Aviso ${i + 1}`);
  const LOTE = 500;

  let quantos = $state(LOTE);
  let restantes = $derived(avisos.length - quantos);
</script>

<p>Desenhados: {quantos}</p>
<p>Faltando: {restantes}</p>

<button onclick={() => (quantos += LOTE)}>mais {LOTE}</button>

O componente conta o que está desenhado e o que falta, em vez de esconder o número:

<p>Desenhados: 500</p> <p>Faltando: 4500</p> <button>mais 500</button>

Esse contador é a diferença entre "acho que ficou mais rápido" e "ficou mais rápido". Se o número de elementos não mudou, o ganho veio de outro lugar — do CSS, da memória, do cache. E se a lista tem trinta itens, o número vai dizer que não havia problema nenhum, o que também é uma informação útil.

10. Quando dá errado

As três mensagens abaixo saíram do compilador e do navegador desta versão, copiadas como estão.

Erro 1 — requestAnimationFrame no servidor

Este erro aparece quando o componente roda também no servidor. A função é do navegador e não existe lá.

<script>
  let avisos = $state(['Aviso 1', 'Aviso 2']);
  requestAnimationFrame(() => console.log('desenhei'));
</script>

<p>{avisos.length} avisos</p>
Erro ao renderizar: requestAnimationFrame is not defined

A tradução: "não conheço esse nome". A defesa é chamar o requestAnimationFrame dentro de um $effect ou de um onMount, que só rodam no navegador. Chamar no corpo do <script> executa no servidor também, e é aí que quebra.

Erro 2 — medir o DOM antes de ele existir

Aqui a medição está no corpo do <script>, que roda também no servidor, onde não existe document.

<script>
  const avisos = Array.from({ length: 5000 }, (_, i) => `Aviso ${i + 1}`);
  const total = document.querySelectorAll('li').length;
</script>

<p>{total} itens no DOM</p>
Erro ao renderizar: document is not defined

document is not defined aparece para qualquer coisa do navegador usada no servidor: document, window, localStorage. A correção é a mesma do erro 1: mover a medição para um $effect ou para dentro de uma função chamada por um clique.

Erro 3 — fatiar o que não é lista

O nome avisos sugere lista, mas o valor é um número. O compilador aceita; o erro aparece na hora de desenhar.

<script>
  let avisos = $state(5000);
  let visiveis = $derived(avisos.slice(0, 500));
</script>

<p>{visiveis.length}</p>
Erro ao renderizar: avisos.slice is not a function

"is not a function" quer dizer que o valor antes do ponto não tem essa função. Cinco mil é um número, não uma lista: para gerar a lista, use Array.from({ length: 5000 }, …), como na seção 2.

Exercícios

1. O que trava a página numa lista de cinco mil itens?

2. Para que serve await tick()?

3. O que content-visibility: auto faz?

Complete o código

let visiveis = $derived(avisos.(0, quantos));

// só os primeiros "quantos" itens vão para a tela

Resumo

  • Guardar muitos itens é barato; desenhar muitos elementos de uma vez é caro.
  • Desenhe por lotes: o estado guarda quantos itens já estão na tela e o {#each} recebe a fatia.
  • requestAnimationFrame espalha o trabalho em quadros e deixa a página responder no meio.
  • Efeitos não rodam no servidor: por isso o HTML do servidor pode mostrar a lista vazia.
  • await tick() espera o DOM ficar pronto antes de medir.
  • A chave (item.id) precisa ser única e estável; o índice é a pior escolha.
  • content-visibility: auto com contain-intrinsic-size alivia a pintura.
  • Filtrar costuma resolver mais que otimizar: mostrar menos é mais barato que desenhar rápido.
  • Meça antes: um contador de elementos na tela responde "está lento?" com número.
  • O tamanho do arquivo e o tamanho do DOM são custos diferentes, medidos de formas diferentes.
