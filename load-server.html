SvelteKit · +page.server.js

A Ana guarda o caderno de encomendas numa gaveta que só ela abre. O balcão mostra a lista pronta, mas o caderno em si ninguém leva embora. No SvelteKit essa gaveta é o arquivo +page.server.js: um load que roda só no servidor e por isso pode abrir arquivos, ler cookies e usar senhas sem que nada disso chegue ao navegador. É a mesma ideia da aula anterior, com uma porta a mais trancada.

Você vai aprender
  • Para que serve o +page.server.js e quando escolher ele.
  • Como ler um arquivo do disco com node:fs dentro do load.
  • Por que esse arquivo nunca é baixado pelo navegador.
  • O que pode e o que não pode voltar de um load de servidor.
  • O que são cookies, locals e parent no evento.
  • Como importar seus próprios módulos com #lib — e por que $lib saiu.
  • O erro load_not_serializable e o que ele protege.
  • Como conferir a rota com curl e o que o código 403 revela.
  • Três erros reais, copiados do terminal do projeto.
  • A diferença prática entre este arquivo e o +page.js.

1. A ideia: o caderno que fica na gaveta

Toda padaria tem dois tipos de informação. O preço do pão pode ficar na parede: se o cliente ver, ótimo. O caderno de fiado, não. Ele tem nome, dívida e às vezes um comentário que ninguém precisa ler. Guardar esse caderno na parede seria um desastre; guardá-lo na gaveta e mostrar só o total é o certo.

Site funciona igual. Alguns dados são públicos: a lista de pães, o horário de funcionamento, a foto da vitrine. Outros são internos: a chave da API dos Correios, a senha do banco, o caminho de um arquivo no disco, o histórico de compras de uma pessoa. A regra é simples e não tem exceção: o que o navegador recebe, o visitante pode ler. Não existe "escondido no JavaScript"; o código do navegador é público.

O +page.server.js é a gaveta. O load escrito nele roda no computador do servidor, tem acesso ao disco e aos cookies da requisição, e devolve apenas o resultado — o total, o nome, a lista já filtrada. O navegador nunca vê o caderno, só o bilhete que saiu dele.

Na padariaNo SvelteKit
O caderno de fiado na gavetaUm arquivo lido com node:fs
A chave da gavetaA variável de ambiente com a senha
O bilhete com o totalO objeto do return
Quem pergunta "sou eu?"O cookie da sessão, lido no cookies
O balcão aberto para a ruaO +page.svelte, que vai para o navegador

O nome do arquivo não é enfeite: o .server no meio é a garantia. O SvelteKit compila esse arquivo só para o lado do servidor e, se você tentar importá-lo de um componente, o build recusa. Isso é diferente de "eu prometo que não uso no navegador" — é o empacotador que impede.

2. O primeiro +page.server.js

A rota /encomendas da Ana mostra as retiradas do dia. Os dados moram num arquivo JSON na pasta dados/ do projeto, fora de src. Ler esse arquivo é trabalho de servidor, então o arquivo é +page.server.js:

import { readFile } from 'node:fs/promises';

export async function load() {
	const texto = await readFile('dados/encomendas.json', 'utf8');
	const encomendas = JSON.parse(texto);

	const total = encomendas.reduce((soma, e) => soma + e.total, 0);

	return {
		encomendas,
		total,
		carregadoEm: new Date().toLocaleTimeString('pt-BR')
	};
}

Compare com a aula anterior: nenhum fetch, nenhum url. Aqui o dado está no disco, e quem lê o disco é o readFile do módulo node:fs/promises. Esse módulo não existe no navegador — e é justamente por isso que o arquivo precisa ser .server.

O componente que recebe o pacote não muda nada em relação à aula anterior. Ele declara data, desenha o total com duas casas e faz uma tabela com uma linha por encomenda:

<script>
	let { data } = $props();
</script>

<h1>Encomendas para retirada</h1>
<p>Total do dia: R$ {data.total.toFixed(2)}</p>
<p>Lido do servidor às {data.carregadoEm}</p>

<table>
	<tbody>
	{#each data.encomendas as e}
		<tr>
			<td>{e.cliente}</td>
			<td>{e.itens} item(ns)</td>
			<td>{e.retirada}</td>
		</tr>
	{/each}
	</tbody>
</table>

Missão: o servidor somou as três encomendas e devolveu total. Faça a conta certa: o total tem de ser R$ 90.50.

O reduce percorre a lista guardando um acumulador. O segundo argumento, 0, é o valor inicial; a função recebe o acumulador e o item e devolve o novo acumulador. Trocar + por - não gera erro nenhum — gera -90.50, um número perfeitamente válido e completamente errado. É o tipo de defeito que só a conferência pega.

3. A anatomia do arquivo de servidor

import { readFile } from 'node:fs/promises'
ferramenta do Node para ler arquivo sem travar o servidor. Só existe no servidor, e é por isso que este arquivo é .server.
readFile('dados/encomendas.json', 'utf8')
o caminho é relativo à raiz do projeto, onde o npm run dev foi iniciado. O 'utf8' diz que o conteúdo é texto, não bytes.
JSON.parse(texto)
transforma o texto do arquivo em lista de objetos. Se o arquivo tiver uma vírgula sobrando, este é o ponto que estoura.
new Date().toLocaleTimeString('pt-BR')
roda no servidor, no fuso da máquina. Serve para provar que o valor foi calculado agora, e não no navegador.
return { encomendas, total, carregadoEm }
só dados. O que sai daqui é o que o navegador recebe; o resto fica.

Uma diferença de comportamento que surpreende: no +page.server.js o load roda a cada requisição ao servidor, e não há a versão "no navegador" da aula anterior. Quando o leitor navega de /painel para /encomendas, o SvelteKit faz uma requisição ao servidor só para essa rota e recebe o data em JSON. A página não recarrega, mas o servidor trabalha.

<script>
	const encomendas = [
		{ cliente: 'Ana', total: 27.5 },
		{ cliente: 'Bia', total: 9.0 }
	];

	const total = encomendas.reduce((soma, e) => soma + e.total, 0);
</script>

<p>Total do dia: R$ {total.toFixed(2)}</p>
<p>Total do dia: R$ 36.50</p>

O componente acima é um pedaço isolado, sem SvelteKit, só para mostrar a conta e a formatação. A saída é a que o compilador gerou: 27.5 + 9 virou 36.50 porque o toFixed(2) entrou na hora de escrever. Guardar número e formatar na saída é o padrão em todo o projeto.

4. A saída real: o que chega ao navegador

O arquivo dados/encomendas.json fica fora de src e fora de static. Isso significa que ele não tem endereço: não existe URL que devolva o conteúdo dele. Quem quiser os dados passa pela rota, e a rota devolve só o que o return mandar.

ana@notebook:~/loja$ ls dados
encomendas.json
ana@notebook:~/loja$ curl -s localhost:5173/encomendas | grep -o 'Total do dia: R$ [0-9.]*'
Total do dia: R$ 90.50
ana@notebook:~/loja$ curl -s localhost:5173/encomendas | grep -o 'Lido do servidor às [0-9:]*'
Lido do servidor às 17:16:46

O horário vem do servidor, no formato brasileiro, e muda a cada requisição. Se você abrir o "ver código-fonte" do navegador nessa página, vai encontrar Total do dia: R$ 90.50 — o resultado já calculado — e não vai encontrar o readFile, nem o caminho do arquivo, nem o código do load. Esse código nunca viajou para o navegador.

E se alguém tentar adivinhar o endereço do arquivo? O servidor responde com um código, não com o conteúdo:

ana@notebook:~/loja$ curl -s -o /dev/null -w '%{http_code}\n' localhost:5173/dados/encomendas.json
403

O 403 quer dizer "proibido". O servidor de desenvolvimento sabe que aquele caminho não é público e recusa. Em produção a resposta pode ser 404, mas o efeito é o mesmo: o arquivo não sai. Quem garante isso não é a sua disciplina, é a posição do arquivo no projeto.

Pasta static é a rua

Tudo o que está em static/ é servido com endereço público — static/logo.png vira /logo.png. Nunca coloque ali arquivo com dado de cliente, senha ou backup. Se o dado precisa de proteção, ele fica fora de static e só sai por um load de servidor ou por um endpoint que confira quem está pedindo.

5. O que pode voltar de um load de servidor

O objeto do return atravessa uma fronteira: sai do processo do servidor e entra no navegador como texto. Por isso ele precisa ser serializável. Número, texto, booleano, null, lista e objeto simples passam. Função, classe, Map, Set e instâncias de biblioteca não passam — ou passam deformados.

Valor no returnPassa?Por quê
'Ana', 27.5, true, nullsimviram texto e voltam iguais
Lista de objetos simplessimé o caso mais comum: linhas de uma tabela
Datesim, com cuidadoo SvelteKit usa devalue e reconstrói a data; ainda assim, texto é mais previsível
BigIntsimdevalue também cobre esse tipo
Funçãonãoload_not_serializable, o erro desta aula
Classe com métodosnãoos métodos são funções; perdem-se no caminho

A regra prática evita quase todos os problemas: devolva dado, não comportamento. Se o componente precisa de uma conta, calcule no componente com $derived. Se a conta é pesada ou depende do banco, calcule no load e devolva o resultado pronto. Função é a única coisa que nunca deve atravessar.

Missão: o JSON guarda o total como texto ('27.50'). Some os dois totais de verdade e mostre Total: R$ 36.5 — sem colar texto com texto.

<script>
	const encomendas = [
		{ cliente: 'Ana', total: '27.50' },
		{ cliente: 'Bia', total: '9.00' }
	];

	let total = $derived(encomendas.reduce((soma, e) => soma + e.total, 0));
</script>

<p>Total: R$ {total}</p>
<script>
	const encomendas = [
		{ cliente: 'Ana', total: '27.50' },
		{ cliente: 'Bia', total: '9.00' }
	];

	let total = $derived(encomendas.reduce((soma, e) => soma + Number(e.total), 0));
</script>

<p>Total: R$ {total}</p>

O sinal de mais tem dois empregos em JavaScript: somar números e colar textos. Com '27.50' e 0 na mesma conta, ele escolhe colar — o resultado vira uma string enorme e sem sentido. O Number() converte antes da conta. O problema nasce na fronteira: JSON não tem tipo numérico próprio, e um valor entre aspas chega como texto.

6. O evento do servidor: cookies, locals e parent

No +page.js o evento traz fetch, url e params. No +page.server.js ele traz tudo isso e mais três coisas que só existem no servidor:

cookies
ler e gravar cookies da resposta. cookies.get('cliente') devolve o valor ou undefined. É o assunto de uma aula inteira mais adiante.
locals
um objeto que o hooks.server.js preenche antes de qualquer load. Serve para guardar "quem é o usuário" uma vez e usar em todas as rotas.
request
a requisição crua: cabeçalhos, corpo, método. Em load quase nunca é preciso; em formulário, sim.
parent()
espera e devolve o data de um +layout.server.js acima. Chame só quando precisar: antes dele, o seu load roda em paralelo com o do layout.

Não é preciso decorar a lista. O hábito útil é outro: quando o erro disser "cannot read properties of undefined", pergunte o que este arquivo recebe e confira se aquela ferramenta existe neste lado da fronteira. cookies no +page.js dá esse erro exato, como você viu na aula anterior.

7. Importando seus módulos: #lib

Projeto cresce e o código comum sai da rota para um módulo. No SvelteKit, a pasta combinada para isso é src/lib, e o package.json do projeto declara atalhos para ela:

{
	"imports": {
		"#lib": "./src/lib/index.js",
		"#lib/*": "./src/lib/*"
	}
}

Com esse atalho, qualquer arquivo do projeto importa #lib/pedidos.js sem precisar de ../../. No SvelteKit 3 o atalho antigo, com cifrão, foi removido: quem escreve $lib recebe um erro que explica a troca. É um bom exemplo de mensagem que ensina — e está no cenário 1, mais adiante.

Vale saber que src/lib é só uma convenção de organização. O que protege o arquivo é onde ele é usado: um módulo importado por um +page.server.js não vai para o navegador; o mesmo módulo importado por um +page.js ou por um componente vai. A fronteira é o arquivo que importa, não a pasta.

Missão: o servidor devolve a lista já ordenada — e a maior encomenda primeiro. O botão ordena ao contrário. Acerte a comparação para o primeiro nome ser Caio.

<script>
	let encomendas = $state([
		{ cliente: 'Bia', total: 9.0 },
		{ cliente: 'Caio', total: 54.0 },
		{ cliente: 'Ana', total: 27.5 }
	]);

	function ordenar() {
		encomendas = [...encomendas].sort((a, b) => a.total - b.total);
	}
</script>

<button onclick={ordenar}>ordenar</button>
<p>{encomendas[0].cliente}</p>
<script>
	let encomendas = $state([
		{ cliente: 'Bia', total: 9.0 },
		{ cliente: 'Caio', total: 54.0 },
		{ cliente: 'Ana', total: 27.5 }
	]);

		encomendas = [...encomendas].sort((a, b) => b.total - a.total);
	}
</script>

<button onclick={ordenar}>ordenar</button>
<p>{encomendas[0].cliente}</p>

Três detalhes nesse trecho. O [...encomendas] copia a lista antes de ordenar, porque sort mexe na lista original — e estado reativo pede uma lista nova para avisar a tela. O sort recebe uma função de comparação; devolver número negativo põe o primeiro antes. E a ordenação poderia estar no load, no servidor: a escolha é entre mandar a lista crua ou já ordenada. Lista grande e ordem fixa? Ordene no servidor e mande pronta.

8. Quando dá errado

As três mensagens abaixo saíram do terminal do projeto da Ana. Todas as rotas mostram 500 Internal Error no navegador; o texto útil fica do lado do servidor.

Erro 1 — $lib, que não existe mais

O atalho antigo da pasta lib foi removido no SvelteKit 3. O erro não é "módulo não encontrado": vem com a receita da troca.

import { encomendas } from '$lib/encomendas.js';

export function load() {
	return { encomendas };
}
Internal server error: module_removed_lib
`$lib` has been removed. Use `#lib` instead: https://svelte.dev/docs/kit/$lib. To keep using `$lib`, add `alias: { '$lib': 'src/lib' }` to your SvelteKit config.
https://svelte.dev/e/kit/module_removed_lib

Traduzindo: "troque $lib por #lib; se você realmente quer o nome antigo, declare um apelido na configuração". A segunda opção existe para projetos migrados, não para projeto novo.

Erro 2 — devolver uma função

O return tentou mandar um comportamento em vez de um dado. O SvelteKit recusa antes de desenhar e diz qual campo foi o culpado.

export function load() {
	return { total: () => 90.5 };
}
SvelteKit error: load_not_serializable
Data returned from `load` while rendering `/encomendas` is not serializable: Cannot stringify a function (`data.total`). If you need to serialize/deserialize custom types, use transport hooks: https://svelte.dev/docs/kit/hooks#transport.
https://svelte.dev/e/kit/load_not_serializable
DevalueError: Cannot stringify a function

data.total é o caminho exato do campo problemático. A correção é chamar a função no servidor e devolver o número: return { total: 90.5 }. O total que o componente mostra é dado, não cálculo.

Erro 3 — o nome do campo não combina

O load devolveu soma; o componente pediu data.total. Nenhum erro de compilação: só um undefined chegando no toFixed.

return { encomendas, soma, carregadoEm };
TypeError: Cannot read properties of undefined (reading 'toFixed')
    at eval (src/routes/encomendas/+page.svelte:6:33)
500 GET /encomendas

A linha 6 do componente é a do total. O conserto pode ser no servidor (total: soma) ou no componente (data.soma), desde que os dois lados usem o mesmo nome. Um jeito de não repetir esse erro: escreva o return e o HTML na mesma sessão, olhando os dois.

9. Conferindo a rota sem abrir o navegador

Quem está começando tende a conferir tudo no navegador: clicar, recarregar, olhar. Funciona, mas é lento e engana — o navegador mostra a página já hidratada, com JavaScript no meio. O curl mostra o que o servidor respondeu, que é a metade que decide se o dado chegou.

Um roteiro de conferência em três linhas, sempre igual: o código de status, o texto que interessa e a ausência do que não devia aparecer. A terceira parte é a que pega vazamento de segredo.

ana@notebook:~/loja$ curl -s localhost:5173/encomendas | grep -o '<td>[^<]*</td>'
<td>Ana</td>
<td>3 item(ns)</td>
<td>08:00</td>
<td>Bia</td>
<td>1 item(ns)</td>
<td>09:30</td>
<td>Caio</td>
<td>6 item(ns)</td>
<td>10:15</td>
ana@notebook:~/loja$ curl -s localhost:5173/encomendas | grep -c 'encomendas.json'
0

grep -c conta linhas e imprime o número. Zero é a resposta que você quer: o nome do arquivo não aparece no HTML entregue. Se aparecesse, seria sinal de que um caminho interno vazou para a página — e caminho interno é uma pista para quem procura o que explorar.

Cache do navegador engana

Se a página não muda depois de você salvar o arquivo, recarregue com Ctrl+Shift+R antes de suspeitar do código. E se o curl mostrar o valor novo enquanto o navegador mostra o antigo, o problema é cache, não load.

Exercícios

1. Onde roda o load de um +page.server.js?

2. Por que uma função no return derruba a rota?

3. O que o 403 ao pedir /dados/encomendas.json prova?

Complete o código

import { readFile } from '';

export async function load() {
  const texto = await readFile('dados/encomendas.json', 'utf8');
  return { encomendas: JSON.(texto) };
}

Resumo

  • +page.server.js guarda um load que roda só no servidor, a cada requisição.
  • É o arquivo para ler disco, banco, variável de ambiente, cookie e qualquer segredo.
  • O .server no nome não é estilo: o empacotador impede que esse arquivo vá para o navegador.
  • O que o navegador recebe é só o objeto do return — dado, nunca comportamento.
  • load_not_serializable acontece quando o return leva função ou classe; a mensagem diz qual campo.
  • Arquivo em dados/ não tem endereço público; static/ tem, e por isso não guarda segredo.
  • O evento de servidor traz cookies, locals, request e parent().
  • Importe seus módulos com #lib/…: no SvelteKit 3 o $lib foi removido e a mensagem ensina a troca.
  • curl mostra o que o servidor respondeu de verdade; grep -c com zero confirma que nada vazou.
  • Nome de campo diferente entre o return e o HTML não gera erro de compilação — gera undefined.
