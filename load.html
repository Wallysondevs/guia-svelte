SvelteKit · +page.js

A Ana abriu a padaria às seis da manhã e o cardápio da parede ainda estava escrito com o giz de ontem. Antes de abrir o balcão, alguém precisa ir até a cozinha, ver o que saiu do forno e só então escrever a lista. No SvelteKit esse alguém tem nome: load, uma função que você escreve no arquivo +page.js. Ela busca os dados primeiro e entrega o resultado pronto para a página desenhar. Esta aula é sobre esse arquivo e sobre o objeto que ele devolve.

  • O que muda quando o mesmo arquivo roda no servidor e no navegador.

1. A ideia: o bilhete da cozinha antes do balcão

Na padaria da Ana existe uma ordem que ninguém precisa explicar: primeiro a cozinha produz, depois o balcão mostra. Se o balcão mostrasse a lista antes de a cozinha terminar, o cliente leria "pão de queijo" e não haveria pão de queijo. A página de um site tem o mesmo problema. O HTML precisa de dados — preços, nomes, quantidades — e esses dados vêm de algum lugar: um arquivo, um banco, outro endereço da internet.

O load é o mensageiro entre a cozinha e o balcão. Ele é uma função que você escreve no arquivo +page.js, do lado do +page.svelte. O SvelteKit chama essa função antes de desenhar a página, espera a resposta e entrega o que ela devolveu para o componente. O componente não sabe de onde o dado veio; ele só recebe um objeto chamado data e desenha.

Há um ganho escondido nessa separação. Quem busca o dado é uma função de JavaScript puro, sem HTML no meio. Isso significa que você pode testar a busca sozinha, trocar a fonte do dado sem tocar no desenho e ler o código em duas camadas: "de onde vem" e "como aparece". É a mesma divisão que a Ana faz entre a cozinha e o balcão.

Na padariaNo SvelteKit
A cozinha, que produz os pãesA função load do +page.js
A bandeja que vai do fundo até o balcãoO objeto que o load devolve com return
O balcão, que mostra o que chegouO +page.svelte
O bilhete com o pedido do clienteO url, com os parâmetros do endereço
O fornecedor de farinha de outra cidadeO fetch para outro endereço
O caderno de receitas, que fica na cozinhaO +page.server.js, que só roda no servidor

Repare no vocabulário: rota é um endereço do site (por exemplo /cardapio), load é a função que busca os dados dessa rota, e data é o nome do pacote que chega ao componente. Três palavras que voltam em todas as aulas de SvelteKit. O data não é mágica: é apenas o objeto que o seu return devolveu, embalado pelo SvelteKit e entregue como prop.

2. O primeiro load do cardápio

O projeto da Ana fica em ~/loja e a rota do cardápio é uma pasta dentro de src/routes. Toda rota é uma pasta com arquivos de nome reservado: +page.svelte é o que aparece na tela, +page.js é o que busca os dados antes. Comece pelo arquivo que busca:

export async function load({ fetch, url }) {
	const tipo = url.searchParams.get('tipo') ?? 'salgado';
	const resposta = await fetch('/api/cardapio?tipo=' + tipo);
	const paes = await resposta.json();

	return {
		tipo,
		paes,
		quantos: paes.length
	};
}

Cinco linhas úteis. A função é async porque espera respostas da rede; recebe um objeto com duas ferramentas (fetch e url); monta o endereço do outro arquivo do projeto; e devolve um objeto com três campos. O nome load não é escolha sua: é o nome que o SvelteKit procura. Se você chamar de buscar, ninguém chama a sua função.

A página que recebe esse objeto é um componente comum, com uma diferença: ela declara o prop data com $props(). Não há importação, não há chamada de função, não há await no componente. Quando o componente começa a desenhar, o dado já está ali.

<script>
	let { data } = $props();
</script>

<h1>Cardápio de hoje</h1>
<p>{data.quantos} pão(es) do tipo {data.tipo}</p>

<ul>
	{#each data.paes as pao}
		<li>{pao.nome} — R$ {pao.preco.toFixed(2)}</li>
	{/each}
</ul>

<a href="/cardapio?tipo=doce">ver os doces</a>

Missão: no projeto, este objeto é o que o load devolveu. O campo certo chama-se quantos. Faça a linha mostrar 3 pães no cardápio.

<script>
	// no projeto, este objeto é o que o load devolveu
	const data = { paes: ['Pão francês', 'Pão de queijo', 'Croissant'], quantos: 3 };
</script>

<p>{data.total} pães no cardápio</p>
<script>
	// no projeto, este objeto é o que o load devolveu
	const data = { paes: ['Pão francês', 'Pão de queijo', 'Croissant'], quantos: 3 };
</script>

<p>{data.quantos} pães no cardápio</p>

A caixa acima compila um componente sozinho, sem SvelteKit, então o objeto está escrito à mão com o mesmo formato que o load entrega. Trocar total por quantos parece pouco, mas é exatamente o tipo de erro que aparece quando o nome do campo do return não combina com o nome usado no HTML. O JavaScript não avisa: ele devolve undefined e segue em frente.

3. A anatomia do arquivo

Antes de seguir, vale olhar peça por peça. O +page.js é um módulo JavaScript normal, com uma regra: a função exportada com o nome load é o ponto de entrada. Tudo o que ela devolve vai para o componente; tudo o que ela não devolve, o componente não vê.

export async function load
export deixa a função visível para o SvelteKit; async permite usar await dentro dela. O nome tem de ser exatamente load.
({ fetch, url })
o evento: um objeto com ferramentas. Aqui pedimos duas. Poderia ser só () se a função não precisasse de nada.
url.searchParams.get('tipo')
lê o pedaço do endereço depois do ?. Se não existir, o ?? escolhe 'salgado' como padrão.
await fetch('/api/cardapio…')
faz a requisição e espera a resposta. Sem o await, você teria uma promessa, não a resposta.
return { tipo, paes, quantos }
o pacote que vai para o componente. Só campos de dados: nada de funções, nada de classes.

A última linha merece atenção. O objeto devolvido precisa ser serializável: texto, número, booleano, lista, objeto simples, null. Uma função dentro dele derruba a rota com a mensagem load_not_serializable, que aparece mais adiante nesta aula. O motivo é que esse objeto viaja do servidor para o navegador como texto, e função não vira texto.

O arquivo pode ter outro nome?

Não. O SvelteKit monta a rota a partir de nomes reservados: +page.svelte, +page.js, +page.server.js, +layout.svelte. Um arquivo cardapio.js na mesma pasta é só um módulo comum, que ninguém chama sozinho. Você pode importá-lo de dentro do load, e isso é comum.

4. A saída real: o que o servidor manda

Quem monta o HTML é o servidor, e ele usa o seu load antes de responder. Para ver isso sem abrir o navegador, use o curl, que baixa a página e mostra o texto que chega. Primeiro, o terminal do projeto:

ana@notebook:~/loja$ npm run dev

> loja@0.0.1 dev
> vite dev

  VITE v8.4.0  ready in 1811 ms

  ➜  Local:   http://localhost:5173/
  ➜  Network: use --host to expose

O endereço http://localhost:5173/ é a sua máquina falando com ela mesma. A porta 5173 é o padrão do Vite; se estiver ocupada por outro projeto, ele avisa e escolhe a próxima. Com o servidor no ar, peça a rota do cardápio e filtre só o que interessa:

ana@notebook:~/loja$ curl -s localhost:5173/cardapio | grep -o '<h1>[^<]*</h1>'
<h1>Cardápio de hoje</h1>
ana@notebook:~/loja$ curl -s localhost:5173/cardapio | grep -o '<p>[^<]*</p>'
<p>3 pão(es) do tipo salgado</p>
ana@notebook:~/loja$ curl -s localhost:5173/cardapio | grep -o '<li>[^<]*</li>'
<li>Pão francês — R$ 0.90</li>
<li>Pão de queijo — R$ 3.50</li>
<li>Croissant — R$ 7.00</li>

Três lições nessa saída. A primeira: o {data.quantos} virou 3 e o {data.tipo} virou salgado — o HTML que o navegador recebe já vem com os valores no lugar. A segunda: a lista foi desenhada no servidor, com três <li>, uma para cada pão. A terceira: o preço saiu com duas casas porque o toFixed(2) rodou antes de virar texto.

Esse HTML é o que um leitor vê ao chegar de fora, vindo do Google por exemplo. Um site feito só com componente no navegador chegaria vazio e desenharia depois; aqui o conteúdo já vem escrito. Isso vale para leitores de tela, para o robô de busca e para quem está com internet lenta.

Se você isolar só o pedaço do HTML que desenha a lista, sem SvelteKit no meio, dá para ver o que o compilador do Svelte faz com um {#each}. O componente abaixo tem os dados fixos no script, e a saída ao lado é a que o compilador gerou:

<script>
	const paes = [
		{ nome: 'Pão francês', preco: 0.9 },
		{ nome: 'Pão de queijo', preco: 3.5 }
	];
</script>

<p>{paes.length} pão(es) no balcão</p>
<ul>
	{#each paes as pao}
		<li>{pao.nome} — R$ {pao.preco.toFixed(2)}</li>
	{/each}
</ul>
<p>2 pão(es) no balcão</p> <ul><li>Pão francês — R$ 0.90</li><li>Pão de queijo — R$ 3.50</li></ul>

Não há laço no HTML que o navegador recebe: o {#each} desapareceu e no lugar ficaram dois <li> já escritos. O mesmo acontece com a lista do cardápio, só que ali quem manda os dados é o load.

5. fetch dentro do load: o servidor conversando consigo mesmo

O load pediu /api/cardapio usando o fetch que veio no evento, não o fetch global do navegador. Essa diferença importa. No servidor, esse fetch resolve o endereço internamente, sem sair para a internet; no navegador, ele faz uma requisição normal. Você escreve uma vez e funciona nos dois lugares.

Do outro lado existe um endpoint: um arquivo +server.js que responde JSON. Ele é o fornecedor de farinha da metáfora — não sabe quem pediu, só entrega. Nesta aula ele aparece de passagem; a aula própria dele vem depois.

import { json } from '@sveltejs/kit';
import { paes } from '#lib/cardapio.js';

export function GET({ url }) {
	const tipo = url.searchParams.get('tipo');
	const lista = tipo ? paes.filter((p) => p.tipo === tipo) : paes;
	return json(lista);
}

O dado em si mora num módulo da pasta src/lib, que no SvelteKit 3 se importa com #lib (o antigo $lib foi removido — há um cenário sobre isso mais adiante). É uma lista de objetos, do jeito que o banco devolveria:

export const paes = [
	{ nome: 'Pão francês', preco: 0.9, tipo: 'salgado' },
	{ nome: 'Pão de queijo', preco: 3.5, tipo: 'salgado' },
	{ nome: 'Croissant', preco: 7.0, tipo: 'salgado' },
	{ nome: 'Bolo de cenoura', preco: 6.5, tipo: 'doce' }
];

Para ver o endpoint sozinho, peça direto o endereço. O curl mostra o JSON cru, sem HTML em volta:

ana@notebook:~/loja$ curl -s localhost:5173/api/cardapio
[{"nome":"Pão francês","preco":0.9,"tipo":"salgado"},{"nome":"Pão de queijo","preco":3.5,"tipo":"salgado"},{"nome":"Croissant","preco":7,"tipo":"salgado"},{"nome":"Bolo de cenoura","preco":6.5,"tipo":"doce"}]
ana@notebook:~/loja$ curl -s 'localhost:5173/api/cardapio?tipo=doce'
[{"nome":"Bolo de cenoura","preco":6.5,"tipo":"doce"}]

Repare que 7.0 virou 7 no JSON. Não é erro: número é número, e o zero à direita não existe na representação. Quem devolve as duas casas é o toFixed(2) na hora de mostrar. Guardar o valor cru e formatar só na tela é a regra que vale para dinheiro em qualquer projeto.

Use o fetch do evento, não o global

Dentro do load, o fetch que chega no primeiro parâmetro carrega os cookies da requisição e evita chamar a si mesmo pela rede. Se você usar o fetch global, a chamada perde a identidade do visitante e pode até travar, porque o servidor tenta fazer uma requisição HTTP para ele mesmo enquanto ainda está ocupado respondendo.

6. url: o filtro que vem no endereço

O endereço de uma página carrega informação. Em /cardapio?tipo=doce existe um pedaço depois da interrogação chamado query string — a "pergunta" que o visitante fez. No load, ela aparece em url.searchParams, que tem o método get para pegar um valor pelo nome.

Por que não guardar o filtro numa variável de estado e pronto? Porque o filtro precisa sobreviver ao recarregamento, ao link compartilhado e ao botão voltar do navegador. Se o estado do filtro vive no endereço, qualquer pessoa que copie o link entrega o mesmo filtro para outra pessoa. Essa é a diferença entre um site e uma tela solta.

ana@notebook:~/loja$ curl -s 'localhost:5173/cardapio?tipo=doce' | grep -o '<li>[^<]*</li>'
<li>Bolo de cenoura — R$ 6.50</li>

O mesmo arquivo, o mesmo código, outro resultado — porque o url mudou. O load roda de novo a cada endereço diferente, e o SvelteKit guarda o resultado por endereço. Isso é o que permite ao link "ver os doces" da página funcionar sem nenhum JavaScript extra: é um <a href> comum apontando para outro endereço.

Missão: o botão troca o filtro para doce, mas a lista fica vazia. O filtro deve comparar o tipo do pão com o tipo escolhido. Faça aparecer 1 pão(es) do tipo doce depois do clique.

<script>
	const paes = [
		{ nome: 'Pão francês', tipo: 'salgado' },
		{ nome: 'Bolo de cenoura', tipo: 'doce' }
	];

	let tipo = $state('salgado');
	let lista = $derived(paes.filter((pao) => pao.nome === tipo));
</script>

<p>{lista.length} pão(es) do tipo {tipo}</p>
<button onclick={() => (tipo = 'doce')}>ver os doces</button>
<script>
	const paes = [
		{ nome: 'Pão francês', tipo: 'salgado' },
		{ nome: 'Bolo de cenoura', tipo: 'doce' }
	];

	let tipo = $state('salgado');
	let lista = $derived(paes.filter((pao) => pao.tipo === tipo));
</script>

<p>{lista.length} pão(es) do tipo {tipo}</p>
<button onclick={() => (tipo = 'doce')}>ver os doces</button>

O $derived é a peça que faz a lista se recalcular sozinha quando tipo muda: ele guarda o resultado de uma conta feita a partir de outros valores reativos. Não é uma função que você chama; é uma variável que se atualiza. Se você trocar por uma variável comum, o filtro roda uma vez e nunca mais.

7. params: o pedaço variável do caminho

Além da pergunta depois da interrogação, existe o valor que faz parte do caminho: em /cardapio/pao-de-queijo, o último pedaço identifica um pão. No SvelteKit uma pasta com colchetes marca esse pedaço variável — src/routes/cardapio/[nome]/+page.js — e o valor chega no load em params.nome.

import { error } from '@sveltejs/kit';
import { paes } from '#lib/cardapio.js';

export function load({ params }) {
	const pao = paes.find((p) => p.nome === params.nome);

	if (!pao) {
		error(404, 'esse pão não está no cardápio');
	}

	return { pao };
}

Aqui aparece uma ferramenta nova: error(404, …), importada de @sveltejs/kit. Ela interrompe o load e manda o SvelteKit desenhar a página de erro com o código e a mensagem. Sem ela, o componente receberia pao: undefined e quebraria com um erro feio de JavaScript no meio do HTML.

O params e o url parecem primos, e são: os dois vêm do endereço. A diferença é que o params faz parte do caminho e é obrigatório para a rota existir, enquanto a query string é opcional e não muda qual página é. Guarde a regra prática: o que identifica vai no caminho; o que filtra ou ordena vai na query.

8. O mesmo arquivo roda duas vezes

Esta é a parte que confunde. O +page.js roda no servidor quando alguém chega de fora, e roda no navegador quando alguém navega de uma página para outra sem recarregar. O SvelteKit chama esse arquivo de load universal justamente por isso: ele vale nos dois mundos.

A consequência é dura: dentro dele você não pode usar nada que exista só num dos lados. window, document e localStorage não existem no servidor. node:fs, process.env e cookies não existem no navegador. O código compila, o servidor responde, e o erro aparece quando o leitor clica num link — o pior lugar possível.

Você quer usarEm +page.jsEm +page.server.js
fetchsim, o do eventosim, o do evento
url e paramssimsim
cookiesnão existesim
node:fs, banco de dadosnão (roda no navegador também)sim
window, localStoragesó depois de montar, com $effectnão roda no navegador
Segredo, chave de APInuncasim, e não devolva para a página

O bind:value liga o campo à variável nos dois sentidos: o que está na variável aparece no campo, e o que a pessoa digita volta para a variável. Sem ele, seria preciso um oninput copiando o valor à mão. O $derived então recalcula a lista, e a tela acompanha.

9. Quando dá errado

As mensagens abaixo saíram do servidor do projeto, copiadas como estão. Elas aparecem no terminal onde o npm run dev está rodando — o navegador mostra apenas 500 Internal Error, o que não ajuda em nada. Esse é o primeiro hábito a criar: quando a página quebra, olhe o terminal.

Erro 1 — pedir cookies no arquivo errado

O load universal recebe fetch, url e params. cookies não está no pacote, então o valor chega como undefined e o .get estoura.

export function load({ cookies }) {
	return { nome: cookies.get('cliente') };
}
TypeError: Cannot read properties of undefined (reading 'get')
    at load (src/routes/cardapio/+page.js:2:25)
500 GET /cardapio

A leitura é direta: na linha 2, coluna 25, alguém chamou um método em undefined. A correção é mover a função para o +page.server.js, onde cookies existe de verdade — o assunto da próxima aula.

Erro 2 — esquecer o return

Buscar o dado e não devolver nada é um erro silencioso: o servidor responde 200, a página aparece, e o componente recebe um objeto vazio. Nenhum erro vermelho, só um buraco onde deveria estar o número.

export async function load({ fetch }) {
	const resposta = await fetch('/api/cardapio');
}
ana@notebook:~/loja$ curl -s localhost:5173/cardapio | grep -o '<p>[^<]*</p>'
<p> pão(es) do tipo </p>

Repare nos dois espaços vazios: {data.quantos} e {data.tipo} viraram nada, porque o JavaScript desenha undefined como texto vazio. Quando um número some sem erro, procure o return: ele é a única ligação entre a busca e a tela.

Erro 3 — actions no arquivo errado

Formulário é assunto de +page.server.js. Se você exportar actions do +page.js, o SvelteKit recusa a rota inteira antes de rodar qualquer coisa:

export const actions = {
	padrao: async () => ({ ok: true })
};

export function load() {
	return { quantos: 1 };
}
SvelteKit error: invalid_export_location
Invalid export `actions` in `src/routes/cardapio/+page.js` (`actions` is a valid export in +page.server.js)
https://svelte.dev/e/kit/invalid_export_location
500 GET /cardapio

O SvelteKit lista os nomes que valem em cada arquivo. Decorar não é o caminho: a mensagem já diz onde o actions deveria estar. Sempre que o erro trouxer um endereço começando por https://svelte.dev/e/, vale abrir — é a página da documentação daquele erro exato.

10. +page.js ou +page.server.js?

Os dois arquivos fazem a mesma pergunta ("quais são os dados desta página?") e respondem em lugares diferentes. O +page.js responde no servidor e no navegador; o +page.server.js responde só no servidor, e por isso pode tocar arquivos, cookies e segredos.

A escolha prática é uma pergunta só: este dado precisa existir no servidor por segurança, ou porque só ele alcança a fonte? Se sim, +page.server.js. Se não — uma lista pública, um filtro de endereço — o +page.js tem uma vantagem: na navegação interna ele roda no navegador e a página não precisa de uma ida ao servidor só para trocar um filtro.

PerguntaEscolha
O dado é público e pequeno?+page.js
Preciso ler um arquivo, um banco ou process.env?+page.server.js
Preciso saber quem é o visitante (cookie, sessão)?+page.server.js
Quero que a navegação interna seja instantânea?+page.js, se possível
Os dois arquivos na mesma pasta?o SvelteKit recusa; escolha um

1. O que o load de um +page.js precisa devolver?

2. De onde vem o data que o +page.svelte recebe?

3. Por que cookies não funciona no +page.js?

Complete o código

export async function ({ fetch }) {
  const resposta = await fetch('/api/cardapio');
  const paes = await resposta.json();
   { paes };
}

Resumo

  • O +page.js é o arquivo do load universal: busca os dados antes de a página desenhar.
  • A função tem de se chamar load e ser exportada; outro nome não é chamado.
  • O objeto do return chega ao componente como o prop data, lido com let { data } = $props().
  • Use o fetch do evento: ele carrega os cookies e evita a requisição para si mesmo.
  • url.searchParams.get() lê o que vem depois do ?; params lê o pedaço variável do caminho.
  • O mesmo arquivo roda no servidor e no navegador: nada de cookies, node:fs ou segredo.
  • O HTML chega pronto do servidor — quem confere isso é o curl, não o "ver código-fonte" do navegador.
  • error(404, '…') interrompe o load e mostra a página de erro em vez de quebrar o componente.
  • O objeto devolvido precisa ser serializável: função dentro dele derruba a rota com load_not_serializable.
  • Quando a página mostra 500 Internal Error, a mensagem de verdade está no terminal do npm run dev.
  • Para dados secretos ou que só o servidor alcança, o arquivo é o +page.server.js — a próxima aula.
