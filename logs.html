SvelteKit · Logs e Observabilidade

A Ana tem um caderno atrás do balcão onde anota o que aconteceu no dia: o pão que queimou, o cliente que reclamou do troco, a entrega que atrasou. Ninguém lê o caderno quando tudo dá certo — ele existe para o dia em que algo dá errado e ela precisa saber o que houve. Num programa, esse caderno são os logs: linhas de texto que o servidor escreve sozinho a cada pedido. Esta aula mostra onde essas linhas aparecem, como escrever as úteis e o que nunca deve entrar nelas.

Você vai aprender
  • O que é log e por que ele é diferente de mensagem de erro na tela.
  • Onde as linhas aparecem: terminal do dev, saída do build e log de produção.
  • Como registrar método, caminho, status e tempo de cada requisição.
  • Como ler uma pilha de erro de verdade, linha por linha.
  • Como o handleError separa o que o cliente vê do que a equipe vê.
  • Por que 'texto ' + objeto vira [object Object].
  • O que nunca pode ser gravado: senha, cookie, dado pessoal.
  • Para onde vai o log em produção: stdout, journalctl, Docker.
  • Os três tropeços reais: objeto colado, ciclo no JSON e a pilha de erro de 500.

1. A ideia: o caderno atrás do balcão

Existe uma diferença grande entre o cartaz que o cliente lê e o caderno da Ana. O cartaz diz “voltamos já” — é curto, educado e não conta nada de útil. O caderno diz “12h03, forno 2 apagou, 14 pães perdidos, eletricista avisado às 12h40” — é feio, técnico e resolve o problema da semana seguinte.

No SvelteKit acontece a mesma divisão. A página de erro que o cliente vê é o cartaz: uma frase curta, sem detalhe técnico, sem nome de arquivo. O log é o caderno: método HTTP, caminho, status, tempo, mensagem do erro e a pilha de chamadas que levou até ali. Quem confunde os dois acaba mostrando a senha do banco no cartaz ou escondendo do caderno a informação que resolveria o caso.

Logar é barato e salva tempo. Uma linha por pedido responde perguntas que você vai fazer: a página ficou lenta por causa do banco ou do componente? O erro de ontem às 3h da manhã apareceu de novo? O formulário de login está sendo atacado? Sem log, a resposta é “acho que”.

O que aconteceumétodo, caminho e status
Quanto tempo levoumilissegundos medidos com performance.now()

2. Onde o log aparece

A mesma linha de console.log pode cair em três lugares diferentes, e saber qual é qual economiza muita procura:

MomentoOnde a linha apareceQuem vê
npm run devo terminal onde o comando rodavocê, na sua máquina
npm run buildo terminal do build, durante o prerendervocê, no build
node buildo terminal do servidor, ou o arquivo de log delequem administra o servidor
navegadoro console do inspetor (F12)quem está com a página aberta

O ponto que confunde: um console.log escrito dentro de um componente .svelte roda nos dois lados. Durante a renderização no servidor, ele aparece no terminal; no navegador, aparece no inspetor. Já um console.log dentro de um +page.server.js só existe no servidor — é o lugar certo para registrar informação sensível, porque ela não vai para o navegador de ninguém.

O build também gera log, mesmo sem você escrever nada. Quando o SvelteKit pré-renderiza páginas, ele roda o seu app e registra cada uma:

Prerendering
GET /seo → 200 (12 ms)
GET /sobre → 200 (2 ms)
GET / → 204 (0 ms)
GET /produtos → 204 (0 ms)
GET /entrar → 204 (0 ms)

As duas primeiras linhas vieram do console.log do hooks.server.js — o mesmo hook da aula anterior, rodando durante o build. As outras três, com status 204, são páginas que o rastreador de links visitou mas não gerou arquivo. Se uma delas tivesse consultado o banco, o banco precisaria estar no ar naquele instante.

3. O primeiro log: dentro do load

Para registrar algo de dentro de uma página, o lugar natural é o load do servidor. O arquivo abaixo calcula o total de produtos e anota no terminal quantos são:

const produtos = [
	{ id: 1, nome: 'Pão francês', preco: 0.9 },
	{ id: 2, nome: 'Sonho de creme', preco: 4.5 },
	{ id: 3, nome: 'Pão de queijo', preco: 3.0 }
];

export function load() {
	console.log(`[produtos] ${produtos.length} itens no catálogo`);
	return { produtos };
}

Com o servidor no ar, cada visita à página escreve a mesma linha. O texto entre crases é um template literal: a parte fixa fica entre crases e o valor calculado entra entre ${ }. É o mesmo buraco das chaves no HTML, só que em JavaScript puro.

console.log
escreve uma linha na saída padrão do processo. No servidor, é o terminal; em produção, o arquivo de log do gerenciador.
[produtos]
um prefixo com o nome da área. Com dez logs no projeto, o prefixo é o que permite filtrar a saída com grep.
${produtos.length}
o valor calculado na hora. A conta acontece antes de a linha ser escrita.
console.error
a mesma coisa, mas na saída de erro. A diferença aparece quando alguém filtra o log por gravidade.
performance.now()
o relógio de alta precisão do JavaScript, em milissegundos. É o que permite medir o tempo de um pedido.

Uma linha de log bem feita responde “o que, onde, quanto”. A do exemplo tem o assunto (produtos) e o número. Uma linha ruim seria console.log('aqui'): não diz nada quando você lê o arquivo três dias depois.

4. A linha de log como componente

Ver o log na tela, durante o desenvolvimento, ajuda a entender o formato. O componente abaixo monta uma linha no padrão que o hook usa:

<script>
	let { metodo = 'GET', caminho = '/produtos', status = 200 } = $props();
</script>

<p>{metodo} {caminho} → {status}</p>
<p>GET /produtos → 200</p>

A seta → é só um caractere de texto, mas ajuda a separar o pedido da resposta quando a linha é lida rápido. Numa página de diagnóstico, esse componente vira uma lista de pedidos recentes — é o que a caixa abaixo pede.

5. Caixa 1: montando as linhas do caderno

A caixa abaixo tem dois pedidos e escreve só o método e o caminho. A missão é acrescentar o status, no formato que o terminal mostra.

Missão: mostre cada pedido no formato método caminho → status. O texto precisa conter POST /entrar → 400.

<script>
	const pedidos = [
		{ metodo: 'GET', caminho: '/produtos', status: 200 },
		{ metodo: 'POST', caminho: '/entrar', status: 400 }
	];
</script>

{#each pedidos as p}
	<p>{p.metodo} {p.caminho}</p>
{/each}
<script>
	const pedidos = [
		{ metodo: 'GET', caminho: '/produtos', status: 200 },
		{ metodo: 'POST', caminho: '/entrar', status: 400 }
	];
</script>

{#each pedidos as p}
	<p>{p.metodo} {p.caminho} → {p.status}</p>
{/each}

O 400 na segunda linha diz muito: é o status de pedido malformado, e no projeto da Ana ele aparece quando a senha do formulário está errada. Um 400 repetido dezenas de vezes por minuto é sinal de gente tentando adivinhar senha. É esse tipo de leitura que o log permite e a tela não.

6. Medindo tempo sem inventar número

Tempo de resposta é a primeira métrica que a Ana vai querer quando o site ficar lento. A conta é simples: guarda o instante antes, guarda o instante depois, subtrai. A caixa abaixo mostra zero, porque ninguém somou nada ainda.

Missão: some as três medidas e mostre o total: Tempo total: 63 ms. Use reduce, não o número escrito à mão.

<script>
	const medidas = [12, 48, 3];
</script>

<p>Tempo total: 0 ms</p>
<script>
	const medidas = [12, 48, 3];
	const total = $derived(medidas.reduce((soma, m) => soma + m, 0));
</script>

<p>Tempo total: {total} ms</p>

reduce percorre a lista carregando um acumulador. O primeiro argumento é a função que soma; o segundo é o valor inicial, zero. Sem o valor inicial, o reduce usaria o primeiro item da lista como ponto de partida — e numa lista vazia ele lançaria erro. Detalhe pequeno, diferença grande quando a lista pode estar vazia.

7. handleError: o log que sobra quando algo quebra

Os logs de rotina contam o que deu certo. O log de erro conta o que deu errado, e é o mais importante. No projeto da Ana, o handleError do hooks.server.js escreve no terminal e devolve uma mensagem curta para a tela:

export function handleError({ error, event, status }) {
	console.error(`[erro ${status}] ${event.request.method} ${event.url.pathname}: ${error.message}`);
	return {
		message: 'A padaria teve um problema. Tente de novo em instantes.',
		codigo: status
	};
}

O que o cliente vê é o return. O que a equipe vê é o console.error. Essa separação é o motivo de o handleError existir: sem ele, o SvelteKit mostra uma página genérica e você fica sem saber qual erro foi. Com ele, o terminal registra e a página continua educada.

Rodando, cada erro produz duas linhas: a do projeto e a do Vite.

[erro 404] GET /erro: Pão não encontrado na prateleira
GET /erro → 404 (16 ms)
404 GET /erro
[erro 500] GET /quebra-500: o forno apagou
GET /quebra-500 → 500 (15 ms)
500 GET /quebra-500

Repare na diferença de gravidade. O 404 é esperado: alguém pediu uma página que não existe, e a mensagem é específica (“Pão não encontrado na prateleira”). O 500 é inesperado: o load lançou um erro comum, sem status, e o framework transformou em 500. Em produção, é o 500 que precisa acordar alguém.

8. Caixa 2: o que não pode entrar no caderno

Log é texto que fica guardado e circula: aparece no terminal, no arquivo, no painel da plataforma. Senha em log é senha vazada. A caixa abaixo escreve uma linha com a senha na query, do jeito que um pedido mal feito chegaria.

Missão: troque o valor da senha por três asteriscos, mantendo o resto da linha igual: GET /entrar?senha=*** → 200.

<script>
	const linha = 'GET /entrar?senha=pao123 → 200';
</script>

<p>{linha}</p>
<script>
	const linha = 'GET /entrar?senha=pao123 → 200';
	const limpa = $derived(linha.replace(/senha=\S*/, 'senha=***'));
</script>

<p>{limpa}</p>

O \S* pega tudo o que não é espaço, então para no espaço antes da seta. Se você usasse .*, o resto da linha iria junto — e o log perderia justamente o status, que é a parte útil. A lição vale para qualquer texto: escolha o padrão pelo que ele precisa parar, não pelo que ele precisa pegar.

Vale o mesmo para token de sessão, cookie inteiro, número de cartão e dados pessoais. O princípio é o do caderno aberto no balcão: se você não escreveria aquilo num papel que qualquer um pode ler, não escreva no log.

9. O que registrar e o que evitar

RegistreEvite
método, caminho, status e tempocorpo inteiro do formulário
identificador do pedido, não o nome do clienteCPF, telefone, endereço completo
mensagem do erro e a pilhasenha, token, chave de API
nome da operação ([produtos])console.log('aqui') sem contexto
contagem e duraçãoo objeto inteiro da requisição

Existe uma razão técnica além da segurança para não logar tudo. Log gigante enche o disco, e disco cheio derruba o servidor. Numa VPS pequena, um log que cresce sem limite é uma bomba-relógio: o gerenciador de processos grava, o arquivo cresce, e um dia o servidor não consegue mais escrever. Rotação de log — guardar só os últimos dias — é configuração do sistema, não do SvelteKit, mas é a sua responsabilidade quando você administra a máquina.

10. Caixa 3: lendo o log de erro

Uma pilha de erro é o caderno no seu formato mais técnico: cada linha é uma chamada, da mais recente para a mais antiga. A caixa abaixo só mostra o status; a missão é separar o que é do projeto e o que é da biblioteca.

<script>
	let {
		pilha = [
			{ local: 'src/routes/+page.svelte:5', projeto: true },
			{ local: 'node_modules/svelte/internal/server.js:416', projeto: false }
		]
	} = $props();
</script>

{#each pilha as c}
	<p>{c.local}{c.projeto ? ' aqui' : ''}</p>
{/each}
<p>src/routes/+page.svelte:5 aqui</p><p>node_modules/svelte/internal/server.js:416</p>

A primeira linha da pilha de verdade é quase sempre a sua. Encontrar o arquivo src/… no meio de vinte linhas de node_modules é a habilidade que transforma um erro assustador em uma correção de cinco minutos. O resto da pilha explica o caminho que o framework fez até você — útil quando o problema não está no seu código.

11. Log em produção: para onde vai

No servidor, não existe “terminal aberto na sua frente”. O console.log escreve na saída padrão do processo, e alguém precisa estar coletando. As três formas mais comuns:

Onde o app rodaComo ler o log
VPS com systemdjournalctl -u loja -f
Dockerdocker logs -f nome-do-container
Plataforma (Netlify, Vercel)o painel da plataforma, aba de logs
Arquivo próprioredirecionar a saída: node build >> loja.log 2>&1

Repare no padrão do último caso: >> acrescenta no fim do arquivo em vez de apagar, e 2>&1 manda a saída de erro para o mesmo lugar que a saída comum. Sem esse segundo pedaço, você perde justamente as linhas de erro — que são as que importam.

Existe uma prática que vale desde o começo: escrever log em uma linha, sem quebra de linha no meio. Um log de várias linhas vira uma bagunça no arquivo, e ferramentas que leem log procuram uma linha por evento. Se você precisa registrar um objeto, converta com JSON.stringify em vez de imprimir o objeto direto.

12. Quando dá errado

As três saídas abaixo são reais. Duas saíram do próprio Node, com um comando de uma linha; a terceira é a pilha de erro de uma página que quebrou no servidor de desenvolvimento.

Erro 1 — o objeto virou [object Object]

Você juntou texto com um objeto usando +. A conversão de objeto para texto não sabe o que fazer e devolve a assinatura genérica.

ana@notebook:~/loja$ node -e "console.log('usuario: ' + { nome: 'Ana', papel: 'dona' })"
usuario: [object Object]

A informação existe, mas não chegou ao log. A correção é escolher o campo — usuario.nome — ou usar JSON.stringify para ver o objeto inteiro. O console.log chamado direto com o objeto até mostra os campos no terminal, mas concatenar com + sempre vira [object Object].

Erro 2 — o JSON com ciclo não converte

Este aparece quando o objeto tem uma referência para si mesmo, coisa comum em objetos de configuração e em estruturas que apontam de volta para o pai.

ana@notebook:~/loja$ node -e "const a = { nome: 'Ana' }; a.self = a; try { JSON.stringify(a) } catch (e) { console.log(e.message) }"
Converting circular structure to JSON
    --> starting at object with constructor 'Object'
    --- property 'self' closes the circle

A mensagem aponta o culpado: a propriedade self fecha o círculo. Para logar, escolha os campos que interessam — JSON.stringify({ nome: a.nome }) — em vez de mandar a estrutura inteira. O mesmo erro acontece em produção quando alguém loga event ou a requisição inteira.

Erro 3 — a pilha do 500 no terminal

Uma página acessou data.usuario.nome quando usuario era null. O SvelteKit registrou a pilha e devolveu uma página 500 ao cliente.

TypeError: Cannot read properties of null (reading 'nome')
    at eval (src/routes/quebra-locals/+page.svelte:5:29)
    at eval (node_modules/svelte/src/internal/server/renderer.js:416:11)
    at Renderer.child (node_modules/svelte/src/internal/server/renderer.js:305:18)
    at Renderer.component (node_modules/svelte/src/internal/server/renderer.js:414:8)

A primeira linha diz o tipo do erro e a propriedade: leitura de nome em null. A segunda aponta o lugar exato — src/routes/quebra-locals/+page.svelte:5:29, linha 5, coluna 29. As seguintes são do framework e explicam por que a renderização chegou ali; a pilha completa tem mais linhas internas. A correção é data.usuario?.nome, com o encadeamento opcional da aula de hooks.

Resumo

  • Log é o caderno do servidor: técnico, detalhado, para quem mantém o site.
  • O cartaz da tela é a página de erro; ele não mostra detalhe técnico.
  • console.log em +page.server.js e em hooks aparece no terminal do servidor.
  • O build também roda o app, então os logs do hook aparecem durante o prerender.
  • Uma linha útil tem assunto, dado e contexto: [produtos] 3 itens.
  • Tempo de resposta é a diferença entre dois performance.now(), arredondada.
  • handleError registra o erro e devolve a mensagem curta que o cliente vê.
  • Nunca logue senha, token, cookie inteiro ou dado pessoal; mascare com replace.
  • [object Object] vem de concatenar objeto com texto; use JSON.stringify.
  • Objeto com ciclo quebra o JSON.stringify; logue só os campos que importam.
  • A primeira linha da pilha costuma apontar o arquivo e a linha do seu projeto.
  • Em produção, o log vai para journalctl, docker logs ou o painel da plataforma.
