Svelte · O que é Svelte

A Ana tem uma padaria e um caderno de receitas. Ela sabe que a receita de pão doce não é o pão doce: a receita é papel, o pão é comida. O sobrinho dela voltou da faculdade falando de uma tal de Svelte, e ela quer entender o que é antes de instalar qualquer coisa no notebook. Esta aula é a resposta curta e sem pressa: Svelte é um compilador que transforma um arquivo de texto em um pedaço de tela que se atualiza sozinho quando os dados mudam.

Você vai aprender
  • O que é um compilador e por que o Svelte é um deles.
  • A diferença entre a receita (o arquivo .svelte) e o bolo (o que o navegador recebe).
  • Por que a tela consegue mudar sozinha, sem você caçar elemento por elemento.
  • O que é um componente e o que é estado reativo.
  • O vocabulário do Svelte 5: as runas $state, $derived, $effect e $props.
  • Como ler a saída do compilador e o que ela prova.
  • O que o Svelte não é, para você não procurar no lugar errado.
  • Por que o projeto precisa de um comando de build e o que ele gera.
  • Os três primeiros erros que quem começa encontra, com a mensagem real.

1. A ideia: a receita e o bolo

Quando a Ana escreve "2 ovos, 300 g de farinha, 30 minutos de forno", ela não está fazendo um bolo. Está escrevendo instruções para alguém que sabe cozinhar. O forno nunca leu a receita: quem lê é a pessoa, que transforma ingredientes em bolo. Se a receita tem um erro — "300 kg de farinha" em vez de gramas —, o erro aparece antes do bolo, no papel, e ninguém perde a farinha.

Com o Svelte é igual. Você escreve um arquivo com extensão .svelte cheio de HTML, JavaScript e CSS. Esse arquivo é a receita. Ele não vai para o navegador. Quem lê a receita é o compilador do Svelte, um programa que roda no seu computador e traduz o arquivo para JavaScript comum. O navegador recebe o bolo pronto: HTML montado e o JavaScript que sabe atualizá-lo.

Essa é a diferença que organiza o resto do guia. Em HTML puro, o que você escreve é exatamente o que o navegador lê. No Svelte, entre você e o navegador existe uma etapa de tradução — e é ela que permite escrever {preco} no meio do HTML e ver o número certo na tela, mesmo que o preço mude depois. O preço do trabalho é que você precisa de um comando para "assar" o projeto. O ganho é que a tela passa a acompanhar os dados.

2. O problema que o Svelte resolve

Na parede da padaria, a Ana tem um quadro de avisos com o preço do pão. Quando o quilo da farinha sobe, ela apaga o número e escreve outro. Um número, uma canetada. O problema começa quando o mesmo preço aparece em vários lugares: o quadro da parede, o cardápio do balcão, a etiqueta da vitrine, a lista que ela manda no grupo. São quatro lugares; ela apaga e reescreve quatro vezes. Se esquecer um, o cliente reclama.

Em uma página feita só com HTML e JavaScript, acontece a mesma coisa. Cada lugar onde o preço aparece é um pedaço de tela separado, e o programador precisa escrever, para cada um, uma instrução do tipo "pegue o elemento com tal identificador e troque o texto dele". São linhas compridas, fáceis de esquecer e difíceis de manter quando a página cresce.

O Svelte resolve isso com uma ideia só: você escreve o preço uma vez, numa variável, e no HTML escreve {preco} em quantos lugares quiser. Quando a variável muda, o compilador já deixou pronto o código que atualiza todos esses lugares. Esse comportamento tem nome: reativo. Reativo quer dizer "reage sozinho quando o dado muda", e não "o programador lembrou de atualizar".

Repare que o Svelte não adivinha o que você quer. Ele só sabe que aquele pedaço de HTML depende daquela variável, porque você escreveu {preco} ali. A ligação é declarada por você, uma vez; a atualização é trabalho do código gerado. É a mesma lógica da receita: você diz os ingredientes, o cozinheiro segue os passos.

3. No dia a dia × no componente

Uma tabela para fixar o vocabulário antes de ver código. Do lado esquerdo, a padaria. Do lado direito, o mundo do Svelte.

Na padariaNo Svelte
A receita escrita no cadernoO arquivo App.svelte

O cozinheiro que segue a receitaO compilador do Svelte

Trocar o recheio sem refazer o boloMudar o valor de uma variável e ver a tela acompanhar
Provar a massa antes de assarO compilador recusar o arquivo com uma mensagem de erro

O vocabulário do guia tem três palavras que voltam sempre. Componente é o arquivo com nome — um pedaço de tela com identidade própria, como "o cartão do pão". Estado é o valor que pode mudar dentro dele, como o preço de hoje. Reativo é o adjetivo para o que se atualiza quando o estado muda. Componente é a caixa; estado é o conteúdo; reatividade é o que acontece quando o conteúdo muda.

4. Um compilador, não uma biblioteca

Existe mais de um jeito de construir telas que mudam. Um deles é entregar ao navegador uma biblioteca grande, que lê a sua marcação e decide, na hora em que a página abre, o que desenhar. O outro é fazer esse trabalho antes, na sua máquina, e entregar JavaScript já preparado. O Svelte segue o segundo caminho — por isso ele se apresenta como compilador.

Isso tem uma consequência prática que você sente no primeiro dia: o arquivo .svelte não abre sozinho no navegador. Clicar duas vezes nele não mostra nada. Para ver o resultado, você roda um comando que compila e serve a página. Também é por isso que muitos erros aparecem no terminal, antes de a página abrir: o compilador leu a receita e achou "300 kg de farinha".

O primeiro comando da Ana confere o que está instalado no projeto dela:

ana@notebook:~/loja$ node -v
v22.23.5
ana@notebook:~/loja$ node -e "console.log(require('svelte/package.json').version)"
5.59.2

Duas linhas, duas informações. A primeira diz a versão do Node, o programa que executa JavaScript fora do navegador — é nele que o compilador roda. A segunda diz a versão do Svelte instalada no projeto: 5.59.2. Fixe esse costume: quando alguma coisa não bate com o guia, confira a versão primeiro. Uma aula escrita para o Svelte 5 pode usar recursos que o Svelte 3 não conhece.

Agora o teste que mostra o compilador trabalhando. O comando abaixo lê o arquivo src/App.svelte e pede ao compilador as quatro primeiras linhas do JavaScript gerado:

ana@notebook:~/loja$ node -e "console.log(require('svelte/compiler').compile(require('fs').readFileSync('src/App.svelte','utf8'),{generate:'client'}).js.code.split('\n').slice(0,4).join('\n'))"
import 'svelte/internal/init-operations';
import 'svelte/internal/disclose-version';
import * as $ from 'svelte/internal/client';

O arquivo tinha HTML e um <script>; o que saiu foi JavaScript com import. Nenhuma linha de HTML sobrou do jeito que estava: o compilador transformou a marcação em instruções que criam elementos. Você não precisa entender essas três linhas agora. Precisa entender o que elas provam: existe uma tradução, e ela acontece antes da página abrir.

Por que o guia mostra saída de verdade

Toda saída neste guia foi copiada de uma execução real do compilador, com a versão 5.59.2. Se o seu resultado for diferente, alguma coisa no código é diferente — e vale comparar letra por letra antes de suspeitar do guia.

5. O primeiro componente da Ana

Chega de teoria. Este é um componente inteiro: um bloco de script, um título e um parágrafo. Guarde o arquivo como src/App.svelte dentro do projeto.

<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}</h1>
<p>Bem-vinda à padaria.</p>

Pedindo ao compilador o HTML que esse componente produz, sai exatamente isto:

<h1>Olá, Ana</h1> <p>Bem-vinda à padaria.</p>

Duas coisas merecem atenção. Primeiro: {nome} desapareceu e no lugar ficou Ana — as chaves são um buraco no HTML por onde um valor entra. Segundo: o HTML que o navegador recebe não tem o <script> do componente; o valor já foi resolvido. Quem montou essa saída foi o compilador, não você.

<script>
o bloco de JavaScript do componente. Fica no topo do arquivo, e o que é declarado aqui pode ser usado mais abaixo, no HTML.
let nome
uma variável chamada nome. let quer dizer "isto pode mudar depois" — é o contrário de uma constante.
$state('Ana')
o valor inicial, embrulhado numa runa. Quem está dentro de $state avisa a tela quando muda; quem está fora, não.
<h1>Olá, {nome}</h1>
HTML com um buraco. As chaves podem conter qualquer expressão: um nome de variável, uma conta, uma chamada de função.
</script>
fecha o bloco. O que vem depois é HTML comum, sem document.querySelector e sem innerHTML: o Svelte liga o valor ao lugar sozinho.

O nome do arquivo começa com maiúscula por um motivo técnico: é assim que o compilador distingue "um componente meu" de "uma tag do HTML". <App /> é o seu componente; <app /> seria uma tag desconhecida. Você vai ver essa convenção em todos os exemplos.

Missão: o componente cumprimenta o mundo. Troque o valor para que ele cumprimente a Ana e clique em Verificar.

<script>
  let nome = $state('mundo');
</script>

<h1>Olá, {nome}</h1>
<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}</h1>

A caixa compila o seu código com o compilador de verdade e mostra o componente funcionando. Se você escrever algo impossível, a mensagem que aparece é a do compilador, não um aviso inventado pelo guia.

6. As runas: o vocabulário do Svelte 5

Você viu $state('Ana') e talvez tenha estranhado o cifrão. No Svelte 5, palavras que começam com $ e são seguidas de parênteses são runas: comandos que o compilador reconhece e transforma em código. Elas não existem no JavaScript comum — são vocabulário do Svelte, e só funcionam dentro de um arquivo .svelte.

São quatro, e cada uma responde a uma pergunta diferente. $state responde "o que muda?". $derived responde "o que é calculado a partir do que muda?". $effect responde "o que deve acontecer quando algo muda?". $props responde "o que vem de fora?". Nesta aula só $state entra em cena; as outras têm aulas próprias, mais adiante no guia.

RunaResponde à perguntaExemplo
$stateo que pode mudar?let preco = $state(0.9)
$derivedo que é calculado a partir do estado?let total = $derived(preco * 3)
$effecto que fazer quando o estado mudar?$effect(() => console.log(preco))
$propso que este componente recebe de fora?let { titulo } = $props()

Existe um custo nessa escolha de linguagem. Tutoriais escritos entre 2019 e 2023 ensinam outro jeito de declarar valores e outro jeito de escrever eventos; aquele jeito ainda funciona, mas é considerado antigo e o compilador chega a avisar. Este guia ensina só o Svelte 5 com runas. Se um exemplo da internet não tiver cifrão nenhum, desconfie: provavelmente é de outra época.

Um detalhe que confunde no começo: a runa não é uma função que roda na hora. $state('Ana') não "chama" nada; é uma marca que o compilador vê e troca por código de verdade. É por isso que ela só pode aparecer em lugares específicos — na declaração de uma variável, por exemplo. Fora disso, o compilador reclama.

Missão: o mesmo nome aparece escrito duas vezes à mão, e por isso eles podem divergir. Use uma variável com $state nos dois lugares, de modo que a tela mostre "Olá, Ana" e "pão quentinho, Ana".

<h1>Olá, Ana</h1>
<p>pão quentinho, Bia</p>
<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}</h1>
<p>pão quentinho, {nome}</p>

Repare na meta da caixa: ela confere o texto inteiro que aparece na tela. É por isso que a solução precisa acertar os dois lugares ao mesmo tempo — exatamente o que a Ana faria se tivesse um caderno em vez de quatro canetadas.

7. Um botão e um clique

Componente que só mostra texto é cartaz. A graça começa quando a tela reage a alguma coisa: um clique, uma tecla, um formulário enviado. No Svelte 5, ligar um clique a uma ação é um atributo comum, com o nome do evento em minúsculas:

<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}</h1>
<button onclick={() => (nome = 'Bia')}>trocar o nome</button>
<h1>Olá, Ana</h1> <button>trocar o nome</button>

A parte da direita do sinal de igual é uma função: um pedaço de código guardado para rodar depois. Os parênteses vazios dizem que ela não precisa de informação para trabalhar; a seta => separa "o que entra" de "o que acontece"; e o que acontece é nome = 'Bia' — a variável de estado recebe outro valor, avisa quem depende dela, e a tela se atualiza.

O HTML gerado mostra o estado inicial, Olá, Ana, porque o clique ainda não aconteceu. Isso é normal: a saída é uma fotografia do primeiro instante. A parte que muda só aparece quando alguém aperta o botão, e é aí que a reatividade entra.

Missão: o botão soma um, mas o número na tela está escrito à mão e nunca muda. Faça o parágrafo mostrar o valor de cliques, para que um clique deixe a tela em "Cliques: 1".

<script>
  let cliques = $state(0);
</script>

<button onclick={() => cliques++}>somar</button>
<p>Cliques: 0</p>
<script>
  let cliques = $state(0);
</script>

<button onclick={() => cliques++}>somar</button>
<p>Cliques: {cliques}</p>

Esse erro — variável certa, HTML escrito à mão — é o mais comum de todos. O programa funciona, o número muda na memória, e a tela continua mostrando o zero. Quando a tela não acompanha, a primeira pergunta é sempre: o valor está dentro de chaves no HTML?

8. O que o Svelte não é

Quem começa costuma procurar no lugar errado. O Svelte não é uma linguagem de programação nova: dentro do <script> roda JavaScript normal, com if, for, funções e objetos. Você não precisa aprender uma sintaxe paralela para somar dois números. O que o Svelte acrescenta é a camada de marcação — as chaves, os blocos, as runas.

O Svelte também não é o SvelteKit. SvelteKit é um conjunto de ferramentas construído em cima do Svelte para fazer sites com várias páginas, rotas, dados vindos do servidor e formulários. Ele aparece no Nível 3 deste guia. Antes disso, tudo o que você escreve é componente puro, rodando com o Vite, sem roteador e sem servidor.

E o Svelte não é banco de dados, nem hospedagem, nem inteligência artificial. Ele cuida de uma coisa: transformar os seus arquivos em uma interface que reage. Guardar dados, autenticar usuário e publicar o site são outros assuntos, com outras ferramentas — algumas delas aparecem mais tarde, quando você já souber o básico.

9. Do arquivo até a tela: o build

Durante o desenvolvimento, um comando liga um servidor que recompila a cada arquivo salvo. Quando o trabalho está pronto, outro comando gera a versão final, chamada build — a pasta que você publica. Rode o build do projeto da Ana e veja o que sai:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v7.3.8 building client environment for production...
transforming...
✓ 111 modules transformed.
rendering chunks...
computing gzip size...
dist/index.html                 0.25 kB │ gzip:  0.19 kB
dist/assets/index-D4Bgwu4I.js  33.60 kB │ gzip: 12.93 kB
✓ built in 1.28s

Leia com calma, porque cada linha conta uma parte da história. 111 modules transformed significa que o Vite pegou 111 arquivos — o seu componente, o motor do Svelte, pedaços internos — e transformou todos em JavaScript que o navegador entende. No fim, sobraram dois arquivos: um HTML pequeno e um JavaScript de 33,60 kB, já comprimido em 12,93 kB quando o servidor usa gzip.

O nome index-D4Bgwu4I.js tem um pedaço estranho de oito caracteres. É um hash: uma impressão digital calculada a partir do conteúdo. Se uma vírgula mudar no seu código, o hash muda e o nome do arquivo muda junto. Isso permite que o navegador guarde o arquivo em cache para sempre: conteúdo novo tem nome novo, então nunca serve coisa velha.

Trinta e três quilômetros de bytes parecem muito para um "Olá, Ana" — e são, porque o motor do Svelte vai junto. O ganho vem depois: cada componente novo que você escreve acrescenta pouco, porque o motor já está lá. É o contrário de uma biblioteca que precisa interpretar a sua marcação: nesse caso, o custo aparece em cada página aberta.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Elas são o primeiro contato de muita gente com o Svelte 5: quase sempre é sintaxe antiga misturada com sintaxe nova.

Erro 1 — export let junto com runas

export let era o jeito antigo de declarar uma propriedade. Quando o arquivo usa runas, o compilador recusa a mistura.

<script>
  export let nome;
  let total = $state(0);
</script>

<p>{nome} {total}</p>
Erro de compilação (linha 2, coluna 2): Cannot use `export let` in runes mode — use `$props()` instead

A tradução é direta: "não use export let no modo runas; use $props()". A mensagem já diz o substituto. O par ($props) tem aula própria, mas o resumo é: o que vem de fora entra por let { nome } = $props().

Erro 2 — $state sem let

A runa precisa estar na declaração de uma variável. Sem o let, não existe lugar para guardar o estado.

<script>
  contador = $state(0);
</script>

<button>{contador}</button>
Erro de compilação (linha 2, coluna 13): `$state(...)` can only be used as a variable declaration initializer, a class field declaration, or the first assignment to a class field at the top level of the constructor.

A mensagem é comprida porque o Svelte aceita $state em três lugares diferentes. Para quem está começando, a tradução é uma só: escreva let antes do nome. E repare no "linha 2, coluna 13": a posição exata do problema, que você usa para ir direto ao ponto.

Erro 3 — dois blocos <script>

Um componente tem um <script> e, se precisar, um <script module>. Dois scripts comuns não são permitidos.

<script>
  let nome = 'Ana';
</script>

<script>
  let idade = 30;
</script>

<p>{nome} {idade}</p>
Erro de compilação (linha 5, coluna 0): A component can have a single top-level `<script>` element and/or a single top-level `<script module>` element

A solução é juntar as declarações em um bloco só. O compilador não está sendo chato: ele não saberia em que ordem executar dois scripts separados por HTML. Um bloco, uma ordem, um resultado.
