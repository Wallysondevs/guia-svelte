Svelte · Organizando as Pastas

A Ana guardava tudo numa gaveta só: a nota fiscal, o cartão da fornecedora, o preço do pão e o telefone do padeiro. Funcionava até a gaveta encher. No projeto dela aconteceu igual: dez arquivos jogados em src/, todos chamados Cartao.svelte ou Cartao2.svelte. Nesta aula ela arruma as gavetas — e aprende por que o computador também depende dessa arrumação.

Você vai aprender
  • Para que servem as pastas de um projeto Svelte e o que vai em cada uma.
  • O papel de src/lib na organização do projeto da Ana.
  • Como ler a árvore de arquivos com ls -R no terminal.
  • O que ./ e ../ querem dizer num import.
  • Por que agrupar por assunto rende mais do que agrupar por tipo de arquivo.
  • Como deixar o próprio componente organizado por dentro, com blocos na ordem.
  • O que o build imprime quando o caminho apontado não existe.
  • O que muda quando o nome exportado no módulo está diferente.
  • Os três tropeços de organização desta aula, com a mensagem real de cada um.

1. A ideia: organização é sobre onde procurar

Existe uma diferença entre arquivo guardado e arquivo achado. Se a Ana precisa do preço do sonho e leva quarenta segundos abrindo arquivos até encontrar, o problema não é o conteúdo dos arquivos: é o endereço deles. Pasta é endereço.

Um projeto Svelte já nasce com um endereço combinado. src/ é onde fica o código que você escreve; index.html é a página que carrega tudo; package.json lista o que o projeto precisa. Quem chega no projeto da Ana pela primeira vez sabe onde olhar sem perguntar nada — porque o mapa é o mesmo em todo projeto Svelte do mundo.

O ganho é o mesmo da padaria: quando o padeiro novo entra no turno, ele não precisa aprender o seu sistema particular de gavetas. Ele abre a gaveta escrita “farinha”. No código, essa gaveta tem nome: src/lib/Cartao.svelte.

2. O mapa de um projeto Svelte

Um projeto criado com o npm create vite traz uma estrutura mínima. A Ana apagou os exemplos que vinham prontos e ficou com o essencial:

<script>
  import Cartao from './lib/Cartao.svelte';
  import { formatarPreco } from './lib/formato.js';

  let precos = $state([0.9, 2.5, 4]);
</script>

<h1>Loja da Ana</h1>
<Cartao titulo="Pão francês" preco={0.9} />

<ul>
  {#each precos as preco}
    <li>{formatarPreco(preco)}</li>
  {/each}
</ul>

Repare que o App.svelte não sabe como um cartão é desenhado, nem como um preço é formatado. Ele pede: “me dá um cartão com este título e este preço”, “me dá este valor em reais”. Essa é a divisão que organiza o projeto inteiro — quem monta a página não precisa conhecer os detalhes das peças.

O caminho entre parênteses é o endereço da peça. './lib/Cartao.svelte' quer dizer: “a partir da pasta onde este arquivo está, entre em lib e pegue Cartao.svelte”. O ponto sozinho é a pasta atual; a barra separa as pastas; o nome do arquivo vem por último, com a extensão.

CaminhoO que quer dizer
./lib/Cartao.sveltena pasta atual, dentro de lib
./formato.jsna pasta atual, o arquivo formato.js
../lib/Cartao.sveltesuba uma pasta, entre em lib
sveltesem ponto e sem barra: pacote instalado, não arquivo seu

3. O terminal mostra a árvore

Antes de mover arquivo, veja o que existe. O comando ls lista uma pasta; ls -R lista a pasta e tudo o que está dentro dela, em ordem:

ana@notebook:~/loja$ ls -R src
src:
App.svelte
lib
main.js

src/lib:
Cartao.svelte
formato.js

Leia de cima para baixo. Primeiro a pasta pedida (src:) com o que está diretamente nela; depois cada subpasta que apareceu, uma seção por vez. O main.js e o App.svelte moram na raiz de src; o cartão e o módulo de formatação moram em src/lib.

src:
o endereço que você pediu, terminado em dois-pontos. Tudo o que vem abaixo, até a próxima seção, está dentro dela.
App.svelte
o componente principal: o único que o main.js monta na página.
main.js
o ponto de entrada. Ele importa o App e chama mount(); não tem HTML nem estilo.
lib
uma pasta. Por estar sem extensão, você já sabe que precisa descer nela para ver o conteúdo — e é o que a seção seguinte mostra.
Cartao.svelte / formato.js
as peças reaproveitáveis. Uma desenha, a outra calcula. Estão separadas porque têm trabalhos diferentes.

Essa é a árvore inteira do projeto da Ana depois da limpeza: cinco arquivos. Um projeto pequeno não precisa de mais do que isso — e um projeto grande cresce a partir daqui, uma pasta por assunto.

4. Dentro de src/lib: as peças com nome

A pasta lib é a gaveta das peças. Nela ficam os componentes que não são a página em si e os módulos que guardam conta ou formatação. O cartão da vitrine é o exemplo mais simples:

<script>
  let { titulo = 'Pão francês', preco = 0.9 } = $props();
</script>

<article>
  <h2>{titulo}</h2>
  <p>R$ {preco.toFixed(2)}</p>
</article>
<article><h2>Pão francês</h2> <p>R$ 0.90</p></article>

O componente não sabe onde o preço nasceu. Ele recebe duas propriedades com valor padrão e desenha. Os padrões existem porque o compilador deste guia monta o componente sem passar nada — e você vê a saída acima em vez de um erro. No projeto da Ana, os padrões servem para outra coisa: um cartão de demonstração sempre que alguém esquecer de passar o título.

Já o formato.js não desenha nada. Ele exporta uma função:

export function formatarPreco(valor) {
  return 'R$ ' + valor.toFixed(2);
}

Um arquivo .js assim é a menor unidade que existe: não tem componente, não tem estilo, não precisa de navegador. Você pode chamá-lo direto do terminal do projeto para ver se está certo:

ana@notebook:~/loja$ node --input-type=module -e "import('./src/lib/formato.js').then(m => console.log(m.formatarPreco(2.5)))"
R$ 2.50

Uma linha de saída, nenhum navegador aberto. Isso é o motivo de separar cálculo de desenho: a conta pode ser conferida sozinha, dez vezes mais rápido do que abrindo a página e procurando o número na tela.

Regra da gaveta

Se o arquivo desenha algo que aparece na tela, ele é .svelte e mora junto dos componentes. Se ele só calcula, formata ou busca dado, é .js e pode morar em lib também — mas nunca dentro do componente, escondido no meio do HTML.

Missão: os dados do produto foram agrupados num objeto chamado produto, mas o HTML continua procurando nome e preco soltos — e o componente quebra. Aponte para as propriedades do objeto.

<script>
  let produto = $state({ nome: 'Sonho', preco: 2.5 });
</script>

<p>{nome} custa R$ {preco.toFixed(2)}</p>
<script>
  let produto = $state({ nome: 'Sonho', preco: 2.5 });
</script>

<p>{produto.nome} custa R$ {produto.preco.toFixed(2)}</p>

Agrupar em objeto tem um preço: cada acesso ganha o prefixo produto.. Em troca, o nome do objeto diz a que conjunto o dado pertence, e você pode ter dois produtos no mesmo arquivo sem inventar nome1 e nome2.

5. Agrupar por assunto, não por tipo

Existem duas escolas de arrumar pasta. A primeira separa por tipo de arquivo: uma pasta para componentes, uma para funções, uma para estilos. A segunda separa por assunto: tudo o que é da vitrine junto, tudo o que é do caixa junto.

Por tipoPor assunto
components/, utils/, styles/vitrine/, caixa/, estoque/
Uma mudança na vitrine mexe em três pastasUma mudança na vitrine mexe em uma pasta
Fácil de explicar no começoFácil de manter quando cresce
utils/ vira a pasta “de tudo”A pasta diz o que o código faz

O guia prefere a segunda, com uma exceção: projeto pequeno, com menos de dez arquivos, não precisa de subpasta de assunto. src/lib e pronto. Criar vitrine/ com dois arquivos dentro é organização de fachada — mais cliques, nenhuma vantagem.

O critério prático é a pergunta que você faz ao procurar: “onde está o código que calcula o desconto da vitrine?”. Se a resposta é “em utils/, junto com mais trinta funções que não têm nada a ver”, a pasta está organizada por tipo e você vai sofrer. Se é “em vitrine/desconto.js”, você achou antes de abrir o editor.

6. O componente também tem organização por dentro

Pasta é o nível de fora. Existe o nível de dentro: a ordem do arquivo .svelte. A convenção do guia é sempre a mesma — primeiro o <script>, depois o HTML, por último o <style>. Dentro do script, uma ordem que também ajuda:

<script>
  let precos = $state([0.9, 2.5, 4]);
  let total = $derived(precos.reduce((soma, p) => soma + p, 0));
</script>

{#snippet linha(valor)}
  <li>{valor.toFixed(2)}</li>
{/snippet}

<ul>
  {#each precos as preco}
    {@render linha(preco)}
  {/each}
</ul>
<p>Total: {total.toFixed(2)}</p>
<ul><li>0.90</li><li>2.50</li><li>4.00</li></ul> <p>Total: 7.40</p>

Três decisões de organização nesse arquivo pequeno. Primeira: total é $derived, não $state — ele não guarda um valor, ele calcula a partir de precos. Segunda: o pedaço de HTML que se repete virou {#snippet}, com nome e parâmetro, em vez de duas cópias do <li> escritas à mão. Terceira: o snippet ficou entre o script e o uso, na ordem em que se lê.

O que não se guarda duas vezes

Se um valor pode ser calculado a partir de outro, guarde o de origem e derive o resto. Dois $state para a mesma informação criam duas verdades: uma atualiza, a outra esquece, e a tela mostra o número errado. É o erro de organização mais caro que existe dentro de um componente.

Missão: a lista tem dois preços, mas o total ficou congelado em 0. Tire o $state do total e faça dele um valor derivado da lista — a soma dos preços.

<script>
  let precos = $state([0.9, 2.5]);
  let total = $state(0);
</script>

<p>Total: {total.toFixed(2)}</p>
<script>
  let precos = $state([0.9, 2.5]);
  let total = $derived(precos.reduce((soma, p) => soma + p, 0));
</script>

<p>Total: {total.toFixed(2)}</p>

A solução usa reduce, que percorre a lista acumulando um valor: começa em 0 e soma cada preço. O $derived refaz a conta sozinho sempre que precos mudar. Você escreve a conta uma vez e nunca mais precisa lembrar de atualizar o total.

7. O build de um projeto organizado

Com as peças nos seus lugares, o comando de produção roda sem aviso:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v7.3.8 building client environment for production...
transforming...
✓ 113 modules transformed.
rendering chunks...
computing gzip size...
dist/index.html                 0.25 kB │ gzip:  0.19 kB
dist/assets/index-DZ9lvoL7.js  41.48 kB │ gzip: 15.97 kB
✓ built in 2.44s

“113 modules transformed” conta tudo o que entrou no pacote: o Svelte, o seu componente, o módulo de formatação, cada dependência. Um projeto organizado não gera menos módulos — organiza os mesmos. O tamanho final é o preço do que você importou; o endereço não pesa nada.

O que muda, de verdade, é o tempo até achar o problema quando ele aparece. Num projeto com quarenta arquivos na raiz, a mensagem de erro aponta um arquivo e você ainda precisa descobrir qual dos cinco Cartao é. Com pastas por assunto, o caminho na mensagem já é a resposta.

8. Quando o caminho não existe

A Ana moveu o Cartao.svelte para lib e esqueceu de atualizar o import. O import continuou pedindo o arquivo na raiz de src:

Erro 1 — caminho que não aponta para arquivo nenhum 
<script>
  import Cartao from './Cartoes.svelte';
</script>

<h1>Loja da Ana</h1>
<Cartao titulo="Pão francês" preco={0.9} />

O editor não reclama, porque nada foi digitado errado — só o endereço está velho. Quem descobre é o build:

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v7.3.8 building client environment for production...
transforming...
✓ 19 modules transformed.
✗ Build failed in 579ms
error during build:
Could not resolve "./Cartoes.svelte" from "src/App.svelte"

“Could not resolve” quer dizer não consegui resolver — não achei o arquivo que esse caminho aponta. A mensagem vem em duas partes: o caminho que falhou ("./Cartoes.svelte") e o arquivo que pediu ("src/App.svelte"). Com os dois, você sabe exatamente onde olhar. Abaixo dessa linha o Vite ainda imprime a pilha de chamadas interna dele, que não ajuda em nada nesta hora.

O que conferir, nesta ordem

Primeiro: o nome do arquivo no disco é igual, letra por letra, ao do import? Maiúscula conta. Segundo: o caminho relativo aponta para a pasta certa — ./ é a pasta do arquivo que importa, ../ sobe uma. Terceiro: a extensão está escrita (.svelte, .js). Faltando qualquer um dos três, o build para com “Could not resolve”.

9. Quando o nome exportado está errado

O caminho pode estar certo e o nome, não. O módulo exporta formatarPreco; o componente pediu formatarPrecos, no plural:

Erro 2 — arquivo certo, nome exportado errado 
<script>
  import Cartao from './lib/Cartao.svelte';
  import { formatarPrecos } from './lib/formato.js';

  let precos = $state([0.9, 2.5]);
</script>

<h1>Loja da Ana</h1>
<Cartao titulo="Pão francês" preco={0.9} />

<ul>
  {#each precos as preco}
    <li>{formatarPrecos(preco)}</li>
  {/each}
</ul>
ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

vite v7.3.8 building client environment for production...
transforming...
✓ 113 modules transformed.
✗ Build failed in 620ms
error during build:
src/App.svelte (3:11): "formatarPrecos" is not exported by "src/lib/formato.js", imported by "src/App.svelte".

1: <script>
2:   import Cartao from './lib/Cartao.svelte';
3:   import { formatarPrecos } from './lib/formato.js';
              ^
4:
5:   let precos = $state([0.9, 2.5]);

Essa mensagem é melhor que a anterior, e vale aprender a ler. Ela começa pela posição — src/App.svelte (3:11), linha 3, coluna 11 — depois diz o que não existe e onde deveria existir. Embaixo vem o trecho do arquivo com o acento circunflexo sob a palavra errada.

O erro é de organização na origem: o nome do export vive no formato.js, longe de quem importa. Por isso a mensagem cita os dois arquivos. A correção é escolher um dos dois nomes e usá-lo nos dois lugares — nunca “consertar” criando um alias para esconder a diferença.

10. Quando dois componentes têm o mesmo nome

Agora o caso mais comum de quem tem duas pastas de assunto: dois cartões diferentes, ambos chamados Cartao. A Ana importou os dois no mesmo arquivo:

Erro 3 — dois componentes com o mesmo nome 
<script>
  import Cartao from './lib/Cartao.svelte';
  import Cartao from './lib/CartaoGrande.svelte';
</script>

<h1>Loja da Ana</h1>
<Cartao titulo="Pão francês" preco={0.9} />
Erro de compilação (linha 3, coluna 9): Identifier 'Cartao' has already been declared

“O identificador ‘Cartao’ já foi declarado”: a segunda linha tenta criar o mesmo nome da primeira. O compilador nem chega a olhar o conteúdo dos arquivos — o problema está no script, antes de qualquer componente ser desenhado.

A saída é renomear na importação, no momento em que o nome entra no arquivo:

<script>
  import CartaoVitrine from './vitrine/Cartao.svelte';
  import CartaoCaixa from './caixa/Cartao.svelte';
</script>

<h1>Loja da Ana</h1>
<CartaoVitrine titulo="Pão francês" preco={0.9} />
<CartaoCaixa titulo="Total" preco={2.7} />

Os arquivos no disco continuam com o mesmo nome, cada um na sua pasta. Quem mudou foram os nomes dentro deste arquivo — e a mudança conta uma história: aqui é o cartão da vitrine, ali o do caixa. Repare que o nome na importação e o nome na tag continuam iguais; é essa repetição que faz a tag ser reconhecida como componente.

Missão: o pedaço de HTML que desenha a linha virou um {#snippet} chamado precoFormatado, mas o {@render} ainda chama pelo nome antigo. Acerte a chamada para a lista aparecer.

<script>
  let precos = $state([0.9, 2.5]);
</script>

{#snippet precoFormatado(valor)}
  <li>{valor.toFixed(2)}</li>
{/snippet}

<ul>
  {#each precos as preco}
    {@render linha(preco)}
  {/each}
</ul>
<script>
  let precos = $state([0.9, 2.5]);
</script>

{#snippet precoFormatado(valor)}
  <li>{valor.toFixed(2)}</li>
{/snippet}

<ul>
  {#each precos as preco}
    {@render precoFormatado(preco)}
  {/each}
</ul>

Ao rodar a caixa, o erro é linha is not defined. Um snippet e uma função são a mesma coisa para o compilador: um nome que precisa existir no momento em que é chamado. Nome de snippet é nome de gaveta — se a etiqueta está errada, ninguém acha o conteúdo.

Resumo

  • Pasta é endereço: o projeto fica previsível para você e para quem chega depois.
  • src/ guarda o código, src/lib/ guarda as peças reaproveitáveis.
  • import X from './lib/X.svelte': o ponto é a pasta atual, a barra separa pastas.
  • ../ sobe uma pasta; nome sem ponto e sem barra é pacote instalado.
  • ls -R mostra a árvore inteira de uma pasta no terminal.
  • Agrupe por assunto quando o projeto crescer; utils/ vira a pasta “de tudo”.
  • Dentro do componente: <script>, HTML, <style>; e derive o que dá para calcular.
  • Could not resolve = caminho errado; is not exported by = nome do export errado.
  • Dois imports com o mesmo nome param a compilação: Identifier 'X' has already been declared.
  • Snippet e função precisam existir no momento da chamada; nome errado quebra na tela.
