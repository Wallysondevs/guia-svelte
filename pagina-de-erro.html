SvelteKit · +error.svelte

A Ana colou um cartaz na porta da padaria: "se o pão acabou, avise com educação". Não é um cartaz sobre pão — é um cartaz sobre o que fazer quando não tem pão. Toda aplicação precisa disso, e é fácil de esquecer: o caminho feliz é divertido de programar, o caminho triste não. O +error.svelte é o cartaz do SvelteKit. Ele aparece quando um endereço não existe, quando o load diz que o item sumiu e quando o código estoura no meio do caminho — e nesta aula você vai ver os três casos com os números e as mensagens reais.

Você vai aprender

  • De onde vêm page.status e page.error.
  • Por que o 404 já funciona antes de você escrever qualquer coisa.
  • Como responder um erro com mensagem própria usando error(...).
  • A diferença entre erro esperado (404) e erro inesperado (500).
  • Por que a mensagem do 500 é sempre "Internal Error" na tela.
  • Como o layout continua aparecendo na página de erro.
  • O padrão error?.message ?? 'algo deu errado' e por que ele existe.
  • O que acontece quando a própria página de erro quebra.
  • As três falhas reais desta aula, com a saída do terminal.

1. A ideia: o cartaz de "hoje não temos"

Numa padaria, o cartaz de "hoje não temos pão de queijo" não é um fracasso: é informação. Quem chega sabe o que aconteceu e o que fazer — pedir outra coisa, voltar amanhã, perguntar o horário. O que estraga a experiência é a porta fechada sem aviso: a pessoa empurra, não entende, vai embora achando que a padaria fechou.

Na web é igual, com uma diferença de vocabulário. "Hoje não temos" é o 404: o endereço não existe ou o item não está mais lá. "A cozinha pegou fogo" é o 500: o endereço existe, mas o código quebrou. São situações diferentes, merecem páginas diferentes e — detalhe importante — merecem números diferentes na resposta HTTP, porque robôs de busca e programas leem o número, não o texto.

O SvelteKit entrega os dois casos prontos, com uma página padrão feia mas funcional. O +error.svelte existe para você trocar essa página padrão por uma que fale a língua da padaria, sem perder os números. É um arquivo só, e ele serve para o site inteiro — ou para uma parte do site, se você colocar dentro de uma pasta.

Repare que o desenho da tabela separa duas coisas que costumam andar juntas: o fato (não tem pão) e o aviso (o cartaz). No código, o fato acontece no load, com error(404, …); o aviso é o componente que desenha. Você pode mudar o aviso sem tocar no fato, e é isso que permite ter um cartaz bonito sem espalhar texto de erro por vinte arquivos.

3. Onde mora a página de erro

O arquivo é src/routes/+error.svelte. Este é o da Ana:

<script>
	import { page } from '$app/state';
</script>

<h1>{page.status}</h1>
<p>{page.error?.message}</p>
<a href="/">voltar para o início</a>
+error.svelte
o nome fixo. O + diz que é arquivo especial do SvelteKit; error diz qual é o papel dele.
page
o objeto da página atual, importado de $app/state. Nele estão status, error, url e params.
page.status
o número HTTP que o servidor vai responder: 404, 500, ou o que o seu error() mandou.
page.error?.message
o texto do erro. O ?. protege o caso de page.error ser nulo, que acontece em páginas normais.
<a href="/">
a saída. Uma página de erro sem caminho de volta é um beco sem saída.

Se você comparar com o que o SvelteKit gera quando não existe +error.svelte, a diferença é só de acabamento: a página padrão tem o mesmo <h1>404</h1> e o mesmo <p>Not Found</p>, sem menu e sem link de volta. O +error.svelte não cria o comportamento do erro — ele veste o comportamento que já existe.

4. De onde vêm status e error

Quando uma requisição falha, o SvelteKit monta um objeto de erro com duas informações — número e mensagem — e o coloca em page.error. O número também aparece sozinho em page.status, porque é ele que vai no cabeçalho da resposta HTTP. A tabela abaixo mostra o que você pode ler:

CampoTipoQuando tem valor
page.statusnúmerosempre na página de erro (404, 500, …)
page.errorobjeto ou nullna página de erro, com message; null em página normal
page.urlURLsempre: serve para mostrar qual endereço falhou
page.paramsobjetoquando a rota tem colchetes

O page.error ser nulo em página normal não é detalhe teórico: é a causa do erro mais comum desta aula. Se você escrever page.error.message numa página comum, o JavaScript tenta ler message de null e o componente estoura. O ?. resolve: "se o da esquerda existir, leia; se não, devolva undefined".

5. O 404 que você não escreveu

Antes de qualquer código seu, o SvelteKit já responde 404 para endereços que não existem. A Ana conferiu com o curl, olhando os cabeçalhos:

ana@notebook:~/loja/kit$ curl -s -i localhost:4173/nao-existe | head -4
HTTP/1.1 404 Not Found
Vary: Origin
content-length: 4371
content-type: text/html

A primeira linha é o que importa: 404 Not Found. E o corpo dessa resposta é a página de erro da Ana dentro do layout do site. O comando abaixo tira os comentários internos do Svelte e recorta o miolo:

ana@notebook:~/loja/kit$ curl -s localhost:4173/nao-existe | sed -e 's/<!--[^>]*-->//g' | grep -o '<nav.*</footer>'
<nav class="svelte-12qhfyh"><a href="/" class="svelte-12qhfyh">Início</a> <a href="/paes" class="svelte-12qhfyh">Pães</a> <a href="/sobre" class="svelte-12qhfyh">Sobre</a> <a href="/contato" class="svelte-12qhfyh">Contato</a></nav> <main><h1>404</h1> <p>Not Found</p> <a href="/">voltar para o início</a></main> <footer class="svelte-12qhfyh">Padaria da Ana</footer>

Leia com calma, porque tem muita informação boa aí. O nav e o footer vieram do +layout.svelte; dentro do main está o <h1>404</h1> do +error.svelte; e o <p>Not Found</p> é a mensagem que o SvelteKit usa quando ninguém escreveu outra. Ou seja: o erro não foge da moldura. Quem se perde no site continua com o menu à mão.

6. Responder um erro com mensagem própria

A mensagem "Not Found" serve, mas não ajuda. A Ana queria dizer o que acabou. Para isso existe a função error, importada de @sveltejs/kit, usada dentro de um load:

import { error } from '@sveltejs/kit';

export function load({ params }) {
	if (params.slug === 'queijo') {
		error(404, 'O pão de queijo acabou');
	}
	return { slug: params.slug };
}

O primeiro argumento é o status HTTP; o segundo é a mensagem que aparece na tela. A partir do momento em que error é chamada, o SvelteKit abandona o resto do load, não chama o componente da página e monta a página de erro. O terminal mostra as duas rotas, uma com erro e outra sem:

ana@notebook:~/loja/kit$ curl -s localhost:4173/paes/queijo | grep -o '<h1>.*</a>'
<h1>404</h1> <p>O pão de queijo acabou</p> <a href="/">voltar para o início</a>
ana@notebook:~/loja/kit$ curl -s localhost:4173/paes/forma | grep -o '<h1>.*</a>'
<h1>forma</h1> <p>Você pediu o pão forma.</p> <a href="/paes">voltar</a>

A primeira resposta tem o status 404 e a mensagem da Ana; a segunda seguiu o caminho normal. Repare que a página de erro usou page.error?.message e mostrou exatamente o texto que veio do load — sem tratamento, sem tradução. É por isso que a mensagem precisa ser escrita para humanos e sem informação interna.

Missão: o componente mostra o número, mas não a explicação. Acrescente um parágrafo com a mensagem, para a tela mostrar 404 página não encontrada.

<script>
  let status = $state(404);
  let mensagem = $state('página não encontrada');
</script>

<h1>{status}</h1>
<script>
  let status = $state(404);
  let mensagem = $state('página não encontrada');
</script>

<h1>{status}</h1>
<p>{mensagem}</p>

Número e mensagem são coisas diferentes e aparecem em lugares diferentes: o número é para a máquina (o cabeçalho HTTP, o robô de busca), a mensagem é para a pessoa. A página de erro é o único lugar em que você escreve os dois juntos, e por isso ela costuma ser mais útil do que parece.

7. Erro esperado × erro inesperado

Existe uma diferença de fundo entre os dois números. error(404, …) é um erro esperado: você previu a situação e decidiu responder com ela. Já o 500 é inesperado: ninguém escreveu aquele erro, ele aconteceu porque uma linha de código tentou ler algo que não existia. A Ana provocou um de propósito, numa página comum:

<script>
	import { page } from '$app/state';
</script>

<h1>{page.error.message}</h1>

Vai parecer inofensivo, e é justamente aí que mora o perigo: em uma página normal, page.error é null. O servidor tentou desenhar a página, quebrou, e o SvelteKit respondeu com o status 500 e a página de erro:

ana@notebook:~/loja/kit$ curl -s -o /dev/null -w '%{http_code}\n' localhost:5183/sobre
500
ana@notebook:~/loja/kit$ curl -s localhost:5183/sobre | sed -e 's/<!--[^>]*-->//g' | grep -o '<main.*</main>'
<main class="svelte-12qhfyh"><h1>500</h1> <p>Internal Error</p> <a href="/">voltar para o início</a></main>

Na tela, o texto é sempre "Internal Error", nunca o motivo. O motivo fica no terminal, e é ali que você vai procurar:

TypeError: Cannot read properties of null (reading 'message')
    at eval (src/routes/sobre/+page.svelte:5:17)
    at eval (node_modules/svelte/src/internal/server/renderer.js:416:11)
    at Renderer.child (node_modules/svelte/src/internal/server/renderer.js:305:18)
    at Renderer.component (node_modules/svelte/src/internal/server/renderer.js:414:8)
    at _page (src/routes/sobre/+page.svelte:2:2)
500 GET /sobre

Três informações para guardar. A primeira: a mensagem do erro diz null, não undefined — foi page.error que era nulo. A segunda: a posição 5:17 aponta para a coluna exata onde o .message foi lido. A terceira: a última linha do log, 500 GET /sobre, é o resumo do pedido que falhou. Procurar essa linha no terminal é o primeiro passo de qualquer investigação.

Missão: numa página normal o erro chega nulo e o componente quebra ao ler error.message. Faça a tela mostrar sem erro quando não houver erro nenhum.

<script>
  // na página de erro este objeto vem preenchido; numa página comum vem null
  let { error = null } = $props();
</script>

<p>{error.message}</p>
<script>
  // na página de erro este objeto vem preenchido; numa página comum vem null
  let { error = null } = $props();
</script>

<p>{error?.message ?? 'sem erro'}</p>

Enquanto você editar, a caixa vai mostrar o erro de verdade do navegador no primeiro caso — é a mesma classe de falha que a Ana viu no terminal. Depois da correção, aparece o texto de reserva. O ?? só entra quando o da esquerda é null ou undefined; uma mensagem vazia ('') passaria por ele, e isso é o comportamento correto: vazio é diferente de ausente.

8. A moldura continua no erro

Um detalhe que separa um site cuidado de um site amador: a página de erro também tem menu. Isso acontece porque o +error.svelte da raiz é desenhado dentro do +layout.svelte da raiz. O layout não sabe que houve erro, e nem precisa saber — ele só desenha o buraco.

Isso tem uma consequência prática: se o seu layout depende de um dado que só existe em páginas normais, ele vai quebrar justamente na hora do erro. O layout precisa ser capaz de desenhar sem dados. No projeto da Ana, o layout só tem menu e rodapé, então funciona nos dois mundos.

Missão: para 404 a página oferece o caminho de volta, mas para 500 ela fica sem nada. Acrescente o {:else} com o texto tente de novo em alguns minutos.

<script>
  let { status = 500 } = $props();
</script>

<h1>{status}</h1>
{#if status === 404}
  <a href="/">voltar para o início</a>
{/if}
<script>
  let { status = 500 } = $props();
</script>

<h1>{status}</h1>
{#if status === 404}
  <a href="/">voltar para o início</a>
{:else}
  <p>tente de novo em alguns minutos</p>
{/if}

Tratar cada número com uma ação diferente é o padrão em sites grandes: 404 pede um caminho de volta, 500 pede paciência, 403 pede login. A condição é uma só e o componente continua pequeno. Se as mensagens ficarem grandes, é hora de separar um componente de aviso e chamá-lo com props — mas isso é refino, não obrigação.

9. Onde colocar um +error.svelte por pasta

Como todo arquivo +, o +error.svelte vale para a pasta onde está e para as subpastas. Isso permite um cartaz diferente em cada área: o site público com um tom, o painel restrito com outro. A tabela mostra a escolha e o custo.

Onde o arquivo estáAparece quando falhaCusto
src/routes/+error.sveltequalquer rotaum texto para todo mundo
src/routes/admin/+error.svelte/admin e abaixomais um arquivo para manter
src/routes/(painel)/+error.svelteas rotas do grupoo grupo não aparece na URL

Um aviso que economiza horas: o +error.svelte mais próximo não captura erros que acontecem no load do próprio layout. Se o +layout.js da pasta estoura, o SvelteKit usa a página de erro do nível acima. Erro no layout é resolvido pelo pai, não pelo filho — porque o filho nem chegou a ser desenhado.

10. Quando dá errado

Os três casos abaixo saíram do terminal do projeto da Ana. O primeiro é o que você já viu na seção 7, resumido; os outros dois mostram o que acontece quando é a própria página de erro que falha.

Caso 1 — ler page.error.message em página comum

O código está na seção 7. O componente não compila mal: ele quebra na hora de desenhar, porque page.error é null. A resposta vira 500 e a página de erro aparece no lugar da página /sobre.

TypeError: Cannot read properties of null (reading 'message')
    at eval (src/routes/sobre/+page.svelte:5:17)
500 GET /sobre

O conserto é o ?.: page.error?.message. Em página comum o valor vira undefined e o Svelte desenha vazio, sem quebrar. Na página de erro, o mesmo código mostra a mensagem. Um caractere de diferença entre uma página que funciona e um 500.

Caso 2 — a página de erro também quebra

A Ana digitou page.erro.message, com um "o" a menos. Como esse código está dentro do +error.svelte, o erro acontece enquanto a página de erro é desenhada. O SvelteKit não tem para onde fugir: usa a página de emergência, sem layout e sem menu.

TypeError: Cannot read properties of undefined (reading 'message')
    at eval (src/routes/+error.svelte:6:15)
    at _error (src/routes/+error.svelte:2:2)
500 GET /nao-existe

E o corpo da resposta, nesse caso, é só isto:

ana@notebook:~/loja/kit$ curl -s localhost:5183/nao-existe | grep -o '<h1[^>]*>[^<]*</h1>'
<h1>Internal Error</h1>

Repare no detalhe cruel: o endereço pedido era um 404, e a resposta final foi 500. Quando a página de erro falha, o número do erro original se perde. É a única página do site em que um erro de digitação custa tão caro — vale testar o +error.svelte abrindo um endereço inexistente de propósito.

Caso 3 — sem +error.svelte

Para ver o que o SvelteKit faz sozinho, a Ana renomeou o arquivo e pediu um endereço inexistente. A resposta veio 404, com a página padrão:

ana@notebook:~/loja/kit$ curl -s localhost:5183/nao-existe | grep -oE '(<h1[^>]*>[^<]*</h1>|<p[^>]*>[^<]{0,40}</p>)'
<h1>404</h1>
<p>Not Found</p>

Funciona, e é feio: sem menu, sem link de volta, sem a voz da padaria. A página padrão não é um erro — é o mínimo. Ter o +error.svelte é o que transforma o beco sem saída em caminho de volta.

12. Uma frase sobre segurança

A mensagem do erro é pública. Ela aparece na tela, no HTML, no cache do navegador e no histórico de quem visitou. Nunca escreva ali o nome da tabela do banco, o caminho de um arquivo do servidor, o token de uma API ou o e-mail de um cliente. "O pão de queijo acabou" é uma boa mensagem; "SELECT falhou em paes_estoque linha 4" é um presente para quem procura brechas.

Para o caso do 500, o SvelteKit já resolve metade do problema: a tela mostra sempre "Internal Error", e o detalhe fica no terminal do servidor, onde só você lê. Se você precisa guardar esse detalhe em algum lugar (um arquivo de log, um serviço de monitoramento), existe o gancho handleError, no arquivo hooks.server.js, que aparece mais adiante no guia.

13. O caminho até aqui

O site da Ana agora tem um cartaz à altura da padaria: número grande, mensagem em português, caminho de volta e o menu do site em volta. O 404 existe para endereço errado e para pão que acabou; o 500 existe para quando o código escorrega; e a diferença entre os dois está no número, não no texto.

Ficou de fora uma pergunta que aparece rápido: e quando o erro não é para mostrar cartaz, e sim para levar a pessoa para outro lugar — depois de um login, por exemplo? Essa é a função do redirect, que aparece junto com Navegando com goto. E se o assunto é agrupar rotas para um cartaz só valer numa área do site, o caminho é Grupos de Rotas.

Resumo

  • src/routes/+error.svelte é a página que aparece quando algo falha.
  • O 404 já funciona sem você escrever nada; o arquivo só troca o acabamento.
  • page.status traz o número; page.error?.message traz o texto.
  • page.error é null em página comum: sem ?., o componente quebra e vira 500.
  • error(status, mensagem) de @sveltejs/kit responde um erro esperado dentro do load.
  • 500 é erro inesperado: a tela mostra "Internal Error" e o motivo fica no terminal.
  • O +error.svelte é desenhado dentro do layout, então o menu continua à mão.
  • Se a própria página de erro quebra, o SvelteKit usa a página de emergência e o status original se perde.
  • +error.svelte dentro de uma pasta vale só para aquela parte do site.
  • Mensagem de erro é pública: nada de nome de tabela, caminho de arquivo ou token.
