Projetos · Blog com SvelteKit

A Ana escreve receitas num caderno e quer publicá-las na internet. Ela já sabe fazer componentes, mas um blog não é um componente: são endereços. Cada receita precisa de um link próprio, que funcione quando alguém colar no WhatsApp e abrir dias depois — inclusive com o JavaScript desligado. É exatamente para isso que existe o SvelteKit. Nesta aula o blog é construído em três versões, e cada uma é conferida com um pedido HTTP de verdade, com o código de resposta que o servidor devolveu.

Você vai aprender
  • O que muda quando o projeto deixa de ser um componente e vira um site.
  • Como o +page.svelte vira o endereço /.
  • O papel do +layout.svelte e do children.
  • Como carregar dados no servidor com +page.server.js.
  • Como uma pasta com colchetes, [slug], vira endereço variável.
  • Como responder 404 com error() e uma página de erro própria.
  • Como ler a query string (?categoria=bolos) no load.
  • Como criar um endpoint JSON com +server.js.
  • O que o servidor devolve em HTML e por que aparecem marcadores de comentário.
  • As mensagens reais de 500 e de $lib removido.

1. Um blog não é uma tela, são endereços

Um componente Svelte vive dentro de uma página. Um site precisa de mais: cada conteúdo tem um endereço que pode ser copiado, guardado nos favoritos e aberto direto. O SvelteKit resolve isso ligando arquivos a endereços. Uma pasta dentro de src/routes é um pedaço do caminho, e o arquivo +page.svelte é o que aparece naquele endereço.

Arquivo no projetoEndereço no navegador
src/routes/+page.svelte/
src/routes/post/+page.svelte/post
src/routes/post/[slug]/+page.svelte/post/qualquer-coisa
src/routes/api/receitas/+server.js/api/receitas (JSON, sem HTML)

Essa ligação tem uma consequência prática: o servidor recebe o pedido, monta o HTML e devolve. O navegador recebe uma página pronta e só depois o JavaScript assume. Se o JavaScript falhar, o texto ainda está lá. É por isso que a Ana consegue compartilhar uma receita e ela abrir no celular de quem nunca visitou o site.

2. Versão 1 — um componente com a lista

A primeira versão é a menor coisa que já é um site: uma página na raiz, com três receitas escritas no próprio arquivo e um link para cada uma.

<script>
  let posts = [
    {
      slug: 'pao-de-fermentacao-natural',
      titulo: 'Pão de fermentação natural',
      resumo: 'Como alimentar o fermento e assar um pão de casca grossa.'
    },
    {
      slug: 'bolo-de-cenoura',
      titulo: 'Bolo de cenoura da padaria',
      resumo: 'A receita que sai às terças, com cobertura de chocolate.'
    },
    {
      slug: 'pao-de-queijo',
      titulo: 'Pão de queijo mineiro',
      resumo: 'Polvilho azedo, queijo meia-cura e forno bem quente.'
    }
  ];
</script>

<h1>Receitas da padaria</h1>

<ul>
  {#each posts as post (post.slug)}
    <li>
      <a href="/post/{post.slug}">{post.titulo}</a>
      <p>{post.resumo}</p>
    </li>
  {/each}
</ul>

O compilador não precisa do SvelteKit para montar este componente; ele devolve o HTML abaixo. Repare no href: o endereço de cada receita saiu do slug.

<h1>Receitas da padaria</h1> <ul><li><a href="/post/pao-de-fermentacao-natural">Pão de fermentação natural</a> <p>Como alimentar o fermento e assar um pão de casca grossa.</p></li><li><a href="/post/bolo-de-cenoura">Bolo de cenoura da padaria</a> <p>A receita que sai às terças, com cobertura de chocolate.</p></li><li><a href="/post/pao-de-queijo">Pão de queijo mineiro</a> <p>Polvilho azedo, queijo meia-cura e forno bem quente.</p></li></ul>

Nesta versão os dados moram no componente. É a decisão mais simples e a que envelhece pior: para marcar uma receita como publicada, seria preciso editar o arquivo e recompilar o site. Note também que let posts = [...] não tem $state — a lista não muda enquanto a página está aberta, então não há estado nenhum ali.

A anatomia da versão 1

src/routes/+page.svelte
o endereço /. O + no começo do nome é o que diz ao SvelteKit "este arquivo é uma página".
let posts = [...]
uma lista de objetos. Cada objeto tem slug (o pedaço do endereço), titulo e resumo.
{#each posts as post (post.slug)}
um item por receita, com a chave no slug — a mesma chave que identifica a receita no endereço.
href="/post/{post.slug}"
texto e variável misturados dentro de um atributo. O resultado é o endereço completo, montado para cada item.
<ul> e <li>
uma lista de verdade, não uma sequência de div. O navegador e os leitores de tela sabem que estes itens são um conjunto.

3. O layout que se repete em toda página

Todo site tem pedaços que aparecem em todas as páginas: o cabeçalho, o menu, o rodapé. No SvelteKit eles moram no +layout.svelte, e a parte que muda entra no lugar de {@render children()}.

<script>
  let { children } = $props();
</script>

<header>
  <a href="/">Padaria da Ana · receitas</a>
</header>

<main>
  {@render children()}
</main>

<style>
  header { padding: 8px 0; border-bottom: 1px solid #ddd; margin-bottom: 16px; }
  main { max-width: 40rem; }
</style>

O children é uma propriedade especial: ela chega como uma função que desenha o conteúdo da página. Não é um <slot>, que era o jeito antigo. E o <style> do layout vale para o layout — o escopo não vaza para a página filha.

Com o layout no lugar, a versão 1 já tem cabeçalho, e o endereço / responde com o HTML montado no servidor. O terminal confirma o código 200 e o título:

ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5174/
200
ana@notebook:~/loja$ curl -s http://localhost:5174/ | grep -o "<h1>[^<]*</h1>"
<h1>Receitas da padaria</h1>

O curl é um programa que pede uma página e mostra a resposta, sem navegador. O primeiro comando descarta o corpo (-o /dev/null) e imprime só o código; o segundo pega o corpo e filtra a linha do h1. Se você abrir o mesmo endereço no navegador, o resultado é o mesmo HTML — só que com a página desenhada.

4. Versão 2 — os dados vêm do servidor

Na segunda versão a lista sai do componente e vai para um módulo compartilhado. Quem entrega os dados para a página é um arquivo com um nome específico: +page.server.js. Ele exporta uma função load, e o que ela devolve chega ao +page.svelte como a propriedade data.

import { posts } from '#lib/posts.js';

export function load() {
  return {
    posts: posts.map(({ slug, titulo, resumo }) => ({ slug, titulo, resumo }))
  };
}

Três coisas para observar. O sufixo .server.js promete que este arquivo nunca vai para o navegador — pode ler banco de dados, senha, arquivo. O #lib é o atalho para src/lib nesta versão do SvelteKit (o antigo $lib foi removido). E o map no fim existe para não mandar o texto inteiro da receita na listagem: só o que a lista mostra.

<script>
  let { data } = $props();
</script>

<h1>Receitas da padaria</h1>

<ul>
  {#each data.posts as post (post.slug)}
    <li>
      <a href="/post/{post.slug}">{post.titulo}</a>
      <p>{post.resumo}</p>
    </li>
  {/each}
</ul>

A anatomia da versão 2

export function load()
a função que o SvelteKit chama antes de desenhar a página. Ela roda no servidor.
return { posts: ... }
o objeto devolvido vira o data da página. Precisa ser dado simples: texto, número, lista, objeto.
#lib/posts.js
atalho para src/lib/posts.js, definido em package.json. Serve para não escrever caminho relativo cheio de ../../.
let { data } = $props()
a página recebe o resultado do load como propriedade. Sem export let, que é o modo antigo.
posts.map(({ slug, titulo, resumo }) => ...)
monta um objeto novo com só três campos. O que não é listado não viaja para o navegador.

5. A rota [slug] e o 404

Para cada receita ter endereço próprio, a pasta ganha colchetes: src/routes/post/[slug]/. O nome entre colchetes é o pedaço variável do caminho, e ele chega ao load dentro de params.

import { error } from '@sveltejs/kit';
import { posts } from '#lib/posts.js';

export function load({ params }) {
  const post = posts.find((p) => p.slug === params.slug);
  if (!post) error(404, 'Receita não encontrada');
  return { post };
}

O find devolve o primeiro item que casa, ou undefined. É esse undefined que precisa de tratamento: sem o error(404, ...), a próxima linha tentaria ler uma propriedade de nada e o servidor devolveria 500 — um erro de programação disfarçado de página. Com o error, a resposta é 404 e o SvelteKit desenha o +error.svelte que você escreveu.

<script>
  import { page } from '$app/state';
</script>

<h1>{page.status} — {page.error.message}</h1>
<a href="/">voltar para as receitas</a>

E o resultado, pedido por pedido, direto do servidor de desenvolvimento:

ana@notebook:~/loja$ curl -s http://localhost:5174/post/bolo-de-cenoura | grep -o "<h1>[^<]*</h1>"
<h1>Bolo de cenoura da padaria</h1>
ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5174/post/sem-receita
404
ana@notebook:~/loja$ curl -s http://localhost:5174/post/sem-receita | grep -o "<h1>[^<]*</h1>"
<h1>404 — Receita não encontrada</h1>

<script>

    { id: 1, data: '2026-02-10', titulo: 'Pão de queijo' },

    <li>{p.data} — {p.titulo}</li>
  {/each}
</ul>

Datas no formato ano-mês-dia têm uma propriedade útil: comparadas como texto, elas já ficam na ordem do calendário. É por isso que o localeCompare basta aqui — com 10/03/2026 a mesma comparação erraria, porque "10" vem antes de "9".

6. Versão 3 — o filtro na URL e o endpoint JSON

A terceira versão deixa o visitante escolher uma categoria. O detalhe importante: a escolha vai para a URL, não para um estado do componente. Assim o endereço /?categoria=bolos pode ser compartilhado e mostra a mesma coisa para qualquer pessoa.

import { posts } from '#lib/posts.js';

export function load({ url }) {
  const categoria = url.searchParams.get('categoria') ?? 'todas';
  const lista = posts
    .filter((p) => categoria === 'todas' || p.categoria === categoria)
    .map(({ slug, titulo, resumo }) => ({ slug, titulo, resumo }));

  return {
    categoria,
    categorias: ['todas', 'pães', 'bolos'],
    posts: lista
  };
}

No componente, o filtro é um <form method="GET"> comum. Sem JavaScript, o botão recarrega a página com ?categoria=... no endereço, e o load roda de novo no servidor. Com JavaScript, o SvelteKit intercepta e atualiza sem recarregar. O mesmo formulário serve nos dois casos.

<script>
  let { data } = $props();
</script>

<h1>Receitas da padaria</h1>

<form method="GET">
  <select name="categoria" value={data.categoria}>
    {#each data.categorias as c}
      <option value={c}>{c}</option>
    {/each}
  </select>
  <button>Filtrar</button>
</form>

<p>{data.posts.length} receita(s) em {data.categoria}</p>

<ul>
  {#each data.posts as post (post.slug)}
    <li>
      <a href="/post/{post.slug}">{post.titulo}</a>
      <p>{post.resumo}</p>
    </li>
  {/each}
</ul>

O ?? 'todas' é o valor padrão: quando ninguém escolheu categoria, o parâmetro não existe na URL e get devolve null. O ?? troca null por 'todas'.

Ainda na versão 3, o blog ganha um endereço que devolve dados em vez de página: um +server.js. Ele serve para outro programa consumir as receitas — um aplicativo, uma planilha, uma futura busca.

import { json } from '@sveltejs/kit';
import { posts } from '#lib/posts.js';

export function GET() {
  return json(posts.map(({ slug, titulo, categoria }) => ({ slug, titulo, categoria })));
}

A anatomia da versão 3

load({ url })
recebe um objeto com informações do pedido. url traz o endereço completo, incluindo o que vem depois do ?.
url.searchParams.get('categoria')
lê um parâmetro da query string. Devolve null quando ele não está no endereço.
?? 'todas'
o valor padrão para quando o parâmetro não veio. Diferente de ||: só troca null e undefined.
form method="GET"
manda os campos pelo endereço. É o que faz o filtro funcionar sem uma linha de JavaScript.
export function GET()
no +server.js, a função que responde a um pedido GET. O nome do arquivo define o endereço.
json(...)
transforma o valor em resposta JSON, com o cabeçalho de tipo certo.

7. O HTML que o servidor devolve

Este é o começo da resposta do endereço /, copiado do curl. Vale ler linha por linha, porque é aqui que o SvelteKit se revela:

<!doctype html>
<html lang="pt-BR">
	<head>
		<meta charset="utf-8" />
		<meta name="viewport" content="width=device-width, initial-scale=1" />
		<meta name="text-scale" content="scale" />
		
		<style data-sveltekit>
  header.svelte-12qhfyh { padding: 8px 0; border-bottom: 1px solid #ddd; margin-bottom: 16px; }
  main.svelte-12qhfyh { max-width: 40rem; }
 .svelte-12qhfyh{}</style>
	</head>
	<body data-sveltekit-preload-data="hover">

Três detalhes. Primeiro: o CSS do layout já vem dentro do <head>, numa tag <style data-sveltekit> — não há arquivo externo para o navegador buscar antes de pintar a tela. Segundo: o selo svelte-12qhfyh aparece igual ao que você viu em componente, porque é o mesmo mecanismo de escopo. Terceiro: o <body> traz data-sveltekit-preload-data="hover", que faz o SvelteKit começar a buscar a próxima página quando o mouse passa por cima de um link.

Mais abaixo, dentro do <select>, aparecem marcadores de comentário:

<form method="GET"><select name="categoria"><!--[--><option value="todas" selected="">todas</option><option value="pães">pães</option><option value="bolos">bolos</option><!--]--></select> <button>Filtrar</button></form>

Os <!--[--> e <!--]--> marcam o começo e o fim de um bloco dinâmico. Eles não aparecem na tela; existem para o JavaScript, quando assume a página, saber exatamente onde estão os pedaços que podem mudar. É o preço de entregar HTML pronto e continuar interativo depois.

9. Quando dá errado

Erro 1 — a página lê data que ninguém entregou

Sem +page.server.js, o data chega vazio. O componente compila e quebra na hora de desenhar, porque data.posts não existe.

<script>
  let { data } = $props();
</script>

<h1>{data.posts.length} receitas</h1>
Erro ao renderizar: Cannot read properties of undefined (reading 'posts')

No servidor de desenvolvimento, o mesmo problema aparece como resposta 500:

ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5174/
500
ana@notebook:~/loja$ curl -s http://localhost:5174/ | grep -o "<h1>[^<]*</h1>"
<h1>500 — Internal Error</h1>

O 500 é o aviso de que o problema é seu, não do visitante: a página não deveria depender de um dado que pode não vir.

Erro 2 — load sem o tratamento de "não achei"

Este é o bug que o error(404) evita. Sem ele, o find devolve undefined e a linha seguinte estoura.

import { posts } from '#lib/posts.js';

export function load({ params }) {
  const post = posts.find((p) => p.slug === params.slug);
  return { post: post.titulo };
}

A resposta do servidor para um endereço que não existe:

ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:5174/post/sem-receita
500
ana@notebook:~/loja$ curl -s http://localhost:5174/post/sem-receita | grep -o "<h1>[^<]*</h1>"
<h1>500 — Internal Error</h1>

Um endereço que não existe deveria responder 404. O 500 diz "eu quebrei", e isso confunde quem procura: o visitante acha que o site caiu, o buscador entende que a página é um erro temporário.

Erro 3 — $lib não existe mais

Quem aprendeu SvelteKit em material antigo escreve $lib/posts.js. Nesta versão o atalho foi renomeado, e o erro só aparece quando a página é pedida — o servidor responde 500 e o terminal mostra a mensagem abaixo (as linhas de plugin e de caminho de arquivo ficam de fora aqui).

Internal server error: module_removed_lib
`$lib` has been removed. Use `#lib` instead: https://svelte.dev/docs/kit/$lib. To keep using `$lib`, add `alias: { '$lib': 'src/lib' }` to your SvelteKit config.
https://svelte.dev/e/kit/module_removed_lib

A mensagem já dá as duas saídas: trocar por #lib, que é o atalho novo, ou declarar o alias na configuração para manter o nome antigo. O package.json gerado pelo sv create já traz "imports": { "#lib": "./src/lib/index.js", "#lib/*": "./src/lib/*" } — é de lá que o atalho vem.

Resumo

  • No SvelteKit, cada pasta em src/routes é um pedaço do endereço, e o +page.svelte é o que aparece nele.
  • +page.server.js roda só no servidor e entrega dados pelo load.
  • A página recebe esses dados como data: let { data } = $props().
  • +layout.svelte envolve as páginas e desenha o conteúdo com {@render children()}.
  • Uma pasta com colchetes, [slug], aceita qualquer valor no caminho e o entrega em params.
  • error(404, …) responde 404 de verdade; sem ele, o erro de programação vira 500.
  • O filtro mora na URL (?categoria=bolos), o que faz o endereço ser compartilhável.
  • +server.js devolve dados crus, como JSON, no endereço da pasta.
  • O HTML do servidor traz o CSS do layout embutido e marcadores <!--[--> para a hidratação.
  • Nesta versão o atalho é #lib; escrever $lib gera o erro module_removed_lib.
