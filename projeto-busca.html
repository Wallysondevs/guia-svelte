Svelte · Projeto Busca com Debounce

A vitrine da Ana tem dezessete produtos, e a cliente pergunta "tem pão de queijo?" enquanto a fila anda. A Ana precisa de um campo onde ela digita três letras e a lista encurta na hora. O problema é que cada letra digitada é uma busca, e busca custa tempo — ainda mais quando os dados vêm de um servidor. Esta aula monta a busca em três versões até chegar no debounce: esperar a pessoa parar de digitar antes de procurar. Toda saída foi compilada e rodada de verdade.

Você vai aprender
  • A filtrar uma lista com filter e includes a partir do que foi digitado.
  • Por que comparar sem toLowerCase perde resultados.
  • O que é debounce (esperar a digitação parar) e por que ele economiza trabalho.
  • Como atrasar uma ação com setTimeout e clearTimeout.
  • Como usar $effect para reagir ao texto e devolver a função de limpeza.
  • Os quatro estados de uma busca: carregando, com resultados, sem resultados e com erro.
  • Como testar um atraso no navegador sem esperar com cronômetro na mão.
  • O terminal do projeto: dev, build e preview.
  • Dois erros reais: bind num <div> e bind numa constante.

1. A ideia: procurar é comparar pedaços de texto

Buscar numa lista é uma das operações mais antigas da computação e uma das mais simples: para cada item, verifique se ele contém o que foi digitado. Se contém, mostre; se não, esconda. O Svelte não tem nada de especial aqui — a busca é JavaScript comum, e o que ele acrescenta é manter a lista na tela em sincronia com o resultado.

A parte que engana é o "cada letra". Quando a Ana digita pão, o campo dispara três eventos de input: p, pã, pão. Numa lista de dezessete itens isso não custa nada. Numa lista que vem de um servidor, são três pedidos; numa lista de dez mil itens, são três varreduras inteiras. O debounce existe para transformar três buscas em uma: ele espera um tempinho depois da última tecla e só então procura.

O nome vem da eletrônica: um botão mecânico, ao ser apertado, faz o contato pular várias vezes em poucos milissegundos. O circuito "debounce" ignora os pulos e entrega um único sinal limpo. Aqui é a mesma coisa com o teclado — os pulos são as letras, e o sinal limpo é a palavra inteira.

2. Versão 1: o filtro imediato

A primeira versão é a busca mais direta possível: um campo ligado por bind:value e um $derived que filtra o catálogo a cada mudança do termo. Sem atraso, sem estado de carregando — cada letra atualiza a lista.

<script>
  const catalogo = ['Pão francês', 'Pão de queijo', 'Sonho', 'Bolo de fubá'];
  let termo = $state('');

  let achados = $derived(catalogo.filter((nome) => nome.includes(termo)));
</script>

<h1>Busca na vitrine</h1>

<input bind:value={termo} placeholder="o que você procura?" />

<p>{achados.length} resultado(s)</p>

<ul>
  {#each achados as nome}
    <li>{nome}</li>
  {/each}
</ul>

Com o termo vazio, includes('') é sempre verdadeiro — todo texto contém o texto vazio. Por isso a lista aparece inteira na primeira renderização:

<h1>Busca na vitrine</h1> <input value="" placeholder="o que você procura?"/> <p>4 resultado(s)</p> <ul><li>Pão francês</li><li>Pão de queijo</li><li>Sonho</li><li>Bolo de fubá</li></ul>

A anatomia da versão 1

const catalogo = [...]
a lista fixa de produtos. É const porque não muda; quem muda é o termo.
let termo = $state('')
o que a pessoa digitou. Começa vazio, e o bind:value mantém o campo e a variável iguais.
nome.includes(termo)
devolve verdadeiro quando o termo aparece em qualquer posição do nome, com maiúsculas e acentos exatamente como foram escritos.
catalogo.filter(…)
devolve uma lista nova só com os aprovados. O catálogo original fica intacto — filtrar não apaga nada.
{#each achados as nome}
desenha um <li> por resultado. Quando a lista filtrada fica vazia, o {#each} não desenha nada.

Missão: a Ana digita PÃO em maiúsculas e a busca não acha nada. Faça a comparação ignorar maiúsculas e minúsculas.

<script>
  let itens = $state(['Pão francês', 'Pão de queijo', 'Sonho']);
  let termo = $state('');
  let achados = $derived(itens.filter((t) => t.includes(termo)));
</script>

<input bind:value={termo} placeholder="buscar" />
<p>{achados.length} resultado(s)</p>
<script>
  let itens = $state(['Pão francês', 'Pão de queijo', 'Sonho']);
  let termo = $state('');
  let achados = $derived(itens.filter((t) => t.toLowerCase().includes(termo.toLowerCase())));
</script>

<input bind:value={termo} placeholder="buscar" />
<p>{achados.length} resultado(s)</p>

Note que a solução chama toLowerCase() nos dois lados. Baixar só o termo não resolve: 'Pão'.includes('pão') continua falso, porque o P maiúsculo do nome não casa com o p minúsculo do termo. Baixar os dois lados é o que faz a comparação funcionar em qualquer combinação.

3. Versão 2: esperar 300 milissegundos

A versão 2 põe o atraso. A ideia é ter duas variáveis de texto: termo, que acompanha o campo letra por letra, e aplicado, que só muda quando a pessoa para de digitar. A lista filtra por aplicado, não por termo.

<script>
  const catalogo = ['Pão francês', 'Pão de queijo', 'Sonho', 'Bolo de fubá'];
  let termo = $state('');
  let aplicado = $state('');
  let carregando = $state(false);

  let achados = $derived(
    catalogo.filter((nome) => nome.toLowerCase().includes(aplicado.toLowerCase()))
  );

  function digitar(evento) {
    termo = evento.target.value;
    carregando = true;
    setTimeout(() => {
      aplicado = termo;
      carregando = false;
    }, 300);
  }
</script>

<h1>Busca na vitrine</h1>

<input value={termo} oninput={digitar} placeholder="o que você procura?" />

<p>{carregando ? 'Buscando…' : achados.length + ' resultado(s)'}</p>

<ul>
  {#each achados as nome}
    <li>{nome}</li>
  {/each}
</ul>

A saída inicial é igual à da versão 1, porque aplicado também começa vazio e a lista mostra tudo:

<h1>Busca na vitrine</h1> <input value="" placeholder="o que você procura?"/> <p>4 resultado(s)</p> <ul><li>Pão francês</li><li>Pão de queijo</li><li>Sonho</li><li>Bolo de fubá</li></ul>

A diferença aparece ao digitar rápido. Cada tecla cria um setTimeout novo, e todos os atrasados vão disparar — o primeiro com p, o segundo com pã, o terceiro com pão. O resultado final é o certo por acaso: o último a disparar é o último a ser criado. Mas os três disparos acontecem, e num caso real de rede isso significa três pedidos.

A anatomia da versão 2

termo e aplicado
dois textos com papéis diferentes: um é o que está na tela, o outro é o que a busca usa. Separar os dois é a essência do debounce.
oninput={digitar}
entrega a função, não o resultado dela. O navegador chama digitar(evento) a cada tecla.
evento.target.value
o texto atual do campo. Como aqui não há bind, esse é o jeito de saber o que foi digitado.
setTimeout(fn, 300)
agenda a função para daqui a trezentos milissegundos e devolve um número de identificação, que a versão 3 vai usar para cancelar.
{carregando ? … : …}
mostra "Buscando…" enquanto o atraso corre. É o primeiro dos quatro estados da busca.

Missão: a busca só acontece quando alguém aperta o botão. Faça ela acontecer sozinha, 300 ms depois da última tecla, e sumir com o botão.

<script>
  let termo = $state('');
  let aplicado = $state('nada');
</script>

<input bind:value={termo} placeholder="buscar" />
<button onclick={() => (aplicado = termo)}>buscar</button>
<p>Resultados: {aplicado}</p>
<script>
  let termo = $state('');
  let aplicado = $state('nada');

  $effect(() => {
    const id = setTimeout(() => {
      aplicado = termo;
    }, 300);
    return () => clearTimeout(id);
  });
</script>

<input bind:value={termo} placeholder="buscar" />
<p>Resultados: {aplicado}</p>

O $effect roda uma vez e depois de novo a cada mudança em termo. Antes de rodar de novo, o Svelte chama a função devolvida no return — a famosa limpeza. Com clearTimeout(id) ali, o atraso da tecla anterior é cancelado, e só o último sobrevive. É o mesmo mecanismo que cancela um ouvinte de evento ou fecha uma conexão; a diferença é o que você cancela.

4. Versão 3: quatro estados e o atraso que cancela

A versão pronta junta o debounce com a limpeza e organiza a tela em quatro estados. Uma busca de verdade tem mais do que "achou" e "não achou": tem o tempo de espera, tem o resultado vazio e tem a falha. Quem não desenha os quatro acaba mostrando uma tela em branco sem explicação.

<script>
  const catalogo = ['Pão francês', 'Pão de queijo', 'Sonho', 'Bolo de fubá', 'Coxinha'];

  let termo = $state('');
  let aplicado = $state('');
  let carregando = $state(false);
  let erro = $state('');

  let achados = $derived(
    catalogo.filter((nome) => nome.toLowerCase().includes(aplicado.toLowerCase()))
  );

  $effect(() => {
    const alvo = termo.trim();

    if (alvo === aplicado) return;

    carregando = true;
    erro = '';

    const id = setTimeout(() => {
      if (alvo === 'erro') {
        erro = 'A busca falhou. Tente outro nome.';
      } else {
        aplicado = alvo;
      }
      carregando = false;
    }, 300);

    return () => clearTimeout(id);
  });

  function limpar() {
    termo = '';
    aplicado = '';
    erro = '';
  }
</script>

<h1>Busca na vitrine</h1>

<label>
  Buscar
  <input bind:value={termo} placeholder="o que você procura?" />
</label>
{#if termo !== ''}
  <button onclick={limpar}>limpar</button>
{/if}

{#if carregando}
  <p class="aviso">Buscando…</p>
{:else if erro}
  <p class="erro">{erro}</p>
{:else if achados.length === 0}
  <p class="aviso">Nada encontrado para {aplicado}.</p>
{:else}
  <p>{achados.length} resultado(s){aplicado === '' ? ' na vitrine' : ' para ' + aplicado}</p>
  <ul>
    {#each achados as nome (nome)}
      <li>{nome}</li>
    {/each}
  </ul>
{/if}

<style>
  .aviso {
    color: #666;
  }
  .erro {
    color: #b00020;
  }
</style>

Na primeira renderização, o $effect nem chega a agendar nada: alvo é '' e aplicado também, então o return antecipado sai. A frase mostra os cinco itens e diz "na vitrine" em vez de "para", porque não há termo aplicado:

<h1>Busca na vitrine</h1> <label>Buscar <input value="" placeholder="o que você procura?"/></label>  <p>5 resultado(s) na vitrine</p> <ul><li>Pão francês</li><li>Pão de queijo</li><li>Sonho</li><li>Bolo de fubá</li><li>Coxinha</li></ul>

O CSS gerado são duas regras, e o selo aparece só nos parágrafos que podem receber as classes:

.aviso.svelte-1n46o8q {
    color: #666;
  }
  .erro.svelte-1n46o8q {
    color: #b00020;
  }

Repare que a solução usa {termo} na mensagem, não {aplicado}: neste componente não existe aplicado, e o termo digitado é a informação que a pessoa precisa ver para corrigir o que escreveu. Na versão 3, com debounce, a mensagem usa aplicado — mostrar o termo enquanto a busca ainda está correndo diria "nada encontrado" para algo que nem foi procurado.

5. Quanto o debounce economiza

O ganho depende de quanto tempo a pessoa leva entre as teclas. A tabela usa uma busca de 300 ms e uma digitação rápida de 150 ms por letra, que é mais ou menos o ritmo de quem escreve no celular.

Termo digitadoSem debounceCom debounce de 300 ms
pão3 buscas1 busca
sonho5 buscas1 busca
pão de queijo13 buscas1 busca
digitação lenta (1 s por letra)3 buscas3 buscas — o atraso vence entre as teclas

A última linha é a parte honesta: debounce não elimina buscas, ele elimina buscas intermediárias. Quem digita devagar recebe uma busca por letra de qualquer jeito, e está certo — o atraso é menor que a pausa. O valor do atraso é uma escolha de projeto: 150 ms parece instantâneo e economiza pouco; 500 ms economiza muito e começa a parecer lento. Trezentos milissegundos é o meio-termo mais comum.

Existe um custo escondido no debounce: durante o atraso, a tela mostra resultado velho. Se a pessoa digita sonho e o resultado de pão continua ali por trezentos milissegundos, ela pode clicar no lugar errado. A defesa é o estado "Buscando…", que a versão 3 desenha antes de qualquer lista.

6. Busca que ignora acento

A cliente digita pao, sem til, e a vitrine tem Pão francês. Com includes puro, a busca não acha — e o problema não é maiúscula, é acento. Baixar para minúsculas não resolve, porque ã e a são letras diferentes para o computador.

A solução é separar a letra do acento antes de comparar. O método normalize('NFD') faz exatamente isso: transforma ã em a mais um acento separado, e esse acento é um caractere na faixa que vai de U+0300 a U+036F. Uma expressão regular remove essa faixa, e o texto fica sem acento: texto.normalize('NFD').replace(/[\u0300-\u036f]/g, '').

O custo é que a normalização precisa rodar dos dois lados, e rodar a cada tecla. Em listas pequenas, tanto faz. Em listas grandes, vale normalizar o catálogo uma vez, quando ele carrega, e guardar o nome já sem acento ao lado do nome bonito — assim a busca compara textos prontos e a tela mostra o nome com acento. É o mesmo raciocínio do preço: calcule com um valor, mostre outro.

Vale lembrar também que includes diferencia maiúsculas de minúsculas em qualquer idioma, e que ordenar alfabeticamente em português exige localeCompare com o locale pt-BR. São detalhes que passam despercebidos até a primeira cliente chamada Ângela procurar o próprio nome.

Debounce não substitui cancelar o pedido

O atraso evita pedidos intermediários, mas não cancela o pedido que já saiu. Se a pessoa digitar pão, esperar meio segundo e digitar sonho, o pedido de pão pode chegar depois do de sonho — e a resposta velha sobrescrever a nova. A solução é guardar o pedido atual e descartar a resposta que não corresponde mais ao termo, ou usar AbortController para abortar de verdade. É o próximo degrau depois desta aula.

8. Quando dá errado

Os dois erros abaixo são de compilação e nascem da mesma confusão: bind não é um atributo qualquer. Ele só funciona em elemento de formulário e só aponta para algo que pode mudar. As mensagens são cópias das execuções.

Erro 1 — bind:value numa constante

O termo foi declarado com const. O compilador aceita bind em estado ou propriedade, porque a ligação precisa escrever no alvo; constante não aceita escrita.

<script>
  const catalogo = ['Pão francês', 'Sonho'];
  const termo = '';
</script>

<input bind:value={termo} placeholder="buscar" />
<p>{catalogo.length} resultado(s)</p>
Erro de compilação (linha 6, coluna 7): Cannot bind to constant

"Cannot bind to constant" é curto e direto: não dá para ligar a uma constante. Troque por let termo = $state(''). Repare que o catalogo pode continuar constante — ele é lido, nunca escrito pelo campo.

Erro 2 — bind:value num <div>

O bind parece um atributo comum e não é: ele precisa de um elemento que saiba receber valor. <div> não sabe.

<script>
  let termo = $state('');
</script>

<div bind:value={termo}>digite aqui</div>
Erro de compilação (linha 5, coluna 5): `bind:value` can only be used with `<input>`, `<textarea>`, `<select>`

A mensagem lista os três elementos que aceitam bind:value. Para uma div editável existe bind:innerHTML e bind:textContent, mas o caminho normal de um campo de busca é <input bind:value={termo} />.

Resumo

  • Buscar é filtrar: lista.filter((item) => item.includes(termo)).
  • includes('') é sempre verdadeiro, e é por isso que a lista aparece inteira com o campo vazio.
  • Comparar sem toLowerCase() nos dois lados perde resultados.
  • Debounce é esperar a digitação parar: termo acompanha o campo, aplicado só muda depois do atraso.
  • setTimeout agenda e devolve um id; clearTimeout(id) cancela o agendamento anterior.
  • O return do $effect é a limpeza: roda antes da próxima execução e quando o componente sai da tela.
  • Uma busca tem quatro estados: carregando, com resultado, sem resultado e com erro; a ordem dos {#if} importa.
  • Debounce reduz buscas intermediárias, não cancela pedido já enviado — para isso existe AbortController.
  • Erros desta aula: Cannot bind to constant e `bind:value` can only be used with `<input>`, `<textarea>`, `<select>`.
  • Terminal: dev em 5173, build com JS e CSS com hash, preview em 4173.
