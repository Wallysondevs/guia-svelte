Projetos · O Projeto Final

Chegou a hora de juntar as peças. A Ana já sabe fazer componente, guardar estado, listar e filtrar, validar formulário e pedir dados ao servidor. O que falta é um app inteiro: uma página inicial, uma área de pedidos, um login e um endereço que devolve dados para outros programas. Nesta aula o app nasce em três versões — a primeira cabe num arquivo só, a última tem seis — e cada versão é conferida com o código HTTP que o servidor devolveu. O build final também é real, com os números que saíram do terminal.

Você vai aprender
  • A diferença entre uma tela que funciona e um app que lembra.
  • Por que o estado do componente desaparece quando o servidor responde.
  • Como transformar um formulário em action com validação no servidor.
  • Como um load entrega a lista e um fail devolve a mensagem.
  • Onde os dados moram enquanto não existe banco de dados.
  • Como proteger rotas e API com um único hooks.server.js.
  • O que um +server.js devolve e para quem serve.
  • A árvore de arquivos de um app pronto e o endereço de cada um.
  • O que o build de produção mostra no fim do projeto.
  • As três falhas que este app provoca de verdade.

1. O mapa antes da obra

Um app é um conjunto de endereços com uma regra de acesso. A padaria precisa de cinco: a vitrine, o login, os pedidos, a API dos pedidos e a página de erro. Cada um é uma pasta em src/routes, e o que aparece nela depende de dois arquivos — o que desenha (+page.svelte) e o que busca os dados (+page.server.js).

EndereçoQuem entraO que mostra
/qualquer pessoaa vitrine e o link para os pedidos
/loginqualquer pessoao formulário de entrada
/pedidossó com sessãoa lista do dia e o formulário de novo pedido
/api/pedidossó com sessãoos mesmos dados em JSON
/qualquer-coisaqualquer pessoaa página de erro 404

A regra de acesso é o que separa um projeto de exercício de um projeto de verdade. Sem ela, a lista de pedidos de todos os clientes fica aberta para quem digitar o endereço. É por isso que as versões desta aula terminam numa aplicação com sessão, e não numa tela bonita.

2. Versão 1 — tudo num arquivo

A primeira versão é a que você já sabe escrever: um componente com uma lista, um formulário e três estados. Ela roda, mostra os pedidos e aceita um novo — enquanto a página está aberta.

<script>
  let pedidos = $state([
    { id: 1, cliente: 'Dona Bia', item: 'Bolo de chocolate', retirada: '8:30' },
    { id: 2, cliente: 'Firma São José', item: '30 pães franceses', retirada: '10:00' }
  ]);
  let cliente = $state('');
  let item = $state('');
</script>

<h1>Pedidos de hoje</h1>

<form onsubmit={(e) => {
  e.preventDefault();
  pedidos = [...pedidos, { id: Date.now(), cliente, item, retirada: '12:00' }];
  cliente = '';
  item = '';
}}>
  <input bind:value={cliente} placeholder="Cliente">
  <input bind:value={item} placeholder="Pedido">
  <button>Adicionar</button>
</form>

<p>{pedidos.length} pedido(s)</p>

<ul>
  {#each pedidos as pedido (pedido.id)}
    <li>{pedido.retirada} — {pedido.cliente}: {pedido.item}</li>
  {/each}
</ul>

O compilador entrega a lista com dois pedidos e o contador:

<h1>Pedidos de hoje</h1> <form><input value="" placeholder="Cliente"/> <input value="" placeholder="Pedido"/> <button>Adicionar</button></form> <p>2 pedido(s)</p> <ul><li>8:30 — Dona Bia: Bolo de chocolate</li><li>10:00 — Firma São José: 30 pães franceses</li></ul>

A anatomia da versão 1

let pedidos = $state([...])
a lista vive na memória da página. Some ao recarregar, e cada visitante tem a sua.
onsubmit com preventDefault()
impede o envio ao servidor. O pedido novo nunca sai do navegador.
pedidos = [...pedidos, novo]
cria uma lista nova com o item no fim. É o que avisa a tela para redesenhar.
{pedidos.length} pedido(s)
o contador lido da lista, sempre coerente com o que aparece.
{#each pedidos as pedido (pedido.id)}
uma linha por pedido, com chave estável para o Svelte saber o que mudou.

3. O que o servidor não sabe

Abra a versão 1, adicione um pedido, aperte F5. A lista volta a ter dois. Isso não é um defeito do Svelte: é a natureza da web. O servidor não guarda nada do que aconteceu na tela, e cada pedido HTTP começa do zero.

Dá para provar com o curl, que não tem JavaScript nem memória de página. Ele pede a mesma página duas vezes e recebe sempre os dois pedidos iniciais:

ana@notebook:~/loja$ curl -s -H 'Accept: text/html' http://localhost:5173/ | grep -o "<p>[0-9]* pedido[^<]*</p>"
<p>2 pedido(s)</p>
ana@notebook:~/loja$ curl -s -H 'Accept: text/html' http://localhost:5173/ | grep -o "<li>[^<]*</li>"
<li>8:30 — Dona Bia: Bolo de chocolate</li>
<li>10:00 — Firma São José: 30 pães franceses</li>

A conclusão é a que muda o projeto de patamar: se o pedido precisa sobreviver, ele tem de ser enviado ao servidor. E se ele vai para o servidor, alguém precisa decidir o que fazer com ele lá — validar, guardar, responder.

4. Versão 2 — o pedido vira dado do servidor

A segunda versão move a lista para um módulo e coloca a validação numa action. O formulário passa a ter method="POST", e o SvelteKit procura a action no +page.server.js ao lado.

import { fail } from '@sveltejs/kit';
import { pedidos, adicionar } from '#lib/pedidos.js';

export function load() {
  return { pedidos };
}

export const actions = {
  default: async ({ request }) => {
    const dados = await request.formData();
    const cliente = dados.get('cliente')?.trim() ?? '';
    const item = dados.get('item')?.trim() ?? '';

    if (cliente === '' || item === '') {
      return fail(400, { cliente, item, erro: 'Cliente e pedido são obrigatórios' });
    }

    adicionar({ cliente, item, retirada: '12:00' });
    return { ok: true };
  }
};
<script>
  let { data, form } = $props();
</script>

<h1>Pedidos de hoje</h1>

<form method="POST">
  <input name="cliente" placeholder="Cliente" value={form?.cliente ?? ''}>
  <input name="item" placeholder="Pedido" value={form?.item ?? ''}>
  <button>Adicionar</button>
</form>

{#if form?.erro}
  <p class="erro">{form.erro}</p>
{/if}

<p>{data.pedidos.length} pedido(s)</p>

<ul>
  {#each data.pedidos as pedido (pedido.id)}
    <li>{pedido.retirada} — {pedido.cliente}: {pedido.item}</li>
  {/each}
</ul>

<style>
  .erro { color: #b3261e; font-weight: 600; }
</style>

Três coisas passaram a acontecer no servidor. O load entrega a lista a cada pedido. A action confere os campos e, quando falta algo, responde 400 com a mensagem. E o pedido novo entra no módulo compartilhado, então aparece para qualquer pessoa que pedir a página depois.

ana@notebook:~/loja$ curl -s -H 'Accept: text/html' -X POST -d 'cliente=&item=' http://localhost:5173/ | grep -o '<p class="erro[^>]*>[^<]*</p>'
<p class="erro svelte-1uha8ag">Cliente e pedido são obrigatórios</p>
ana@notebook:~/loja$ curl -s -H 'Accept: text/html' -X POST -d 'cliente=Seu João&item=12 pães de queijo' -o /dev/null -w "%{http_code}\n" http://localhost:5173/
200
ana@notebook:~/loja$ curl -s -H 'Accept: text/html' http://localhost:5173/ | grep -o "<li>[^<]*</li>"
<li>8:30 — Dona Bia: Bolo de chocolate</li>
<li>10:00 — Firma São José: 30 pães franceses</li>
<li>12:00 — Seu João: 12 pães de queijo</li>

A anatomia da versão 2

export function load()
roda no servidor a cada pedido e devolve o que a página precisa. O resultado chega em data.
export const actions
recebe o POST do formulário. Sem actions, o POST responde 405.
request.formData()
lê os campos pelo name. Campo sem name não chega.
fail(400, { … })
resposta de erro com dados: a página redesenha com form.erro preenchido.
#lib/pedidos.js
o módulo onde a lista mora. Importar de lá é o que faz a action e o load verem os mesmos dados.
{data.pedidos.length}
o contador agora vem do servidor, e não de um estado do navegador.

5. Onde os dados moram de verdade

O módulo #lib/pedidos.js guarda a lista numa variável. Isso funciona enquanto o servidor está de pé: reiniciou, voltou aos dois pedidos de exemplo. E se o site roda em duas máquinas ao mesmo tempo, cada uma tem a sua lista. Não é um banco de dados — é um ensaio dele.

Onde guardarSobrevive aCusto
Estado do componentenada — some ao recarregarzero
Módulo no servidora navegação; some ao reiniciarzero, mas engana
Arquivo JSON no servidora reinicializaçãosimples, sem consultas
Banco de dadostudo, inclusive várias máquinasinstalar, modelar, migrar

Para o tamanho deste projeto, o módulo é honesto: o objetivo da aula é o caminho do dado, não a persistência. Quando você trocar por um banco, o load e a action continuam iguais — só o conteúdo de #lib/pedidos.js muda. Esse é o sinal de que a separação foi bem feita.

Missão: a caixinha "só os prontos" não filtra nada e o contador mostra sempre 2. Faça a lista e o número mostrarem 1 quando a caixinha for marcada.

  {#each pedidos as p (p.id)}

  {/each}

    { id: 1, item: 'Bolo', pronto: true },
    { id: 2, item: 'Pães', pronto: false }
  ];
  let soProntos = $state(false);

O mesmo $derived que resolve o filtro resolve o contador: os dois leem visiveis. Quando a regra de negócio muda ("só os prontos"), ela muda num lugar só e a tela inteira acompanha.

6. Versão 3 — o porteiro e a API

A versão final cresce: os pedidos ganham endereço próprio (/pedidos), a vitrine fica em /, entra o /login e nasce o /api/pedidos. Com mais rotas, proteger cada uma por conta própria vira erro garantido. O hooks.server.js centraliza a decisão.

import { redirect } from '@sveltejs/kit';

const PROTEGIDAS = ['/pedidos', '/api/pedidos'];

export async function handle({ event, resolve }) {
  event.locals.usuario = event.cookies.get('sessao') ?? null;

  const precisaEntrar =
    !event.locals.usuario && PROTEGIDAS.some((p) => event.url.pathname.startsWith(p));

  if (precisaEntrar) redirect(303, '/login');

  return resolve(event);
}

O hook roda em todo pedido, inclusive nos da API. É por isso que o curl sem cookie recebe 303 até quando pede JSON:

ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" -H 'Accept: text/html' http://localhost:5173/pedidos
303 http://localhost:5173/login
ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" -H 'Accept: text/html' http://localhost:5173/api/pedidos
303 http://localhost:5173/login
ana@notebook:~/loja$ curl -s -H 'Cookie: sessao=ana@padaria.com' http://localhost:5173/pedidos | grep -o "<p[^>]*>[0-9]* pedido[^<]*</p>"
<p class="svelte-1ld628l">2 pedido(s)</p>

Com a sessão, a página responde 200 e a API devolve o mesmo conteúdo em JSON — é o endereço que um aplicativo de celular usaria:

ana@notebook:~/loja$ curl -s -H 'Cookie: sessao=ana@padaria.com' http://localhost:5173/api/pedidos
{"usuario":"ana@padaria.com","pedidos":[{"id":1,"cliente":"Dona Bia","item":"Bolo de chocolate","retirada":"8:30"},{"id":2,"cliente":"Firma São José","item":"30 pães franceses","retirada":"10:00"}]}

E o pedido novo, enviado pelo formulário com a sessão, muda o que os dois endereços mostram:

ana@notebook:~/loja$ curl -s -H 'Accept: text/html' -H 'Cookie: sessao=ana@padaria.com' -X POST -d 'cliente=Seu João&item=12 pães de queijo' -o /dev/null -w "%{http_code}\n" http://localhost:5173/pedidos
200
ana@notebook:~/loja$ curl -s -H 'Accept: text/html' -H 'Cookie: sessao=ana@padaria.com' http://localhost:5173/pedidos | grep -o "<p[^>]*>[0-9]* pedido[^<]*</p>"
<p class="svelte-1ld628l">3 pedido(s)</p>

O +server.js da API é curto porque não desenha nada: recebe o pedido, lê locals e devolve JSON. O hook já garantiu que existe sessão antes de chegar aqui.

import { json } from '@sveltejs/kit';
import { pedidos } from '#lib/pedidos.js';

export function GET({ locals }) {
  return json({
    usuario: locals.usuario,
    pedidos: pedidos.map(({ id, cliente, item, retirada }) => ({ id, cliente, item, retirada }))
  });
}

A anatomia da versão 3

handle({ event, resolve })
roda antes de qualquer rota. O que ele decide vale para o site inteiro, API incluída.
event.url.pathname.startsWith(p)
compara o começo do caminho. /pedidos/hoje também cai na proteção.
event.locals.usuario
o resultado da checagem, disponível para a rota daquele pedido.
resolve(event)
continua o atendimento. Sem essa chamada, nenhuma página é desenhada.
export function GET({ locals })
responde ao verbo GET no endereço da pasta. Um POST aqui precisaria da sua própria função.
json({ … })
transforma o objeto em resposta JSON, com o tipo de conteúdo certo.

9. Quando dá errado

Erro 1 — campo sem name

A action lê o formulário pelos nomes. Sem name, o valor chega vazio e a validação reprova tudo — o formulário parece quebrado.

<script>
  let { data, form } = $props();
</script>

<form method="POST">
  <input placeholder="Cliente">
  <input placeholder="Pedido">
  <button>Adicionar</button>
</form>

{#if form?.erro}
  <p>{form.erro}</p>
{/if}

<p>{data.pedidos.length} pedido(s)</p>

Depois do POST, a resposta é 400 e a mensagem aparece:

ana@notebook:~/loja$ curl -s -H 'Accept: text/html' -X POST -d 'cliente=Seu João&item=12 pães' http://localhost:5173/ | grep -o '<p class="erro[^>]*>[^<]*</p>'
<p class="erro svelte-1uha8ag">Cliente e pedido são obrigatórios</p>

A mensagem está certa; o problema é o HTML. O curl manda os campos pelos nomes, mas a página sem name não os envia quando um navegador faz o POST.

Erro 2 — a página lê data que ninguém entregou

Se o +page.server.js for apagado ou renomeado, o data chega vazio e o componente quebra ao desenhar.

<script>
  let { data, form } = $props();
</script>

<h1>Pedidos de hoje</h1>

<p>{data.pedidos.length} pedido(s)</p>
Erro ao renderizar: Cannot read properties of undefined (reading 'pedidos')

O erro parece de JavaScript, mas a causa é de estrutura: o arquivo que deveria entregar os dados não está lá. Confira se o +page.server.js existe na mesma pasta do +page.svelte.

Erro 3 — POST sem corpo de formulário

Uma action exige conteúdo de formulário. Um POST vazio, sem content-type, é recusado antes de chegar ao seu código.

ana@notebook:~/loja$ curl -s -i -H 'Accept: text/html' -H 'Cookie: sessao=ana@padaria.com' -X POST "http://localhost:5173/pedidos" | head -3
HTTP/1.1 415 Unsupported Media Type
Vary: Origin
content-length: 1271

O 415 é "tipo de conteúdo não suportado". Com -d '', o curl passa a mandar um corpo de formulário vazio e a action roda — foi assim que o logout funcionou na aula de login.

Complete o código

export const actions = {
  default: async ({ request }) => {
    const dados = await request.();
    const cliente = dados.get('cliente') ?? '';
    if (cliente === '') return fail(400, { erro: 'Cliente obrigatório' });
  }
};

Resumo

  • Um app é um conjunto de endereços com uma regra de acesso — não uma tela com estado.
  • Estado de componente não sobrevive ao recarregamento: o servidor não sabe dele.
  • Para o dado durar, ele precisa ser enviado ao servidor por uma action.
  • load entrega data; fail entrega form com a mensagem de erro.
  • Campo sem name não chega ao formData.
  • Módulo no servidor guarda dados em memória: some ao reiniciar e não serve para várias máquinas.
  • hooks.server.js centraliza a sessão e protege rotas e API de uma vez.
  • locals leva o resultado do hook até a rota daquele pedido.
  • +server.js devolve JSON para outros programas, com a mesma sessão.
  • O build de produção compila dois ambientes e termina pedindo um adaptador.
