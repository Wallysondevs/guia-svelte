Projetos · Formulário em Etapas

A Ana vende bolo por encomenda e recebe os pedidos por mensagem. Metade das mensagens chega pela metade: "quero um bolo", sem nome, sem telefone, sem sabor. Ela quer uma ficha que pergunte na ordem certa e que não deixe ninguém confirmar um pedido incompleto. Nesta aula você constrói essa ficha do zero, em três versões: uma tela só, depois em etapas, e por fim com o resumo montado por snippet. As três versões rodam de verdade, e o que aparece aqui saiu do compilador do Svelte 5.

Você vai aprender
  • Como transformar uma ficha de papel em um componente com campos.
  • O que bind:value faz entre o campo e a variável de estado.
  • Por que onsubmit precisa de preventDefault().
  • A validar um campo vazio com trim() antes de deixar passar.
  • Como dividir um formulário em etapas com um único $state.
  • O padrão da função que segura o avanço: valida, avisa e só então muda.
  • Como {#snippet} e {@render} evitam repetir marcação.
  • Por que o selo svelte-xxxxx muda quando o arquivo muda de lugar.
  • As três mensagens de erro que este projeto provoca de verdade.
  • O que npm run dev, o HMR e npm run build imprimem.

1. A ficha de papel que chega pela metade

Toda padaria tem uma ficha de encomenda: um papel com linhas em branco para nome, telefone, sabor, tamanho e dia da retirada. A ficha funciona porque pergunta uma coisa de cada vez e porque quem preenche vê o que ainda falta. Quando a Ana troca a ficha pelo celular, perde as duas coisas.

Um formulário é a ficha do papel traduzida para a tela. Cada linha vira um campo, cada campo vira uma variável no <script>, e a ordem das perguntas vira a ordem dos elementos no HTML. A parte nova é a validação: o papel aceita qualquer coisa escrita, mas o componente pode recusar um pedido sem nome antes de registrar. Validar é escrever a regra da padaria em código.

Na padariaNo componente
A ficha de papel com linhas em brancoO <form> com os campos
O que o cliente escreveu na linha "nome"A variável nome, criada com $state
A regra "sem nome não aceito"A função enviar() que confere antes de seguir
O carimbo "faltou preencher"A mensagem guardada em erro
Separar a ficha em três folhas numeradasO estado etapa com {#if}

Combine o vocabulário: campo é a caixinha onde se digita; valor é o que está dentro dela; estado é a variável que guarda esse valor e avisa a tela quando ele muda.

2. Versão 1 — tudo numa tela

A primeira versão é a mais direta: dois campos, um botão e a frase que confirma o pedido. Repare que cada campo tem um bind:value apontando para uma variável diferente, e que a frase do fim lê as duas variáveis ao mesmo tempo.

<script>
  let nome = $state('');
  let sabor = $state('chocolate');
  let erro = $state('');

  function enviar() {
    if (nome.trim() === '') {
      erro = 'Informe o nome de quem encomenda';
      return;
    }
    erro = '';
  }
</script>

<form onsubmit={(e) => { e.preventDefault(); enviar(); }}>
  <label>Nome <input bind:value={nome}></label>
  <label>Sabor
    <select bind:value={sabor}>
      <option>chocolate</option>
      <option>morango</option>
    </select>
  </label>
  <button>Encomendar</button>
</form>

{#if erro}
  <p class="erro">{erro}</p>
{/if}

<p>Pedido de {nome || 'ninguém'} — bolo de {sabor}</p>

<style>
  .erro { color: #b3261e; font-weight: 600; }
</style>

O compilador devolve o HTML abaixo. Note três coisas: o <script> não existe mais no arquivo que o navegador recebe; o campo de nome saiu com value="", porque a variável começou vazia; e o sabor já vem com selected="", porque sabor começa valendo 'chocolate'.

<form><label>Nome <input value=""/></label> <label>Sabor <select><option selected="">chocolate</option><option>morango</option></select></label> <button>Encomendar</button></form>  <p>Pedido de ninguém — bolo de chocolate</p>

A anatomia da versão 1

let nome = $state('')
o estado do campo. Começa com texto vazio: a ficha nasce em branco, como o papel.
bind:value={nome}
liga o campo à variável nas duas direções: digitar muda nome, e mudar nome muda o que o campo mostra.
onsubmit={(e) => { … }}
roda quando o formulário é enviado — pelo botão ou pela tecla Enter.
e.preventDefault()
cancela o comportamento padrão do navegador, que é recarregar a página. Sem isso, a validação desaparece no primeiro envio.
{#if erro} … {/if}
só desenha a mensagem quando existe texto em erro. Texto vazio conta como falso.
{nome || 'ninguém'}
o operador || devolve o lado direito quando o esquerdo é vazio. É o "se não tiver nome, escreva ninguém".

O custo desta versão é o tamanho da tela. Com seis campos — nome, telefone, sabor, tamanho, dia, observação — o cliente do celular vê um bloco comprido e erra um campo no meio. É esse o problema que a versão 2 ataca.

3. O botão que aceita qualquer coisa

Na versão 1, o botão Encomendar chamava enviar(), e enviar() conferia o nome. Tire a conferência e o formulário aceita um pedido sem nome: a frase final vira "Pedido de ninguém". A regra da casa não está no HTML — está na função.

function enviar() {
  if (nome.trim() === '') {
    erro = 'Informe o nome de quem encomenda';
    return;
  }
  erro = '';
}

Leia de cima para baixo, em voz alta: "se o nome, sem espaços nas pontas, for igual a texto vazio, então guarde a mensagem de erro e saia da função". O return é a saída antecipada: nada depois dele roda naquela chamada. Sem o return, a função continuaria, apagaria o erro na linha seguinte e o aviso nunca apareceria.

O trim() existe por causa do espaço. Se o cliente digitar só a barra de espaço, o valor não é vazio — é um texto com um caractere. trim() remove os espaços das pontas antes da comparação, e é a diferença entre um formulário que funciona e um que aceita lixo.

Missão: o botão confirma mesmo sem nome. Faça o componente recusar o envio vazio e mostrar a frase "Informe seu nome antes de enviar".

4. Versão 2 — o formulário em etapas

Agora a ficha vira três folhas numeradas. A pergunta muda conforme o número da etapa, e os botões Voltar e Avançar mudam esse número. Existe um estado controlando qual pedaço aparece: passo.

<script>
  let passo = $state(1);
  let nome = $state('');
  let telefone = $state('');
  let sabor = $state('chocolate');
  let tamanho = $state('médio');
  let erro = $state('');

  function avancar() {
    erro = '';
    if (passo === 1 && nome.trim() === '') {
      erro = 'Informe o nome de quem encomenda';
      return;
    }
    if (passo === 2 && telefone.trim().length < 8) {
      erro = 'Telefone com pelo menos 8 dígitos';
      return;
    }
    if (passo < 3) passo += 1;
  }

  function voltar() {
    erro = '';
    if (passo > 1) passo -= 1;
  }
</script>

<div class="barra">
  {#each [1, 2, 3] as n}
    <span class:atual={n === passo}>etapa {n}</span>
  {/each}
</div>

{#if passo === 1}
  <h2>Quem encomenda</h2>
  <label>Nome <input bind:value={nome} placeholder="Ana"></label>
  <label>Telefone <input bind:value={telefone} placeholder="11999990000"></label>
{:else if passo === 2}
  <h2>O bolo</h2>
  <label>Sabor
    <select bind:value={sabor}>
      <option>chocolate</option>
      <option>morango</option>
      <option>cenoura</option>
    </select>
  </label>
  <label>Tamanho
    <select bind:value={tamanho}>
      <option>pequeno</option>
      <option>médio</option>
      <option>grande</option>
    </select>
  </label>
{:else}
  <h2>Confira</h2>
  <p>{nome} — {telefone}</p>
  <p>Bolo de {sabor}, tamanho {tamanho}</p>
{/if}

{#if erro}
  <p class="erro">{erro}</p>
{/if}

<div class="botoes">
  <button onclick={voltar} disabled={passo === 1}>Voltar</button>
  <button onclick={avancar}>{passo === 3 ? 'Confirmar' : 'Avançar'}</button>
</div>

Duas coisas mudaram em relação à versão 1. O bloco {#if} escolheu um galho e descartou os outros — não há vestígio da etapa 2 no HTML. E "Voltar" saiu com disabled="", porque passo === 1 é verdade.

A anatomia da versão 2

let passo = $state(1)
o número da folha atual. É o único estado que decide qual marcação aparece.
{#if passo === 1}
um galho por etapa. O {:else if} testa a próxima condição quando a anterior é falsa.
{:else}
o galho final: o resumo. Ele não testa nada, entra quando os outros dois falharam.
class:atual={n === passo}
põe a classe atual só no item que corresponde à etapa. É uma condicional curta dentro do atributo.
disabled={passo === 1}
desliga o botão na primeira etapa. Expressão booleana vira atributo presente ou ausente.
passo += 1
o mesmo que passo = passo + 1. Como passo é estado, a tela se redesenha.

5. A função que segura o avanço

Repare na ordem das linhas de avancar(). Primeiro ela limpa o erro antigo, depois confere a etapa atual, e só no fim muda o número. Essa ordem é o que faz o botão se comportar como uma porta: ou passa, ou mostra o motivo de não passar — nunca as duas coisas.

O teste if (passo === 1 && nome.trim() === '') tem duas condições ligadas por && ("e"). As duas precisam ser verdadeiras para o erro aparecer. Sem a primeira, o telefone seria exigido já na etapa do nome, e o cliente veria uma mensagem sobre um campo que não está na tela. Validar por etapa é validar o que está visível.

Existe uma armadilha comum aqui: confiar no disabled. Ele impede o clique, mas não a tecla Enter no último campo, nem um leitor de tela que dispare o envio. O disabled é conforto; a validação dentro da função é a regra.

Missão: o botão avança mesmo com o campo vazio. Faça ele não sair do passo 1 enquanto o nome estiver vazio — dois cliques e a tela tem de continuar mostrando "Passo 1 de 3".

<script>
  let passo = $state(1);
  let nome = $state('');
</script>

<input bind:value={nome} placeholder="Seu nome">
<p>Passo {passo} de 3</p>
<button onclick={() => (passo = Math.min(passo + 1, 3))}>Avançar</button>
<script>
  let passo = $state(1);
  let nome = $state('');

  function avancar() {
    if (nome.trim() === '' || passo === 3) return;
    passo += 1;
  }
</script>

<input bind:value={nome} placeholder="Seu nome">
<p>Passo {passo} de 3</p>
<button onclick={avancar}>Avançar</button>

A solução usa || ("ou") para juntar duas razões de parar: campo vazio ou já estar na última etapa. As duas levam ao mesmo return. Quando várias condições têm a mesma consequência, juntar com || deixa a função mais curta e mais fácil de ler do que dois if separados.

6. Versão 3 — snippets para não repetir marcação

A terceira versão resolve um incômodo da segunda: o resumo precisa de uma linha por campo, e escrever quatro <tr> na mão é convite a erro. O Svelte 5 guarda um pedaço de marcação com nome e o reaproveita: o snippet. Ele fica no HTML entre chaves e é chamado com {@render}.

<script>
  let etapa = $state(1);
  let nome = $state('');
  let telefone = $state('');
  let sabor = $state('chocolate');
  let tamanho = $state('médio');
  let erro = $state('');
  let enviado = $state(false);

  let resumo = $derived([
    ['Nome', nome],
    ['Telefone', telefone],
    ['Sabor', sabor],
    ['Tamanho', tamanho]
  ]);

  function avancar() {
    erro = '';
    if (etapa === 1 && nome.trim() === '') {
      erro = 'Informe o nome de quem encomenda';
      return;
    }
    if (etapa === 2 && telefone.replace(/\D/g, '').length < 8) {
      erro = 'Telefone com 8 dígitos ou mais';
      return;
    }
    if (etapa === 3) {
      enviado = true;
      return;
    }
    etapa += 1;
  }

  function voltar() {
    erro = '';
    if (etapa > 1) etapa -= 1;
  }

  function recomecar() {
    enviado = false;
    etapa = 1;
    erro = '';
  }
</script>

{#snippet linha(rotulo, valor)}
  <tr><th>{rotulo}</th><td>{valor}</td></tr>
{/snippet}

{#if enviado}
  <h2>Encomenda registrada</h2>
  <p>Obrigada, {nome}! O bolo de {sabor} fica pronto amanhã.</p>
  <button onclick={recomecar}>Nova encomenda</button>
{:else}
  <p class="progresso">Etapa {etapa} de 3</p>

  {#if etapa === 1}
    <label>Nome <input bind:value={nome}></label>
  {:else if etapa === 2}
    <label>Telefone <input bind:value={telefone}></label>
  {:else}
    <table>
      <tbody>
        {#each resumo as [rotulo, valor]}
          {@render linha(rotulo, valor || '—')}
        {/each}
      </tbody>
    </table>
  {/if}

  {#if erro}
    <p class="erro">{erro}</p>
  {/if}

  <button onclick={voltar} disabled={etapa === 1}>Voltar</button>
  <button onclick={avancar}>{etapa === 3 ? 'Confirmar' : 'Avançar'}</button>
{/if}

<style>
  .progresso { color: #555; font-size: .9rem; }
  .erro { color: #b3261e; font-weight: 600; }
  table { border-collapse: collapse; margin: 8px 0; }
  th, td { text-align: left; padding: 4px 10px; border-bottom: 1px solid #ddd; }
</style>

Com o componente recém-aberto, a tela mostra pouca coisa — e é essa a prova de que só a primeira etapa existe:

Etapa 1 de 3 Nome Voltar Avançar

Três detalhes dessa saída. O <p class="progresso"> virou texto comum, sem tags, porque o --texto mostra o que a pessoa lê. O <input> não aparece: campo vazio não tem texto. E "Voltar" aparece sem conteúdo próprio, mas existe — só está desabilitado.

A anatomia da versão 3

{#snippet linha(rotulo, valor)}
uma marcação com nome e dois parâmetros. Ela não desenha nada sozinha: fica guardada para ser chamada.
{@render linha(rotulo, valor)}
o momento em que o snippet é desenhado, com os valores daquela linha. É o substituto do antigo <slot>.
{#each resumo as [rotulo, valor]}
desmonta cada par da lista em duas variáveis. O resumo é uma lista de pares [nome do campo, valor].
let resumo = $derived([...])
um valor que se recalcula sozinho quando nome, telefone, sabor ou tamanho mudam.
{valor || '—'}
mostra um traço quando o campo ainda está vazio. Um resumo com buracos em branco parece defeito.
telefone.replace(/\D/g, '')
tira tudo que não é dígito antes de contar. Assim "(11) 99999-0000" conta 11 caracteres numéricos, não 15.

Missão: depois de confirmar, o botão "Editar" volta para o resumo, mas a etapa continua em 3. Faça "Editar" recomeçar da etapa 1.

É o tipo de defeito que passa em revisão rápida: o botão faz algo e a tela muda. O que falta é zerar os dois estados — "enviado" e a etapa — quando o ciclo recomeça.

7. O que o navegador mostra

A saída do compilador é o HTML do primeiro desenho. Depois, quem manda é o navegador: cada clique e cada tecla atualizam o estado e o Svelte redesenha só o pedaço que mudou. Abaixo, o que a versão 3 mostrou no servidor de desenvolvimento da Ana, com o texto lido da tela a cada passo.

AçãoTexto que apareceu na tela
abrir a páginaEtapa 1 de 3 Nome Voltar Avançar
clicar em Avançar sem digitarEtapa 1 de 3 Nome Informe o nome de quem encomenda Voltar Avançar
digitar "Ana" e clicar em AvançarEtapa 2 de 3 Telefone Voltar Avançar

A primeira linha é igual à saída do compilador na seção 6: o HTML do servidor é o mesmo que o navegador monta no primeiro instante. A diferença começa no segundo clique, quando quem desenha é o JavaScript do componente.

Vale notar o que não mudou entre as linhas: o rótulo "Nome" continua na tela durante o erro, e o botão "Avançar" também. O Svelte não joga a tela no lixo a cada mudança — atualiza o parágrafo de erro e, quando ele some, remove só aquele parágrafo. Por isso o cursor não pula do campo e o foco não se perde.

8. O selo do estilo e o nome do arquivo

A versão 3 não é a única com estilo. A versão 2 tinha uma barra de etapas, e o componente abaixo é o menor pedaço dela: um parágrafo com uma classe e duas regras de CSS. Pedindo o CSS ao compilador, sai isto:

<script>
  let etapa = $state(1);
</script>

<p class="contador">Etapa {etapa} de 3</p>

<style>
  .contador {
    color: #2e7d32;
    font-weight: 600;
  }
</style>
.contador.svelte-dvr9tu {
  color: #2e7d32;
  font-weight: 600;
}

O seletor escrito foi .contador; o seletor publicado é .contador.svelte-dvr9tu. O compilador acrescentou um selo para que a regra só valha dentro deste componente. E o mesmo selo vai para a tag no HTML:

Na tela, o parágrafo sai como <p class="contador svelte-dvr9tu">Etapa 1 de 3</p>: duas classes, a sua e a do compilador. É a segunda que fecha o escopo.

Aqui vem uma descoberta que economiza meia hora de susto. O selo não é calculado a partir do CSS: ele vem do nome do arquivo. O mesmo componente compilado como src/App.svelte recebe svelte-1n46o8q; compilado como src/Etapa.svelte, recebe svelte-dvr9tu. Mudar a cor de uma regra não troca o selo; mudar o caminho do arquivo, sim.

Nome passado ao compiladorSelo que sai no CSS
src/App.sveltesvelte-1n46o8q
src/Etapa.sveltesvelte-dvr9tu
src/lib/Campo.sveltesvelte-82495

Por que isso importa? Porque toda saída deste guia depende do caminho usado na compilação. Se você rodar o mesmo código em um arquivo com outro nome, o selo muda e o CSS parece "diferente" — mas o comportamento é idêntico. E dois componentes com a mesma classe contador nunca brigam pelo estilo.

O projeto fica em ~/loja com o src/App.svelte da versão 3. O primeiro comando liga o servidor de desenvolvimento:

ana@notebook:~/loja$ npm run dev

1815 é o tempo até o servidor aceitar conexões, em milissegundos. Local é o endereço para abrir no navegador; Network lembra que ninguém de fora da máquina alcança aquele endereço. Nada foi publicado.

Com a página aberta, salvar o arquivo aparece no terminal como uma linha de HMR (hot module replacement, troca de módulo a quente) — a prova de que o servidor viu a mudança e mandou só o pedaço novo:

5:07:32 PM [vite] (client) hmr update /src/App.svelte?svelte&type=style&lang.css

Repare no fim da linha: type=style&lang.css. A mudança era só de CSS, então o Vite trocou o estilo sem remontar o componente — o que estava digitado não se perdeu.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão, com a linha e a coluna que ele aponta. Todas foram provocadas pelo mesmo projeto deste capítulo.

Erro 1 — bind:value no lugar errado

O bind: só existe para elementos que guardam valor. Colocar em um parágrafo parece inofensivo, e o compilador recusa na hora.

<script>
  let nome = $state('');
</script>

<p bind:value={nome}>{nome}</p>
Erro de compilação (linha 5, coluna 3): `bind:value` can only be used with `<input>`, `<textarea>`, `<select>`

A mensagem lista os três elementos que aceitam ligação de valor. Se a intenção era mostrar o valor, o caminho é {nome}; se era editar, o caminho é um <input>.

Erro 2 — bloco aberto e não fechado

Aqui o {#if} ficou sem o {/if} no fim. O compilador avisa no ponto onde desistiu de esperar, que é o fim do arquivo.

<script>
  let etapa = $state(1);
</script>

{#if etapa === 1}
  <p>Etapa 1</p>
{:else}
  <p>Etapa {etapa}</p>
Erro de compilação (linha 5, coluna 0): Block was left open

"Block was left open" quer dizer "o bloco ficou aberto". A linha apontada é o começo do bloco, não o fim do arquivo — é ali que falta o fechamento.

Erro 3 — $state sem let

Sem a palavra let, o compilador não tem onde guardar o estado. É o erro mais comum de quem está começando, e a mensagem é comprida porque a runa vale em três lugares diferentes.

<script>
  etapa = $state(1);
</script>

<p>{etapa}</p>
Erro de compilação (linha 2, coluna 10): `$state(...)` can only be used as a variable declaration initializer, a class field declaration, or the first assignment to a class field at the top level of the constructor.

Para quem está começando, a tradução é uma só: escreva let antes do nome. A coluna 10 aponta exatamente o $state, que é onde o compilador percebeu que não havia declaração.

O aviso que não impede a compilação

Uma tabela com <tr> solto dentro de <table>, sem <tbody>, compila e mostra o conteúdo — mas o compilador avisa: "`<tr>` cannot be a child of `<table>`…". O navegador conserta a estrutura ao montar a página, e o resultado pode não ser o que você escreveu. Por isso a versão 3 tem um <tbody> em volta do {#each}.

Resumo

  • Um formulário é um conjunto de estados mais uma regra que decide quando estão completos.
  • bind:value liga o campo à variável nos dois sentidos, e só existe em input, textarea e select.
  • onsubmit com e.preventDefault() trata o envio sem recarregar.
  • trim() antes de comparar evita que um campo só com espaços passe por preenchido.
  • A validação mora na função; o disabled é conforto, não regra.
  • return cedo encerra a função e impede que o erro seja apagado logo depois de criado.
  • Um único estado (passo ou etapa) decide qual pedaço aparece.
  • {#snippet} guarda marcação com nome e {@render} a desenha — é o par que substitui o <slot>.
  • $derived recalcula o resumo quando os campos mudam.
  • O selo svelte-xxxxx depende do nome do arquivo, não das regras de CSS.
