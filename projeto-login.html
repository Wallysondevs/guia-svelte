Projetos · Login e Sessão

A Ana quer uma área do cliente onde cada pessoa vê as próprias encomendas. O problema não é a tela de senha — é que a internet não tem memória. Cada pedido chega ao servidor como se fosse a primeira vez: ele não sabe que você acabou de entrar na página anterior. Quem resolve isso é um cookie, e é ele que faz o login existir de verdade. Nesta aula o login é construído em três versões, e cada passo é conferido com o cabeçalho HTTP que o servidor devolveu.

Você vai aprender
  • Por que "estar logado" não é um estado do componente.
  • A diferença entre um login que só troca a tela e um login que o servidor reconhece.
  • Como escrever uma action de formulário com +page.server.js.
  • O que fail(400, …) devolve e como a página usa isso.
  • Como redirect(303, …) muda o endereço depois do login.
  • O que cada atributo do cookie significa: HttpOnly, SameSite, Max-Age.
  • Como o hooks.server.js lê o cookie em todo pedido.
  • Como proteger uma rota inteira sem repetir a checagem em cada página.
  • Como apagar o cookie no botão "Sair" com cookies.delete.
  • As mensagens reais de invalid_export_location e action_data_not_serializable.

1. A internet não tem memória

Quando você abre uma página, o navegador manda um pedido e o servidor responde. O pedido seguinte é uma conversa nova: nada do anterior sobrevive. Se o servidor não fizer nada a mais, ele não tem como saber que os dois pedidos vieram da mesma pessoa. É por isso que "estar logado" precisa ser provado em cada pedido.

A prova viaja num cookie: um pedacinho de texto que o servidor manda na resposta, o navegador guarda, e devolve em todo pedido para o mesmo site. O cookie não diz "sou a Ana" — ele diz "esta conversa já foi autenticada", e o servidor confere isso antes de entregar qualquer dado.

Na padariaNa aplicação
A pessoa diz o nome no balcãoO formulário de login
O crachá que ela recebeO cookie de sessão
Mostrar o crachá a cada pedidoO navegador devolvendo o cookie
O porteiro que olha o crachá na portaO hooks.server.js
Devolver o crachá ao saircookies.delete

Repare que o crachá não é a pessoa. Ele é uma prova que o servidor emitiu e reconhece. Se alguém copiar o crachá, entra no lugar dela — e é por isso que o cookie de sessão precisa de cuidados: HttpOnly impede o JavaScript da página de ler, e SameSite limita quando ele é enviado.

2. Versão 1 — o login que mora na tela

A primeira versão é a que todo mundo escreve primeiro: um componente com dois campos e um $state dizendo se a pessoa entrou.

<script>
  let logado = $state(false);
  let email = $state('');
</script>

<h1>Entrar</h1>

{#if logado}
  <p>Bem-vinda, {email}!</p>
  <a href="/painel">ir para o painel</a>
{:else}
  <form onsubmit={(e) => { e.preventDefault(); logado = true; }}>
    <label>E-mail <input bind:value={email} type="email"></label>
    <label>Senha <input type="password"></label>
    <button>Entrar</button>
  </form>
{/if}

Na primeira visita, o compilador entrega o formulário vazio:

<h1>Entrar</h1> <form><label>E-mail <input value="" type="email"/></label> <label>Senha <input type="password"/></label> <button>Entrar</button></form>

Funciona na tela e não funciona no mundo. Dois motivos, e os dois são graves. O primeiro: a senha não é conferida em lugar nenhum — qualquer texto passa. O segundo: o servidor nunca soube de nada. Se o visitante clicar em "ir para o painel", o pedido chega sem prova nenhuma, e a página do painel vai mostrar o que estiver escrito nela, para qualquer pessoa.

O terminal mostra esse segundo problema sem rodeios: o painel responde 200 para quem nunca entrou.

ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" -H 'Accept: text/html' http://localhost:5175/painel
200
ana@notebook:~/loja$ curl -s -H 'Accept: text/html' http://localhost:5175/painel | grep -o "
[^<]*
"
<h1>Área do cliente</h1>

A anatomia da versão 1

let logado = $state(false)
um booleano que só existe na memória da página. Recarregar apaga.
onsubmit com preventDefault()
impede o envio de verdade ao servidor. É justamente esse envio que faria o login existir.
bind:value={email}
guarda o e-mail digitado, para a mensagem de boas-vindas.
type="password"
esconde os caracteres na tela. Não é segurança: quem quiser lê o valor no inspetor do navegador.
{#if logado}
troca o formulário pela saudação. Puro desenho, nenhuma verificação.

Missão: o botão entra sem e-mail nenhum e a saudação fica "Bem-vinda, !". Faça ele recusar e mostrar "Informe o e-mail".

<script>
  let email = $state('');
  let logado = $state(false);
</script>

{#if logado}
  <p>Bem-vinda, {email}</p>
{:else}
  <input bind:value={email} placeholder="E-mail">
  <button onclick={() => (logado = true)}>Entrar</button>
{/if}
<script>
  let email = $state('');
  let logado = $state(false);
  let erro = $state('');

  function entrar() {
    if (email.trim() === '') {
      erro = 'Informe o e-mail';
      return;
    }
    erro = '';
    logado = true;
  }
</script>

{#if logado}
  <p>Bem-vinda, {email}</p>
{:else}
  <input bind:value={email} placeholder="E-mail">
  <button onclick={entrar}>Entrar</button>
  {#if erro}
    <p>{erro}</p>
  {/if}
{/if}

Mesmo com essa validação, a versão 1 continua sendo só a tela. Conferir no navegador serve para avisar o usuário; conferir no servidor serve para proteger os dados. As duas coisas são necessárias, e a segunda é obrigatória.

3. Versão 2 — a ação do formulário no servidor

Agora o formulário ganha method="POST", e o SvelteKit procura uma action no arquivo ao lado. A action recebe o formulário, confere a senha e, se estiver tudo certo, grava o cookie e manda o navegador para outra página.

import { fail, redirect } from '@sveltejs/kit';

const USUARIOS = {
  'ana@padaria.com': { nome: 'Ana', senha: 'pao123' }
};

export const actions = {
  default: async ({ request, cookies }) => {
    const dados = await request.formData();
    const email = dados.get('email')?.trim() ?? '';
    const senha = dados.get('senha') ?? '';
    const usuario = USUARIOS[email];

    if (!usuario || usuario.senha !== senha) {
      return fail(400, { email, erro: 'E-mail ou senha incorretos' });
    }

    cookies.set('sessao', email, {
      path: '/',
      httpOnly: true,
      sameSite: 'lax',
      maxAge: 60 * 60
    });

    redirect(303, '/painel');
  }
};

Leia a ordem: buscar os campos, procurar o usuário, errar cedo com fail, gravar o cookie, sair com redirect. O redirect não é um return — ele interrompe a função lançando um aviso que o SvelteKit captura. Por isso não há nada depois dele.

E a página que usa a action:

<script>
  let { form } = $props();
</script>

<h1>Entrar</h1>

<form method="POST">
  <label>E-mail <input name="email" type="email" value={form?.email ?? ''}></label>
  <label>Senha <input name="senha" type="password"></label>
  <button>Entrar</button>
</form>

{#if form?.erro}
  <p class="erro">{form.erro}</p>
{/if}

<style>
  .erro { color: #b3261e; font-weight: 600; }
</style>

Duas coisas mudaram no HTML. Cada campo agora tem name — é esse nome que chega ao formData do outro lado. E o e-mail volta preenchido quando o login falha, porque a action devolveu o valor em { email }: ninguém quer digitar o e-mail de novo só porque errou a senha.

O compilador, ao desenhar a página sem nenhuma resposta de action, produz:

<h1>Entrar</h1> <form method="POST"><label>E-mail <input name="email" type="email" value=""/></label> <label>Senha <input name="senha" type="password"/></label> <button>Entrar</button></form>

A anatomia da versão 2

export const actions
o dicionário de ações da rota. default é o nome da ação que roda num <form method="POST"> sem endereço especial.
request.formData()
lê o corpo do pedido como formulário. Devolve um objeto do qual se puxa cada campo pelo name.
fail(400, { … })
responde 400 e devolve esses dados para a página, na propriedade form. Não é exceção: é uma resposta.
cookies.set(nome, valor, opções)
manda o Set-Cookie na resposta. As opções decidem quem pode ler, por quanto tempo e em que pedidos ele vai.
redirect(303, '/painel')
responde "veja outro endereço". O 303 é o código certo depois de um POST: o navegador refaz o pedido como GET.

4. O cookie, por dentro

Quando o login dá certo, o servidor responde assim. Copiado do terminal, sem edição:

ana@notebook:~/loja$ curl -s -i -H 'Accept: text/html' -X POST -d 'email=ana@padaria.com&senha=pao123' http://localhost:5175/login | head -4
HTTP/1.1 303 See Other
Vary: Origin
location: /painel
set-cookie: sessao=ana@padaria.com; Max-Age=3600; Path=/; HttpOnly; SameSite=Lax

Cada pedaço da última linha tem uma função. sessao é o nome escolhido por você; ana@padaria.com é o valor; Max-Age=3600 diz que o navegador guarda por uma hora; Path=/ diz que ele vale para o site inteiro; HttpOnly proíbe o JavaScript de ler; SameSite=Lax evita que outro site use o cookie num formulário escondido.

AtributoO que fazSe faltar
HttpOnlyo JavaScript da página não lê o cookieum script malicioso pode copiar a sessão
SameSite=Laxo cookie só vai em pedidos do próprio siteoutro site pode disparar pedidos autenticados
Max-Age=3600expira em uma horavira cookie de sessão: some ao fechar o navegador
Path=/vale para todas as rotassó vale para a rota que o emitiu
Securesó vai por httpsviaja em texto claro numa rede aberta

Aqui está o custo desta versão: o cookie guarda o e-mail em texto. Quem conseguir ler o cookie vira a Ana. Num app de verdade, o valor seria um identificador aleatório, e o servidor guardaria numa tabela o que aquele identificador significa. O mecanismo é o mesmo; muda o conteúdo.

5. A área do cliente

Com o cookie gravado, o painel pode perguntar ao servidor quem está pedindo. A checagem fica no +page.server.js da rota, e o redirect expulsa quem não tem cookie.

import { redirect } from '@sveltejs/kit';

export function load({ cookies }) {
  const usuario = cookies.get('sessao');
  if (!usuario) redirect(303, '/login');
  return { usuario };
}

O resultado, com e sem o cookie, muda completamente o que o servidor devolve:

ana@notebook:~/loja$ curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" -H 'Accept: text/html' http://localhost:5175/painel
303 http://localhost:5175/login
ana@notebook:~/loja$ curl -s -H 'Accept: text/html' -H 'Cookie: sessao=ana@padaria.com' http://localhost:5175/painel | grep -o "
Olá[^<]*
"
<p>Olá, ana@padaria.com. Suas encomendas aparecem aqui.</p>

O primeiro comando não tem cookie e recebe 303 com o endereço do login no cabeçalho location. O segundo manda o cookie na mão (-H 'Cookie: …') e recebe a página com o nome. É exatamente o que o navegador faz sozinho: guarda o cookie e o envia em cada pedido ao mesmo site.

Missão: a tela conta as tentativas e não faz nada com o número. Mostre o aviso "Muitas tentativas" a partir da terceira.

<script>
  let tentativas = $state(0);
</script>

<p>tentativas: {tentativas}</p>
<button onclick={() => (tentativas += 1)}>Entrar</button>
<script>
  let tentativas = $state(0);
</script>

<p>tentativas: {tentativas}</p>
<button onclick={() => (tentativas += 1)}>Entrar</button>

{#if tentativas >= 3}
  <p>Muitas tentativas. Espere um minuto.</p>
{/if}

Contar no navegador é só a metade fácil. Quem quiser tentar senhas em sequência usa um programa, e ele não passa pela sua tela. O limite de verdade mora no servidor, junto com a checagem da senha — a versão 3 não resolve isso; ela resolve o próximo problema, que é repetir a checagem em cada rota.

6. Versão 3 — o porteiro na porta

A versão 2 protege o painel dentro do próprio +page.server.js. Com dez rotas protegidas, seriam dez cópias da mesma checagem — e basta esquecer uma. O hooks.server.js existe para rodar antes de qualquer rota, em todo pedido.

import { redirect } from '@sveltejs/kit';

const PROTEGIDAS = ['/painel'];

export async function handle({ event, resolve }) {
  event.locals.usuario = event.cookies.get('sessao') ?? null;

  const precisaEntrar =
    !event.locals.usuario && PROTEGIDAS.some((p) => event.url.pathname.startsWith(p));

  if (precisaEntrar) redirect(303, '/login');

  return resolve(event);
}

Duas ideias novas. A primeira é locals: um objeto por pedido, onde o hook deixa o que as rotas vão precisar. A segunda é resolve(event): a função que continua o caminho normal e devolve a resposta da rota. Entre uma coisa e outra, o hook decide se deixa passar.

Com o hook no lugar, o load do painel fica curto, e o +page.svelte só mostra o que recebeu. O botão "Sair" é outra action, e ela apaga o cookie:

import { redirect } from '@sveltejs/kit';

export function load({ locals }) {
  return { usuario: locals.usuario };
}

export const actions = {
  logout: async ({ cookies }) => {
    cookies.delete('sessao', { path: '/' });
    redirect(303, '/login');
  }
};

No formulário, o action="?/logout" escolhe a action pelo nome. Sem esse pedaço, o SvelteKit procuraria a ação default, que não existe nesta rota. O resultado do clique, conferido no terminal:

ana@notebook:~/loja$ curl -s -i -H 'Accept: text/html' -H 'Cookie: sessao=ana@padaria.com' -X POST -d '' "http://localhost:5175/painel?/logout" | head -4
HTTP/1.1 303 See Other
Vary: Origin
location: /login
set-cookie: sessao=; Max-Age=0; Path=/; HttpOnly; SameSite=Lax

O Max-Age=0 é o jeito de apagar um cookie: o navegador recebe a mesma linha de antes, com validade zero, e joga fora o que tinha guardado. O -d '' no comando não é detalhe: sem corpo, o servidor responde 415 porque uma action de formulário exige conteúdo de formulário.

A anatomia da versão 3

handle({ event, resolve })
a função que roda em todo pedido, antes da rota. Tudo o que ela fizer vale para o site inteiro.
event.cookies.get('sessao')
lê o cookie que o navegador mandou. Devolve undefined quando ele não veio.
event.locals.usuario
um valor por pedido, criado no hook e lido pelas rotas. Não é global: cada pedido tem o seu.
PROTEGIDAS.some(...)
uma lista de prefixos e um teste para cada. startsWith cobre também as rotas filhas.
resolve(event)
continua o atendimento normal. Se o hook não chamar, nada é respondido.
action="?/logout"
aponta para a action chamada logout na rota atual, em vez da default.

Missão: clicar em "Sair" apaga a saudação e deixa a tela vazia. Faça aparecer a frase "Entre para continuar" depois de sair.

<script>
  let logado = $state(true);
</script>

{#if logado}
  <p>Olá, Ana</p>
  <button onclick={() => (logado = false)}>Sair</button>
{/if}
<script>
  let logado = $state(true);
</script>

{#if logado}
  <p>Olá, Ana</p>
  <button onclick={() => (logado = false)}>Sair</button>
{:else}
  <p>Entre para continuar</p>
{/if}

O {:else} parece enfeite, mas é o que fecha o ciclo: todo estado tem de ter uma tela para cada valor. Sem ele, o usuário sai e fica olhando para o vazio, sem saber se a página quebrou ou se ele saiu.

8. Quando dá errado

Erro 1 — actions no arquivo errado

A action precisa estar em +page.server.js. Colocada em +page.js, o SvelteKit recusa com uma mensagem que diz onde ela deveria estar.

SvelteKit error: invalid_export_location
Invalid export `actions` in `src/routes/login/+page.js` (`actions` is a valid export in +page.server.js)
https://svelte.dev/e/kit/invalid_export_location

A resposta para a página foi 500. O sufixo .server.js não é decoração: ele decide o que pode rodar no servidor e o que pode ir para o navegador.

Erro 2 — devolver algo que não vira texto

O que a action devolve precisa ser serializável: texto, número, booleano, lista, objeto simples. Uma função no meio quebra a resposta.

SvelteKit error: action_data_not_serializable
Data returned from action inside `/login` is not serializable: Cannot stringify a function (`data.fn`)
https://svelte.dev/e/kit/action_data_not_serializable

DevalueError: Cannot stringify a function

A mensagem aponta o campo exato: data.fn. Função não atravessa a fronteira entre servidor e navegador — só dados.

Erro 3 — a página lê data sem load

Sem o load que devolve o usuário, o data chega vazio. O componente compila e quebra ao desenhar.

<script>
  let { data } = $props();
</script>

<h1>Área do cliente</h1>
<p>Olá, {data.usuario}. Suas encomendas aparecem aqui.</p>
Erro ao renderizar: Cannot read properties of undefined (reading 'usuario')

O painel da versão 3 nunca chega a esse erro porque o hook barra o pedido antes — mas qualquer rota nova sem load cai na mesma armadilha.

Resumo

  • Cada pedido HTTP é uma conversa nova; a sessão precisa ser provada em todos eles.
  • O cookie é a prova: o servidor emite, o navegador devolve em cada pedido ao mesmo site.
  • Login de verdade acontece numa action, com +page.server.js — nunca só no componente.
  • fail(400, dados) é resposta, não exceção: os dados chegam à página em form.
  • redirect(303, …) interrompe a função e manda o navegador para outro endereço.
  • HttpOnly, SameSite e Secure são o mínimo para um cookie de sessão.
  • Apagar um cookie é mandá-lo de novo com Max-Age=0.
  • hooks.server.js roda antes de toda rota e evita repetir a checagem em cada página.
  • locals carrega o resultado do hook até o load da rota.
  • Uma action de formulário exige corpo de formulário: sem ele, a resposta é 415.
