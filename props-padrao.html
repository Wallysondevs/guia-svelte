Svelte · Valores padrão e resto das props

A Ana manda imprimir blocos de comanda em branco, com os campos já preenchidos no que nunca muda: o nome da padaria, o horário, a frase de agradecimento. Quem usa o bloco só precisa escrever o que muda naquele pedido. Na aula de props você viu como um componente recebe valores de fora; nesta você vai ver o outro lado da mesma ideia: o que fazer quando o valor não vem. O Svelte resolve isso com um sinal de igual na desestruturação — e guarda o que sobra numa variável de resto.

1. A ideia: a resposta que já vem preenchida

Um formulário em branco obriga quem preenche a inventar uma resposta para tudo. Um formulário com sugestões impressas resolve metade do trabalho: quem quiser, apaga e escreve outra coisa; quem não quiser, deixa como está. Valor padrão de prop é essa sugestão impressa: um valor que o componente usa quando o pai não manda nada.

Sem padrão, o componente precisa decidir o que fazer com undefined em cada lugar onde a prop é usada: um {#if} para o nome, outro para o preço, outro para o texto do botão. É código de proteção espalhado por toda a marcação. Com padrão, você resolve isso na porta de entrada, uma vez, e o resto do componente trabalha com a certeza de que o valor existe.

A escrita é a mesma do JavaScript para parâmetros de função: sinal de igual e o valor, dentro da desestruturação. Quem já viu function soma(a = 0) reconhece na hora. E o efeito é o mesmo: o padrão só entra quando o valor não veio.

Na padariaNo componente
A comanda já com o nome da padaria impressonome = 'Ana' na desestruturação
O cliente escreve por cimao pai passa nome="Bia"
A comanda com tudo impresso, nada escrito à mãocomponente sem props: todos os padrões valem
O espaço em branco no fim, para observações...resto: as props que você não listou
A caixa "outros" da comanda{...resto} repassado para um elemento

Uma coisa importante: valor padrão não é o mesmo que valor inicial de estado. $state(0) cria um valor que pode mudar e que avisa a tela. Um padrão de prop é o valor que a prop assume quando o pai não manda nada; se o pai mandar, o padrão não existe naquela renderização. São papéis diferentes, e a confusão entre os dois gera componentes que ignoram o pai sem você entender por quê.

2. O primeiro valor padrão

Comece com duas props com padrão: o nome e o preço.

<script>
  let { nome = 'Ana', preco = 0.9 } = $props();
</script>

<h1>{nome}</h1>
<p>R$ {preco.toFixed(2)}</p>

Montado sem nenhuma prop, o componente usa os dois padrões:

<h1>Ana</h1> <p>R$ 0.90</p>

Se o pai passar os dois valores, os padrões não entram — e o preço formata o valor dele:

<h1>Bia</h1> <p>R$ 4.50</p>

Duas saídas do mesmo arquivo, com props diferentes. É exatamente isso que o padrão faz: garante que o componente funcione sozinho, sem exigir que o pai conheça todos os campos. Quem usa pode passar só o nome, só o preço, os dois ou nenhum.

A anatomia do padrão

let { nome = 'Ana' }
o nome da prop à esquerda do igual, e o valor padrão à direita. Vale para todas as props da mesma desestruturação.
= 0.9
o padrão pode ser número, texto, booleano, lista, objeto, ou o resultado de uma conta.
= $props()
o lado direito da declaração: a runa que entrega as props. O padrão fica no lado esquerdo, dentro das chaves.
preco.toFixed(2)
no corpo, a prop é um valor comum. Com padrão, você pode chamar métodos sem medo de o valor não existir.

Repare que o padrão vai dentro das chaves da desestruturação, não depois do $props(). Escrever let { nome } = $props() || {} é outra coisa e não faz o que você quer. O igual de padrão é uma regra da desestruturação do JavaScript, e o Svelte só aproveita a mesma sintaxe.

Padrão bom é padrão neutro

Escolha valores que façam o componente parecer correto com o mínimo de informação: 'Ana' para um nome de exemplo, 0 para um contador, [] para uma lista, false para um interruptor. Padrão estranho ('não informado' em todo campo) faz o componente parecer quebrado quando o pai esquece algo.

3. Experimente: complete os padrões

A caixa abaixo tem um padrão só, e o preço sai vazio. Sua missão é fazer o componente mostrar o preço formatado quando ninguém passar nada.

Missão: preco não tem padrão e a tela mostra R$ sem número. Dê o padrão 0.9 e formate com toFixed(2).

<script>
  let { nome = 'Ana', preco } = $props();
</script>

<h1>{nome}</h1>
<p>R$ {preco}</p>
<script>
  let { nome = 'Ana', preco = 0.9 } = $props();
</script>

<h1>{nome}</h1>
<p>R$ {preco.toFixed(2)}</p>

Note que a missão tem duas partes: dar o padrão e formatar. Só o padrão mostraria R$ 0.9, que não é dinheiro; só a formatação quebraria, porque undefined não tem toFixed. O padrão resolve a ausência do valor; a formatação resolve a aparência dele.

Essa combinação de erros é comum no começo: você conserta um e o outro aparece. Ler a mensagem e ir por partes, como aqui, é mais rápido do que tentar adivinhar a correção inteira de uma vez.

4. Quando o padrão entra (e quando não)

O padrão só vale para um valor: undefined. Todo o resto passa direto, inclusive valores que parecem "vazios". A tabela abaixo é a que você vai consultar quando o componente mostrar algo inesperado.

O que o pai mandaA prop valeO padrão entra?
nada (atributo ausente)undefinedsim
nome={undefined}undefinedsim
nome={null}nullnão
nome=""''não
preco={0}0não
nome="Bia"'Bia'não

Essa regra tem consequência prática. Se a sua API devolve null num campo vazio, o padrão não vai entrar, e o componente vai receber null — que quebra na hora em que você chama toFixed ou toUpperCase. Duas saídas: normalizar no pai (null vira undefined) ou tratar no filho com o operador ??:

{@const nomeFinal = nome ?? 'Ana'}
<h1>{nomeFinal}</h1>

O ?? (chamado "coalescência nula") devolve o valor da direita quando o da esquerda é null ou undefined — um pouco mais generoso que o padrão da desestruturação. É a ferramenta certa quando os dados vêm de fora e você não controla o formato.

5. ...resto: as props que sobraram

Um componente pode receber mais props do que ele lista. Em vez de recusar ou ignorar as extras, você pode recolhê-las todas numa variável de resto, com três pontos antes do nome.

<script>
  let { nome = 'Ana', ...resto } = $props();
</script>

<h1>{nome}</h1>
<pre>{JSON.stringify(resto)}</pre>

Sem nenhuma prop extra, o resto é um objeto vazio:

<h1>Ana</h1> <pre>{}</pre>

Com as props quantidade={3} e obs="sem sal" passadas pelo pai, o resto vem com as duas:

<h1>Ana</h1> <pre>{"quantidade":3,"obs":"sem sal"}</pre>

Duas informações importantes nessas saídas. A primeira: nome não entrou no resto — ela foi listada antes dos três pontos, então é capturada pelo próprio nome. A segunda: o resto é sempre um objeto, nunca undefined; com zero extras, ele existe e está vazio. Isso significa que você pode chamar Object.keys(resto).length sem medo.

A anatomia do resto

...resto
os três pontos recolhem tudo o que não foi listado. O nome é livre: resto, outras, extras.
{ nome = 'Ana', ...resto }
o resto vem sempre por último na desestruturação. Não existe resto no meio.
{JSON.stringify(resto)}
para inspecionar o conteúdo, JSON.stringify transforma o objeto em texto legível.
{...resto}
com os mesmos três pontos, dentro de uma tag, o objeto é repassado como atributos.

O mesmo trio de pontos tem dois papéis dependendo do lugar. Na desestruturação (do lado esquerdo do igual), ele junta o que sobra num objeto. Numa tag, ele espalha as chaves daquele objeto como atributos. É a mesma sintaxe, com sentidos opostos — e é por isso que ela aparece duas vezes nos exemplos desta aula.

6. Experimente: conte as props extras

A caixa abaixo lista só o nome. Sua missão é recolher o resto e mostrar quantas props extras chegaram.

Missão: troque o ? pela contagem de props extras, usando ...resto na desestruturação. Como aqui ninguém passa prop nenhuma, a contagem é zero.

<script>
  let { nome = 'Ana' } = $props();
</script>

<h1>{nome}</h1>
<p>Extras: ?</p>
<script>
  let { nome = 'Ana', ...resto } = $props();
</script>

<h1>{nome}</h1>
<p>Extras: {Object.keys(resto).length}</p>

O Object.keys devolve a lista de nomes das chaves de um objeto, e .length conta quantas são. Com nenhuma prop extra, a lista é vazia e a contagem é zero. Se o componente recebesse quantidade={3}, a mesma expressão mostraria 1.

7. Repassar o resto para um elemento

O uso mais comum do resto é o repasse: o componente recebe props que não conhece e as entrega para uma tag, que sabe o que fazer com elas. Classes, identificadores, atributos de acessibilidade — tudo chega ao elemento.

<script>
  let { nome = 'Ana', ...resto } = $props();
</script>

<section {...resto}>
  <h1>{nome}</h1>
</section>

Sem props extras, o repasse não acrescenta atributo nenhum:

<section><h1>Ana</h1></section>

Com class="cartao" e id="principal" passados pelo pai, os dois atributos aparecem na <section>:

<section class="cartao" id="principal"><h1>Ana</h1></section>

Repare que o componente não conhece nem class nem id: ele só repassa. Isso é o que permite criar componentes que se comportam como uma tag comum, aceitando qualquer atributo que o HTML aceite. É um padrão muito usado em bibliotecas de componentes, e a base dele é essa linha de três pontos.

Cuidado com o que você repassa

O repasse é cego: se o pai passar um atributo que o elemento não aceita, ele vai aparecer no HTML do mesmo jeito. E se o resto contiver class, ele sobrescreve a classe que você escreveu na tag, a não ser que você combine as duas antes. Em projetos grandes, vale escrever um teste visual para conferir o HTML gerado.

8. O padrão é calculado uma vez

Aqui está a parte que confunde. O valor padrão é calculado na montagem do componente, não a cada mudança de estado. Se ele depende de outra variável reativa, a conta é feita com o valor daquele instante e não se atualiza depois.

<script>
  let subtotal = $state(0);
  let { total = subtotal * 2 } = $props();
</script>

<p>Total: {total}</p>
<p>Total: 0</p>

O subtotal vale 0 quando o componente monta, então total fica 0. Se o subtotal mudar depois, total continua 0 — o padrão não é reativo. Para acompanhar, o caminho é $derived: let total = $derived(subtotal * 2), que recalcula quando a origem muda.

O mesmo cuidado vale para ler uma prop fora da desestruturação. Este código compila, mas o compilador avisa:

Aviso real do compilador

This reference only captures the initial value of `props`. Did you mean to reference it inside a closure instead? — com o código state_referenced_locally. Ele aparece quando você faz let props = $props(); let nome = props.nome;. A leitura acontece uma vez, e o valor não acompanha mudanças. Prefira desestruturar: let { nome } = $props().

9. Experimente: $props() no lugar certo

A caixa abaixo chama $props() dentro de uma função, e o compilador recusa o arquivo. Sua missão é mover a chamada para o lugar permitido.

Missão: o compilador recusa com `$props()` can only be used at the top level…. Tire a função do caminho: desestruture direto de $props(), no topo do <script>.

<script>
  function pegarProps() {
    return $props();
  }

  let { nome = 'Ana' } = pegarProps();
</script>

<h1>{nome}</h1>
<script>
  let { nome = 'Ana' } = $props();
</script>

<h1>{nome}</h1>

O conserto tem menos linhas que o erro: uma função e uma chamada viram uma declaração só. O $props() é uma runa — um comando que só faz sentido no topo do componente, no momento em que o Svelte prepara o arquivo. Dentro de uma função, ela seria executada depois, e o compilador sabe que isso não funciona.

11. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Todas são sobre o lugar e a forma de declarar props.

Erro 1 — export let no meio de runas

O modo antigo de declarar props era export let. No Svelte 5, um componente que usa runas não pode misturar os dois modelos.

<script>
  export let nome = 'Ana';
  let { preco = 0.9 } = $props();
</script>

<h1>{nome}</h1>
<p>R$ {preco.toFixed(2)}</p>
Erro de compilação (linha 2, coluna 2): Cannot use `export let` in runes mode — use `$props()` instead

A mensagem diz exatamente o que fazer: usar $props(). A linha apontada é a do export let, mesmo que ela venha antes da runa no arquivo. Se você está migrando um componente antigo, troque todas as declarações de uma vez — misturar é o que gera esse erro.

Erro 2 — $props() dentro de uma função

A runa só vale no topo do componente, como inicializador de uma declaração de variável. Dentro de uma função, ela seria executada em outro momento.

<script>
  function pegarProps() {
    return $props();
  }

  let { nome = 'Ana' } = pegarProps();
</script>

<h1>{nome}</h1>
Erro de compilação (linha 3, coluna 11): `$props()` can only be used at the top level of components as a variable declaration initializer

A mensagem é comprida e precisa: "$props() só pode ser usado no topo de componentes, como inicializador de declaração de variável". A coluna 11 aponta o começo da chamada. Mova a desestruturação para o topo e passe os valores que a função precisar como argumentos.

Erro 3 — a runa sem parênteses

Runa é chamada: $props(), com parênteses, mesmo sem argumento nenhum. Sem eles, o compilador não sabe se você quer a runa ou uma variável de mesmo nome.

<script>
  let { nome = 'Ana' } = $props;
</script>

<h1>{nome}</h1>
Erro de compilação (linha 2, coluna 25): Cannot use rune without parentheses

"Cannot use rune without parentheses" é uma das mensagens mais curtas do Svelte. A coluna 25 é o fim da declaração, onde os parênteses deveriam estar. Vale para todas as runas: $state(), $derived(), $effect(), $props().

Resumo

  • Valor padrão se escreve dentro da desestruturação: let { nome = 'Ana' } = $props().
  • O padrão só entra quando a prop vale undefined — não com null, 0 ou ''.
  • Com padrão na porta de entrada, o corpo do componente não precisa de proteção espalhada.
  • ...resto recolhe as props não listadas, sempre por último na desestruturação.
  • O resto é sempre um objeto: vazio quando não há extras, nunca undefined.
  • {...resto} numa tag repassa as chaves como atributos do elemento.
  • Repasse é cego: atributos desconhecidos aparecem e class pode ser sobrescrita.
  • O padrão é calculado uma vez, na montagem; para acompanhar mudanças, use $derived.
  • Ler props.nome direto no <script> gera o aviso state_referenced_locally.
  • Os erros desta aula: export let com runas, $props() fora do topo e runa sem parênteses.
