Svelte · $props()

A Ana tem uma placa de preço na parede da padaria, e quer a mesma placa para o café, o pão de queijo e o sonho. O desenho é igual; o que muda é o nome do produto e o preço. Num componente, essas duas informações que chegam de fora têm nome: propriedades, ou props. Nesta aula você aprende a declarar o que o seu componente aceita e a passar valores para ele — sem copiar e colar o mesmo HTML três vezes.

Você vai aprender
  • O que é uma propriedade e por que ela vem de fora.
  • Como declarar o que o componente recebe com $props().
  • Como o componente pai passa texto, número e expressões.
  • Valores padrão com = dentro da desmontagem.
  • Como renomear uma prop com nome: apelido.
  • Como juntar as props que sobram com ...resto.
  • O que acontece quando o pai não manda nada e o filho não tem padrão.
  • Por que a prop é do pai, mesmo quando o filho a copia para uma variável.
  • Os três erros reais desta aula, com a mensagem do compilador.
  • Como o projeto da Ana compila dois componentes com npm run build.

1. A ideia: a placa que serve para vários produtos

Na padaria, a placa do pão francês e a placa do café têm o mesmo formato: fundo branco, nome do produto em cima, preço embaixo. Se a Ana desenhar cada placa do zero, ela vai errar a cor de uma, o tamanho da letra de outra, e qualquer mudança no formato vira uma tarde inteira de trabalho. O jeito inteligente é desenhar uma placa com dois espaços em branco: um para o nome, outro para o preço.

Um componente funciona assim. Ele é o desenho da placa, e as props são os espaços em branco. Quem usa o componente — o pai — preenche os espaços. O componente que recebe — o filho — só precisa declarar quais espaços existem. O filho não decide o preço do café; ele sabe desenhar um preço qualquer que receba.

Isso muda a forma de pensar. Sem props, você escreveria três blocos de HTML quase iguais. Com props, você escreve um componente e chama três vezes, mudando só o que é diferente. Quando o formato da placa mudar, você mexe num arquivo e as três placas mudam juntas.

Na padariaNo componente
O desenho da placa, igual para todosO arquivo Cartao.svelte
O espaço em branco do nome do produtoUma prop: nome
O espaço em branco do preçoOutra prop: preco
Quem escreve o nome na placaO componente pai: <Cartao nome="café" />
Uma placa sem nome nenhumProp que o pai não mandou: chega vazia

O vocabulário do guia: propriedade é o valor que vem de fora; pai é quem usa o componente; filho é o componente usado. Repare que a prop é uma via de mão única: o pai manda, o filho mostra. Quando o filho precisa devolver uma mudança, existe $bindable, que tem aula própria mais adiante.

2. O componente que recebe

Toda prop nasce de uma linha parecida com esta, no topo do <script>:

<script>
  let { nome = 'pão francês', preco = 0.9 } = $props();
</script>

<p>{nome}: R$ {preco.toFixed(2)}</p>

Aqui está o pulo do gato: $props() devolve um objeto com tudo o que o pai mandou, e você desmonta esse objeto em variáveis com let { … } =. O que está antes do sinal de igual, entre chaves, são os nomes das props. O que está depois é a runa.

<p>pão francês: R$ 0.90</p>

Esse é o HTML que o compilador gera quando ninguém passa nada — o componente usa os padrões. Dez centavos e um nome: o filho desenha a placa sozinho, com o conteúdo de reserva.

A anatomia da linha que recebe

let { … }
a desmontagem: pega o objeto devolvido e separa o que interessa em variáveis com nome.
nome
o primeiro espaço em branco da placa. É o nome que o pai usa ao passar o valor.
= 'pão francês'
o valor padrão, usado quando o pai não manda nada. Sem ele, a prop chega vazia.
preco = 0.9
outra prop, com padrão numérico. Número não leva aspas.
= $props()
a runa que entrega os valores do pai. Precisa ficar no topo do script do componente.
Uma vez só

$props() é chamado uma vez por componente. Você pode desmontar tudo numa linha só, como aqui, ou guardar o objeto inteiro em let props = $props() e ler props.nome depois. Chamar a runa duas vezes não é permitido, e a mensagem desse erro aparece no fim da aula.

3. O pai que manda os valores

Do outro lado existe um componente que importa o filho e o usa como se fosse uma tag. Repare no nome com maiúscula e nos atributos:

<script>
  import Cartao from './Cartao.svelte';
</script>

<h1>Padaria da Ana</h1>
<Cartao nome="café" preco={0.5} />
<Cartao nome="pão de queijo" preco={1.2} />

Cada <Cartao … /> é uma placa desenhada com valores diferentes: o primeiro cartão mostra café: R$ 0.50, o segundo mostra pão de queijo: R$ 1.20. O arquivo do filho não mudou uma linha. Esse é o ganho inteiro das props: um desenho, muitos usos.

Tem duas sintaxes no mesmo elemento, e é importante não confundir. nome="café" passa o texto café; as aspas fazem parte do valor. preco={0.5} passa o número 0.5; as chaves dizem "isto é uma expressão, calcule antes de passar". Se você escrever preco="0.5", o filho recebe o texto "0.5" e a conta preco.toFixed(2) quebra.

A anatomia do que o pai escreve

<Cartao
o componente importado, com inicial maiúscula. Minúscula seria tratada como tag de HTML desconhecida.
nome="café"
prop com texto: aspas normais, sem chaves. O valor vai como está.
preco={0.5}
prop com expressão: chaves em volta. Pode ser número, conta, variável — preco={cesta.total} também vale.
/>
fecha o componente sem conteúdo dentro. Um componente que recebe conteúdo usa <Cartao>…</Cartao>.

Quando o componente tem muitas props, escrever uma a uma cansa. Existe o espalhamento: <Cartao {...produto} /> passa cada campo do objeto produto como uma prop. O nome do campo tem de bater com o nome da prop — { nome, preco } vira nome={…} preco={…}. É útil quando os dados vêm de uma lista.

4. Quando o pai não manda nada

Nem todo pai manda tudo. Se o filho declara preco sem valor padrão e o pai esquece de passar, o valor chega undefined — a palavra que o JavaScript usa para "não existe". Veja o estrago:

<script>
  let { nome, preco } = $props();
</script>

<p>{nome}: R$ {preco.toFixed(2)}</p>

Sem props nenhuma, o componente nem termina de desenhar:

Erro ao renderizar: Cannot read properties of undefined (reading 'toFixed')

"Não consigo ler propriedades de algo indefinido (lendo toFixed)" — em português claro: você pediu para o número se formatar, mas não havia número nenhum ali. O texto nome não quebra porque o vazio vira string vazia; o número quebra porque undefined não tem o método toFixed.

Duas saídas para isso. A primeira é o valor padrão, que já apareceu na seção anterior: preco = 0.9. A segunda é tratar o caso na hora de mostrar, com ?? — o operador que diz "se o valor da esquerda não existir, use o da direita":

<script>
  let props = $props();
</script>

<p>{props.nome ?? 'sem nome'}</p>
<p>sem nome</p>

O ?? não substitui o zero nem a string vazia — só undefined e null. Isso importa: um preço 0 é um preço de verdade (o pão de ontem, de graça), e não pode virar "sem preço".

5. O primeiro experimento: conserte o cartão

O componente abaixo é um cartão sem valores padrão. Ele quebra quando ninguém passa nada, e a caixa mostra a mesma mensagem que o compilador mostrou acima. Sua missão é fazer o cartão funcionar sozinho.

Missão: dê valores padrão para nome e preco, de modo que o cartão mostre pão francês: R$ 0.90 mesmo sem receber nada.

<script>
  let { nome, preco } = $props();
</script>

<p>{nome}: R$ {preco.toFixed(2)}</p>
<script>
  let { nome = 'pão francês', preco = 0.9 } = $props();
</script>

<p>{nome}: R$ {preco.toFixed(2)}</p>

Repare que o HTML não mudou: só a linha do $props(). Em quase todo conserto de props o trabalho é na declaração, porque é ela que decide o que o componente aceita e o que ele faz quando não recebe.

6. Trocar o nome da variável

Às vezes o nome que o pai usa não é o nome que faz sentido dentro do filho. O pai pode passar nome, e o filho preferir chamar de produto para deixar claro que aquilo é um produto. A desmontagem permite renomear com dois-pontos:

<script>
  let { nome: produto = 'pão francês', preco = 0.9 } = $props();
</script>

<p>{produto}: R$ {preco.toFixed(2)}</p>
<p>pão francês: R$ 0.90</p>

A leitura é: "pegue o campo nome do objeto e guarde na variável produto, com padrão 'pão francês'". O pai continua escrevendo nome="café"; dentro do filho, o valor se chama produto. Se você usar {nome} no HTML, o compilador reclama que nome não existe — não há variável com esse nome ali.

Missão: a prop chega como nome e é guardada em produto. Use a variável certa no HTML para o cartão voltar a desenhar.

<script>
  let { nome: produto = 'pão francês', preco = 0.9 } = $props();
</script>

<p>{nome}: R$ {preco.toFixed(2)}</p>
<script>
  let { nome: produto = 'pão francês', preco = 0.9 } = $props();
</script>

<p>{produto}: R$ {preco.toFixed(2)}</p>

Ao rodar, a caixa mostra nome is not defined. É um erro de JavaScript comum, e a solução é de uma palavra: trocar {nome} por {produto}. Sempre que renomear na desmontagem, procure o nome antigo no HTML.

7. O resto das props: ...resto

Um componente que embrulha outro — um cartão que aceita qualquer atributo e repassa — precisa pegar as props que não conhece. Para isso serve o resto, com três pontinhos:

<script>
  let { nome = 'pão', ...resto } = $props();
</script>

<p>{nome}</p>
<p>outras props: {Object.keys(resto).length}</p>
<p>pão</p> <p>outras props: 0</p>

resto é um objeto com tudo o que o pai mandou e não foi desmontado. Sem props extras, ele é vazio e a contagem dá zero. Com preco={0.9} e desconto={10} chegando, daria dois.

O uso mais comum do resto é repassar: <button {...resto}> leva adiante onclick, disabled, aria-label e o que mais o pai tiver passado, sem que o componente precise conhecer cada nome. É a diferença entre um componente fechado e um componente que se adapta.

let { nome = 'pão' } = $props()declara com valor padrão'pão'
let { nome: produto } = $props()renomeia para uso internoundefined
let { nome, ...resto } = $props()separa o que sobraresto é {}

8. O objeto inteiro e o ??

Nem sempre você sabe de antemão quais props vão chegar. Guardar o objeto inteiro deixa o componente flexível: você lê o que precisa na hora e decide o que fazer quando falta.

<script>
  let props = $props();
</script>

<p>{props.nome ?? 'sem nome'}</p>
<p>sem nome</p>

O custo dessa flexibilidade é que o compilador não tem como avisar que você digitou props.nme — não existe lista de props para conferir. Com a desmontagem, um nome errado vira erro na hora; com o objeto, vira uma tela vazia e meia hora de procura. Prefira desmontar; guarde o objeto quando o componente for mesmo genérico.

Missão: quando o pai não manda nome, a tela fica vazia. Mostre o texto sem nome nesse caso.

<script>
  let props = $props();
</script>

<p>{props.nome}</p>
<script>
  let props = $props();
</script>

<p>{props.nome ?? 'sem nome'}</p>

O verificador compara o texto inteiro da tela, e o texto inicial é vazio. Depois da correção ele é sem nome — nem mais, nem menos.

9. A prop é do pai (e isso é de propósito)

Tem uma confusão que aparece sempre: o filho recebe preco e quer mudar o preço. Ele até consegue, porque dentro do script preco é uma variável como outra qualquer. Mas o valor que o pai guarda não muda. No dia seguinte, o pai desenha o filho de novo com o preço antigo, e ninguém entende por que a mudança sumiu.

A regra é: quem manda é o pai. O filho desenha o que recebeu e avisa o pai quando algo acontece (com um evento, ou com uma prop vinculada). Esse caminho de volta tem nome — fluxo de dados de baixo para cima — e é o assunto das aulas de eventos de componente e de $bindable.

Enquanto isso, trate as props como leitura. Se precisar de um valor que muda dentro do filho, crie um estado separado e comece com o valor recebido:

<script>
  let { preco = 0.9 } = $props();
  let desconto = $state(0);
</script>

<p>R$ {(preco * (1 - desconto)).toFixed(2)}</p>
<p>R$ 0.90</p>

Aqui o filho não mexe na prop: ele mexe no próprio desconto, que nasceu com $state e é dele. A conta mistura os dois — o valor de fora e o valor de dentro — e o resultado aparece na tela. Essa mistura é o pão de cada dia de um componente.

11. Quando dá errado

Três mensagens reais, colhidas do compilador rodando os arquivos quebrados. As duas primeiras param a compilação; a terceira só aparece quando a página tenta desenhar.

1. export let no modo runas. Quem aprendeu Svelte antes de 2024 escreve assim. O compilador recusa:

<script>
  let { nome } = $props();
  export let preco = 0.9;
</script>

<p>{nome}: R$ {preco}</p>
Erro de compilação (linha 3, coluna 2): Cannot use `export let` in runes mode — use `$props()` instead

"Não posso usar export let no modo runas — use $props()". A partir do momento em que o componente usa uma runa, ele está no modo novo, e o jeito antigo de declarar prop não vale mais. A correção é juntar tudo na desmontagem: let { nome, preco = 0.9 } = $props().

2. Passar valores para a runa. Parece natural escrever os padrões dentro do $props(…), mas a runa não aceita argumentos:

<script>
  let { nome, preco } = $props({ nome: 'pão', preco: 0.9 });
</script>

<p>{nome}: R$ {preco}</p>
Erro de compilação (linha 2, coluna 24): `$props` cannot be called with arguments

"$props não pode ser chamado com argumentos". Os padrões moram do lado esquerdo, na desmontagem: let { nome = 'pão', preco = 0.9 } = $props(). A runa só entrega; quem decide o que fazer com o que chegou é o seu código.

3. O pai não manda e o filho confia. Este compila sem uma queixa e quebra na hora de desenhar:

<script>
  let { nome, preco } = $props();
</script>

<p>{nome}: R$ {preco.toFixed(2)}</p>
Erro ao renderizar: Cannot read properties of undefined (reading 'toFixed')

O compilador não sabe se o pai vai mandar preco — isso só se descobre rodando. Por isso valor padrão não é luxo: é o que transforma um componente frágil num componente que sempre desenha alguma coisa.

Uma última ideia: props são a fronteira do componente. Tudo o que está dentro é seu; tudo o que vem de fora passa por essa linha. Quanto mais clara a fronteira — com nomes bons e padrões honestos —, mais fácil é usar o componente sem ler o código dele.

Exercícios

1. Qual linha declara duas props com valor padrão?

2. Como o pai passa o número 0.5 para a prop preco?

3. O que let { nome: produto } = $props() faz?

Complete o código

let { nome = 'café', preco = } = $props();
<p>{nome}: R$ {preco.toFixed(2)}</p>

// o café custa cinquenta centavos quando o pai não manda nada

Resumo

  • Propriedade (prop) é o valor que o componente recebe de fora; o pai manda, o filho mostra.
  • let { nome, preco } = $props() declara o que o componente aceita, desmontando o objeto da runa.
  • Valores padrão ficam na desmontagem: nome = 'pão', preco = 0.9.
  • O pai passa texto com aspas e expressão com chaves: nome="café", preco={0.5}.
  • Componente usado como tag tem inicial maiúscula; o nome do arquivo também.
  • nome: produto renomeia a prop para uso interno, sem mudar o nome que o pai usa.
  • ...resto junta as props não desmontadas, útil para repassar atributos.
  • Sem padrão e sem valor do pai, a prop chega undefined e o número quebra em toFixed.
  • ?? troca undefined e null por um valor de reserva — sem afetar 0 nem texto vazio.
  • A prop pertence ao pai: mudar a variável no filho não muda o pai; o caminho de volta é evento ou $bindable.
  • Erros desta aula: export let no modo runas, $props com argumentos, $props() duas vezes e prop sem padrão.
