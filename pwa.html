SvelteKit · PWA

A Ana descobriu que a cliente abre o site da padaria no celular, no ponto de ônibus, e fica olhando uma tela de erro quando a internet cai. O cardápio e o telefone poderiam continuar ali mesmo sem rede. Um PWA (aplicativo web progressivo) é isso: um site comum que ganha um cartão de identidade, um trabalhador de plantão e uma cópia dos arquivos dentro do aparelho. Nesta aula você monta as três peças no projeto SvelteKit da Ana — e vê o que o compilador e o terminal respondem de verdade.

Você vai aprender
  • O que separa um site comum de um PWA instalável.
  • Como escrever o manifest.webmanifest e o que cada campo muda na tela inicial.
  • O que é um service worker e por que ele roda fora da página.
  • Como o SvelteKit 3 monta o service worker com $app/manifest e $app/env.
  • O que o npm run build gera e o tipo certo que o servidor precisa devolver.
  • As três estratégias de cache e o custo de cada uma.
  • Como uma versão nova chega sem prender a Ana no cache velho.
  • Por que ler navigator.onLine no servidor dá a resposta errada.
  • Os erros reais desta aula, com a mensagem copiada do terminal.

1. A ideia: o cartaz que continua na parede

Todo domingo a Ana pendura um cartaz na porta com o cardápio do dia. Se a luz acabar, o cartaz continua lá: ele não depende de tomada nem de internet. O site dela faz o contrário. Cada visita precisa buscar o HTML no servidor, depois o CSS, depois o JavaScript, e se qualquer uma dessas buscas falhar a tela fica vazia. A cliente que chega sem sinal não vê nem o telefone da padaria.

Um PWA resolve esse problema com uma ideia simples: na primeira visita, o site guarda uma cópia dos próprios arquivos dentro do navegador. Nas visitas seguintes, ele pode responder do bolso antes de tentar a rede. O cartaz passa a morar no aparelho. O ganho não é só a economia de dados — é a tela abrir em meio segundo e continuar útil no elevador, no metrô e no fundo da loja.

O custo existe e precisa ser dito: você passa a ser responsável por quando a cópia é atualizada. Um service worker mal configurado serve a versão de ontem por semanas, e a Ana jura que mudou o preço. O resto desta aula é aprender a usar esse bolso sem perder a mão do que está lá dentro.

Na padariaNo PWA
O cartaz na portaO manifest.webmanifest com nome, cor e ícone
O funcionário que fica depois do expedienteO service worker, que roda em segundo plano
A caixa onde ficam as cópias dos cartazesO Cache Storage, com um nome por versão
A placa "abrimos sem luz"A página que responde quando não há rede
Trocar o cartaz velho pelo novoO evento activate, que apaga o cache antigo

2. As três peças de um PWA

PWA não é uma biblioteca nem um comando mágico. É um conjunto de três peças que o navegador reconhece:

Primeira peça: manifest. Um arquivo JSON que diz o nome do app, a cor da barra, o ícone que vai para a tela inicial e o endereço em que ele começa. Sem manifest, o navegador oferece "adicionar à tela inicial" como um favor; com manifest, ele mostra o ícone certo e abre sem a barra de endereço.

Segunda peça: service worker. Um arquivo JavaScript que o navegador instala e mantém vivo mesmo quando a aba está fechada. Ele não tem acesso ao HTML, não tem document e não vê a tela. O que ele vê são eventos: instalou, ativou, chegou uma requisição. É ele que decide se a resposta vem da rede ou do cache.

Terceira peça: HTTPS. Service worker só funciona em endereço seguro, porque ele intercepta tudo o que o site pede. A exceção é localhost, que o navegador trata como seguro para você poder desenvolver. Publicar um PWA em HTTP é publicar um PWA que não instala — a lição de Build e Deploy já cuida do endereço; aqui cuidamos dos arquivos.

PeçaArquivo no projetoQuem executaSem ela
Manifeststatic/manifest.webmanifestO navegador, na hora de instalarO app instala como atalho comum
Service workersrc/service-worker.jsUma thread separada da páginaSem cópia local: sempre depende da rede
HTTPSo endereço de publicaçãoO navegadorO service worker nem é registrado

3. O manifest: o cartão de identidade do app

O manifest é um arquivo de texto com extensão .webmanifest, guardado em static/. Tudo o que está em static é copiado para o build sem passar pelo compilador — é exatamente o que um arquivo de configuração precisa. Comece pelo da padaria:

{
  "name": "Padaria da Ana",
  "short_name": "Padaria",
  "lang": "pt-BR",
  "start_url": "/",
  "scope": "/",
  "display": "standalone",
  "background_color": "#fffdf7",
  "theme_color": "#2e7d32",
  "icons": [
    { "src": "/icons/icone-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icone-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/mascara-512.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}

O nome do arquivo não é obrigatório, mas o navegador prefere .webmanifest ao .json porque o tipo MIME é registrado. O conteúdo, sim, tem regras: JSON válido, sem comentários, sem vírgula sobrando no último item. Um erro de vírgula faz o navegador ignorar o manifest inteiro e não avisar na tela.

A anatomia do manifest

name e short_name
name é o nome comprido, que aparece na instalação; short_name é o que cabe embaixo do ícone na tela inicial. Se o segundo faltar, o navegador corta o primeiro.
start_url e scope
start_url é a página que abre ao tocar no ícone; scope é o território que o app controla. Os dois começam com / porque o app é o site inteiro.
display
como a janela aparece. standalone esconde a barra de endereço e mantém os botões do sistema; browser é uma aba comum; fullscreen esconde tudo, e é raro querer isso.
theme_color e background_color
a primeira pinta a barra de status; a segunda é o fundo enquanto o app carrega. Use as mesmas cores do CSS, senão a abertura pisca em branco.
icons
a lista de imagens. O Chrome pede 192×192 e 512×512 em PNG; o purpose: "maskable" permite que o Android recorte o ícone em círculo sem cortar o desenho.

Repare no que o manifest não faz: ele não guarda arquivo nenhum para uso offline. Quem guarda é o service worker. O manifest só descreve o app para o sistema operacional. Essa divisão confunde muita gente no começo, e separá-la mentalmente economiza horas de depuração.

Ícone maskable não é enfeite

No Android, o ícone é recortado em círculo, quadrado arredondado ou gota, conforme o fabricante. Um ícone maskable reserva uma margem de segurança de 10% em volta do desenho. Sem ela, o pão da Ana perde a casca no recorte — literalmente.

4. O service worker: quem fica de plantão

O service worker é um arquivo JavaScript com um ciclo de vida próprio. Ele nasce quando o navegador registra o arquivo, passa por uma fase de instalação, espera a vez e só então assume o controle das páginas. Entender essa ordem é o que separa um cache que funciona de um cache que serve lixo.

Na instalação, você aproveita para buscar e guardar os arquivos que quer ter à mão. Se qualquer download falhar, a instalação inteira falha e o service worker antigo continua no comando — o que é uma proteção, não um defeito. Na ativação, você apaga os caches de versões anteriores. No dia a dia, cada requisição GET passa pelo evento fetch, e é ali que você escolhe entre rede e cache.

O detalhe que mais causa erro: o service worker não tem window, document nem localStorage. Quem escreve document.querySelector ali recebe uma mensagem de erro no console do próprio service worker, numa aba separada das ferramentas da página. O objeto global dele é self.

A anatomia do ciclo de vida

install
roda uma vez, quando o arquivo é novo ou mudou. É o lugar de abrir o cache e baixar a lista de arquivos. Se um addAll falhar, a instalação é descartada.
activate
roda quando o service worker novo assume. É o lugar de apagar caches com nome antigo — e de chamar clients.claim(), se você quiser controlar abas já abertas.
fetch
roda a cada requisição da página. Você pode responder do cache, buscar na rede, ou as duas coisas. Requisições POST não entram no Cache Storage.
self
o equivalente ao window dentro do worker. Os eventos são registrados nele, e não no document.

5. O service worker no SvelteKit 3

O SvelteKit tem um lugar reservado para esse arquivo: src/service-worker.js. Se ele existir, o build compila e publica, e o próprio Kit registra o worker na primeira visita em produção. Você não escreve a chamada de register; só escreve o worker.

A versão 3 do Kit aposentou o módulo $service-worker, que os tutoriais antigos mostram. No lugar dele existem dois módulos: $app/manifest, que entrega as listas de arquivos, e $app/env, que entrega a versão do build. O worker da padaria fica assim:

import { assets, immutable, prerendered } from '$app/manifest';
import { version } from '$app/env';

const CACHE = `padaria-${version}`;
const ARQUIVOS = [
  ...assets.map((arquivo) => arquivo.path),
  ...immutable.map((arquivo) => arquivo.path),
  ...prerendered.map((arquivo) => arquivo.path)
];

self.addEventListener('install', (evento) => {
  evento.waitUntil(
    caches.open(CACHE).then((cache) => cache.addAll(ARQUIVOS))
  );
});

self.addEventListener('activate', (evento) => {
  evento.waitUntil(
    caches.keys().then((chaves) =>
      Promise.all(
        chaves.filter((chave) => chave !== CACHE).map((chave) => caches.delete(chave))
      )
    )
  );
});

self.addEventListener('fetch', (evento) => {
  if (evento.request.method !== 'GET') return;

  evento.respondWith(
    caches.match(evento.request).then((guardado) => guardado ?? fetch(evento.request))
  );
});

Cada linha dessa tem uma razão. assets são os arquivos de static/ — o manifest, os ícones, o robots.txt. immutable são os arquivos gerados pelo Vite, com hash no nome, que nunca mudam de conteúdo. prerendered são as páginas que o build já deixou prontas em HTML. Juntar as três listas é juntar tudo o que pode ser guardado sem medo de ficar velho.

O nome do cache carrega version, que muda a cada build. É esse detalhe que faz a atualização funcionar: cache novo, nome novo; o antigo é apagado na ativação. Se você usar um nome fixo, como "padaria", o cache de hoje e o de amanhã se misturam e o navegador pode continuar entregando o arquivo de ontem.

O service worker não é compilado como componente

Ele é um arquivo JavaScript separado, com o seu próprio ambiente de build. Por isso as runas ($state, $derived) não existem ali, e as variáveis de ambiente do servidor também não. O que você pode importar é o que o Kit marca como seguro para worker.

6. Ligando o manifest e conferindo o tipo

O manifest precisa ser anunciado no app.html, o molde de todas as páginas. O caminho usa %sveltekit.assets% para funcionar também quando o site é publicado numa subpasta:

<!doctype html>
<html lang="pt-BR">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <link rel="manifest" href="%sveltekit.assets%/manifest.webmanifest" />
    <meta name="theme-color" content="#2e7d32" />
    %sveltekit.head%
  </head>
  <body data-sveltekit-preload-data="hover">
    <div style="display: contents">%sveltekit.body%</div>
  </body>
</html>

Depois do build, o teste é olhar o que o servidor devolve. O tipo do manifest precisa ser application/manifest+json; se vier text/html, o navegador tratou o arquivo como página e o manifest não vale. O service worker precisa vir como JavaScript:

ana@notebook:~/loja/kit$ curl -sI localhost:4173/manifest.webmanifest
HTTP/1.1 200 OK
content-length: 334
content-type: application/manifest+json

ana@notebook:~/loja/kit$ curl -sI localhost:4173/service-worker.js
HTTP/1.1 200 OK
content-length: 1527
content-type: text/javascript

A resposta tem 200 e o tipo certo nas duas linhas. Se o seu resultado for 404, o arquivo está no lugar errado: static/ é copiado, src/ é compilado. Um manifest dentro de src/ não vira arquivo público, e a página pede por algo que não existe.

Missão: o app já está instalado, então o botão de instalar não existe. Faça o contrário: comece sem instalar, mostre o botão e, depois do clique, troque o aviso por Instalado! O cardápio abre sem internet.

<script>
  let instalado = $state(true);
</script>

<h1>Padaria da Ana</h1>

{#if instalado}
  <p>Instalado! O cardápio abre sem internet.</p>
{:else}
  <p>Instale o app para ver o cardápio offline.</p>
{/if}
<script>
  let instalado = $state(false);
</script>

<h1>Padaria da Ana</h1>

{#if instalado}
  <p>Instalado! O cardápio abre sem internet.</p>
{:else}
  <button onclick={() => (instalado = true)}>Instalar</button>
{/if}

A caixa é o pedaço de interface que o manifest promete: ou o botão de instalar, ou o aviso de que o app já está no aparelho. O manifest não decide isso sozinho — o evento beforeinstallprompt avisa quando o navegador permite instalar, e o seu componente guarda a resposta. A lógica é a mesma de qualquer estado: um valor que muda e um trecho de tela que depende dele.

7. As três estratégias de cache

Guardar arquivo é fácil; decidir qual arquivo guardar e por quanto tempo é o trabalho de verdade. Existem três receitas que resolvem quase todos os casos, e elas têm custos diferentes:

EstratégiaComo funcionaBom paraCusto
Cache primeiroprocura no cache; se não achar, vai à rede e guardaícones, fontes, CSS e JS com hasha atualização só aparece no próximo build
Rede primeirotenta a rede; se falhar, usa o cacheHTML, cardápio, preço do diamais lento no 3G; offline depende do cache antigo
Rede e cache juntosresponde do cache e atualiza em segundo planolistas que mudam poucoa tela mostra o dado velho por um instante

O erro clássico é usar cache primeiro para tudo. O HTML fica preso na primeira visita, e a Ana muda o preço no servidor sem entender por que o celular dela continua mostrando o valor antigo. A regra prática: arquivo com hash pode vir do cache para sempre; página e dado de servidor precisam passar pela rede primeiro.

No worker da seção 5, o fetch faz cache primeiro para tudo. É um começo didático, não uma configuração de produção. Para o cardápio, o certo é tentar a rede e cair no cache quando ela falhar. A diferença cabe em poucas linhas, e o custo é o tempo de espera quando a rede está lenta.

Missão: a faixa de offline aparece mesmo com a internet funcionando. Deixe o aviso escondido no começo e mostre-o só depois de clicar em simular queda — e esconda de novo no segundo clique.

<script>
  let offline = $state(false);
</script>

<h1>Padaria da Ana</h1>
<button onclick={() => (offline = !offline)}>simular queda</button>
<p>Você está offline. O cardápio continua.</p>
<p>Pão quentinho às 6h.</p>
<script>
  let offline = $state(false);
</script>

<h1>Padaria da Ana</h1>
<button onclick={() => (offline = !offline)}>simular queda</button>
{#if offline}
  <p>Você está offline. O cardápio continua.</p>
{/if}
<p>Pão quentinho às 6h.</p>

A caixa simula o que o evento offline do navegador faria: muda um estado e a tela reage. No app de verdade, esse estado começaria falso e seria ligado por window.addEventListener('offline', ...) — mas com um cuidado: no servidor não existe janela, então esse ouvinte precisa ser registrado depois da montagem, e não no topo do arquivo.

8. A versão nova e o cache velho

Quando a Ana publica um preço novo, o build gera um version novo, o navegador baixa o service worker novo, e ele fica em espera. A versão em espera só assume quando todas as abas antigas fecham — ou quando o seu código chama self.skipWaiting(). Cada escolha tem um preço:

Sem skipWaiting, a Ana vê o preço antigo até fechar todas as abas do site. Com skipWaiting, a próxima navegação já pega o código novo, mas uma aba aberta no meio de um formulário pode receber um JavaScript diferente do que ela carregou. A saída mais educada é avisar: "há uma versão nova, recarregue quando puder".

O aviso se apoia em dois eventos. registration.updatefound dispara quando o navegador encontra um worker novo; registration.waiting é o worker que está pronto e esperando. O botão do aviso chama waiting.postMessage({ tipo: 'assumir' }), e o worker responde com skipWaiting e clients.claim. É comunicação entre duas threads, e por isso usa postMessage, não uma variável compartilhada.

Missão: baixe dois arquivos e o contador deve dizer Cache: 2 de 3 · faltam 1. Hoje o número que falta não acompanha o que já foi guardado.

<script>
  let guardados = $state(0);
  const total = 3;
  let faltam = guardados;
</script>

<p>Cache: {guardados} de {total} · faltam {faltam}</p>
<button onclick={() => (guardados++)}>baixar um</button>
<script>
  let guardados = $state(0);
  const total = 3;
  let faltam = $derived(total - guardados);
</script>

<p>Cache: {guardados} de {total} · faltam {faltam}</p>
<button onclick={() => (guardados++)}>baixar um</button>

O $derived é o mesmo mecanismo que você usaria para mostrar "faltam X arquivos" na tela de atualização: o valor não é guardado, ele é calculado a partir do que mudou. A regra vale para qualquer contador de progresso: guarde o que aconteceu, calcule o que falta.

9. O build de verdade: onde o worker aparece

O service worker não é um arquivo que você vê no editor e pronto. O Kit o compila numa etapa separada do build, e o terminal mostra essa etapa com um nome próprio. Rode na pasta do projeto:

ana@notebook:~/loja/kit$ npm run build 2>&1 | tail -12
rendering chunks...
computing gzip size...
.svelte-kit/output/client/.vite/service-worker-manifest.json  0.15 kB │ gzip: 0.10 kB
.svelte-kit/output/client/service-worker.js                   1.52 kB │ gzip: 0.64 kB

✓ built in 29ms

Run npm run preview to preview your production build locally.

> Using @sveltejs/adapter-auto
Could not detect a supported production environment. See https://svelte.dev/docs/kit/adapters to learn how to configure your app for the platform of your choosing
✔ done

Três linhas dessa saída importam. service-worker-manifest.json é o mapa que o Kit usa para saber o que o worker pode guardar. service-worker.js 1.52 kB é o arquivo final, publicado na raiz do site. E ✓ built in 29ms é o tempo dessa etapa: rápido porque o worker não carrega o Svelte inteiro, só as listas de caminhos. A etapa aparece mais acima no build, com o nome Building service worker — o tail cortou.

O padrão do SvelteKit é registrar o worker automaticamente em produção. Em desenvolvimento, o registro fica desligado para você não brigar com cache enquanto edita. Se precisar conferir o comportamento real, use npm run preview, que serve o build:

ana@notebook:~/loja/kit$ npm run preview

> kit@0.0.1 preview
> vite preview

  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose

A porta 4173 é a do preview, diferente da 5173 do desenvolvimento. As duas podem ficar ligadas ao mesmo tempo, e é comum confundir. Para o PWA, use sempre a 4173: o service worker só existe no build.

10. Quando dá errado

As três mensagens abaixo saíram de execuções reais neste projeto. A primeira é a que mais aparece em quem copiou um tutorial antigo; a segunda é uma armadilha silenciosa, que não gera erro nenhum; a terceira é um caminho de arquivo.

Erro 1 — o módulo $service-worker não existe mais

Este é o exemplo da documentação antiga, com build, files e version. No SvelteKit 3 o build recusa o import e diz exatamente o que usar no lugar.

ana@notebook:~/loja/kit$ npm run build 2>&1 | grep -A14 "Building service worker"
Building service worker
vite v8.4.0 building serviceWorker environment for production...
transforming...
✓ 2 modules transformed.
✗ Build failed in 21ms
error during build:
Build failed with 1 error:

[plugin vite-plugin-sveltekit-guard]
Error: Errored while resolving "$service-worker" in `this.resolve`.
Caused by:
  [plugin vite-plugin-sveltekit-setup]
  SvelteKit error: module_removed_service_worker
  `$service-worker` has been removed. Use `immutable`, `assets` and `prerendered` from `$app/manifest`, `version` from `$app/env`, and `resolve(...)` from `$app/paths` instead: https://svelte.dev/docs/kit/$service-worker
  https://svelte.dev/e/kit/module_removed_service_worker

A mensagem é longa, mas o começo dela é o resumo: module_removed_service_worker. A tradução é "este módulo foi removido". Troque build por immutable, files por assets, e version por import { version } from '$app/env'. O prerendered entra se você tiver páginas pré-renderizadas.

Erro 2 — navigator.onLine no servidor

Este não quebra o build. A página abre, o servidor renderiza, e o texto chega errado: o servidor não tem a menor ideia de como está a internet do celular da cliente.

<script>
  let online = $state(navigator.onLine);
</script>

<p>{online ? 'Você está online' : 'Você está offline'}</p>
<p>Você está offline</p>

O navigator existe no Node 22, mas o campo onLine não: ele vale undefined, que em condição vira falso. O resultado é a frase "Você está offline" numa página que está online. No navegador, a hidratação corrige o texto um instante depois — e a cliente vê a frase piscar. A correção é começar com false e ler o valor real dentro de um $effect ou de onMount, que só rodam no navegador.

Erro 3 — manifest no lugar errado

Se o arquivo ficar em src/ em vez de static/, o build passa, mas o endereço devolve 404. O teste com curl mostra o código e o tipo:

ana@notebook:~/loja/kit$ curl -sI localhost:4173/manifest.webmanifest.json
HTTP/1.1 404 Not Found
content-length: 4932
content-type: text/html
x-sveltekit-page: true

Repare no content-type: text/html: o servidor devolveu a página de erro do SvelteKit, não o manifest. O caminho público de um arquivo estático é o mesmo nome que ele tem dentro de static/. Mover o arquivo para a pasta certa resolve, sem mexer em configuração nenhuma.

11. O aviso do jsconfig.json

Tem um aviso que aparece no build e não impede nada, mas assusta. Ele nasce porque o service worker usa tipos de navegador que o checador de tipos do projeto não conhece, e o Kit pede para excluí-lo da checagem:

ana@notebook:~/loja/kit$ npm run build 2>&1 | head -8

> kit@0.0.1 build
> vite build

tsconfig_invalid
Found issues while validating `jsconfig.json`:
  - "src/service-worker" should be added to the "exclude" array
https://svelte.dev/e/kit/tsconfig_invalid

A mensagem manda adicionar "src/service-worker" ao exclude, mas o valor que silencia o aviso neste projeto é com a extensão: "src/service-worker.js". O arquivo jsconfig.json fica assim:

{
	"extends": "$app/tsconfig",
	"compilerOptions": {
		"strict": true
	},
	"include": ["src", "vite.config.ts"],
	"exclude": ["src/service-worker.js"]
}

Depois disso, npm run build segue sem a linha tsconfig_invalid. É um ajuste de ferramenta, não de comportamento: o worker já funcionava antes. Vale fazer para o terminal ficar limpo e para uma mensagem de verdade não se perder no meio do ruído.

Resumo

  • PWA é um site com manifest, service worker e HTTPS — três peças, não uma biblioteca.
  • O manifest fica em static/, porque ali nada é compilado; o tipo certo é application/manifest+json.
  • O service worker fica em src/service-worker.js e roda numa thread sem DOM.
  • No SvelteKit 3, $service-worker saiu: use $app/manifest para as listas e $app/env para a versão.
  • O build compila o worker numa etapa separada e publica service-worker.js na raiz.
  • Cache primeiro serve arquivo com hash; rede primeiro serve HTML e dado que muda.
  • O nome do cache leva a versão do build; o activate apaga os nomes antigos.
  • navigator.onLine no servidor vale undefined e faz a página chegar dizendo "offline".
  • Sem HTTPS (fora do localhost) o navegador nem registra o worker.
  • Confira com o DevTools em Application e com curl -sI no manifest e no worker.
