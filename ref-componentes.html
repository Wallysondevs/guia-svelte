Svelte · APIs de Componente

A Ana comprou uma caixa de vidro para a vitrine. O que entra pela tampa de cima é o pedido do cliente; o que sai pela fresta lateral é o aviso de "pronto". A caixa não sabe quem está lá fora, e quem está lá fora não sabe o que tem dentro — só o que entra e o que sai. Um componente funciona igual: as props entram, os callbacks saem, e o meio é problema dele. Esta página é o manual das portas da caixa: como abrir, como fechar e como conversar sem quebrar o vidro.

Você vai aprender

  • mount() e unmount(), o começo e o fim de tudo.

  • <svelte:boundary> como rede de proteção de erro.
  • As mensagens reais quando a API é usada fora do lugar.

1. A ideia: portas de entrada e de saída

Um componente é uma função que devolve tela. As entradas são as props; a saída é o que ele chama de volta — hoje, funções que o pai entregou. O que não é porta é detalhe interno: as variáveis de estado, as funções auxiliares, o CSS. Essa fronteira é o que permite trocar o conteúdo da caixa sem quebrar quem a usa.

Quem vem de outras bibliotecas procura três coisas que o Svelte 5 resolveu de outro jeito: eventos de componente (não existem mais como API própria; use callback como prop), slots (viraram snippets, com children sendo o caso especial) e acesso ao elemento do componente (não existe; use bind:this ou contexto). A tabela abaixo é o mapa completo.

2. $props(): o que entra pela tampa

Toda prop nasce de uma desestruturação de $props(), no topo do <script>. O valor à direita do = é o padrão, usado quando ninguém passa nada:

<script>
  let { titulo = 'Pão francês', preco = 0.9 } = $props();
</script>

<p>{titulo}: R$ {preco.toFixed(2)}</p>
<p>Pão francês: R$ 0.90</p>

Sem padrão, a prop que ninguém passa vale undefined — e undefined.toFixed(2) quebra o componente. Por isso a recomendação prática é dar padrão a toda prop que pode faltar, ou tratar o valor com ?? na hora de usar.

let { … } = $props()
a porta de entrada. Os nomes dentro das chaves são as props que o componente aceita.
titulo = 'Pão francês'
o padrão. Vale só quando a prop não é passada; undefined explícito também cai no padrão.
...resto
o resto: um objeto com todas as props que não foram nomeadas. Útil para repassar opções.
onSalvar
uma prop de função. O pai passa a função; o filho chama quando tem algo a avisar.

Missão: ninguém passa props para este componente e a tela mostra : R$. Dê valores padrão para titulo e preco, e formate o preço com duas casas.

<script>
  let { titulo, preco } = $props();
</script>

<p>{titulo}: R$ {preco}</p>
<script>
  let { titulo = 'Pão francês', preco = 0.9 } = $props();
</script>

<p>{titulo}: R$ {preco.toFixed(2)}</p>

A caixa roda o componente sozinho, sem pai — é o mesmo caso de um componente usado sem atributos. Se a tela mostra Pão francês: R$ 0.90, os padrões estão certos e a formatação também.

3. children: o conteúdo que vem de fora

Um componente que só aceita texto e número é limitado. Muitas vezes o pai quer mandar marcação: um parágrafo, um botão, outro componente. É para isso que existe a prop children — ela é um snippet com o conteúdo escrito entre as tags.

<script>
  let { titulo = 'Pão francês', preco = 0.9, children } = $props();
</script>

<article>
  <h2>{titulo}</h2>
  <p>R$ {preco.toFixed(2)}</p>
  {@render children?.()}
</article>
<article><h2>Pão francês</h2> <p>R$ 0.90</p> </article>

O ponto de interrogação antes dos parênteses é JavaScript: se children não existir (o pai não passou conteúdo), a chamada não acontece. Sem ele, o componente quebraria ao ser usado como <Cartao /> sozinho.

<script>
  import Cartao from './Cartao.svelte';
</script>

<Cartao titulo="Pão de queijo" preco={1.5}>
  <p>Feito na hora.</p>
</Cartao>
<Cartao />

Sozinho, o cartão usa os padrões e não desenha conteúdo extra — o children não existe e o ?. evita a chamada. Com dois cartões na vitrine, um com conteúdo e outro sem, o HTML que o navegador recebe é <article><h2>Pão de queijo</h2> <p>R$ 1.50</p> <p>Feito na hora.</p></article> seguido de <article><h2>Pão francês</h2> <p>R$ 0.90</p> </article>.

Repare que o componente filho não aparece no HTML com o nome dele: o compilador desmancha a caixa e entrega as tags de dentro, como se o conteúdo tivesse sido escrito ali desde o começo.

Para mandar mais de um trecho com nome — um cabeçalho, um rodapé —, declare snippets no pai e passe como props: <Painel>{#snippet cabecalho()}…{/snippet}{/Painel}>. O filho renderiza {@render cabecalho()}. É o substituto direto dos slots nomeados do Svelte 4.

4. Callback props: o filho avisando o pai

Quando o filho tem algo a dizer, ele chama uma função que o pai entregou. Não existe mais createEventDispatcher no caminho recomendado: evento de componente virou prop de função, com nome começando por on.

<script>
  let { onSalvar } = $props();
  let texto = $state('');
</script>

<input bind:value={texto} placeholder="pedido" />
<button onclick={() => onSalvar(texto)}>Salvar</button>
<input value="" placeholder="pedido"/> <button>Salvar</button>

Sozinho, o filho desenha o campo vazio e o botão. No pai, o mesmo filho aparece seguido do parágrafo, e o texto inicial é Último pedido: nada ainda — o campo só muda quando alguém digita e clica.

<script>
  import Filho from './Filho.svelte';
  let ultimo = $state('nada ainda');
</script>

<Filho onSalvar={(t) => (ultimo = t)} />
<p>Último pedido: {ultimo}</p>

A vantagem sobre o despachante antigo é que o fluxo fica visível: quem lê o pai vê onSalvar={(t) => …} e sabe exatamente o que acontece. A desvantagem é que o filho não avisa "olha, eu tenho um evento" sem declarar a prop — o que, na prática, é uma vantagem para quem lê.

5. $bindable: quando o filho devolve o valor

Callback resolve o aviso de um evento. Quando o filho edita um valor que pertence ao pai — um campo numérico, um seletor —, a ligação de duas vias é mais direta. $bindable marca a prop como ligável:

<script>
  let { valor = $bindable(0) } = $props();
</script>

<input type="number" bind:value={valor} />
<input type="number" value="0"/>

Sozinho, o campo nasce com o padrão 0. No pai, o valor inicial vem de qtd e o HTML sai com value="2" seguido do parágrafo 2 pães.

<script>
  import Quantidade from './Quantidade.svelte';
  let qtd = $state(2);
</script>

<Quantidade bind:valor={qtd} />
<p>{qtd} pães</p>

Dentro do filho, valor se comporta como estado: muda quando o usuário digita. Fora, o pai recebe a mudança na variável qtd. O compilador gera a ponte nos dois sentidos, e o valor inicial vem do pai (2, no exemplo).

O custo é de propriedade: com bind, o dado tem dois donos. Isso é aceitável num campo de formulário e problemático num dado de negócio, porque fica difícil saber quem mudou o quê. A regra que o guia segue: $bindable para controles de entrada; callback para tudo o mais.

6. Contexto: o que desce sem passar de mão em mão

Existe um caso em que passar prop é pior do que não passar: quando o valor precisa chegar a um componente fundo na árvore. O contexto resolve isso — o pai publica, qualquer descendente lê, sem prop no meio.

<script>
  import { setContext } from 'svelte';
  import Cabecalho from './Cabecalho.svelte';

  setContext('padaria', { nome: 'Padaria da Ana', aberta: true });
</script>

<Cabecalho />
<script>
  import { getContext } from 'svelte';
  let padaria = getContext('padaria');
</script>

<p>{padaria.nome} — {padaria.aberta ? 'aberta' : 'fechada'}</p>

Com o pai acima publicando o contexto, o HTML que o navegador recebe é <p>Padaria da Ana — aberta</p>. O cabeçalho não recebeu prop nenhuma e mesmo assim soube o nome da padaria.

A chave ('padaria') é o endereço do valor. Qualquer descendente que peça a mesma chave recebe o mesmo objeto. Se ninguém publicou, getContext devolve undefined — e aí padaria.nome quebra na hora de desenhar, como na seção de erros.

Duas regras práticas. Primeira: publique o contexto durante a inicialização do componente, não dentro de um evento ou de um setTimeout — depois da montagem, os filhos já leram. Segunda: se o valor muda, publique um objeto com estado dentro ({ contador } criado com $state) em vez de um número solto; assim os filhos acompanham.

7. Ciclo de vida: onMount, $effect, tick

Alguns trabalhos só podem acontecer no navegador e depois que o elemento existe. O mais comum é onMount, que roda uma vez, quando o componente entra na página:

<script>
  import { onMount } from 'svelte';
  let status = $state('carregando');

  onMount(() => {
    status = 'pronto';
  });
</script>

<p>{status}</p>
<p>carregando</p>

No servidor, onMount não roda — e a saída mostra o estado inicial. No navegador, o texto vira pronto no primeiro quadro. Essa diferença é a razão de a tela piscar em páginas que dependem de dados do navegador, e a razão de você nunca colocar no onMount algo que o HTML precisa ter.

Missão: a tela fica presa em carregando. Use onMount para trocar o estado para pronto assim que o componente entrar na página.

<script>
  let status = $state('carregando');
</script>

<p>{status}</p>
<script>
  import { onMount } from 'svelte';
  let status = $state('carregando');

  onMount(() => {
    status = 'pronto';
  });
</script>

<p>{status}</p>

As outras peças do ciclo de vida se encaixam assim: $effect roda depois de cada desenho em que suas dependências mudaram; onDestroy roda quando o componente sai; tick() devolve uma promessa que resolve no próximo desenho, útil quando você precisa medir algo que acabou de aparecer; untrack() lê um valor sem que ele vire dependência do efeito.

<script>
  import { tick } from 'svelte';
  let lista = $state([]);
  let altura = $state(0);

  async function adicionar() {
    lista = [...lista, 'pão'];
    await tick();
    altura = lista.length * 24;
  }
</script>

<button onclick={adicionar}>adicionar</button>
<p>{lista.length} itens, {altura}px</p>
<button>adicionar</button> <p>0 itens, 0px</p>

Sem o await tick(), a medida seria feita antes de o novo item existir na tela — o clássico "medi zero". O tick não faz mágica: ele só espera o compilador terminar o trabalho que já estava na fila.

8. mount() e unmount(): o começo e o fim

Todo projeto Svelte tem um arquivo de entrada que liga o componente principal ao HTML. No Svelte 5 ele usa mount, não new App():

import { mount } from 'svelte';
import App from './App.svelte';

const app = mount(App, {
  target: document.getElementById('app')
});

export default app;

O target é o elemento onde a aplicação vai morar — no projeto da Ana, a <div id="app"></div> do index.html. O retorno é um objeto com o componente montado; guardar numa constante permite desmontar depois:

import { unmount } from 'svelte';
import app from './main.js';

unmount(app);

Duas coisas que costumam confundir. Primeira: mount não existe no servidor — é função de navegador, e chamá-la durante a renderização do servidor quebra. Segunda: montar duas vezes no mesmo target duplica a aplicação; se você precisa trocar a tela, desmonte antes ou deixe o próprio componente decidir o que mostrar.

9. <svelte:element> e os outros elementos especiais

Quando a tag precisa ser escolhida em tempo de execução — um título que pode ser h1 ou h2, um link que pode ser a ou button —, use <svelte:element>:

<script>
  let tag = $state('h2');
</script>

<svelte:element this={tag}>Pão</svelte:element>
<h2>Pão</h2>

O valor de this é o nome da tag, em texto. Se ele for null ou vazio, nada é desenhado — útil para quando a tag só é conhecida depois de carregar um dado.

ElementoPara que serveExemplo

<svelte:window>eventos da janela<svelte:window onkeydown={…} />
<svelte:document>eventos do documento<svelte:document onvisibilitychange={…} />
<svelte:body>eventos do corpo<svelte:body onmouseenter={…} />
<svelte:head>título e meta tags<svelte:head><title>…</title></svelte:head>
<svelte:boundary>rede de proteção de erro<svelte:boundary>…{/snippet}</svelte:boundary>

O <svelte:window> é o mais usado no dia a dia: ele escuta um evento global sem que você precise pegar o objeto window e lembrar de remover o ouvinte depois. Vale saber que <svelte:head> escreve no cabeçalho do documento, e não no corpo — por isso não aparece na saída HTML que este guia mostra.

10. <svelte:boundary>: a rede de proteção

Um erro dentro do componente derruba a página inteira. O <svelte:boundary> limita o estrago: o que está dentro pode falhar, e o snippet failed mostra uma alternativa em vez do vazio.

<script>
  function risco() {
    throw new Error('sem estoque');
  }
</script>

<svelte:boundary>
  <p>{risco()}</p>
  {#snippet failed(erro)}
    <p>Deu erro: {erro.message}</p>
  {/snippet}
</svelte:boundary>
Erro ao renderizar: sem estoque

A saída acima é o que acontece no servidor: o boundary não segura o erro durante a renderização do servidor, e o processo inteiro falha. No navegador, o mesmo componente mostra Deu erro: sem estoque, e o resto da página continua vivo. É por isso que a caixa abaixo funciona e a linha de comando acima não.

Missão: a função risco sempre lança um erro e o componente cai. Coloque o parágrafo dentro de um <svelte:boundary> com o snippet failed que mostra Deu erro: sem estoque.

<script>
  function risco() {
    throw new Error('sem estoque');
  }
</script>

<p>{risco()}</p>
<script>
  function risco() {
    throw new Error('sem estoque');
  }
</script>

<svelte:boundary>
  <p>{risco()}</p>
  {#snippet failed(erro)}
    <p>Deu erro: {erro.message}</p>
  {/snippet}
</svelte:boundary>

O snippet failed recebe o erro como argumento. Existe também pending, que aparece enquanto uma promessa lida dentro do boundary não resolve. O custo dessa rede é que ela esconde o erro do usuário — e é exatamente o que você quer quando o pedido é "a página não pode ficar em branco", e exatamente o que você não quer quando está tentando descobrir o bug: nesse caso, deixe o erro aparecer.

11. Quando dá errado

As quatro mensagens abaixo saíram do compilador desta versão, com linha e coluna. A última vem do navegador, não do compilador.

Erro 1 — export let em modo de runas

Assim que o componente usa uma runa, o modo antigo é desligado e export let deixa de ser prop.

<script>
  export let nome = 'Ana';
  let total = $state(0);
</script>

<p>{nome}: {total}</p>
Erro de compilação (linha 2, coluna 2): Cannot use `export let` in runes mode — use `$props()` instead

A mensagem diz o substituto: "não pode usar export let no modo de runas — use $props()". Troque por let { nome = 'Ana' } = $props();.

Erro 2 — {@render} sem chamada

O trecho precisa ser chamado como função. Sem os parênteses, o compilador recusa.

<script>
  let { children } = $props();
</script>

<div>{@render children}</div>
Erro de compilação (linha 5, coluna 14): `{@render ...}` tags can only contain call expressions

"Só podem conter expressões de chamada" — ou seja, children(), com parênteses. Sem conteúdo opcional, a forma segura é {@render children?.()}.

Erro 3 — $props() fora do topo

Props são lidas uma vez, na inicialização. Dentro de uma função, não existe "topo do componente".

<script>
  function somar() {
    let { a } = $props();
    return a;
  }
</script>

<p>{somar()}</p>
Erro de compilação (linha 3, coluna 16): `$props()` can only be used at the top level of components as a variable declaration initializer

Mova a linha para o começo do <script> e use a variável dentro da função.

Erro 4 — getContext sem quem publique

Compila e quebra ao desenhar: ninguém chamou setContext com essa chave acima deste componente.

<script>
  import { getContext } from 'svelte';
  let padaria = getContext('padaria');
</script>

<p>{padaria.nome}</p>
Cannot read properties of undefined (reading 'nome')

A mensagem fala de 'nome' em undefined: o contexto voltou vazio. Confira a chave e se o componente que publica está realmente acima na árvore.

Resumo

  • Props entram por let { … } = $props(), com padrão à direita do =.
  • children é o conteúdo entre as tags; renderize com {@render children?.()}.
  • O filho avisa o pai chamando uma prop de função — não existe mais createEventDispatcher no caminho novo.
  • $bindable cria ligação de duas vias; use em controle de entrada, não em dado de negócio.
  • setContext publica para descendentes; getContext lê pelo mesmo nome, e devolve undefined se ninguém publicou.
  • onMount não roda no servidor; o HTML sai com o estado inicial.
  • tick() espera o próximo desenho; untrack() lê sem criar dependência.
  • mount(App, { target }) liga a aplicação ao HTML e unmount(app) desliga.
  • <svelte:element this={tag}> escolhe a tag em execução; os outros svelte: ligam a janela, o documento e o cabeçalho.
  • <svelte:boundary> segura o erro no navegador, mas não no servidor.
