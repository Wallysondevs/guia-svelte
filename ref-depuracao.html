Svelte · Depuração

A Ana tem uma balança antiga que às vezes marca errado. Ela não troca a balança: coloca um peso de meio quilo em cima e vê o que o ponteiro diz. Depois põe um quilo, depois dois. Em três tentativas ela sabe se o erro é fixo, se cresce com o peso ou se aparece só em certo intervalo. Depurar é isso: fazer perguntas cuja resposta você consegue observar. Esta página é a caixa de pesos da Ana — as janelas, os comandos e as técnicas para achar o bug sem adivinhar.

1. A ideia: perguntar "onde" antes de "por quê"

Quem está começando tenta entender o bug inteiro de uma vez. Quem já depurou muito faz outra coisa: localiza. "O valor está certo antes do clique? Está certo depois? A tela não mudou ou o valor não mudou?" Cada pergunta elimina metade das hipóteses, e em quatro ou cinco você chega à linha.

Para isso você precisa de lugares onde olhar. Um componente Svelte tem pelo menos três: o terminal, onde o compilador reclama; o console do navegador, onde o JavaScript reclama; e a tela, onde o resultado aparece. A quarta janela, a de rede, serve para quando o problema é dado que não chegou — e é a que quase todo mundo esquece.

JanelaO que apareceComo abrir

console do navegadorerro de execução, console.log, $inspectF12 e a aba Console

Uma regra que economiza muito tempo: se a página nem abriu, o problema é de compilação e está no terminal. Se a página abriu e algo não funciona, o problema é de execução e está no console. Procurar erro de execução no terminal é o mesmo que procurar a chave na geladeira.

2. O painel do Vite: o erro na cara

Durante o desenvolvimento, o Vite toma a tela quando o arquivo não compila. O texto é o mesmo do terminal, com o código em volta e a linha sublinhada. A mensagem abaixo é a de um bloco aberto — a mais comum de todas:

Bloco sem fechamento 
<script>
  let nome = $state('Ana');
</script>

{#if nome === 'Ana'}
  <p>oi</p>
Erro de compilação (linha 5, coluna 0): Block was left open

A linha 5 é a do {#if}, não a do fim do arquivo. A correção é acrescentar {/if} no fim. Enquanto o erro existir, a página não atualiza — o Vite mantém a última versão que funcionava por baixo da sobreposição.

O painel do Vite tem duas informações que o terminal não dá: o trecho de código em volta e, em muitos casos, a indicação de qual arquivo está com problema quando o projeto tem vários. Se a sobreposição não aparecer, olhe o terminal: ele nunca esconde o erro.

3. console.log: a ferramenta que sempre funciona

Antes de qualquer ferramenta sofisticada, o bom e velho log. A diferença entre um log útil e um log inútil é o rótulo: console.log(total) mostra um número solto; console.log('total', total) mostra o nome junto. Com vários logs na tela, o rótulo é o que permite saber qual é qual.

<script>
  let itens = $state([{ nome: 'pão', preco: 0.9 }]);

  function adicionar() {
    itens = [...itens, { nome: 'leite', preco: 4.5 }];
    console.log('itens depois de adicionar', itens.length);
  }
</script>

<button onclick={adicionar}>adicionar</button>
<p>{itens.length} itens</p>

O log aparece no console do navegador, não na tela. O HTML gerado continua sendo só o botão e o parágrafo — o log não desenha nada. Se você precisa que o valor apareça para quem está usando a página, isso não é log: é tela.

ComandoPara que serveCuidado
console.log(rótulo, valor)ver um valor no consoleesquecer de apagar depois
console.table(lista)ver uma lista de objetos em tabelalistas enormes travam o console
console.warn(…)destacar um avisoconfundir com erro
console.error(…)mostrar erro em vermelho, com pilhausar para mensagem comum
console.assert(cond, msg)só reclama se a condição for falsaninguém vê se ninguém abrir o console
console.time(rótulo)medir tempo entre início e fimmede o que você envolveu, não o resto

Um detalhe importante no Svelte 5: o valor de um estado é um objeto especial. console.log(pedido) pode mostrar o valor atual mesmo que você tenha logado antes de mudar — o console guarda a referência e atualiza a prévia. Para ver o retrato do momento, use $state.snapshot, assunto da seção 5.

4. $inspect: o log que não vai para produção

$inspect é uma runa de depuração. Ela mostra o valor no console sempre que ele muda e, na build de produção, o compilador remove a linha. É a diferença entre um console.log que você precisa lembrar de apagar e um que se apaga sozinho.

<script>
  let nome = $state('Ana');
  $inspect(nome);
</script>

<p>{nome}</p>
<p>Ana</p>

A saída na tela não muda: a runa não desenha. No navegador, com o console aberto, cada mudança de nome imprime uma linha marcada como inspeção. Existem duas variantes úteis: $inspect(nome).with(fn) troca o console.log por uma função sua, e $inspect.trace(), chamada dentro de uma função, imprime a pilha de quem chamou.

O $inspect só funciona em modo de desenvolvimento. Se você rodar o build de produção e não vir nada no console, não é bug: é o compilador fazendo o trabalho dele. Essa é a razão de o guia preferir $inspect a console.log quando o log é temporário.

5. $state.snapshot: ver o valor de verdade

Um objeto criado com $state é cheio de ligações internas. Ao mandar esse objeto para o console, você vê as ligações, não o dado. $state.snapshot tira uma cópia comum, que o console mostra como você espera e que o JSON.stringify aceita.

<script>
  let pedido = $state({ cliente: 'Ana', itens: ['pão', 'leite'] });
  let copia = $state.snapshot(pedido);
  console.log('cópia', copia);
</script>

<p>{copia.cliente}: {copia.itens.length}</p>
<p>Ana: 2</p>

O compilador avisa quando a foto é tirada na hora errada: se você usar o snapshot para alimentar a tela, ele congela no primeiro desenho. O aviso tem nome próprio e aparece no terminal:

O aviso real 
state_referenced_locally: This reference only captures the initial value of `nome`. Did you mean to reference it inside a closure instead?

Tradução: "esta referência só captura o valor inicial". Para depurar, o congelamento é justamente o que você quer; para a tela, não. Se o aviso aparecer num valor que deveria acompanhar mudanças, troque por $derived.

6. Erros de execução: a mensagem sem linha

Quando o componente compila e quebra ao desenhar, a mensagem vem do JavaScript e não tem linha do arquivo .svelte. Ela tem três partes: o tipo do erro, a mensagem e a pilha. A pilha aponta para o código compilado, o que assusta — mas o começo dela costuma bastar.

Nome que não existe 
<script>
  let nome = $state('Ana');
</script>

<h1>{naoExiste}</h1>
naoExiste is not defined

A mensagem diz o nome exato que falhou. Na dúvida entre dois nomes parecidos, é a resposta: naoExiste não foi declarado em lugar nenhum.

naoExiste
o nome que falhou. É a primeira coisa a procurar no arquivo, letra por letra.
is not defined
o tipo do problema: o nome não existe no escopo. Compare com "is not a function", que é outro problema.
pilha
a lista de chamadas que levou até ali. O primeiro item é onde o erro estourou; os seguintes mostram quem chamou.
arquivo compilado
o mapa entre o seu .svelte e o JavaScript gerado. Em desenvolvimento, a aba Sources mostra o original.

Três mensagens de execução cobrem a maioria dos casos: X is not defined (nome inexistente), Cannot read properties of undefined (valor vazio usado como objeto) e X is not a function (parênteses em algo que não é função). A tradução de cada uma está no Catálogo de Erros.

7. <svelte:boundary>: teste de falha

Um jeito de descobrir onde o erro nasce é isolar: coloque um pedaço do componente dentro de um <svelte:boundary> com um snippet failed. Se a alternativa aparecer, o erro está naquele pedaço. É a versão Svelte do "tira uma peça e vê se continua quebrado".

<script>
  function risco() {
    throw new Error('sem estoque');
  }
</script>

<svelte:boundary>
  <p>{risco()}</p>
  {#snippet failed(erro)}
    <p>Deu erro: {erro.message}</p>
  {/snippet}
</svelte:boundary>
Erro ao renderizar: sem estoque

Na renderização do servidor, o boundary não segura: o processo falha com a mensagem do erro. No navegador, o mesmo componente mostra Deu erro: sem estoque e o resto da página continua. Isso significa que o boundary é ótimo para isolar durante a depuração no navegador e não serve como rede de proteção do HTML gerado no servidor.

Missão: a função risco sempre lança. Isole o parágrafo num <svelte:boundary> com o snippet failed mostrando Deu erro: sem estoque.

<script>
  function risco() {
    throw new Error('sem estoque');
  }
</script>

<p>{risco()}</p>
<script>
  function risco() {
    throw new Error('sem estoque');
  }
</script>

<svelte:boundary>
  <p>{risco()}</p>
  {#snippet failed(erro)}
    <p>Deu erro: {erro.message}</p>
  {/snippet}
</svelte:boundary>

8. A técnica: reduzir pela metade

Com muitas linhas e nenhuma pista, o método mais rápido é a bisseção. Apague metade do componente e rode. Se o erro sumir, ele estava na metade apagada; se continuar, está na outra. Repita. Em sete rodadas você sai de cem linhas para uma.

Três variações que valem a pena:

Desconfie do que mudou. Bug que aparece do nada quase sempre veio de uma edição — sua ou de outra pessoa. Volte uma versão no Git, ou desfaça a última mudança no editor, e veja se volta a funcionar. Se voltar, você já sabe onde está.

Troque o dado por um fixo. Se o componente funciona com um valor escrito à mão e falha com o valor real, o problema é no dado (formato, tipo, campo faltando), não na tela. Essa é a pergunta que mais rápido separa as duas metades do problema.

Faça funcionar sozinho. Copie o componente para uma caixa "Experimente" deste guia e apague as importações. Se ele funciona ali e falha no projeto, o problema é de contexto — prop faltando, provider ausente, ordem de carregamento.

9. Os três bugs invisíveis

Existe uma categoria de bug que não gera erro nenhum: a página abre, o console fica limpo e a tela mostra a coisa errada. São os mais caros, porque não há mensagem para seguir. Três deles aparecem toda semana no projeto da Ana.

Primeiro: variável sem runa. O valor muda no script, mas ninguém avisa a tela. O compilador avisa no terminal com non_reactive_update, mas só quando o componente já usa alguma runa. Se o componente inteiro estiver no modo antigo, let volta a ser reativo e o bug desaparece — o que confunde ainda mais.

Missão: o clique soma no script e a tela não muda. Ache a variável que não é estado e conserte para aparecer Cliques: 1.

<script>
  let nome = $state('Ana');
  let cliques = 0;
</script>

<button onclick={() => cliques++}>Cliques: {cliques}</button>
<script>
  let nome = $state('Ana');
  let cliques = $state(0);
</script>

<button onclick={() => cliques++}>Cliques: {cliques}</button>

Segundo: $state.raw mutado. A lista recebe um item novo com push, mas a runa só avisa quando o valor inteiro é trocado. A tela continua mostrando o tamanho antigo, sem erro nenhum.

Missão: o botão empurra um item e a tela continua em Itens: 1. Faça chegar a Itens: 2 sem trocar a runa.

<script>
  let itens = $state.raw(['pão']);
  function adicionar() {
    itens.push('leite');
  }
</script>

<button onclick={adicionar}>Adicionar</button>
<p>Itens: {itens.length}</p>
<script>
  let itens = $state.raw(['pão']);
  function adicionar() {
    itens = [...itens, 'leite'];
  }
</script>

<button onclick={adicionar}>Adicionar</button>
<p>Itens: {itens.length}</p>

Terceiro: lista sem chave. A lista é ordenada ou filtrada e os elementos se confundem: o texto de um aparece no lugar do outro, o cursor do campo pula. Aqui não há erro nem valor errado no script — o problema é que o compilador reaproveitou o elemento pela posição. A correção é a chave: {#each lista as item (item.id)}.

O quarto item da tabela engana muito: $effect e onMount só rodam no navegador. Se o valor aparece no HTML do servidor e o efeito nunca age, confira se o componente está sendo renderizado no servidor e não hidratado no cliente — nesse caso, não há navegador para rodar o efeito.

10. Um roteiro de cinco minutos

Quando o bug não tem cara, siga a ordem. Ela é chata de propósito: cada passo elimina hipóteses.

1. Leia o erro inteiro. Terminal primeiro. Se houver mensagem de compilação, o resto é consequência dela: conserte e rode de novo.

2. Abra o console. Se houver erro de execução, a mensagem diz o nome que falhou. Procure esse nome no arquivo antes de mexer em qualquer outra coisa.

3. Verifique o valor. Sem erro, o problema é de valor. Coloque um $inspect na variável suspeita e olhe se ela muda quando você interage. Se não muda, o problema está no evento; se muda, o problema está na tela.

4. Reduza. Apague metade. Rode. Repita. Em poucas rodadas, sobra a linha culpada.

5. Conserte e trave o bug. Depois de consertar, escreva um teste ou uma caixa "Experimente" que reproduza o caso. Bug que não deixa teste volta.

Resumo

  • Erro de compilação aparece no terminal e na sobreposição do Vite; erro de execução, no console do navegador.
  • console.log('rótulo', valor) é mais útil do que o valor solto, porque diz o que é.
  • $inspect mostra o valor em desenvolvimento e some na produção; $inspect.trace() mostra a pilha.
  • $state.snapshot tira a foto do valor; usado na tela, congela — e o compilador avisa.
  • Erro de execução nomeia o que falhou: is not defined, Cannot read properties, is not a function.
  • <svelte:boundary> isola o pedaço que falha no navegador, mas não no servidor.
  • Reduza pela metade, compare com o que funcionava, troque o dado por um fixo.
  • Três bugs invisíveis: variável sem runa, raw mutado e lista sem chave.
  • $effect e onMount só rodam no navegador; no servidor, não há DOM.
  • Depois de consertar, escreva o caso que reproduz o bug — bug sem teste volta.
