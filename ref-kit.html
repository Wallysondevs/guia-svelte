SvelteKit · Arquivos do SvelteKit

A Ana organiza a padaria por endereço: a rua é o bairro, o número é a casa, o complemento é o apartamento. Se ela muda um móvel de lugar, o endereço não muda — a casa é a mesma. O SvelteKit funciona assim: o caminho do arquivo é o endereço da página, e o nome do arquivo diz o que ele faz naquela casa. Esta página é a lista de nomes: o que cada um significa, onde mora e o que acontece quando você troca um pelo outro.

Você vai aprender
  • Como uma pasta em src/routes vira um endereço no navegador.
  • O que faz +page.svelte, +layout.svelte e +error.svelte.
  • A diferença entre +page.js e +page.server.js.
  • Como o load entrega data para a página.
  • Como criar uma API com +server.js.
  • Como hooks.server.js roda antes de cada requisição.
  • Os módulos especiais: $app/navigation, $app/state, $app/environment e $env.
  • Parâmetros, grupos e rotas opcionais no nome da pasta.
  • O que o npm run dev de um projeto Kit mostra no terminal.

1. A ideia: o caminho do arquivo é o endereço

Num projeto Svelte comum, você tem um App.svelte e pronto: uma página só. Num projeto SvelteKit, a pasta src/routes é uma árvore de endereços. Um arquivo em src/routes/pedidos/+page.svelte atende o endereço /pedidos. Um arquivo em src/routes/pedidos/2026/+page.svelte atende /pedidos/2026.

O nome do arquivo não é enfeite: é o papel dele. +page.svelte é o que aparece na tela; +layout.svelte é a moldura que envolve as páginas daquela pasta e das subpastas; +page.js busca dados antes de desenhar; +server.js responde a uma chamada de API sem desenhar nada. Trocar o nome de um arquivo muda o comportamento, mesmo que o conteúdo seja idêntico.

ArquivoRoda ondeServe para
+page.svelteservidor e navegadoro conteúdo da página
+layout.svelteservidor e navegadormoldura em volta das páginas filhas
+page.jsservidor e navegadorbuscar dados que podem rodar nos dois lados
+page.server.jssó no servidorbuscar dados com segredo, banco, cookie
+layout.js / +layout.server.jsservidor (e navegador no universal)dados que valem para várias páginas
+server.jssó no servidorendpoint de API (JSON, texto, arquivo)
+error.svelteservidor e navegadora tela quando algo dá errado
hooks.server.jssó no servidorrodar antes de cada requisição

Essa convenção tem um custo e um ganho. O custo é que você precisa aprender nomes antes de escrever a primeira rota — a curva é mais íngreme do que abrir um arquivo e desenhar. O ganho é que o projeto se explica pelo sistema de arquivos: quem abre a pasta routes vê os endereços do site, sem precisar de configuração de rotas em lugar nenhum.

2. O projeto Kit por dentro

Um projeto criado com o CLI oficial tem uma estrutura pequena. Esta é a listagem real de um projeto mínimo, com o servidor desligado:

ana@notebook:~/loja$ ls -R src
src:
app.html
lib
routes

src/lib:
assets
index.js

src/lib/assets:
favicon.svg

src/routes:
+layout.svelte
+page.svelte

Três pastas e dois arquivos de rota. app.html é o casco HTML que envolve tudo: nele ficam o %sveltekit.head% e o %sveltekit.body%, os dois buracos que o Kit preenche. lib é onde ficam componentes e utilidades reaproveitáveis, importados pelo atalho $lib. E routes é o mapa do site.

src/routes/
a raiz dos endereços. Cada pasta aqui dentro é um pedaço do caminho na URL.
+page.svelte
a página daquele endereço. É o único arquivo que precisa existir para a rota responder.
+layout.svelte
a moldura herdada pelas páginas da pasta e das subpastas. Recebe children.
+page.js
o carregador de dados daquela página. Devolve um objeto que chega na página como data.
app.html
o casco HTML. Fora de routes, mas é o primeiro arquivo que o navegador recebe.

Repare no sinal de mais antes de cada nome. Ele existe para separar os arquivos especiais do Kit dos arquivos comuns da pasta: um Cartao.svelte ao lado do +page.svelte é só um componente, não uma rota. Sem o +, o Kit ignoraria o arquivo como rota — e é por isso que renomear um arquivo de rota "só tirando o mais" faz a página sumir.

Fora de src há um arquivo que decide tudo: o vite.config.js. No SvelteKit 3 não existe mais svelte.config.js — o plugin do Kit e o adaptador moram aqui. Este é o arquivo real que o CLI cria, num projeto com SvelteKit 3.4.1 e Vite 8.4.0:

import adapter from '@sveltejs/adapter-auto';
import { sveltekit } from '@sveltejs/kit/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [
    sveltekit({
      compilerOptions: {
        // Force runes mode for the project, except for libraries. Can be removed in svelte 6.
        runes: ({ filename }) =>
          filename.split(/[/\\]/).includes('node_modules') ? undefined : true
      },

      // adapter-auto only supports some environments, see https://svelte.dev/docs/kit/adapter-auto for a list.
      // If your environment is not supported, or you settled on a specific environment, switch out the adapter.
      // See https://svelte.dev/docs/kit/adapters for more information about adapters.
      adapter: adapter()
    })
  ]
});

Três partes importam. plugins: [sveltekit({ … })] é o que faz o Vite entender a pasta routes — sem ele, o Kit não existe. adapter: adapter() é o empacotador de publicação; o adapter-auto tenta adivinhar a plataforma e, num computador comum, avisa que não conseguiu. E runes liga o modo moderno em todos os arquivos do projeto, menos nos de node_modules: é por isso que, num projeto criado pelo CLI, um export let dá erro na hora, enquanto o mesmo código num componente isolado até compila.

3. +page.svelte: a página

A página é um componente Svelte comum, com um acréscimo: ela recebe uma prop chamada data, com o que o load devolveu. Se não há load, a página simplesmente não usa a prop.

<h1>Padaria da Ana</h1>
<p>Pão quentinho a partir das 6h.</p>
<h1>Padaria da Ana</h1> <p>Pão quentinho a partir das 6h.</p>

O endereço dessa página é /, porque ela está na raiz de routes. Uma pasta pedidos com um +page.svelte dentro atende /pedidos, e assim por diante. Não há registro de rota em arquivo de configuração: a pasta é o registro.

Missão: a página espera data.titulo, mas ninguém passou data e ela quebra. Dê um valor padrão para a prop, como o Kit faria com um load vazio.

<script>
  let { data } = $props();
</script>

<h1>{data.titulo}</h1>
<script>
  let { data = { titulo: 'Pedidos' } } = $props();
</script>

<h1>{data.titulo}</h1>

A caixa mostra o padrão que o Kit usa: a página é um componente que recebe dados por prop. No projeto de verdade, quem preenche data é o load — e é isso que as próximas seções explicam.

4. +layout.svelte: a moldura e o children

O layout é o que se repete em várias páginas: cabeçalho, menu, rodapé. Ele envolve as páginas filhas e recebe o conteúdo delas na prop children, renderizada com {@render children()}.

<script>
  let { children } = $props();
</script>

<header>
  <strong>Padaria da Ana</strong>
</header>

<main>
  {@render children()}
</main>

<footer>Rua das Flores, 12</footer>

Com esse layout na raiz, toda página do site ganha cabeçalho e rodapé sem repetir uma linha. Um layout dentro de src/routes/pedidos vale só para as rotas daquela pasta e das subpastas — é o jeito de dar uma moldura diferente a uma seção do site.

O layout também pode carregar dados, com +layout.js ou +layout.server.js. O que ele devolve desce para as páginas filhas, junto com o que cada página carregou. Duas armadilhas: o layout precisa renderizar children (se esquecer, a página não aparece) e a herança é por pasta, não por arquivo — um +layout.svelte ao lado de um +page.svelte envolve só as rotas daquela pasta para baixo.

5. +page.js e +page.server.js: o load

Buscar dados é papel do load. Ele roda antes de a página desenhar e devolve um objeto; o objeto chega na página como data. Existem duas versões, e a diferença é onde o código roda.

export function load() {
  return {
    pedidos: ['pão', 'leite', 'café']
  };
}

O +page.js é o carregador universal: roda no servidor na primeira visita e no navegador nas navegações seguintes. Serve para dado público, que pode ser buscado dos dois lados.

import { readFile } from 'node:fs/promises';

export async function load() {
  const bruto = await readFile('dados/pedidos.json', 'utf8');
  return { pedidos: JSON.parse(bruto) };
}

O +page.server.js roda só no servidor. É o lugar de senha, token, banco de dados e acesso a arquivo — nada disso pode ir para o navegador. Se o seu load importa um módulo de servidor, ele precisa ser .server.js; o contrário (usar fs num +page.js) quebra no navegador.

ArquivoRoda no servidorRoda no navegadorPode ter segredo
+page.jssimsimnão
+page.server.jssimnãosim
+layout.jssimsimnão
+layout.server.jssimnãosim
+server.jssimnãosim

Um detalhe de nomenclatura que confunde: o Kit chama de "universal" o código que roda nos dois lados e de "server" o que roda só no servidor. O sufixo .server.js é a marca — qualquer arquivo com esse sufixo nunca vai para o pacote do navegador.

6. O data que desce e o fetch que o Kit trata

Quando o load devolve { pedidos }, a página recebe data.pedidos. A página não chama o banco nem a API: ela recebe o resultado pronto e desenha.

<script>
  let { data } = $props();
</script>

<h1>Pedidos</h1>
<ul>
  {#each data.pedidos as pedido}
    <li>{pedido}</li>
  {/each}
</ul>

Dentro do load, use o fetch que vem nos argumentos, não o global. O do Kit sabe que está no servidor e reaproveita a resposta se a mesma chamada aparecer em outro load; além disso, ele carrega os cookies da requisição quando é chamado no servidor. O fetch global também funciona, mas perde essas vantagens.

O objeto que o load devolve precisa ser serializável: texto, número, booleano, lista, objeto simples, Date, Map, Set. Função não atravessa a fronteira servidor/navegador — se você devolver uma função, ela some ou dá erro. Quando os dados são grandes, existe a opção de transmitir promessas, mas isso é assunto de outra aula.

Um caso que aparece em todo projeto: o load pode não achar o registro. O padrão é devolver null e deixar a página decidir o que mostrar. A página, então, precisa aguentar data vazio — e é aí que quem testa o componente isolado tropeça, porque sem load não existe data nenhum.

Missão: este é o trecho da página que trata "pedido não achado". Sem load por perto, a prop chega indefinida e o componente quebra antes de desenhar. Dê um data inicial e mostre Não encontrado.

<script>
  let { data } = $props();
</script>

{#if data.pedido}
  <p>Pedido: {data.pedido}</p>
{:else}
  <p>Não encontrado</p>
{/if}
<script>
  let { data = { pedido: null } } = $props();
</script>

{#if data.pedido}
  <p>Pedido: {data.pedido}</p>
{:else}
  <p>Não encontrado</p>
{/if}

Em produção, o load preenche data e o valor padrão quase nunca é usado. Ele existe para o caso de erro e para deixar o componente testável sozinho. É a mesma ideia de Ana deixando um pedido em branco no caderno: se a linha não vier preenchida, o caixa sabe o que escrever.

7. +server.js: o endpoint de API

Nem tudo é página. Um endereço pode responder JSON, texto ou arquivo, sem desenhar HTML. Para isso existe o +server.js, que exporta funções com o nome do método HTTP:

import { json } from '@sveltejs/kit';

export async function GET() {
  const pedidos = ['pão', 'leite'];
  return json({ pedidos, total: pedidos.length });
}

export async function POST({ request }) {
  const corpo = await request.json();
  return json({ recebido: corpo }, { status: 201 });
}

O endereço é o caminho da pasta: /api/pedidos. Um GET devolve a lista; um POST recebe o corpo e responde com 201. O json() do @sveltejs/kit monta a resposta com o cabeçalho certo — usar new Response(JSON.stringify(…)) também funciona, só dá mais trabalho.

Se você exportar GET e POST, o mesmo endereço atende os dois métodos. Se exportar só GET, um POST recebe 405. E há um detalhe que economiza uma pasta: dentro de src/routes/api/pedidos, você não pode ter +page.svelte e +server.js juntos no mesmo nível — o Kit recusa, porque o endereço não pode ser página e API ao mesmo tempo.

8. +error.svelte e as funções error() e redirect()

Quando um load falha, o Kit procura o +error.svelte mais próximo na árvore e mostra aquela tela. O arquivo recebe uma prop data com status e message:

<script>
  import { page } from '$app/state';
</script>

<h1>{page.status}</h1>
<p>{page.error?.message ?? 'Algo deu errado.'}</p>
<a href="/">Voltar para a padaria</a>

O page de $app/state é a fonte dos dados da requisição: endereço, parâmetros, status e erro. No +error.svelte ele é o jeito mais direto de ler o que aconteceu.

FunçãoVem deO que faz
error(404, 'Não encontrado')@sveltejs/kitinterrompe o load e mostra a tela de erro
redirect(303, '/login')@sveltejs/kitmanda o navegador para outro endereço
json(dados)@sveltejs/kitresponde JSON num endpoint
fail(400, { erro })@sveltejs/kitdevolve erro de formulário para a página
goto('/pedidos')$app/navigationnavega pelo código, no navegador

A diferença entre error() e fail() não é de gravidade, é de destino: error() mostra a tela de erro; fail() volta para a página do formulário com os dados que você mandou, para preencher as mensagens de validação.

9. hooks.server.js: o gancho antes de tudo

Alguns trabalhos precisam acontecer em toda requisição: ler o cookie de sessão, medir tempo, bloquear IP, colocar o usuário em locals. Para isso existe o hooks.server.js, na raiz do projeto (ao lado de src):

export async function handle({ event, resolve }) {
  const inicio = Date.now();
  const resposta = await resolve(event);
  console.log(event.url.pathname, Date.now() - inicio + 'ms');
  return resposta;
}

O handle recebe o evento e a função que resolve a requisição. Você pode fazer algo antes, chamar resolve(event) e fazer algo depois com a resposta. Se não chamar resolve, a requisição não termina — e o navegador fica esperando.

O uso mais comum no projeto da Ana é preencher event.locals: um objeto que vive durante aquela requisição e que os load podem ler. É assim que a sessão do usuário chega às páginas sem passar por parâmetro de um lado para o outro.

10. $app, $env e os nomes que o Kit reserva

O Kit expõe módulos com prefixo de cifrão. Eles não têm caminho de arquivo: são atalhos que o compilador resolve. Os que você vai usar primeiro:

MóduloO que temOnde pode rodar
$app/statepage com url, params, status, datanavegador e servidor
$app/navigationgoto, beforeNavigate, invalidatesó navegador
$app/environmentbrowser, dev, buildingos dois
$app/formsenhance, applyActionsó navegador
$app/pathsbase, resolveos dois
$env/static/publicvariáveis públicas, embutidas no buildos dois
$env/static/privatevariáveis privadassó servidor
$env/dynamic/publicpúblicas lidas em execuçãoos dois
$env/dynamic/privateprivadas lidas em execuçãosó servidor

A confusão mais comum é entre $env/static e $env/dynamic. O static é lido no momento do build e substituído no código: mudar a variável depois exige build novo. O dynamic é lido em execução: útil quando o valor muda no servidor sem rebuild. Em troca, o dynamic só funciona onde há servidor — não serve para site totalmente estático.

$app/stores ainda existe

A forma antiga, com page vindo de $app/stores e lido com $page, continua funcionando em muitos projetos. A forma nova, $app/state, expõe page como valor reativo direto. Em código novo, prefira $app/state.

11. Parâmetros, grupos e rotas opcionais

O nome da pasta também é sintaxe. Colchetes marcam pedaços variáveis do endereço; parênteses marcam grupos que não aparecem na URL.

PastaEndereçoPara que serve
pedidos//pedidosrota fixa
pedidos/[id]//pedidos/42parâmetro: params.id vale '42'
pedidos/[[id]]//pedidos e /pedidos/42parâmetro opcional
[[linguagem]]// e /ptidioma opcional
(admin)/painel//painelgrupo: layout e organização sem entrar na URL
[...caminho]//a/b/cresto do caminho, em params.caminho

Os parâmetros chegam pelo segundo argumento do load ({ params }) e, na página, por page.params de $app/state. Um grupo entre parênteses não muda a URL: ele permite dar um layout diferente a um conjunto de rotas sem criar um endereço novo.

Quando um arquivo de rota usa uma prop de forma errada, o erro é o mesmo de qualquer componente Svelte — porque o arquivo é um componente Svelte. Um exemplo real, com uma runa usada dentro de função:

Erro de compilação numa página de rota 
<script>
  function somar() {
    let { a } = $props();
    return a;
  }
</script>

<p>{somar()}</p>
Erro de compilação (linha 3, coluna 16): `$props()` can only be used at the top level of components as a variable declaration initializer

Ser +page.svelte não muda as regras de Svelte: $props() continua sendo do topo do componente. A mensagem aponta a linha, e o conserto é mover a chamada para fora da função.

12. Rodando o projeto Kit

Os comandos são os mesmos do projeto Svelte comum, com uma diferença interna: o Kit precisa analisar as rotas antes de servir. O servidor de desenvolvimento mostra isso na saída.

ana@notebook:~/loja$ npm run dev

> loja@0.0.1 dev
> vite dev

  VITE v8.4.0  ready in 640 ms

  ➜  Local:   http://localhost:5173/
  ➜  Network: use --host to expose

Duas coisas mudam em relação a um projeto Svelte puro. O comando por baixo é vite dev (e não vite), porque o Kit se instala como plugin do Vite. E o tempo de prontidão é maior: o servidor precisa ler a pasta routes antes de aceitar conexões. O endereço é o mesmo de sempre, http://localhost:5173/; se a porta estiver ocupada, o Vite escreve Port 5173 is in use, trying another one… e sobe na seguinte — a linha Local é a que vale.

ana@notebook:~/loja$ npm run preview

> loja@0.0.1 preview
> vite preview

  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose

O preview serve a build de produção, na porta 4173. É o último teste antes de publicar: se a navegação entre rotas funciona ali, funciona no ar — com uma ressalva, o adaptador. O projeto criado pelo CLI vem com @sveltejs/adapter-auto, que tenta descobrir a plataforma de publicação; num computador comum ele avisa que não detectou ambiente de produção.

Duas construções no mesmo comando: a de ssr (o HTML que sai do servidor) e a de cliente (o JavaScript que hidrata). "Analysing routes" é o Kit lendo a pasta routes e montando o mapa de endereços — se uma rota não aparece no site, a primeira coisa a conferir é se o arquivo tem o + no nome.

O aviso do adaptador não é erro: a build terminou ("done"). Ele só diz que, para publicar, você precisa escolher um adaptador — estático, Node, ou o da plataforma que for usar. Essa escolha é a última etapa antes do ar, e tem aula própria.

Resumo

  • Em src/routes, o caminho da pasta é o endereço da URL.
  • O + no nome marca arquivo especial do Kit; sem ele, o arquivo não é rota.
  • +page.svelte é a página; +layout.svelte é a moldura que recebe children.
  • +page.js roda nos dois lados; +page.server.js roda só no servidor e pode ter segredo.
  • O load devolve um objeto que chega na página como data e precisa ser serializável.
  • +server.js responde API com funções GET, POST e companhia, no endereço da pasta.
