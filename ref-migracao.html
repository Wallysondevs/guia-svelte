Svelte · Migrando do Svelte 4

A Ana trocou o forno a lenha por um forno elétrico. As receitas continuam as mesmas, mas três coisas mudaram: a temperatura agora é em graus exatos, o tempo tem timer e a porta não abre no meio. Ela não jogou o caderno fora: foi ajustando receita por receita, provando o pão de cada uma antes de passar para a seguinte. Migrar do Svelte 4 para o Svelte 5 é isso — não é reescrever o projeto, é ajustar arquivo por arquivo, conferindo cada um.

Você vai aprender
  • Por que o Svelte 5 mudou a forma de declarar estado e props.
  • export let → $props(), com o padrão no lugar certo.
  • $: → $derived para conta e $effect para efeito.
  • on:click → onclick, e o aviso que o compilador dá.
  • <slot> → children e snippets.
  • createEventDispatcher → callback como prop.
  • O que continua igual: stores, onMount, onDestroy, bind:.
  • <svelte:component> e <svelte:self> no mundo novo.
  • Como o migrador automático entra, e o que ele não resolve.
  • Uma ordem de migração que não para o projeto.

1. A ideia: o mesmo componente, com runas explícitas

No Svelte 4, a reatividade era implícita: uma variável comum era reativa, e o compilador descobria as dependências pelas atribuições. No Svelte 5, você marca o que é estado com $state, o que é conta com $derived e o que é prop com $props(). O ganho é previsibilidade: olhando o arquivo, você sabe o que muda a tela e o que não muda.

O custo é que o código antigo não é automaticamente código novo. O compilador do Svelte 5 aceita o modo antigo quando o arquivo não usa nenhuma runa — é o que permite migrar devagar, arquivo por arquivo. Assim que uma runa aparece no arquivo, o modo antigo é desligado naquele arquivo, e as construções legadas passam a dar erro.

$: y = x * 2let y = $derived(x * 2)sim, para conta
$: { efeito() }$effect(() => { efeito() })sim, para efeito
on:clickonclicksim, sem os dois-pontos
<slot />{@render children()}sim, com snippet

Uma observação que evita pânico: o Svelte 5 não removeu o modo antigo. Um projeto inteiro em Svelte 4 continua compilando e rodando. A migração é uma escolha de qualidade, não uma emergência — e pode ser feita componente por componente, na velocidade da equipe.

2. Passo 1 — props: export let vira $props()

No modo antigo, a prop era uma variável exportada. Compila, roda e continua funcionando enquanto o arquivo não tiver runas:

<script>
  export let titulo = 'Pedidos';
</script>

<h1>{titulo}</h1>
<h1>Pedidos</h1>

A versão nova faz a mesma coisa com uma linha diferente. O valor padrão vai à direita do sinal de igual, dentro da desestruturação:

<script>
  let { titulo = 'Pedidos' } = $props();
</script>

<h1>{titulo}</h1>
<h1>Pedidos</h1>

A saída é idêntica — e é isso que você quer numa migração: mudar a forma sem mudar o comportamento. A diferença aparece no dia em que o arquivo ganha uma runa: a partir daí, export let não é mais aceito.

let
a declaração que continua existindo. A prop agora é uma variável comum, criada a partir do objeto de props.
{ titulo = 'Pedidos' }
a desestruturação com padrão: o nome da prop e o valor usado quando ela não vem.
$props()
a runa que devolve todas as props recebidas. Só pode ser chamada no topo do componente.
...resto
o resto, quando existe: as props não nomeadas ficam nesse objeto, no lugar de $$restProps.
O erro que marca a virada

Este arquivo mistura prop antiga com estado novo. A presença de $state desliga o modo antigo.

<script>
  export let nome = 'Ana';
  let total = $state(0);
</script>

<p>{nome}: {total}</p>
Erro de compilação (linha 2, coluna 2): Cannot use `export let` in runes mode — use `$props()` instead

"Não pode usar export let no modo de runas — use $props()". A mensagem entrega o substituto, e a correção é uma linha.

Missão: o componente mistura prop antiga com $state e não compila. Migre a prop para $props() mantendo o padrão Pedidos.

<script>
  export let titulo = 'Pedidos';
  let total = $state(0);
</script>

<p>{titulo}: {total}</p>
<script>
  let { titulo = 'Pedidos' } = $props();
  let total = $state(0);
</script>

<p>{titulo}: {total}</p>

Duas armadilhas comuns nesse passo. A primeira: export let x sem valor padrão equivale a let { x } = $props(), sem = nenhum. A segunda: se o componente usava $$props ou $$restProps, o equivalente é let { ...resto } = $props(), e os nomes não vêm mais com prefixo de cifrão duplo.

3. Passo 2 — $: vira $derived ou $effect

A declaração reativa com $: fazia dois trabalhos: conta e efeito. No modo novo, os dois se separaram. Conta vira $derived; efeito vira $effect.

<script>
  let preco = 0.9;
  let qtd = 2;
  $: total = preco * qtd;
</script>

<p>Total: R$ {total.toFixed(2)}</p>
<p>Total: R$ 1.80</p>

No modo antigo, isso funciona e atualiza quando preco ou qtd mudam. A versão migrada troca a declaração por estado explícito e derivado:

<script>
  let preco = $state(0.9);
  let qtd = $state(2);
  let total = $derived(preco * qtd);
</script>

<p>Total: R$ {total.toFixed(2)}</p>
<p>Total: R$ 1.80</p>

Quando a conta tem laço ou if, a tradução é $derived.by(() => { … }). Quando o $: tinha efeito colateral — escrever no localStorage, chamar uma API, mexer no título —, a tradução é $effect, e não $derived: derivado é para valor, efeito é para ação.

O erro de quem mistura os dois mundos

Com runa no arquivo, $: não é aceito. A mensagem lista as duas alternativas.

<script>
  let preco = $state(0.9);
  let qtd = $state(2);
  $: total = preco * qtd;
</script>

<p>Total: R$ {total.toFixed(2)}</p>
Erro de compilação (linha 4, coluna 2): `$:` is not allowed in runes mode, use `$derived` or `$effect` instead

"$: não é permitido no modo de runas; use $derived ou $effect". A escolha entre os dois é a pergunta "isto é um valor ou uma ação?".

Missão: a declaração $: não compila mais. Troque por um valor derivado, mantendo o mesmo resultado na tela.

<script>
  let preco = $state(0.9);
  let qtd = $state(2);
  $: total = preco * qtd;
</script>

<p>Total: R$ {total.toFixed(2)}</p>
<script>
  let preco = $state(0.9);
  let qtd = $state(2);
  let total = $derived(preco * qtd);
</script>

<p>Total: R$ {total.toFixed(2)}</p>
Padrão antigoPadrão novoPor quê
$: y = x * 2let y = $derived(x * 2)é conta
$: { lista.length; console.log() }$effect(() => { console.log(lista.length) })é ação
$: if (x) { … }$effect(() => { if (x) { … } })ação condicional
$: { y = x } (atribuindo estado)elimine: calcule com $derivedestado não se sincroniza com estado

4. Passo 3 — eventos: on:click vira onclick

A mudança mais mecânica da migração. O evento deixa de ser diretiva e vira atributo comum, com o nome em minúsculas depois de on. O código antigo continua compilando, mas com aviso:

<script>
  let cliques = $state(0);
</script>

<button on:click={() => cliques++}>Cliques: {cliques}</button>
<button>Cliques: 0</button>
O aviso real do compilador

O componente funciona. O aviso aparece no terminal e no painel do Vite, com o código do problema.

event_directive_deprecated: Using `on:click` to listen to the click event is deprecated. Use the event attribute `onclick` instead

"Usar on:click para escutar o evento de clique está fora de moda; use o atributo onclick". A correção é apagar on: e escrever onclick={…}.

Três detalhes que aparecem na migração de projetos grandes. Primeiro: modificadores como on:click|preventDefault não existem no atributo novo — chame evento.preventDefault() dentro da função. Segundo: on:click|once também não existe; use uma variável de controle. Terceiro: eventos encaminhados de componente (on:salvar em um componente) eram eventos; agora são props de função, assunto da seção 6.

5. Passo 4 — slots: <slot /> vira {@render children()}

O slot recebia conteúdo de quem usa o componente. No Svelte 5, o conteúdo entre as tags chega como a prop children, que é um snippet — uma função que devolve marcação. Você a chama onde o slot ficava.

<div class="cartao">
  <slot>vazio</slot>
</div>
<div class="cartao">vazio</div>

O conteúdo de fallback do slot (o "vazio") aparece quando ninguém passa nada. A versão migrada precisa expressar o mesmo com children?.() e um {:else} de bloco:

<script>
  let { children } = $props();
</script>

<div class="cartao">
  {#if children}
    {@render children()}
  {:else}
    vazio
  {/if}
</div>
<div class="cartao">vazio</div>

Para slots nomeados (<slot name="topo" />), a tradução é um snippet por prop: o pai declara {#snippet topo()} … {/snippet} dentro da tag do filho, e o filho renderiza {@render topo?.()}. Slots com let: (slot props) viram snippets com parâmetros.

6. Passo 5 — eventos de componente: dispatcher vira callback

No Svelte 4, o filho criava um despachante e o pai escutava com on:. O código abaixo ainda compila no Svelte 5:

<script>
  import { createEventDispatcher } from 'svelte';
  const dispatch = createEventDispatcher();
</script>

<button onclick={() => dispatch('salvar', 1)}>salvar</button>
<button>salvar</button>

A versão nova dispensa a importação: o pai passa uma função, o filho chama. Fica mais direto e o fluxo aparece na leitura do pai:

<script>
  let { onSalvar = () => {} } = $props();
</script>

<button onclick={() => onSalvar(1)}>salvar</button>
<button>salvar</button>

O valor padrão () => {} evita o erro de chamar undefined quando o pai não passa a função. No pai, a chamada fica <Filho onSalvar={(n) => …} />, e o nome começa por on por convenção — não por obrigação do compilador.

7. Passo 6 — o que continua igual

Nem tudo mudou, e saber o que ficou poupa trabalho. Stores continuam iguais, com o cifrão na leitura. onMount e onDestroy continuam com o mesmo nome e o mesmo papel. bind: continua com a mesma sintaxe. tick, untrack e getContext seguem disponíveis.

<script>
  import { writable } from 'svelte/store';
  const contador = writable(0);
</script>

<p>{$contador}</p>
<p>0</p>

O que sai de cena são beforeUpdate e afterUpdate, que davam acesso ao momento do ciclo. O substituto é $effect (para depois do desenho) e $effect.pre (para antes). E os acessores de componente — export function foo() lido de fora com bind:this — continuam existindo, mas o caminho recomendado é passar callback por prop.

8. Passo 7 — <svelte:component> e <svelte:self>

No Svelte 5, componente é dinâmico por padrão: se a variável guarda um componente, a tag já resolve. O <svelte:component> deixou de ser necessário e ganhou aviso de fora de moda:

O aviso do <svelte:component> 
svelte_component_deprecated: `<svelte:component>` is deprecated in runes mode — components are dynamic by default

"Está fora de moda no modo de runas — componentes são dinâmicos por padrão". A correção é usar a variável direto como tag: <Atual />.

O aviso do <svelte:component> é fácil de resolver e ensina uma coisa: no Svelte 5 a tag já entende componente em variável, então aquele elemento especial só existia para contornar uma limitação que não existe mais. Se o seu projeto monta componentes por um mapa de rotas ou por um seletor de abas, a migração aqui é apagar o invólucro e usar <Atual /> direto.

Já o <svelte:self>, que renderizava o próprio componente para estruturas recursivas, só é aceito dentro de um bloco que possa repetir: {#if}, {#each}, {#snippet} ou slot. Fora disso, o compilador recusa:

<svelte:self> fora de bloco 
<svelte:self />
Erro de compilação (linha 1, coluna 0): `<svelte:self>` components can only exist inside `{#if}` blocks, `{#each}` blocks, `{#snippet}` blocks or slots passed to components

A mensagem lista os lugares aceitos. A forma mais comum é um {#if} que decide quando parar a recursão — sem condição de parada, o componente se desenha para sempre.

9. O migrador automático

O CLI oficial do Svelte tem uma tarefa de migração. A versão instalada no projeto da Ana responde assim:

ana@notebook:~/loja$ npx sv --version
1.7.1

O comando da migração é npx sv migrate svelte-5, e npx sv migrate --help lista as opções: --files para limitar a um conjunto de arquivos, --no-git-check para rodar com alterações pendentes e --no-install para não mexer nas dependências. Ele pergunta antes de mexer nos arquivos e trabalha pasta por pasta. Duas recomendações de quem já rodou esse tipo de ferramenta: faça commit antes, para poder comparar o antes e o depois, e rode com --files num punhado de arquivos primeiro.

O migrador resolve o mecânico: troca export let por $props(), converte $: simples, renomeia eventos. O que ele não resolve é o que exige decisão: se aquele $: era conta ou efeito, se aquele slot precisava de fallback, se aquele evento deveria virar callback com nome diferente. Essas escolhas continuam sendo suas — e é nelas que mora o valor da migração.

Uma pasta por vez

Comece pelos componentes-folha (os que ninguém importa), depois os do meio, deixe os pais para o fim. Cada arquivo migrado roda de novo no servidor de desenvolvimento, então você vê o erro na hora em que ele aparece, não três dias depois.

10. Uma ordem de migração que não para o projeto

Migrar tudo de uma vez funciona num projeto de dez arquivos e vira crise num de duzentos. A ordem abaixo mantém o site no ar durante o processo:

1. Atualize a dependência e rode os testes. Sem mudar código, só trocando a versão. O modo antigo continua valendo, e você descobre o que quebrou antes de misturar as duas coisas.

2. Migre os componentes sem estado. Botões, cartões, ícones. São os de menor risco e servem de treino para o time.

3. Migre os componentes com estado local. Aqui aparece a decisão $derived × $effect, e é onde o time aprende de verdade.

4. Migre a comunicação entre componentes. Slots e dispatcher viram children e callbacks. Esta etapa muda a API dos componentes e é a que exige revisar quem os usa.

5. Apague o que sobrar do modo antigo. Depois que ninguém usa export let nem on:, o projeto é Svelte 5 de verdade.

Em cada etapa, rode o build e abra as telas principais. Migração não é refatoração: o objetivo é o comportamento idêntico com a sintaxe nova. Se a tela mudou, o problema é seu, não do compilador — e é mais fácil achar com poucos arquivos alterados do que com duzentos.

11. Quando dá errado

Os quatro tropeços mais comuns de quem migra, com a mensagem real do compilador. Todos acontecem no mesmo ponto: o arquivo ganhou uma runa e o resto dele ainda é do Svelte 4.

Há um erro que não tem mensagem: o componente migra, compila, e a tela deixa de atualizar. Quase sempre é uma variável que era reativa no modo antigo e virou comum no modo novo — o aviso non_reactive_update aparece no terminal, e o conserto é $state. Se o aviso não aparecer, confira se o arquivo realmente entrou em modo de runas: basta uma runa em qualquer lugar do script.

Resumo

  • O Svelte 5 decide o modo por arquivo: sem runas, vale o modo antigo; com uma runa, vale o novo.
  • export let vira let { x = padrão } = $props(); $$props vira ...props.
  • $: de conta vira $derived (ou $derived.by com bloco); de ação vira $effect.
  • on:click vira onclick; modificadores como |preventDefault não existem no atributo.
  • <slot> vira children com {@render children()}; slots nomeados viram snippets por prop.
  • createEventDispatcher vira callback como prop, com padrão () => {}.
  • Stores, onMount, onDestroy, tick e bind: continuam iguais.
  • beforeUpdate/afterUpdate viram $effect.pre/$effect.
  • <svelte:component> está fora de moda; <svelte:self> só dentro de bloco.
  • npx sv migrate svelte-5 faz o mecânico; as decisões continuam suas. Migre por etapa e rode o build a cada uma.
