Svelte · render() no Servidor

A Ana descobriu que metade dos clientes abre o site da padaria no celular, na rua, com internet ruim. Hoje a página chega vazia e só depois de baixar e rodar o JavaScript é que o pão aparece — nos primeiros segundos, a pessoa vê uma tela em branco. Existe outro caminho: montar o HTML na cozinha (o servidor) e entregar pronto, deixando o navegador só para o que precisa de interação. Quem faz esse trabalho é a função render(), e é dela que trata esta aula.

  • Os três erros reais desta aula, com a mensagem do renderizador.

1. A ideia: cozinha e mesa

Existem dois jeitos de servir um jantar. No primeiro, a cozinha prepara o prato e o garçom leva pronto; o cliente só come. No segundo, a cozinha manda os ingredientes e o cliente monta o prato na mesa. O primeiro é mais rápido para quem tem fome e não quer pensar; o segundo é mais flexível, mas exige que o cliente saiba cozinhar — ou, no caso da web, que o navegador baixe e execute o programa antes de mostrar qualquer coisa.

Renderizar no servidor é o primeiro jeito. O servidor roda o componente, produz uma string de HTML e manda essa string na resposta. O navegador recebe texto pronto e desenha na hora, mesmo antes de o JavaScript chegar. Depois, quando o JavaScript chega, o componente "ganha vida" — botões passam a responder, o estado começa a existir. Esse segundo momento se chama hydration (hidratação): o HTML seco ganha comportamento.

O ganho é a primeira impressão: a pessoa vê o conteúdo antes de o programa carregar. O custo é que o mesmo componente é desenhado duas vezes — uma no servidor, outra no navegador, para conferir que o HTML bate — e que o servidor precisa saber executar o componente, o que significa ter Node rodando atrás da página.

O vocabulário: SSR é renderização no servidor; CSR é renderização no cliente; hydration é o momento em que o HTML pronto ganha comportamento; e string é o texto que o servidor devolve. Quatro palavras que separam "a página aparece rápido" de "a página aparece quando o JavaScript termina".

2. render(): o componente vira texto

A função vem de svelte/server, um caminho separado do pacote principal porque ela só existe no servidor. Ela recebe o componente e um objeto de opções, e devolve dois pedaços: o body, com o conteúdo da tela, e o head, com o que o componente pediu para colocar na cabeça do documento.

<script>
  let { nome = 'Ana', cidade = 'São Paulo' } = $props();
</script>

<svelte:head>
  <title>Vitrine da padaria</title>
  <meta name="description" content="Pães frescos todos os dias" />
</svelte:head>

<h1>Olá, {nome}</h1>
<p>Pães frescos em {cidade}.</p>

O corpo que o renderizador devolve é este. O head vem no mesmo objeto, como a próxima seção mostra — e a seção 8 traz o texto cru que sai do Node, com os dois pedaços:

<h1>Olá, Ana</h1> <p>Pães frescos em São Paulo.</p>
render(App, { props })
recebe o componente e as props. Devolve um objeto com head e body, os dois como texto.
<svelte:head>
o pedaço do componente que escreve no cabeçalho do documento: título, descrição, endereço canônico.
let { nome = 'Ana' } = $props()
as props com valor padrão. No servidor, quem não manda usa o padrão — igual ao navegador.
head
o que vai dentro de <head>: aqui, o title e a meta de descrição.

O HTML do body vem com comentários estranhos, do tipo <!--[--> e <!--]-->. Eles são âncoras internas do Svelte: marcam onde começa e onde termina um bloco, para a hydration saber o que aproveitar. Não atrapalham nada e não aparecem na tela; o pre.out desta aula usa a versão sem eles, e a seção 8 mostra o texto cru que sai do Node.

3. O head separado do body

Quem monta a página final junta os dois pedaços num documento. O head vai para dentro da tag <head>; o body vai para dentro da tag <body>. Essa separação é o que permite o servidor entregar um documento completo, com título e descrição, sem que ninguém escreva o título à mão na página.

O head também carrega o selo do componente, o mesmo svelte-xxxxx que aparece no CSS escopado. É por isso que o título e a descrição de um componente não se misturam com os de outro: cada um escreve o seu pedaço, e o Svelte sabe de quem é cada linha.

import { render } from 'svelte/server';
import App from './App.svelte';

const { head, body } = render(App, { props: { nome: 'Ana' } });

const pagina = `<!doctype html>
<html lang="pt-BR">
<head>${head}</head>
<body><div id="app">${body}</div></body>
</html>`;

Esse é o desenho geral de qualquer SSR: um molde de página com dois buracos, um para o head e outro para o body. O resto do arquivo é o mesmo HTML de sempre, com a div#app que a hydration vai usar como alvo.

4. O que não roda no servidor

O servidor não tem tela, não tem janela e não tem navegador. O que existe é o Node: memória, arquivos, rede. Por isso o Svelte desliga, durante o render(), tudo o que depende do navegador: efeitos não rodam, onMount não é chamado, e as APIs como window, document, localStorage e matchMedia não existem.

<script>
  import { onMount } from 'svelte';

  let visitas = $state(0);

  $effect(() => {
    visitas += 1;
  });

  onMount(() => {
    console.log('montou no navegador');
  });
</script>

<p>visitas: {visitas}</p>

O componente tem um efeito que incrementa o contador de visitas e um onMount que escreve no console. O HTML devolvido mostra o estado inicial, sem nenhum dos dois:

<p>visitas: 0</p>
let visitas = $state(0)
o estado começa em zero. No servidor ele fica em zero, porque ninguém interage com a página.
$effect(() => …)
não roda no servidor. Efeito é para sincronizar com algo de fora, e no servidor não há de fora.
onMount(() => …)
também não roda. O nome já diz: é para quando o componente monta no navegador.
visitas: {visitas}
o texto sai com o valor inicial. É esse número que a pessoa vê antes de o JavaScript chegar.

Missão: o parágrafo está escrito à mão com "só HTML" e nunca muda. Use o estado e o efeito, que já existem no arquivo, para mostrar interativo depois que o componente montar.

<script>
  let montado = $state(false);

  $effect(() => {
    montado = true;
  });
</script>

<p>só HTML</p>
<script>
  let montado = $state(false);

  $effect(() => {
    montado = true;
  });
</script>

<p>{montado ? 'interativo' : 'só HTML'}</p>

Esse é o motivo pelo qual um componente que mostra "carregando" precisa de cuidado: no servidor ele desenha "carregando" e é isso que a pessoa vê primeiro. Se o efeito que busca os dados demora, a pessoa fica com o texto de espera na tela — e é exatamente o comportamento correto, desde que o texto seja honesto.

5. render, mount e hydrate

As três funções fazem coisas diferentes, e confundi-las é a origem de metade dos problemas de SSR. O render só produz texto: não cria elemento, não liga evento, não guarda estado. O mount cria tudo do zero no navegador. O hydrate aproveita o texto que já está na página e liga o comportamento a ele.

FunçãoOnde rodaDevolvePara que serve
renderservidor (Node){ head, body }gerar o HTML da resposta
mountnavegadora instânciacriar a tela do zero
hydratenavegadora instâncialigar comportamento ao HTML pronto

O par certo é sempre render no servidor com hydrate no navegador. Misturar — render com mount — funciona, mas joga fora o HTML do servidor e faz a página piscar: o navegador apaga o que veio pronto e desenha de novo.

A aula mount() e flushSync mostra o lado do navegador com calma; aqui o assunto é o lado da cozinha.

6. Texto escapado: por que <b> não vira negrito

Quando o Svelte escreve um valor dentro de uma tag, ele escapa os caracteres que poderiam virar marcação. O menor que vira &lt;, e o navegador mostra o sinal em vez de interpretar como começo de tag. É uma proteção: sem ela, qualquer texto vindo de fora poderia injetar HTML na sua página.

<script>
  let aviso = '<b>Pão quentinho</b> às 7h';
</script>

<p>{aviso}</p>

O HTML devolvido mostra o sinal escapado no começo de cada tag — e o maior que fica como está, porque sozinho ele não abre nada:

<p>&lt;b>Pão quentinho&lt;/b> às 7h</p>

Missão: o aviso é interpretado como HTML e o negrito aparece, escondendo as tags. Faça a tela mostrar o texto literal <b>Pão quentinho</b>, com os sinais visíveis.

<script>
  let aviso = '<b>Pão quentinho</b>';
</script>

<p>{@html aviso}</p>
<script>
  let aviso = '<b>Pão quentinho</b>';
</script>

<p>{aviso}</p>
{@html} é uma porta aberta

A tag {@html texto} insere o texto sem escapar. Ela existe para conteúdo que você mesmo gera e controla — um trecho de marcação vindo do seu banco, um ícone. Com texto digitado por outra pessoa, ela é um buraco de segurança: um script escondido no texto roda na página de quem lê. Se a origem não é confiável, use {texto} e deixe o escape acontecer.

7. Props no servidor

Props funcionam no servidor do mesmo jeito que no navegador, com uma diferença de responsabilidade: quem chama o render decide os valores. É o servidor que sabe qual produto foi pedido, qual é o nome de quem entrou e qual idioma usar — e é ele que passa isso para o componente.

<script>
  let { nome = 'Ana', cidade = 'São Paulo' } = $props();
</script>

<p>Olá, {nome} — entregamos em {cidade}.</p>
<p>Olá, Ana — entregamos em São Paulo.</p>

Missão: o componente espera a prop nome e mostra "Olá, !". Dê um valor padrão para a prop, como o servidor faria quando não recebe o dado, e mostre Olá, Ana!.

<script>
  let { nome } = $props();
</script>

<p>Olá, {nome}!</p>
<script>
  let { nome = 'Ana' } = $props();
</script>

<p>Olá, {nome}!</p>

Valor padrão em prop não é preguiça: é contrato. O componente declara o que aceita e o que acontece quando o dado falta. Num SSR isso importa mais, porque o servidor pode não ter o dado na hora e a página precisa sair mesmo assim, sem quebrar.

8. O caminho completo, com Vite

Para rodar o SSR num projeto Vite, existem duas construções: a do cliente, que é a de sempre, e uma segunda, com a opção --ssr, que gera um arquivo para o Node executar. O comando abaixo é real, rodado no projeto da Ana com um arquivo de entrada que chama o render:

ana@notebook:~/loja$ npx vite build --ssr src/entry-server.js --outDir dist-ssr
vite v7.3.8 building ssr environment for production...
transforming...
✓ 54 modules transformed.
rendering chunks...
dist-ssr/entry-server.js  37.75 kB
✓ built in 450ms

Repare no número de módulos: 54, bem menos que os 111 da construção do cliente. O motivo é que o SSR não precisa do runtime de interface no navegador — só do código que produz texto. O arquivo gerado é um módulo Node, e rodar é executar:

ana@notebook:~/loja$ node dist-ssr/entry-server.js
HEAD: Vitrine da padaria
BODY: 
Olá, Ana
 
Pães frescos em São Paulo.

É esse texto que o servidor manda na resposta. O head traz o título e a descrição com o selo do componente; o body traz a tela pronta, com os comentários-âncora que a hydration usa. O console.log é só para ver o resultado: num servidor de verdade, esse texto entraria no molde da seção 3 e viraria a resposta HTTP.

Depois de responder, o navegador baixa a construção do cliente e chama hydrate no mesmo alvo. A partir daí, os botões respondem, o estado existe e a página é a mesma de antes — só que já nasceu com conteúdo.

9. Quando dá errado

As três mensagens abaixo saíram do renderizador desta versão, copiadas como estão. Todas são erros de SSR: o componente funciona no navegador e quebra no servidor.

Erro 1 — localStorage no servidor

Guardar o carrinho na memória do navegador é comum. Fazer isso no corpo do <script> significa fazer também no servidor, onde essa memória não existe.

<script>
  const salvo = localStorage.getItem('carrinho') ?? '';
</script>

<p>{salvo || 'carrinho vazio'}</p>
Erro ao renderizar: localStorage is not defined

"localStorage is not defined" quer dizer "esse nome não existe aqui". A correção é ler a memória dentro de um onMount ou de um $effect, com um valor inicial que sirva para o servidor.

Erro 2 — matchMedia no servidor

Descobrir o tema do sistema com matchMedia é outra API de navegador. No servidor, ela não existe — e o componente nem chega a desenhar.

<script>
  const resposta = await fetch('/api/produtos');
  const produtos = await resposta.json();
</script>

<p>{produtos.length} produtos</p>
Erro de compilação (linha 2, coluna 19): Cannot use `await` in deriveds and template expressions, or at the top level of a component, unless the `experimental.async` compiler option is `true`

A tradução é a mesma: nome desconhecido no servidor. A saída é usar um valor padrão e ajustar no navegador depois da montagem, aceitando que a primeira pintura pode vir no tema claro.

Erro 3 — componente que lança no desenho

Um erro de dado — uma lista que devia existir e não existe — derruba a renderização do servidor. Não há boundary que salve aqui: o svelte:boundary atua no navegador.

<script>
  const resposta = {};
</script>

<p>{resposta.produtos.length} produtos</p>
Erro ao renderizar: Cannot read properties of undefined (reading 'length')

A mensagem é o texto do erro que o componente lançou. No servidor, o tratamento é da camada de cima: responder 500, registrar o problema e mostrar uma página de erro. O componente deve validar o dado antes de desenhar.

10. O custo do SSR

SSR não é de graça. O servidor passa a executar o componente a cada requisição, o que consome processador; o componente é desenhado duas vezes, o que dobra a chance de divergência; e o código precisa ficar atento a tudo o que só existe no navegador. Em troca, a primeira pintura chega antes, e quem tem internet ruim agradece.

Vale a pena quando o conteúdo importa para quem chega — uma vitrine, uma notícia, um catálogo. Vale menos quando a página é uma ferramenta que só funciona depois de o JavaScript carregar de qualquer jeito. A decisão é de produto, não de gosto.

Num projeto com SvelteKit, todo esse caminho já está montado: o framework chama o render, junta com o molde e liga a hydration. Num projeto Vite puro, como o da Ana, você monta as peças — e é por isso que esta aula existe.

Exercícios

1. O que render(App) devolve?

2. Por que $effect e onMount não rodam no servidor?

3. Qual par de funções combina SSR com navegador?

Complete o código

import { } from 'svelte/server';
import App from './App.svelte';

const { head, body } = render(App, { props: { nome: 'Ana' } });

Resumo

  • SSR desenha o componente no servidor e entrega HTML pronto; o navegador só hidrata.
  • render(App, { props }) vem de svelte/server e devolve { head, body }.
  • head e body vão para lugares diferentes do documento final.
  • No servidor não existem window, document, localStorage nem matchMedia.
  • $effect e onMount não rodam no servidor; o HTML sai com o estado inicial.
  • O par correto é render no servidor e hydrate no navegador.
  • Texto é escapado por padrão; {@html} desliga o escape e exige confiança na origem.
  • vite build --ssr gera o arquivo Node que executa o render.
  • SSR custa processador no servidor e atenção dobrada ao código; o ganho é a primeira pintura.
