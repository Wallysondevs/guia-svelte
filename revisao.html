1. O mapa do Nível 2

O nível 2 não ensinou sintaxe nova: ensinou a usar bem a sintaxe do nível 1. Cada grupo de aulas respondeu a uma pergunta que só aparece quando o projeto cresce.

GrupoPergunta que respondeuPeça central
Ciclo de vidao que roda quando o componente nasce e morre?onMount, tick, $effect
Composiçãocomo um componente conversa com outro?$props, snippets, context, stores
Recursos avançadoscomo lidar com listas grandes e trabalho repetido?use:, debounce, paginação
Qualidadecomo o projeto continua legível e confiável?pastas, nomes, testes, medição, refatoração

Cada grupo desses tem uma aula de “quando dá errado”, e vale reler a mensagem antes de reler a explicação. A mensagem é a mesma que você vai encontrar no projeto; a explicação, não.

Existe um jeito rápido de saber se o nível está firme: pegue um componente seu e tente explicar, em voz alta, o que cada variável guarda e quem a atualiza. Se você conseguir sem “mais ou menos”, está pronto. Se travar em alguma, é ali que falta revisão.

Se algum desses grupos ficou nebuloso, não siga para o nível 3: o SvelteKit multiplica os conceitos. Rotas e dados de servidor são fáceis quando você já sabe o que é estado, propriedade e derivado — e são confusos quando não sabe.

2. O componente que resume o nível

Este componente pequeno usa quatro ideias do nível ao mesmo tempo: propriedade com valor padrão, estado em lista, derivado e laço com formatação.

<script>
  let { titulo = 'Vitrine da Ana' } = $props();
  let precos = $state([0.9, 2.5, 4]);
  let total = $derived(precos.reduce((soma, p) => soma + p, 0));
</script>

<h1>{titulo}</h1>

<ul>
  {#each precos as preco}
    <li>R$ {preco.toFixed(2)}</li>
  {/each}
</ul>

<p>Total: R$ {total.toFixed(2)}</p>
<h1>Vitrine da Ana</h1> <ul><li>R$ 0.90</li><li>R$ 2.50</li><li>R$ 4.00</li></ul> <p>Total: R$ 7.40</p>
let { titulo = 'Vitrine da Ana' } = $props()
propriedade com valor padrão. Sem padrão, a demonstração mostraria um título vazio.
let precos = $state([...])
estado: a lista muda durante o uso e a tela acompanha.
let total = $derived(...)
derivado: não guarda um segundo valor, calcula a partir de precos.
{#each precos as preco}
laço: um <li> por preço, com a formatação de dinheiro em um lugar só.
R$ {total.toFixed(2)}
formatação na saída. O valor guardado continua número; o que aparece na tela é texto.

Se você conseguir explicar cada uma dessas cinco linhas para alguém que nunca programou, o nível 2 está consolidado. Se alguma delas exigir “mais ou menos isso”, volte à aula correspondente antes de seguir.

3. Estado, derivado e a tentação do $effect

A distinção que mais rende no dia a dia é entre o que você guarda e o que você calcula. Guarde só o que vem de fora ou do usuário; calcule todo o resto.

PerguntaSe simSe não
o valor vem do usuário ou de fora?$stateprovavelmente $derived
dá para calcular a partir de outro valor?$derived$state
precisa fazer algo quando o valor muda?$effect, com cuidadonada
esse “algo” é só calcular outro valor?$derived, não $effect—

Uma pergunta de controle que funciona bem: “se eu apagar esta variável e calcular o valor no lugar onde ele é usado, alguma coisa quebra?”. Se a resposta é não, ela não devia existir como estado. Estado a mais é a fonte mais comum de tela desatualizada.

O $effect é a ferramenta mais poderosa e a mais fácil de usar errado. Ele serve para conversar com o mundo de fora — buscar dado, escrever no localStorage, medir um elemento. Para manter duas variáveis iguais, ele é sempre a resposta errada: vira laço, fica fora de sincronia ou os dois problemas juntos.

4. Filtrar uma lista com busca

Filtro é o exemplo que junta bind:value, $derived e {#each}. O campo de busca escreve no estado; o derivado recalcula a lista visível; o laço desenha o resultado.

Missão: o campo de busca guarda o texto digitado, mas a lista ignora. Faça a lista mostrar só os produtos cujo nome contém o que foi digitado, sem diferenciar maiúscula de minúscula.

<script>
  let busca = $state('');
  let produtos = $state([{ nome: 'Pão francês' }, { nome: 'Sonho' }]);
  let visiveis = produtos;
</script>

<input aria-label="Buscar" bind:value={busca} />
{#each visiveis as produto}
  <p>{produto.nome}</p>
{/each}
<script>
  let busca = $state('');
  let produtos = $state([{ nome: 'Pão francês' }, { nome: 'Sonho' }]);
  let visiveis = $derived(
    produtos.filter((p) => p.nome.toLowerCase().includes(busca.toLowerCase()))
  );
</script>

<input aria-label="Buscar" bind:value={busca} />
{#each visiveis as produto}
  <p>{produto.nome}</p>
{/each}

A solução tem duas partes que se explicam sozinhas. toLowerCase() nas duas pontas faz a busca ignorar maiúscula. includes pergunta se o nome contém o texto, em vez de exigir igualdade — buscar “Son” encontra “Sonho”.

Vale reparar no que o derivado não faz: ele não guarda o resultado, não dispara efeito nenhum e não muda a lista original. Ele apenas descreve uma conta que o Svelte refaz quando a busca muda — e só quando a busca muda. É esse detalhe que faz o filtro parecer instantâneo mesmo em listas grandes.

Repare que produtos continua com os dois itens: o filtro não apaga dado, só escolhe o que desenhar. Essa separação é a razão de existir um derivado separado — a lista original precisa continuar inteira para quando a busca ficar vazia.

5. Snippet com parâmetro

Snippet é um pedaço de HTML com nome, e aceita parâmetros como uma função. A chamada acontece com {@render}:

Missão: o snippet espera a posição de cada item, e a chamada passa só o nome — a lista sai sem número. Passe também a posição, começando em 1.

<script>
  let itens = $state(['Pão', 'Sonho']);
</script>

{#snippet item(nome, posicao)}
  <li>{posicao}. {nome}</li>
{/snippet}

<ul>
  {#each itens as nome}
    {@render item(nome)}
  {/each}
</ul>
<script>
  let itens = $state(['Pão', 'Sonho']);
</script>

{#snippet item(nome, posicao)}
  <li>{posicao}. {nome}</li>
{/snippet}

<ul>
  {#each itens as nome, i}
    {@render item(nome, i + 1)}
  {/each}
</ul>

O {#each} aceita um segundo nome depois do item, e ele recebe a posição a partir de zero — por isso o i + 1. Parâmetro que não é passado vale undefined, e o Svelte desenha undefined como nada: a lista saiu com o ponto e o nome, sem o número.

6. A lista vazia precisa de recado

Uma lista sem itens desenha nada. Para quem olha, a tela parece quebrada. A mensagem de lista vazia é parte do componente, não enfeite:

Missão: o componente abre com a lista vazia e nenhuma explicação. Mostre Nenhum item quando não houver nada na lista.

<script>
  let itens = $state([]);
</script>

<button onclick={() => (itens = [...itens, 'Pão'])}>Adicionar</button>
{#each itens as item}
  <p>{item}</p>
{/each}
<script>
  let itens = $state([]);
</script>

<button onclick={() => (itens = [...itens, 'Pão'])}>Adicionar</button>

{#if itens.length === 0}
  <p>Nenhum item</p>
{/if}

{#each itens as item}
  <p>{item}</p>
{/each}

A condição é itens.length === 0 — “o tamanho da lista é zero”. Poderia ser !itens.length, que é mais curto e menos legível para quem começa. Prefira a versão que se lê em voz alta.

7. Ciclo de vida em uma página

Três funções cobrem quase todo o ciclo de vida. Elas respondem a “quando rodar” e “quando limpar”:

FunçãoQuando rodaPara que serve
onMountuma vez, depois de montarbuscar dado, medir elemento, iniciar algo externo
$effectdepois de cada mudança de estado que ele lêconversar com o mundo de fora
tickdepois que a tela foi atualizadamedir ou focar algo que acabou de aparecer
untrackdentro de um efeitoler um valor sem virar dependência

A regra que evita a maioria dos problemas: onMount roda uma vez e não volta. Se o seu código precisa rodar de novo quando um valor muda, o lugar é $effect — e se o que ele faz é calcular outra coisa, o lugar é $derived.

Uma consequência prática desse desenho: em Svelte puro, onMount roda no navegador e pode usar window e document à vontade. Se o mesmo componente for desenhado no servidor, o onMount simplesmente não roda lá — e é por isso que buscar dado dentro dele é seguro.

Lembre também de limpar o que criou: um setInterval, um ouvinte de teclado, uma conexão. O retorno do onMount (ou do $effect) é a função de limpeza, chamada quando o componente sai da tela. Sem ela, o intervalo continua rodando depois que a tela sumiu.

8. Como os dados atravessam componentes

Quatro caminhos, do mais simples ao mais amplo. Escolha o menor que resolve:

CaminhoAlcanceQuando usar
$propspai para filhoum componente precisa de um dado do pai
Snippet / childrenpai dentro do filhoo pai quer mandar pedaço de tela
setContext / getContextuma árvore de componentesvários níveis precisam do mesmo dado
Storeo projeto inteiroestado global: sessão, carrinho, tema

Existe um teste simples para escolher: conte quantos componentes intermediários precisariam repassar o dado. Zero ou um: propriedade. Dois ou três: comece a pensar em context. A árvore inteira: store. O número é uma aproximação, mas evita a decisão por hábito.

A ordem importa porque cada passo aumenta o acoplamento. Propriedade é explícita: quem lê o componente vê o que ele recebe. Store é implícita: qualquer arquivo pode importar e mudar. Comece explícito e só suba de nível quando o “passar de mão em mão” ficar insuportável.

Dois arquivos, quatro casos, tudo verde. Note que um teste de componente custa 140 ms e um de módulo custa 5 ms: a diferença é o DOM de mentira sendo montado. Essa proporção é a dica de onde investir esforço — muitos testes de módulo, poucos de componente, cada um cobrindo o que só ele consegue cobrir.

Uma coisa que os testes do projeto ainda não cobrem: o formulário de pedido. Ele tem regra de negócio (aceite obrigatório, quantidade mínima) e é justamente onde um teste de componente faria diferença. Fica como tarefa para o próximo mês.

Repare também na linha do ambiente: ele consumiu 70% do tempo. O relatório não está reclamando; está dizendo onde o tempo vai. Medir é isso: transformar “parece lento” em um número que se pode acompanhar.

11. O que muda quando entra o SvelteKit

O SvelteKit é a camada que transforma componentes em um site com endereços, dados de servidor e publicação. Ele não substitui nada do que você aprendeu: usa tudo. A diferença é que agora existe um lugar onde o código roda antes de chegar ao navegador.

No Svelte puroNo SvelteKit
src/App.svelte montado pelo main.jsuma página por arquivo: src/routes/+page.svelte
você importa o componente na mãoa rota é o arquivo; o endereço é a pasta
dado buscado no navegador com onMountdado buscado no +page.js ou no servidor
estado global em store ou contextstore, mais o estado de sessão do servidor
npm run build gera dist/o adaptador decide onde o site vai rodar

O conceito novo é o servidor: parte do código roda antes de a página chegar ao navegador, e lá não existe window nem document. É por isso que a aula de “o que roda no servidor” vem antes de SvelteKit — componente que toca o navegador no topo do script quebra na renderização do servidor.

Fora isso, o dia a dia continua igual: $state para o que muda, $derived para o que se calcula, $props para o que vem de fora, teste para o que precisa continuar valendo. Quem chega ao SvelteKit com esses quatro conceitos firmes aprende rotas em uma tarde.

12. Quando dá errado

Três erros que voltam sempre, um de cada grupo do nível. As mensagens são as reais desta versão.

Erro 1 — propriedade que não chega

Um componente recebe uma lista e a usa sem valor padrão. Se o pai não passar nada, o valor é undefined e o primeiro acesso quebra.

<script>
  let { itens } = $props();
</script>

<p>{itens.length} itens</p>
Cannot read properties of undefined (reading 'length')

“Não consigo ler propriedades de undefined (lendo ‘length’)”. O conserto é valor padrão: let { itens = [] } = $props(). Com ele, o componente funciona mesmo quando o pai esquece — e a tela mostra “0 itens” em vez de quebrar.

Erro 2 — tag movida sem o fechamento

Ao reorganizar o HTML, o fechamento do <article> ficou para trás. O compilador aponta a tag que abriu e não terminou.

<script>
  let preco = $state(2.5);
</script>

<article>
  <h2>Sonho</h2>
  <p>R$ {preco.toFixed(2)}</p>
Erro de compilação (linha 5, coluna 0): `<article>` was left open

“<article> ficou aberto”. Mover HTML exige mover o par: abrir e fechar juntos, ou o compilador não consegue montar a árvore.

Erro 3 — o mesmo nome importado duas vezes

Dois cartões diferentes, ambos chamados Cartao, importados no mesmo arquivo. O segundo import tenta criar um nome que já existe.

<script>
  import Cartao from './lib/Cartao.svelte';
  import Cartao from './lib/CartaoGrande.svelte';
</script>

<h1>Loja da Ana</h1>
<Cartao titulo="Pão francês" preco={0.9} />
Erro de compilação (linha 3, coluna 9): Identifier 'Cartao' has already been declared

“O identificador ‘Cartao’ já foi declarado”, na linha 3, coluna 9. A saída é renomear na importação: import CartaoVitrine from … e usar <CartaoVitrine />.
