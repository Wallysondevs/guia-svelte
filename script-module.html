Svelte · Estado Compartilhado

A Ana comprou um caderno novo para a padaria e escreveu na capa: "abre às seis". O caderno fica na prateleira, e todo funcionário que precisa do horário olha a capa — não existe uma capa por pessoa. O arquivo .svelte tem um lugar igual a essa capa: o bloco <script module>, que roda uma vez para o arquivo inteiro, enquanto o <script> comum roda uma vez por componente na tela. Esta aula é sobre essa diferença — e sobre o estado que vive na capa do caderno em vez de viver na mão de cada um.

Você vai aprender

  • A diferença entre o script de módulo e o script da instância.
  • Exportar constantes e funções do módulo para outros arquivos.
  • Guardar estado no módulo com $state — e o que muda com isso.
  • Usar $derived no módulo para uma conta compartilhada.
  • Por que todas as instâncias do arquivo leem o mesmo valor.
  • O que não pode morar no módulo: $props, contexto e DOM.
  • Como o módulo aparece no terminal e no build do Vite.
  • Os três erros reais desta aula, com a mensagem do compilador.
  • Quando o estado de módulo é a resposta certa e quando é armadilha.

1. A ideia: o caderno do arquivo, não da pessoa

Um componente pode aparecer várias vezes na tela. O placar da vitrine, o cartão de cada produto, o aviso de cada pedido: todos são o mesmo arquivo montado várias vezes. Cada montagem é uma instância, com as suas próprias variáveis. Se o cartão guarda "quantas vezes eu fui clicado", cada cartão tem o seu número — e isso quase sempre é o que você quer.

Mas às vezes o número não é do cartão: é do arquivo. "Quantos cartões existem", "qual é o horário de abertura da loja", "quantas visitas o site recebeu nesta sessão". Esse tipo de valor não pertence a nenhuma instância; pertence ao arquivo. No Svelte, o lugar dele é o bloco <script module>.

A diferença é a mesma entre o caderno na prateleira e a agenda no bolso. A agenda é sua: cada funcionário tem a sua, e escrever nela não muda a do colega. O caderno na prateleira é de todos: quem escreve na capa muda o que todo mundo lê. O bloco de módulo é a prateleira; o script comum é o bolso.

E existe uma consequência que surpreende no começo: o código do módulo roda antes de qualquer componente existir, uma vez só. Se você colocar um console.log lá, ele aparece uma vez, mesmo que a tela mostre dez cartões. No script comum, apareceria dez vezes.

A ordem no arquivo não importa para o JavaScript — os dois convivem no mesmo módulo compilado —, mas o guia escreve o bloco de módulo primeiro, porque é ele que roda primeiro.

3. O bloco <script module>

Para criar um bloco de módulo, basta escrever module depois da palavra script:

<script module>
  let cliques = $state(0);
</script>

<p>Cliques: {cliques}</p>
<button onclick={() => cliques++}>+1</button>
<p>Cliques: 0</p> <button>+1</button>
<script module>
o bloco que roda uma vez por arquivo, antes de qualquer instância. Não é o mesmo que <script>: os dois podem existir no mesmo arquivo.
let cliques
a variável vive no módulo compilado, não na instância. Todas as instâncias do componente leem a mesma.
$state(0)
a runa continua valendo aqui: o valor é reativo e a tela acompanha quando ele muda.
{cliques}
no HTML, o nome do módulo é usado como qualquer outro. Não precisa de prop nem de import.

O ponto que mais confunde: $state no módulo funciona, mas o valor não é recriado a cada instância. Se a tela mostrar três componentes deste arquivo e alguém clicar em um, os três mostram 1. É estado compartilhado de verdade, sem store e sem contexto.

Svelte 4 escrevia diferente

Você pode encontrar em projetos antigos <script context="module">. As duas formas ainda compilam nesta versão, mas a atual é <script module> — mais curta e a única que aparece na documentação nova.

4. O que o módulo pode exportar

O bloco de módulo aceita export, e é isso que o transforma em lugar de coisas compartilhadas entre arquivos: constantes, funções, stores, tipos. Quem importar o componente recebe essas exportações do módulo:

<script module>
  export const ABERTURA = '06:00';
  export function precoComDesconto(preco) {
    return preco * 0.9;
  }
</script>

<p>Abre às {ABERTURA} · pão com desconto: R$ {precoComDesconto(0.9).toFixed(2)}</p>
<p>Abre às 06:00 · pão com desconto: R$ 0.81</p>

Não é preciso exportar para usar dentro do próprio arquivo: o HTML enxerga tudo o que está no módulo. O export serve para quem está fora — por exemplo, um teste que quer conferir a regra de desconto sem desenhar o componente, ou outro componente que precisa da mesma constante.

Quem importa o componente recebe as duas coisas no mesmo import. Um arquivo de teste pode fazer import App, { precoComDesconto } from './App.svelte' e chamar a regra sem montar nada na tela — o que é ótimo, porque testar função é dez vezes mais rápido que testar tela.

Esse é o uso mais seguro do módulo: constantes e funções puras. Elas não têm estado, não mudam com o tempo e não dependem de nada que só existe no navegador. Regra de negócio em função pura no módulo é fácil de ler, de testar e de mover para outro arquivo quando crescer.

5. Os dois blocos no mesmo arquivo

Agora os dois lado a lado. O módulo guarda o que é do arquivo; o script comum guarda o que é da instância:

<script>
  let contador = $state(0);
</script>

<script module>
  let visitas = $state(0);
</script>

<p>contador: {contador} · visitas: {visitas}</p>
<p>contador: 0 · visitas: 0</p>
<script>
roda uma vez por instância. contador nasce em zero em cada componente montado.
<script module>
roda uma vez por arquivo. visitas existe antes do primeiro componente e sobrevive a todos.
os dois juntos
o compilador gera um único módulo JavaScript com as duas partes; o que muda é quando cada parte roda.

Cuidado com uma armadilha de leitura: os dois blocos compartilham o mesmo escopo de módulo no JavaScript final. Se você declarar let visitas nos dois, o compilador reclama de nome duplicado. Nomes diferentes, papéis diferentes.

6. Estado de módulo: $state fora da instância

O detalhe que decide tudo é este: sem $state, uma variável de módulo é só uma variável. Ela guarda o valor, muda quando alguém escreve, e a tela não fica sabendo de nada. Com $state, a mudança avisa todo mundo que está lendo.

Missão: o contador mora no bloco de módulo, mas o clique não muda a tela. Faça o estado do módulo ser reativo para o clique mostrar Cliques: 1.

<script module>
  let cliques = 0;
</script>

<p>Cliques: {cliques}</p>
<button onclick={() => cliques++}>+1</button>
<script module>
  let cliques = $state(0);
</script>

<p>Cliques: {cliques}</p>
<button onclick={() => cliques++}>+1</button>

A missão mostra o essencial em uma linha: o módulo não é reativo por natureza, ele é reativo quando o valor é criado com $state. E, ao contrário do que acontece na instância, esse $state é único — não existe "o cliques deste cartão" e "o cliques daquele cartão", existe um.

7. $derived no módulo

Contas também funcionam no módulo, e pela mesma regra: $derived recalcula; uma variável comum calcula uma vez e congela. Como o valor de base é do módulo, a conta é compartilhada por todas as instâncias:

Missão: o dobro foi calculado uma vez, no carregamento, e ficou em 0. Faça a conta do módulo acompanhar o contador para o clique mostrar Cliques: 1 · dobro: 2.

<script module>
  let cliques = $state(0);
  let dobro = cliques * 2;
</script>

<p>Cliques: {cliques} · dobro: {dobro}</p>
<button onclick={() => cliques++}>+1</button>
<script module>
  let cliques = $state(0);
  const dobro = $derived(cliques * 2);
</script>

<p>Cliques: {cliques} · dobro: {dobro}</p>
<button onclick={() => cliques++}>+1</button>

Uma conta de módulo é útil quando ela é cara e o resultado interessa a todas as instâncias — o total do carrinho, por exemplo. É uma péssima ideia quando cada instância tem os seus próprios dados, porque aí a conta não teria como saber de quem está falando.

<script module>
  let a = $state(1);
  let b = $derived(a * 2);
</script>

<p>{a} {b}</p>
<p>1 2</p>

Esse é o menor exemplo possível de estado e conta no módulo, e ele deixa uma coisa clara: o compilador não reclama de runas no bloco de módulo. O que ele não aceita lá são as runas que dependem de um componente — $props e as funções de contexto. A próxima seção é sobre isso.

8. Uma cópia para todos, ou uma por instância?

Esta é a decisão que você vai tomar em cada componente. A tabela abaixo resume o comportamento real, medido nesta versão:

let x = $state(0) no <script>uma por instânciasim, em cada instância

const X = '06:00' no módulouma constantenão muda, então não precisa

Um jeito de sentir a diferença sem abrir dois arquivos é ter dois lugares na tela lendo o mesmo módulo, cada um com o seu botão. Com estado de instância (aqui simulado por uma lista de contadores), cada botão mexe no seu número; com estado de módulo, os dois botões mexem no mesmo:

Missão: cada caixa tem o seu contador e elas vivem discordando. Mova o contador para o bloco <script module> para um clique valer nas duas caixas.

<script>
  let contadores = $state([0, 0]);
</script>

{#each contadores as c, i}
  <p>Caixa {i + 1}: {c}</p>
  <button onclick={() => contadores[i]++}>+1</button>
{/each}
<script module>
  let total = $state(0);
</script>

{#each [1, 2] as n}
  <p>Caixa {n}: {total}</p>
  <button onclick={() => total++}>+1</button>
{/each}

No projeto da Ana, a mesma coisa acontece com instâncias de verdade: dois <Cartao /> na página leem o mesmo total do módulo. A regra é sempre a mesma — o módulo tem um valor, as instâncias têm outro —, e é por isso que o estado de módulo é a forma mais simples de compartilhar algo entre cópias do mesmo componente.

Estado de módulo não é estado global de projeto

Ele vale para um arquivo. Outro componente, em outro arquivo, não enxerga a variável do módulo de Cartao.svelte — a não ser que ela seja exportada e importada, e aí você já está montando um store na mão. Para valor que atravessa arquivos, o caminho continua sendo um módulo .js com writable.

9. O que não pode morar no módulo

O bloco de módulo roda antes de existir componente. Tudo o que depende de uma instância fica de fora:

ItemPode no módulo?Por quê
$state, $derivedsimnão dependem de instância
$props()nãoprops são de uma instância específica
setContext, getContextnãocontexto é por instância, precisa de um componente para pendurar o recado
onMount, onDestroynãosão ganchos do ciclo de vida de um componente
document, windowcom cuidadono servidor essas variáveis não existem; o módulo roda também lá
export const, export functionsimé justamente para isso que o bloco existe

A última linha da parte "não pode" é a que mais dá dor de cabeça em produção. O código do módulo roda no servidor também, e lá não existe window nem document. Um localStorage.getItem no módulo derruba a renderização inteira. Se precisar do navegador, faça dentro de onMount ou de um $effect, que só rodam no cliente.

10. Quando dá errado

As três mensagens abaixo são do compilador desta versão, copiadas da execução.

Erro 1 — $props() no módulo

Props pertencem a uma instância, e o módulo não tem instância. O compilador recusa:

<script module>
  let { nome } = $props();
</script>

<p>{nome}</p>
Erro de compilação (linha 2, coluna 17): `$props()` can only be used at the top level of components as a variable declaration initializer

"$props() só pode ser usado no nível de cima dos componentes, como inicializador de declaração de variável." Traduzindo: mova a linha para o <script> comum. Se o valor precisa valer para o arquivo inteiro, ele não é prop — é configuração do módulo.

Erro 2 — dois blocos de módulo

Cada arquivo pode ter um <script> e um <script module>. O segundo bloco de módulo é recusado, mesmo que as variáveis tenham nomes diferentes:

<script module>
  export const x = 1;
</script>
<script module>
  export const y = 2;
</script>
<p>{x}{y}</p>
Erro de compilação (linha 4, coluna 0): A component can have a single top-level `<script>` element and/or a single top-level `<script module>` element

"Um componente pode ter um único elemento <script> de nível de cima e/ou um único <script module>." A correção é juntar os dois blocos num só. Repare na posição: linha 4, coluna 0 — exatamente onde começa o segundo bloco.

Erro 3 — export default no módulo

O componente já é a exportação padrão do arquivo. Tentar exportar outro default pelo módulo colide com ele:

<script module>
  export default function x() {}
</script>

<p>ok</p>
Erro de compilação (linha 2, coluna 2): A component cannot have a default export

"Um componente não pode ter exportação padrão." Use exportações com nome — export const, export function —, que são justamente as que outro arquivo importa com { chaves }.

12. O módulo no servidor: uma vez por processo

Existe uma consequência do "roda uma vez" que só aparece quando o componente é renderizado no servidor. Numa aplicação com SvelteKit, o servidor carrega o módulo do componente uma vez e reaproveita esse mesmo módulo para todas as requisições. O $state do módulo, portanto, é compartilhado entre usuários diferentes durante a vida do processo.

Para um contador de cliques que só existe no navegador, isso não faz diferença: o módulo do servidor morre antes de qualquer clique. Para dados de usuário — nome, carrinho, sessão —, é um vazamento: o carrinho de uma pessoa poderia aparecer para outra. A regra prática é curta: nunca guarde dado de usuário em estado de módulo. Use props, contexto ou store, que têm o tempo de vida certo.

O que sobra de bom para o módulo é exatamente o que não muda por usuário: constantes de configuração, tabelas fixas, funções puras e caches de coisas públicas. Tudo o que é "o mesmo para todos, para sempre" cabe bem ali. Tudo o que é "meu, agora" não cabe.

No módulo, pode ficarNo módulo, não pode ficar
horário de abertura, lista de estados, tabela de preçosnome do cliente, carrinho, sessão, formulário em edição
função pura de desconto, formatador de dinheiroresultado de uma consulta que depende de quem está logado
contador de quantas vezes o componente foi montado no navegadorcontador de visitas do site inteiro (isso é do servidor, não do componente)

Guardadas essas fronteiras, o bloco de módulo é a ferramenta mais barata que existe para compartilhar algo entre cópias do mesmo componente: uma tag, uma runa, nenhum arquivo novo.

Resumo

  • <script module> roda uma vez por arquivo; <script> roda uma vez por instância.
  • O módulo guarda o que é do arquivo: constantes, funções, estado compartilhado e stores.
  • export const e export function no módulo ficam disponíveis para quem importa o componente.
  • $state no módulo cria um valor reativo para todas as instâncias do arquivo.
  • $derived no módulo recalcula a conta compartilhada; uma variável comum congela no primeiro valor.
  • $props, contexto e ganchos de ciclo de vida não podem morar no módulo.
  • O módulo roda no servidor também: window e document ali quebram a renderização.
  • Um arquivo aceita um <script> e um <script module>, no máximo.
  • Estado de módulo vale para um arquivo; para atravessar arquivos, use um store num .js.
  • Os erros desta aula: $props() no módulo, dois blocos de módulo e export default.
