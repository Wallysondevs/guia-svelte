SvelteKit · Segurança

A Ana fecha a padaria às 19h, tranca a porta da frente e confere a dos fundos. Segurança de site é a mesma rotina, com outras portas: o texto que o cliente escreve, o formulário que envia dinheiro, o cookie que diz quem ele é e o segredo do banco. A boa notícia é que o SvelteKit já tranca algumas dessas portas sozinho. A parte que sobra é sua, e é sobre ela que esta aula trata — com as respostas reais do servidor, copiadas do terminal.

Você vai aprender
  • Como o SvelteKit escapa texto e o que o {@html} faz de diferente.
  • Por que inserir HTML de terceiro é a porta dos fundos mais comum da web.
  • O que é CSRF e o que o SvelteKit bloqueia em produção — e não bloqueia em desenvolvimento.
  • Para que servem httpOnly, sameSite e secure num cookie.
  • Por que javascript: num link é perigoso e como recusar.
  • Como o erro server_only_import protege o segredo do banco.
  • O que vaza sem querer: página pré-renderizada, log e mensagem de erro.
  • O que fazer quando o build acusa importação de módulo privado.

1. A ideia: a porta da frente, a dos fundos e o cofre

Toda padaria tem uma porta da frente, que recebe o cliente, e uma dos fundos, que recebe o padeiro às 4h da manhã. A da frente tem vitrine e campainha; a dos fundos tem fechadura e ninguém anuncia o endereço. Quem confunde as duas mantém o estoque aberto para a rua.

Um site tem as mesmas duas portas. A da frente é o que o visitante manda: nome, comentário, número do pedido. A dos fundos é o que só o servidor acessa: banco, chave de API, arquivo de configuração. A regra de ouro é simples de dizer e difícil de cumprir: tudo o que vem do visitante é suspeito até prova em contrário.

“Suspeito” não quer dizer que o visitante é má intenção. Quer dizer que o texto que ele digita entra no HTML da página e pode virar marcação, script ou link malicioso. O trabalho de segurança é fazer esse texto entrar como texto, sempre, e deixar o navegador sem instrução nenhuma que ele não deveria executar.

2. As quatro portas de entrada

Antes de detalhar cada uma, vale ver o mapa. Um site é atacado por onde recebe dado, e são quatro lugares:

PortaExemploProteção
Texto na telacomentário do clienteescapar sempre; evitar {@html}

Cookiesessão do usuáriohttpOnly, sameSite, secure
Dependênciapacote instalado com npmnpm audit e pouca dependência

A quarta porta é a que ninguém lembra: cada pacote instalado é código de outra pessoa rodando na sua máquina e no seu servidor. Não é motivo para não usar biblioteca — é motivo para usar poucas, manter atualizadas e rodar npm audit de vez em quando. O erro mais caro de segurança costuma vir de uma dependência desatualizada, não de um hacker criativo.

3. Texto que vira HTML: { } contra {@html}

Aqui está a decisão que mais importa no dia a dia. O Svelte tem duas formas de colocar valor na tela, e só uma delas é segura para texto de terceiro:

<script>
	const comentario = '<img src=x onerror="alert(1)">';
</script>

<p>{comentario}</p>
<p>{@html comentario}</p>
<p>&lt;img src=x onerror="alert(1)"></p> <p><img src=x onerror="alert(1)"></p>

A saída mostra as duas personalidades lado a lado. No primeiro parágrafo, as chaves escaparam o texto: o que era <img> virou &lt;img&gt;, e o navegador mostra a marcação como texto, sem criar imagem nenhuma. No segundo, o {@html} injetou o texto cru: agora existe de verdade uma tag img na página, apontando para um endereço inválido e com um atributo onerror — o mesmo truque que roda código na máquina de quem visita.

{comentario}
a interpolação normal. Escapa <, >, & e aspas: o valor vira texto, não marcação.
{@html comentario}
a diretiva que insere HTML cru. O navegador interpreta o conteúdo como tags e atributos.
onerror="…"
um atributo de evento: o navegador executa o conteúdo quando a imagem falha ao carregar. É por isso que a tag acima não é inofensiva.
src=x
um endereço que não existe, usado de propósito para acionar o onerror.

A regra prática cabe numa frase: {@html} é para conteúdo que você escreveu, não para o que o cliente escreveu. Um rodapé com negrito fixo, uma resposta de API confiável com HTML já limpo — esses casos existem. Comentário de visitante, nunca. Se a necessidade for exibir negrito vindo do cliente, o caminho é uma biblioteca de markdown ou de sanitização, que transforma o texto num subconjunto seguro de marcação.

4. Caixa 1: o comentário que vira tag

A caixa abaixo mostra o problema em tamanho de brinquedo. Ela recebe texto e joga direto na página com {@html}. Digite uma marcação simples e veja a diferença.

Missão: troque a exibição para que a marcação digitada apareça como texto, e não como formatação. Digite <b>oi</b> no campo: o texto na tela deve conter literalmente <b>oi</b>.

<script>
	let texto = $state('');
</script>

<input oninput={(e) => (texto = e.currentTarget.value)} />
<p>{@html texto}</p>
<script>
	let texto = $state('');
</script>

<input oninput={(e) => (texto = e.currentTarget.value)} />
<p>{texto}</p>

Com {@html}, o texto digitado vira negrito e o que aparece na tela é só “oi” — a marcação foi interpretada. Sem a diretiva, aparece a marcação como ela foi escrita. Essa diferença é a fronteira entre uma página que mostra o comentário e uma página que executa o comentário.

5. Formulário e CSRF: o pedido que vem de outro site

A sigla CSRF significa “falsificação de requisição entre sites”. O ataque é mais simples do que o nome: você está logada na padaria no seu navegador, com o cookie de sessão ativo, e abre um site qualquer. Esse site esconde um formulário que envia POST para https://padariadaana.com.br/entrar?/entrar. O navegador manda o pedido junto com o seu cookie, e o servidor não tem como saber que a intenção não foi sua.

O SvelteKit se protege comparando a origem do pedido com a origem do site. Pedido de formulário com origem diferente recebe 403. A resposta abaixo é do servidor de produção do projeto da Ana, com um POST forjado:

ana@notebook:~/loja$ curl -s -i -X POST -H 'origin: http://evil.example' -H 'content-type: application/x-www-form-urlencoded' -d 'senha=pao123' 'http://localhost:3000/entrar?/entrar' | head -8
HTTP/1.1 403 Forbidden
content-length: 46
Date: Thu, 26 Nov 2026 17:10:32 GMT
Connection: keep-alive
Keep-Alive: timeout=5

Cross-site POST form submissions are forbidden

A mensagem diz exatamente o que aconteceu: “envios de formulário entre sites estão proibidos”. O corpo tem 46 bytes e é texto puro; a ação nem foi executada, então a senha correta não fez login nenhum.

Existe um detalhe que muda o hábito de testar: essa proteção só vale fora do modo de desenvolvimento. No código do SvelteKit, o bloco da checagem começa com uma condição explícita:

ana@notebook:~/loja$ sed -n 101,103p node_modules/@sveltejs/kit/src/runtime/server/respond.js
	if (!__SVELTEKIT_DEV__) {
		const request_origin = request.headers.get('origin');
		const self_origin = get_self_origin(__SVELTEKIT_PATHS_ORIGIN__, url.origin);

Em português: “se não estiver em desenvolvimento”. No npm run dev, o mesmo POST forjado passou e a ação rodou. Isso não é falha de segurança do SvelteKit — o servidor de desenvolvimento é seu, na sua máquina. É um aviso para quem testa proteção: teste no build, com node build, e não no dev.

6. Caixa 2: as três bandeiras do cookie

O cookie de sessão é o crachá. Um crachá mal feito pode ser lido por script de terceiro, viajar em pedido de outro site ou ir por conexão sem criptografia. A caixa abaixo tem as opções certas no código e escreve “sem proteção” na tela.

Missão: mostre as opções do cookie na tela, no formato cookie: httpOnly: sim · sameSite: lax. O texto precisa conter httpOnly: sim.

<script>
	const opcoes = { path: '/', httpOnly: true, sameSite: 'lax' };
</script>

<p>cookie: sem proteção</p>
<script>
	const opcoes = { path: '/', httpOnly: true, sameSite: 'lax' };
</script>

<p>cookie: httpOnly: {opcoes.httpOnly ? 'sim' : 'não'} · sameSite: {opcoes.sameSite}</p>
OpçãoO que fazCusto
httpOnly: trueo JavaScript da página não lê o cookiese precisar ler no cliente, não dá
sameSite: 'lax'não envia o cookie em POST de outro sitelinks externos ainda funcionam
secure: truesó envia o cookie por HTTPSquebra em http://localhost
path: '/'o cookie vale no site inteirovale em toda rota
maxAgequanto tempo o cookie duradura mais, expõe mais tempo

O secure: true merece um aviso: em desenvolvimento o endereço é http://localhost, sem o “s”, e o navegador recusa cookie marcado como seguro nesse caso. A solução comum é ligar a bandeira apenas em produção, o que se faz lendo o ambiente — assunto da aula de $env.

7. Link com javascript: e outras armadilhas

Um endereço de link não é só um endereço: pode ser um comando. Quando o navegador vê href="javascript:alert(1)", ele executa o que vem depois dos dois pontos em vez de navegar. Se esse href veio do que o visitante digitou, você acabou de dar a ele execução de código na sua página.

Missão: só aceite destino que comece com /. Digite javascript:alert(1) no campo: o texto deve conter link: bloqueado.

<script>
	let destino = $state('/conta');
</script>

<input oninput={(e) => (destino = e.currentTarget.value)} />
<p>link: {destino}</p>
<script>
	let destino = $state('/conta');
	const seguro = $derived(destino.startsWith('/'));
</script>

<input oninput={(e) => (destino = e.currentTarget.value)} />
<p>link: {seguro ? destino : 'bloqueado'}</p>

Vale um cuidado parecido com link externo. Quando um link abre em aba nova — target="_blank" —, a aba aberta ganha acesso limitado à sua página pela propriedade window.opener. O remédio é uma palavra no atributo: rel="noopener". Navegadores modernos já aplicam esse comportamento por padrão em muitos casos, mas escrever o atributo custa nada e funciona em navegador antigo. É a mesma lógica do cadeado na porta dos fundos: você não conta com a sorte.

Aceitar só caminho que começa com barra é a política mais fechada e a mais segura: limita o destino ao próprio site. Quando link externo é necessário, a validação precisa ser por lista — https:// com domínio conhecido — e nunca por “não começa com javascript”. Lista fechada de permitidos envelhece bem; lista de proibidos sempre esquece um caso.

8. Segredo que não sai do servidor

A quarta porta é a mais silenciosa. Uma variável privada importada num componente .svelte seria enviada ao navegador junto com o resto do código, e qualquer visitante leria. O SvelteKit trata isso como erro de build, não como aviso — e os milissegundos do build são a medição daquela execução, o erro é sempre o mesmo:

Building app
vite v8.4.0 building client environment for production...
transforming...
✓ 196 modules transformed.
✗ Build failed in 281ms
error during build:
Build failed with 1 error:

[plugin vite-plugin-sveltekit-guard]
SvelteKit error: server_only_import
Cannot import `$app/env/private` into code that runs in the browser, as this could leak sensitive information.

 src/routes/quebra/+page.svelte imports
  $app/env/private

If you're only using the import as a type, change it to `import type`.
https://svelte.dev/e/kit/server_only_import

O nome do erro é server_only_import, e o plugin que o levanta se chama vite-plugin-sveltekit-guard — “guarda”. A tradução da mensagem: “não dá para importar isso em código que roda no navegador, porque vazaria informação sensível”. A correção é mover a leitura para um +page.server.js e devolver só o que a tela precisa.

O mesmo vale para qualquer coisa que você escreva à mão no componente: uma chave de API em const no <script> de um .svelte vai para o navegador, com ou sem variável de ambiente. Se a chave é secreta, ela não pode estar no arquivo que o cliente baixa.

9. O que vaza sem querer

Existem três vazamentos que não dão erro nenhum e por isso passam batido. O primeiro é a página pré-renderizada. No projeto da Ana, o rastreador de links congelou /conta num arquivo de 112 bytes, e ele é servido com status 200:

ana@notebook:~/loja$ wc -c build/prerendered/conta.html
112 build/prerendered/conta.html
ana@notebook:~/loja$ grep -o 'url=[^"]*' build/prerendered/conta.html
url=/entrar?de=/conta
ana@notebook:~/loja$ curl -s -D - -o /dev/null http://localhost:3000/conta | head -2
HTTP/1.1 200 OK
etag: "7-DYfYF_Azx3mHEh08LY_w65McduCKKcStU7BxjvvLY"

O segundo é o log. Senha, token e cookie inteiro não podem ir para o arquivo de log, porque o log circula: fica no terminal, no arquivo do servidor e no painel da plataforma. O terceiro é a mensagem de erro. Uma pilha de erro completa na tela conta ao visitante qual biblioteca você usa, em que versão e em que linha está o problema — informação de presente para quem procura falha.

A defesa é a mesma nos três casos: mostrar pouco e registrar muito. O handleError devolve uma frase curta para a tela e escreve o detalhe no terminal. A pasta prerendered é revisada antes de publicar. E o log passa por um filtro que mascara senha, do jeito que a aula de logs mostrou.

10. Quando dá errado

As três respostas abaixo são reais. A primeira é do build, a segunda do servidor em produção e a terceira do processo de desenvolvimento.

Erro 1 — segredo importado no componente

Um .svelte importou $app/env/private. O build para antes de gerar o pacote do cliente, e a mensagem explica o risco.

ana@notebook:~/loja$ npm run build

> loja@0.0.1 build
> vite build

[plugin vite-plugin-sveltekit-guard]
SvelteKit error: server_only_import
Cannot import `$app/env/private` into code that runs in the browser, as this could leak sensitive information.

 src/routes/quebra/+page.svelte imports
  $app/env/private

A saída é mover a importação para o +page.server.js e devolver o dado já tratado. Se o valor realmente pode ser público, ele muda de declaração em src/env.js — e passa a ser visível para qualquer visitante, o que é uma decisão de produto, não de código.

Erro 2 — POST de outro site

O servidor de produção recusou um formulário com origem estranha. A resposta é 403 e o corpo é uma frase, sem página de erro.

HTTP/1.1 403 Forbidden
content-length: 46
Date: Thu, 26 Nov 2026 17:10:32 GMT
Connection: keep-alive
Keep-Alive: timeout=5

Cross-site POST form submissions are forbidden

Se esse 403 aparece no seu teste com curl e você não mandou cabeçalho de origem nenhum, o motivo é o mesmo: sem origem, o SvelteKit trata o pedido como suspeito. Basta enviar -H 'origin: http://localhost:3000' para simular o mesmo site. Em navegador, o cabeçalho vai sozinho e o problema não acontece.

Erro 3 — a mesma proteção não vale em desenvolvimento

No npm run dev, o POST forjado passou e a ação rodou. O terminal não mostra erro nenhum; o status é 200 e o cookie de sessão é gravado.

ana@notebook:~/loja$ curl -s -i -X POST -H 'origin: http://evil.example' -d 'senha=pao123' 'http://localhost:5173/entrar?/entrar' | head -4
HTTP/1.1 200 OK
Vary: Origin
content-type: application/json
set-cookie: sessao=ana-123; Max-Age=86400; Path=/; HttpOnly; SameSite=Lax

Este é o cenário que ensina a testar no lugar certo. A checagem de origem é desligada em desenvolvimento de propósito, para não atrapalhar teste local. Proteção de segurança se confere no build: npm run build e node build, como a aula de deploy mostra.

Exercícios

1. Qual das duas formas é segura para mostrar um comentário de visitante?

2. O que o SvelteKit faz com um POST de formulário cuja origem é outro site, em produção?

3. Para que serve httpOnly: true no cookie de sessão?

Complete o código

// src/routes/entrar/+page.server.js
cookies.set('sessao', 'ana-123', {
  path: '/',
  httpOnly: ,
  sameSite: 'lax',
  maxAge: 60 * 60 * 24
});

Resumo

  • Tudo o que vem do visitante é suspeito: texto, formulário, link e cabeçalho.
  • {valor} escapa a marcação; {@html valor} insere HTML cru e executa atributos de evento.
  • {@html} é para conteúdo próprio, nunca para comentário de terceiro.
  • CSRF é o POST forjado por outro site; o SvelteKit responde 403 com Cross-site POST form submissions are forbidden.
  • A checagem de origem é desligada em desenvolvimento: teste com node build.
  • Cookie de sessão pede httpOnly, sameSite e secure em produção.
  • Link que começa com javascript: executa código; aceite só caminho iniciado por /.
  • server_only_import impede que variável privada vaze para o navegador.
  • Página pré-renderizada, log e mensagem de erro podem vazar informação sem aviso.
