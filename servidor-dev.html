Svelte · O Servidor de Desenvolvimento

A Ana assa pão todos os dias e prova a massa antes de levar ao forno. Se estivesse ruim, ela corrige e prova de novo — não espera o pão pronto para descobrir que faltou sal. Um servidor de desenvolvimento faz esse papel no projeto: ele deixa a página aberta, você salva o arquivo e o resultado aparece em menos de um segundo, ainda quente. Nesta aula você liga esse servidor, entende cada linha que ele imprime e aprende o que ele faz quando alguma coisa quebra.

Você vai aprender
  • O que é um servidor de desenvolvimento e por que ele não é a internet.
  • O que npm run dev faz e o que cada linha da saída significa.
  • Como ler um endereço http://localhost:5173/ por partes.
  • Por que a porta pode mudar sozinha e o que fazer quando isso acontece.
  • O que é recarga automática (HMR) e o que aparece no terminal a cada arquivo salvo.
  • O que o HMR não resolve e quando é preciso reiniciar o servidor.
  • A diferença entre o servidor de desenvolvimento e o npm run preview.
  • Como parar o servidor sem deixar processo pendurado.
  • Os erros reais que aparecem com o servidor no ar: propriedade de undefined, método que não existe e recursão sem fim.

1. A ideia: o fogão ligado enquanto você prova

Sem servidor de desenvolvimento, o ciclo é lento e chato: você muda o arquivo, roda o build, abre a pasta gerada, recarrega a página, descobre que errou uma vírgula e recomeça. Cada tentativa custa dezenas de segundos. Com o servidor ligado, o ciclo é: salva, olha a página. O tempo entre uma coisa e outra é o tempo de piscar.

Essa diferença parece pequena e muda tudo na prática. Quando o ciclo é curto, você experimenta mais: testa uma cor, um texto, um espaçamento. Quando o ciclo é longo, você junta cinco mudanças antes de testar e, se algo quebrar, não sabe qual das cinco foi. O servidor de desenvolvimento é uma ferramenta de paciência: ele devolve a sua.

O nome assusta. "Servidor" parece coisa de datacenter, de gente de terno. Aqui é só um programa que fica rodando no seu computador, olhando os arquivos e respondendo a um endereço. Nada sai da máquina da Ana: quando o terminal diz localhost, está dizendo "aqui dentro".

2. O que é um servidor de desenvolvimento

Um servidor é um programa que espera pedidos e responde. O navegador pede um endereço; o servidor devolve um arquivo. O servidor de desenvolvimento do Vite faz isso e mais duas coisas: compila os arquivos .svelte quando o navegador pede e observa o disco para saber quando algo mudou.

Ele também serve os arquivos por http, e não por file://. Isso não é detalhe: o navegador bloqueia módulos JavaScript carregados por file:// por segurança (a regra se chama CORS). Se você abrir o index.html clicando duas vezes, verá uma página vazia e um erro no console. O servidor existe justamente para dar um endereço http ao seu projeto.

Por último, o servidor de desenvolvimento não é o site publicado. Ele inclui ferramentas de depuração, mapas de código e recarga automática — coisas boas para você e ruins para o cliente. O que vai para o ar é o resultado do npm run build, que veremos mais adiante nesta aula.

3. Ligando o servidor

Na pasta do projeto, um comando. O terminal responde com quatro blocos: o nome do projeto, o comando que está sendo executado, o aviso de porta e o endereço.

ana@notebook:~/loja$ npm run dev

> loja@0.0.1 dev
> vite

Port 5173 is in use, trying another one...

  VITE v7.3.8  ready in 620 ms

  ➜  Local:   http://localhost:5173/
  ➜  Network: use --host to expose

O bloco > loja@0.0.1 dev é o npm mostrando o que ele leu no package.json: o projeto loja, na versão 0.0.1, executando o atalho dev. A linha seguinte mostra o comando real, vite. É uma boa prática olhar essas duas linhas: se o atalho estiver apontando para outro programa, o problema está no package.json, não no Svelte.

O aviso Port 5173 is in use, trying another one... quer dizer que outro programa já estava usando a porta 5173. O Vite não desiste: ele tenta a próxima e avisa. O endereço final veio na linha Local — nesse exemplo, 5173 mesmo, porque a porta acabou liberando antes do teste. Quando isso acontece com você, use o endereço que aparecer na tela, não o que você decorou.

O servidor fica rodando e ocupando o terminal. Não feche a janela e não aperte Ctrl+C sem querer: os dois encerram o processo. Para trabalhar em outra coisa, abra uma segunda aba do terminal — é o que a Ana faz quando precisa pesar farinha enquanto o forno está aceso.

4. Lendo o endereço por partes

O endereço http://localhost:5173/ tem quatro pedaços, e cada um responde a uma pergunta.

http://
o protocolo: como o navegador fala com o servidor. É o mesmo das páginas comuns; o s de https indica conexão criptografada, que não é necessária aqui porque nada sai da máquina.
localhost
o endereço da própria máquina. Vale 127.0.0.1 também: é o computador conversando consigo mesmo. Nenhum dado atravessa a internet.
:5173
a porta: o número do balcão. Um computador pode ter vários servidores ao mesmo tempo, cada um em uma porta diferente, como uma padaria com vários caixas.
/
o caminho pedido. A barra sozinha significa "a página inicial"; no Vite, isso entrega o index.html da raiz.

A linha Network: use --host to expose é um convite. Por padrão o servidor só aceita conexões da própria máquina; com --host, ele aceita da rede local — útil para testar no celular, arriscado em rede pública. Para quem está começando, deixe como está: localhost basta.

Um erro comum é abrir o endereço errado, com https em vez de http, ou trocar a porta. O navegador então mostra "não foi possível conectar" — e o servidor está lá, funcionando, esperando no endereço certo. Antes de mexer no código, confira o endereço na tela do terminal.

5. Salvou, mudou: a recarga automática

Com o servidor no ar, cada vez que você salva um arquivo o Vite percebe e manda a mudança para o navegador. O terminal registra isso em uma linha:

ana@notebook:~/loja$ npm run dev

> loja@0.0.1 dev
> vite

  VITE v7.3.8  ready in 620 ms

  ➜  Local:   http://localhost:5173/
  ➜  Network: use --host to expose
5:21:05 PM [vite] (client) hmr update /src/App.svelte

hmr update /src/App.svelte quer dizer "atualização em tempo real no arquivo App.svelte". HMR é a sigla de Hot Module Replacement, troca de módulo a quente: o Vite substitui só aquele pedaço da página, sem recarregar tudo. O relógio na frente é a hora em que a atualização aconteceu.

Na prática, você vê o texto novo sem perder o que estava fazendo: um campo preenchido continua preenchido, um contador não volta a zero. Isso é diferente de recarregar a página com F5, que joga tudo fora e começa do zero. A diferença importa quando você está testando um formulário longo.

Vale reparar no relógio: 5:21:05 PM é a hora local do computador da Ana. Em uma sessão longa, essas linhas viram um diário do trabalho — dá para ver quantas vezes você salvou e em que ordem. Quando algo para de atualizar, a ausência da linha é a informação: o Vite não percebeu a mudança, e o problema pode ser o editor salvando em outro arquivo, ou o servidor observando outra pasta.

O componente que a Ana estava ajustando é este:

<script>
  let preco = $state(0.9);
</script>

<h1>Pão francês</h1>
<p>R$ {preco.toFixed(2)}</p>
<h1>Pão francês</h1> <p>R$ 0.90</p>

Quando ela muda 0.9 para 1.1 e salva, o terminal imprime a linha de hmr update e o navegador passa a mostrar R$ 1.10. Nenhum comando a mais: o ciclo é salvar e olhar.

Missão: o campo já escreve no estado, mas o parágrafo não mostra nada. Faça o cumprimento aparecer na tela quando você digitar "Ana" no campo.

<script>
  let nome = $state('');
</script>

<input oninput={(e) => (nome = e.currentTarget.value)} placeholder="seu nome" />
<p>Digite seu nome acima.</p>
<script>
  let nome = $state('');
</script>

<input oninput={(e) => (nome = e.currentTarget.value)} placeholder="seu nome" />
<p>Olá, {nome}!</p>

O e.currentTarget.value é o texto que está dentro do campo no momento do evento. O oninput dispara a cada tecla — é o mesmo ciclo de salvar e ver, só que disparado por você em vez do disco.

6. O que o HMR não faz

A recarga automática é boa, mas não é mágica. Existe uma lista de mudanças que ela não consegue aplicar a quente, e o Vite resolve isso com uma recarga completa da página — você vê a tela piscar e o estado volta ao início. É normal, mas explica aquele "sumiu o que eu tinha digitado".

Algumas mudanças exigem mais do que recarregar a página: exigem reiniciar o servidor. É o caso de alterações em vite.config.js, em svelte.config.js, no package.json ou depois de instalar um pacote novo. Se você mudou a configuração e nada aconteceu, pare o servidor com Ctrl+C e ligue de novo. Custa dois segundos e resolve.

Também vale saber o que não é recarregado: o código que roda fora do componente, como o main.js, costuma provocar recarga total. E se o servidor reclamar que a porta está ocupada a cada reinício, é sinal de que o processo antigo não morreu — feche a aba do terminal ou encerre o processo antes de abrir outro.

Missão: o botão soma um e o total chega a 3 depois de dois cliques. Faça o valor dobrar a cada clique, para que dois cliques levem de 1 a 4.

<script>
  let total = $state(1);
</script>

<button onclick={() => total++}>Total: {total}</button>
<script>
  let total = $state(1);
</script>

<button onclick={() => (total *= 2)}>Total: {total}</button>

Enquanto você edita, a caixa compila o componente com o compilador de verdade e roda o resultado. É o mesmo ciclo do servidor de desenvolvimento, só que sem o terminal no meio.

7. O servidor não conserta o seu código

Existe uma confusão comum: achar que, se o servidor está no ar, a página está certa. Não é assim. O servidor entrega o que você escreveu; se o componente quebra ao desenhar, o servidor continua lá, imperturbável, servindo a página quebrada.

Os problemas aparecem em dois momentos diferentes, e vale distinguir. O primeiro é a compilação: o arquivo nem chega a virar JavaScript, porque tem um erro de sintaxe — chave sem fechar, tag aberta, runa no lugar errado. O terminal mostra a mensagem e o navegador exibe uma sobreposição de erro no lugar da página. O segundo é a execução: o componente compilou, mas quebra quando tenta rodar — um valor que não existe, um método chamado em um tipo errado.

Essa distinção economiza tempo. Erro de compilação se resolve lendo a mensagem e indo à linha apontada. Erro de execução se resolve olhando quando a página quebra: ao abrir, ao clicar, ao digitar. O console do navegador mostra a sequência; a mensagem sozinha não conta a história toda.

Missão: o componente quebra porque pessoa existe mas está vazia, e ler .nome de vazio dá erro. Dê a ela um objeto com o nome "Ana".

<script>
  let pessoa = $state();
</script>

<p>Olá, {pessoa.nome}</p>
<script>
  let pessoa = $state({ nome: 'Ana' });
</script>

<p>Olá, {pessoa.nome}</p>

O erro que aparece na caixa é o mesmo que você veria no console do navegador: Cannot read properties of undefined (reading 'nome'). Ele quer dizer "tentei pegar a propriedade nome de algo que não existe". A solução nunca é esconder a mensagem: é garantir que o objeto exista antes de ler.

8. npm run preview: vendo o build

O servidor de desenvolvimento tem ferramentas que o cliente não deve receber. Para ver o site como ele vai ao ar, primeiro gere o build e depois sirva o resultado:

ana@notebook:~/loja$ npm run preview

> loja@0.0.1 preview
> vite preview

  ➜  Local:   http://localhost:4173/
  ➜  Network: use --host to expose

Repare nas diferenças: a porta padrão é 4173, não 5173, e o terminal não mostra a linha do VITE com o tempo de inicialização. O preview não compila nada: ele só serve a pasta dist que já existe. Se você rodar o preview sem ter rodado o build, ele avisa que não encontrou a pasta.

O uso certo é uma conferida final, antes de publicar: rode npm run build, depois npm run preview e clique pelas páginas. O que aparece ali é exatamente o que o servidor de produção vai entregar — mesmos arquivos, mesmos nomes com hash. Se algo funciona no dev e quebra no preview, a diferença está no build, e é melhor descobrir isso antes do cliente.

9. Parando o servidor

Para encerrar, clique na janela do terminal e aperte Ctrl+C. O servidor para, a porta é liberada e o prompt volta a aparecer. Se você fechar a janela do terminal direto, o processo também morre — mas é mais fácil esquecer um servidor rodando em uma aba escondida e depois brigar com a porta ocupada.

Quando o terminal parece travado, sem responder a nada, quase sempre é um servidor rodando e esperando. Ctrl+C é a saída; se não funcionar, feche a aba. E não existe problema em ligar e desligar o servidor quantas vezes quiser: ele não guarda estado do projeto, só lê os arquivos de novo.

Uma última recomendação de organização: um terminal para o servidor, outro para os comandos. Assim você roda npm install sem derrubar o servidor e vê as mensagens dos dois sem misturar. A Ana faz o mesmo na cozinha: um fogão para o pão, outro para o recheio.

10. Quando dá errado

As três mensagens abaixo são de erro em tempo de execução: o arquivo compila, o servidor continua no ar e a página quebra ao ser desenhada. São as mensagens reais desta versão.

Erro 1 — ler uma propriedade de algo vazio

A variável existe, mas o valor dentro dela é undefined. Tentar ler .nome de undefined derruba o componente.

<script>
  let pessoa = $state();
</script>

<p>{pessoa.nome}</p>
Erro ao renderizar: Cannot read properties of undefined (reading 'nome')

Dê um valor inicial ao estado: $state({ nome: 'Ana' }). Se o dado vem de fora e pode demorar, a solução é condicional — mostrar outra coisa enquanto ele não chega —, assunto das aulas de {#if}.

Erro 2 — chamar um método que o tipo não tem

trim() existe em texto, não em número. O componente compila e quebra na hora de desenhar.

<script>
  let nome = $state(42);
</script>

<p>{nome.trim()}</p>
Erro ao renderizar: nome.trim is not a function

A mensagem diz exatamente qual método não é função. Aqui, o valor guardado é número; para tratar como texto, use String(nome).trim(). Vale a regra geral: confira o tipo antes de chamar método.

Erro 3 — função que chama a si mesma sem parar

A função soma chama soma de novo, sempre, e nunca chega a um resultado. Em algum momento a pilha de chamadas estoura.

<script>
  function soma(n) {
    return soma(n + 1);
  }
</script>

<p>{soma(1)}</p>
Erro ao renderizar: Maximum call stack size exceeded

Falta a condição de parada: um if que devolva o resultado sem chamar a função de novo. Toda recursão precisa de uma saída, senão é só um laço disfarçado — e o navegador trava até desistir.

Resumo

  • O servidor de desenvolvimento deixa a página aberta e recompila a cada arquivo salvo.
  • npm run dev usa a porta 5173 por padrão; se ela estiver ocupada, o Vite escolhe outra e avisa.
