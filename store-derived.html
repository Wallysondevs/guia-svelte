Svelte · derived e get

Na padaria da Ana existe uma placa com o número de pães e outra com o total da compra. O total nunca é digitado: ele é sempre a conta dos pães mais os bolos. Se a Ana anota o total à mão, mais cedo ou mais tarde os dois números discordam — e é o cliente que descobre. O Svelte resolve isso com derived: um store que não guarda valor nenhum, ele calcula a partir de outros. E resolve a outra metade do problema com get: ler o valor de um store uma vez, na hora, sem virar visor.

Você vai aprender
  • O que é um store derivado e por que ele não guarda valor.
  • Criar um com derived(origem, fn) e ler com o cifrão.
  • Juntar dois ou mais stores numa conta só.
  • Por que o derivado é somente leitura e o que acontece se você tentar escrever.
  • A diferença entre derived (biblioteca) e $derived (runa).
  • Guardar o derivado num módulo e usar em vários componentes.
  • Ler o valor na hora com get() e por que ele não é reativo.
  • O derivado assíncrono e o terceiro argumento (valor inicial).
  • Os três erros reais desta aula, com a mensagem do compilador ou do navegador.
  • O que o terminal da Ana mostra ao ler um derivado sem abrir o navegador.

1. A ideia: a conta que ninguém digita

A Ana tem um caderno com duas colunas: a quantidade de pães e o total a pagar. Durante anos ela preencheu as duas à mão. O problema é óbvio: quando o preço do pão muda, ela corrige uma coluna e esquece a outra. O número que sobra no caderno está errado, e ninguém percebe até o cliente reclamar.

Um store derivado é a coluna que se preenche sozinha. Você não escreve nela; você escreve a regra dela. "O total é a quantidade de pães vezes noventa centavos, mais os bolos vezes doze reais." Toda vez que a quantidade de pães ou de bolos muda, a regra roda de novo e o total aparece atualizado. Não existe um momento em que o total esteja desatualizado, porque ele nunca foi guardado: ele é sempre o resultado de uma conta feita agora.

Isso muda o jeito de pensar. Com um store comum (writable) você guarda um valor e corre atrás dele: alguém precisa lembrar de escrever o valor novo. Com um derivado você guarda uma dependência: basta saber de quem ele depende. A conta é sempre refeita a partir das fontes, e as fontes são a única verdade.

O get é o oposto filosófico: ele não acompanha nada. Ele é a foto do número naquele instante, para quando você precisa do valor dentro de uma função — e não de um visor que se atualiza. As duas ferramentas parecem primas, mas resolvem problemas diferentes, e a aula inteira é sobre essa diferença.

Repare na terceira linha: um derivado pode depender de vários stores. É aí que ele economiza mais código, porque a regra fica num lugar só em vez de espalhada por cada botão que muda um dos valores.

3. derived: um store que nasce de outro

O primeiro derivado da Ana transforma pães em dúzias. Ele não guarda o número de dúzias: ele sabe que dúzia é pão dividido por doze.

<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(2);
  const duzias = derived(paes, (n) => n / 12);
</script>

<p>{$paes} pães são {$duzias.toFixed(2)} dúzias</p>

A saída real do renderizador:

<p>2 pães são 0.17 dúzias</p>
derived(paes, …)
o primeiro argumento é a fonte: o store que será observado. Pode ser um store só ou uma lista deles.
(n) => n / 12
a regra. Ela recebe o valor atual da fonte e devolve o valor do derivado. Roda de novo a cada mudança da fonte.
const duzias
o resultado é outro store, com subscribe igual a qualquer um. Por isso aceita o cifrão.
{$duzias.toFixed(2)}
o valor derivado tem os mesmos métodos do tipo que você devolveu — aqui, um número com toFixed.

O detalhe que vale ouro: derived devolve um objeto com só o subscribe. Ele não tem set nem update, porque escrever nele não faria sentido — na próxima mudança da fonte, o valor seria recalculado e a sua escrita sumiria. Isso não é uma limitação, é o que garante que o número esteja sempre certo.

Missão: a regra devolve sempre 7, então caixas mostra 7 em vez de 1. Faça a conta sair do valor que vem da fonte: 7 pães são 1 caixa de 6.

<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(7);
  const caixas = derived(paes, () => 7);
</script>

<p>Pães: {$paes} · caixas: {$caixas}</p>
<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(7);
  const caixas = derived(paes, (n) => Math.floor(n / 6));
</script>

<p>Pães: {$paes} · caixas: {$caixas}</p>

A caixa importa o derived de verdade, do mesmo svelte/store que o projeto da Ana usa. E ela deixa ver o que a regra recebe: o valor da fonte. Com () => 7 a função ignora o store e repete um número; com (n) => Math.floor(n / 6) ela transforma os sete pães em uma caixa.

4. O derivado acompanha a fonte

Para ver o derivado mudar, basta um botão que escreve na fonte. Repare que ninguém toca em duzias:

<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(2);
  const duzias = derived(paes, (n) => n / 12);
</script>

<p>{$paes} pães são {$duzias.toFixed(2)} dúzias</p>
<button onclick={() => $paes += 1}>mais um pão</button>
<p>2 pães são 0.17 dúzias</p> <button>mais um pão</button>

No navegador, cada clique soma um pão e as dúzias aparecem recalculadas. A ordem é sempre a mesma: o clique escreve em paes, o paes avisa quem assinou, o duzias está entre os que assinaram, ele roda a regra e avisa os seus próprios inscritos. É uma corrente de avisos, e o componente está no fim dela.

Essa corrente tem um custo: a regra roda a cada mudança da fonte, mesmo que o componente que mostra o derivado esteja fora da tela. Se a regra for uma conta de três números, ninguém sente. Se ela varrer uma lista de dez mil pedidos, você sente — e a solução é guardar o resultado num $derived dentro do componente que precisa, ou recalcular só quando a lista mudar de verdade.

Regra prática

Uma conta que qualquer componente pode querer, feita de stores compartilhados: derived no módulo. Uma conta que só uma tela mostra, feita de valores que só ela tem: $derived no componente. As duas formas convivem no mesmo projeto sem briga.

5. Dois stores, uma conta

O total do pedido depende de pães e de bolos. Passe uma lista de stores como primeiro argumento e a regra recebe uma lista de valores, na mesma ordem:

<script>
  import { writable, derived } from 'svelte/store';

  const pao = writable(2);
  const bolo = writable(1);
  const total = derived([pao, bolo], ([$pao, $bolo]) => $pao * 0.9 + $bolo * 12);
</script>

<p>Total: R$ {$total.toFixed(2)}</p>
<p>Total: R$ 13.80</p>
[pao, bolo]
a lista de fontes. O derivado assina todas e só roda a regra quando alguma muda.
([$pao, $bolo]) => …
a regra recebe uma lista, não dois argumentos. Os parênteses em volta são a desestruturação: é o mesmo truque de const [a, b] = lista.
$pao * 0.9 + $bolo * 12
a conta. Os valores dentro dos colchetes são valores comuns; o cifrão aqui é só parte do nome que você escolheu.

Errar o formato do parâmetro é fácil, e o sintoma muda com o erro. (valores) => valores * 0.9 recebe a lista inteira e a conta vira NaN — é o que a caixa abaixo mostra. Já ($pao, $bolo) => … tem dois parâmetros, e dois parâmetros são a assinatura da regra assíncrona: o segundo recebe o set, o valor devolvido é ignorado e o derivado nunca entrega nada. Quando um derivado de várias fontes der número errado, o primeiro lugar para olhar é a forma dos parâmetros.

Missão: a regra recebe a lista inteira de valores e o total vira NaN. Dê nome às duas posições da lista para a conta usar pão e bolo, e o clique deve mostrar Total: R$ 25.80.

<script>
  import { writable, derived } from 'svelte/store';

  const pao = writable(2);
  const bolo = writable(1);
  const total = derived([pao, bolo], (valores) => valores * 0.9 + 12);
</script>

<p>Total: R$ {$total.toFixed(2)}</p>
<button onclick={() => $bolo += 1}>mais um bolo</button>
<script>
  import { writable, derived } from 'svelte/store';

  const pao = writable(2);
  const bolo = writable(1);
  const total = derived([pao, bolo], ([p, b]) => p * 0.9 + b * 12);
</script>

<p>Total: R$ {$total.toFixed(2)}</p>
<button onclick={() => $bolo += 1}>mais um bolo</button>

A diferença entre o código inicial e a solução está no formato do parâmetro: (valores) => recebe a lista inteira e tenta multiplicar uma lista por um número; ([p, b]) => dá nome a cada posição. Por dentro, o derived assina as duas fontes, guarda o último valor de cada uma e só roda a regra quando todas já entregaram o primeiro valor.

6. O derivado é somente leitura

Não existe total.set(…) num store derivado. A tentativa falha na hora, com uma mensagem curta e direta, como você vai ver na seção 11. O motivo é o mesmo de não escrever a lápis numa coluna que se preenche sozinha: na próxima mudança das fontes, o número seria recalculado e a sua escrita desapareceria sem aviso.

Se você precisa de um valor que seja calculado e ajustável, o caminho é outro: guarde o ajuste num store comum (um desconto, por exemplo) e inclua esse store na conta do derivado. Assim o ajuste tem set, a conta tem a regra, e cada um cuida do seu papel:

<script>
  import { writable, derived } from 'svelte/store';

  const subtotal = writable(13.8);
  const desconto = writable(0);
  const total = derived([subtotal, desconto], ([$subtotal, $desconto]) => $subtotal - $desconto);
</script>

<p>Total: R$ {$total.toFixed(2)}</p>
<p>Total: R$ 13.80</p>

Sempre que a Ana dá desconto, ela escreve em desconto; o total se ajusta. O derivado continua sem set, e ninguém precisa lembrar de refazer a subtração em cada botão. Esse é o padrão que escala: quanto mais entradas viram stores próprios, menos casos especiais a regra precisa prever.

7. $derived × derived: qual usar

Os dois têm "derived" no nome e fazem contas, mas vivem em mundos diferentes. A tabela abaixo é o resumo honesto:

derived$derived
Onde moranum módulo .js ou no <script>dentro do componente, sempre
De quem dependede outros storesde qualquer valor reativo: $state, $props ou $store
Quem pode lerqualquer componente que importarsó o componente onde foi declarado (ou quem o receber)
Tem set?nãonão (é uma constante reativa)
Melhor usoregra de negócio compartilhadaformatação e conta de tela

Na prática, o projeto da Ana tem os dois. O total do pedido é derived, porque o caixa e a vitrine precisam do mesmo número. Já o texto "R$ 1,80" com vírgula é $derived, porque é uma preocupação de quem desenha a tela. E o detalhe que pega todo mundo: dentro de $derived você não usa o store, usa o valor dele. O cifrão continua ali, mas ele é do store, não da runa:

<script>
  import { writable, derived } from 'svelte/store';

  const pao = writable(2);
  const total = derived(pao, (n) => n * 0.9);
  const precoNaTela = $derived($total.toFixed(2).replace('.', ','));
</script>

<p>R$ {precoNaTela}</p>
<p>R$ 1,80</p>

O $total assina o derivado e o $derived recalcula o texto a cada mudança. Dois mecanismos, um resultado: o preço na tela sempre acompanha a quantidade de pães, e a conta do dinheiro continua num lugar só. Se você escrever $derived(total.toFixed(2)), sem o cifrão do store, a runa não tem nada para observar e o texto nunca muda — é o erro silencioso mais comum desta seção.

8. O derivado num módulo

Quando a regra é do negócio e não da tela, ela vai para src/lib, junto com as fontes. O arquivo fica assim:

import { writable, derived } from 'svelte/store';

export const paes = writable(2);
export const bolos = writable(1);

// o total não é guardado: ele é recalculado a cada mudança de pães ou bolos
export const total = derived([paes, bolos], ([$paes, $bolos]) => $paes * 0.9 + $bolos * 12);

E o componente só consome. Aqui o mesmo derivado aparece dentro de <script module>, que roda uma vez por arquivo — é a forma de mostrar o padrão sem criar três arquivos:

<script module>
  import { writable, derived } from 'svelte/store';

  export const paes = writable(2);
  export const duzias = derived(paes, (n) => n / 12);
</script>

<p>{$paes} pães são {$duzias.toFixed(2)} dúzias</p>
<p>2 pães são 0.17 dúzias</p>

O terminal da Ana mostra o outro lado: o módulo é JavaScript puro, então dá para exercitá-lo sem navegador. O cat primeiro, para lembrar o que está lá:

ana@notebook:~/loja$ cat src/lib/total.js
import { writable, derived } from 'svelte/store';

export const paes = writable(2);
export const bolos = writable(1);

// o total não é guardado: ele é recalculado a cada mudança de pães ou bolos
export const total = derived([paes, bolos], ([$paes, $bolos]) => $paes * 0.9 + $bolos * 12);

9. get(): a foto do valor

get lê o valor de qualquer store — inclusive de um derivado — e devolve na hora. Por dentro, ele assina e cancela a assinatura imediatamente, o que dá exatamente o valor atual sem deixar ninguém inscrito:

<script>
  import { writable, derived, get } from 'svelte/store';

  const paes = writable(2);
  const duzias = derived(paes, (n) => n / 12);
  const comecou = get(duzias);
</script>

<p>Começou em {comecou.toFixed(2)} dúzias</p>
<p>Começou em 0.17 dúzias</p>

A variável comecou guarda 0.1666… e não muda nunca. Se os pães forem para quatro, comecou continua 0.1666… e a tela continua mostrando 0.17 — enquanto {$duzias} mostraria 0.33. Isso é uma foto, e uma foto não é um espelho.

O uso certo de get é dentro de funções, onde você quer o valor do momento e não uma assinatura. O botão da Ana soma um ao valor que está no store naquele instante, mesmo que outro componente tenha mudado o valor no meio do caminho:

Missão: cada clique escreve 1 no store, então dois cliques mostram Cliques: 1. Leia o valor de agora com get para o segundo clique mostrar Cliques: 2.

<script>
  import { writable } from 'svelte/store';

  const cliques = writable(0);

  function somar() {
    cliques.set(1);
  }
</script>

<p>Cliques: {$cliques}</p>
<button onclick={somar}>+1</button>
<script>
  import { writable, get } from 'svelte/store';

  const cliques = writable(0);

  function somar() {
    cliques.set(get(cliques) + 1);
  }
</script>

<p>Cliques: {$cliques}</p>
<button onclick={somar}>+1</button>

get(cliques) é esse mesmo assinar-e-cancelar, pronto na biblioteca: ele devolve o valor de agora e não deixa ninguém inscrito. A solução troca set(1) por set(get(cliques) + 1) — e a tela sobe 1, 2, 3 a cada clique.

E aqui está a prova de que o módulo funciona fora do componente, no terminal, sem navegador nenhum:

ana@notebook:~/loja$ node --input-type=module -e "import { get } from 'svelte/store'; import { paes, total } from './src/lib/total.js'; console.log('total:', get(total)); paes.set(4); console.log('com 4 paes:', get(total));"
total: 13.8
com 4 paes: 15.6

Duas leituras, dois valores diferentes, e nenhum componente envolvido. O primeiro get calculou o total com dois pães; depois o set mudou a fonte; o segundo get recalculou com quatro. O derivado não "lembra" nada entre as duas chamadas: ele só sabe fazer a conta com o que está nas fontes agora.

10. Derivado assíncrono e o valor inicial

Uma regra pode depender de algo lento: uma consulta, um arquivo, uma promessa. Nesse caso a função pode ser async e recebe um set como segundo argumento para entregar o resultado quando estiver pronto. O problema é o intervalo: o que aparece na tela enquanto a conta não termina? É para isso que existe o terceiro argumento, o valor inicial.

<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(2);
  const conta = derived(paes, async ($paes, set) => {
    await new Promise((r) => setTimeout(r, 10));
    set($paes * 10);
  }, 'calculando...');
</script>

<p>{$conta}</p>
<p>calculando...</p>

A renderização no servidor mostra o valor inicial, porque a conta ainda não terminou. No navegador, dez milissegundos depois, o parágrafo passa a mostrar 20. A sequência de valores que os inscritos recebem é ["calculando...", 20] — primeiro o inicial, depois o resultado. Sem o terceiro argumento, o primeiro valor seria undefined e a tela mostraria um buraco.

ana@notebook:~/loja$ node --input-type=module -e 'import { writable, derived } from "svelte/store"; const p = writable(2); const c = derived(p, async ($v, set) => { await new Promise((r) => setTimeout(r, 10)); set($v * 10); }, "calculando..."); const vistos = []; c.subscribe((v) => vistos.push(v)); await new Promise((r) => setTimeout(r, 50)); console.log(JSON.stringify(vistos));'
["calculando...",20]
Assíncrono muda a ordem das coisas

Com uma regra assíncrona, o derivado pode entregar um valor velho depois de um novo, se duas contas demorarem tempos diferentes. Para telas simples isso não aparece; quando aparecer, a solução é cancelar a conta antiga dentro da função de retorno do derived — o mesmo lugar onde o subscribe devolve a função de cancelamento.

11. Quando dá errado

As três mensagens abaixo saíram do compilador e do renderizador desta versão, copiadas como estão.

Erro 1 — escrever num derivado

O derivado não tem set. Chamar o método que não existe quebra na primeira execução:

<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(2);
  const duzias = derived(paes, (n) => n / 12);

  duzias.set(5);
</script>

<p>{$duzias}</p>
Erro ao renderizar: duzias.set is not a function

Repare que a mensagem traz o nome da sua variável: duzias.set is not a function. Ela não é um erro de sintaxe — o código compila. É o JavaScript dizendo que a propriedade set não existe naquele objeto. A correção é escrever na fonte (paes.set(60)) e deixar o derivado recalcular.

Erro 2 — regra que não é função

O segundo argumento de derived tem de ser uma função. Um número ali parece inofensivo e quebra na hora de calcular:

<script>
  import { writable, derived } from 'svelte/store';

  const paes = writable(2);
  const dobro = derived(paes, 5);
</script>

<p>{$dobro}</p>
Erro ao renderizar: fn is not a function

fn é o nome interno que a biblioteca dá ao segundo argumento. A mensagem é seca porque o erro é de tipo, não de intenção: onde o Svelte esperava (n) => n * 2, encontrou o número 5.

Erro 3 — importar do lugar errado

derived não mora em svelte; ele mora em svelte/store. Trocar um pelo outro produz um erro de módulo, não de sintaxe:

<script>
  import { derived } from 'svelte';
  import { writable } from 'svelte/store';

  const paes = writable(2);
  const dobro = derived(paes, (n) => n * 2);
</script>

<p>{$dobro}</p>
Erro ao renderizar: The requested module 'svelte' does not provide an export named 'derived'

"O módulo svelte não fornece uma exportação chamada derived." As runas ($state, $derived) são do compilador e não precisam de import; as funções de store precisam, e vêm de svelte/store. Guarde os dois endereços: svelte para setContext, getContext, onMount e tick; svelte/store para writable, readable, derived, get e readonly.

Para não esquecer

derived é uma função importada de svelte/store que devolve um store; $derived é uma runa que declara uma constante reativa dentro do componente. Se você precisa que outro componente leia a conta, é derived. Se a conta só existe para montar o texto daquela tela, é $derived.

Exercícios

1. O que derived(paes, (n) => n / 12) devolve?

2. Por que derived não tem set?

3. O que get(store) faz?

Complete o código

import { writable, } from 'svelte/store';

const pao = writable(2);
const bolo = writable(1);

const total = derived(, ([$pao, $bolo]) => $pao * 0.9 + $bolo * 12);

Resumo

  • derived(origem, regra) cria um store que calcula o valor a partir de outros stores.
  • A regra roda de novo a cada mudança das fontes; o derivado nunca guarda o resultado.
  • Várias fontes vão numa lista: derived([a, b], ([$a, $b]) => …) — e a regra recebe uma lista.
  • O derivado é somente leitura: set e update não existem nele.
  • Para um valor calculado e ajustável, guarde o ajuste num store comum e inclua na conta.
  • derived vem de svelte/store; $derived é runa e vive dentro do componente.
  • O terceiro argumento é o valor inicial, usado enquanto a regra assíncrona não terminou.
  • get(store) assina, lê e cancela: devolve uma foto do valor, não um visor.
  • Use get dentro de funções; no HTML, use $store ou $derived.
  • Os erros desta aula: set num derivado, regra que não é função e importar de svelte em vez de svelte/store.
