SvelteKit · Promessas e Streaming

A Ana tem um problema de relógio: o pão sai em dois segundos, mas o relatório de quanto cada pedido esperou leva vinte. Se o balcão só abrisse depois do relatório, a fila dobraria na porta. No SvelteKit acontece o mesmo, e a solução é a mesma da padaria: entregue o que já está pronto e mande o resto quando ficar. O nome disso é streaming, e a ferramenta é uma promessa devolvida pelo load junto com o bloco {#await}.

Você vai aprender
  • O que é uma promessa e por que o load pode devolver uma sem esperar.
  • Como o bloco {#await} mostra um texto enquanto o valor não chega.
  • Como {:then} e {:catch} completam o bloco.
  • Como medir o tempo do primeiro byte contra o tempo total com curl.
  • O que o SvelteKit escreve no HTML para "completar depois".
  • Por que o streaming só acontece no +page.server.js.
  • O que fazer quando a promessa falha no meio do caminho.
  • O custo do streaming: cache, robô de busca e layout que pula.
  • Três erros reais, com a mensagem do compilador e do servidor.
  • Como conferir tudo isso sem abrir o navegador.

1. A ideia: o balcão abre antes do bolo assar

Uma promessa é um valor que ainda não existe, mas vai existir. Você não segura o valor: segura o papel que diz "chego já". Em JavaScript, toda operação lenta devolve um desses — ler arquivo, consultar banco, chamar outra API. E existe uma regra que vale a pena decorar: uma promessa não bloqueia nada até alguém usar await nela.

O load do SvelteKit aproveita essa regra. Se você devolver a promessa dentro do objeto, sem await, o servidor responde na hora com o que já tem e deixa a promessa terminar em segundo plano. Quando ela termina, o restante do HTML é enviado pelo mesmo canal, ainda aberto. O navegador completa a página. O visitante nunca ficou olhando uma tela branca.

O ganho é de percepção. Uma página que leva 1,2 segundo para ficar completa parece instantânea se o título e a moldura aparecem em 0,1 segundo. Uma página que espera tudo para aparecer de uma vez parece lenta mesmo quando o total é o mesmo. Streaming não deixa o servidor mais rápido: ele muda quando as coisas chegam.

O bilhete "o relatório sai às 10h"O bloco {#await} com o texto de espera
A bandeja que chega depoisO segundo pedaço da resposta, com o valor

2. O load que devolve promessas

A rota /cozinha mostra duas coisas: a fila, que é rápida, e o relatório de espera, que é lento. O load busca a fila e devolve o relatório como promessa. Repare na ausência do await antes do async interno:

import { listar } from '#lib/pedidos.js';

const espera = (ms) => new Promise((ok) => setTimeout(ok, ms));

export async function load() {
	// a parte rápida sai na hora…
	const fila = listar();

	// …e a parte lenta sai depois, sem segurar a página
	const relatorio = (async () => {
		await espera(1200);
		return fila.map((p) => ({ ...p, espera: p.pronto ? '0 min' : '12 min' }));
	})();

	return { fila, relatorio };
}

O (async () => { … })() é uma função assíncrona chamada na hora: ela começa a trabalhar e devolve a promessa imediatamente. Se você escrevesse const relatorio = await (async () => …)(), o load esperaria e o streaming sumiria. É uma diferença de uma palavra que muda o comportamento inteiro.

Do lado da tela, o componente recebe data com os dois campos, mas trata o segundo como algo que pode não estar pronto. É para isso que existe o bloco {#await}:

<script>
	let { data } = $props();
</script>

<h1>Cozinha</h1>
<p>Na frente: {data.fila.length} pedido(s)</p>

{#await data.relatorio}
	<p>calculando o tempo de espera…</p>
{:then tempos}
	<ul>
		{#each tempos as t}
			<li>{t.cliente}: {t.espera}</li>
		{/each}
	</ul>
{:catch erro}
	<p>não deu para calcular: {erro.message}</p>
{/await}
{#await promessa}
abre o bloco. O conteúdo aqui dentro aparece enquanto a promessa não resolve — é o texto de espera.
{:then valor}
o pedaço que aparece quando a promessa dá certo. O nome depois de then é a variável que recebe o resultado.
{:catch erro}
o pedaço que aparece quando dá errado. Aqui, um objeto de erro; erro.message é o texto da falha.
{/await}
fecha o bloco. Cada {#await} precisa de um {/await}, senão o compilador reclama.
await
a palavra do JavaScript que espera. Dentro do load, ela existe e é o que tira o streaming. Aqui, dentro da marcação, ela é só o nome do bloco.

Atenção a uma confusão comum: o {#await} da marcação e o await do JavaScript são coisas diferentes com o mesmo nome. Um é bloco de HTML, o outro é operador de linguagem. O bloco não espera nada — ele desenha conforme. O operador bloqueia a função até o valor chegar.

3. A saída real: o que o servidor manda primeiro

Para ver o streaming sem navegador, o curl tem duas medidas úteis: time_starttransfer é quando o primeiro byte chegou, e time_total é quando a resposta terminou. Se os dois números forem parecidos, não houve transmissão em partes. Se o primeiro for bem menor, houve.

ana@notebook:~/loja$ curl -s -o /dev/null -w 'primeiro byte %{time_starttransfer}s · total %{time_total}s\n' localhost:5173/cozinha
primeiro byte 0.097875s · total 1.256349s

Um décimo de segundo para o primeiro byte, um segundo e um quarto para terminar. A diferença é exatamente o espera(1200) do load: a página saiu com a fila e com o aviso, e o relatório chegou depois, pelo mesmo cano. Se você comentar o return da promessa e usar await, os dois números passam a ser iguais.

O HTML que chega primeiro contém o texto de espera, e não a lista. Este é o componente isolado, compilado de verdade, com uma promessa que resolve na hora — mesmo assim, a primeira renderização mostra o aviso:

<script>
	const relatorio = Promise.resolve(['Ana', 'Bia']);
</script>

{#await relatorio}
	<p>calculando…</p>
{:then nomes}
	<p>{nomes.length} pedidos</p>
{/await}
<p>calculando…</p>

Não é falha: é o retrato do instante zero. O renderizador do servidor não espera promessa nenhuma; ele desenha o que dá e devolve. Quem completa o resto é o navegador, quando o pedaço final chega.

E o tal pedaço final tem uma cara. No fim do HTML do /cozinha vem um <script> com o valor já resolvido:

ana@notebook:~/loja$ curl -s localhost:5173/cozinha | grep -o 'calculando o tempo de espera…'
calculando o tempo de espera…
ana@notebook:~/loja$ curl -s localhost:5173/cozinha | tail -c 130
nte:"Ana",sabor:"frango",pronto:true,espera:"0 min"},{id:2,cliente:"Bia",sabor:"queijo",pronto:false,espera:"12 min"}]])</script>

Aquele final é o SvelteKit fechando o buraco deixado pela promessa. No meio do HTML, no lugar do relatório, ficou um marcador — algo como relatorio:__sveltekit_dev.defer(1) — dizendo "este valor chega no pedaço 1". O script no fim entrega o pedaço 1. No build de produção o nome muda, a ideia não.

Missão: a promessa entrega uma lista de nomes depois de 300 ms. Enquanto isso o aviso aparece; depois, mostre 2 pedidos.

<script>
	const relatorio = new Promise((ok) => {
		setTimeout(() => ok(['Ana', 'Bia']), 300);
	});
</script>

{#await relatorio}
	<p>calculando…</p>
{:then nomes}
	<p>{nomes} pedidos</p>
{/await}
<script>
	const relatorio = new Promise((ok) => {
		setTimeout(() => ok(['Ana', 'Bia']), 300);
	});
</script>

{#await relatorio}
	<p>calculando…</p>
{:then nomes}
	<p>{nomes.length} pedidos</p>
{/await}

O depois:500 da meta é o que dá tempo à promessa. Em uma caixa de teste, esperar é parte da verificação: sem isso, o avaliador olharia a tela no instante do aviso e diria que está errado. Guarde a ideia — teste de coisa assíncrona sempre tem uma espera, e escolher o tempo errado cria teste instável.

4. Por que só no +page.server.js

Streaming depende de o servidor manter a resposta aberta e mandar mais HTML depois. Isso exige que o load rode no servidor. No +page.js o mesmo objeto com promessa funciona, mas o SvelteKit não transmite: o HTML sai com o aviso e a promessa termina no navegador, sem nada a transmitir.

Não acredite na explicação sem medir. O teste abaixo usa uma rota de rascunho, /teste-promessa, com o mesmo load movido para um +page.js:

ana@notebook:~/loja$ curl -s -o /dev/null -w 'primeiro byte %{time_starttransfer}s · total %{time_total}s\n' localhost:5173/teste-promessa
primeiro byte 0.024051s · total 0.024117s

Os dois números praticamente iguais contam a história: não há pedaço para transmitir, porque o servidor não prometeu nada. O aviso sai junto com a página e o resto acontece no navegador. É útil para o visitante, mas não é streaming.

+page.server.jscom awaitnão: espera tudo

5. Quando a promessa falha

Promessa tem dois finais: deu certo ou deu errado. O {:catch} existe para o segundo caso, e ele não é opcional em página de verdade. Sem ele, a falha sobe e derruba o componente — e como o componente já foi enviado ao navegador, o visitante vê a página pela metade.

export function load() {
	const quebrada = Promise.reject(new Error('o forno desligou'));
	return { fila: [], relatorio: quebrada };
}

Com esse load, o servidor responde 200 e desenha o aviso. A rejeição aparece no terminal, mas não impede a resposta — o SvelteKit já tinha mandado o primeiro pedaço:

Error: o forno desligou
    at load (src/routes/cozinha/+page.server.js:2:34)
200 GET /cozinha

No navegador, o {:catch} da página pega o erro e mostra o texto. Se você não tivesse escrito esse bloco, o erro apareceria como falha de renderização e o aviso "calculando…" ficaria na tela para sempre. Uma promessa sem tratamento é uma tela travada esperando algo que já falhou.

Missão: esta promessa já nasce rejeitada e a página quebra. Trate o erro e mostre deu ruim: o forno desligou.

<script>
	const relatorio = Promise.reject(new Error('o forno desligou'));
</script>

{#await relatorio}
	<p>calculando…</p>
{:then nomes}
	<p>{nomes.length} pedidos</p>
{/await}
<script>
	const relatorio = Promise.reject(new Error('o forno desligou'));
</script>

{#await relatorio}
	<p>calculando…</p>
{:then nomes}
	<p>{nomes.length} pedidos</p>
{:catch erro}
	<p>deu ruim: {erro.message}</p>
{/await}

O erro.message é o texto que você passou ao new Error(...). Em produção, cuidado com o que vai nessa mensagem: ela aparece na tela do visitante. "o forno desligou" é simpático; o caminho do arquivo e a consulta SQL não são.

6. O valor que não é promessa

O {#await} aceita qualquer coisa, não só promessa. Se o valor já estiver resolvido — uma lista, um número — o bloco cai direto no {:then}, sem passar pelo aviso. Isso é útil quando o campo pode vir de dois jeitos: prometido ou pronto.

E existe a forma curta, sem o bloco de espera: {#await promessa then valor} seguido do conteúdo. Serve quando não faz sentido mostrar aviso — uma lista que já está em cache, por exemplo. O efeito é o mesmo; muda só a quantidade de linhas.

{#await data.relatorio then tempos}
	<p>{tempos.length} pedidos com tempo calculado</p>
{/await}

Forma curta tem um custo: se a promessa falhar, não há {:catch} para onde ir. Use quando a falha não é possível ou quando ela não precisa de tratamento próprio. Em página com dado de fora, prefira a forma completa.

Missão: o data.relatorio é uma promessa, e a página tentou usá-la como lista antes de ela resolver. Espere a promessa e mostre 2 pedidos.

<script>
	const data = {
		relatorio: new Promise((ok) => setTimeout(() => ok(['Ana', 'Bia']), 300))
	};
</script>

<p>{data.relatorio.length} pedidos</p>
<script>
	const data = {
		relatorio: new Promise((ok) => setTimeout(() => ok(['Ana', 'Bia']), 300))
	};
</script>

{#await data.relatorio}
	<p>calculando…</p>
{:then nomes}
	<p>{nomes.length} pedidos</p>
{/await}

O erro do código inicial é silencioso: Promise.length é undefined, e a tela escreve "undefined pedidos". Nenhum aviso, nenhum erro — só um texto errado. É o mesmo tipo de defeito do campo com nome trocado, e a defesa é a mesma: olhar a saída de verdade, não a intenção.

7. O custo do streaming

Streaming não é de graça. A resposta fica aberta por mais tempo, o que ocupa uma conexão do servidor e deixa o cache mais difícil. Um proxy no meio do caminho pode segurar os pedaços até o fim e anular o ganho. E robôs de busca antigos leem só o primeiro pedaço, então o conteúdo importante não deve ficar apenas na parte transmitida.

Há também o pulo de layout. Quando o relatório chega, a lista aparece e empurra o que estava abaixo. Se a página tem botão no rodapé, ele muda de lugar na frente do leitor. A solução é reservar espaço: um min-height no contêiner do bloco, ou um esqueleto com a mesma altura do conteúdo final.

Não transmita segredo

O que chega no segundo pedaço viaja como texto no HTML, igual ao primeiro. Streaming muda o momento, não a visibilidade. Se o dado não pode ser lido pelo visitante, ele não pode ser mandado — nem depois, nem escondido.

Comece pelo await

Se a página ainda não tem problema de lentidão, escreva o load com await e pronto. Streaming é remédio para uma dor específica: uma parte lenta que não precisa segurar o resto. Adicionar promessa sem necessidade troca simplicidade por complexidade e não melhora nada.

8. Quando dá errado

Erro 1 — bloco {#await} sem fechar

Todo bloco aberto precisa fechar. O compilador aponta o fim do arquivo, não o começo do bloco, porque é ali que ele desiste de esperar.

<script>
	let { data } = $props();
</script>

{#await data.relatorio}
	<p>calculando…</p>
{:then tempos}
	<p>{tempos.length} pedidos</p>
Erro de compilação (linha 5, coluna 0): Block was left open

"Block was left open" quer dizer "bloco ficou aberto". A linha citada é a última do arquivo. Conte os pares: cada {#await} pede um {/await}, e o mesmo vale para {#if}, {#each} e {#snippet}.

Erro 2 — promessa rejeitada sem tratamento

O servidor responde, o aviso fica na tela e o erro só aparece no terminal. Quem olha a página não vê nada de errado — só um "calculando…" eterno.

export function load() {
	const quebrada = Promise.reject(new Error('o forno desligou'));
	return { fila: [], relatorio: quebrada };
}
Error: o forno desligou
    at load (src/routes/cozinha/+page.server.js:2:34)
200 GET /cozinha

O 200 no fim é o detalhe cruel: o status é de sucesso porque o primeiro pedaço saiu bem. A correção é no componente, com {:catch}, e no servidor, evitando promessa que nasce rejeitada — prefira criar a promessa que pode falhar dentro de um try.

Erro 3 — await no lugar errado

Com await antes da função assíncrona interna, o load espera o relatório inteiro. A página funciona, o resultado é o mesmo — e o streaming desaparece sem nenhum aviso.

const relatorio = await (async () => {
	await espera(1200);
	return fila.map((p) => ({ ...p, espera: p.pronto ? '0 min' : '12 min' }));
})();
ana@notebook:~/loja$ curl -s -o /dev/null -w 'primeiro byte %{time_starttransfer}s · total %{time_total}s\n' localhost:5173/cozinha
primeiro byte 1.231678s · total 1.231746s

Os dois números praticamente iguais são a assinatura do "esperei tudo". Não há mensagem de erro porque não há erro: só uma otimização que deixou de acontecer. Meça antes e depois quando mexer nesse trecho.

9. A navegação interna também espera

Quando o visitante chega pela primeira vez, o servidor manda o HTML em pedaços, como você viu. Quando ele clica num link interno e vai de /painel para /cozinha, não há HTML novo: o SvelteKit pede só o data da nova rota, em JSON, e o componente já está no navegador. O campo relatorio chega como o mesmo tipo de promessa, e o mesmo {#await} trata os dois casos.

Isso é conveniente e explica por que o componente não precisa saber de onde veio. O bloco {#await} funciona igual nos dois caminhos: mostra o aviso, recebe o valor, desenha. Quem muda é o transporte — HTML em pedaços na primeira visita, JSON na navegação — e não o seu código.

Se a promessa demora e o visitante clica em outro link antes dela resolver, o SvelteKit cancela a navegação e descarta a resposta antiga. Você não precisa de AbortController para isso: o trabalho de cancelar é dele. Vale saber porque é comum ver o aviso "calculando…" sumir sem nunca ter mostrado o resultado — foi uma navegação abandonada.

Resumo

  • Promessa é um valor que ainda não existe; o load pode devolvê-la sem esperar.
  • Devolver a promessa no objeto faz o SvelteKit enviar o HTML em partes: isso é streaming.
  • {#await} mostra o conteúdo de espera; {:then} e {:catch} completam o bloco.
  • Sem {:catch}, uma promessa rejeitada deixa a tela parada no aviso.
  • O streaming só acontece no +page.server.js; no +page.js a promessa resolve no navegador.
  • await antes da função assíncrona interna mata o streaming sem gerar erro.
  • curl com %{time_starttransfer} e %{time_total} mostra se houve transmissão em partes.
  • O valor transmitido chega num <script> no fim do HTML, fechando o marcador deixado no meio.
  • O custo: resposta aberta por mais tempo, cache mais difícil e layout que pula se o espaço não for reservado.
  • Streaming não esconde dado: o que chega depois também é visível no navegador.
