Svelte · Testando um Componente

O teste do troco da Ana estava verde, e o preço na tela aparecia sem a segunda casa: R$ 2.5. A conta certa não garante a tela certa. Nesta aula ela escreve um teste que abre o componente num navegador de mentira, procura o texto na tela e clica no botão — e descobre no caminho por que o primeiro teste quebrou com uma mensagem sobre servidor.

  • Para que serve o jsdom: um DOM de mentira para o teste.
  • As três peças do teste de componente: render, screen e fireEvent.
  • Como procurar elementos por texto e por papel (getByText, getByRole).
  • Por que o teste quebra com lifecycle_function_unavailable e como consertar.
  • O que a condição browser faz no vite.config.js.
  • Como simular um clique com fireEvent e conferir o texto novo.
  • O que document is not defined diz sobre o ambiente do teste.
  • Os três erros desta aula, com a saída real do Vitest.

1. A ideia: a tela também tem regra

Um teste de módulo pergunta: “a conta está certa?”. Um teste de componente pergunta: “o que a pessoa vê está certo?”. São perguntas diferentes, e a Ana precisou das duas na mesma tarde.

A regra da tela pode ser simples e mesmo assim quebrar: o preço tem duas casas, o botão está escrito “Cliques:” e não “Clique:”, o título é um h2 e não um strong. Nada disso aparece no teste da função, porque a função nem sabe que existe tela.

Testar componente é mais trabalhoso que testar função: precisa de um DOM (a árvore de elementos) e de um jeito de procurar coisas nele. Em troca, você ganha a certeza de que a peça que a pessoa usa realmente mostra o que devia.

2. Teste de módulo × teste de componente

As duas coisas convivem no mesmo projeto e rodam com o mesmo comando. A diferença está no que cada arquivo importa e no que ele confere:

Como o teste de componente é mais lento, a ordem natural é escrever primeiro os de módulo e reservar os de componente para o que só a tela pode provar: o texto que aparece, o elemento que existe, a interação que muda algo.

3. As três peças: render, screen e fireEvent

Todo teste de componente usa as mesmas três ferramentas, vindas da Testing Library. Elas fazem o serviço de abrir, procurar e agir.

render(Cartao, { … })
monta o componente num DOM de teste, passando as propriedades do segundo argumento. É o equivalente a abrir a página.
screen
a “tela” do teste: um atalho para procurar elementos no que foi montado. Sempre se procura em screen, nunca no documento inteiro.
getByText('Sonho')
procura um elemento cujo texto seja exatamente aquele. Se não achar, o teste falha e mostra o DOM que existia.
getByRole('button')
procura pelo papel do elemento na página, e não pelo texto. Um <button> tem o papel button; um <div> não tem.
fireEvent.click(botao)
dispara o evento de clique no elemento, como se a pessoa tivesse clicado. Depois dele, a tela deve ter mudado.

A escolha entre getByText e getByRole não é estilo. Procurar por texto prende o teste à redação (“Sonho”); procurar por papel prende o teste à estrutura (existe um botão). Um teste que procura papel costuma durar mais, porque a redação muda com o marketing e o papel, não.

4. O componente a testar

O alvo é o cartão de produto que a Ana usa na vitrine. Ele recebe duas propriedades e desenha um artigo com título e preço:

<script>
  let { titulo = 'Pão francês', preco = 0.9 } = $props();
</script>

<article>
  <h2>{titulo}</h2>
  <p>R$ {preco.toFixed(2)}</p>
</article>
<article><h2>Pão francês</h2> <p>R$ 0.90</p></article>

Esse é o HTML que o componente produz. Um teste de componente faz a mesma pergunta, mas pelo caminho da tela: “depois de montar com titulo: 'Sonho' e preco: 2.5, existe na tela um elemento escrito Sonho e outro escrito R$ 2.50?”.

O segundo componente é ainda menor, e serve para testar interação. Ele tem um botão que conta cliques:

<script>
  let cliques = $state(0);
</script>

<button onclick={() => cliques++}>Cliques: {cliques}</button>
<button>Cliques: 0</button>

5. Instalando o ambiente

O Vitest sozinho não sabe o que é um botão: ele roda em Node, onde não existe document. Faltam duas peças — um DOM de mentira e a biblioteca que sabe procurar elementos nele:

ana@notebook:~/loja$ npm install -D vitest jsdom @testing-library/svelte

added 44 packages, and audited 101 packages in 6s

19 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

jsdom é o DOM de mentira: um objeto em memória com a mesma forma do navegador, sem tela. @testing-library/svelte é a ponte entre o componente Svelte e esse DOM — é de onde vêm render, screen e fireEvent.

Nada disso vai para o site publicado: são dependências de desenvolvimento, como o próprio Vitest.

6. O primeiro teste e a surpresa do servidor

Com o ambiente instalado, o teste parece simples: montar o componente e procurar dois textos.

import { render, screen } from '@testing-library/svelte';
import { describe, it, expect } from 'vitest';
import Cartao from './Cartao.svelte';

describe('Cartao', () => {
  it('mostra o título e o preço com duas casas', () => {
    render(Cartao, { titulo: 'Sonho', preco: 2.5 });
    expect(screen.getByText('Sonho')).toBeTruthy();
    expect(screen.getByText('R$ 2.50')).toBeTruthy();
  });
});

Rodando, o teste falha — mas não pelo motivo que a Ana esperava:

 ❯ src/lib/Cartao.test.js (1 test | 1 failed) 16ms
   ❯ Cartao (1)
     × mostra o título e o preço com duas casas 13ms

 FAIL  src/lib/Cartao.test.js > Cartao > mostra o título e o preço com duas casas
Svelte error: lifecycle_function_unavailable
`mount(...)` is not available on the server
https://svelte.dev/e/lifecycle_function_unavailable

Leia a segunda linha: “mount(...) não está disponível no servidor”. O teste está rodando em Node, e o Node, para o pacote do Svelte, se apresenta como servidor — igual ao que acontece quando o SvelteKit desenha uma página antes de mandar para o navegador. No servidor não existe DOM, então não há o que montar.

Svelte error: lifecycle_function_unavailable
o código do erro. Ele não é do seu componente: é do Svelte avisando que a função chamada não existe naquele ambiente.
`mount(...)` is not available on the server
a explicação em uma linha: a função de montar não existe no servidor.
https://svelte.dev/e/lifecycle_function_unavailable
o endereço da documentação do erro. O Svelte imprime o link em toda mensagem, porque as mensagens são curtas.

A causa é a forma como o Node resolve importações: por padrão, ele pega a versão de servidor do pacote svelte. Existe uma condição chamada browser que diz “neste teste, use a versão de navegador”. É isso que a configuração abaixo faz.

7. O conserto no vite.config.js

Duas linhas resolvem: uma diz ao Vitest para usar o DOM de mentira, a outra pede a versão de navegador do Svelte quando o Vitest está rodando.

import { defineConfig } from 'vite';
import { svelte } from '@sveltejs/vite-plugin-svelte';

export default defineConfig({
  plugins: [svelte()],
  resolve: process.env.VITEST ? { conditions: ['browser'] } : undefined,
  test: {
    environment: 'jsdom'
  }
});
plugins: [svelte()]
o plugin que já existia: ensina o Vite a ler arquivos .svelte. Sem ele, o teste nem entende o componente.
process.env.VITEST ? … : undefined
um condicional: se a variável VITEST existe (ou seja, quem está rodando é o Vitest), use o objeto; se não, nada. O build normal continua igual.
conditions: ['browser']
a condição que faz o pacote svelte entregar a versão de navegador, com mount disponível.
test: { environment: 'jsdom' }
diz ao Vitest para criar o DOM de mentira em cada arquivo de teste. É o que faz document existir.

Com a configuração no lugar, o mesmo teste passa. O resumo mostra só o essencial:

 ✓ src/lib/Cartao.test.js (1 test) 92ms

 Test Files  1 passed (1)
      Tests  1 passed (1)
   Start at  17:25:43
   Duration  3.90s (transform 53%, environment 31%, import 13%, tests 2%)

Repare no tempo: 3,90 s, contra os 357 ms do teste de módulo da aula anterior. A diferença vem do ambiente: criar um DOM de mentira custa caro. É por isso que se testa o máximo possível no módulo, onde não há DOM.

8. Testando o clique

Interação se testa em três passos: montar, achar o elemento, agir. Depois do clique, o texto na tela precisa ter mudado.

import { render, screen, fireEvent } from '@testing-library/svelte';
import { describe, it, expect } from 'vitest';
import Cartao from './Cartao.svelte';
import Contador from './Contador.svelte';

describe('Contador', () => {
  it('soma um a cada clique', async () => {
    render(Contador);
    const botao = screen.getByRole('button');
    await fireEvent.click(botao);
    await fireEvent.click(botao);
    expect(botao.textContent).toContain('Cliques: 2');
  });
});

O teste inteiro passa, e o resumo conta os dois arquivos e os quatro casos:

 ✓ src/lib/Cartao.test.js (2 tests) 140ms
 ✓ src/lib/troco.test.js (2 tests) 5ms

 Test Files  2 passed (2)
      Tests  4 passed (4)
   Start at  17:26:27
   Duration  5.21s (environment 70%, transform 20%, import 7%, tests 3%)

Duas coisas merecem atenção nesse resultado. A primeira: getByRole('button') encontrou o botão sem procurar por texto — é o jeito resistente a mudança de redação. A segunda: o relatório avisa que o ambiente consumiu 70% do tempo, com uma dica de configuração. Não é erro; é informação de quem mediu.

Missão: o teste procura o elemento com getByRole('button'), e o componente usa um div com onclick. Troque pela tag que o teste consegue achar — e que também funciona com teclado.

<script>
  let cliques = $state(0);
</script>

<div onclick={() => cliques++}>Cliques: {cliques}</div>
<script>
  let cliques = $state(0);
</script>

<button onclick={() => cliques++}>Cliques: {cliques}</button>

O erro do código inicial, ao rodar a caixa, é não achei o elemento "button" para clicar — a mesma coisa que a Testing Library diria com outras palavras. Um div não tem papel de botão: para o teste, ele não existe como botão. E para quem navega com teclado, também não.

9. Quando dá errado

As três saídas abaixo vieram de execuções reais nesta versão. As duas primeiras param o teste antes de qualquer verificação; a terceira é a mais comum de todas.

Erro 1 — montar sem a versão de navegador

O teste roda, mas o render chama uma função que não existe no ambiente de servidor escolhido pelo Node.

Svelte error: lifecycle_function_unavailable
`mount(...)` is not available on the server
https://svelte.dev/e/lifecycle_function_unavailable

O conserto é a condição browser no vite.config.js. Note que o erro fala de mount, uma função que você nem chamou: quem chama é o render da Testing Library.

Erro 2 — montar sem DOM

Se a configuração tem a condição de navegador mas esquece o environment: 'jsdom', o JSX do teste funciona e o document não existe.

ReferenceError: document is not defined
 ❯ setup node_modules/@testing-library/svelte-core/src/setup.js:68:56

“document não está definido”. O teste está rodando em Node puro, onde não existe árvore de elementos. A linha apontada é da biblioteca, não do seu teste — a causa está na configuração, e é ali que se conserta.

Erro 3 — o texto não existe na tela

O componente montou, o texto é outro, e a Testing Library mostra o DOM inteiro para você ver o que havia.

TestingLibraryElementError: Unable to find an element with the text: R$ 2.5. This could be because the text is broken up by multiple elements. In this case, you can provide a function for your text matcher to make your matcher more flexible.

Ignored nodes: comments, script, style
<body>
  <div>
    <article>
      <h2>
        Sonho
      </h2>
      <p>
        R$ 2.50
      </p>
    </article>
  </div>
</body>

“Não consigo achar um elemento com o texto: R$ 2.5”. O DOM impresso logo abaixo mostra a resposta: o texto real é R$ 2.50. A expectativa estava errada, não o componente — e a mensagem economizou uma sessão de depuração.

10. O preço formatado também é regra

Voltando ao problema que abriu a aula: a conta do troco estava certa e a tela mostrava R$ 2.5. Um teste de componente pega isso porque compara texto, não número.

Missão: um teste que procura R$ 2.50 na tela falha, porque o componente mostra o número cru. Formate o preço com duas casas.

<script>
  let preco = $state(2.5);
</script>

<article>
  <h2>Sonho</h2>
  <p>R$ {preco}</p>
</article>
<script>
  let preco = $state(2.5);
</script>

<article>
  <h2>Sonho</h2>
  <p>R$ {preco.toFixed(2)}</p>
</article>

A regra “dinheiro tem duas casas” não pertence à conta: pertence à apresentação. Por isso ela se testa na tela. Se a mesma formatação aparece em cinco componentes, vale extrair uma peça — como o PrecoLinha da aula de componentes pequenos — e testar essa peça uma vez.

Missão: o teste usa screen.getAllByRole('article') e espera dois cartões. O componente desenha só o primeiro produto. Repita o cartão para cada item da lista.

<script>
  let produtos = $state([
    { nome: 'Sonho', preco: 2.5 },
    { nome: 'Pão francês', preco: 0.9 }
  ]);
</script>

<article>
  <h2>{produtos[0].nome}</h2>
  <p>R$ {produtos[0].preco.toFixed(2)}</p>
</article>
<script>
  let produtos = $state([
    { nome: 'Sonho', preco: 2.5 },
    { nome: 'Pão francês', preco: 0.9 }
  ]);
</script>

{#each produtos as produto}
  <article>
    <h2>{produto.nome}</h2>
    <p>R$ {produto.preco.toFixed(2)}</p>
  </article>
{/each}

Quando o componente passa a desenhar a lista, um teste que procura getByRole('article') começa a falhar com “found multiple elements”: existem dois artigos, e o getBy… espera um só. A troca é usar getAllByRole('article') e conferir o tamanho da lista — o assunto da seção de referência.

11. O que não vale a pena testar

Teste também custa: cada caso é código para escrever, ler e manter. Um teste que confere detalhe interno quebra a cada refatoração sem que nada tenha ficado errado — e a equipe aprende a ignorar a barra vermelha. Três coisas costumam não valer o esforço:

Não vale testarPor quê
que o Svelte desenha {titulo}é o framework fazendo o trabalho dele; o teste não acrescenta nada
nome de classe CSS internomuda com o visual; quebra o teste sem quebrar a tela
a mesma conta que o teste de módulo já confereduplica o caso e dobra o tempo de manutenção
texto exato de mensagem de bibliotecamuda quando a biblioteca atualiza; confira o comportamento

O critério é o mesmo da divisão de componentes: teste o que a pessoa percebe. “Aparece o preço com duas casas”, “o botão conta”, “a lista mostra os dois produtos” são regras do ponto de vista de quem usa. “O segundo div tem a classe cartao” é detalhe de quem escreveu — e detalhe de quem escreveu muda toda semana.

Também vale resistir à tentação de testar tudo. Um projeto com cinco testes que provam as regras importantes pega mais erro real que cinquenta testes de detalhe, porque os cinco são lidos e mantidos. A conta que a Ana aprendeu a fazer é simples: se o teste não descreve uma regra que ela explicaria para o padeiro, provavelmente não precisa existir.

Exercícios

1. O teste falhou com lifecycle_function_unavailable. O que fazer?

2. Por que getByRole('button') costuma durar mais que getByText('Cliques: 0')?

3. O que quer dizer ReferenceError: document is not defined num teste de componente?

Complete o código

import { render, screen } from '@testing-library/svelte';
import Cartao from './Cartao.svelte';

render(Cartao, { titulo: 'Sonho', preco: 2.5 });
expect(screen.('Sonho')).toBeTruthy();
expect(screen.('R$ 9.99')).toBeNull();

Resumo

  • Teste de módulo confere a conta; teste de componente confere a tela.
  • O componente precisa de DOM: jsdom é o DOM de mentira usado no teste.
  • render monta, screen procura, fireEvent age.
  • getByText procura pelo texto exato; getByRole pelo papel do elemento.
  • getAllByRole devolve lista e serve para vários elementos iguais.
  • lifecycle_function_unavailable quer dizer que o Svelte entregou a versão de servidor.
  • A condição browser no vite.config.js resolve isso, e só quando o Vitest roda.
  • environment: 'jsdom' cria o document; sem ele, document is not defined.
  • Quando o texto não é achado, a mensagem imprime o DOM real — leia antes de mexer no componente.
  • Teste de componente é mais lento que o de módulo: use-o no que só a tela prova.
