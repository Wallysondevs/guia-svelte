SvelteKit · Testando Rotas

A Ana já sabe testar uma conta isolada: a aula de Vitest deixou o cálculo do troco coberto. Mas a cliente não digita uma função no navegador — ela abre /paes, envia uma encomenda e espera a resposta certa. Entre a conta e a tela existe a rota: o arquivo que busca os dados, o que recebe o formulário e o que devolve JSON. Nesta aula você chama esses arquivos direto do teste, sem navegador, e vê o que o Vitest responde de verdade quando a rota está certa e quando a expectativa está errada.

Você vai aprender
  • O que é uma rota no SvelteKit e quais funções dela dá para testar.
  • Como chamar um load de +page.server.js com uma URL de mentira.
  • Como conferir um redirect com isRedirect.
  • Como montar um FormData e testar uma action até o caso de erro 400.
  • Como testar um endpoint +server.js com Request e Response.
  • Como passar um fetch falso para um load universal.
  • Por que a mensagem de falha aponta a linha da expectativa, e não a da rota.
  • O que muda entre testar uma função pura e testar uma rota.
  • Os três erros reais desta aula, com a saída do terminal.

1. A ideia: conferir o balcão, não só a receita

Na aula de Vitest, a Ana testou a conta do troco: entrou um número, saiu outro. É o teste mais fácil que existe, porque a função não conversa com ninguém. A rota é diferente. Ela recebe uma requisição, olha a URL, às vezes consulta o banco, às vezes devolve um erro 400 e às vezes manda o navegador para outro endereço. Testar a rota é conferir o balcão: o pedido entrou, a resposta saiu com o status certo e o corpo dizia o que devia dizer.

O ganho é o mesmo do teste de função, multiplicado. Uma rota muda por muitos motivos — alguém troca o nome do campo do formulário, muda o código de status, esquece de devolver o total. Sem teste, você descobre no sábado cheio, com a cliente na frente do balcão. Com teste, descobre em um segundo, antes de publicar.

O custo também existe: teste de rota exige montar os objetos que o SvelteKit montaria. Uma URL, um Request, um FormData, um fetch. Não é difícil, mas é diferente de chamar uma função com dois números. É esse vocabulário de mentira que esta aula ensina — e o nome técnico dele é dublê ou stub.

Na padariaNo teste de rota
O pedido que a cliente faz no balcãoO objeto event: url, request, params
A resposta: pão ou "acabou"O retorno do load ou o Response do endpoint
"Hoje não tem, volte amanhã"redirect(307, '/paes/promo')
"Falta o seu nome no pedido"fail(400, { erro: 'Diga o seu nome' })
O caderno onde a resposta é anotadaexpect(...), que compara e reclama

2. O que existe numa rota para testar

Uma rota do SvelteKit é uma pasta com arquivos de nome fixo. Cada arquivo tem uma responsabilidade, e cada responsabilidade pede um teste diferente:

ArquivoO que fazComo o teste chamaO que conferir
+page.server.jsbusca dados no servidor e trata formuláriosload({ url }) e actions.encomenda({ request })o objeto devolvido, o status, o erro
+page.jsbusca dados no servidor ou no navegadorload({ params, fetch })o que ele faz com a resposta do fetch
+server.jsum endpoint HTTP: devolve JSON, texto ou statusGET({ url }) e POST({ request })status, cabeçalhos e corpo
+page.svelteo desenho da telaprecisa de navegador simuladoo HTML que aparece

Repare que os três primeiros são funções JavaScript comuns, exportadas por um arquivo comum. O SvelteKit só as chama em produção com objetos que ele mesmo monta. No teste, você monta esses objetos à mão — e é justamente aí que mora a liberdade: dá para simular uma URL com ?promo=1 sem abrir navegador, e simular um formulário vazio sem digitar nada.

O quarto arquivo, o componente, é outra história. Ele espera um DOM, e o Node não tem um. Testar componente exige uma biblioteca de DOM, e o assunto fica para outra aula. Aqui o foco é a camada que decide: dados, status e destino.

Teste a rota antes de testar a tela

Se a rota devolve o total errado, nenhum teste de tela vai consertar. Começar pelas funções é mais barato: o teste roda em milissegundos, não precisa de navegador e aponta a linha exata do problema.

4. O primeiro teste: o load da rota

Comece pelo arquivo que a rota usa para buscar os pães. Ele tem um load e uma action de encomenda:

import { fail, redirect } from '@sveltejs/kit';
import { paes } from '#lib/paes.js';

export function load({ url }) {
  if (url.searchParams.has('promo')) {
    redirect(307, '/paes/promo');
  }
  return { paes, total: paes.length };
}

export const actions = {
  encomenda: async ({ request }) => {
    const dados = await request.formData();
    const nome = String(dados.get('nome') ?? '').trim();
    const quantidade = Number(dados.get('quantidade') ?? 0);

    if (!nome) {
      return fail(400, { nome, erro: 'Diga o seu nome' });
    }
    if (!Number.isInteger(quantidade) || quantidade < 1) {
      return fail(400, { nome, erro: 'Quantidade inválida' });
    }

    return { sucesso: true, nome, quantidade };
  }
};

O teste importa load e actions diretamente do arquivo. Nada de servidor, nada de navegador:

import { describe, it, expect } from 'vitest';
import { isRedirect } from '@sveltejs/kit';
import { load, actions } from './+page.server.js';

describe('rota /paes', () => {
  it('o load entrega os pães e o total', () => {
    const dados = load({ url: new URL('http://localhost/paes') });
    expect(dados.total).toBe(3);
    expect(dados.paes[0].nome).toBe('Pão francês');
  });

  it('pedir com promo manda para a página de promoção', () => {
    let erro;
    try {
      load({ url: new URL('http://localhost/paes?promo=1') });
    } catch (e) {
      erro = e;
    }
    expect(isRedirect(erro)).toBe(true);
    expect(erro.location).toBe('/paes/promo');
  });
});

describe('action encomenda', () => {
  function pedido(campos) {
    const dados = new FormData();
    for (const [chave, valor] of Object.entries(campos)) dados.set(chave, valor);
    return new Request('http://localhost/paes', { method: 'POST', body: dados });
  }

  it('aceita uma encomenda completa', async () => {
    const r = await actions.encomenda({ request: pedido({ nome: 'Ana', quantidade: '6' }) });
    expect(r).toEqual({ sucesso: true, nome: 'Ana', quantidade: 6 });
  });

  it('recusa quem esqueceu o nome', async () => {
    const r = await actions.encomenda({ request: pedido({ nome: '', quantidade: '2' }) });
    expect(r.status).toBe(400);
    expect(r.data.erro).toBe('Diga o seu nome');
  });
});

Quatro testes, duas famílias. O describe('rota /paes') cobre o load: um caso comum e um caso de redirecionamento. O describe('action encomenda') cobre o formulário: um pedido válido e um pedido sem nome. Repare que a função pedido existe só para não repetir a criação do FormData nas duas vezes.

A anatomia de um teste de rota

import { load, actions }
o teste importa as funções exportadas pelo arquivo da rota. É a mesma importação que o SvelteKit faria; a diferença é quem chama.
load({ url })
o primeiro argumento é o evento. Aqui ele traz só o que o load usa: uma URL de verdade, criada com new URL(...), apontando para localhost.
new FormData()
o corpo do formulário, montado à mão. Cada set vira um campo como se a cliente tivesse digitado.
new Request(url, { method, body })
a requisição que a action recebe. O Request é o mesmo objeto do navegador, e o Node 22 já o tem.
expect(...).toBe(...)
a comparação. Quando falha, o Vitest mostra o valor esperado e o recebido, na linha exata da expectativa.

Um detalhe que economiza tempo: load pode ser síncrono ou assíncrono, dependendo de como foi escrito. Se o seu for async, o teste precisa de await; se não for, o await não atrapalha. Use await sempre que tiver dúvida — o valor de um load assíncrono é uma promessa, e comparar a promessa com o objeto nunca dá certo.

5. Testando um redirect

O load da Ana tem uma regra: se a URL trouxer ?promo=1, o cliente vai para a página de promoção. No SvelteKit, redirect() não devolve um valor: ele lança uma exceção que o framework captura. O teste precisa fazer o mesmo — capturar e conferir.

É por isso que o teste usa try/catch e depois isRedirect(erro). O valor lançado não é um Error comum, e comparar erro.message não é confiável. A função isRedirect, importada de @sveltejs/kit, é a forma oficial de perguntar "isto é um redirecionamento?".

O mesmo vale para error(): existe isHttpError para conferir. E o código do status importa. Um 307 preserva o método e o corpo; um 303 transforma tudo em GET. Depois de um POST de formulário, o comum é 303; num redirecionamento de URL, 307 ou 308.

Não compare a mensagem do redirect

A mensagem interna de um redirect() muda entre versões. O contrato que você quer testar é o location, e não o texto. Teste erro.location, que é o endereço para onde o navegador vai.

6. Testando uma action com FormData

A action encomenda lê dois campos, valida e devolve um objeto. Quando algo falta, ela devolve fail(400, { ... }), que é um objeto com status e data — não uma exceção. O teste confere os dois:

describe('action encomenda', () => {
  function pedido(campos) {
    const dados = new FormData();
    for (const [chave, valor] of Object.entries(campos)) dados.set(chave, valor);
    return new Request('http://localhost/paes', { method: 'POST', body: dados });
  }

  it('aceita uma encomenda completa', async () => {
    const r = await actions.encomenda({ request: pedido({ nome: 'Ana', quantidade: '6' }) });
    expect(r).toEqual({ sucesso: true, nome: 'Ana', quantidade: 6 });
  });

  it('recusa quem esqueceu o nome', async () => {
    const r = await actions.encomenda({ request: pedido({ nome: '', quantidade: '2' }) });
    expect(r.status).toBe(400);
    expect(r.data.erro).toBe('Diga o seu nome');
  });
});

Três coisas merecem atenção. Primeiro: o formulário chega como texto, então quantidade é "6", e a action converte com Number. O teste confirma que a conversão aconteceu ao esperar quantidade: 6, sem aspas. Segundo: o fail tem status e data, e o teste lê os dois. Terceiro: a action é async, então o teste é async e usa await.

Missão: o load devolve total: 0 e a tela mostra Pães na lista: 0. Faça a função devolver a quantidade certa, do mesmo jeito que o teste expect(dados.total).toBe(3) espera.

<script>
  const paes = ['francês', 'forma', 'queijo'];
  function load() {
    return { total: 0 };
  }
  let dados = load();
</script>

<p>Pães na lista: {dados.total}</p>
<script>
  const paes = ['francês', 'forma', 'queijo'];
  function load() {
    return { total: paes.length };
  }
  let dados = load();
</script>

<p>Pães na lista: {dados.total}</p>

A caixa mostra por que o total errado é fácil de escrever e fácil de testar: a lista tem três itens, o retorno diz zero, e a tela obedece ao retorno. O teste não olha a lista — olha o que o load devolveu. É essa fronteira que o teste de rota protege.

7. Testando um endpoint +server.js

O endpoint é a rota que não desenha tela: ela responde JSON. O arquivo exporta uma função por método HTTP. O teste chama a função e recebe um Response de verdade, com status, headers e json():

import { json } from '@sveltejs/kit';
import { paes } from '#lib/paes.js';

export function GET({ url }) {
  const busca = (url.searchParams.get('busca') ?? '').toLowerCase();
  const encontrados = paes.filter((p) => p.nome.toLowerCase().includes(busca));
  return json({ total: encontrados.length, paes: encontrados });
}

export async function POST({ request }) {
  const corpo = await request.json();
  if (!corpo.nome) {
    return json({ erro: 'o nome é obrigatório' }, { status: 400 });
  }
  return json({ criado: { slug: 'novo', nome: corpo.nome } }, { status: 201 });
}
import { describe, it, expect } from 'vitest';
import { GET, POST } from './+server.js';

describe('endpoint /api/paes', () => {
  it('devolve 200 e a lista filtrada', async () => {
    const resposta = await GET({ url: new URL('http://localhost/api/paes?busca=queijo') });
    expect(resposta.status).toBe(200);
    const dados = await resposta.json();
    expect(dados.total).toBe(1);
    expect(dados.paes[0].slug).toBe('queijo');
  });

  it('responde 400 quando falta o nome', async () => {
    const resposta = await POST({
      request: new Request('http://localhost/api/paes', {
        method: 'POST',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify({})
      })
    });
    expect(resposta.status).toBe(400);
    expect(await resposta.json()).toEqual({ erro: 'o nome é obrigatório' });
  });
});

O teste do GET monta uma URL com ?busca=queijo e confere três coisas: o status 200, o total 1 e o slug do primeiro item. O teste do POST monta um Request com cabeçalho content-type: application/json e corpo vazio, e espera 400 com a mensagem de erro.

O cabeçalho não é enfeite: sem ele, request.json() não sabe que o corpo é JSON e a rota responde outra coisa. É o tipo de detalhe que o teste pega antes do navegador.

Missão: o teste do endpoint espera resposta.status igual a 400 e o corpo o nome é obrigatório. Faça a simulação responder os dois.

<script>
  let status = $state(200);
  let corpo = $state('lista de pães');

  function responder() {
    corpo = 'o nome é obrigatório';
  }
</script>

<button onclick={responder}>POST /api/paes sem nome</button>
<p>{status} · {corpo}</p>
<script>
  let status = $state(200);
  let corpo = $state('lista de pães');

  function responder() {
    status = 400;
    corpo = 'o nome é obrigatório';
  }
</script>

<button onclick={responder}>POST /api/paes sem nome</button>
<p>{status} · {corpo}</p>

Aqui a caixa é uma simulação didática do que o teste verifica. No endpoint de verdade, o status e o corpo saem de json({ erro: ... }, { status: 400 }); o teste lê os dois do Response. Guardar status e corpo em estados separados ajuda a enxergar que são duas informações diferentes — e que uma pode estar certa enquanto a outra está errada.

8. Testando o load universal com fetch falso

O +page.js é o load que roda nos dois lados. Ele recebe um fetch pronto, e esse fetch é especial: aceita caminho relativo, como /api/paes, porque o SvelteKit o embrulha para funcionar também no servidor. No teste, você passa o seu próprio fetch:

export async function load({ params, fetch }) {
  const resposta = await fetch(`/api/paes?busca=${params.slug}`);
  if (!resposta.ok) {
    return { encontrado: false };
  }
  const dados = await resposta.json();
  return { encontrado: dados.total > 0, pao: dados.paes[0] ?? null };
}
import { describe, it, expect } from 'vitest';
import { load } from './+page.js';

describe('load universal de /paes/[slug]', () => {
  it('usa o fetch que recebeu, sem rede de verdade', async () => {
    const falso = async (url) =>
      new Response(JSON.stringify({ total: 1, paes: [{ slug: 'queijo', nome: 'Pão de queijo' }] }), {
        status: 200,
        headers: { 'content-type': 'application/json' }
      });

    const dados = await load({ params: { slug: 'queijo' }, fetch: falso });
    expect(dados.encontrado).toBe(true);
    expect(dados.pao.nome).toBe('Pão de queijo');
  });

  it('quando a resposta falha, devolve encontrado: false', async () => {
    const falso = async () => new Response('erro', { status: 500 });
    const dados = await load({ params: { slug: 'sumido' }, fetch: falso });
    expect(dados.encontrado).toBe(false);
  });
});

O fetch falso devolve um Response montado na hora, sem rede. O teste verifica o caminho feliz e o caminho de erro — a resposta 500 que faz o load devolver encontrado: false. Nenhum servidor foi ligado, e o teste roda em milissegundos.

Esse é o maior ganho de testar rota com dublê: você consegue simular o que é difícil de provocar na vida real. Servidor fora do ar, banco lento, cliente sem nome, URL com promoção. O teste vira um laboratório de casos ruins, e os casos ruins são justamente os que ninguém testa à mão.

9. O teste que falha por culpa da expectativa

Missão: a action recusa quem esqueceu o nome, mas o componente mostra o erro justamente quando o nome foi preenchido. Envie o formulário vazio e faça a frase Diga o seu nome aparecer.

<script>
  let nome = $state('');
  let erro = $state('');

  function encomendar(evento) {
    evento.preventDefault();
    if (nome) {
      erro = 'Diga o seu nome';
    }
  }
</script>

<h1>Encomenda</h1>
<form onsubmit={encomendar}>
  <input bind:value={nome} aria-label="nome">
  <button>encomendar</button>
</form>
{#if erro}
  <p>{erro}</p>
{/if}
<script>
  let nome = $state('');
  let erro = $state('');

  function encomendar(evento) {
    evento.preventDefault();
    if (!nome) {
      erro = 'Diga o seu nome';
    }
  }
</script>

<h1>Encomenda</h1>
<form onsubmit={encomendar}>
  <input bind:value={nome} aria-label="nome">
  <button>encomendar</button>
</form>
{#if erro}
  <p>{erro}</p>

A condição invertida é o erro de lógica mais comum em validação: if (nome) quando o certo é if (!nome). O teste da action pega isso no servidor; a caixa pega na tela. Os dois juntos fecham o caminho inteiro, e é por isso que o guia insiste em testar a rota e depois olhar a tela.

10. Quando dá errado

As três saídas abaixo vieram de execuções reais neste projeto. A primeira é de importação, a segunda é de ambiente e a terceira é uma expectativa de endereço que não bate.

A mensagem é curta e honesta: document is not defined. Para testar componente, o projeto precisa de um ambiente de DOM, como jsdom ou happy-dom, configurado no Vitest. Sem isso, o caminho é testar a rota — que não precisa de tela — e conferir o componente no navegador.

Resumo

  • Rota é a camada entre a conta e a tela: +page.server.js, +page.js e +server.js.
  • O teste importa as funções da rota e monta os objetos que o SvelteKit montaria.
  • load recebe o evento; no teste, uma URL de localhost basta para os casos simples.
  • redirect() e error() lançam: capture e confira com isRedirect ou isHttpError.
  • Action se testa com FormData dentro de um Request POST; fail devolve status e data.
  • Endpoint se testa chamando GET ou POST e lendo o Response com status, json() e cabeçalhos.
  • O fetch do load universal pode ser trocado por uma função que devolve Response na hora.
  • Sem configuração extra, o Vitest lê o vite.config.js e respeita os atalhos #lib.
  • Teste de componente precisa de DOM; teste de rota não. Comece pela rota.
  • A falha aponta a linha da expectativa: leia Expected e Received antes de mexer no código.
