Svelte · Os Três Blocos

A Ana tem três cadernos na padaria: um com os números do dia (quanto entrou, quanto saiu), um quadro na parede com o que o cliente lê e uma lata de tinta para deixar tudo apresentável. Ela não mistura os três: número fica no caderno, recado fica no quadro, tinta fica na parede. Um componente Svelte tem exatamente essa divisão, em blocos com nomes: <script>, o HTML e <style>. Nesta aula você vê o que pode entrar em cada um, o que acontece quando um bloco vaza para o outro e por que o estilo não pinta a página inteira.

Você vai aprender
  • Quais são os três blocos e o que cada um faz.
  • Qual bloco é obrigatório e quais são opcionais.
  • Por que o <script> não aparece na tela e para onde ele vai.
  • Como o compilador transforma o HTML do componente em marcação final.
  • O que é CSS escopado e de onde vem o selo svelte-xxxxxx.
  • Quando usar :global() e qual é o custo disso.
  • Que um componente só com HTML é válido — e quando isso basta.
  • Que a ordem dos blocos não muda o resultado, mas muda a leitura.
  • Os erros reais: dois estilos, script fechado com a tag errada e CSS querendo ler variável.

1. A ideia: caderno, quadro e tinta

Pense no trabalho da Ana em três camadas. A primeira é o que ela sabe: o preço do pão hoje, quantos pães sobraram, se a farinha acabou. A segunda é o que o cliente vê: a placa com o preço, o cardápio, o aviso de "fechado". A terceira é a aparência: a cor da placa, o tamanho da letra, a moldura. As três camadas conversam, mas cada uma tem o seu lugar.

No componente, essas camadas são os blocos. O <script> é o caderno: guarda os valores e as funções. O HTML solto no arquivo é o quadro: é o que aparece na tela. O <style> é a tinta: cuida de cor, espaçamento, tamanho. O compilador lê os três, resolve os valores do caderno e entrega ao navegador um quadro já pintado.

A vantagem de separar é a mesma da padaria: quando o preço muda, a Ana não repinta a placa. Ela muda o número no caderno, e o quadro se atualiza. Quando quer mudar a cor da placa, não mexe no número. Cada mudança tem um lugar certo, e isso reduz o tempo que você perde procurando onde alterar.

BlocoNa padariaNo componente
<script>o caderno de números e contasvariáveis, funções, importações
HTMLo quadro que o cliente lêas tags que aparecem na tela
<style>a tinta e a molduraCSS com escopo do componente

2. Os três blocos, na ordem

Este é um componente completo, com os três blocos. O <script> vem primeiro, o HTML no meio, o <style> no fim — a ordem que o guia usa em todos os exemplos.

<script>
  let titulo = 'Pão francês';
  let preco = $state(0.9);
</script>

<article>
  <h2>{titulo}</h2>
  <p>R$ {preco.toFixed(2)}</p>
</article>

<style>
  article {
    border: 1px solid #ddd;
    padding: 8px;
  }
  h2 {
    color: #2e7d32;
  }
</style>

O HTML gerado já vem com um atributo a mais em cada tag que o CSS atinge:

<article class="svelte-1n46o8q"><h2 class="svelte-1n46o8q">Pão francês</h2> <p>R$ 0.90</p></article>

O <script> desapareceu: os valores foram resolvidos e escritos na marcação. O svelte-1n46o8q é o selo deste componente — o compilador inventou esse código para que o CSS de article e h2 valha só aqui. O <p> não recebeu o selo porque nenhuma regra do estilo aponta para ele.

<script> … </script>
o bloco de JavaScript. Roda uma vez, quando o componente é criado, e não aparece na tela. É onde ficam variáveis, funções e importações.
<article> … </article>
o HTML, único bloco obrigatório. Tudo o que está aqui aparece na página; as chaves { } trazem valores do script.
<style> … </style>
o CSS. O compilador acrescenta o selo em cada seletor e nas tags correspondentes, então a regra não vaza para outros componentes.

3. O bloco <script>

Dentro do script roda JavaScript comum. Você pode declarar variáveis, escrever funções, importar arquivos, fazer contas. A diferença é que o compilador observa o que é usado no HTML e prepara a atualização automática para aqueles valores.

Uma coisa que confunde: o script não é o lugar de escrever texto na tela. Se você colocar um console.log ali, a mensagem vai para o console do navegador, não para a página. Quem escreve na tela é o HTML. O script prepara os valores; o HTML os mostra. Misturar os dois papéis é a origem de muitos "não aparece nada".

O script também é o lugar das importações. Quando um componente usa outro, é aqui que a ligação acontece: import Cartao from './Cartao.svelte'. Tudo o que vem de fora entra por esse bloco, e é por isso que ele fica no topo: quem lê o arquivo vê primeiro do que o componente depende.

Missão: o nome da variável começa com um número e o compilador recusa o arquivo. Renomeie a variável para nome, nos dois lugares em que ela aparece.

<script>
  let 2nome = $state('Ana');
</script>

<h1>Olá, {2nome}</h1>
<script>
  let nome = $state('Ana');
</script>

<h1>Olá, {nome}</h1>

Nome de variável em JavaScript não pode começar com número, nem ter espaço, nem acento. As regras são as mesmas do JavaScript, porque é JavaScript de verdade: letras, números e sublinhado, começando por letra ou sublinhado. A mensagem do compilador fala de "identificador diretamente depois de número" — é a tradução técnica do mesmo problema.

4. O HTML: o que aparece

O bloco do meio é o único obrigatório. Um componente com uma linha de texto é um componente válido:

<p>Pão fresquinho, todo dia.</p>
<p>Pão fresquinho, todo dia.</p>

Esse componente não tem script nem estilo. Ele é útil do mesmo jeito: pode ser importado por outro componente para não repetir a mesma frase em cinco lugares. Se amanhã a Ana quiser mudar o slogan, muda em um arquivo só. Essa é a primeira vantagem de componentizar, antes de qualquer reatividade.

No HTML do componente, as chaves são a porta de entrada dos valores. Elas podem conter uma variável, uma conta, uma chamada de função, um texto entre aspas. O que não cabe dentro das chaves é uma declaração: {let x = 1} não declara nada — o compilador ignora e a expressão vale vazio. Declaração é coisa do script.

E o HTML do componente não precisa de html, head ou body. Essas tags ficam no index.html. O componente é um pedaço de tela que será encaixado dentro da página; escrever a página inteira aqui gera HTML dentro de HTML, como vimos na aula de estrutura.

5. O bloco <style> e o escopo

O terceiro bloco é CSS normal, com uma diferença que muda a vida: ele vale só para este componente. O compilador faz isso renomeando os seletores com um selo. Veja o CSS que ele gerou para o componente do início da aula:

article.svelte-1n46o8q {
    border: 1px solid #ddd;
    padding: 8px;
  }
  h2.svelte-1n46o8q {
    color: #2e7d32;
  }

Cada seletor ganhou .svelte-1n46o8q. Como o mesmo selo foi colocado nas tags do HTML gerado, a regra só encontra os elementos deste componente. Um h2 de outro componente, mesmo que apareça na mesma página, não é atingido: ele tem outro selo, ou nenhum.

O preço dessa proteção é que às vezes você quer atingir algo de fora — o body, por exemplo, para mudar a cor de fundo da página inteira. Para isso existe :global(), que desliga o escopo naquele seletor:

<p>Pão fresquinho</p>

<style>
  p { color: #2e7d32; }
  :global(body) { background: #fff8e1; }
</style>
p.svelte-1n46o8q { color: #2e7d32; }
  body { background: #fff8e1; }

O p continua com selo; o body saiu sem. Cada :global é uma porta que você abre no isolamento: use quando precisar, sabendo que a regra passa a valer para a página toda. Em excesso, você perde a principal vantagem do CSS escopado, que é nunca precisar inventar nome de classe para evitar conflito.

Missão: o componente tem dois blocos <style> e o compilador recusa. Junte as duas regras num bloco só, mantendo o título "Pão francês" e o preço "R$ 0.90".

<script>
  let preco = $state(0.9);
</script>

<h1>Pão francês</h1>
<p>R$ {preco.toFixed(2)}</p>

<style>
  h1 { color: #2e7d32; }
</style>

<style>
  p { padding: 4px; }
</style>
<script>
  let preco = $state(0.9);
</script>

<h1>Pão francês</h1>
<p>R$ {preco.toFixed(2)}</p>

<style>
  h1 { color: #2e7d32; }
  p { padding: 4px; }
</style>

Um bloco de cada tipo, sempre. Se você tem duas listas de regras, junte: o compilador precisa de uma ordem única para saber em que momento aplicar cada coisa. É a mesma razão pela qual dois scripts não são aceitos.

6. Só HTML também é componente

Já vimos esse caso, mas vale olhar a saída com atenção: o componente de uma linha produz exatamente uma linha de HTML, sem selo nenhum. Sem <style>, não há o que escopar.

<p>Pão fresquinho</p>

<style>
  p { color: #2e7d32; }
</style>
<p class="svelte-1n46o8q">Pão fresquinho</p>

Agora com estilo, a mesma frase ganha o selo — e o CSS correspondente aparece no bundle com o mesmo código:

p.svelte-1n46o8q { color: #2e7d32; }

Repare que o texto não mudou. O estilo não altera o conteúdo, só a apresentação. É por isso que o guia mostra as duas saídas separadas: uma é o que a tela diz, outra é como a tela se pinta. Quando você depurar, pergunte primeiro "o texto está certo?" e só depois "o estilo está aplicado?".

Missão: o <script> foi escrito dentro da div e o componente quebra. Tire o script de dentro da marcação e coloque no topo do arquivo.

<div>
  <script>
    let nome = 'Ana';
  </script>
  <h1>Olá, {nome}</h1>
</div>
<script>
  let nome = 'Ana';
</script>

<div>
  <h1>Olá, {nome}</h1>
</div>

Um <script> dentro de uma div é apenas uma tag de HTML: o navegador não executa o conteúdo dela como código do componente. Por isso a variável não existe no momento de desenhar. Os blocos do Svelte são de nível superior, soltos no arquivo, não aninhados na marcação.

7. A ordem dos blocos

A convenção é script no topo, HTML no meio, estilo no fim. O compilador, porém, não exige essa ordem: ele lê os três blocos onde estiverem e monta o resultado. Este componente tem o estilo no meio e o HTML depois dele — e funciona:

<script>
  let nome = $state('Ana');
</script>

<p>Pão</p>

<style>
  p { color: green; }
</style>

<h1>Olá, {nome}</h1>
<p class="svelte-1n46o8q">Pão</p> <h1>Olá, Ana</h1>

Funciona, mas não é uma boa ideia. A convenção existe para quem lê: com o estilo sempre no fim, você sabe onde procurar a cor de um elemento sem varrer o arquivo. Em um projeto com dezenas de componentes, padronizar a leitura economiza mais tempo do que qualquer otimização. Use a ordem do guia.

Existe uma exceção legítima: o <script module>, que roda uma vez para todos os usos do componente, pode vir antes ou depois do <script> comum. Ele é usado para estado compartilhado e tem aula própria no Nível 2. Por enquanto, um script comum basta.

Outro detalhe de leitura: o HTML pode ter comentários, mas eles somem da saída. Isso é assunto da próxima aula, com calma — só saiba que o compilador limpa o que é comentário antes de entregar a página.

8. O que vai para o navegador

Depois de compilar, o navegador recebe três coisas: o HTML com os valores já resolvidos, o JavaScript que sabe atualizar esse HTML quando o estado muda, e o CSS com os selos. Nada de <script> com o seu código-fonte e nada de <style> no meio da marcação: o compilador separa e organiza.

Isso explica um comportamento que assusta: quando você inspeciona a página no navegador e procura a sua variável, não encontra. Ela virou um valor dentro de uma função fechada, com nome gerado pelo compilador. Você depura pelo comportamento — clicar, digitar, ver o que muda — e não lendo o HTML final como se fosse o seu arquivo.

Explica também por que o CSS aparece com um nome estranho no bundle: é o mesmo CSS que você escreveu, com o selo aplicado. Se você procurar p.svelte-1n46o8q no arquivo gerado, encontra a regra. Se procurar p { color: #2e7d32 } puro, não encontra — e não é erro.

O build deixa isso visível. Rodando o build do componente com estilo, aparece um arquivo .css separado, do lado do JavaScript:

Dois arquivos com hash: um para o JavaScript, outro para o CSS. O Vite junta o estilo de todos os componentes em um arquivo só, porque o navegador baixa mais rápido um arquivo grande do que dez pequenos. O nome tem hash pelo mesmo motivo de sempre: conteúdo novo, nome novo, cache seguro.

Eis o CSS compilado: minificado (sem espaços nem quebras) e com o selo em cada seletor. É o mesmo conteúdo que você escreveu no bloco <style>, em outra forma. Se você procurar a regra no JavaScript também encontra o selo, porque o HTML gerado precisa dele para casar com o CSS:

ana@notebook:~/loja$ grep -o "svelte-[a-z0-9]*" dist/assets/*.js | sort -u
svelte-1n46o8q
svelte-trusted

Duas linhas. A primeira é o selo deste componente. A segunda, svelte-trusted, não é um selo de componente: é um nome interno do motor do Svelte, que apareceu na busca porque começa com as mesmas letras. Detalhe bobo que assusta na primeira vez — e que vale saber para não sair caçando componente fantasma.

9. Quando o bloco vaza

O erro clássico de quem está começando é escrever texto dentro do bloco de estilo, ou CSS dentro do bloco de script. Os dois não compilam, e as mensagens não são óbvias na primeira leitura. O teste é simples: se tem chave de CSS (seletor { propriedade: valor }), é estilo; se tem JavaScript, é script; se tem tag, é HTML.

Também é comum tentar usar uma variável dentro do CSS:

<script>
  let cor = 'green';
</script>

<h1>Pão</h1>

<style>
  h1 { color: {cor}; }
</style>
Erro de compilação (linha 8, coluna 13): Expected a valid CSS identifier

O CSS é compilado antes de o componente rodar: ele não tem acesso a valores que só existem na hora da execução. Para mudar cor dinamicamente, o caminho é o atributo style com chaves, ou a diretiva style: — assuntos da aula de atributos dinâmicos e de estilo por condição. O bloco <style> é para o que não muda.

10. Quando dá errado

As três mensagens abaixo saíram do compilador desta versão, copiadas como estão. Todas são de confusão entre blocos.

Erro 1 — script fechado com a tag errada

A pressa faz fechar o <script> com </style>. O compilador continua esperando o fim do script até o arquivo acabar.

<script>
  let nome = $state('Ana');
</style>

<h1>Olá, {nome}</h1>
Erro de compilação (linha 5, coluna 20): `<script>` was left open

"Ficou aberto" é literal: o compilador não achou </script> em lugar nenhum. A posição aponta para o fim do arquivo, onde ele desistiu. Confira a tag de fechamento antes de qualquer outra coisa.

Erro 2 — variável dentro do CSS

O bloco de estilo não enxerga variáveis. As chaves ali não são expressão: são parte da sintaxe do CSS, e o valor não é um identificador válido.

<script>
  let cor = 'green';
</script>

<h1>Pão</h1>

<style>
  h1 { color: {cor}; }
</style>
Erro de compilação (linha 8, coluna 13): Expected a valid CSS identifier

Para cor dinâmica, use <h1 style="color: {cor}"> ou style:color={cor}. O bloco <style> fica com o que é fixo: espaçamento, borda, tipografia.

Erro 3 — texto dentro do estilo

Uma frase solta no meio das regras CSS não é declaração válida. O compilador tenta ler como seletor e para no primeiro caractere.

<p>Pão</p>

<style>
  p { color: green; }
  Pão fresquinho
</style>
Erro de compilação (linha 6, coluna 0): Expected a valid CSS identifier

A linha apontada é a da frase. Mova o texto para fora do <style>, dentro de uma tag de HTML. Na dúvida, conte as chaves: dentro do estilo, tudo tem de estar entre { }.

Exercícios

1. Qual bloco é obrigatório em um componente?

2. De onde vem o svelte-1n46o8q que aparece nas tags?

3. O que :global(body) faz dentro de um <style>?

Complete o código

<script>
  let preco = $state(0.9);

Resumo

  • O componente tem até três blocos: <script>, HTML e <style>.
  • Só o HTML é obrigatório; um componente com uma frase é válido.
  • O <script> guarda valores e funções e não aparece na tela.
  • As chaves { } no HTML trazem valores do script.
  • O <style> é escopado: o compilador renomeia os seletores com um selo.
  • :global(seletor) desliga o escopo naquele seletor, com custo para o isolamento.
  • A ordem script → HTML → estilo é convenção de leitura; o compilador aceita outra.
  • Um bloco de cada tipo por arquivo: dois <style> não compilam.
  • Os erros desta aula: script fechado com </style>, variável dentro do CSS e texto dentro do estilo.
