SvelteKit · use:enhance

A Ana não gosta de ver o cliente sair da fila para preencher a ficha de novo. No site é igual: o envio de formulário clássico recarrega a página inteira, o que apaga o que a pessoa estava vendo e faz a tela piscar. O use:enhance existe para isso — uma palavra colada no formulário que faz o envio acontecer em segundo plano, com a mesma action do servidor e sem recarregar nada. E, se o JavaScript falhar, o formulário continua funcionando do jeito antigo.

Você vai aprender
  • O que a diretiva use:enhance faz e de onde ela vem.
  • O que muda no envio: requisição em segundo plano, sem recarregar.
  • Por que o servidor responde JSON em vez de HTML nesse caminho.
  • O que é o data codificado e por que existe deserialize.
  • Como usar o callback com result, update e formData.
  • Como mostrar o estado "enviando…" sem travar o botão.
  • Como redirecionar e como aplicar o resultado à mão.
  • Por que o formulário continua funcionando sem JavaScript.
  • Três erros reais: 415, 404 e 405.
  • Como testar o caminho do enhance com curl.

1. A ideia: entregar a ficha sem sair da fila

O envio clássico de formulário é uma viagem inteira: o navegador manda os campos, espera, recebe uma página nova e a desenha do zero. Funciona sempre e é a base de tudo. O problema é o "do zero": a posição da rolagem volta ao topo, o campo perde o foco, a imagem recarrega, e a pessoa tem a sensação de que saiu do lugar onde estava.

Com JavaScript, dá para fazer melhor: interceptar o envio, mandar os campos em segundo plano, receber só o resultado e trocar apenas o pedaço que mudou. É o que o use:enhance faz — sem que você escreva o fetch, sem que você trate a resposta, sem que você redesenhe nada à mão.

A parte boa é que ele não substitui o formulário: ele melhora o formulário que já existe. O HTML continua <form method="POST">, a action continua a mesma, a validação continua no servidor. Se o script não carregar, o envio clássico acontece e ninguém fica sem enviar. Isso tem nome — aprimoramento progressivo — e é a razão de o SvelteKit ter escolhido esse desenho.

2. A diretiva no formulário

O formulário da Ana na rota /enhance tem a mesma action da aula anterior. O que muda é a importação e o atributo use:enhance:

<script>
	import { enhance } from '$app/forms';

	let { data, form } = $props();

	let enviando = $state(false);
</script>

<h1>Pedido com use:enhance</h1>

{#if form?.ok}
	<p class="ok">Anotado para {form.cliente}.</p>
{:else if form?.falta}
	<p class="erro">{form.falta}</p>
{/if}

<form
	method="POST"
	use:enhance={() => {
		enviando = true;
		return async ({ update }) => {
			await update();
			enviando = false;
		};
	}}
>
	<input name="cliente" placeholder="quem pediu" />
	<button disabled={enviando}>{enviando ? 'enviando…' : 'anotar'}</button>
</form>

<p>Na fila: {data.pedidos.length}</p>
import { enhance } from '$app/forms'
o módulo do SvelteKit que só existe no navegador. É por isso que ele não pode ser usado no +page.server.js.
use:enhance
uma ação de elemento: quando o formulário entra na tela, o Svelte chama a função e ela liga o comportamento extra.
() => { enviando = true; … }
a função que roda antes de enviar. É onde você desabilita o botão e mostra o aviso.
return async ({ update }) => {}
a função que roda depois. Recebe o resultado do servidor e a função que aplica esse resultado à página.
await update()
aplica o resultado: atualiza form e data, redesenha o que mudou. É uma promessa; espere antes de dizer que terminou.

Um detalhe de sintaxe que confunde: use:enhance={funcao} recebe uma função que devolve outra função. A primeira prepara (liga o "enviando"), a segunda conclui (desliga). Se você devolver undefined na primeira, o SvelteKit usa o comportamento padrão — que já atualiza tudo sozinho.

Missão: depois do clique, o botão fica travado em "enviando…" para sempre. Faça a mensagem final aparecer: Anotado para Caio.

<script>
	let cliente = $state('Caio');
	let enviando = $state(false);
	let aviso = $state('');

	async function enviar(evento) {
		evento.preventDefault();
		enviando = true;

		await new Promise((ok) => setTimeout(ok, 200));

		aviso = 'Anotado para ' + cliente + '.';
	}
</script>

<form onsubmit={enviar}>
	<input bind:value={cliente} />
	<button disabled={enviando}>{enviando ? 'enviando…' : 'anotar'}</button>
</form>
<p>{enviando ? '' : aviso}</p>

Esse é o defeito mais comum de quem usa enhance pela primeira vez: ligar o "enviando" e esquecer de desligar. O botão fica desabilitado para sempre e a página parece travada. Com use:enhance, o lugar de desligar é o fim do segundo callback, depois do await update().

3. A saída real: o que o servidor responde nesse caminho

Aqui está a parte que surpreende. O mesmo POST que devolve uma página inteira para o navegador devolve JSON quando o cliente pede assim. O SvelteKit decide pelo cabeçalho accept e por um cabeçalho próprio, o x-sveltekit-action, que o enhance manda:

ana@notebook:~/loja$ curl -s -X POST -H 'x-sveltekit-action: true' -d 'cliente=Caio&sabor=frango' localhost:5173/enhance -w '\n%{http_code}\n'
{"type":"success","status":200,"location":"/enhance","data":"[{\"ok\":1,\"cliente\":2},true,\"Caio\"]"}
200

Leia com calma. type: "success" diz que a action devolveu dados. status: 200 é o status HTTP. location é o endereço da página. E data é o objeto que a action retornou — mas codificado como texto, e com um formato estranho: [{"ok":1,"cliente":2},true,"Caio"].

Esse formato é do devalue, a biblioteca que o SvelteKit usa para levar valores que o JSON comum não leva: Date, BigInt, Map, undefined, e referências repetidas — daí o 1 e o 2 apontando para as posições da lista. Não é JSON de propósito; é um superconjunto. Quem transforma esse texto em objeto é a função deserialize.

ana@notebook:~/loja$ curl -s -X POST -H 'x-sveltekit-action: true' -d 'cliente=' localhost:5173/enhance -w '\n%{http_code}\n'
{"type":"failure","status":400,"location":"/enhance","data":"[{\"cliente\":1,\"falta\":2},\"\",\"escreva o nome de quem pediu\"]"}
400

Agora type: "failure" e status 400: foi o fail() da action. O data traz os campos que você mandou — cliente vazio e falta com a mensagem. É esse conteúdo que o enhance entrega ao seu callback em result.data, já decodificado.

E o mesmo POST feito por um navegador sem o cabeçalho?

ana@notebook:~/loja$ curl -s -X POST -H 'accept: text/html' -d 'cliente=Caio&sabor=frango' localhost:5173/enhance | grep -o '<p class="ok">[^<]*</p>'
<p class="ok">Anotado para Caio.</p>

HTML completo, com a mensagem dentro. É a mesma action respondendo a dois clientes diferentes. Nada no seu +page.server.js muda por causa disso — a diferença está só no formato da resposta.

4. O callback: result, update e companhia

O segundo callback recebe um objeto com tudo o que aconteceu. Os três campos que você vai usar de verdade são result, update e formData:

<script>
	import { enhance } from '$app/forms';

	let { form } = $props();

	let enviando = $state(false);
	let mensagem = $state('');
</script>

<form
	method="POST"
	use:enhance={() => {
		enviando = true;

		return async ({ result, update }) => {
			if (result.type === 'failure') {
				mensagem = result.data.falta;
			} else if (result.type === 'success') {
				mensagem = 'anotado para ' + result.data.cliente;
			}

			await update();
			enviando = false;
		};
	}}
>
	<input name="cliente" placeholder="quem pediu" />
	<button disabled={enviando}>{enviando ? 'enviando…' : 'anotar'}</button>
</form>

<p>{mensagem}</p>

result.type pode ser 'success', 'failure', 'redirect' ou 'error'. Essa distinção evita um monte de if sobre status: um redirect não é falha, e um erro de rede não tem página nova para onde ir. Trate cada tipo com o que faz sentido para o seu formulário.

Campo do callbackPara que serve
resulto que o servidor respondeu: type, status, data ou location
update()aplica o resultado: atualiza os props form e data e redesenha
formDatao que a pessoa digitou, já pronto para reenviar ou inspecionar
formElemento formulário no DOM, útil para resetar campos
cancel()desiste do envio antes de ele sair

Missão: simule a resposta da action: o result.type foi 'failure' e o data.falta tem a mensagem. Faça aparecer falta o nome.

<script>
	const result = { type: 'failure', status: 400, data: { falta: 'falta o nome' } };
	let mensagem = $state('');
</script>

<p>{result.type === 'success' ? result.data.falta : ''}</p>
<script>
	const result = { type: 'failure', status: 400, data: { falta: 'falta o nome' } };
	let mensagem = $state('');
</script>

<p>{result.type === 'failure' ? result.data.falta : ''}</p>

Comparar com 'success' quando o resultado é 'failure' é o erro de digitação que passa nos testes rápidos: a página não quebra, só não mostra a mensagem. Em formulário, mensagem que não aparece é pior que erro vermelho, porque ninguém sabe que precisa corrigir algo.

5. Redirecionar com enhance

Quando a action chama redirect(303, '/encomenda'), o resultado chega ao callback com type: 'redirect' e o endereço em location. O comportamento padrão do enhance é navegar para lá — sem recarregar a página, como um link interno. Você quase nunca precisa fazer nada.

Precisa quando quer algo antes ou depois. Um exemplo: avisar que o pedido foi criado e só então sair. Ou bloquear o redirecionamento para mostrar um resumo. Nesse caso você trata o tipo e chama update() apenas quando fizer sentido:

use:enhance={() => {
	return async ({ result, update }) => {
		if (result.type === 'redirect') {
			mensagem = 'pedido criado, indo para ' + result.location;
		}

		await update();
	};
}}

O update() é quem executa a navegação no caso de redirect. Sem ele, a tela fica parada e o usuário não vê o resultado. Com ele, o SvelteKit faz a troca de rota do jeito dele, mantendo o histórico e a rolagem.

O botão que volta sozinho

Desabilitar o botão durante o envio é bom; esquecer de reabilitar é ruim. Uma proteção extra: no finally do callback, sempre desligue o enviando. Se o update() estourar — rede caiu no meio — o finally roda do mesmo jeito e a pessoa pode tentar de novo.

6. O que acontece quando o JavaScript não carrega

Este é o teste que separa aprimoramento de dependência. Desligue o JavaScript no navegador e envie o formulário: o navegador faz o envio clássico, o servidor responde HTML, a página recarrega com a mensagem. Tudo funciona — só sem a fluidez.

O curl mostra exatamente esse caminho, porque ele nunca executa JavaScript. Quando você manda o POST com accept: text/html e sem o cabeçalho do enhance, recebe uma página inteira. É a prova de que a action não depende da diretiva.

<script>
	const enviando = true;
</script>

<button disabled={enviando}>{enviando ? 'enviando…' : 'anotar'}</button>
<button disabled="">enviando…</button>

O pedacinho acima é o botão no estado de envio, compilado de verdade. Duas coisas acontecem: o atributo disabled aparece vazio (presença é o que conta em HTML) e o texto muda para "enviando…". É esse par que dá a sensação de que o clique foi registrado.

7. applyAction e deserialize

Em quase todo formulário, o enhance resolve. Existem dois casos em que você precisa das peças que ele usa por dentro. O primeiro é quando o resultado chega de outro lugar que não um envio de formulário — um fetch feito à mão. O segundo é quando você guardou o data codificado e precisa lê-lo depois.

applyAction(result) faz o que o update() faz: pega um resultado de action e aplica na página, atualizando form e data. A diferença é que ele não envia nada — você já tem o resultado em mãos. Serve para reaproveitar um envio feito em outro momento, ou para tratar uma resposta que veio de um serviço externo no mesmo formato.

<script>
	import { applyAction, deserialize } from '$app/forms';

	async function reaplicar(texto) {
		const resultado = {
			type: 'success',
			status: 200,
			location: '/enhance',
			data: deserialize(texto)
		};

		await applyAction(resultado);
	}
</script>

deserialize(texto) transforma aquele [{"ok":1,"cliente":2},true,"Caio"] de volta em objeto. Você só precisa disso quando o texto chega por fora — por exemplo, guardado no localStorage ou vindo de outro servidor. No caminho normal do enhance, o resultado já vem decodificado e você usa result.data direto.

FunçãoQuando usar
update()dentro do callback do enhance, com o resultado que ele entregou
applyAction(result)quando o resultado veio de outro lugar e você quer aplicá-lo à página
deserialize(texto)quando o data chegou como texto codificado e você precisa do objeto

8. O custo: clique duplo e botão travado

Envio em segundo plano tem um risco que o envio clássico não tinha. No clássico, a página sai da tela e o segundo clique cai no vazio. No enhance, a página continua ali, viva, e um clique duplo manda dois POST — dois pedidos, dois e-mails, duas cobranças.

É para isso que existe o enviando. Desabilitar o botão no primeiro callback resolve o clique duplo de propósito. Para o clique duplo acidental, vale também trocar o rótulo: quando o botão diz "enviando…", ninguém tenta de novo. E, no servidor, a defesa final é a action ser idempotente ou recusar pedido repetido — porque o botão é do navegador, e o navegador não é seu.

Não use enhance onde não precisa

Formulário de uma pergunta, com resposta rara, funciona bem do jeito clássico. O enhance brilha em formulário que a pessoa usa muitas vezes e onde perder o foco do campo irrita — busca, filtro, anotação rápida. Adicionar a diretiva em tudo troca simplicidade por um recurso que ninguém pediu.

Missão: o envio termina, mas o contador não sobe. Faça aparecer 1 envio(s) depois do clique.

<script>
	let enviando = $state(false);
	let vezes = $state(0);

	async function enviar(evento) {
		evento.preventDefault();
		enviando = true;
		await new Promise((ok) => setTimeout(ok, 200));
		enviando = false;
	}
</script>

<form onsubmit={enviar}>
	<button disabled={enviando}>{enviando ? 'enviando…' : 'anotar'}</button>
</form>
<p>{vezes} envio(s)</p>
<script>
	let enviando = $state(false);
	let vezes = $state(0);

	async function enviar(evento) {
		evento.preventDefault();
		enviando = true;
		await new Promise((ok) => setTimeout(ok, 200));
		vezes = vezes + 1;
		enviando = false;
	}
</script>

<form onsubmit={enviar}>
	<button disabled={enviando}>{enviando ? 'enviando…' : 'anotar'}</button>
</form>
<p>{vezes} envio(s)</p>

A contagem sobe só quando o envio termina, e não no clique. Essa ordem é a mesma do update(): primeiro o resultado chega, depois você atualiza a tela. Contar antes seria mentir para o leitor se o envio falhasse.

9. Quando dá errado

Erro 1 — POST sem content-type

O enhance sempre manda o cabeçalho; um teste com curl pode esquecer. O SvelteKit recusa antes de chamar a sua action:

ana@notebook:~/loja$ curl -s -X POST localhost:5173/enhance -w '\n%{http_code}\n'
{"type":"error","location":"/enhance","error":{"status":415,"message":"Unsupported Media Type"}}
415

É o mesmo 415 da aula anterior, agora no formato JSON do enhance. Note o type: "error": não é falha de validação, é requisição malformada. O seu callback receberia esse resultado e result.data não existiria.

Erro 2 — action que não existe

O formulário aponta para ?/apagar e a action não está no arquivo. O enhance recebe um resultado de erro com status 404 — e não uma falha com campos:

ana@notebook:~/loja$ curl -s -X POST -H 'x-sveltekit-action: true' -d 'cliente=Ana' 'localhost:5173/enhance?/apagar' -w '\n%{http_code}\n'
{"type":"error","location":"/enhance","error":{"status":404,"message":"Not Found"}}
404

Se o seu código trata só failure, esse caso passa batido e a página não avisa nada. Trate error também, mesmo que seja com uma mensagem genérica de "não foi possível enviar, tente de novo".

Erro 3 — formulário numa página sem action

Colocar um <form method="POST"> numa rota que não exporta actions dá 405. A página aceita GET, e só.

ana@notebook:~/loja$ curl -s -i -X POST -H 'accept: text/html' -d '' localhost:5173/painel | head -3
HTTP/1.1 405 Method Not Allowed
Vary: Origin
allow: GET

O allow: GET é a resposta: neste endereço, só se busca. Ou você cria a action no +page.server.js daquela rota, ou o formulário aponta para a rota que tem a action — o que costuma ser o certo, porque um formulário pertence a uma página específica.

Exercícios

1. De onde vem a diretiva enhance?

2. Para que serve o update() no callback?

3. O que acontece com o formulário sem JavaScript?

Complete o código

<script>
  import { } from '$app/forms';
  let enviando = $state(false);
</script>

<form method="POST" ={() => {
  enviando = true;
  return async ({ update }) => { await update(); enviando = false; };
}}>

Resumo

  • use:enhance vem de $app/forms e liga o envio do formulário em segundo plano.
  • Nesse caminho o servidor responde JSON com type, status, location e data.
  • O data é codificado por devalue; quem decodifica é deserialize.
  • O primeiro callback roda antes do envio; o segundo recebe result e update.
  • await update() aplica o resultado e atualiza form e data.
  • result.type pode ser success, failure, redirect ou error.
  • Ligue e desligue o estado "enviando" — no finally, para não deixar o botão travado.
  • Sem JavaScript o formulário continua funcionando do jeito clássico: aprimoramento, não dependência.
  • 415, 404 e 405 aparecem como type: "error", com o status dentro de error.
  • curl com x-sveltekit-action: true reproduz o caminho do enhance sem navegador.
