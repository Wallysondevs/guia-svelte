Svelte · Testes com Vitest

Toda vez que a Ana mexia no cálculo do troco, precisava abrir a página, comprar um pão, digitar valores e conferir na mão. Quando o troco saiu errado num sábado cheio, ela decidiu escrever a conferência uma vez só, num arquivo, para o computador repetir em um segundo. Nesta aula ela instala o Vitest e escreve o primeiro teste de verdade.

1. A ideia: a conferência que fica

Conferir na mão tem um defeito grave: não fica. Na segunda-feira ninguém lembra quais casos foram testados no sábado, e a mesma conferência é refeita do zero. Pior: quando o projeto cresce, ela deixa de ser feita — e o erro volta sem ninguém notar.

Um teste automático é a mesma conferência escrita num arquivo. Ele diz “se eu pagar 10 e o preço for 7,50, o troco tem de ser 2,50”. O computador roda isso em milissegundos, todas as vezes, sem esquecer nenhum caso.

O ganho maior não é pegar erro: é poder mudar. Com testes, a Ana pode reorganizar o cálculo do troco sem medo, porque a conferência avisa na hora se algo quebrou. Sem eles, cada mudança é uma aposta.

2. O que um teste responde

Um teste é uma pergunta com resposta de sim ou não. Se a resposta for “não”, o Vitest mostra o que ele esperava e o que veio. Essa é a única coisa que um teste faz — e é o suficiente para mudar a rotina de trabalho.

PerguntaComo vira teste
o troco de 10 com preço 7,50 é 2,50?expect(calcularTroco(10, 7.5)).toBe(2.5)
e quando o valor é exato?expect(calcularTroco(5, 5)).toBe(0)
e quando falta dinheiro?expect(calcularTroco(4, 7.5)).toBe(0)
a função devolve número?expect(typeof calcularTroco(10, 7.5)).toBe('number')

Repare que as perguntas são pequenas e concretas. “A função funciona?” não é uma pergunta de teste: não tem resposta sim ou não, e quando falha não diz onde. “O troco de 10 com preço 7,50 é 2,50?” diz tudo.

3. As quatro palavras de um teste

Todo teste no Vitest usa as mesmas quatro palavras. Elas aparecem nesta ordem: um grupo, um caso, uma expectativa e um comparador.

import { describe, it, expect } from 'vitest';
import { calcularTroco } from './troco.js';

describe('calcularTroco', () => {
  it('devolve a diferença entre o pago e o preço', () => {
    expect(calcularTroco(10, 7.5)).toBe(2.5);
  });
});
import … from 'vitest'
traz as quatro ferramentas do pacote. Sem essa linha, describe não existe no arquivo.
describe('calcularTroco', …)
o grupo: um nome para o conjunto de casos. Serve para o resumo dizer onde falhou.
it('devolve a diferença…', …)
o caso: uma pergunta escrita em português, no presente. É o texto que aparece no relatório.
expect(…)
o valor que o código produziu, embrulhado para ser conferido.
.toBe(2.5)
o comparador: o valor esperado. Trocar o comparador muda o tipo de conferência.

A frase dentro de it não é decoração. É ela que aparece quando o teste falha, e é ela que a Ana vai ler seis meses depois sem lembrar do código. Escreva a frase como se estivesse explicando para outra pessoa: “devolve a diferença entre o pago e o preço” diz mais que “teste 1”.

4. Instalando o Vitest

O Vitest é uma dependência de desenvolvimento: ele não vai para o site publicado, só fica no projeto para rodar os testes. Por isso a instalação usa -D:

ana@notebook:~/loja$ npm install -D vitest

added 44 packages, and audited 101 packages in 6s

19 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

Quarenta e quatro pacotes instalados — o Vitest e as peças de que ele depende. Nada disso entra no dist/: o build de produção só pega o que o site importa. O package.json ganha uma linha em devDependencies e pronto.

O comando pode ser rodado de dois jeitos. npx vitest run roda uma vez e devolve o resultado — é o que usamos aqui, porque queremos a resposta e não o modo de espera. Sem o run, o Vitest fica olhando os arquivos e roda de novo a cada salvamento, o que é ótimo no dia a dia e péssimo para copiar o resultado.

5. O primeiro teste: o módulo e o arquivo de teste

O Vitest testa funções, não telas. Por isso o primeiro alvo é o módulo que calcula o troco, sem componente nenhum:

export function calcularTroco(pago, preco) {
  return pago - preco;
}

A palavra export é o que permite outro arquivo importar a função. Sem ela, o teste não a enxerga. O arquivo de teste fica ao lado, com a mesma raiz e a terminação .test.js:

import { describe, it, expect } from 'vitest';
import { calcularTroco } from './troco.js';

describe('calcularTroco', () => {
  it('devolve a diferença entre o pago e o preço', () => {
    expect(calcularTroco(10, 7.5)).toBe(2.5);
  });

  it('devolve zero quando o valor é exato', () => {
    expect(calcularTroco(5, 5)).toBe(0);
  });
});

A terminação .test.js não é enfeite: é por ela que o Vitest encontra os arquivos sozinho. Rodando na pasta do projeto, ele procura todos os arquivos com esse padrão e executa:

ana@notebook:~/loja$ npx vitest run

 ✓ src/lib/troco.test.js (2 tests) 7ms

 Test Files  1 passed (1)
      Tests  2 passed (2)
   Start at  17:24:30
   Duration  357ms (transform 61%, import 25%, tests 8%, worker 5%)

Leia o resumo de baixo para cima. Test Files 1 passed: um arquivo, aprovado. Tests 2 passed: dois casos, aprovados. O sinal de certo antes do nome do arquivo (✓) é a barra verde no terminal. E a linha Duration mostra o total em milissegundos: 357 ms para conferir duas contas que, na mão, custariam bem mais.

6. Um teste que falha

Um teste que sempre passa não prova nada. A Ana escreveu um caso novo, sobre dinheiro quebrado em centavos, e o teste reprovou:

import { describe, it, expect } from 'vitest';
import { calcularTroco } from './troco.js';

describe('calcularTroco', () => {
  it('devolve a diferença entre o pago e o preço', () => {
    expect(calcularTroco(10, 7.5)).toBe(2.5);
  });

  it('fecha a conta nos centavos', () => {
    expect(calcularTroco(0.3, 0.1)).toBe(0.2);

Note o valor recebido: 0.19999999999999998. Não é bug do Vitest nem do Svelte. O computador guarda números decimais em binário, e algumas frações não têm representação exata — 0.3 - 0.1 sobra com um resto minúsculo. Para dinheiro, isso é inaceitável: a tela mostraria centavos errados.

Teste que nunca falhou não vale nada

Depois de escrever um teste, mude o código de propósito para ver o teste reprovar. Se ele continuar verde, o teste não está medindo o que você pensa. Essa conferência de si mesmo se chama “ver o teste falhar”.

7. O conserto até a barra verde

Consertar é arredondar para centavos dentro da função. Multiplicar por 100, arredondar e dividir de volta resolve o resto binário:

export function calcularTroco(pago, preco) {
  return Math.round((pago - preco) * 100) / 100;
}
ana@notebook:~/loja$ npx vitest run

 ✓ src/lib/troco.test.js (2 tests) 6ms

 Test Files  1 passed (1)
      Tests  2 passed (2)
   Start at  17:24:48
   Duration  587ms (transform 44%, import 35%, worker 11%, tests 10%)

Duas linhas de mudança, dois testes verdes. Repare no que o teste fez por ela: a correção podia ter quebrado o caso do troco exato, e não quebrou — porque o Vitest conferiu os dois na mesma execução. É essa rede que permite mexer sem medo.

Missão: a conta do troco carrega o resto binário: o valor aparece como 0.19999999999999998. Arredonde para centavos, como o teste da Ana exige, e mostre só R$ 0.20.

<script>
  let pago = $state(0.3);
  let preco = $state(0.1);
  let troco = $derived(pago - preco);
</script>

<p>R$ {troco.toFixed(2)} - {troco}</p>
<script>
  let pago = $state(0.3);
  let preco = $state(0.1);
  let troco = $derived(Math.round((pago - preco) * 100) / 100);
</script>

<p>R$ {troco.toFixed(2)}</p>

O toFixed(2) esconde o problema na tela, mas não o resolve no valor: o número continua com o resto. Arredondar na função, como a solução faz, conserta o dado — e aí qualquer lugar que use o valor está certo, com ou sem formatação.

8. Os comparadores do expect

O comparador é a parte final: .toBe(2.5). Cada um faz um tipo de pergunta diferente, e escolher o errado gera teste que passa quando deveria falhar.

ComparadorPergunta que fazExemplo
toBeé exatamente este valor? (número, texto, verdadeiro/falso)expect(calcularTroco(5, 5)).toBe(0)
toBeCloseToé quase este valor, com tolerância?expect(0.3 - 0.1).toBeCloseTo(0.2)
toEqualtem o mesmo conteúdo? (objetos e listas)expect(item).toEqual({ id: 1, nome: 'Pão' })
toBeGreaterThané maior que este número?expect(troco).toBeGreaterThan(0)
toContaincontém este pedaço? (texto ou lista)expect(texto).toContain('R$')

toBeCloseTo existe justamente por causa do resto binário: ele compara com uma margem de erro. Usar toBeCloseTo(0.2) faria o teste passar sem consertar a função — o que seria pior, porque esconderia o problema do dinheiro. Comparador não é enfeite: cada escolha diz o que você considera certo.

Missão: a tela é um teste em miniatura: três casos, cada um com o valor esperado. Só um passa, porque a função não arredonda e devolve troco negativo. Conserte calcularTroco para os três passarem.

<script>
  function calcularTroco(pago, preco) {
    return pago - preco;
  }

  let casos = $state([
    { pago: 10, preco: 7.5, esperado: 2.5 },
    { pago: 0.3, preco: 0.1, esperado: 0.2 },
    { pago: 4, preco: 7.5, esperado: 0 }
  ]);

  let certos = $derived(casos.filter((c) => calcularTroco(c.pago, c.preco) === c.esperado).length);
</script>

<p>{certos} de {casos.length} verificações passaram</p>
<script>
  function calcularTroco(pago, preco) {
    return Math.max(0, Math.round((pago - preco) * 100) / 100);
  }

  let casos = $state([
    { pago: 10, preco: 7.5, esperado: 2.5 },
    { pago: 0.3, preco: 0.1, esperado: 0.2 },
    { pago: 4, preco: 7.5, esperado: 0 }
  ]);

  let certos = $derived(casos.filter((c) => calcularTroco(c.pago, c.preco) === c.esperado).length);
</script>

<p>{certos} de {casos.length} verificações passaram</p>

Essa caixa é o Vitest em versão pequena: uma lista de casos com valor esperado e uma contagem de quantos bateram. A diferença é que o Vitest mostra qual caso falhou e com que valores; a caixa mostra só o total. Nos dois, o trabalho é o mesmo: escrever o caso certo antes de consertar.

9. O teste do troco negativo

O terceiro caso da lista acima tem uma decisão de negócio dentro: quando falta dinheiro, o troco é zero, não negativo. Essa regra não estava escrita em lugar nenhum — estava só na cabeça da Ana. Um teste é onde ela fica escrita.

Missão: quem paga 4 por um sonho de 7,50 não tem troco a receber, e a tela mostra -3.50. Faça a função devolver zero quando falta dinheiro.

<script>
  function calcularTroco(pago, preco) {
    return pago - preco;
  }

  let pago = $state(4);
  let preco = $state(7.5);
  let troco = $derived(calcularTroco(pago, preco));
</script>

<p>Troco: R$ {troco.toFixed(2)}</p>
<script>
  function calcularTroco(pago, preco) {
    return Math.max(0, pago - preco);
  }

  let pago = $state(4);
  let preco = $state(7.5);
  let troco = $derived(calcularTroco(pago, preco));
</script>

<p>Troco: R$ {troco.toFixed(2)}</p>

Math.max(0, valor) devolve o maior entre zero e o valor — ou seja, nunca deixa passar número negativo. É mais curto que um if e não tem caminho alternativo para esquecer.

10. Teste não substitui olhar a tela

O teste do módulo confere a conta. Ele não confere que o componente mostra o valor com duas casas, nem que o botão está no lugar. Isso é assunto da próxima aula, mas vale ver a diferença com um componente simples:

<script>
  let pago = $state(10);
  let preco = $state(7.5);
  let troco = $derived(Math.round((pago - preco) * 100) / 100);
</script>

<p>Troco: R$ {troco.toFixed(2)}</p>
<p>Troco: R$ 2.50</p>

O módulo podia estar perfeito e a tela mostrar R$ 2.5 por falta de toFixed. Testes de módulo cuidam da conta; testes de componente cuidam da tela. Um projeto saudável tem os dois, e a ordem natural é começar pelo módulo — é mais fácil, mais rápido e pega a maior parte dos erros.

11. Quando dá errado

As três saídas abaixo vieram das execuções reais desta aula. Repare que todas apontam arquivo e linha, e que o resumo final sempre repete a contagem.

Erro 1 — a expectativa não bateu

O caso mais comum: o código rodou, o valor veio diferente do esperado. O Vitest mostra a diferença lado a lado.

 FAIL  src/lib/troco.test.js > calcularTroco > fecha a conta nos centavos
AssertionError: expected 0.19999999999999998 to be 0.2 // Object.is equality

 Test Files  1 failed (1)
      Tests  1 failed | 1 passed (2)

Leia o expected … to be … como “veio isso, eu esperava aquilo”. A correção pode ser no código (arredondar) ou na expectativa (se ela estava errada) — mas nunca no comparador, a não ser que você saiba exatamente por que.

Erro 2 — arquivo importado não existe

Um erro de digitação no caminho do import impede o arquivo de teste de carregar. Nenhum caso roda, e o resumo diz “no tests”.

 ❯ src/lib/troco.test.js (0 test)

 FAIL  src/lib/troco.test.js [ src/lib/troco.test.js ]
Error: Cannot find module './trocos.js'

 Test Files  1 failed (1)
      Tests  no tests

O 0 test ao lado do nome do arquivo é o sinal: o problema aconteceu antes de qualquer caso. Confira o caminho e a extensão — './troco.js', com s no singular.

Erro 3 — sintaxe inválida no arquivo de teste

Um parêntese a menos e o Vitest nem consegue analisar o arquivo. A mensagem fala de “invalid JS syntax” e aponta a linha 1, porque é ali que a análise começa.

 FAIL  src/lib/troco.test.js [ src/lib/troco.test.js ]
Error: Failed to parse source for import analysis because the content contains invalid JS syntax.
  Plugin: vite:import-analysis
  File: src/lib/troco.test.js:1:0

“Falha ao analisar o arquivo para a análise de imports porque o conteúdo tem sintaxe JavaScript inválida”. A linha 1 é o começo do arquivo, não o erro: procure o parêntese sem par, geralmente na chamada do expect.

Resumo

  • Teste automático é a conferência escrita uma vez, que o computador repete sempre.
  • npm install -D vitest instala só para desenvolvimento; nada vai para o dist/.
  • npx vitest run roda uma vez; npx vitest fica olhando os arquivos.
  • Todo teste tem describe (grupo), it (caso), expect (valor) e um comparador.
  • O arquivo de teste termina em .test.js e fica ao lado do módulo.
  • AssertionError quer dizer “o valor veio diferente do esperado”, não erro de sintaxe.
  • 0.3 - 0.1 dá 0.19999999999999998: arredonde com Math.round(… * 100) / 100.
  • toBe compara valor exato; toBeCloseTo aceita margem; toEqual compara conteúdo.
  • Teste de módulo cuida da conta; teste de componente cuida da tela.
  • Veja o teste falhar de propósito antes de confiar nele.
